# 03 计算机组成与数据表示
## Computer Organization & Data Representation

> [!info]- 章节信息
> **所属方向**：通用基础 ｜ **难度阶段**：L0 预备期 ｜ **前置要求**：[[02-C语言与内存模型|02 C 语言与内存模型]]
> **本章目标**：看懂 CPU 到底在"跑"什么，以及数据在机器里到底长什么样。前者是读汇编的前提，后者是每天处理 CTF 输入输出（进制、位运算、字节序、编码）的常用工具。

## 1. 计算机组成原理非常重要

02 讲的是"数据在内存里怎么排"，这一章再往前推一层，回答两个问题：

- **CPU 是怎么执行程序的**。理解「取指 → 译码 → 执行 → 写回」这个循环，汇编才不是一堆鬼画符，而是这个循环每一步的动作。
- **数据在机器里到底是什么**。机器里只有 0 和 1。进制、位运算、补码、字节序、字符编码你都要会才能做题目。

> [!note] 本节范围
> 不是《计算机组成原理》教材。只有**CTF 会用到的机器层常识**：寄存器、指令周期、存储层次、以及数据的各种表示形式。
> >[!danger] 提醒
> 孩子们好好学，计组是408考研重点。

## 2. CPU 在做什么：指令执行循环

### 2.1 冯·诺依曼结构

现代计算机的骨架：

| 部件 | 作用 |
| ---- | ---- |
| 运算器（ALU） | 做算术与逻辑运算 |
| 控制器（CU） | 取指令、译码、发出控制信号 |
| 存储器 | 存放指令与数据 |
| 输入设备 | 键盘、网卡…… |
| 输出设备 | 显示器、网卡…… |

运算器 + 控制器 = **CPU**；存储器通常指主存（RAM）。

冯·诺依曼结构里最关键的一条是：==指令和数据放在同一个存储器里，形式完全一样，都是二进制==。这正是漏洞利用的哲学基础 —— **只要能让 CPU 把"数据"当成"指令"去执行，就能控制程序**。ret2win、shellcode 注入、栈迁移，本质上都是这个。

### 2.2 指令执行循环

![[03-指令执行循环.svg|563]]

02 里那条 `mov rax, [rbp-0x10]`：

| 步骤 | 具体做什么 |
| ---- | ---------- |
| 取指 Fetch | 从 `RIP` 指向的地址读出一条指令，`RIP` 自动加上这条指令的长度 |
| 译码 Decode | 控制器解析：要做什么操作、操作数在哪里 |
| 执行 Execute | ALU 计算，或访问内存（这里是读 `rbp-0x10` 处的 8 字节） |
| 写回 Writeback | 把结果写进寄存器（这里是写进 `RAX`） |

> [!info] 为什么"控制 RIP"就等于"控制程序"
> 循环的第一步永远是"按 `RIP` 去取指令"。所以只要能让 `RIP` 指向你安排好的数据 —— 栈上的 shellcode、某个函数的地址、一段 `pop rdi; ret` —— CPU 就会照办。==所有控制流劫持类漏洞，都是这个。==

### 2.3 寄存器

寄存器是 CPU 内部速度最快的存储，容量以"个"计。x86_64 常见寄存器：

| 寄存器 | 常见用途 |
| ------ | -------- |
| `RAX` | 累加器，也是函数返回值 |
| `RBX` | 通用，被调用者保存 |
| `RCX` / `RDX` | 通用；`RCX` 常用于循环计数，`RDX` 参与乘除 |
| `RSI` / `RDI` | 通用；x64 下是第 2 / 第 1 个参数 |
| `RSP` | 栈指针，指向栈顶 |
| `RBP` | 帧指针，指向当前栈帧基址 |
| `RIP` | 指令指针，指向下一条要执行的指令 |
| `RFLAGS` | 标志寄存器，存放运算结果的状态位 |

> [!note] 寄存器名是"套娃"
> 同一个物理寄存器按宽度有多个名字：`RAX`（64 位）→ `EAX`（低 32 位）→ `AX`（低 16 位）→ `AL`（低 8 位）/ `AH`（次低 8 位）。
> ==注意 x64 特有的行为：写 `EAX` 会**自动把 `RAX` 的高 32 位清零**。==逆向时看到地址的高 32 位"突然没了"，大概率就是因为这个特性。

`RFLAGS` 里最要紧的几位，直接决定条件跳转走不走：

| 标志 | 含义 | 相关跳转 |
| ---- | ---- | -------- |
| `ZF` | 结果为零 | `je` / `jne` |
| `SF` | 结果为负（最高位为 1） | `js` / `jns` |
| `CF` | 无符号进位 / 借位 | `jb` / `jae` |
| `OF` | 有符号溢出 | `jo` / `jno` |

> [!warning] `cmp` 本身不跳转
> `cmp a, b` 只做一次减法并设置标志位，真正跳转的是紧跟其后的 `jcc`。逆向时看到 `cmp` 别停在那里，==一定要看下面那条跳转用的是哪个标志==，否则很容易把"大于"和"大于等于"搞反。

## 3. 存储层次与地址空间

### 3.1 速度与容量的取舍

![[03-内存层次.svg|563]]

| 层次 | 典型容量 | 典型延迟 | 谁在管 |
| ---- | -------- | -------- | ------ |
| 寄存器 | 几十个 × 8 字节 | < 1 ns | 编译器 |
| L1 缓存 | 32–64 KB | ~1 ns | 硬件 |
| L2 / L3 缓存 | 几 MB – 几十 MB | ~10 ns | 硬件 |
| 主存 RAM | GB 级 | ~100 ns | 操作系统 |
| 磁盘 / SSD | TB 级 | ~100 µs | 操作系统 |

> [!note] 缓存对 CTF 有意义吗
> 没有。这张表你记住"寄存器最快、内存中等、磁盘慢"就行，理解编译器为什么拼命把变量往寄存器里塞 —— 这也解释了 `-O2` 之后为什么"变量不见了"。

### 3.2 虚拟地址空间

每个进程都以为自己独占一整块内存，这就是**虚拟地址空间**：

- 进程用的是**虚拟地址**，CPU 通过**页表**（page table）翻译成**物理地址**；
- 映射以**页**为单位，x86_64 上常见页大小是 **4 KB**；
- 翻译由 MMU（内存管理单元）硬件完成，操作系统负责维护页表。

> [!info] 为什么 PWN 必须懂这个
> - **ASLR 保护的就是虚拟地址**：每次运行，栈、堆、libc 的基址都会变，所以要先泄露地址、再算偏移。
> - **页面权限就是 NX**：02 讲的"段"在映射到页表时会带上权限位，`r-x` 的页可执行、`rw-` 的页不可执行。NX 的实现就是"把栈所在的页标成不可执行"。
> - **调试里看到的地址都是虚拟地址**：GDB 里的 `0x7ffd...` 与真实物理地址没有直接关系。

## 4. 数据在机器里怎么表示

### 4.1 进制

| 进制 | 前缀 / 写法 | 常见用途 |
| ---- | ---------- | -------- |
| 二进制 | `0b` | 位运算、权限位 |
| 八进制 | C 里的 `0` 开头 | `chmod 755` |
| 十进制 | 无前缀 | 日常读写 |
| 十六进制 | `0x` | ==反汇编、hexdump、payload，几乎全是 16 进制== |

常用换算（背下来能省很多事）：

| 十六进制 | 十进制 | 二进制 | 记忆点 |
| -------- | ------ | ------ | ------ |
| `0x10` | 16 | 0001 0000 | |
| `0x40` | 64 | 0100 0000 | |
| `0x7f` | 127 | 0111 1111 | ASCII 可打印字符上限 |
| `0xff` | 255 | 1111 1111 | 1 字节最大值 |
| `0x100` | 256 | 1 0000 0000 | |
| `0x1000` | 4096 | — | 一页 = 4 KB |
| `0x100000` | 1048576 | — | 1 MB |

> [!note] 16 进制为什么好用
> 1 个 16 进制位正好对应 4 个二进制位，所以**1 字节 = 2 个 16 进制位**。`0xdeadbeef` 一眼就是 4 字节，`0x41414141` 一眼就是 `AAAA`。
> ==做 PWN 时看到地址先数位数：8 位 = 32 位地址，12 位 = 64 位地址。==

### 4.2 位运算

| 运算  | 符号   | 例子                          | 典型用途                    |
| --- | ---- | --------------------------- | ----------------------- |
| 与   | `&`  | `0b1100 & 0b1010 = 0b1000`  | 取某些位、掩码                 |
| 或   | `\|` | `0b1100 \| 0b1010 = 0b1110` | 置位                      |
| 异或  | `^`  | `0b1100 ^ 0b1010 = 0b0110`  | 翻转位；XOR 加密、safe-linking |
| 取反  | `~`  | `~0x0 = 0xFFFFFFFF`         | 构造掩码                    |
| 左移  | `<<` | `1 << 4 = 16`               | 乘 2 的幂                  |
| 右移  | `>>` | `16 >> 4 = 1`               | 除 2 的幂                  |

> [!warning] 右移有两种，别搞混
> - **逻辑右移**（无符号数）：高位补 0。
> - **算术右移**（有符号数）：高位补符号位。
>
> 所以 `(int)-8 >> 1 == -4`，而 `(unsigned)-8 >> 1 == 0x7FFFFFFC`。==汇编里 `sar` 是算术右移（补符号位），`shr` 是逻辑右移（补 0），差一个字母，结果天差地别。==

### 4.3 补码：负数怎么存

计算机里**没有减法器**，减法统一用"加一个负数"实现，所以负数必须有一种能和正数一起做加法的表示 —— 这就是**补码**。

| 表示法 | `+1` | `-1` | 说明 |
| ------ | ---- | ---- | ---- |
| 原码 | `0000 0001` | `1000 0001` | 符号位 + 绝对值，有 `+0` / `-0` 两个零 |
| 反码 | `0000 0001` | `1111 1110` | 负数 = 原码按位取反 |
| **补码** | `0000 0001` | `1111 1111` | 负数 = 反码 + 1；==现代计算机统一用这个== |

补码的两个关键性质：

- **取负 = 按位取反再 +1**：`-x == ~x + 1`；
- **`-1` 就是全 1**：所以 `0xFFFFFFFF` 按无符号数是 4294967295，按有符号数就是 `-1`。

> [!warning] 补码带来的两个经典陷阱
> 1. **有符号 / 无符号只是"解释方式"不同**：同一串位 `0xFFFFFFFF`，`int` 看是 `-1`，`unsigned` 看是 4294967295。程序用哪种类型比较，结果完全不同。
> 2. **最小负数的取负还是它自己**：`-INT_MIN == INT_MIN`，因为 `INT_MIN` 的绝对值超出了 `int` 能表示的范围。==看到 `if (x < 0) x = -x;` 这类代码，就要想到 `INT_MIN` 这个绕过点。==

### 4.4 字节序

02 的 7.2 已经讲过 x86 / x64 是**小端序**，这里补两个知识：

| 场景 | 字节序 |
| ---- | ------ |
| x86 / x64 内存 | 小端 |
| 网络传输（TCP/IP） | **大端**（网络字节序） |
| ARM | 默认小端，可切换 |

```python
from pwn import *
p32(0x41424344)                  # b'DCBA' —— 小端打包，按地址升序读内存是 44 43 42 41
p32(0x41424344, endian='big')    # b'ABCD'
```

> [!warning] 两个高频问题
> - **手动拼 payload 把地址写反**（写成了大端）—— 一律用 `p32` / `p64`，不要手拼字节串。
> - **从内存 dump 出 4 字节还原整数时忘了字节序**，把 `44 43 42 41` 读成 `0x44434241` —— 用 `u32()` / `u64()` 还原，不要手动移位。

### 4.5 字符编码

| 编码 | 特点 | 字节长度 | 常见场景 |
| ---- | ---- | -------- | -------- |
| ASCII | `0x00`–`0x7F`，共 128 个 | 1 | 英文与控制字符 |
| Latin-1 | `0x00`–`0xFF` | 1 | 西欧字符 |
| GBK / GB2312 | 中文双字节编码 | 1–2 | 中文 Windows 的遗留文件 |
| UTF-8 | 变长，兼容 ASCII | 1–4 | Linux、网页、现代标准 |
| UTF-16 | 变长 | 2 / 4 | Windows 内部、Java 字符串 |

必背的 ASCII 片段：

| 字节                       | 字符            | 记忆点                                                  |
| ------------------------ | ------------- | ---------------------------------------------------- |
| `0x00`                   | NUL           | ==字符串终止符==                                           |
| `0x09` / `0x0a` / `0x0d` | Tab / LF / CR | 换行相关；`gets`、`scanf` 会在这些字节处截断输入                      |
| `0x20`                   | 空格            |                                                      |
| `0x30`–`0x39`            | `0`–`9`       |                                                      |
| `0x41`–`0x5a`            | `A`–`Z`       |                                                      |
| `0x61`–`0x7a`            | `a`–`z`       | ==`0x61` 就是 `a`，所以 `cyclic` 偏移里全是 `0x6161616c` 这类值== |
| `0x7f`                   | DEL           | ASCII 可打印区上限                                         |

UTF-8 的变长规则（做题经常要手写解码）：

| 字节数 | 首字节模式 | 码点范围 |
| ------ | ---------- | -------- |
| 1 | `0xxxxxxx` | U+0000 – U+007F |
| 2 | `110xxxxx 10xxxxxx` | U+0080 – U+07FF |
| 3 | `1110xxxx 10xxxxxx 10xxxxxx` | U+0800 – U+FFFF |
| 4 | `11110xxx 10xxxxxx ×3` | U+10000 – U+10FFFF |

> [!note] 一眼看出这是不是 UTF-8 中文
> 中文字符在 UTF-8 里通常是 **3 字节**，首字节以 `1110` 开头（即 `0xE0`–`0xEF`），后两字节都以 `10` 开头（`0x80`–`0xBF`）。==hexdump 里看到 `e4 b8 ad` 这种"E 打头 + 两个 8/9/A/B 打头"的三连，基本就是中文（`e4 b8 ad` 正是"中"字）。==

### 4.6 常见编码转换

| 编码         | 特征                                | 工具                      |
| ---------- | --------------------------------- | ----------------------- |
| Base64     | 字符集 `A–Z a–z 0–9 + /`，末尾常有 `=` 填充 | `base64` 命令、CyberChef   |
| Base32     | 只用 `A–Z` 和 `2–7`，填充多              | 同上                      |
| Hex        | 只含 `0–9 a–f`，长度必为偶数               | `xxd`、`bytes.fromhex()` |
| URL 编码     | `%` + 两个 16 进制位                   | `urllib.parse.quote`    |
| ROT13 / 凯撒 | 位移后仍是字母                           | 手写脚本                    |

```bash
echo -n "flag{test}" | base64        # 编码 → ZmxhZ3t0ZXN0fQ==
echo "ZmxhZ3t0ZXN0fQ==" | base64 -d  # 解码 → flag{test}
echo -n "abc" | xxd -p               # 转 hex → 616263
```

> [!info] 先认出来，再谈解码
> CTF 编码题 90% 卡在"认出这是什么编码"。判断顺序：**字符集 → 长度特征 → 填充符**。全是 `A–Z a–z 0–9 + / =` 且长度是 4 的倍数 → Base64；只有 `0–9 a–f` → Hex；出现 `%` → URL 编码。

## 5. 常见问题

| 现象 | 原因与解决 |
| ---- | ---------- |
| `0x` 开头的地址数不清是几位 | 1 字节 = 2 个 16 进制位；8 位 = 32 位地址，12 位 = 64 位地址 |
| 从内存 dump 出的字节还原成整数不对 | 忘了小端序，用 `u32()` / `u64()`，不要手动移位 |
| 打包 payload 后地址反了 | 手拼字节串导致，改用 `p32` / `p64` |
| 有符号与无符号比较结果诡异 | 同一串位按不同类型解释的结果不同，注意隐式类型转换 |
| `-INT_MIN` 还是负数 | 补码最小负数取负会溢出，是经典绕过点 |
| `sar` 和 `shr` 分不清 | `sar` 补符号位（算术右移），`shr` 补 0（逻辑右移） |
| 中文乱码、字节数对不上 | 编码不一致（UTF-8 中文 3 字节，GBK 2 字节），先确认编码 |
| 输入被莫名截断 | 撞上了 `0x00`（NUL）、`0x0a`（换行）等终止字节，常见于 `gets` / `strcpy` |
| 汇编里地址高 32 位突然变成 0 | 写入 32 位寄存器（如 `EAX`）会清零 64 位寄存器的高半部分 |
