## 1. 分层模型：一个请求出门要套几层壳

[[06-Python与CTF脚本基础#4. 文件与网络 IO|06 章]]留过一个问题：「TCP 是什么？看我心情写不写单独文章」。心情到位了，就是这一章。==孩子们，计算机网络必学哦==

先回答最基本的问题：网络为什么要分层。因为「把一串字节从 A 机送到 B 机」拆开全是杂活——应用只管内容说了什么，传输管送到没、按序没，网络管走哪条路，链路管这一跳的下一站是谁。杂活分层干，每层只跟上下两层说话，出了故障才知道该骂谁。

寄快递是现成的比喻：合同文本是应用层内容，快递单号和保价承诺是传输层的可靠性保障，分拣路线是网络层的路由，最后一公里那辆电驴是链路层。你不需要懂电驴的品牌，快递员也不需要读懂合同。

一个 HTTP 请求从浏览器出门，每过一层就被套一层壳（封装），到对端再逐层剥掉（解封装）：

```
应用层  HTTP 报文      "GET / HTTP/1.1 ..."           管内容说了什么
传输层  + TCP 头       源端口 42164 → 目的端口 8000     管找进程、管可靠
网络层  + IP 头        源 IP → 目的 IP                 管跨网络找主机
链路层  + 帧头帧尾     MAC 地址                        管这一跳的下一跳
```

==每层只干一件事、只认识相邻两层，这是互联网还没散架的唯一原因==。学的时候倒着来一遍：抓包软件里看到一个包，从链路层往上逐层剥，就是一次完整的解封装。

CTF 三个方向各盯哪层：

| 方向 | 盯的位置 | 日常动作 |
| ---- | -------- | -------- |
| PWN | 应用层之上的进程 | 连上端口直接跟程序对话，[[06-Python与CTF脚本基础#5. pwntools 骨架\|06 章]]的 `remote()` 干的就是这个 |
| Web | 应用层 HTTP | 在报文里找注入点、改包绕权限 |
| MISC | 全栈 | 从帧到报文逐层还原流量包，谁的 payload 都跑不掉 |

==PWN 盯进程，Web 盯 HTTP，MISC 流量分析盯全栈==——地基是同一套，本章讲完三个方向都受用。

> [!note] 几层的定义
> OSI 七层模型，OSI为国际标准，然而因为一些原因，我们实际并未使用，而是使用TCP/IP 四层（链路/网络/传输/应用）。在我们实际教学中，我们一般性使用五层来教学。==依旧 408 考研重点==。

## 2. IP 与端口：门牌与房号

IP 地址定位机器，端口定位机器上的进程。快递只写小区名到不了家，得写到几零几——端口就是那个几零几。

- 端口号 0-65535，16 位。0-1023 是知名端口（22 SSH、80 HTTP、443 HTTPS），绑定要 root；CTF 靶机爱用大端口（8000、1337、8888），随便绑。
- ==IP:端口 四元组决定一条 TCP 连接==。`127.0.0.1:8000` 和 `192.168.1.5:8000` 是两个不同的地址，哪怕在同一台机器上。

两个特殊地址，起靶机服务前必须懂：

| 地址 | 名字 | 含义 | 什么时候用 |
| ---- | ---- | ---- | ---------- |
| `127.0.0.1` | 回环地址 | 数据不出网卡，本机跟自己玩 | 只给自己用的服务 |
| `0.0.0.0` | 通配地址 | 绑全部网卡，谁来都接 | 靶机要给别人访问时 |

`python3 -m http.server` 默认绑 `0.0.0.0`，效果是整个局域网都能下载你目录下的文件——临时共享资料很好用。只想自己用就补 `--bind 127.0.0.1`。

看本机连接状态的命令是 `ss -tan`（`-t` 只看 TCP、`-n` 不解析域名、`-a` 连未建立的也看），01 装系统时就有。实拍（==节选，当时本机还挂着我没杀干净的演示服务，勿学==）：

```
State     Recv-Q Send-Q  Local Address:Port  Peer Address:Port 
LISTEN    0      1000   10.255.255.254:53         0.0.0.0:*    
LISTEN    0      4096    127.0.0.53%lo:53         0.0.0.0:*    
LISTEN    0      5           127.0.0.1:9001       0.0.0.0:*    
TIME-WAIT 0      0           127.0.0.1:8001     127.0.0.1:44916
```

State 列的 LISTEN 是「端口上蹲着个进程等连接」，其他状态下一节全是重点。

## 3. TCP：三次握手与四次挥手

TCP（传输控制协议）的活就一句话：把字节流可靠、按序地送到对面。手段也一句话：==序号 + 确认 + 超时重传==——每个字节有编号，收到要回执，超时没回执就重发。拥塞控制、滑动窗口那些，做题用不上，考研再战。

### 3.1 三次握手

```
客户端                     服务端
  | ------- SYN -------->   |    我要连你，初始序号 x
  | <----- SYN+ACK ------   |    收到，我的初始序号 y
  | ------- ACK -------->   |    你的序号也收到了
```

为什么不是两次？==三次的本质：双方各确认一次「我能发、你能收」==。

- 客户端发 SYN：服务端确认了「客户端能发、自己能收」
- 服务端回 SYN+ACK：客户端确认了「双方收发都行」——到这里其实已经够通信了
- 客户端再回 ACK：服务端这才确认「自己能发、客户端能收」

两次的问题出在服务端信息不全：它发出 SYN+ACK 就单方面认为连接建好，可这个包要是在网络里迷路又迟到，客户端早就不想连了，服务端却守着一个根本不会有人说话的连接干等资源——历史旧连接问题，SYN Flood 半连接攻击打的也是这个软肋。第三次握手把「要不要这段对话」的决定权交回给真正想说话的一方。

### 3.2 四次挥手与 TIME_WAIT

TCP 全双工，两个方向独立关闭，所以断开要四个包：

```
主动方                     被动方
  | ------- FIN -------->   |    我说完了
  | <----- ACK ----------   |    知道了（我可能还没说完）
  | <----- FIN ----------   |    我也说完了
  | ------- ACK -------->   |    好
  [ 主动方等 2MSL 后才真正关闭 ]
```

主动关的那方最后停在 ==TIME_WAIT==，等 2MSL（报文最大生存时间的两倍，Linux 实际 60 秒）才消失。用途有二：最后的 ACK 丢了还能补发；让旧连接的残留包在网络里自然死亡，免得污染复用同四元组的新连接。

### 3.3 把状态机亲手跑一遍

光看图记不住，写个最小 socket 服务端+客户端，边跑边用 ss 盯状态（`socket_demo.py` 全文，就是实跑这份）：

```python
import socket, subprocess, time, threading

def ss_lines():                    # 抓 ss -tan 里带 9001 的行
    out = subprocess.run(['ss', '-tan'], capture_output=True, text=True).stdout
    hits = [l for l in out.splitlines() if ':9001' in l]
    return '\n'.join(hits) or '(nothing on 9001)'

srv = socket.socket()
srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
srv.bind(('127.0.0.1', 9001))
srv.listen(1)
print('[server] bind + listen 127.0.0.1:9001')
print('== ss ==')
print(ss_lines())

def client_job():
    time.sleep(0.5)
    c = socket.socket()
    c.connect(('127.0.0.1', 9001))
    c.sendall(b'ping')
    print('[client] connect + send ping')
    print('== ss ==')
    print(ss_lines())
    time.sleep(0.8)
    print('[client] recv ->', c.recv(1024).decode())
    c.close()                      # 客户端先关
    print('[client] close()')

t = threading.Thread(target=client_job)
t.start()

conn, addr = srv.accept()
print('[server] accept <-', addr)
data = conn.recv(1024)
print('[server] recv ->', data.decode())
conn.sendall(b'pong: ' + data)
t.join()
time.sleep(0.2)                    # 拖一下，让客户端先进 FIN 流程
print('== ss ==')
print(ss_lines())
conn.close(); srv.close()
time.sleep(1.5)
print('== ss, 1.5s later ==')
print(ss_lines())
```

实测输出（服务端/客户端两个线程的打印交错出现，是真实调度结果）：

```
[server] bind + listen 127.0.0.1:9001
== ss ==
LISTEN     0      1                127.0.0.1:9001       0.0.0.0:*
[client] connect + send ping
== ss ==
[server] accept <- ('127.0.0.1', 44550)
[server] recv -> ping
LISTEN     0      1                127.0.0.1:9001       0.0.0.0:*
ESTAB      0      0                127.0.0.1:9001     127.0.0.1:44550
ESTAB      10     0                127.0.0.1:44550    127.0.0.1:9001
[client] recv -> pong: ping
[client] close()
== ss ==
LISTEN     0      1                127.0.0.1:9001       0.0.0.0:*
CLOSE-WAIT 1      0                127.0.0.1:9001     127.0.0.1:44550
FIN-WAIT-2 0      0                127.0.0.1:44550    127.0.0.1:9001
== ss, 1.5s later ==
TIME-WAIT  0      0                127.0.0.1:44550    127.0.0.1:9001
```

四张快照对应四段：

1. `listen()` 之后：LISTEN，等连接。
2. 握手完成：两条 ESTAB。客户端那行 Recv-Q=10——`pong: ping` 这 10 个字节已经到了内核接收缓冲区，应用还没来 `recv`，==Recv-Q/Send-Q 就是这么个「内核收了/发了但应用还没过手」的计数器==。
3. 客户端先 `close()`：客户端发完 FIN 进 FIN-WAIT-2，等服务端也关；服务端收到 FIN 但应用还没调 close，进 CLOSE-WAIT。==一堆 CLOSE-WAIT 挂在 ss 里 = 服务端代码忘了 close==，运维面经典送分题。
4. 服务端也 close 之后：客户端进 TIME_WAIT，60 秒自动消失，最后一行快照里只剩它。

### 3.4 nc：连的就是裸 TCP

[[01-Linux环境与CTF实验环境搭建|01 章]]装过 nc（netcat），现在能说清它到底是什么了：==nc 不封装任何应用层协议，连上端口就把 stdin 原样扔进 TCP，收到的字节原样吐到 stdout==——TCP 的一张人肉网卡。

```bash
nc -lvp 1337              # 终端一：本机监听 1337（服务端）
nc 127.0.0.1 1337         # 终端二：连过去（客户端）
# 两边互打的每一行，就是这条 TCP 连接里流动的原始字节
```

PWN 远程题 `nc 1.2.3.4 1337` 连上的就是个监听端口的进程；Web 的 80 端口后面蹲的也是，只是它说的方言叫 HTTP。下一节就逼它说人话。

## 4. UDP：发完就跑

| 维度 | TCP | UDP |
| ---- | --- | --- |
| 连接 | 三次握手 | ==无连接==，拿地址就发 |
| 可靠性 | 确认+重传，不丢不乱 | 尽力而为，丢了就没了 |
| 有序性 | 严格按序送达 | 不保证 |
| 头部开销 | 20 字节起步 | 8 字节 |
| 典型场景 | HTTP、SSH、PWN 远程交互 | DNS、直播、游戏 |

UDP 把 IP 的不可靠原样暴露给应用，换来低延迟：不握手、不确认、不重传。丢包？上层自己看着办。

DNS 是 UDP 的招牌客户：查一次域名就是一个包问、一个包答，0.05 秒完事。改走 TCP 的话光握手就三个包，比查询本身还重——而 DNS 答案丢了重问一次毫无心理负担。==一问一答、丢了重问不心疼的流量，UDP 永远更划算==。MISC 流量题里，53 端口的 DNS 查询也是常见的藏货点（子域名、外带数据都爱走它）。

## 5. HTTP：把报文逐段拆开

HTTP 是明文文本协议，对新手最大的善意就在这：==看得懂字就看得懂 HTTP==。

### 5.1 起服务，看一次真实往返

```bash
mkdir www && echo '<h1>hello ctf</h1>' > www/index.html
python3 -m http.server 8000 --bind 127.0.0.1 --directory www
```

另开终端用 `curl -v` 发请求（本机环境有代理劫持，加了 `--noproxy '*'`；没配代理的环境可省）：

```bash
curl -v --noproxy '*' http://127.0.0.1:8000/
```

实测输出（进度条行已删）：

```
*   Trying 127.0.0.1:8000...
* Established connection to 127.0.0.1 (127.0.0.1 port 8000) from 127.0.0.1 port 42164
* using HTTP/1.x
> GET / HTTP/1.1
> Host: 127.0.0.1:8000
> User-Agent: curl/8.18.0
> Accept: */*
> 
* Request completely sent off
* HTTP 1.0, assume close after body
< HTTP/1.0 200 OK
< Server: SimpleHTTP/0.6 Python/3.14.4
< Date: Sun, 18 Oct 2026 12:35:24 GMT
< Content-type: text/html
< Content-Length: 19
< Last-Modified: Sun, 18 Oct 2026 12:35:22 GMT
< 
<h1>hello ctf</h1>
```

curl 用 `>` 标我方发出、`<` 标对方发回。对着原文拆结构——

请求报文（`>` 部分）：

```
GET / HTTP/1.1            ← 起始行：方法 路径 版本
Host: 127.0.0.1:8000      ← 头部：一组 key: value
User-Agent: curl/8.18.0
Accept: */*
                          ← 空行：头到此为止（必须有）
（请求体，GET 一般没有）      ← POST 的参数住这里
```

响应报文（`<` 部分）：

```
HTTP/1.0 200 OK           ← 状态行：版本 状态码 短语
Server: SimpleHTTP/0.6 Python/3.14.4
Content-type: text/html
Content-Length: 19
                          ← 空行
<h1>hello ctf</h1>        ← 响应体，浏览器渲染的就是它
```

==起始行、头、空行、体，四段式==。空行是头和体的分界，手工构造报文忘打空行，服务器就一直等你把头说完。顺带注意 `Host` 头：一台服务器挤着很多网站，靠它决定把请求交给谁——Web 方向的 Host 头注入就是在这动了心思。

### 5.2 方法表：对资源干什么

| 方法      | 语义         | CTF 用途                  |
| ------- | ---------- | ----------------------- |
| GET     | 读资源        | 拿页面、带参数探测（`?id=1`）      |
| POST    | 提交数据       | 登录、上传、塞 payload         |
| HEAD    | 只响应头不要体    | 探测文件存在与否，省流量            |
| PUT     | 上传/替换资源    | 服务器放行 PUT ≈ 可能直接写 shell |
| DELETE  | 删除资源       | 危险操作探测                  |
| OPTIONS | 问服务器支持什么方法 | 打靶前的例行侦察                |

OPTIONS 值得养成习惯：碰上 Web 靶机先问一嘴支持哪些方法，服务器自己交代攻击面。

### 5.3 状态码：服务器的态度

| 分类 | 含义 | CTF 高频 |
| ---- | ---- | -------- |
| 1xx | 收到，继续说 | 101 协议升级（WebSocket） |
| 2xx | 成功 | ==200== OK |
| 3xx | 重定向 | 301 永久搬家 / ==302== 临时跳转 |
| 4xx | 客户端的错 | 400 请求本身烂 / ==403== 禁止 / ==404== 没有 |
| 5xx | 服务器的错 | ==500== 内部炸了 |

两条 CTF 视角注解。302 会配 `Location` 头指路，==但 302 的响应体照样存在==——有的靶机把 flag 藏在跳转响应体里，浏览器自动跳走了你看不见，curl 默认不跟跳你才看得见（`curl -L` 才跟随）。403 和 404 的区别是「有但不让看」和「没有」，==404 有时是 403 的马甲==，换方法换路径多敲一次。

实测两个非 200。POST 一个 `http.server` 不支持的方法：

```
> POST / HTTP/1.1
> Host: 127.0.0.1:8000
> Content-Length: 10
> Content-Type: application/x-www-form-urlencoded
> 
< HTTP/1.0 501 Unsupported method ('POST')
< Server: SimpleHTTP/0.6 Python/3.14.4
```

请求不存在的路径：

```
> GET /no_such_file HTTP/1.1
> Host: 127.0.0.1:8000
> 
< HTTP/1.0 404 File not found
```

501 是「这方法我不干」，404 是「这路径我没有」。`http.server` 是个只读文件分发器，==从来不是合法的测试后端==，收 POST 的活要自己写（第 6 节就是现成模板）。

### 5.4 nc 手发原始 HTTP

明文协议 nc 就能对话。保持 8000 在跑，手工把报文灌进去：

```bash
printf 'GET /index.html HTTP/1.1\r\nHost: 127.0.0.1:8000\r\nConnection: close\r\n\r\n' | nc 127.0.0.1 8000
```

实测输出：

```
HTTP/1.0 200 OK
Server: SimpleHTTP/0.6 Python/3.14.4
Date: Sun, 18 Oct 2026 12:35:24 GMT
Content-type: text/html

<h1>hello ctf</h1>
```

没有浏览器没有 curl，字节进字节出——==所谓「发 HTTP 请求」，本质就是往 TCP 连接里写文本==。Burp Suite 的拦截重放干的是同一件事，套了层 GUI 而已。手撕报文两次，对 Web 的手感就超过一票只会点按钮的人。两个细节：行尾必须 `\r\n`（HTTP/1.1 规定），结尾空行必须真空一行；服务器拿 HTTP/1.0 回话是它自己的选择，两边版本不一致不犯法。

## 6. Cookie 与 Session：给无状态的 HTTP 装记忆

HTTP 无状态：服务器记不住上一个请求是谁发的，每次都得自报家门。总不能逛个购物网站每点一下都重新登录，于是有了 Cookie：

1. 服务器响应时带 `Set-Cookie` 头，要求浏览器存张小纸条
2. 浏览器之后每次访问同一站点，自动带上 `Cookie` 头
3. 服务器读小纸条认人

Session 是加强版：登录态、购物车这些数据存在==服务器端==，Cookie 只带一把钥匙（session id）。==Cookie 是证件，Session 是前台登记簿，证件上只印编号==——编号丢了可以挂失，证件被抄就是被冒名。

写个 20 行服务器实测（`cookie_srv.py` 全文）：

```python
from http.server import BaseHTTPRequestHandler, HTTPServer

class H(BaseHTTPRequestHandler):
    def do_GET(self):
        if self.path == '/set':
            self.send_response(200)
            self.send_header('Set-Cookie', 'session=ctf12345; Path=/')
            self.send_header('Content-Type', 'text/plain; charset=utf-8')
            self.end_headers()
            self.wfile.write('cookie 已发放'.encode())
        elif self.path == '/get':
            cookie = self.headers.get('Cookie', '(no Cookie header)')
            body = f'服务器收到 Cookie 头: {cookie}'.encode()
            self.send_response(200)
            self.send_header('Content-Type', 'text/plain; charset=utf-8')
            self.send_header('Content-Length', str(len(body)))
            self.end_headers()
            self.wfile.write(body)

HTTPServer(('127.0.0.1', 8001), H).serve_forever()
```

四步验证（本机环境有代理劫持，实测同样加了 `--noproxy '*'`，下述命令里省去不写）：

```bash
curl -si http://127.0.0.1:8001/set            # 裸访问，看 Set-Cookie
curl -s -c jar.txt http://127.0.0.1:8001/set  # -c 把 Cookie 存进 jar.txt
curl -s http://127.0.0.1:8001/get             # 不带 Cookie 访问
curl -s -b jar.txt http://127.0.0.1:8001/get  # -b 带上 Cookie 访问
```

实测输出：

```
HTTP/1.0 200 OK
Server: BaseHTTP/0.6 Python/3.14.4
Date: Sun, 18 Oct 2026 12:48:00 GMT
Set-Cookie: session=ctf12345; Path=/
Content-Type: text/plain; charset=utf-8

cookie 已发放
```

```
# jar.txt 的正文行（curl 的 cookie 罐格式）
127.0.0.1	FALSE	/	FALSE	0	session	ctf12345
```

```
服务器收到 Cookie 头: (no Cookie header)
服务器收到 Cookie 头: session=ctf12345
```

服务器一句 `Set-Cookie`，客户端存进罐子，之后每个请求自动回带——==所谓登录态，就是 jar.txt 里那一行==。CTF Web 的 Cookie 伪造题从这来：抓包把 `session=guest` 改成 `session=admin` 试试，出题人要是没做签名没做加密，你就登进去了。这行字值一道 100 分的入门题。

## 7. HTTPS/TLS：给明文穿盔甲

HTTP 明文裸奔，同 WiFi 下任何人都能看你的密码、改你的响应、冒充网站。TLS（传输层安全）怼的就是这三件事：==窃听、篡改、冒充==。（~~其实依旧根本不安全~~）

HTTPS = HTTP over TLS：先建 TCP，再跑一次 TLS 握手，之后 HTTP 报文整体加密。握手概览：

1. 客户端：我会这些加密套件，亮证书（Client hello）
2. 服务器：证书拿好 + 选定套件（Server hello / Certificate / Server key exchange）
3. 客户端拿证书对照本机 CA 信任库验签，用证书里的公钥参与算出会话密钥（Client key exchange）
4. 双方互发 Finished 校验密钥一致，之后全程==对称加密==

==非对称加密（证书里的公钥）只负责验身份、换钥匙，扛流量的是对称加密==——非对称算法太慢，扛不动网页这种吞吐量。套件名 `ECDHE-RSA-AES128-GCM-SHA256` 的读法：ECDHE 换钥匙，RSA 验身份，AES128-GCM 干粗活。

`curl -v` 能看完整握手。实测 `curl -sv https://www.baidu.com`（本机走了代理，开头的 CONNECT 隧道一并保留——顺便白嫖个冷知识：代理转发 HTTPS 用的就是 HTTP 的 CONNECT 方法）：

```
* Establish HTTP proxy tunnel to www.baidu.com:443
> CONNECT www.baidu.com:443 HTTP/1.1
> Host: www.baidu.com:443
> User-Agent: curl/8.18.0
> Proxy-Connection: Keep-Alive
> 
< HTTP/1.1 200 Connection established
* CONNECT tunnel established, response 200
* TLSv1.3 (OUT), TLS handshake, Client hello (1):
* TLSv1.3 (IN), TLS handshake, Server hello (2):
* TLSv1.2 (IN), TLS handshake, Certificate (11):
* TLSv1.2 (IN), TLS handshake, Server key exchange (12):
* TLSv1.2 (IN), TLS handshake, Server finished (14):
* TLSv1.2 (OUT), TLS handshake, Client key exchange (16):
* TLSv1.2 (OUT), TLS handshake, Finished (20):
* TLSv1.2 (IN), TLS handshake, Finished (20):
* SSL connection using TLSv1.2 / ECDHE-RSA-AES128-GCM-SHA256
* Server certificate:
*   subject: C=CN; ST=Beijing; L=Beijing; CN=baidu.com
*   start date: Jul  9 02:32:55 2026 GMT
*   expire date: Jan 24 02:32:55 2027 GMT
```

（开头的代理环境变量声明行、每条消息后面的 `[N bytes data]` 字节数行，以及证书的剩余字段已省略。）括号里的编号就是握手消息类型，跟上面四步一一入座。证书 subject 写着 baidu.com，客户端拿本地 CA 库验签通过才继续——==验签不过直接拒连，拦「冒充」就拦在这==。

> [!warning] 为什么抓 HTTPS 全是密文
> 抓包工具看到的 TLS 记录全是加密字节。Burp/Charles 能看明文，是因为你亲手装了它们的根证书，让流量从中间过一手——==同一套机制，正着用叫安全，反着用叫中间人攻击==。Web 方向会天天用这招，先记下原理。

## 8. DNS：域名变 IP

人记域名，网络认 IP，DNS 站中间翻译。一句话过程：==你的机器向本地 DNS 服务器发递归查询（只要答案，别让我管过程），它要么自己知道，要么替你按 根 → 顶级域 → 权威服务器 一路问过去（这部分叫迭代查询，每级只肯指路）==，最后把 IP 递回来。全程毫秒级，用户无感。

本机没装 dig、nslookup（`which` 探测过），用 Python 的 `getaddrinfo` 实测——它是各语言「域名变地址」的底层入口，`socket.connect(('域名', 端口))` 内部走的就是它：

```python
import socket

for af, st, proto, canon, sa in socket.getaddrinfo('www.baidu.com', 443, proto=socket.IPPROTO_TCP):
    print(af.name, sa[0])
print(socket.gethostbyname('localhost'))
```

实测输出：

```
AF_INET 28.0.0.35
AF_INET6 2001:2::26
127.0.0.1
```

这份输出比想象的有意思：`www.baidu.com` 解析出 `28.0.0.35` 和 `2001:2::26`，都不是百度的真身——==因为我挂着代理软件，它的 DNS 把所有外部域名重写成假地址（fake-ip 手法）==，好让流量都从它那儿过。curl 打开百度一切正常，因为真实解析由代理在远端完成。

这件小事就是本节最要紧的知识点：==DNS 应答没有任何强制校验，链路上的谁都能改它==。hosts 文件能盖过 DNS，路由器 DNS 被劫持能把人导去假银行站。MISC 里「从 DNS 流量里挖隐藏信息」的题、渗透里的 DNS 隧道，吃的都是这个饭。

> [!note] 想要「真」解析结果
> `getent hosts 域名` 可用；指定公共 DNS 查询需要 dig/nslookup（`apt install dnsutils`）。在 WSL 里做 DNS 实验前，先搞清本机 DNS 是不是已经被改写了。

## 9. Wireshark 初见：抓包就是全栈透视

前面八节把四层拆开讲，Wireshark 都能查看：时间戳、源目 IP、端口、协议、TCP 标志位、HTTP 明文，一行一个包。==抓包=全栈透视==，MISC 流量分析的全部工作都长在这个视角上。

安装：

```bash
sudo apt install wireshark      # Linux；询问「允许非 root 用户抓包」选 yes
# Windows 官网下安装包，GUI 的 Wireshark 和命令行的 tshark 一起到手
```

本节给标准用法和过滤语法速查，界面实操留给流量分析专章（[[12-隐写与流量取证|12 章]]）展开。

显示过滤器速查（注意这叫显示过滤，跟抓包过滤的 BPF 语法是两套东西）：

| 过滤式 | 作用 |
| ------ | ---- |
| `http` | 只看 HTTP |
| `tcp.port == 1337` | 只看 1337 端口的 TCP |
| `ip.addr == 1.2.3.4` | 涉及该 IP 的所有包 |
| `tcp.stream eq 0` | 第 0 条 TCP 流的全部包 |
| `http.request.method == "POST"` | 只看 POST |
| `dns` | 只看 DNS |

CTF 流量题标准起手式：

1. 打开 `.pcap/.pcapng`，先看 **Statistics → Protocol Hierarchy**：出题人把货埋在哪个协议，占比直接现形
2. 显示过滤锁定可疑流：`http`、`tcp.port == 8888`、`ftp`……
3. 右键 → **Follow → TCP Stream**：==把一条 TCP 连接的双向字节按顺序拼回原文==，聊天记录、上传的文件、flag 通常直接躺在这
4. **File → Export Objects → HTTP** 一键抠出流量里传过的所有文件

==Follow TCP Stream 是流量题的第一生产力==，一半入门题到这一步就交卷了。USB 键盘流量、蓝牙、TLS 密钥日志那些花活全是它的变体，后面的流量分析专章再收拾。

## 10. 常见问题

| 现象 | 原因与解决 |
| ---- | ---------- |
| curl 连 127.0.0.1 却显示 `Trying 127.0.0.1:7897` | 环境变量 `http_proxy` 在劫持；`no_proxy` 里写的 `127.*` 通配 curl 不认。加 `--noproxy '*'`（本章实测踩到，第 5 节就是这么跑出来的） |
| `OSError: [Errno 98] Address already in use` | 端口被没退干净的服务占着：`ss -tanp` 配 `grep 8000` 找 PID 再 kill；写服务端记得加 `SO_REUSEADDR` |
| http.server 收到 POST 回 501 | 它只是只读文件分发器，不是后端框架；要收 POST 照第 6 节的 `BaseHTTPRequestHandler` 自己写 |
| ss 里一堆 TIME-WAIT，慌 | 正常现象，主动关闭方 60 秒的遗产，自动消失，kill 不掉也不用 kill |
| curl 卡住半天没动静 | 在等一个永远不来的响应，或被代理吊住；加 `--max-time 10`，配 `-v` 看卡在哪一步 |
| `curl -v` 的 `>`/`<` 明细重定向后消失 | `-v` 详情走 stderr，`2>&1` 合流再存文件 |
| nc 手发 HTTP 石沉大海 | 行尾用了 `\n`（规定 `\r\n`）、忘了结尾空行、或没带 `Connection: close`，服务器还等你下一句 |
| 浏览器打不开 `127.0.0.1:8000` | 先 `ss -tan` 配 `grep 8000` 确认 LISTEN 在不在；服务绑了 `127.0.0.1` 时别的机器连不进来，要给别人访问绑 `0.0.0.0` |
| WSL 起的服务 Windows 侧访问不了 | WSL2 的 localhost 转发默认单向（Windows→WSL 通）；反向要镜像网络或用 WSL 的 IP，环境细节回看 [[01-Linux环境与CTF实验环境搭建\|01 章]] |
| DNS 解析出 28.x、2001:2::x 这类怪地址 | 本地 DNS 被代理/安全软件改写（fake-ip），不是玄学是有人在中间，对照第 8 节实测 |
| 没有图形界面也想抓包 | `apt install tshark`，`tshark -i lo -f "port 8000"` 抓、`-Y "http"` 过滤，语法与 GUI 显示过滤同源 |
