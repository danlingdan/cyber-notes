## Steganography, Forensics & Traffic Analysis

## 1. MISC 解题总流程：先验身份证

[[08-编码与古典密码|08 章]]处理的是明面上的字符。MISC 的另一半战场是一坨二进制：图片、压缩包、音频、流量包、磁盘镜像。出题人最爱干的事，是把 A 东西塞进 B 容器，图片尾上粘个压缩包，或者往音频频谱里画一面摩斯电码旗，都算基本操作。你的全部任务浓缩成一句话：

==MISC 解题 = 识别文件真身 → 按容器类型选套路 → 层层剥离==

拿到附件，第一件事永远是这两条命令：

```bash
file misc.zip          # 问 file：这到底是什么
xxd misc.zip | head    # 亲自看前几行字节
```

后缀名只是文件名里的一串字符，改成 `.exe` 也不用动文件一个字节。`file` 不看后缀，它读内容、查魔数表，然后报出真身。==后缀会骗人，魔数不会==。

真身认完，按类型对号入座：

| 真身 | 套路 | 工具 |
| ---- | ---- | ---- |
| 图片 | 看尾部夹带 → EXIF → LSB → 口令隐写 | xxd、exiftool、stegsolve、steghide |
| 压缩包 | 试弱口令 → 查伪加密 → 爆破/明文攻击 | unzip、ARCHPR、bkcrack |
| 流量包 | 协议统计 → Follow Stream → 导出对象 | Wireshark、tshark |
| 四不像 | strings 扫可见串 → binwalk 分离嵌套文件 | strings、binwalk、foremost |

strings 有时候一步到位。实测（STORED 方式打包、未加密的 zip）：

```bash
strings normal.zip | head -3
```

```
R]FIP
flag.txtflag{not_really_encrypted}PK
R]FIP
```

flag 明晃晃躺在文件名旁边。碰到"看不出是什么"的附件，先 strings 一遍再谈别的。成本一秒钟，收益经常是整个 flag。

## 2. 文件格式与魔数

### 2.1 魔数速查表

魔数（magic number）= 文件开头几个约定俗成的字节。[[03-计算机组成与数据表示|03 章]]说过磁盘上只有字节序列，所谓"格式"，就是解析器按这几个字节认亲。

| 格式   | 文件头                                                 | 文件尾                    |
| ---- | --------------------------------------------------- | ---------------------- |
| PNG  | `89 50 4E 47 0D 0A 1A 0A`                           | IEND 块 + `AE 42 60 82` |
| JPEG | `FF D8 FF`                                          | `FF D9`                |
| GIF  | `47 49 46 38 39 61`（GIF89a，87a 同理）                  | `3B`                   |
| ZIP  | `50 4B 03 04`（本地头）                                  | `50 4B 05 06`（EOCD）    |
| RAR  | `52 61 72 21 1A 07`（后跟 `00`=RAR4 / `01 00`=RAR5）    | —                      |
| 7Z   | `37 7A BC AF 27 1C`                                 | —                      |
| PDF  | `25 50 44 46 2D`（`%PDF-`）                           | `%%EOF`                |
| BMP  | `42 4D`（`BM`）                                       | —                      |
| WAV  | `52 49 46 46 ?? ?? ?? ?? 57 41 56 45`（RIFF....WAVE） | —                      |
| MP3  | `49 44 33`（ID3）或 `FF FB`/`FF F3`/`FF F2`            | —                      |
| pcap | `D4 C3 B2 A1` / `A1 B2 C3 D4`（大小端两种）                | —                      |


样本全部用 Python 现场生成（造一个最小合法文件比下载快），跑 `file`：

```bash
file test.png test.gif test.jpg test.pdf test.rar test.zip t.7z t.pcap t.wav t.mp3
```

实测输出：

```
test.png: PNG image data, 8 x 8, 8-bit/color RGB, non-interlaced
test.gif: GIF image data, version 89a, 1 x 1
test.jpg: JPEG image data, JFIF standard 1.01, aspect ratio, density 1x1, segment length 16
test.pdf: PDF document, version 1.4
test.rar: RAR archive data, v5
test.zip: Zip archive data (empty)
t.7z:     7-zip archive data, version 0.0
t.pcap:   pcap capture file, microsecond ts (little-endian) - version 2.4 (Ethernet, capture length 65535)
t.wav:    RIFF (little-endian) data, WAVE audio, Microsoft PCM, 8 bit, mono 8000 Hz
t.mp3:    Audio file with ID3 version 2.3.0, contains: MPEG ADTS, layer III, v1, 128 kbps, 44.1 kHz, Stereo
```

再以人肉视角看 PNG 的前 48 字节（xxd 实拍）：

```
00000000: 8950 4e47 0d0a 1a0a 0000 000d 4948 4452  .PNG........IHDR
00000010: 0000 0008 0000 0008 0802 0000 004b 6d29  .............Km)
00000020: dc00 0000 6c49 4441 5478 da0d c941 0100  ....lIDATx...A..
```

`89 50 4e 47 0d 0a 1a 0a` 是签名，紧跟的 `49 48 44 52` 就是 "IHDR"，下一节拆它。

### 2.2 文件头修复实测

MISC 题最常见的损毁方式：出题人把头几个字节改烂，图片双击打不开。修复 = 把正确魔数写回去。拿刚才那个 PNG 开刀，把前 4 字节抹成 00：

```python
png = open("test.png", "rb").read()
open("broken.png", "wb").write(b"\x00\x00\x00\x00" + png[4:])
```

再把 8 字节签名原样补回：

```python
broken = open("broken.png", "rb").read()
open("fixed.png", "wb").write(png[:8] + broken[8:])
```

```bash
file broken.png fixed.png
```

实测输出：

```
broken.png:     data
fixed.png:      PNG image data, 8 x 8, 8-bit/color RGB, non-interlaced
```

`data` 的意思是"file 放弃理解你"。修复套路固定：`file` 判断原格式 → 查魔数表 → 补头；尾部损坏同理补尾（JPEG 补 `FF D9`，PNG 补 IEND 块）。头尾都完好还打不开，进下一节拆内部结构。

## 3. PNG 内部结构：拆开看

PNG = 8 字节签名 + 一串 chunk。每个 chunk 四段，字段表：

| 字段 | 大小 | 说明 |
| ---- | ---- | ---- |
| 长度 | 4 字节 | 数据区长度（大端，不含类型和 CRC） |
| 类型 | 4 字节 | IHDR / IDAT / IEND / tEXt / zTXt … |
| 数据 | 长度字段所示 | 内容本体 |
| CRC | 4 字节 | 对"类型+数据"的 CRC32 校验值 |

必备三件套：IHDR（宽高、位深、颜色类型，固定 13 字节数据）、IDAT（zlib 压缩后的像素，可有多个，解压时按序拼接）、IEND（空壳收尾）。

### 3.1 纯 Python 逐字段解析实测

```python
import struct, zlib

png = open("test.png", "rb").read()
pos = 8
while pos < len(png):
    ln = struct.unpack(">I", png[pos:pos+4])[0]
    ctype = png[pos+4:pos+8].decode()
    data = png[pos+8:pos+8+ln]
    crc_stored = struct.unpack(">I", png[pos+8+ln:pos+12+ln])[0]
    crc_calc = zlib.crc32(png[pos+4:pos+8+ln]) & 0xffffffff
    ok = "OK" if crc_stored == crc_calc else "BAD"
    print(f"{ctype}: len={ln} crc={crc_stored:08x}/{crc_calc:08x} [{ok}]")
    pos += 12 + ln
```

实测输出：

```
IHDR: len=13 crc=4b6d29dc/4b6d29dc [OK]
IDAT: len=108 crc=f9a60b79/f9a60b79 [OK]
IEND: len=0 crc=ae426082/ae426082 [OK]
```

CRC 全部对得上 = 文件没被动过手脚。这份脚本就是 MISC 界的听诊器：哪个 chunk 的 CRC 是 BAD，哪里就被改过。chunk 列表里冒出不认识的名字（tEXt、zTXt、自定义小写块），直接看内容，藏 flag 的老位置。

### 3.2 改宽高：MISC 招牌题

IHDR 数据区前 8 字节是宽、高（各 4 字节大端）。在这张 8 字节样本里，宽度字段落在文件偏移 16（签名 8 + 长度 4 + 类型 4）。出题人把高度改小，图片下半截"消失"，flag 就在那截里。亲手改一遍（宽 8 → 16）：

```python
png = open("test.png", "rb").read()
wide = png[:16] + struct.pack(">I", 16) + png[20:]
```

只改宽不重算 CRC，查看器直接罢工。实测对比：

```
[1] 只改宽度：IHDR CRC 存储=4b6d29dc 重算=7f14e8c0 -> BAD，查看器报 CRC error
[2] 修 CRC 后逐 chunk 校验: [('IHDR', 'OK'), ('IDAT', 'OK'), ('IEND', 'OK')]，宽高字段=(16, 8)
```

修 CRC 三行，位置要对准（CRC 在偏移 29，紧跟 13 字节的数据区）：

```python
crc = zlib.crc32(wide[12:29]) & 0xffffffff
wide_fix = wide[:29] + struct.pack(">I", crc) + wide[33:]
open("wide_fix.png", "wb").write(wide_fix)
```

修好后 `file wide_fix.png` 报 `PNG image data, 16 x 8`。图是 16 宽了，但 IDAT 里的像素每行只够铺 8 列，右半边要么被截断要么渲染成垃圾。==改宽高必须连 CRC 一起重算，两件事是一件事==。

改回去验证手艺：

```python
back = wide_fix[:16] + struct.pack(">I", 8) + wide_fix[20:29]
back += struct.pack(">I", zlib.crc32(back[12:29]) & 0xffffffff) + wide_fix[33:]
print(back == png)    # True，逐字节复原
```

实战反方向更有用：图被改小了，怎么爆破原宽高？IDAT 解压后的字节数是固定的，==每行 = 1 字节滤波 + 宽 × 每像素字节数，总长 = 高 × 每行长==。遍历合理的宽高组合，算到总长匹配为止，再逐个试 CRC 或肉眼看哪组正常。

### 3.3 zlib 解 IDAT：像素的素颜

```python
idat = b""
pos = 8
while pos < len(png):
    ln = struct.unpack(">I", png[pos:pos+4])[0]
    if png[pos+4:pos+8] == b"IDAT":
        idat += png[pos+8:pos+8+ln]
    pos += 12 + ln
raw = zlib.decompress(idat)
print(len(idat), len(raw), raw[:13].hex(" "))
```

实测输出：

```
108 200 00 00 00 80 1e 00 80 3c 00 80 5a 00 80
```

108 字节的 IDAT 解压出 200 字节，正好 8 行 × (1 + 8×3)。第一字节 `00` 是行滤波类型（None，还有 Sub/Up/Average/Paeth 四种），之后每 3 字节一个像素：第一个像素 RGB = (0,0,128)，第二个 = (30,0,128)。5.1 节的 PNG LSB 提取、宽高爆破的长度校验，全靠这一手。zsteg、stegsolve 干的也是这个活，只是把它们包装成了界面。

## 4. 压缩包三套路

### 4.1 爆破：zipfile 口令循环

先造靶子。WSL 里没有 zip 命令，索性纯标准库手搓一个 ZipCrypto 加密包（口令 9527），再用 zipfile 爆它，一条龙：

```python
import struct, zipfile

def _gen_table():
    table = []
    for i in range(256):
        c = i
        for _ in range(8):
            c = (c >> 1) ^ 0xEDB88320 if c & 1 else c >> 1
        table.append(c)
    return table
CRCTAB = _gen_table()

class ZipCrypto:
    def __init__(self, pwd):
        self.k = [0x12345678, 0x23456789, 0x34567890]
        for p in pwd:
            self.update(p)
    def update(self, c):
        k = self.k
        k[0] = (k[0] >> 8) ^ CRCTAB[(k[0] ^ c) & 0xff]
        k[1] = ((k[1] + (k[0] & 0xff)) & 0xffffffff) * 134775813 + 1 & 0xffffffff
        k[2] = (k[2] >> 8) ^ CRCTAB[(k[2] ^ (k[1] >> 24)) & 0xff]
    def stream_byte(self):
        t = self.k[2] | 2
        return ((t * (t ^ 1)) >> 8) & 0xff
```

加密循环每次：先吐一个密钥流字节，再用明文字节更新密钥，输出两者异或。文件结构就是第 2 节的魔数表加上字段拼接（本地头 + 12 字节加密头 + 密文 + 中央目录 + EOCD），完整脚本见本章配套仓库。造好后爆破，核心是 zipfile 的口令循环：

```python
target = zipfile.ZipFile("crackme.zip")
for n in range(10000):
    pwd = f"{n:04d}".encode()
    try:
        out = target.read("secret.txt", pwd=pwd)
        print("命中口令:", pwd.decode(), "，解出:", out.decode())
        break
    except (RuntimeError, zipfile.BadZipFile, zlib.error):
        continue
```

实测输出：

```
[2] 手搓 ZipCrypto 包：is_encrypted = True  compress_size = 43 （= 12 字节加密头 + 31 明文）
[2] 正确口令 9527 读出: flag{z1p_crack3d_by_bruteforce}
[3] 爆破 0000-9999 -> 命中口令: 9527 ，解出: flag{z1p_crack3d_by_bruteforce}
```

口令错时 `read()` 抛 RuntimeError（Bad password），try/except 接住继续循环。四位纯数字 Python 秒杀；真实赛题的口令交给专业工具：`zip2john flag.zip > hash` 提出哈希，john 或 hashcat 挂 rockyou 字典跑，Windows 下图形界的 ARCHPR 也行。工具箱见 [[01-Linux环境与CTF实验环境搭建|01 章]]的装机清单。

> [!warning] 一个值钱的坑
> 密钥更新必须用裸 CRC 查表步进。`zlib.crc32(bytes([c]), key0)` 的链式值带补码约定，和 PKWARE 的寄存器步进不是一回事。直接拿来写加密，产物 zipfile 解不开，报 Bad password。本章实测时在这上面翻过车，报错信息和口令错误一模一样，很有迷惑性。

### 4.2 伪加密

ZIP 头部有个两字节的"通用标志位"（general purpose bit flag），最低位为 1 表示"本条目已加密"。==数据加没加密是一回事，标志位写没写 1 是另一回事==。出题人把标志置 1、数据照旧明文，你输什么口令都"错"，这就叫伪加密。

标志位的位置（相对各自签名）：本地文件头 `PK\x03\x04` 偏移 +6；中央目录 `PK\x01\x02` 偏移 +8。==两处都要改==。实测走一遍：

```python
def flip_bits(z, on):
    for sig, off in ((b"PK\x03\x04", 6), (b"PK\x01\x02", 8)):
        i = 0
        while (i := z.find(sig, i)) >= 0:
            z[i+off] = (z[i+off] | 0x01) if on else (z[i+off] & 0xFE)
            i += 4
    return z
```

实测输出（普通 zip → 置位 → 恢复）：

```
[1] 伪加密：本地头(偏移 0 )标志字节 0x1 ，中央目录(偏移 64 )标志字节 0x1 —— 两处最低位都被置 1
[1] zipfile.is_encrypted()： 0 位判定 = False -> True
[1] 输入任意口令读它 -> RuntimeError : Bad password for file 'flag.txt'
[1] 标志位改回 0 后正常读出: flag{not_really_encrypted}
```

判断口诀：unzip 张口要口令，但 7z 能列出文件、CRC 和大小看着全正常，十有八九是伪加密。修复就是把那两个最低位清回去。反过来的题也存在：真加密被伪装成没加密，一解密 CRC 对不上，这时候才轮到 4.1 的爆破。

### 4.3 明文攻击

ZipCrypto 是上世纪的流密码，存在已知明文攻击：拿到加密包内某个文件的原始明文（12 字节起步，越多越好），bkcrack 或 pkcrack 能反推出内部密钥，之后整个包随便解。适用场景：题面直接给了某个原文件；或包里塞了公开可下载的东西（某软件的 readme、系统自带 dll）。标准用法：

```bash
bkcrack -C flag.zip -c readme.txt -p readme_original.txt
# -C 加密包，-c 包内密文条目，-p 对应明文文件；拿到密钥后用 -d 解包
```

碰到"包里有个 4MB 的 .dll 介绍都没介绍"，先想想网上能不能搜到同款。

## 5. 图片隐写

### 5.1 LSB 原理与 BMP 手撕实测

24 位 BMP 的像素区就是 BGR 三字节的裸排（无压缩，行按 4 字节对齐）。LSB（Least Significant Bit）隐写的全部原理：==把消息按位拆开，塞进像素字节的最低位；一个字节改 ±1，颜色肉眼不可辨==。

BMP 没有压缩层，适合手撕。生成 16×16 素图 → 藏 `flag{lsb_in_bmp_is_easy}` → 提取还原，全程实测：

```python
import struct

W, H = 16, 16
pixel_off = 54                                   # 14 文件头 + 40 DIB 头
data = bytearray(W * H * 3)                      # 像素随便填，能看即可
bmp = bytearray(b"BM" + struct.pack("<IHHI", pixel_off + len(data), 0, 0, pixel_off)
      + struct.pack("<IiiHHIIiiII", 40, W, H, 1, 24, 0, len(data), 0, 0, 0, 0) + data)

msg = b"flag{lsb_in_bmp_is_easy}"
bits = "".join(f"{b:08b}" for b in msg) + "0" * 8        # 8 个 0 当结束哨兵
stego = bytearray(bmp)
for i, bit in enumerate(bits):
    stego[pixel_off + i] = (stego[pixel_off + i] & 0xFE) | int(bit)
```

提取反向操作：从文件头偏移 10 读出像素区起点，收集每个字节的 `& 1`，8 位拼 1 字节，遇哨兵停：

```python
stego = open("stego.bmp", "rb").read()
off = struct.unpack("<I", stego[10:14])[0]
bits_out = bytes(stego[off + i] & 1 for i in range(len(bits)))
out = bytes(int("".join(map(str, bits_out[i:i+8])), 2) for i in range(0, len(bits_out), 8))
```

实测输出：

```
[1] plain.bmp 生成：822 字节 = 54 头 + 768 像素（16x16x3）
[2] 藏入 24 字节消息，占用 200 个像素字节的最低位
[2] 两文件大小相同: True，逐字节差异统计: 110 / 768
[3] 从像素偏移 54 起读 LSB，拼回的字节串: b'flag{lsb_in_bmp_is_easy}'
[3] 藏的原文: b'flag{lsb_in_bmp_is_easy}'，还原一致: True
```

文件大小一个字节没变，768 个像素字节里 110 个被动过，每个 ±1。这就是 LSB 隐写"隐"的全部底气。

PNG 的 LSB 玩法相同，只是像素被 zlib 压在 IDAT 里：解压 → 改扫描线 LSB（记得跳过每行首的滤波字节）→ 重压。实测藏 `png too`：

```
[1] 藏入 b'png too'：原 PNG 165 字节，藏后 180 字节（IDAT 重压缩后长度略有差异）
[2] 取出: b'png too'  一致: True
```

重压缩之后 strings 什么都扫不到——==LSB 数据在解压后的像素里，不掀开 IDAT 就看不见==，这正是它比"图片尾部粘文件"难缠的地方。

> [!note] 赛场标准姿势
> 不用每次手撕，两个界面工具覆盖九成 LSB 题：stegsolve（Java GUI）打开图 → Analyse → Data Extract，把 R/G/B × Bit 0–7 的通道挨个勾，flag 通常直接在预览里现形；PNG 还有 zsteg 一键扫全部位序组合。装法：官网下 stegsolve.jar 用 `java -jar` 跑，zsteg 用 `gem install zsteg`。

### 5.2 EXIF：图片的简历

元数据藏在图片头部结构里，exiftool 一条命令全倒出来（装法 `sudo apt install libimage-exiftool-perl`）：

```bash
exiftool flag.jpg              # 全部元数据：相机、时间、GPS、注释……
exiftool -b -Comment flag.jpg  # 单独抠 Comment 字段（flag 常住地）
exiftool -Comment="flag{x}" a.jpg   # 写入
```

做题习惯：拿到图片先 `exiftool`，扫一眼 Comment / Artist / Description 字段，成本五秒钟。flag 直接写在元数据里的题，是出题人送的温暖。

### 5.3 steghide：口令隐写

把文件嵌进图片/音频，靠口令保护，DCT 变换域写入：

```bash
steghide embed -cf cover.jpg -ef secret.txt -p 1234   # 嵌入
steghide info stego.jpg                               # 探测有没有货
steghide extract -sf stego.jpg -p 1234                # 提取
```

装法：`sudo apt install steghide`。两个必背知识点：==steghide 只支持 JPEG/BMP/WAV/AU，PNG 不在列==（高频坑，PNG 别浪费时间）；口令爆破有专职工具 stegseek，rockyou 字典秒级跑完，`stegseek stego.jpg rockyou.txt`。

## 6. 音频隐写

三条路，按出镜率排：

| 套路 | 工具与用法 |
| ---- | ---- |
| WAV 口令隐写 | steghide，同 5.3，容器换 `.wav` |
| 频谱图藏图/藏字 | Audacity 打开 → 音轨左上菜单 → 频谱图（Spectrogram），flag 直接画在频域上 |
| MP3 隐写 | MP3Stego：`Encode.bat -E hidden.txt in.wav out.mp3` 嵌入，Decode 提取 |

频谱图是音频题的半壁江山：把一段"难听的噪音"打开成频谱图，flag 或图案赫然在画。摩斯电码题也归 Audacity，波形里长音划、短音点，看比听靠谱。

## 7. 流量分析

题目给一个 `.pcap` / `.pcapng`，Wireshark 开包。协议本身在 [[10-网络协议基础|10 章]]讲过，这里只讲拆包手法。

### 7.1 显示过滤器速查

| 过滤器 | 干什么 |
| ---- | ---- |
| `http` | 只看 HTTP（明文，flag 重灾区） |
| `http.request.method == "POST"` | 看上传，flag 常在 POST body |
| `http contains "flag"` | 全包关键字搜索 |
| `tcp.stream eq 3` | 第 3 条 TCP 流 |
| `icmp` | ping 夹带 |
| `dns` | DNS 隧道 |
| `usb.capdata`（新版 Wireshark 叫 `usbhid.data`） | USB 键鼠流量 |
| `ftp` | 明文协议挨个翻，smtp、telnet 同理 |
| `ip.addr == 1.2.3.4` | 按主机收敛 |
| `frame contains "ctf"` | 原始帧字节级搜索 |

### 7.2 三个 GUI 动作

1. **统计总览**：Statistics → Protocol Hierarchy。哪个协议占比反常一眼可见。ICMP 占了九成流量，还用猜吗。
2. **Follow TCP Stream**：右键任意 TCP 包 → Follow → TCP Stream。双向会话拼成完整对话，右上角切换 ASCII/RAW。HTTP 明文 flag 十有八九在这一步现形。
3. **导出对象**：File → Export Objects → HTTP。传输过的文件全部扒出来，图片、压缩包经常就是下一层套娃。

命令行党用 tshark 同效：`tshark -r x.pcap -Y "http" -T fields -e http.file_data`。

### 7.3 流量题四大套路

| 套路          | 识别与拆法                                                                        |              |
| ----------- | ---------------------------------------------------------------------------- | ------------ |
| 明文 flag     | 直接搜：`http contains "flag"`，或 `strings x.pcap` 配 `grep flag{`                  |              |
| 编码 flag     | base64/hex 藏在 POST body、Cookie、User-Agent，[[08-编码与古典密码                       \| 08 章]]的解码链伺候 |
| USB 键鼠流量    | `usb.capdata`，键盘一次按键 8 字节，第 3 字节是 HID 位置码（0x04=a、0x05=b……对照表翻译成字符）；鼠标流量抠坐标画图 |              |
| ICMP/DNS 夹带 | ping 的 data 字段塞 base64；DNS 查询子域名拼 flag（`part1.evil.com` 这种）。协议合法字段装私货，就是隧道   |              |

USB 流量翻译脚本的骨架就是 3.1 的解析器套路：读字段、查表、拼接。位置码表一搜一把，不值得背。

## 8. 磁盘与内存取证一瞥

### 8.1 binwalk / foremost：分离嵌套文件

图片尾部粘压缩包、固件里塞文件系统，binwalk 按签名扫描：

```bash
binwalk flag.png              # 列出所有嵌入文件及偏移
binwalk -e flag.png           # 自动提取到 _flag.png.extracted/
foremost -i flag.png -o out   # 独立的文件雕刻器，按头尾魔数切
```

装法：`sudo apt install binwalk foremost`。其实你已经有平替：2.2 的 xxd + 3.1 的解析器手抠 IEND 之后的字节，一样能切，binwalk 只是把这活自动化了。

### 8.2 Volatility：内存镜像三条命令

题目给 `.raw` / `.dmp` 内存镜像，标准工具 Volatility（v2 用法最广，v3 命令改成 `windows.` 前缀）：

```bash
vol.py -f mem.raw imageinfo                        # 画像：系统版本 → 定 profile
vol.py -f mem.raw --profile=Win7SP1x64 pslist      # 进程列表
vol.py -f mem.raw --profile=Win7SP1x64 filescan | grep -i flag   # 扫文件名
```

第一步永远先 imageinfo 拿 profile，后面所有命令都要带它。常用后续：`cmdline` 看进程命令行（flag 在参数里的题不少）、`dumpfiles` 提取文件、`hashdump` 抠密码哈希。取证方向后面有专章，这里混个脸熟。

## 9. 常见问题

| 现象                               | 原因与解决                                                                                            |                 |
| -------------------------------- | ------------------------------------------------------------------------------------------------ | --------------- |
| PNG 打不开，报 CRC error              | 某个 chunk 被改过没修 CRC。用 3.1 的解析脚本定位 BAD 块，按 3.2 重算写入                                                |                 |
| 宽高被改，原值不知道                       | 解压 IDAT 数长度：总字节 = 高 × (1 + 宽 × 每像素字节)，遍历宽高组合试到匹配；`pngcheck -v` 也能直接报错位置                          |                 |
| zip 伪加密改了还报错                     | 本地头和中央目录两处标志位都要清，只清一处照样要口令；改完先 `file` 验证，再 unzip 实测                                              |                 |
| `unsupported compression method` | 不是伪加密，是压缩算法问题：AES 加密的 zip（7z 能开）或新算法；确认加密类型再选工具                                                  |                 |
| steghide 提取报 could not extract   | 口令错，或根本不是 steghide 嵌的。先 `steghide info` 探测；口令爆破上 stegseek；PNG 容器直接放弃此路                           |                 |
| stegsolve 双击没反应                  | 缺 Java 运行时，装 openjdk 后 `java -jar stegsolve.jar`                                                 |                 |
| Wireshark 一个包都抓不到                | Windows 缺 Npcap 驱动或装时没勾管理员权限、网卡选错。做题通常直接给 pcap 文件，很少现场抓                                          |                 |
| strings 中文全是乱码                   | strings 默认只捞 ASCII；`-e l` 扫 UTF-16LE，或 Python `re` 直接扫 `rb"[\x20-\x7e]{4,}"`（[[06-Python与CTF脚本基础 \| 06 章]] 2.1 的套路） |
| binwalk -e 提取是空的                 | 签名在、数据被截断。手抠：xxd 找到嵌入文件头的偏移，`dd if=x of=y bs=1 skip=偏移` 切出来                                      |                 |
