# R1 逆向工程与 CTF 竞赛生态导论
## Reverse Engineering & the CTF Ecosystem

> [!info]- 章节信息
> **所属方向**：逆向工程 ｜ **难度阶段**：L1 筑基期 ｜ **前置要求**：[[01-Linux环境与CTF实验环境搭建|通用基础 01 章]]
> **本章目标**：了解逆向工程的定义、三个应用领域与法律边界；分清静态分析与动态分析；认识常见附件类型；了解 CTF 赛制、flag 机制与平台使用方法；完整执行 file 认文件 → strings 扫关键串 → 运行验证 → 提交 flag 的第一道 Reverse 题流程。

## 1. 逆向工程是什么

用 C 语言写程序时，源码里有变量名、函数名、注释。gcc 一编译，这些信息大多不进入产物：机器码文件里只剩指令和数据（未经 strip 的文件还保留符号表，函数名可以查到；strip 之后符号表也删除）。逆向工程处理的是反方向的问题：手里只有一个能运行的二进制文件，把它使用的格式、实现的逻辑、表现的行为分析出来。

==编译是把"能懂"变成"能跑"，逆向是把"能跑"还原成"能懂"。==[[12-隐写与流量取证|通用基础 12 章]]处理的对象是容器：图片、压缩包、流量包；逆向工程处理的对象是程序本体。两个方向共用一批工具，file、xxd、strings 都是第一步。边界也清楚：MISC 的工作到"从容器里提取出文件"为止；如果提取出来的文件是一个 ELF，后续分析就属于逆向工程。

这门技术的应用领域主要有三个：

| 应用领域 | 干什么 | 产出 | 与 CTF 的关系 |
| ---- | ---- | ---- | ---- |
| 软件破解 | 绕过授权校验、去除限制 | 补丁、注册机 | crackme 题型来源于软件破解练习，是看雪、吾爱破解等社区的传统内容 |
| 漏洞挖掘 | 在二进制里找可利用的缺陷 | 漏洞报告、exploit | 是 PWN 方向的前置工作，PWN 题拿到附件后第一步也是逆向 |
| 恶意代码分析 | 搞清样本干了什么、怎么隐藏 | 分析报告、IOC | RE 赛题常带样本特征，R15 有专章 |

三个领域各补一个具体例子，说明这类工作实际在做什么：

- **软件破解**：一款试用 30 天的共享软件，每次启动时读取注册表里记录的安装日期，与当前日期比较，超期就弹窗并停用功能。破解者的工作是找到这条比较指令：或者在反汇编里定位弹窗前的条件跳转，把"超期则跳转"改成不跳转（修改产物就是补丁）；或者读懂注册码校验函数，按同样算法反推出合法注册码（写出来的程序就是注册机）。
- **漏洞挖掘**：一个监听网络端口的服务程序，分析者用反汇编器读它处理输入的函数，发现程序用 `strcpy` 把网络数据复制进 64 字节的栈缓冲区，复制前不检查长度——输入超过 64 字节就会覆盖栈上保存的返回地址。分析者先写出让程序崩溃的最短输入证明缺陷存在（漏洞报告），再构造出让程序按分析者意图执行的输入（exploit）。PWN 方向的赛题就是把这一过程当成题目。
- **恶意代码分析**：拿到一个可疑 exe，先在隔离的虚拟机里运行，记录行为：修改了哪些注册表键、把自身复制到了哪个目录、连接了哪个域名；再静态反汇编，确认它对外通信前用什么算法加密数据。产出的分析报告记录样本的功能与手法，IOC（失陷指标，如域名、文件路径、互斥量名）用于事后检测。这是安全厂商与应急响应岗位的日常工作之一。

三个领域使用同一套工具链和底层知识（汇编、ELF、操作系统），区别只在目的：==破解改变程序行为，漏洞挖掘寻找可利用缺陷，恶意代码分析还原样本行为==。逆向方向的 crackme、算法还原、脱壳对抗练习，与这三个领域共用这套知识，学一次即可同时支撑三个领域。

## 2. 静态分析与动态分析

逆向工程的所有工作分成两类基本方法，先在这里把两个词定义清楚。

**静态分析**：不运行程序，直接分析文件本身。能做的事：

- `file`、`xxd` 识别文件格式与架构；
- `strings` 提取静态数据里的明文字符串；
- `readelf`、`objdump` 查看节区、符号、导入函数，并反汇编出汇编代码；
- 反编译器（R5 讲的 IDA、Ghidra）把汇编进一步转成接近 C 的伪代码。

两个术语在这里定义：==反汇编是把机器码转换成汇编指令==，一对一转换，结果就是 CPU 实际执行的内容；==反编译是把机器码转换成类似 C 的伪代码==，转换过程有推测成分，读起来快，但个别地方可能与程序真实行为有出入，存疑时以汇编为准。

静态分析覆盖程序的全部代码，包括没有机会执行到的分支，也不会触发反调试检查；局限是程序加壳或加密后，静态看到的只是压缩或加密后的数据，必须先脱壳（R9、R10）。

**动态分析**：把程序放进受控环境（调试器、虚拟机）里执行，观察运行过程。能做的事：

- 在 GDB 里对某条指令下断点，程序停下后查看寄存器、内存、变量的当前值（R6 系统讲）；
- 输入一组数据，观察它在程序内部被逐步变换成什么；
- 用 strace、ltrace 记录程序的系统调用与库函数调用，观察文件读写、网络行为。

动态分析直接呈现程序的真实行为，不要求先读懂代码；局限是只能覆盖实际执行到的路径（输入不同，路径就不同），而且不少题目带反调试代码，检测到调试器会改变行为。

| | 静态分析 | 动态分析 |
| ---- | ---- | ---- |
| 是否运行程序 | 否 | 是（调试器或虚拟机内） |
| 覆盖范围 | 全部代码 | 实际执行到的路径 |
| 常用工具 | file、strings、readelf、objdump、IDA、Ghidra | GDB、x64dbg、strace、ltrace |
| 主要限制 | 加壳加密后看不到真实代码 | 受反调试影响，未执行的分支观察不到 |

实际解题时两类方法交替使用：先静态读出程序的整体结构，再动态验证关键判断；动态分析发现的可疑值，也常要回到静态分析确认来源。本章第 8 节的流程里，file 与 strings 属于静态分析，运行验证属于动态分析。

## 3. 常见附件类型与识别

拿到题目附件，第一件事是弄清它是什么类型，后续工具链的选择由此决定。`file` 与 `xxd` 的用法[[12-隐写与流量取证|通用基础 12 章]]讲过：后缀不可靠，以文件头的魔数为准，[[03-计算机组成与数据表示|通用基础 03 章]]列过常见魔数。逆向工程常见的附件类型如下：

| 类型 | 是什么 | file 报什么 | 对应工具 |
| ---- | ---- | ---- | ---- |
| ELF | Linux 可执行文件格式，也用于共享库 `.so` 和目标文件 `.o`。Linux 题附件绝大多数是它 | `ELF 64-bit LSB executable, x86-64 ...` | readelf、objdump、GDB、IDA |
| PE | Windows 可执行文件格式，即 `.exe`、`.dll`、`.sys`；32 位报 `PE32`，64 位报 `PE32+` | `PE32+ executable (GUI) x86-64 ...` | x64dbg、IDA |
| Mach-O | macOS / iOS 程序格式 | `Mach-O 64-bit executable x86_64` | IDA；iOS 题还需先砸壳 |
| APK | Android 安装包，本质是 zip 压缩包，内含 `classes.dex`（Dalvik/ART 字节码）、资源文件与清单 | `Zip archive data` | jadx、jeb |
| JAR | Java 归档，本质是 zip，内含 `.class`（JVM 字节码） | `Zip archive data` | jadx、jd-gui、CFR |
| .pyc | Python 源码编译后的字节码文件，文件头记录 Python 版本魔数 | `python 3.x byte-compiled`；识别库未收录新版本时报 `data` | pycdc、uncompyle6 |
| .NET 程序 | `.exe`/`.dll`，内部是 CIL 字节码与元数据，不是机器码 | `PE32 executable ...`，需进工具确认 | dnSpy、ILSpy |
| 固件 | 路由器、IoT 设备的系统镜像，常为 `.bin`，可能不含标准文件结构 | `data` | binwalk 先提取文件系统 |

对 PE 类型看一条真实输出，file 识别 Windows 自带的记事本程序：

```bash
file /mnt/c/Windows/System32/notepad.exe
```

输出：

```
/mnt/c/Windows/System32/notepad.exe: PE32+ executable for MS Windows 10.00 (GUI), x86-64, 8 sections
```

读法与 ELF 输出一致：`PE32+` 表示 64 位 PE，`GUI` 表示图形界面程序（区别于 console 控制台程序），`x86-64` 是架构，文件含 8 个节区。

三条实用判断：

- file 报 `data` 不代表文件损坏，只代表这种格式不在 file 的识别库里（新版本 .pyc、固件、加壳程序都会这样）。此时结合后缀、来源和文件头字节人工判断；
- APK、JAR 这类 zip 本质的文件，可以先用 `unzip -l` 列出内部包含的文件；
- ELF 有没有 strip，看 file 输出结尾的 `not stripped` / `stripped`，它决定函数名还在不在（本章第 1 节）。

## 4. 先划红线：合法边界在哪

逆向工程本身是中性技术，是否违法只看两件事：分析对象有没有获得授权，分析成果拿来做什么。

> [!warning] 先授权，再分析
> 合法的分析对象：CTF 平台的题目附件（出题人发布题目，就是供参赛者逆向）、crackmes.one 上的程序（作者主动发布，邀请他人破解）、自己在虚拟机里编译的程序、签订了合同且在授权范围内的测试项目。
> 未经授权侵入计算机系统、破坏系统功能、获取数据，即使不以盈利为目的，也可能触犯《刑法》第 285 条（非法侵入计算机信息系统等）与第 286 条（破坏计算机信息系统罪），会被追究刑事责任。[[01-Linux环境与CTF实验环境搭建|通用基础 01 章]]开篇讲过这些法律条款。
> 分析恶意样本必须使用隔离环境，具体操作步骤见本章第 8 节。

## 5. CTF 赛制与 Reverse 题型

CTF 的主流赛制是 Jeopardy 解题赛：题目按方向发布在比赛平台上，参赛队伍解出题目、提交 flag 获得积分，时限内比总分。==新手阶段的比赛和练习平台几乎全是解题赛==。另一种主要赛制是攻防赛（AWD，Attack with Defense）：每支队伍守卫自己的服务器，同时攻击其他队的服务器，按攻防结果计分，对基础要求更高，本知识库不涉及。国际比赛如 DEFCON CTF、Google CTF、*CTF、SekaiCTF，现阶段了解即可。国内值得关注的比赛：CISCN（全国大学生信息安全竞赛，以学校为单位组队）、强网杯、XCTF 联赛。

Reverse 方向的题目形态很固定：给一个二进制附件和一两句题面，flag 在程序内部。附件通常打包成 zip，解开后多数是 ELF 或 exe，偶尔附一份说明文件。拿 flag 的方式有两类：==校验型==是程序比较你的输入，输入正确时程序才输出 flag；==提取型==是 flag 经过变换后存储在程序数据里，任务就是把它还原出来。

按解题用到的技术，Reverse 题型分类如下：

| 题型          | 附件里的程序做了什么                   | 对应章节                              |
| ----------- | ---------------------------- | --------------------------------- |
| strings 签到型 | flag 或关键字符串以明文形式存于文件中        | [[#8.2 第二步：strings 扫关键串\|本章 8.2]] |
| crackme 校验型 | 明文比较、变换后比较、注册机、patch         | R8                                |
| 算法还原型       | 程序把输入编码（XOR、TEA、RC4 等）后与目标比较 | R7                                |
| 加壳与反调试      | 用 UPX 等壳压缩代码，检测调试器           | R9、R10                            |
| 混淆与 VM      | 控制流平坦化、自定义字节码解释器             | R11、R12                           |
| 多平台         | 附件换成 APK、pyc、Go、Rust、固件      | R13                               |
| 自动求解        | 用 angr、z3 等约束求解工具自动算输入       | R14                               |

表中前几类题型依赖的基础能力，来自[[04-汇编语言精要|通用基础 04 章]]的汇编与[[05-ELF文件格式与链接|通用基础 05 章]]的 ELF。R2 到 R6 会以"读懂程序"为目标把这些内容再讲一遍，并补上 IDA 与 GDB 两个工具。==R1 到 R6 都是基础内容，R7 起进入完整题型==。

Reverse 与 PWN 的关系一句话：社区公认的入门顺序是先逆向、后 PWN，因为 PWN 的每一步都以读懂二进制为前提，之后才谈得上控制程序的执行。

## 6. flag 格式与提交机制

flag 是一串证明"你解出了这道题"的文本，格式固定：前缀加花括号，花括号内是内容。`flag{...}` 是通用写法，不少平台用自己的前缀：攻防世界用 `cyberpeace{...}`，picoCTF 用 `picoCTF{...}`。==提交时连同前缀整串复制==，少一个花括号、多一个空格、大小写不符，平台一律判错。

flag 的发放机制分两种：

- **静态 flag**：flag 写死在题目里，所有人拿到的相同，解出一次永远有效。练习平台的题目和本章第 8 节的 crackme 都是这种。
- **动态 flag**：正式比赛里每支队伍领到的 flag 都不同。生成方式一般是：平台按队伍 token（报名或登录时分配的唯一标识）为每队计算出一串不同的 flag，注入到分发给各队的附件或在线题目实例中；提交时平台校验的是本队 token 对应的那一串。

正式比赛使用动态 flag 的原因有三个：

1. ==防止队伍之间直接抄答案==：其他队的 flag 提交无效，同时平台能从提交记录识别抄袭行为；
2. ==降低题目提前泄露的影响==：某队把附件和 flag 泄露出去，泄露的那串对其他队无效，比赛仍能正常进行；
3. ==题目赛后可复用==：比赛结束、题目公开进题库后，旧 flag 作废，题目配上新的静态 flag 就能继续用于练习（BUUCTF 复刻的历年赛题就是这样来的）。

对解题的实际影响：动态 flag 的题目，本地解出的那一串就是本队要提交的内容；别人题解里出现的 flag 与你的不同，属正常现象。

## 7. 平台使用与赛事生态

积分与排行：常见计分方式有两种，==固定分==（每题分值固定，如攻防世界按星级定分）与==动态积分==（每题设初始分与下限，每多一队解出分值就下降一些，越早解出得分越高）。排名按队伍总分从高到低，同分时按达到该分数的时间先后；部分比赛对最早解出的队伍（一血）有额外加分。

| 平台 | 地址 | 特点 | 建议起点 |
| ---- | ---- | ---- | ---- |
| 攻防世界 | adworld.xctf.org.cn | XCTF 联赛的练习平台，题目分新手区与进阶区 | 新手区 Reverse 全部完成 |
| BUUCTF | buuoj.cn | 历年赛题复刻库，题量大 | Reverse 分类按通过率从高到低 |
| CTFshow | ctf.show | 题目按系列组织，配套知识点成套 | 逆向模块 re 入门系列 |

本次训练使用的比赛平台是[青岑网安 \| QingCen CTF](https://ctf.qingcen.net/)，比赛期间从平台页面进入对应题目即可。

选题方法：==跟着通过率走，不跟自己的难度感觉走==。通过率由大量解题者的实际通过情况统计得出，比题面标注的难度更可靠。

另有两个资源：crackmes.one 是专门的 crackme 社区，程序均由作者主动发布、邀请他人破解，授权没有问题，R8 起刷 crackme 题会用到；CTFtime.org 是全球 CTF 赛事日历，参加正式线上赛时用它查排期。

环境方面没有额外要求：Reverse 附件下载到本地分析，[[01-Linux环境与CTF实验环境搭建|通用基础 01 章]]安装的 WSL 工具链直接可用。两个注意事项：Windows 复制进 WSL 的文件没有执行位，运行时报 Permission denied，`chmod +x` 加上即可；遇到 PE 题目，回 Windows 侧用 x64dbg 处理（R6 讲）。

## 8. 第一道 Reverse 题的完整流程：自建 crackme

练习平台入门区的 Reverse 题，程序本体通常就是一个 crackme：程序要求输入一个 key，输入正确时输出 flag。本章自建一个 crackme，把解题流程完整走一遍。程序里用到的 `strcmp` 字符串比较，[[02-C语言与内存模型|通用基础 02 章]]讲过：

```c
#include <stdio.h>
#include <string.h>

int main(void) {
    char input[64] = {0};
    /* flag 逐字节与 0x2A 异或后存放，编译产物里没有明文 */
    char enc[20] = {76, 70, 75, 77, 81, 76, 27, 88, 89, 94,
                    117, 88, 79, 117, 73, 66, 30, 70, 70, 87};

    printf("Enter license key: ");
    if (scanf("%63s", input) != 1) {
        return 1;
    }
    if (strcmp(input, "str1ngs_1s_m4g1c") != 0) {
        puts("Access denied.");
        return 1;
    }
    for (int i = 0; i < 20; i++) {
        putchar(enc[i] ^ 0x2A);
    }
    putchar('\n');
    return 0;
}
```

这个程序包含两个常见设计：

1. key 用 `strcmp` 与常量字符串比较，这是最简单的校验方式，R8 会讲它的一批变种；
2. flag 不以字符串形式存储：20 个字节先逐个与 `0x2A` 异或（一个数异或同一个值两次会恢复原数，76 与 `0x2A` 异或正好得到字符 `f`），存成数字数组，运行时再异或还原。这样 strings 扫描不到 flag，要拿到 flag 就必须读懂程序逻辑。

编译命令（x86-64 Linux）：

```bash
gcc -O0 -fno-pie -no-pie crackme.c -o crackme
```

`-O0` 关闭优化，使机器码与源码逐句对应，方便后续对照；`-fno-pie -no-pie` 关闭地址无关编译，[[05-ELF文件格式与链接|通用基础 05 章]]讲 ELF 时遇到过。

### 8.1 第一步：file 认文件

[[12-隐写与流量取证|通用基础 12 章]]讲过：后缀不可靠，魔数可靠。

```bash
file crackme
```

输出：

```
crackme: ELF 64-bit LSB executable, x86-64, version 1 (SYSV), dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2, BuildID[sha1]=7b5c39f693574194479ee4601fef6cf9ecbeca5d, for GNU/Linux 3.2.0, not stripped
```

读法：x86-64 架构的 Linux ELF，动态链接，未 strip（符号表还在）。这一步决定后续所有工具的选择：ELF 归 Linux 工具链，PE 归 Windows 工具链。再看文件头几个字节：

```bash
xxd crackme | head -1
```

输出：

```
00000000: 7f45 4c46 0201 0100 0000 0000 0000 0000  .ELF............
```

`7f 45 4c 46` 即 `\x7fELF`，就是[[03-计算机组成与数据表示|通用基础 03 章]]魔数表里 ELF 对应的那组字节。file 与 xxd 耗时很短，==每次拿到附件都先执行这两条命令==，避免被不可靠的后缀误导。

### 8.2 第二步：strings 扫关键串

```bash
strings crackme | grep -Ei "key|denied|str1ngs|flag"
```

输出：

```
Enter license key: 
str1ngs_1s_m4g1c
Access denied.
```

提示语、拒绝语，加上 key 本身 `str1ngs_1s_m4g1c`，都直接可见。flag 呢？再查一次：

```bash
strings crackme | grep -c flag
```

输出：

```
0
```

结果为 0：flag 的 20 个字节在数据区里是 `76 70 75 77 ...`，不是可打印字符，strings 扫不出来。==strings 只能看见静态数据里的明文，运行时才还原的内容它一概不知道==。这是出题人防 strings 的标准做法，也是签到题与后续题型的界线：这些字符串为什么在文件里、存放在哪个节区，[[05-ELF文件格式与链接|通用基础 05 章]]讲 `.rodata` 时说过。

### 8.3 第三步：运行验证，拿 flag

key 已经从 strings 得到，作为输入运行程序：

```bash
echo wrong_guess | ./crackme
echo str1ngs_1s_m4g1c | ./crackme
```

输出：

```
Enter license key: Access denied.
Enter license key: flag{f1rst_re_ch4ll}
```

错误的 key 输出 Access denied.，正确的 key 输出 flag。提示语和结果在同一行，是 printf 没带换行符；分析附件时这类细节能帮助推测程序结构。把 flag 粘进提交框，题目标记为已解出。这道题的完整流程：

==认文件 → 扫字符串 → 运行验证 → 提交 flag==

四个步骤各自的产出：

| 步骤 | 命令 | 产出 |
| ---- | ---- | ---- |
| 认文件 | `file`、`xxd` | 格式、架构、链接方式，工具链由此确定 |
| 扫字符串 | `strings` 配 `grep` | 提示语、拒绝语，有时能直接得到 key |
| 运行验证 | 用输入运行程序 | 确认校验行为，正确的输入换出 flag |
| 提交 | 平台提交框整串粘贴 | 题目记为已解出，积分入账 |

> [!note] 第三步是流程中唯一真正执行代码的一步
> 前两步只在读文件，第三步开始执行附件里的程序。平台官方附件风险可控，习惯仍然要建立：附件优先放进虚拟机运行（[[13-Docker与赛题环境|通用基础 13 章]]的环境随时可用），来源不明的 exe 不运行、直接删除。

> [!info]- 杀毒误报与虚拟机隔离的具体操作
> **杀毒软件误报的处理**：RE 附件常带壳或反调试代码，二进制特征与恶意软件重合，被 Windows Defender 等杀毒软件报毒很常见。操作步骤：① 先确认附件来自平台官方页面，来源可靠才继续；② 打开"Windows 安全中心 → 病毒和威胁防护 → 管理设置 → 排除项"，把专门存放 CTF 附件的目录（例如 `D:\ctf\attach`）加入排除列表；③ 被自动隔离的文件，在"保护历史记录"里选择还原。第三方杀毒软件同理，把附件目录加入白名单；不要整体关闭杀毒防护，只排除附件目录。
> **虚拟机隔离的操作**：用 VMware 或 VirtualBox 装一个 Linux 虚拟机（或使用[[13-Docker与赛题环境|通用基础 13 章]]的容器环境）。拿到附件后的标准动作：① 把附件复制进虚拟机，宿主机上不留可执行副本；② 分析前先拍一个快照；③ 分析可疑样本时把虚拟机网络设为"仅主机"或直接断开网络，阻止样本对外连接；④ 分析结束恢复快照，虚拟机回到干净状态。恶意代码分析（R15）必须走这套流程，平时的题目附件可以按风险酌情执行。

入门区的多数题目用这三步就能解出。如果 strings 扫出来的全是乱码、运行也得不到有效信息，说明这道题的 key 不是明文比较，而是先经过变换——这时就需要打开反汇编器读代码，R5 的 IDA 与 R6 的 GDB 就是做这件事的工具。

## 9. 常见问题

| 现象 | 原因与解决 |
| ---- | ---- |
| 附件拷进 WSL，`./xxx` 报 Permission denied | Windows 文件系统过来的文件没有执行位，执行 `chmod +x xxx` |
| 杀毒软件把题目附件删了 | RE 附件带壳、带反调试，特征与恶意软件重合，误报很常见。平台官方附件按本章第 8 节的方法加排除项或进虚拟机运行，来源不明的直接删除 |
| strings 全扫了没一条线索 | flag 在运行时才生成或解密，静态扫描看不到。先按 [[#8.3 第三步：运行验证，拿 flag\|8.3]] 执行一遍，排除"输入正确才输出"的情况；仍查不出就需要反汇编（R5） |
| 算法逆对了，flag 却判错 | 前缀不符（平台自有前缀）、混进空格、大小写错误。连同前缀整串复制粘贴 |
| exe 附件在 WSL 里跑不了 | 先 `file` 确认格式：ELF 归 WSL，PE 归 Windows 侧，或安装 wine |
| 题目页找不到附件 | 附件一般挂在题目详情页，部分平台要先加入比赛或进入对应模式才显示附件 |
| `file` 报 `data`，看不出类型 | file 的识别库没收录这种格式：新版本 .pyc、固件、加壳程序都可能这样。结合后缀、来源与文件头字节判断（本章第 3 节） |
