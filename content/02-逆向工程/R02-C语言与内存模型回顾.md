# R2 C 语言与内存模型回顾
## C & Memory Model Revisited

> [!info]- 章节信息
> **所属方向**：逆向工程 ｜ **难度阶段**：L1 筑基期 ｜ **前置要求**：[[01-Linux环境与CTF实验环境搭建|通用基础 01 章]] · [[02-C语言与内存模型|通用基础 02 章]] · [[03-计算机组成与数据表示|通用基础 03 章]]
> **本章目标**：能对着 GDB 画出三层调用的栈帧图；能预测指针运算与类型转换的结果；能从 movslq / cdqe 这类扩展指令反推源码里的类型；能按大小端正确读 hexdump。

## 1. 同一套知识，两个视角

[[02-C语言与内存模型|通用基础 02 章]]站在写代码的立场讲内存：写下 `char buf[16]`，心里要有图。逆向把这个立场反过来——手里只有编译完成的机器码，要反推当初的源码长什么样。==编译后的机器码不保留变量名和类型信息，C 内存模型是反推时唯一的依据==。

| 02 章教过的概念        | 到了逆向里要回答的问题               |
| ---------------- | ------------------------- |
| 内存四区各放什么         | 拿到一个地址，先判断它落在哪个区          |
| `p + n` 前进 n 个元素 | `[rax+rdx*4]` 是什么数组的第几个元素 |
| 结构体对齐两条规则        | IDA 里那些奇怪的间隔是填充还是成员       |
| `-1` 就是全 1       | 符号扩展指令为什么出现在这里            |
| SysV 参数寄存器       | 这个函数的参数从哪读、第 7 个参数在栈上哪里   |

本章 11 个程序统一用 `gcc -O0 -fno-pie -no-pie -g xxx.c -o xxx` 编译：`-O0` 让汇编和源码一一对应；`-fno-pie -no-pie` 把程序本体固定到 0x400000 附近；`-g` 给 GDB 提供调试信息。无 PIE 程序的代码地址在任何机器上加载位置都一致；堆和栈的地址每次运行会变，属正常现象。

## 2. 内存四区：先对完地址再谈别的

四区的划分与各区用途 [[02-C语言与内存模型|通用基础 02 章]]讲过，这里不重贴。逆向关心的是另一件事：==拿到一个地址，第一反应是判断它落在哪个区==。写一个把每个区各取一个地址打印出来的程序（regions.c）：

```c
#include <stdio.h>
#include <stdlib.h>
int g_init = 42;
int g_uninit;
int probe(int x) { return x + g_init; }
int main(void) {
    static int s_local = 7;
    int local = 1;
    int *heap = malloc(32);
    printf("probe=%p  &g_init=%p\n", (void *)probe, (void *)&g_init);
    printf("&s_local=%p  &g_uninit=%p\n", (void *)&s_local, (void *)&g_uninit);
    printf("heap=%p  &local=%p\n", (void *)heap, (void *)&local);
    free(heap);
    probe(0);
    return 0;
}
```

```bash
gcc -O0 -fno-pie -no-pie -g regions.c -o regions
./regions
```

输出（运行两次）：

```
probe=0x401196  &g_init=0x404030
&s_local=0x404034  &g_uninit=0x40403c
heap=0x1681e010  &local=0x7ffdb2018a7c
```

第二次运行，前两行不变，`heap` 变成 0x172a0010，`&local` 变成 0x7ffcca3d27cc。代码与静态区地址固定，堆和栈每次运行都换位置，这是 [[03-计算机组成与数据表示|通用基础 03 章]]讲过的 ASLR：==无 PIE 时静态区固定，堆和栈永远在变==。

GDB 给出更完整的图。命令文件 gdbcmds_regions.txt 就五条：`set pagination off`、`break probe`、`run`、`print &g_init`、`info proc mappings`，跑法是 `gdb -batch -x gdbcmds_regions.txt ./regions`。输出（节选，只留关键行）：

```
Mapped address spaces:
Start Addr         End Addr           Size               Offset             Perms File
0x0000000000401000 0x0000000000402000 0x1000             0x1000             r-xp  /tmp/r2/regions
0x0000000000404000 0x0000000000405000 0x1000             0x3000             rw-p  /tmp/r2/regions
0x0000000000405000 0x0000000000426000 0x21000            0x0                rw-p  [heap]
0x00007ffff7c28000 0x00007ffff7dc0000 0x198000           0x28000            r-xp  /usr/lib/x86_64-linux-gnu/libc.so.6
0x00007ffffffde000 0x00007ffffffff000 0x21000            0x0                rw-p  [stack]
```

对着打印的地址逐个看：probe = 0x401196 落在 0x401000 那页 `r-xp`（代码）；g_init、g_uninit 都在 0x404000 那页 `rw-p`（.data 和 .bss）；malloc 的 32 字节落在 [heap]；libc 的可执行页在 0x7ffff7c28000；栈在 0x7ffffffde000。GDB 默认关闭 ASLR，调试时这张表每次都一样。

.bss 还可以直接确认：`objdump -s -j .data regions` 输出只有 `404030  2a000000  07000000` 一行——0x2a = 42，0x07 = 7，正好是 g_init 和 s_local，g_uninit 的 0x40403c 不在里面。==.bss 在文件里没有内容==，加载时才由内核清零，细节见 [[05-ELF文件格式与链接|通用基础 05 章]]。

四区的生命周期与大小限制放一张表。判断地址落在哪个区、估算溢出能不能写进去，都靠它：

| 区域 | 典型内容 | 生命周期 | 大小与管理方 |
| ---- | ---- | ---- | ---- |
| 代码区 | 机器指令、字符串字面量 | 程序启动到退出 | 编译链接时定死；只读、可执行 |
| 静态区（.data / .bss） | 全局变量、static 局部变量 | 程序启动到退出 | 编译链接时定死；可读写 |
| 栈 | 局部变量、函数参数、返回地址 | 函数调用期间，返回即回收 | Linux 默认 8 MB；Windows 默认 1 MB |
| 堆 | malloc / calloc / realloc 的返回 | `malloc` 起到 `free` 止；不 free 则到进程退出 | glibc 的 malloc 管理，用 brk / mmap 向内核按需扩大 |

```bash
ulimit -s
```

输出：

```
8192
```

8192 KB 即 8 MB。==栈的余量小==：递归多几十层、局部开个几 MB 的大数组都可能越上限，直接 SIGSEGV——"stack overflow" 这个词的本义就是栈被用尽。堆由 malloc 管理并向内核按需扩大，能长到远大于 8 MB；分配失败返回 NULL，不检查返回值是另一类漏洞来源。

> [!warning] 别把无 PIE 的地址当常态
> 0x400000 附近这套布局只在 `-no-pie` 下成立。赛题 PIE 全开时，程序本体会被搬进 0x55... 开头的随机位置。判断区域的正确方法是调试时看 `info proc mappings`（pwntools 里对应 `vmmap`），==判断区域看映射表，不猜地址==。

## 3. 用 GDB 把栈帧看在眼里

序言、尾声和 rbp 的角色 [[04-汇编语言精要|通用基础 04 章]]讲过，帧内布局就是那张以 rbp 为基准的图。画图之前先取一份真实数据，断点停下后用 GDB 查看。三层调用的小程序（stack3.c）：

```c
#include <stdio.h>
int leaf(int x, int y) {
    int r = x * 2 + y;
    return r;
}
int middle(int a, int b) {
    int sum = a + b;
    return leaf(sum, a);
}
int top(void) {
    int v = middle(3, 4);
    return v;
}
int main(void) {
    int out = top();
    printf("out = %d\n", out);
    return 0;
}
```

观察用三条命令：`bt` 显示全部调用帧；`frame N` 切换到第 N 帧；`info frame` 显示当前帧的详细信息。写成批量脚本 gdbcmds_stack3.txt：

```
# 跑法：gdb -batch -x gdbcmds_stack3.txt ./stack3
set pagination off
set disassembly-flavor intel
break leaf
run
bt
frame 2
info frame
print $rbp
x/2gx $rbp
info symbol *(void **)($rbp+8)
```

输出（断点命中与 bt）：

```
Breakpoint 1, leaf (x=7, y=3) at stack3.c:4
4	    int r = x * 2 + y;
#0  leaf (x=7, y=3) at stack3.c:4
#1  0x0000000000401183 in middle (a=3, b=4) at stack3.c:10
#2  0x00000000004011a0 in top () at stack3.c:14
#3  0x00000000004011b9 in main () at stack3.c:19
```

断点显示 `leaf (x=7, y=3)`：middle 里算好的 sum = 3+4 = 7，连同 a = 3 一起传了进来。切到 frame 2：

```
#2  0x00000000004011a0 in top () at stack3.c:14
Stack level 2, frame at 0x7fffffffe190:
 rip = 0x4011a0 in top (stack3.c:14); saved rip = 0x4011b9
 called by frame at 0x7fffffffe1b0, caller of frame at 0x7fffffffe170
 Saved registers:
  rbp at 0x7fffffffe180, rip at 0x7fffffffe188
$1 = (void *) 0x7fffffffe180
0x7fffffffe180:	0x00007fffffffe1a0	0x00000000004011b9
main + 17 in section .text of /tmp/r2/stack3
```

读法分四步。`bt` 一次给整条链，每层停在源码第几行都标了。`info frame` 的输出里最关键的是两行：==called by frame at 与 caller of frame at 就是 rbp 链本身==，Saved registers 里 `rip at 0x7fffffffe188` 指明返回地址存在哪个槽。`print $rbp` 得到 top 帧的 rbp = 0x7fffffffe180，`x/2gx` 往那里看两个 8 字节槽：第一个 0x00007fffffffe1a0 是 main 的旧 rbp，第二个 0x00000000004011b9 是返回地址。`info symbol` 把裸地址翻译回符号：main + 17。==bt 显示的每一层，读的就是栈上这两个槽的数据，没有别的机制==。

据此可以画图了：middle 帧的 `[rbp]` 放 top 的旧 rbp，`[rbp+0x8]` 放返回地址 0x4011a0，往下 `[rbp-0xc]` 一带放 sum。==画栈帧图以 rbp 为基准：负偏移是局部变量，[rbp] 是旧 rbp，[rbp+0x8] 是返回地址==。

> [!warning] 具体偏移没有公式
> sum 落在 `[rbp-0xc]` 是 gcc 15 在这个例子里的安排，换编译器版本、换优化等级就变。[[02-C语言与内存模型|通用基础 02 章]]警告过"不要心算偏移"，`info frame` 就是替代心算的工具：断点停下后查，不用背。bt 能沿链逐帧回溯，前提是链没被破坏——PWN 里伪造栈帧、栈迁移攻击的就是这条 rbp 链，这里先记下。

## 4. 指针与数组

[[02-C语言与内存模型|通用基础 02 章]]的核心结论一句话：==`p + n` 前进的是 n × sizeof(*p) 字节，不是 n 字节==。它对应反汇编里的一个固定形状（[[04-汇编语言精要|通用基础 04 章]]拆过 pick() 的例子）：符号扩展下标 → 乘元素宽度 → 加基址 → 解引用。比例因子只有 1/2/4/8 四种，==看到 `[rax*8+...]` 就该反应出"8 字节元素"——指针数组、long 数组、函数指针表都长这样==，[[#5. 函数指针、间接调用与那张地址表|第 5 节]]的地址表就是实例。

### 4.1 数组名什么时候退化为指针

规则一条：==数组名在表达式里退化为指向首元素的指针==，`arr` 与 `&arr[0]` 值相同。三个例外，数组名在这些场合保持"整个数组"的身份：

- `sizeof arr`：结果是整个数组的字节数，不是指针宽度；
- `&arr`：类型是"指向整个数组的指针"（如 `int(*)[4]`），地址数值与 arr 相同，类型不同；
- 用字符串字面量初始化字符数组：`char s[16] = "hello";` 是把 6 个字节拷进数组，不经过指针。

观察程序（ptr_array.c）：

```c
#include <stdio.h>

int *advance(int *p, int i) {
    return p + i;
}

void take(int arr[4]) {
    printf("sizeof arr inside function = %zu\n", sizeof arr);
}

int main(void) {
    int arr[4] = {10, 20, 30, 40};
    int *p = arr;
    printf("sizeof arr = %zu, sizeof p = %zu\n", sizeof arr, sizeof p);
    printf("count = %zu\n", sizeof arr / sizeof arr[0]);
    printf("p+1 - p = %ld, byte delta = %ld\n",
           (long)((p + 1) - p), (long)((char *)(p + 1) - (char *)p));
    printf("*advance(p, 2) = %d\n", *advance(p, 2));
    int **pp = &p;
    printf("**pp = %d\n", **pp);
    take(arr);
    return 0;
}
```

```bash
gcc -O0 -fno-pie -no-pie -g ptr_array.c -o ptr_array
./ptr_array
```

输出：

```
sizeof arr = 16, sizeof p = 8
count = 4
p+1 - p = 1, byte delta = 4
*advance(p, 2) = 30
**pp = 10
sizeof arr inside function = 8
```

逐行对应规则：main 里 arr 还是数组，`sizeof` 是 16（4 个 int）；赋给 p 之后就只剩指针的 8 字节。take 的形参虽然写成 `int arr[4]`，==C 规定数组形参在编译时一律改写成指针==，所以里面 `sizeof` 是 8——gcc 对这一行会给出 `-Wsizeof-array-argument` 警告，警告文本说的就是这个事实。`sizeof arr / sizeof arr[0]` 只在数组定义可见的作用域里才等于元素个数；==出了这个作用域，没有任何办法从指针恢复数组长度==。

### 4.2 指针运算的单位是元素大小

`p + 1` 的"1"是一个元素：p 指向 int 就前进 4 字节，指向 double 就前进 8 字节。上面输出里 `p+1 - p = 1`（指针相减以元素为单位）与 `byte delta = 4`（换成 `char *` 相减才是字节差）是同一个事实的两种读法。advance 的反汇编里，==乘数直接暴露元素宽度==：

```asm
; x86-64 Linux · System V AMD64 ABI（objdump -d -M intel ptr_array 输出，advance 的序言与取参数省略）
  401165:  8b 45 f4                 mov    eax,DWORD PTR [rbp-0xc]   ; eax = i
  401168:  48 98                    cdqe                             ; 下标符号扩展进 rax（见第 8 节）
  40116a:  48 8d 14 85 00 00 00 00  lea    rdx,[rax*4+0x0]           ; i × 4：int 元素宽 4 字节
  401172:  48 8b 45 f8              mov    rax,QWORD PTR [rbp-0x8]   ; rax = p
  401176:  48 01 d0                 add    rax,rdx                    ; rax = p + i*4
```

`lea rdx,[rax*4+0x0]` 没有基址寄存器，只有变址乘 4：==乘数是 4，元素就是 4 字节的 int==；short 数组是 ×2，long 或指针数组是 ×8。辨认顺序与 [[#5. 函数指针、间接调用与那张地址表|第 5 节]]的 ops 表一致：扩展下标 → 乘宽度 → 加基址。

### 4.3 多级指针

指针变量自己也在内存里，也有地址；把它的地址再存进一个指针，就是二级指针 `int **pp`，解引用两次才到 int。ptr_array.c 里的 `int **pp = &p;` 使 `**pp` 输出 10，走的是 pp → p → arr 首元素这条两步链。==二级、三级指针自身的宽度仍是 8 字节==。反汇编里多级指针的形状是==连续多条 mov 解引用==：`mov rax,[pp]` 拿到 p，再 `mov eax,[rax]` 拿到数据。函数参数表里的 `char **argv`、字符串数组、链表结点里套指针，都是这个形状。

两条逆向专属的补充。其一，指针宽 8 字节，这决定了 payload 的语法：==64 位程序里写一个地址就是 8 个字节==，构造输入用 `p64()` 打包（[[03-计算机组成与数据表示|通用基础 03 章]]的字节序一节），数地址先数位数：16 个十六进制位 = 8 字节。其二，数组作参数退化成指针后，长度信息当场丢失：==反汇编里不存在"这个缓冲区多大"这个信息==，只能从读写范围反推——[[02-C语言与内存模型|通用基础 02 章]]4.3 节说过，这也是大量溢出漏洞的源头。

## 5. 函数指针、间接调用与那张地址表

### 5.1 声明、赋值与调用

函数指针的声明语法是 `返回类型 (*名字)(参数列表)`。读法先看内层括号里的 `*名字`：名字是个指针，指向"接收参数列表、返回该类型"的函数：

```c
int (*fp)(int);          /* fp：指针，指向 int(int) 型函数 */
int *fn(int);            /* 没有内层括号：这是返回 int* 的普通函数声明 */
```

==内层括号不能省==，省了语义全变。赋值与调用各有两种等价写法（fptr_basic.c）：

```c
#include <stdio.h>
int add1(int x) { return x + 1; }
int main(void) {
    int (*fp)(int) = add1;      /* 函数名退化成地址，写 &add1 等价 */
    printf("fp(7)    = %d\n", fp(7));
    printf("(*fp)(7) = %d\n", (*fp)(7));

    typedef int (*op_t)(int);   /* typedef 给类型起名 */
    op_t fp2 = add1;
    printf("fp2(7)   = %d\n", fp2(7));
    return 0;
}
```

```bash
gcc -O0 -fno-pie -no-pie -g fptr_basic.c -o fptr_basic
./fptr_basic
```

输出：

```
fp(7)    = 8
(*fp)(7) = 8
fp2(7)   = 8
```

函数名和数组名一样会退化：`add1` 与 `&add1` 是同一个地址；调用时 `fp(7)` 与 `(*fp)(7)` 等价，惯用前者。`typedef int (*op_t)(int);` 之后 op_t 就是完整的类型名——下面这种"一排同型函数指针"的表，没有 typedef 很难写清楚。

### 5.2 逆向里认函数指针

[[02-C语言与内存模型|通用基础 02 章]]4.4 节出现过 `void (*fp)(int) = win;`，ret2win 的"替你调用"也提了。逆向要认的是它的机器形态：==call 的目标是寄存器或内存而不是函数名，这个调用点背后就是函数指针==。直接调用写成 `call <add1>`，间接调用写成 `call rdx`。回调表（fp.c）：

```c
#include <stdio.h>
int add1(int x)   { return x + 1; }
int mul3(int x)   { return x * 3; }
int square(int x) { return x * x; }
int (*ops[3])(int) = { add1, mul3, square };
int run(int i, int v) {
    return ops[i](v);
}
int main(void) {
    for (int i = 0; i < 3; i++)
        printf("ops[%d](7) = %d\n", i, run(i, 7));
    return 0;
}
```

断在 run 上（`break run`），print、x、info symbol 三种查看放一起，输出（节选）：

```
Breakpoint 1, run (i=0, v=7) at fp.c:10
$1 = {0x401136 <add1>, 0x401149 <mul3>, 0x40115f <square>}
$2 = (int (*)(int)) 0x401149 <mul3>
0x404020 <ops>:	0x0000000000401136	0x0000000000401149
0x404030 <ops+16>:	0x000000000040115f
add1 in section .text of /tmp/r2/fp
mul3 in section .text of /tmp/r2/fp
square in section .text of /tmp/r2/fp
```

三种查看指向同一件事：ops 位于 0x404020（.data，可写段），里面并排放着三个 .text 里的代码地址。带调试信息时 print 把符号名标进尖括号；stripped 程序没有这些标注，==info symbol 照样能用——给它一个地址，它报出地址在哪个文件、哪个节==。`disass run` 看地址怎么被用：

```asm
; x86-64 Linux · System V AMD64 ABI（gdb disass run 输出）
mov    eax, DWORD PTR [rbp-0x4]          ; eax = i
cdqe                                      ; i 符号扩展进 rax（int 下标，见第 8 节）
mov    rdx, QWORD PTR [rax*8+0x404020]   ; rdx = ops[i]：取函数地址
mov    eax, DWORD PTR [rbp-0x8]          ; eax = v
mov    edi, eax                          ; 第 1 参数 = v
call   rdx                               ; 间接调用：目标由槽里的值决定
```

重点在最后一条：`call rdx` 去哪，取决于 0x404020 + i×8 那个槽里写的谁，而 .data 是可写的。在断点处现场改一次：

```
(gdb) print ops
$1 = {0x401136 <add1>, 0x401149 <mul3>, 0x40115f <square>}
(gdb) set var ops[1] = add1
(gdb) print ops
$2 = {0x401136 <add1>, 0x401136 <add1>, 0x40115f <square>}
(gdb) disable 1
(gdb) continue
ops[0](7) = 8
ops[1](7) = 8
ops[2](7) = 49
```

mul3 的槽位被换成 add1 之后，`ops[1](7)` 从 21 变成了 8。==函数指针表放在可写段里，改表项就是改控制流==。

### 5.3 同一族地址表

"放满函数地址的表"在逆向里成家族：C 的回调表、C++ 对象头部的虚表、ELF 的 GOT——GOT 由 [[05-ELF文件格式与链接|通用基础 05 章]]拆，虚表属于 C++ 逆向。套路相同：==先找到表，再盯住谁在往表里写==。

## 6. 结构体对齐：ptype /o 直接给答案

两条规则在 [[02-C语言与内存模型|通用基础 02 章]]：==每个成员的偏移必须对齐到自身对齐数，结构体总大小必须是最大对齐数的整数倍==。x86-64 上基本类型的对齐数就是它的宽度：char 1、short 2、int 4、long 与 double 8、指针 8。

为什么要有对齐：CPU 与内存之间的总线一次搬一整块对齐的数据（4 字节或 8 字节）。成员对齐时一次访存读完；成员跨在两块的边界上，x86-64 硬件虽然能处理，但访存次数变多，部分架构（旧款 ARM、SPARC）直接报错。编译器在成员之间和尾部插填充字节，换来每个成员都对齐。

手算走一遍 `struct A { char a; int b; char c; }`：a 对齐数 1，放偏移 0；b 对齐数 4，偏移必须是 4 的倍数，抬到 4，偏移 1–3 是填充（hole）；c 对齐数 1，放偏移 8；总大小抬到最大对齐数 4 的倍数，补到 12。`struct B { int b; char a; char c; }`：b@0、a@4、c@5，尾部补 2 字节，总共 8。同样的三个字段，把 int 放到头部就省 4 字节。

逆向时用 GDB 直接读出布局。两个字段相同、顺序不同的结构体（struct_ab.c）：

```c
#include <stdio.h>
struct A { char a; int  b; char c; };
struct B { int  b; char a; char c; };
int main(void) {
    struct A sa = {1, 2, 3};
    struct B sb = {4, 5, 6};
    printf("sizeof A = %zu, sizeof B = %zu\n", sizeof sa, sizeof sb);
    return 0;
}
```

命令四条：`break main`、`run`、`ptype /o struct A`、`ptype /o struct B`。输出（程序自己的 stdout 是 `sizeof A = 12, sizeof B = 8`）：

```
/* offset      |    size */  type = struct A {
/*      0      |       1 */    char a;
/* XXX  3-byte hole      */
/*      4      |       4 */    int b;
/*      8      |       1 */    char c;
/* XXX  3-byte padding   */

                               /* total size (bytes):   12 */
                             }
```

struct B 同样一张：三个成员落在偏移 0/4/5，尾部 2-byte padding，total 8。==hole（成员间填充）与 padding（尾部填充）ptype /o 全都标出来==，手算结果可以逐项对。

关闭对齐的两种写法（align.c）：`#pragma pack(1)` 与 `__attribute__((packed))`：

```c
#include <stdio.h>
#include <stddef.h>

struct A { char a; int  b; char c; };

#pragma pack(1)
struct P { char a; int  b; char c; };
#pragma pack()

struct __attribute__((packed)) Q { char a; int  b; char c; };

int main(void) {
    printf("A: size=%zu, a@%zu b@%zu c@%zu\n",
           sizeof(struct A),
           offsetof(struct A, a), offsetof(struct A, b), offsetof(struct A, c));
    printf("P: size=%zu\n", sizeof(struct P));
    printf("Q: size=%zu\n", sizeof(struct Q));
    return 0;
}
```

```bash
gcc -O0 -fno-pie -no-pie -g align.c -o align
./align
```

输出：

```
A: size=12, a@0 b@4 c@8
P: size=6
Q: size=6
```

packed 之后没有 hole，1+4+1 正好 6 字节。`#pragma pack(n)` 把对齐数上限压到 n，`__attribute__((packed))` 是 GNU 编译器的等价写法；网络协议头、文件格式的解析代码常用它们做逐字节精确排版。

> [!warning] 逐字节拼字段 = 程序员主动放弃了对齐
> packed 结构没有 hole，成员紧挨着排。反汇编里看到 1 字节粒度的搬运，就按 1 字节粒度还原，==别拿默认对齐规则硬套 packed 数据==。溢出偏移同理，hole 也占地方，[[02-C语言与内存模型|通用基础 02 章]]的警告依然管用——==偏移以工具读出的为准==，ptype /o 和 cyclic 都是工具，选顺手的。

==对齐规则在逆向里的用法是校验==：在 IDA 还原结构体时按偏移摆成员，摆出来的布局违反对齐规则，先怀疑自己猜错了类型。在 IDA 里怎么操作，[[R05-静态分析工具链IDA与Ghidra|R05]]讲。

## 7. 大小端

==多字节整数在内存里按字节怎么排，就是字节序问题==。小端（little-endian）：低位字节放低地址；大端（big-endian）：高位字节放低地址。[[03-计算机组成与数据表示|通用基础 03 章]]给过结论：x86 与 x64 都是小端。

为什么 x86 是小端：Intel 从早期处理器起就采用小端并延续至今，属于硬件设计的历史选择。它在工程上的一个后果是==同一地址按不同宽度去读，低位字节的地址相同==：32 位值 0x12345678 放在小端机器的地址 A 上，从 A 读 1 字节得 0x78，读 2 字节得 0x5678，读 4 字节得 0x12345678——取低位不需要换算地址。大端机器没有这个性质。

这条规则决定两件事：读内存 dump 的方向，读文件里整数的方向。先看内存（endian.c）：

```c
#include <stdio.h>
void show(unsigned char *p) {
    for (int i = 0; i < 4; i++)
        printf("p[%d] = 0x%02X\n", i, p[i]);
}
int main(void) {
    unsigned int x = 0x41424344;
    show((unsigned char *)&x);
    return 0;
}
```

命令五条：`break show`、`run`、`bt`、`print p`、`x/4xb p`。输出：

```
Breakpoint 1, show (p=0x7fffffffe194 "DCBA") at endian.c:4
#0  show (p=0x7fffffffe194 "DCBA") at endian.c:4
#1  0x00000000004011d2 in main () at endian.c:10
$1 = (unsigned char *) 0x7fffffffe194 "DCBA"
0x7fffffffe194:	0x44	0x43	0x42	0x41
```

x = 0x41424344，内存里从低到高却是 `44 43 42 41`。==dump 从左到右是地址升序，小端整数要倒着拼：44 43 42 41 拼回 0x41424344==。GDB 顺手把那 4 字节显示成字符串 "DCBA"，正好把两件事一次讲清：==字符串逐字节排，没有字节序问题，正着读；多字节整数要倒着拼==。

网络字节序是另一套：网络协议头里的多字节整数按大端存放。htonl / htons 把主机序转网络序，ntohl / ntohs 转回来（l 后缀 32 位，s 后缀 16 位）。在本机跑一遍（endian2.c）：

```c
#include <stdio.h>
#include <arpa/inet.h>

int main(void) {
    unsigned int x = 0x12345678;
    unsigned int n = htonl(x);
    unsigned char *p = (unsigned char *)&n;
    printf("htonl(0x12345678) bytes in memory: ");
    for (int i = 0; i < 4; i++)
        printf("%02X ", p[i]);
    printf("\n");
    printf("ntohl(n) = 0x%X\n", ntohl(n));
    return 0;
}
```

```bash
gcc -O0 -fno-pie -no-pie -g endian2.c -o endian2
./endian2
```

输出：

```
htonl(0x12345678) bytes in memory: 12 34 56 78
ntohl(n) = 0x12345678
```

小端机器上 htonl 把字节顺序整个倒了一遍，最高位字节 0x12 落到最低地址——这就是大端排法。工具别用混：==解析网络协议用 hton / ntoh 家族；构造 exploit 输入用 pwntools 的 p32 / p64（按小端打包）==。

文件里的整数一个道理：`printf '\x11\x22\x33\x44' > four.bin` 造个四字节文件，xxd 看到 `1122 3344`，按小端 u32 读就是 0x44332211。[[12-隐写与流量取证|通用基础 12 章]]魔数表里 pcap 的两种开头 `D4 C3 B2 A1` / `A1 B2 C3 D4`，就是同一个数在两种字节序机器上写出来的样子。拿到没见过的格式，==先靠魔数判断这文件按哪个字节序写的，再动手解析==。ELF 文件本身也一样：文件头里声明了字节序字段，x86 上是小端，第 2 节那条 objdump 里 g_init = 42 存的就是 `2a000000`。以后在 hexdump 里看到 `2a000000`，读成 42，别读成 0x2a000000。

## 8. 整型溢出在反汇编里留下的痕迹

[[02-C语言与内存模型|通用基础 02 章]]9 节列过三个整型陷阱：无符号回绕、有符号无符号混比、截断。这节换逆向视角：==类型转换不发生在"概念里"，编译器每次都为隐式转换生成一条看得见的指令==。找到这些指令，就找到了源码里发生过转换的位置。先把宽度与提升交代清楚。

### 8.1 类型宽度与整型提升

x86-64 Linux（LP64 模型）各整数类型的宽度：

| 类型 | 字节数 | 位宽 |
| ---- | ---- | ---- |
| char | 1 | 8 |
| short | 2 | 16 |
| int | 4 | 32 |
| long | 8 | 64 |
| long long | 8 | 64 |
| size_t / 指针 | 8 | 64 |

> [!info]- 平台差异与 char 的符号
> Windows x64 的 long 是 4 字节（LLP64 模型），Linux 是 8 字节——跨平台读结构体、在 IDA 里改类型时先确认 long 宽度。char 是否有符号由编译器决定：x86-64 Linux 上 char 默认有符号，Arm Linux 上默认无符号。long double 在 x86-64 上是 16 字节（x87 扩展精度）。

==整型提升（integer promotion）：比 int 窄的类型（char、unsigned char、short、unsigned short、_Bool）出现在表达式里，先提升成 int 再运算==。x86-64 的 int 是 4 字节，装得下这些类型的全部取值，所以在这台机器上提升结果一律是 int。推论：==比 int 窄的类型不做"窄加法"==，加法、比较都在 32 位 int 里完成，赋回去时才截断。验证程序（int_wrap.c）：

```c
#include <stdio.h>

int main(void) {
    unsigned int u = 0;
    u = u - 1;
    printf("u = %u\n", u);

    unsigned char a = 200, b = 100;
    int t = a + b;
    unsigned char s = a + b;
    printf("t = %d, s = %u\n", t, s);
    return 0;
}
```

```bash
gcc -O0 -fno-pie -no-pie -g int_wrap.c -o int_wrap
./int_wrap
```

输出：

```
u = 4294967295
t = 300, s = 44
```

两行输出各讲一件事。`u = u - 1`：无符号运算定义为==模 2³² 回绕==，0 减 1 得 4294967295（0xFFFFFFFF），==无符号回绕行为有明确定义，不是错误==。`a + b`：a、b 各自提升成 int，200 + 100 = 300，int 装得下，t = 300；同一个值赋回 unsigned char 时==截断低 8 位==得 44。==窄类型的"溢出"通常不发生在运算里，发生在截断里==。

提升在反汇编里的样子（objdump -d -M intel int_wrap 输出，节选，中间的 printf 调用省略）：

```asm
; x86-64 Linux · System V AMD64 ABI
  401142:  c7 45 f8 00 00 00 00  mov    DWORD PTR [rbp-0x8],0x0    ; u = 0
  401149:  83 6d f8 01           sub    DWORD PTR [rbp-0x8],0x1    ; u -= 1：32 位模 2³² 回绕
  401161:  c6 45 f5 c8           mov    BYTE PTR [rbp-0xb],0xc8    ; a = 200
  401165:  c6 45 f6 64           mov    BYTE PTR [rbp-0xa],0x64    ; b = 100
  401169:  0f b6 55 f5           movzx  edx,BYTE PTR [rbp-0xb]     ; a 零扩展提升成 int
  40116d:  0f b6 45 f6           movzx  eax,BYTE PTR [rbp-0xa]     ; b 零扩展提升成 int
  401171:  01 d0                 add    eax,edx                     ; 32 位 int 加法：300
  401173:  89 45 fc              mov    DWORD PTR [rbp-0x4],eax     ; 存进 int t
  401176:  0f b6 55 f5           movzx  edx,BYTE PTR [rbp-0xb]     ; 第二个表达式重新提升一遍
  40117a:  0f b6 45 f6           movzx  eax,BYTE PTR [rbp-0xa]
  40117e:  01 d0                 add    eax,edx
  401180:  88 45 f7              mov    BYTE PTR [rbp-0x9],al       ; 截断：只存低 8 位
```

unsigned char 提升用 movzx（零扩展）；同样的代码换成 signed char 就是 movsx（符号扩展）。==操作数上出现 movzx / movsx，本身就是"这个值来自窄类型"的证据==。

### 8.2 有符号溢出与无符号回绕

无符号整数把运算定义成模 2^N 回绕，行为永远确定。==有符号整数溢出是未定义行为（UB）==：标准不规定结果，编译器可以假设它不发生并据此优化——典型例子是 -O2 下 gcc 把 `i + 1 > i` 直接当作永真。想让有符号运算也按二进制回绕，用 gcc 的 `-fwrapv`，或改用 unsigned。逆向时看到"按源码逻辑走不通、按汇编却自洽"的差异，先想到编译器利用了 UB 做优化。int 与 unsigned 混合比较时 int 转成 unsigned（-1 变最大值）的陷阱，[[02-C语言与内存模型|通用基础 02 章]]9 节列过，下一小节看它落到机器码上的样子。

### 8.3 转换点在反汇编里的样子

带一个 `int → size_t` 转换点的程序（widen.c）：

```c
#include <stdio.h>
#include <string.h>
size_t copy_n(char *dst, const char *src, int n) {
    size_t len = n;             /* int -> size_t, implicit conversion */
    memcpy(dst, src, len);
    return len;
}
int widen_u(unsigned char c) { return c; }
int widen_s(signed char c)   { return c; }
int main(void) {
    char a[16] = "hello";
    char b[16] = {0};
    printf("len = %zu\n", copy_n(b, a, 5));
    return 0;
}
```

objdump 拆 copy_n（逐行注解）：

```asm
; x86-64 Linux · System V AMD64 ABI（objdump -d -M intel widen 输出）
401182:  48 89 7d e8     mov    QWORD PTR [rbp-0x18],rdi  ; dst 落栈
401186:  48 89 75 e0     mov    QWORD PTR [rbp-0x20],rsi  ; src 落栈
40118a:  89 55 dc        mov    DWORD PTR [rbp-0x24],edx  ; n（int，4 字节）落栈
40118d:  8b 45 dc        mov    eax,DWORD PTR [rbp-0x24]  ; 读 n
401190:  48 98           cdqe                             ; ← 痕迹：eax 符号扩展进 rax
401192:  48 89 45 f8     mov    QWORD PTR [rbp-0x8],rax   ; len = n（size_t，8 字节）
401196:  48 8b 55 f8     mov    rdx,QWORD PTR [rbp-0x8]   ; memcpy 第 3 参数
4011a8:  e8 d3 fe ff ff  call   401080 <memcpy@plt>
```

`size_t len = n;` 这一行 C，翻成机器就是 40118d 到 401192 那三条：4 字节读进 eax，cdqe 把符号位铺满高 32 位，8 字节存进 len 的槽。==cdqe 出现 = 这里的 int 正在被当成 64 位用 = 源码里有隐式转换==。gcc 15 在 -O0 下对 int → 64 位生成的是 cdqe（先把 32 位值读进 eax，再一步扩展进 rax）；做同一件事的通用指令是 movsxd（AT&T 名 movslq），常见于直接从内存扩展或 -O2 代码。==看到符号扩展，这个值就是有符号的==。

| 指令 | 动作 | 反推源码类型 |
| ---- | ---- | ----------- |
| `movzx` | 扩展，高位补 0 | 无符号（unsigned char / short / bool） |
| `movsx` / `movslq` | 扩展，高位补符号位 | 有符号 |
| `cdqe` | `eax` 整体符号扩展进 `rax` | int 下标、长度参与 64 位运算 |

同文件的 widen_u 与 widen_s 是一组对照：同是 char 形参，widen_u 用 `movzx eax,BYTE PTR [rbp-0x4]`（高位补 0），widen_s 用 `movsx eax,BYTE PTR [rbp-0x4]`（高位补符号位）——表里第一行的实例。

为什么盯这个？把 copy_n 的 n 换成 -1 就明白了：

```
(gdb) break copy_n
(gdb) run
Breakpoint 1, copy_n (dst=0x7fffffffe180 "", src=0x7fffffffe170 "hello", n=5) at widen.c:5
(gdb) set var n = -1
(gdb) next
6	    memcpy(dst, src, len);
(gdb) print len
$1 = 18446744073709551615
(gdb) print/x len
$2 = 0xffffffffffffffff
```

-1 是全 1，符号扩展之后一个位都没变，size_t 眼里它是 18446744073709551615。==负的下标和长度，经过符号扩展就是巨大的无符号数==，02 章 9 节的陷阱二落到机器码上就是这条 cdqe；继续执行 memcpy 会去写远超映射范围的地址（对照第 2 节的映射表），程序崩溃。配合 jcc 的两套跳转（[[04-汇编语言精要|通用基础 04 章]]：jb/ja 无符号、jl/jg 有符号），类型还原有两条独立证据链，互相印证。

## 9. 三种调用约定的认法

x64 的 SysV 约定 [[04-汇编语言精要|通用基础 04 章]]7.1 讲透：前 6 个整型/指针参数走 `RDI, RSI, RDX, RCX, R8, R9`，返回值在 `RAX`，第 7 个起走栈。本章全部示例都是 x86-64 Linux / System V AMD64 ABI；bt 输出里能直接显示 `leaf (x=7, y=3)`，靠的就是这层约定。cdecl 与 stdcall 属于 32 位世界。四种约定一张表：

| 约定 | 参数位置 | 栈清理方 | 返回值 |
| ---- | ---- | ---- | ---- |
| cdecl（32 位） | 全部压栈，倒序 | 调用者，`add esp, N` | EAX |
| stdcall（32 位） | 全部压栈，倒序 | 被调用者，`ret N` | EAX |
| x64 SysV（Linux/macOS） | 前 6 个整型/指针走 RDI,RSI,RDX,RCX,R8,R9，第 7 个起走栈 | 调用者 | RAX |
| Windows x64 | 前 4 个整型/指针走 RCX,RDX,R8,R9，第 5 个起走栈 | 调用者 | RAX |

cdecl 允许变参——printf 这类函数只有调用者知道自己传了几个参数，只能由调用者清栈——它是 32 位 C 的默认约定；stdcall 是 32 位 Windows API 的约定。Windows x64 要求调用前预留 32 字节 shadow space：哪怕 4 个参数全在寄存器里，也要在栈上备好这 32 字节，被调方可以把寄存器参数存进去再用。

> [!info]- 浮点参数与 32 位的长返回值
> 浮点参数不占整型寄存器：SysV 用 XMM0–XMM7，Windows x64 用 XMM0–XMM3，32 位约定走 x87 浮点栈。32 位程序返回 64 位值（long long）分两半：EDX 放高 32 位，EAX 放低 32 位。

==认约定看三样：参数进没进寄存器、`ret` 后面带不带数、`call` 完有没有 `add esp`==。看到 `ret 8` 收尾，是 32 位 stdcall 的特征；32 位 cdecl 与 x64 SysV 都是调用者清栈。读反汇编前先 `file` 确认平台与位数。32 位约定对 PWN 多一层意义：参数全在栈上，溢出写完返回地址，紧挨着就是参数区——32 位题的 ret2win 摆参数就是这么摆的，到 PWN 批次展开。

### 9.1 保存责任：caller-saved 与 callee-saved

读反汇编绕不开一个问题：==一个寄存器里的值，跨过一次 call 之后还算不算数==。System V 把 16 个通用寄存器分成两类：

| 类别 | 寄存器 | 约定 |
| ---- | ---- | ---- |
| caller-saved（调用者保存，易失） | rax、rcx、rdx、rsi、rdi、r8–r11 | 被调函数可以随意改写；==call 返回后内容不可信==，调用者还要用就得在 call 前自己存好 |
| callee-saved（被调者保存，受保） | rbx、rbp、r12–r15（rsp 另算） | 被调函数想用必须先 push 存底、返回前 pop 还原；==值跨 call 可靠== |

rax 特殊：它是返回值，每次 call 之后必然被改写。落到反汇编上有两条直接推论：

- 函数序言出现 `push rbx` 或 `push r12`–`push r15`，说明函数要跨调用保存值，被保存的就是 callee-saved 寄存器；
- ==跟踪一个跨过 call 的值，先看它当时在不在 callee-saved 里==；在 caller-saved 里，call 之后它已经是别的数据。

完整约定见 [[04-汇编语言精要#3. 寄存器全家桶：约定与保存责任|通用基础 04 章]]的寄存器表。

> [!info]- Windows x64 的划分不同
> Windows x64 把 rbx、rbp、rdi、rsi、r12–r15 都列为 callee-saved（MSDN 术语叫 nonvolatile），比 SysV 多保 rdi 和 rsi。读 Windows 题的汇编按这套判断，套 SysV 的表会把寄存器值判断错。

## 11. 常见问题

| 现象 | 原因与解决 |
| ---- | ---------- |
| gdb -batch -x 一路跑到退出，后面的命令报 `No current process` | 断点没命中：那个函数根本没被调用——比如把断点下在没人调用的 probe 上，gdb 直接跑完。先确认执行路径，再下断 |
| print 变量显示 0x0 | 赋值语句还没执行到，先 `next` 走到赋值之后；或者断进一个专门用来观察的函数（endian.c 的 show 就是这么设计的） |
| 形参写成 `int arr[4]`，里面 sizeof 却是 8 | 数组形参一律按指针处理，长度信息在形参里不存在（见第 4 节） |
| ptype 报 `No type named struct A` | 编译没加 `-g`，二进制里没有调试信息 |
| `x/2gx $rbp` 看到的"返回地址"不像代码地址 | 人不在你以为的那一帧。先 `bt` 确认当前帧号，再 `frame N` |
| objdump 里找不到 movslq 只有 cdqe | 同一件事的两种写法，gcc 15 在 -O0 下生成 cdqe，见第 8 节 |
| info symbol 报 `No symbol matches` | 地址不在符号表里：二进制被 strip，或者地址本身算错了 |
| 程序每次跑地址都不一样 | ASLR 在工作；GDB 默认关闭 ASLR，调试时地址稳定（[[03-计算机组成与数据表示\|通用基础 03 章]]） |
| 32 位程序里对不上 cdqe / rax | 32 位没有这两样，对应的是 eax / cwde；先 `file` 确认位数再读 |
