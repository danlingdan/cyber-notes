# R9 加壳与脱壳
## Packing & Unpacking

> [!info]- 章节信息
> **所属方向**：逆向工程 ｜ **难度阶段**：L2 核心题型期 ｜ **前置要求**：[[R04-可执行文件格式ELF与PE|R04]] · [[R05-静态分析工具链IDA与Ghidra|R05]] · [[R06-动态调试GDB与x64dbg|R06]]
> **本章目标**：能说清壳的三类目标与"入口劫持 → 运行时还原 → 跳 OEP"的工作原理；掌握查壳的四类手工特征；用 UPX 完成一次完整的自动脱壳并逐字节确认还原结果；掌握手动脱壳四步法（定位 OEP、dump 内存、重建 IAT、验证）的原理与 x64dbg 操作路径；能识别并清理花指令。
> **示例平台**：x86-64 Linux（System V AMD64 ABI）；手动脱壳一节以 32 位 Windows PE（x86）为对象。

## 1. 壳是什么，为什么要加壳

### 1.1 定义

加壳（packing）：把原程序的代码与数据压缩或加密成一段数据，在它外面接一段小程序——壳代码，英文资料称 **stub**。发布出去的文件里，入口指向的不是原程序，而是 stub；运行时由 stub 把原程序还原进内存，再把控制权交给原程序的第一条指令。脱壳（unpacking）是反过程：拿到还原后的原程序，或把内存里的还原结果存回文件。

对静态分析的影响直接而彻底：[[R05-静态分析工具链IDA与Ghidra|R05]] 的整条流程（strings 提线索 → 定位校验函数 → 伪代码）建立在"文件里有原代码"之上；加壳后文件里没有明文代码，这套流程全部失效。[[R04-可执行文件格式ELF与PE|R04]] 讲过"程序头删不得，节区表删得"——壳把这句话用到了极致（第 4 节有 `readelf -S` 报 There are no sections 的输出）。

### 1.2 为什么要加壳

| 动机 | 说明 |
| ---- | ---- |
| 压缩体积 | 发行文件更小。UPX 的全名 Ultimate Packer for eXecutables，压缩是它的原始定位 |
| 对抗静态分析 | 字符串、代码、常量表在文件里不存在，strings 搜不到，IDA 读不了 |
| 商业软件保护 | 配合授权校验抬高破解成本，是加密壳的主要市场 |
| 规避查杀 | 恶意软件用壳隐藏特征码躲扫描。CTF 里来路不明的加壳样本按不可信文件对待（R04 对 ldd 的 warning 同样适用） |

### 1.3 三类壳

| 类别 | 目标 | 代表 | 运行时行为 | 脱壳方式 |
| ---- | ---- | ---- | ---- | ---- |
| 压缩壳 | 减小体积 | UPX、ASPack、MEW | 解压还原，原代码逐字节回到内存 | 多有现成工具，UPX 一条命令 |
| 加密壳 | 对抗静态分析 | ASProtect、tElock、Armadillo | 解密后执行，常带完整性校验与反调试 | 一般没有通用工具，走第 5 节手动四步法 |
| 虚拟机壳 | 对抗分析与调试 | VMProtect、Code Virtualizer | 把原代码翻译成自定义虚拟机的指令，由壳内解释器执行 | 高难度，后续章节专门展开，本章不涉及 |

==三类壳的目标逐级递进：压缩壳改变的是体积，加密壳改变的是"读得到读不到"，虚拟机壳改变的是"指令还是不是原来的指令"==。

> [!info]- 术语：stub 与 OEP
> stub 指壳代码本身；一套壳 = stub（程序）+ 压缩/加密数据（被保护内容）。OEP（Original Entry Point，原始入口点）指原程序自己的入口地址：壳的文件入口指向 stub，OEP 才是原程序开始执行的位置。"找到 OEP"是手动脱壳的核心问题（第 5 节）。

## 2. 壳的工作原理：入口劫持与运行时还原

### 2.1 stub 的三步

以 PE 壳为例（对应到 ELF 时字段换成 `e_entry`，机制相同）：

1. **入口劫持**：把 Optional Header 的 `AddressOfEntryPoint`（[[R04-可执行文件格式ELF与PE#3.5 Optional Header|R04 3.5]]）改指到 stub 的起始地址；原节的代码与数据压缩/加密后搬进壳安排的节，节表同步改写。ELF 侧同一个动作是改 `e_entry`（第 4 节有前后对比）。
2. **运行时还原**：系统 loader 照常装载文件，从入口开始执行的是 stub。stub 先保存现场——32 位 PE 上是一条 `pushad`，把 8 个通用寄存器共 32 字节压栈——随后申请内存，把压缩数据解压/解密回原程序的形态。
3. **跳 OEP**：还原完成，`popad` 恢复现场，最后一条 `jmp` 跳到 OEP。此后执行流与未加壳程序完全一致；壳的字节还留在内存里，但不再被执行。

> [!info]- x64 上没有 pushad
> `pushad`/`popad` 是 32 位指令，x64 已删除。64 位壳改用 8 条 `push` 逐个保存寄存器，[[#5.1 第一步：定位 OEP——栈平衡法（ESP 定律）|5.1 节]]的栈平衡思路不变：盯住保存点，等恢复点来碰它。

### 2.2 同一个程序，文件与内存两种形态

| | 文件里（静态） | 内存里（stub 执行完） |
| ---- | ---- | ---- |
| 原程序代码 | 不存在明文，是压缩/加密数据 | 已还原，位于可执行区域 |
| 常量与字符串 | 混在压缩数据里，strings 搜不到 | 明文，R05 的字符串窗口重新可用 |
| stub | 入口指向它 | 字节还在，执行流已离开 |
| 导入信息（PE 的 IAT） | 被壳改写或清空，常只剩 stub 自用的几个 API | stub/loader 已把原程序的导入补回 |

==静态分析读文件，壳把答案搬进了运行时；脱壳就是把运行时形态存回文件==。第 4 节的 UPX 实验把这张表逐行落实：`readelf -S` 无节区、`file` 判定改变、还原后的入口代码在文件里根本不存在。

### 2.3 预备知识：FileSiz 与 MemSiz 的差值

[[R04-可执行文件格式ELF与PE#1.1 链接视图与执行视图：两套目录|R04 1.1]] 讲过 LOAD 段的 FileSiz（文件里占多少）与 MemSiz（内存里占多少），正常 ELF 里两者之差只是 `.bss` 的几个字节。壳把这个差值放大成整个原程序的大小：压缩数据随文件装载（计入 FileSiz），解压结果写到另一块内存（计入 MemSiz）。第 4 节的加壳文件里会看到一个 LOAD 段文件里 0x1000 字节、内存里要 0x4038 字节——多出来的 0x3038（12344）字节就是运行时才被填进来的原程序镜像。

## 3. 查壳：工具与手工特征

拿到一个文件，判断有没有壳、是什么壳，叫查壳。先查壳再分析：文件加着壳时，strings 搜不到线索不是题目没给线索，是线索被压走了。

### 3.1 工具

- **PEiD**：老牌 Windows 查壳工具，靠内置特征签名匹配。2000 年代的产物，已停更，对之后的壳基本认不出。知道名字即可。
- **Detect It Easy（DIE）**：现役开源工具，签名库持续更新，支持 PE/ELF/Mach-O，Windows/Linux/macOS 全平台（GitHub 见延伸阅读）。GUI 操作路径：把文件拖进主窗口 → 主界面显示识别结果（壳/编译器/链接器与版本）→ 点 Entropy 按钮查看整体与逐区段的熵曲线，压缩或加密的区域在曲线上是一段高台。另带命令行版 diec，适合批量过文件。

> [!note] UPX 壳可以不查就知道
> `upx -l 文件` 能直接读出 UPX 的加壳信息（4.5 节有输出）。工具认不出的魔改 UPX，用 3.2 的手工特征。

### 3.2 手工特征：工具认不出时的四条线索

签名库永远追不上新壳与魔改壳，四条不依赖签名的线索按序检查：

**一、节名。** UPX 的 PE 产物节名固定是 `UPX0`、`UPX1`（外加存杂项的 `UPX2`）；其他壳也有各自的命名习惯（`.aspack`、`.themida` 之类）。看到陌生节名先查。但节名只是一个字符串，==改节名是最便宜的对抗手段，节名认不出壳不等于没壳==。

**二、节区属性与大小异常。** 正常 PE 的 `.text` 可执行不可写，壳节常是可写又可执行。更硬的判据在大小关系：正常节 `SizeOfRawData` 不为零、与 `VirtualSize` 相差无几（[[R04-可执行文件格式ELF与PE#3.6 节表与 RVA 换算|R04 3.6]]）；壳的还原目标节正相反——文件里 `SizeOfRawData` 为 0 或极小，`VirtualSize` 却很大，运行时才被 stub 填满。`UPX0` 是典型：VirtualSize 覆盖整个原程序，SizeOfRawData 是 0。

**三、熵升高。** 熵衡量字节分布的混乱程度：

$$H = -\sum_{i=0}^{255} p_i \log_2 p_i \tag{9.1}$$

$p_i$ 是字节值 $i$ 在文件中出现的频率，$H$ 的单位是比特/字节，上限 8（完全随机）。十几行 Python 就能算整文件熵：

```python
#!/usr/bin/env python3
"""entropy.py —— 计算整文件的香农熵：python3 entropy.py <文件>"""
import sys, math

data = open(sys.argv[1], "rb").read()
cnt = [0] * 256
for b in data:
    cnt[b] += 1
n = len(data)
H = -sum((c / n) * math.log2(c / n) for c in cnt if c)
print(f"{sys.argv[1]}: {n} bytes, entropy = {H:.3f} bits/byte")
```

经验值：正常代码段的熵在 5–6.5 之间；压缩或加密过的区域普遍高于 7.2。第 4 节有一组前后对比：同一程序加壳前 1.658、加壳后 7.274——小文件未压缩时大量补零与重复内容拉低整体熵，加壳前后反差因此特别大。==高熵提示压缩或加密，但不能单独定案==：整段加密数据、资源文件同样高熵；要与节区异常、导入表骤减组合使用。

> [!info]- 整体熵会被稀释：看分区熵
> 整文件熵是全文件的平均值，大块低熵数据（补零、明文字符串）会把高熵区域拉平。DIE 的 Entropy 曲线按文件偏移画，压缩块的位置对应曲线上的高台，比单个整体值可靠。自己算分区熵：把 entropy.py 按 R04 的节区表切开来逐节算。

**四、导入表骤减。** PE 的导入表（[[R04-可执行文件格式ELF与PE#3.7 导入表与 IAT|R04 3.7]]）原本罗列程序用到的全部外部函数；加壳后常只剩几个——stub 自己只需要这些：

| 剩下的导入函数 | stub 拿它干什么 |
| ---- | ---- |
| `LoadLibraryA` / `GetProcAddress` | 运行时把原程序的导入逐个补回来 |
| `VirtualAlloc` / `VirtualFree` | 申请、释放还原过程需要的内存 |
| `VirtualProtect` | 改页权限（解压目标区要改成可执行） |
| `ExitProcess`、`GetVersion` 等杂项 | 收尾与环境探测 |

正常程序极少只依赖这一小撮 API。==导入表只剩 `LoadLibraryA`、`GetProcAddress`、`VirtualAlloc` 一类，基本可以定性有壳==。ELF 侧的对应现象更彻底：动态信息整个消失（4.5 节 `readelf -d` 的输出）。

## 4. UPX 专项：加壳、识别与自动脱壳

UPX 是开源跨平台壳（GitHub 见延伸阅读），支持 PE、ELF、Mach-O 与多种 CPU 架构，CTF 里出场率最高、也是唯一"一条命令脱壳"的壳。本节在 Linux 里把一个自编译的 ELF crackme 完整走一遍：打包 → 前后对比 → 特征识别 → 还原 → 逐字节确认。

安装：

```bash
sudo apt install upx-ucl        # Debian/Ubuntu 包名 upx-ucl，命令名 upx
```

### 4.1 靶子

```c
/* crackme.c —— 本章 UPX 实验用的小程序 */
#include <stdio.h>

int main(void) {
    char buf[16] = {0};
    static const unsigned char enc[6] = {0x42, 0x59, 0x47, 0x56, 0x54, 0x5C};
    printf("key: ");
    if (scanf("%15s", buf) != 1)
        return 1;
    for (int i = 0; i < 6; i++) {
        if ((unsigned char)(buf[i] ^ 0x37) != enc[i]) {
            puts("wrong key");
            return 1;
        }
    }
    puts("correct: flag{upx_1s_3asy}");
    return 0;
}
```

key 是 `unpack`（逐字节异或 0x37 等于 `enc` 表）。流程与 [[R05-静态分析工具链IDA与Ghidra|R05]] 第 2 节的 crackme 同型；本节不关心破解它，只用它当加壳对象。

```bash
gcc -O0 -fno-pie -no-pie crackme.c -o crackme
file crackme
readelf -h crackme | grep "Entry point"
echo unpack | ./crackme
```

输出：

```
crackme: ELF 64-bit LSB executable, x86-64, version 1 (SYSV), dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2, BuildID[sha1]=9cf96de2e17b02b3e35097d1b69df5f56a085e5b, for GNU/Linux 3.2.0, not stripped
  Entry point address:               0x4010b0
key: correct: flag{upx_1s_3asy}
```

基准值记下：16056 字节（4.3 的 `ls -l`）、入口 `0x4010b0` 指向 `_start`（[[R04-可执行文件格式ELF与PE#1.6 入口点：_start 与 main|R04 1.6]]）、31 个节区。

### 4.2 加壳

```bash
upx -o crackme_packed crackme      # -o 指定输出文件，原文件保留
```

输出：

```
                       Ultimate Packer for eXecutables
                          Copyright (C) 1996 - 2024
UPX 4.2.4       Markus Oberhumer, Laszlo Molnar & John Reiser    May 9th 2024

        File size         Ratio      Format      Name
   --------------------   ------   -----------   -----------
     16056 ->      6220   38.74%   linux/amd64   crackme_packed

Packed 1 file.
```

16056 字节压到 6220。不带 `-o` 时 UPX 原地改写文件，练习时建议都带 `-o`。

### 4.3 加壳前后对比

```bash
ls -l crackme crackme_packed
file crackme_packed
readelf -h crackme_packed | grep "Entry point"
readelf -SW crackme_packed
```

输出：

```
-rwxr-xr-x 1 hua hua 16056 Oct 21 08:39 crackme
-rwxr-xr-x 1 hua hua  6220 Oct 21 08:39 crackme_packed
crackme_packed: ELF 64-bit LSB executable, x86-64, version 1 (SYSV), statically linked, no section header
  Entry point address:               0x4057a0

There are no sections in this file.
```

逐项对比：

| 观察 | crackme | crackme_packed |
| ---- | ---- | ---- |
| 大小 | 16056 字节 | 6220 字节（38.74%） |
| `file` 判定 | dynamically linked … not stripped | statically linked, no section header |
| 节区表 | 31 个节区 | 无，`readelf -S` 报 There are no sections |
| `e_entry` | 0x4010b0（指向 `_start`） | 0x4057a0（指向 stub） |
| 动态链接信息 | `.dynamic` / `.dynsym` 都在 | `readelf -d` 报 There is no dynamic section（4.5） |
| 整文件熵 | 1.658 | 7.274（4.5） |

三件事对应 2.2 的表格：

- `file` 报 statically linked 并不表示它真的不需要 libc——描述文件头的方法在加壳文件上失真了。==链接状态别只信 `file` 一句话==。
- 节区表整个消失：[[R04-可执行文件格式ELF与PE#2.1 同一份源码的两种产物|R04 2.1]] 的 warning 预告过"把节区表也删掉的是 sstrip 或壳"，这就是那个实例。此后分析只能走程序头（`readelf -l`）。
- 入口从 `_start` 换成 0x4057a0：2.1 的入口劫持。

### 4.4 壳的布局：程序头里的还原现场

```bash
readelf -lW crackme_packed
```

输出：

```

Elf file type is EXEC (Executable file)
Entry point 0x4057a0
There are 3 program headers, starting at offset 64

Program Headers:
  Type           Offset   VirtAddr           PhysAddr           FileSiz  MemSiz   Flg Align
  LOAD           0x000000 0x0000000000400000 0x0000000000400000 0x001000 0x004038 RW  0x1000
  LOAD           0x000000 0x0000000000405000 0x0000000000405000 0x001285 0x001285 R E 0x1000
  GNU_STACK      0x000000 0x0000000000000000 0x0000000000000000 0x000000 0x000000 RW  0x10
```

两个 LOAD 段对照 2.3 的预热：

- 第二个 LOAD（`R E`，0x405000 起）：文件内容的主体，stub 与压缩数据都在这里，入口 0x4057a0 落在其中——系统装载后从 stub 开始执行。
- 第一个 LOAD（`RW`，0x400000 起）：FileSiz 只有 0x1000，MemSiz 却要 0x4038，差的 0x3038 个字节在文件里一个字节都没有。stub 执行时把解压出来的原程序写到这里。==原程序在文件里不存在，在内存里按段就位==——2.2 的表格在程序头上落实了。

对照正常 ELF：[[R04-可执行文件格式ELF与PE#1.1 链接视图与执行视图：两套目录|R04 1.1]] 的 lic_full 用 4 个 LOAD 段分装代码、只读数据、可写数据，FileSiz 与 MemSiz 的差只有 `.bss` 的几个字节；壳把它压成 2 个 LOAD，并把差值放大成整个原程序。

### 4.5 特征复核：3.2 的四条线索逐一应验

**标记。** 最直接的有壳证据，UPX 自己写进文件的说明信息：

```bash
strings crackme_packed | grep -a UPX
```

输出：

```
UPX!
$Info: This file is packed with the UPX executable packer http://upx.sf.net $
$Id: UPX 4.24 Copyright (C) 1996-2024 the UPX Team. All Rights Reserved. $
UPX!u
UPX!
UPX!
```

`$Info` / `$Id` 是 UPX 的自述字符串，`UPX!` 是它头部的魔数（`upx -d` 靠这组结构还原文件）。

**熵。** 用 3.2 的脚本：

```bash
python3 entropy.py crackme
python3 entropy.py crackme_packed
```

输出：

```
crackme: 16056 bytes, entropy = 1.658 bits/byte
crackme_packed: 6220 bytes, entropy = 7.274 bits/byte
```

**`upx -l`。** 不解包就能读出加壳信息，兼做第 3.1 节"UPX 壳可以不查就知道"的注脚：

```bash
upx -l crackme_packed
```

输出：

```
                       Ultimate Packer for eXecutables
                          Copyright (C) 1996 - 2024
UPX 4.2.4       Markus Oberhumer, Laszlo Molnar & John Reiser    May 9th 2024

        File size         Ratio      Format      Name
   --------------------   ------   -----------   -----------
     16056 ->      6220   38.74%   linux/amd64   crackme_packed
```

**动态信息消失。** 3.2 第四条线索的 ELF 侧形态：

```bash
readelf -d crackme_packed
```

输出：

```

There is no dynamic section in this file.
```

原文件的 `.dynamic`、`.dynsym` 随节区表一起被压走——导入表"骤减"在 ELF 上表现为整个消失，运行时由 stub 一手安排。

> [!warning] strings 在加壳文件上仍可能搜到零星明文
> 上面的 packed 文件里，`key: ` 与 `flag{upx_1s_3asy}` 仍能被 strings 搜到——压缩流里存在未被压掉的小片段。==判断有壳看标记、节区、入口与熵，不看"字符串还能不能搜到"==；反过来，搜不到字符串也不能直接定案有壳，可能只是程序本身没有多少字符串。

### 4.6 自动脱壳：upx -d 与逐字节确认

```bash
upx -d -o crackme_unpacked crackme_packed
cmp crackme crackme_unpacked && echo "cmp: identical"
ls -l crackme_unpacked
echo unpack | ./crackme_unpacked
```

输出（UPX 横幅行省略）：

```
Unpacked 1 file.
cmp: identical
-rwxr-xr-x 1 hua hua 16056 Oct 21 08:39 crackme_unpacked
key: correct: flag{upx_1s_3asy}
```

三重确认：UPX 报告解包成功；`cmp` 逐字节对比无差异（cmp 的规则：一致时静默，退出码 0）；脱壳产物运行输出与原文件相同。==`upx -d` 之所以一键，是因为 UPX 在文件里留下了完整的自描述结构==，工具照着读、按部就班还原即可。

> [!info]- upx 常用参数
> `upx -o 输出 原文件` 加壳并保留原文件；`upx 原文件` 原地加壳；`upx -d -o 输出 加壳文件` 脱壳；`upx -l 文件` 列加壳信息；`upx -t 文件` 自检压缩数据完整性；`--best` 最高压缩级别（更慢、更小）。`upx -h` 看全表。

> [!info]- upx -d 拒绝处理的两种情况
> 报 `NotPackedException`：文件头里找不到 UPX 的自描述结构——不是 UPX 壳，或标记被抹；报 `CantUnpackException`：结构在，但版本不兼容或数据校验不过。前者按第 5 节手工路线走，或把特征修回去再试（配套练习第 2 题）；后者换对应版本的 upx（GitHub Releases 存有历史版本）。

### 4.7 UPX 在 PE 与 ELF 上的形态差异

同一个 UPX，两种格式上留下的痕迹不同：

| 痕迹 | PE 上 | ELF 上（本节所见） |
| ---- | ---- | ---- |
| 节区 | 节区表还在，节名 `UPX0` / `UPX1` / `UPX2` | 节区表整个消失 |
| 导入信息 | 骤减到 stub 自用的几个 API | `.dynamic` / `.dynsym` 整个消失 |
| 识别标记 | 节名 + 头部 `UPX!` | 头部 `UPX!` 与 `$Info` / `$Id` 字符串 |
| `file` 判定 | 仍报 PE 可执行 | 报 statically linked, no section header |

原因不难理解：ELF 的节区表本来就"可删"（[[R04-可执行文件格式ELF与PE#1.1 链接视图与执行视图：两套目录|R04 1.1]]），UPX 顺手删掉；PE 的节表是 loader 装载必需的，只能改写、不能删除。

## 5. 手动脱壳四步法（x64dbg）

`upx -d` 依赖壳的自描述结构。加密壳没有对应工具，魔改壳把工具的识别依据破坏掉——这时四步法是通用框架。本节以 32 位 PE 加壳程序为对象，工具是 x64dbg（32 位目标用 release/x32/x32dbg.exe，[[R06-动态调试GDB与x64dbg#12.1 安装、版本选择与界面|R06 12.1]]）；GUI 操作只写路径，不引用具体界面数值。

四步：**定位 OEP → dump 内存 → 重建 IAT → 验证**。

### 5.1 第一步：定位 OEP——栈平衡法（ESP 定律）

问题：stub 有成千上万条指令，逐条单步跟到跳 OEP 不现实。ESP 定律用一个断点解决。

**原理。** 2.1 说过：stub 开头 `pushad` 把 EAX、ECX、EDX、EBX、ESP、EBP、ESI、EDI 八个寄存器压栈（32 字节），此刻 ESP 指向这份副本；结尾 `popad` 必须从同一个位置把这 32 字节读回来——pushad 与 popad 的栈指针必然相等，这就是"栈平衡"。==对 pushad 时 ESP 指向的地址下一个访问断点，程序下一次碰它只会是 popad==：断点命中时正站在 stub 的收尾处，向下几条指令就是跳 OEP 的那条 jmp。机制上就是硬件断点盯内存读（[[R06-动态调试GDB与x64dbg#4. 观察点：watch、rwatch、awatch|R06 第 4 节]]的观察点原理，这里盯的对象是"寄存器现场的副本"）。

**x64dbg 操作路径。**

1. File → Open 打开加壳 EXE，程序停在系统断点；按 F9 运行，停在入口——`AddressOfEntryPoint` 指向的 stub 第一条指令，通常就是 `pushad`。
2. F8 单步执行这条 `pushad`，右上寄存器窗的 ESP 变为压栈后的值。
3. 右键 ESP 的值 → Follow in Dump（在转储中跟随），左下 dump 窗跳到该地址。
4. 选中该地址起的 4 字节 → 右键 → Breakpoint → Hardware, Access → DWORD：对这 4 字节下硬件访问断点。等价命令是在底部命令栏输入 `bphws 地址, r, 4`。
5. F9 放行。`popad` 读回副本时断点命中，程序停在 popad 之后的指令上。
6. 从停下的位置继续 F8，遇到一条跳进陌生区域的 jmp/call，跳转目标就是 OEP。

**两个备选定位法**（ESP 定律失效时用——有的壳不守规矩，在 popad 之前先把副本挪走）：

- **内存执行断点法**：Memory Map 标签页里找到原程序代码所在的内存段，右键设置 execute 断点——原代码第一次被执行必然在 OEP 附近。
- **运行时特征法**：先放行让程序跑起来（壳通常在 OEP 之前就完成还原），此时按 [[R06-动态调试GDB与x64dbg#12.3 字符串引用搜索定位校验函数|R06 12.3]] 的方法搜字符串引用，原程序的提示语已经出现；从字符串引用回溯到所属函数，函数入口就是 OEP。

> [!info]- 为什么停在 popad 后面还要再单步几条
> popad 不是 stub 的最后一条指令，之后常有搬运数据、修正指针的收尾指令，最后一条远跳才是交权。判定"这条跳转去的是 OEP"的标准：目标在 stub 区域之外，且反汇编形态变成正常程序代码（函数序言、对库函数的调用，[[R03-x86与x64汇编精要复习|R03]] 的代码形状）。

### 5.2 第二步：dump 内存

停在 OEP 时，原程序已完整还原在内存里。dump 就是把这块内存按 PE 的布局写回文件——把 2.2 表格"内存里"那一列存成静态文件。x64dbg 新版内置 **Scylla**（脱壳辅助工具，独立版见延伸阅读）：停在 OEP 时打开 Plugins 菜单 → Scylla，设定 OEP 地址后点 Dump，生成 dump 文件。dump 文件已包含还原后的代码与数据，但导入表还是坏的——下一步处理。

> [!note] dump 与 R06 的动态取值是同一件事的两种产出
> [[R06-动态调试GDB与x64dbg#10.2 四步流程：断点、回溯、finish、dump|R06 10.2]] 在停下的瞬间把栈上的密钥读出来用；这里是把停下的瞬间整个进程镜像存回文件。时机都是"答案成形、程序还没走远"。

### 5.3 第三步：重建 IAT

dump 完直接用会失败，IAT 有两层损坏：

1. **运行时地址不能回文件。** IAT 里此刻是本次运行 loader 填的 DLL 内部绝对地址；dump 文件下次加载时系统 DLL 基址已变（ASLR），这些地址全部失效。
2. **壳动过 IAT。** 加壳时原 IAT 被壳替换或搬移，原代码里的 `call [IAT槽]` 在文件层面指向壳的跳板，运行时 stub 才把真地址写回。dump 拍下的是"写回之后"的内存快照，文件层面的导入结构并没有随之恢复。

Scylla 的修复原理：从 OEP 的代码出发，扫描所有对 IAT 槽位的引用（`call` / `jmp [地址]`），收集这些槽位当前指向的地址；再反查各系统 DLL 的导出表（[[R04-可执行文件格式ELF与PE#3.8 导出表|R04 3.8]]），把地址翻译回函数名；据此重建一张干净的导入表，并改写 dump 文件的 DataDirectory 指向它。操作顺序：Scylla 里 IAT Autosearch → Get Imports → 检查列表中的无效条目（右键删除可疑项）→ Fix Dump，生成修复版 `*_SCY.exe`。

### 5.4 第四步：验证脱壳结果

| 检查 | 做法 | 不过关说明 |
| ---- | ---- | ---- |
| OEP 处代码正常 | 反汇编 OEP 附近：函数序言、调用形态与未加壳程序一致 | 还没走到真正的 OEP，回 5.1 |
| 字符串回来 | strings / DIE / IDA 字符串窗口能看到原程序的提示语 | dump 时机太早或数据段没对上，回 5.2 |
| 行为一致 | 运行 dump 文件，与加壳文件行为相同 | IAT 没修干净，或壳带完整性校验，回 5.3 |

三项都过，脱壳才算完成。

> [!info]- OEP 附近的常见代码形态
> VC 编译的程序 OEP 前后常见连续 push 寄存器加一串初始化 call；Delphi 程序 OEP 处常是 `push` 一个大立即数随后 call 窗口管理初始化。记住目标编译器的大致形态，有助于确认"站在 OEP 上"。

> [!note] ELF 的手工脱壳
> 四步法的思想——等还原完成、把内存存回文件、修运行时结构、验证——在 ELF 上同样成立：GDB 断在解压完成点，用 gcore 或 /proc 下的内存镜像取回数据，手工重建 ELF 头、程序头与重定位。工具链比 PE 侧原始，工作量也大；好在比赛里 ELF 的壳绝大多数是 UPX，`upx -d` 直接解决。更多 crackme 实战流程见 [[R08-CrackMe经典题型|R08]]。

## 6. 花指令初步

### 6.1 是什么

花指令（junk code）：混进代码流的垃圾字节，配一条跳转指令从它上面跨过去。对执行没有影响——真执行流走跳转，垃圾字节永远轮不到被执行；对反汇编有影响——objdump、IDA 的初始分析都按地址顺序**线性解码**，不会执行跳转，读到垃圾字节就把它当指令拆，从那里开始解错位。[[R05-静态分析工具链IDA与Ghidra#3.7 F5 伪代码：能力与局限|R05 3.7]] 提过"花指令与混淆"会让伪代码不可信、sp-analysis failed 常由它引起——本节把它拆开：是什么、怎么认、怎么清。

壳的 stub 里也常见花指令，用来干扰对 stub 本身的分析；更成体系的对抗手段（反调试等）见 [[R10-反调试与反分析对抗|R10]]。

### 6.2 一个带花指令的程序

junk.c（x86-64 Linux，gcc 编译，内联汇编为 AT&T 语法）：

```c
/* junk.c —— 花指令实验：一个永远不执行的 0xE8 字节 */
#include <stdio.h>

__attribute__((noinline))       /* 防止内联，保证 check 独立成函数 */
int check(int x) {
    __asm__ volatile (
        "jmp 1f\n\t"            /* 向前跳过 1 个字节       */
        ".byte 0xE8\n"          /* 垃圾字节：call 的操作码 */
        "1:\n\t"
    );
    return x ^ 0x5A;
}

int main(void) {
    printf("%d\n", check(0x1234));
    return 0;
}
```

花指令就是中间两行：`jmp 1f` 跳过紧跟的 1 个字节 `0xE8`，落到真实代码。0xE8 本身是 call 的操作码，而 call 带一个 4 字节相对位移——线性反汇编读到它时，会把 `0xE8` 和**后面 4 个字节的真实指令**并成一条假 call。

```bash
gcc -O0 -fno-pie -no-pie junk.c -o junk
objdump -d -M intel junk | sed -n '/<check>:/,/^$/p'
```

输出：

```
0000000000401136 <check>:
  401136:	f3 0f 1e fa          	endbr64
  40113a:	55                   	push   rbp
  40113b:	48 89 e5             	mov    rbp,rsp
  40113e:	89 7d fc             	mov    DWORD PTR [rbp-0x4],edi
  401141:	eb 01                	jmp    401144 <check+0xe>
  401143:	e8 8b 45 fc 83       	call   ffffffff843c56d3 <_end+0xffffffff83fc16b3>
  401148:	f0 5a                	lock pop rdx
  40114a:	5d                   	pop    rbp
  40114b:	c3                   	ret
```

逐行对照真实情况：

| objdump 显示 | 实际是什么 |
| ---- | ---- |
| `401141: eb 01  jmp 401144` | 正确。真执行流，跳过 1 字节 |
| `401143: e8 8b 45 fc 83  call ffffffff843c56d3` | 假 call。这 5 个字节 = 垃圾字节 e8 + 真实指令 `mov eax,[rbp-0x4]` 的 8b 45 fc + `xor eax,0x5a` 的首字节 83 |
| `401148: f0 5a  lock pop rdx` | 错位解码的残余：真实指令 `xor eax,0x5a` 只剩 f0 5a 两个字节，f0 被当成了 lock 前缀 |
| `40114a: 5d  pop rbp`、`40114b: c3  ret` | 重新对齐，恢复正确 |

程序运行完全正常：

```bash
./junk
```

输出：

```
4718
```

4718 = 0x1234 ^ 0x5A = 0x126E。==花指令不改变执行，只改变反汇编视图==：运行时 rip 从 401141 直达 401144，假 call 那两行从未被执行过。

### 6.3 识别

三个信号，命中其一就该怀疑花指令：

1. **荒谬的目标地址**：call/jmp 的目标落在 `_end` 之后、节区之外或明显不是代码的位置。上例假 call 的目标 `ffffffff843c56d3` 就是个不存在的地址。
2. **执行流对不上**：从函数入口沿真实执行流走一遍（[[R06-动态调试GDB与x64dbg|R06]] 的单步），凡真执行流没经过的"指令"都可疑。上例单步会看到 rip 从 401141 直接到 401144，401143 处什么都没发生。
3. **错位特征**：反常的指令——`lock` 前缀出现在无意义的位置、超长指令、解到一半开始出乱码。

IDA 里的表现：图形视图出现孤立小块或灰色不可识别区域，F5 输出缺代码。处理原则同 [[R05-静态分析工具链IDA与Ghidra#3.7 F5 伪代码：能力与局限|R05 3.7]] 的警告：回汇编视图核对。

### 6.4 清理：nop 填充

思路：把垃圾字节改成 0x90（x86 的 nop，单字节、无副作用）。真执行流本来就跳过它，改成 nop 不影响运行；线性反汇编读到 nop 只占 1 字节，不再吞并后面的真实指令。前提只有一个：==被改的字节必须确认不在真执行流上==。

清理上例。先算文件偏移——非 PIE 程序用 [[R04-可执行文件格式ELF与PE|R04]] 式 (4.1)：文件偏移 = 虚拟地址 − 0x400000，即 0x401143 − 0x400000 = 0x1143。用 xxd 确认字节：

```bash
xxd -s 0x1141 -l 8 junk
```

输出：

```
00001141: eb01 e88b 45fc 83f0                      ....E...
```

`eb 01` 是 jmp，其后 0x1143 处的 `e8` 就是要清理的垃圾字节。改掉它：

```bash
cp junk junk_fixed
printf '\x90' | dd of=junk_fixed bs=1 seek=$((0x1143)) conv=notrunc status=none
xxd -s 0x1141 -l 8 junk_fixed
```

输出：

```
00001141: eb01 908b 45fc 83f0                      ....E...
```

再看反汇编：

```bash
objdump -d -M intel junk_fixed | sed -n '/<check>:/,/^$/p'
```

输出：

```
0000000000401136 <check>:
  401136:	f3 0f 1e fa          	endbr64
  40113a:	55                   	push   rbp
  40113b:	48 89 e5             	mov    rbp,rsp
  40113e:	89 7d fc             	mov    DWORD PTR [rbp-0x4],edi
  401141:	eb 01                	jmp    401144 <check+0xe>
  401143:	90                   	nop
  401144:	8b 45 fc             	mov    eax,DWORD PTR [rbp-0x4]
  401147:	83 f0 5a             	xor    eax,0x5a
  40114a:	5d                   	pop    rbp
  40114b:	c3                   	ret
```

假 call 消失，`check` 恢复成一眼可读的常规形态。运行确认行为不变：

```bash
./junk_fixed
```

输出：

```
4718
```

> [!warning] 先看清执行流，再动字节
> patch 是改文件。把真执行流上的字节改成 nop，程序就真的坏了。动手前用 [[R06-动态调试GDB与x64dbg|R06]] 的单步把执行流走一遍，确认目标字节"只有反汇编会读、运行不会执行"，再改；改完立刻运行对比。

> [!info]- 不改文件的清理法
> IDA 里可以不 patch 文件：在垃圾字节上按 `U`（取消定义）再按 `C`（定义为代码）强制重新分析，配 `P` 重建函数边界。适合只想读通逻辑、不需要干净文件的场合（快捷键见 [[R05-静态分析工具链IDA与Ghidra#3.4 快捷键表|R05 3.4]]）。

### 6.5 更多花指令模式

> [!info]- 互补跳转、多层跳转与自修改代码
> - **互补条件跳转**：`jz L` 与 `jnz L` 相邻，条件互补必有一个成立，两条都去 L；夹在中间的垃圾字节横在静态反汇编的必经之路上。识别特征：相邻两条跳转目标相同且条件互补。
> - **多层跳转**：jmp A、A 处 jmp B、B 处才到真实代码，拉长线性解码的错位链。沿执行流单步即可拆穿。
> - **自修改代码**：运行时改写自身指令（PE 配 `VirtualProtect`，ELF 配 `mprotect`），静态反汇编永远对不上。属于混淆器与壳 stub 的进阶手段，也是 3.5 节导入表里 `VirtualProtect` 值得留意的另一层原因。

## 7. macOS 与 Linux 上的壳

UPX 本身跨平台：PE、ELF、Mach-O 都支持，第 4 节的流程在任何 Linux 发行版上照搬；macOS 上的壳同样以 UPX 为主。

除 UPX 之外，ELF 与 Mach-O 上几乎没有成规模的壳生态。原因一句话：==这两个平台的软件不按 Windows 那种闭源防破解模式发行，壳的主要需求（商业保护、免杀对抗）在这里不存在，逆向考察也就集中在 UPX 这一档==。比赛层面可以直接建立等式：ELF 加壳题 ≈ UPX 题，先 `upx -d`，报错再走手工。

> [!info]- CTF 里 ELF 壳题的三档
> 绝大多数：标准 UPX，`upx -d` 直接过；少数：魔改 UPX（改 `UPX!` 标记、版本号），特征修回后 `upx -d`；罕见：自写壳，按第 5 节的思想在 GDB 里做。见到 ELF 壳题先试第一档。

## 8. 常见问题

| 现象 | 原因与解决 |
| ---- | ---- |
| `upx -d` 报 NotPackedException | 头里没有 UPX 自描述结构：不是 UPX 壳，或 `UPX!` 标记/版本号被改。按 3.2 查特征，修回后重试，或走第 5 节手工路线 |
| `upx -d` 报 CantUnpackException | 结构在但版本不兼容：加壳用的 UPX 版本较老，到 GitHub Releases 找对应旧版本再解 |
| 自己加壳的程序被杀软报毒 | UPX 是恶意软件常用的伪装层，启发式引擎对加壳文件普遍误报；比赛环境的正常现象 |
| x64dbg 里 ESP 定律断点不命中 | 断点下在 pushad 执行之前（ESP 还是旧值），或下成了软件断点。单步过了 pushad 再取 ESP，用硬件访问断点（5.1 第 4 步） |
| 停在 popad 后却找不到跳 OEP 的 jmp | popad 不是 stub 的最后一条指令，收尾还有几条；继续 F8，直到跳进陌生区域 |
| dump 文件 IDA 打开是乱码 | dump 时机不在 OEP（代码未解压完），或没修 IAT；回 5.2、5.3 |
| Fix Dump 后程序运行不了 | 导入表还有无效条目，或壳带完整性校验；Scylla 里逐条清理后重试 |
| objdump 反汇编读到一半乱掉 | 花指令或数据混进代码区；按 6.3 识别、6.4 清理 |
| 花指令 patch 后程序行为变了 | 改到真执行流上的字节了；先动态单步确认再改（6.4 的 warning） |
| 加壳后 `file` 报 statically linked，程序运行却要 libc | 壳让 `file` 的描述失真（4.3）；链接状态以程序头与运行行为为准 |
