# R10 反调试与反分析对抗
## Anti-Debugging & Anti-Analysis

> [!info]- 章节信息
> **所属方向**：逆向工程 ｜ **难度阶段**：L2 核心题型期 ｜ **前置要求**：[[R09-加壳与脱壳|R09]] · [[R06-动态调试GDB与x64dbg|R06]] · [[R05-静态分析工具链IDA与Ghidra|R05]]
> **本章目标**：说清反调试"检测 → 分支 → 假路径"的通用形状与三种绕过思路（改数据、改代码、改环境）；Windows 侧认出 API 检测、时间检测、断点自查、TLS 回调、SEH 五类手法并会用 x64dbg / ScyllaHide 处理；Linux 侧把 ptrace、TracerPid、SIGTRAP、时间差四类检测从源码、调试器下的表现到绕过完整走通。

## 1. 反调试在对抗什么

[[R06-动态调试GDB与x64dbg|R06]]建立的动态调试能力是：把程序作为被调试进程启动，下断点、单步、读寄存器和内存。反调试的目标就是让这条路走不通——==让程序发现自己正在被调试，然后改变行为==。

赛题里反调试的表现有三类：

- **直接退出或报错**：一附加调试器进程就结束，连 main 都进不去；
- **走假路径**：表面正常运行，实际执行的是另一套逻辑——输出错误的 flag、把数据清空、进入死循环；
- **反复检测**：检测逻辑混在业务逻辑中间，通过一处后还有下一处（壳里普遍如此，见 [[R09-加壳与脱壳|R09]]）。

无论手法怎么变，反调试代码都是同一个形状：

```asm
; 反调试的通用形状（x86-64，示意）
call detect          ; 检测例程：被调试时返回非 0
test eax, eax
jne  fake_path       ; 检出 → 假路径：输出错误提示、清数据或退出
; ---- 真路径：正常业务逻辑，flag 校验在这里 ----
```

==所有反调试都能拆成"检测 → 分支 → 假路径"三步==。检测手段决定分支怎么写，但对抗思路只有三种，本章称为三板斧：

| 三板斧 | 做法 | 典型操作 |
| ---- | ---- | ---- |
| 改数据 | 断点停在检测点，直接改返回值或标志 | GDB `set $rax = 0`、`set variable`；x64dbg 寄存器窗改 RAX |
| 改代码 | patch 检测调用或分支指令 | `call` 改 `xor eax,eax`；条件跳转 nop 或反转 |
| 改环境 | 插件抹掉调试痕迹，让检测函数本身返回"干净" | ScyllaHide 一键隐藏 |

本章第 2–7 节讲 Windows 侧的五类检测与绕过操作路径（写原理和操作步骤，GUI 操作没有可复制的固定输出）；第 8 节是 Linux 主线——ptrace、TracerPid、SIGTRAP、时间差四类检测，每一类都给出完整源码、命令与输出，可以在 WSL 里逐条复现。两类平台的检测思想一一对应，三板斧通用。

> [!warning] 先静态读懂，再动手绕
> 反调试逻辑和业务逻辑混在一起，盲目动态跟踪会一直在假路径里打转。按 [[R06-动态调试GDB与x64dbg#11. 静态与动态怎么选|R06 第 11 节]]的分工：先用 [[R05-静态分析工具链IDA与Ghidra|R05]]的流程定位检测代码，想清楚它查什么、走哪条分支，再决定三板斧用哪一招。CrackMe 题里反调试是常见加固（[[R08-CrackMe经典题型|R08]]），绕过之后才是熟悉的算法还原（[[R07-编码与算法识别还原|R07]]）。

## 2. Windows API 检测与绕过

本节平台为 **Windows x64（Microsoft x64 ABI：前四个参数 RCX、RDX、R8、R9，调用方预留 32 字节 shadow space，返回值在 RAX）**。这批 API 的共同点：都向程序提供"是否正被调试"的系统事实，检测代码拿返回值做分支。

### 2.1 IsDebuggerPresent：读 PEB 的一个字节

`IsDebuggerPresent`（kernel32）返回 BOOL：进程被调试返回非零。它的实现是读进程环境块（PEB）里的 `BeingDebugged` 字节——PEB 是进程启动时内核映射进用户态的结构，x64 下通过段寄存器 gs 定位：`gs:[0x60]` 处存放 PEB 基址，`BeingDebugged` 固定在 PEB 偏移 2 处：

```asm
; IsDebuggerPresent 的实现原理（x64 Windows，示意）
mov   rax, gs:[0x60]         ; rax = PEB 基址
movzx eax, byte ptr [rax+2]  ; PEB.BeingDebugged
ret
```

反汇编里看到 `gs:[0x60]` 之后取 `[rax+2]` 的字节、不经过任何 call，就是这条检测的手写版。C 层的用法就是通用形状的直接实例：

```c
if (IsDebuggerPresent()) {
    return 1;                 /* 假路径：退出或清数据 */
}
/* 真路径：正常业务 */
```

绕过三板斧逐条对应：

- **改数据**：断点停在 `call IsDebuggerPresent` 返回处，把 RAX 改成 0 再放行；
- **改代码**：把 5 字节的 `call IsDebuggerPresent` 整条改成 `31 C0`（`xor eax,eax`）+ 3 条 `0x90`（nop）；或把检测后的条件跳转 nop 掉 / 反转（`je`↔`jne`）；
- **改环境**：x64dbg 内存 dump 窗 Ctrl+G 输入 `peb()+2` 跳到 `BeingDebugged` 字节，右键 → Binary → Edit 改成 0；或用 ScyllaHide 勾选 PEB 隐藏（[[#2.4 三板斧在 x64dbg 里的操作路径|2.4 节]]）。

> [!info]- PEB 里还有别的可查项
> `NtGlobalFlag` 在 PEB 偏移 0xBC：进程由调试器创建时该字段带堆调试标志（0x70），检测代码常把它和 `BeingDebugged` 一起查。32 位程序 PEB 在 `fs:[0x30]`，读法同构。这些字段 ScyllaHide 都会一并处理。

### 2.2 CheckRemoteDebuggerPresent 与 NtQueryInformationProcess

`CheckRemoteDebuggerPresent(HANDLE hProcess, PBOOL pbDebuggerPresent)` 把查询结果写进第二个参数指向的 BOOL。它内部调用 ntdll 的原生 API `NtQueryInformationProcess`——不少样本直接调后者，跳过封装。原型五个参数，关键在第二个"信息类"：

| 信息类 | 值 | 被调试时返回 | 未被调试时返回 |
| ---- | ---- | ---- | ---- |
| ProcessDebugPort | 7 | 非零的调试端口（常见 0xFFFFFFFF） | 0 |
| ProcessDebugObjectHandle | 0x1E | 非零的调试对象句柄 | 0 |
| ProcessDebugFlags | 0x1F | 0 | 1（语义相反，注意） |

反汇编认法：call 之前 RDX（第二个参数）装的是 7、0x1E 或 0x1F，就是这三类检测。`ProcessDebugFlags` 最容易看错——==它返回 0 才代表被调试==，因为查的是"不继承调试"标志本身。

绕过仍是三板斧：改数据（断点在 call 返回处改 RAX 或改输出缓冲区里的 BOOL）；改代码（patch call 或跳转）；改环境（ScyllaHide 的钩子配置覆盖 `NtQueryInformationProcess`，勾选即生效）。

> [!info]- 配套的隐身手法：ThreadHideFromDebugger
> 与这三类查询常一起出现的是 `NtSetInformationThread(ThreadHideFromDebugger)`：把线程对调试器设为隐身，调试器收不到它的事件。属于"主动隐身"而不是"被动查询"，ScyllaHide 同样覆盖。

### 2.3 OutputDebugString 技巧

`OutputDebugStringA` 的本义是向调试器发送一条调试字符串；没有调试器时调用几乎没有副作用。检测代码利用这个差异：

```c
SetLastError(0xDEADBEEF);
OutputDebugStringA("ping");
if (GetLastError() != 0xDEADBEEF) {
    /* 错误码被改动：字符串被调试器接收处理，判定被调试 */
}
```

原理：没有调试器时，该 API 的内部异常处理路径会把上一次的错误码原样恢复；调试器接收处理它的调试异常之后，错误码会被改动。不同 Windows 版本的行为细节有差异，赛题里按"==错误码前后不一致 = 有调试器=="理解。绕过：patch 那次比较或跳转；插件钩子也会覆盖这类 API。

### 2.4 三板斧在 x64dbg 里的操作路径

拿到一个 Windows 目标，完整流程：

1. **定位检测代码**。静态侧：IDA 导入窗口看有没有 `IsDebuggerPresent` / `CheckRemoteDebuggerPresent`，再用[[R05-静态分析工具链IDA与Ghidra#3.6 交叉引用（xref）：代码引用与数据引用|R05 的交叉引用]]找到调用点；运行侧：一调试就退出、行为反常，先怀疑检测藏在入口或 TLS 回调（[[#6. 藏在 main 之前：TLS 回调|第 6 节]]）。
2. **三选一处理**：
   - 改数据：软件断点停在检测 call 的下一条，寄存器窗把 RAX 改 0，F9 放行；
   - 改代码：反汇编窗选中 `call` 指令按空格改成 `xor eax,eax`，剩余字节填 nop；或改检测后的条件跳转。Ctrl+P 打开补丁窗口，可把修改写回文件；
   - 改环境：菜单 Plugins → ScyllaHide → Options，顶部下拉选现成配置（如 Hooked，一组常用的 PEB / API 隐藏组合），OK 后重新加载目标。
3. **放行观察**：程序应走到真路径；还在假路径就换下一招，或回到静态把漏掉的检测找出来。

本节汇总：

| 检测手段 | 原理 | 绕过 |
| ---- | ---- | ---- |
| IsDebuggerPresent | 读 PEB+2 的 BeingDebugged 字节 | patch 返回值 / 跳转；手改 PEB；ScyllaHide |
| CheckRemoteDebuggerPresent | 内部查 ProcessDebugPort | 同上 |
| NtQueryInformationProcess | ProcessDebugPort / DebugObjectHandle / DebugFlags 三类信息 | patch 返回值；ScyllaHide 勾选 |
| OutputDebugString 技巧 | 字符串被调试器接收处理时 GetLastError 被改动 | patch 比较；插件钩子覆盖 |

## 3. 时间检测：rdtsc 与 QueryPerformanceCounter

正常执行一小段代码，耗时恒定且极短（微秒级）；单步或断点停顿会把耗时拉长到毫秒甚至秒级。时间检测检查的就是这个差值。Windows 侧两套计时来源：

- **`rdtsc` 指令**：把 64 位时间戳计数器读入 `EDX:EAX`（32/64 位通用），两次读取的差值就是经过的周期数。手写样本常用它：

```asm
; rdtsc 差值检测（x86/x64 通用，示意）
rdtsc                    ; 时间戳 → edx:eax
mov  ebx, eax            ; 存下第一次的低 32 位
; ……被保护的一小段代码……
rdtsc                    ; 第二次读取
sub  eax, ebx            ; 差值
cmp  eax, 0x10000
ja   fake_path           ; 差值过大 = 中途被单步或断点停过
```

- **`QueryPerformanceCounter(LARGE_INTEGER*)`**：高精度计时 API，`GetTickCount`（毫秒级）同理，C 形状与第 8.4 节的 `clock_gettime` 完全同构。

绕过三板斧的对应做法：

- **改代码**：把阈值常量改大（做法与 8.4 节的 `cmp` 立即数 patch 相同），或把比较后的跳转 nop 掉；
- **改环境**：加载时间篡改类插件（x64dbg 插件生态里有专门的时间篡改插件，把 `QueryPerformanceCounter` / rdtsc 的增量按真实流逝时间重新计算，使单步停顿不计入）；
- **改数据**：断点停在比较前，直接把计时变量改小。

| 检测手段 | 原理 | 绕过 |
| ---- | ---- | ---- |
| rdtsc 差值 | 时间戳计数器差值异常大 = 被单步 | patch 阈值/跳转；时间篡改插件 |
| QueryPerformanceCounter | 高精度计时同上 | 同上 |
| GetTickCount | 毫秒级计时，精度低但写法简单 | 同上 |

> [!info]- rdtsc 的两个细节
> rdtsc 不是串行化指令，CPU 乱序执行会让两次读取的差值失真，所以严格一点的样本会在两次 rdtsc 之间插 `cpuid`（串行化）或改用 `rdtscp`；多核系统里各核的计数器不完全同步，样本通常会先把线程绑核。逆向时看到 cpuid 夹着 rdtsc，就是这对组合。

## 4. 断点自查：0xCC 扫描与校验和

[[R06-动态调试GDB与x64dbg#3.1 软件断点：break 与 0xCC|R06 3.1 节]]讲过：软件断点的实现是把目标指令首字节改写成 `0xCC`（int3），磁盘文件不动、内存镜像被动。程序对此的对策是==检查自己的代码段==：

- **直接比对**：把关键函数的首字节读出来和 `0xCC` 比：

```c
unsigned char *p = (unsigned char *)check;
if (*p == 0xCC) {          /* 首字节被换成了 int3 */
    return 1;              /* 假路径 */
}
```

- **校验和**：对整段代码逐字节求和（或循环冗余校验），与启动时算好存放的基值比较；任何一处被改写都会对不上。校验和不止抓软件断点，也抓一切 patch。

绕过：

- **改用硬件断点**：地址写进 CPU 的 DR0–DR3，CPU 取指时硬件比对，==不修改任何内存字节==，两种自查都查不到（GDB 的 `hbreak`、x64dbg 的断点窗口右键 → 断点 → 硬件断点 → 执行；机制与 4 个的上限见 [[R06-动态调试GDB与x64dbg#3.4 硬件断点：hbreak|R06 3.4 节]]）；
- **把断点下在自查范围之外**：校验通常只覆盖关键函数，断在校验例程自身或它前面的调用点，就能单步走进去；
- **改代码**：patch 校验例程，让它恒返回"通过"。

| 检测手段 | 原理 | 绕过 |
| ---- | ---- | ---- |
| 0xCC 首字节比对 | 软件断点改写了内存 | 硬件断点；断点下在自查范围外 |
| 代码段校验和 | 任何改写都会改变校验值 | 同上；patch 校验例程 |

## 5. 硬件断点检测：DR0–DR3

第 4 节的对策换过来用：程序也可以==主动查询调试寄存器==。Windows 下通过 `GetThreadContext` 取 `CONTEXT_DEBUG_REGISTERS` 部分，检查 `Dr0`–`Dr3`（四个断点线性地址）与 `Dr7`（启用位）——任何一项非零，就说明调试器下了硬件断点：

```c
CONTEXT ctx = {0};
ctx.ContextFlags = CONTEXT_DEBUG_REGISTERS;
GetThreadContext(GetCurrentThread(), &ctx);
if (ctx.Dr0 || ctx.Dr1 || ctx.Dr2 || ctx.Dr3) {
    return 1;              /* 有硬件断点 → 假路径 */
}
```

绕过：

- **改用内存断点**：x64dbg 的内存断点靠页面权限实现（GPU 页保护），不占用 DR 寄存器，`GetThreadContext` 查不到；
- **改代码**：patch 这次调用或它后面的比较；
- **改环境**：（内核级工具如 TitanHide 一类驱动挂钩 `NtGetContextThread`，把返回的 DR 值清零——赛题环境少用，知道有这一层即可）。

| 检测手段 | 原理 | 绕过 |
| ---- | ---- | ---- |
| GetThreadContext 查 DR0–DR3 | 硬件断点地址记录在调试寄存器里 | 改用内存断点；patch 调用/比较 |

## 6. 藏在 main 之前：TLS 回调

TLS（Thread Local Storage）目录是 PE 数据目录的第 9 项（数据目录表见 [[R04-可执行文件格式ELF与PE#3.5 Optional Header|R04 3.5 节]]）。其中的回调指针数组 `AddressOfCallBacks` 是一组 NULL 结尾的函数指针：==加载器把进程映射好之后、入口点执行之前，会逐个调用这些函数==；之后每次创建新线程也会回调一次。这就是 TLS 回调——比 main 更早执行的函数。

反调试爱藏在这里的原因：==分析者在 main 里下断没用，检测在 main 之前已经跑完==，等发现"一运行就退出"时，退出动作早发生了。

**IDA 里怎么找**：菜单 View → Open subviews → TLS callbacks，窗口列出 TlsCallback_0、TlsCallback_1……双击跳到函数，按 [[R05-静态分析工具链IDA与Ghidra|R05]]的正常流程 F5 反编译、改名、读逻辑即可。

**x64dbg 里怎么停**：Options → Preferences → Events 页勾选 TLS Callbacks，重新加载目标，调试器会在每个回调入口先停一次，再逐个放行。

> [!info]- TLS 目录结构
> TLS 目录的 IMAGE_TLS_DIRECTORY 共六个字段：StartAddressOfRawData、EndAddressOfRawData、AddressOfIndex、AddressOfCallBacks（回调数组地址，重点是它）、SizeOfZeroFill、Characteristics。PE-bear、CFF Explorer 这类解析器能直接读出这个目录；壳会对它做加密或抹除，脱壳时不要漏掉（[[R09-加壳与脱壳|R09]]）。

## 7. 异常当控制流：SEH 反调试

32 位 Windows 的结构化异常处理（SEH）是一条运行时链：`fs:[0]` 指向链头，`__try`/`__except` 编译后就是链上的节点。反调试把这条链当控制流用——==关键逻辑不写在正常路径上，写在异常处理函数里==：

```c
/* SEH 反调试的形状（32 位 Windows，示意） */
__try {
    __asm int 3;                  /* 故意触发异常 */
    puts("fake path");            /* 正常流程不会走到这里 */
}
__except (EXCEPTION_EXECUTE_HANDLER) {
    real_check();                 /* 真路径：解密、校验等关键逻辑 */
}
```

两种结局：

- **没有调试器**：异常无人接收，分发给程序自己的处理函数 → `real_check()` 执行，真路径成立；
- **有调试器**：异常先送到调试器（first-chance）。调试器若吞下异常再放行（GDB 的 continue 默认不传信号、x64dbg 的异常忽略），处理函数根本不执行，程序走偏或崩溃。

除零、写只读地址等异常同理。绕过的关键是==把异常交还给程序==：

- **x64dbg**：Options → Preferences → Exceptions 页，找到或添加对应异常范围（INT 3 breakpoints、Access Violation 等），设置为"传递给程序"（不忽略），程序自己的处理函数随即接管；
- **GDB**：`handle 信号名 nostop noprint pass`——Linux 没有链式 SEH，但信号机制同构，8.3 节用 SIGTRAP 完整走一遍。

> [!info]- x64 下的变化与 VEH
> x64 Windows 删除了运行时 SEH 链，改用 .pdata/.xdata 表驱动展开（`fs:[0]` 写法失效），但 `__try`/`__except` 语法和分发次序照旧。另有 `AddVectoredExceptionHandler` 注册的 VEH，排在 SEH 之前最先收到异常，CrackMe 常用它把校验藏到所有异常的第一站。调试器侧的处理不变：异常配置成传递，VEH/SEH 照常接管。

## 8. Linux 侧：四类检测完整走通

Linux 没有那批 Win32 API，检测落点换成四样东西：**ptrace、/proc 文件、信号、时钟**。本节是本章主线：每类检测都给出完整源码、命令与输出，环境为 WSL Ubuntu + gcc + gdb，样本统一编译：

```bash
gcc -O0 -fno-pie -no-pie -g anti_ptrace.c -o anti_ptrace
```

`-O0` 让机器码顺序对应源码，`-fno-pie -no-pie` 固定加载基址（[[R03-x86与x64汇编精要复习|R03]]的编译基线），`-g` 保留调试信息。样本故意输出 `real path` / `fake path` 字样标记走的哪条路。以下示例均为 **x86-64 Linux / System V AMD64 ABI**。

统一实验形状，每个样本跑三种状态：正常运行 → GDB 下运行 → 绕过后运行。

> [!note] 输出说明
> 每个 GDB 会话开头固定输出两行线程库提示（`[Thread debugging using libthread_db enabled]` 等），下文一律省略；`[Inferior 1 (process N) …]` 里的进程号每次运行都不同。

### 8.1 ptrace 自占：一个人只能被跟踪一次

调试器与被调试者的关系由内核的 ptrace 机制维护（[[R06-动态调试GDB与x64dbg#9. strace 与 ltrace：观察程序行为|R06 第 9 节]]提示过 strace 与 GDB 同源）。`ptrace(PTRACE_TRACEME)` 的语义是：进程向内核声明"允许我的父进程跟踪我"。内核规定==一个进程同一时刻只能有一个跟踪者==：已经被跟踪时再申请，返回 -1（EPERM）。

程序把这个机制反过来用——先自己申请占住位置，申请失败就说明已有调试者在场：

```c
/* anti_ptrace.c —— ptrace 自占：已被跟踪时 PTRACE_TRACEME 返回 -1 */
#include <stdio.h>
#include <sys/ptrace.h>

int main(void)
{
    if (ptrace(PTRACE_TRACEME, 0, 0, 0) == -1) {
        puts("anti: traced, fake path");
        return 1;
    }
    puts("anti: clean, real path");
    return 0;
}
```

正常运行，申请成功：

```bash
./anti_ptrace
```

输出：

```
anti: clean, real path
```

GDB 下启动，进程一生下来就被 GDB 跟踪，申请失败，走假路径：

```bash
# p1.gdb
run
```

```bash
gdb -q -batch -x p1.gdb ./anti_ptrace
```

输出：

```
anti: traced, fake path
[Inferior 1 (process 581) exited with code 01]
```

绕过一：**LD_PRELOAD 覆盖 ptrace（改环境）**。动态链接的程序调用 libc 函数要经过 PLT，`LD_PRELOAD` 指定的库在符号解析时优先级最高——写一个恒返回 0 的 ptrace，把真的盖掉：

```c
/* hook_ptrace.c —— LD_PRELOAD 覆盖 ptrace：恒返回 0 */
long ptrace(long request, long pid, long addr, long data)
{
    (void)request; (void)pid; (void)addr; (void)data;
    return 0;
}
```

```bash
gcc -shared -fPIC hook_ptrace.c -o hook.so
```

在 GDB 里用 `set environment` 把变量注入被调试进程（本样本的检测发生在启动瞬间，注入必须先于 `run`）：

```bash
# p1_ld.gdb
set environment LD_PRELOAD ./hook.so
run
```

```bash
gdb -q -batch -x p1_ld.gdb ./anti_ptrace
```

输出：

```
anti: clean, real path
[Inferior 1 (process 499) exited normally]
```

> [!warning] LD_PRELOAD 的适用边界
> 静态链接的程序、绕过 libc 直接发 syscall 的程序都不经过 PLT，LD_PRELOAD 无效，只能走 patch。另有一类样本只在启动时检测一次、之后长时间运行——对它们可以正常启动，等过了检测点再 `gdb -p` 附加（附加受 yama ptrace_scope 限制，处理方式见 [[R06-动态调试GDB与x64dbg#2.1 三种启动方式|R06 2.1 节]]）。

绕过二：**patch 掉检测调用（改代码）**。先反汇编看 main 里的检测形状：

```bash
objdump -d -M intel anti_ptrace | sed -n '/<main>:/,/^$/p'
```

输出（节选）：

```
401172:	b8 00 00 00 00       	mov    eax,0x0
401177:	e8 e4 fe ff ff       	call   401060 <ptrace@plt>
40117c:	48 83 f8 ff          	cmp    rax,0xffffffffffffffff
401180:	75 11                	jne    401193 <main+0x3d>
```

`call ptrace@plt` 在 0x401177，共 5 字节（`e8` + 4 字节相对偏移）。把它整条改成 `31 C0`（`xor eax,eax`）+ 3 条 `0x90`（nop）：返回值恒为 0，`cmp rax,-1` 不成立，`jne` 走真路径。写回文件要按**文件偏移**定位：no-pie 程序 `.text` 的虚拟地址减 0x400000 就是文件偏移（改前先核对目标字节确实是 0xE8）：

```python
# patch_ptrace.py —— 把 call ptrace@plt（5 字节）改成 xor eax,eax + 3 条 nop
import re, subprocess

data = bytearray(open('anti_ptrace', 'rb').read())
out = subprocess.run(['objdump', '-d', 'anti_ptrace'],
                     capture_output=True, text=True).stdout
addr = int(re.search(r'^\s*([0-9a-f]+):.*call.*<ptrace@plt>', out, re.M).group(1), 16)
off = addr - 0x400000
assert data[off] == 0xE8, 'not a call instruction'
data[off:off+5] = bytes([0x31, 0xC0, 0x90, 0x90, 0x90])   # xor eax,eax + 3 nop
open('anti_ptrace_patched', 'wb').write(data)
print('call ptrace@plt at', hex(addr), '-> patched to xor eax,eax')
```

输出：

```
call ptrace@plt at 0x401177 -> patched to xor eax,eax
```

patch 过的二进制在 GDB 下也走真路径：

```bash
gdb -q -batch -x p1p.gdb ./anti_ptrace_patched     # p1p.gdb 只有 run 一行
```

输出：

```
anti: clean, real path
[Inferior 1 (process 515) exited normally]
```

| 检测手段 | 原理 | 绕过 |
| ---- | ---- | ---- |
| ptrace 自占 | 已被跟踪时 PTRACE_TRACEME 返回 -1 | LD_PRELOAD 盖掉 ptrace；patch call；启动后 attach |

### 8.2 TracerPid：/proc 里写着谁在跟踪你

内核把每个进程的状态暴露成文本文件 `/proc/self/status`（`self` 即读取者自己），其中一行是 `TracerPid`：==跟踪者的 PID；没有跟踪者时为 0==。检测就是把这个文件读出来找这一行：

```c
/* anti_status.c —— 读 /proc/self/status 查 TracerPid */
#include <stdio.h>

int main(void)
{
    FILE *fp = fopen("/proc/self/status", "r");
    char line[256];
    long tracer = -1;
    while (fgets(line, sizeof line, fp))
        if (sscanf(line, "TracerPid: %ld", &tracer) == 1)
            break;
    fclose(fp);
    printf("TracerPid = %ld\n", tracer);
    if (tracer != 0) {
        puts("anti: traced, fake path");
        return 1;
    }
    puts("anti: clean, real path");
    return 0;
}
```

正常运行，没有跟踪者：

```bash
./anti_status
```

输出：

```
TracerPid = 0
anti: clean, real path
```

GDB 下运行，==GDB 自己的 PID 被直接读走==：

```bash
gdb -q -batch -x p2.gdb ./anti_status      # p2.gdb 只有 run 一行
```

输出：

```
TracerPid = 630
anti: traced, fake path
[Inferior 1 (process 640) exited with code 01]
```

绕过（改数据）：解析发生在 printf 之前，断在第 13 行、把 tracer 改成 0 再放行：

```bash
# p2_fix.gdb
break anti_status.c:13
run
set variable tracer = 0
continue
```

```bash
gdb -q -batch -x p2_fix.gdb ./anti_status
```

输出：

```
Breakpoint 1 at 0x40128e: file anti_status.c, line 13.

Breakpoint 1, main () at anti_status.c:13
13	    printf("TracerPid = %ld\n", tracer);
TracerPid = 0
anti: clean, real path
[Inferior 1 (process 653) exited normally]
```

判断跳转的 patch 与 8.1 同理（把 `tracer != 0` 编译出的条件跳转 nop 或反转），不再重复。

| 检测手段 | 原理 | 绕过 |
| ---- | ---- | ---- |
| TracerPid 检测 | /proc/self/status 记录跟踪者 PID | 断点停下改变量；patch 判断跳转 |

### 8.3 SIGTRAP 陷阱：信号被调试器截留

程序注册一个 SIGTRAP 处理函数，然后主动 `raise(SIGTRAP)`。正常运行时信号送达处理函数，标志位被置 1；被 GDB 调试时，==GDB 默认把 SIGTRAP 留给自己==（断点机制就建立在它上面，[[R06-动态调试GDB与x64dbg#3.1 软件断点：break 与 0xCC|R06 3.1 节]]的 int3 触发的就是 3 号陷阱），信号不传给程序，处理函数不执行，标志位保持 0——假路径。这是第 7 节"异常当控制流"的 Linux 版：

```c
/* anti_trap.c —— SIGTRAP 陷阱：handler 收到信号才走真路径 */
#include <stdio.h>
#include <signal.h>

volatile int trap_ok = 0;

void handler(int sig)
{
    (void)sig;
    trap_ok = 1;
}

int main(void)
{
    signal(SIGTRAP, handler);
    raise(SIGTRAP);
    if (!trap_ok) {
        puts("anti: trap swallowed, fake path");
        return 1;
    }
    puts("anti: clean, real path");
    return 0;
}
```

先看 GDB 对 SIGTRAP 的默认策略：

```bash
gdb -q -batch -ex "info handle SIGTRAP" ./anti_trap
```

输出：

```
Signal        Stop	Print	Pass to program	Description
SIGTRAP       Yes	Yes	No		Trace/breakpoint trap
```

三列开关：Stop（停下）、Print（打印）、Pass to program（把信号传给程序）。默认 ==Stop=Yes、Pass=No==：信号被 GDB 截留。跑一遍验证后果：

```bash
# p3.gdb
run
continue
```

```bash
gdb -q -batch -x p3.gdb ./anti_trap
```

输出：

```
Program received signal SIGTRAP, Trace/breakpoint trap.
__pthread_kill_implementation (threadid=<optimized out>, signo=5, no_tid=0) at ./nptl/pthread_kill.c:44
anti: trap swallowed, fake path
[Inferior 1 (process 677) exited with code 01]
```

`run` 停在信号上（GDB 截到了它），`continue` 按 Pass=No 放行——信号没有传给程序，handler 没执行，trap_ok 仍为 0，假路径。绕过就是改这三列开关（改环境）：

```bash
# p3_pass.gdb
run
handle SIGTRAP nostop noprint pass
continue
```

```bash
gdb -q -batch -x p3_pass.gdb ./anti_trap
```

输出：

```
Program received signal SIGTRAP, Trace/breakpoint trap.
__pthread_kill_implementation (threadid=<optimized out>, signo=5, no_tid=0) at ./nptl/pthread_kill.c:44
SIGTRAP is used by the debugger.
Are you sure you want to change it? (y or n) [answered Y; input not from terminal]
anti: clean, real path
[Inferior 1 (process 540) exited normally]
```

流程：`run` 停在信号上 → `handle` 把 SIGTRAP 改成不停、不打印、继续时传给程序（GDB 提示"SIGTRAP is used by the debugger"要确认，交互式下手动输 y，批量模式自动回答）→ `continue` 这次把信号原样交给程序，handler 执行，trap_ok 置 1，真路径。

> [!warning] pass 要等程序停在信号上之后再设
> 把 `handle SIGTRAP ... pass` 放在 `run` 之前设置，GDB 自己的内部陷阱（断点插入、单步）也会被当成 SIGTRAP 传给程序——进程还没进 main 就死于 SIGTRAP，输出只有两行：
>
> 输出：
>
> ```
> SIGTRAP is used by the debugger.
> Are you sure you want to change it? (y or n) [answered Y; input not from terminal]
> Program terminated with signal SIGTRAP, Trace/breakpoint trap.
> The program no longer exists.
> ```
>
> 正确顺序固定为：先 `run` 停在信号上，再改 handle，最后 continue。

| 检测手段 | 原理 | 绕过 |
| ---- | ---- | ---- |
| SIGTRAP 陷阱 | 调试器默认截留信号，handler 不执行 | 停在信号上后 `handle SIGTRAP nostop noprint pass` 再 continue |

### 8.4 时间差检测：断点停顿计入计时窗口

`clock_gettime(CLOCK_MONOTONIC)` 读纳秒级单调时钟，对应 Windows 侧的 QueryPerformanceCounter / rdtsc（[[#3. 时间检测：rdtsc 与 QueryPerformanceCounter|第 3 节]]）。两次读取之间只隔一小段固定代码，差值应是纳秒级；==断点停下期间时钟照走==，差值直接涨到毫秒级：

```c
/* anti_time.c —— 时间差检测：两读 clock_gettime 之间只该有常量级耗时 */
#include <stdio.h>
#include <time.h>

int main(void)
{
    struct timespec t0, t1;
    clock_gettime(CLOCK_MONOTONIC, &t0);
    volatile int x = 0;
    for (int i = 0; i < 1000; i++)
        x += i;
    clock_gettime(CLOCK_MONOTONIC, &t1);
    long ns = (t1.tv_sec - t0.tv_sec) * 1000000000L + (t1.tv_nsec - t0.tv_nsec);
    printf("elapsed = %ld ns\n", ns);
    if (ns > 1000000L) {
        puts("anti: too slow, fake path");
        return 1;
    }
    puts("anti: clean, real path");
    return 0;
}
```

正常运行：

```bash
./anti_time
```

输出：

```
elapsed = 843 ns
anti: clean, real path
```

断点下在两次读取**之间**（第 12 行），`run` 停住、`continue` 再读 t1——停顿全部计入差值：

```bash
# p4.gdb
break anti_time.c:12
run
continue
```

```bash
gdb -q -batch -x p4.gdb ./anti_time
```

输出：

```
Breakpoint 1 at 0x4011ea: file anti_time.c, line 12.

Breakpoint 1, main () at anti_time.c:12
12	    clock_gettime(CLOCK_MONOTONIC, &t1);
elapsed = 7654335 ns
anti: too slow, fake path
[Inferior 1 (process 567) exited with code 01]
```

843 ns 与 7.6 ms 相差四个数量级，阈值判定边界清晰。绕过（改代码）：patch 阈值常量。先定位比较指令：

```bash
objdump -d -M intel anti_time | sed -n '/<main>:/,/^$/p' | grep -B2 -A2 f4240
```

输出：

```
  401236:	48 81 7d c8 40 42 0f 	cmp    QWORD PTR [rbp-0x38],0xf4240
  40123d:	00 
  40123e:	7e 11                	jle    401251 <main+0xbb>
```

`0xf4240` 就是十进制 1000000，小端编码 `40 42 0f 00`。把它改成 `0x7fffffff`（约 2.1 秒）：断点停顿只有几十毫秒，远低于新阈值。扫描整个文件确认这 4 个字节只出现一次，再替换：

```python
# patch_time.py —— 把阈值 1000000（0xf4240）改成 0x7fffffff
data = bytearray(open('anti_time', 'rb').read())
pat = bytes([0x40, 0x42, 0x0F, 0x00])            # 立即数 1000000 的小端编码
idx = [i for i in range(len(data)) if data[i:i+4] == pat]
assert len(idx) == 1, 'immediate not unique'
data[idx[0]:idx[0]+4] = bytes([0xFF, 0xFF, 0xFF, 0x7F])   # 0x7fffffff ≈ 2.1 秒
open('anti_time_patched', 'wb').write(data)
print('threshold patched at file offset', hex(idx[0]))
```

输出：

```
threshold patched at file offset 0x123a
```

同样的断点停顿，patch 后走真路径：

```bash
gdb -q -batch -x p4p.gdb ./anti_time_patched     # p4p.gdb 内容与 p4.gdb 相同
```

输出：

```
Breakpoint 1 at 0x4011ea: file anti_time.c, line 12.

Breakpoint 1, main () at anti_time.c:12
12	    clock_gettime(CLOCK_MONOTONIC, &t1);
elapsed = 9545557 ns
anti: clean, real path
[Inferior 1 (process 529) exited normally]
```

改数据这板斧同样适用：断点停在比较前 `set variable ns = 0`，二选一。Windows 侧的 rdtsc/QueryPerformanceCounter 检测对应做法一致——找到阈值立即数或跳转，patch。

| 检测手段 | 原理 | 绕过 |
| ---- | ---- | ---- |
| clock_gettime 差值 | 断点停顿被计入计时窗口 | patch 阈值立即数；停下改计时变量 |

### 8.5 Linux 汇总

四类检测对照（三板斧归属见括号）：

| 检测手段 | 原理 | 绕过 |
| ---- | ---- | ---- |
| ptrace 自占 | PTRACE_TRACEME 已被跟踪时返回 -1 | LD_PRELOAD（改环境）/ patch call（改代码）/ 启动后 attach |
| TracerPid | /proc/self/status 记录跟踪者 PID | set variable（改数据）/ patch 跳转（改代码） |
| SIGTRAP 陷阱 | 调试器默认截留信号，handler 不执行 | 停在信号上后 handle pass（改环境） |
| 时间差 | 断点停顿进入计时窗口 | patch 阈值（改代码）/ 停下改值（改数据） |

Windows 与 Linux 的对应关系：IsDebuggerPresent ↔ ptrace 自占，OutputDebugString/异常类 ↔ SIGTRAP，rdtsc ↔ clock_gettime。检测手法会随平台与工具变化，=="检测 → 分支 → 假路径"的形状和三板斧的思路不变==。

## 9. 常见问题

| 现象 | 原因与解决 |
| ---- | ---- |
| 程序一附加就退出，main 都进不去 | 检测藏在入口或 TLS 回调（[[#6. 藏在 main 之前：TLS 回调\|第 6 节]]）；x64dbg 勾选 TLS Callbacks 事件重载，或先开 ScyllaHide 再加载；Linux 样本先 patch ptrace 再调 |
| GDB 下程序行为和直接运行不一样 | 有检测生效了。逐类排查：`info handle SIGTRAP` 看信号策略，断点位置是否落在计时窗口内，ptrace 类检测直接看 [[#8.1 ptrace 自占：一个人只能被跟踪一次\|8.1]] |
| LD_PRELOAD 没有效果 | 样本静态链接或直接 syscall，不经过 PLT；改用 patch |
| patch 之后程序跑飞 | 改错位置或长度不对。改前核对首字节（call 是 0xE8），剩余字节用 nop 补满原指令长度；文件偏移用"虚拟地址 - 基址"换算并核对 |
| patch 常量后仍走假路径 | 阈值比较方向看反了（`jle`/`ja`）；或者检测不止一处，`jne` 后面还有第二道判断 |
| `set variable` 报 No symbol | 程序 strip 过没符号；用 `x` 命令按地址找变量位置，或断在寄存器上 `set $rax = 0` |
| run 之前设好 handle pass，程序直接死于 SIGTRAP | GDB 自己的内部陷阱被传给了程序（[[#8.3 SIGTRAP 陷阱：信号被调试器截留\|8.3]]）；等程序停在信号上再改 handle |
| IDA 里找不到 TLS 回调 | View → Open subviews → TLS callbacks；壳可能加密了 TLS 目录，先脱壳（[[R09-加壳与脱壳\|R09]]） |
| x64dbg 里异常总停在调试器、不走程序的 handler | Exceptions 页没配"传递给程序"（[[#7. 异常当控制流：SEH 反调试\|第 7 节]]） |
| 硬件断点被 GetThreadContext 查出来 | 换内存断点（不占 DR 寄存器），或 patch 检测（[[#5. 硬件断点检测：DR0–DR3\|第 5 节]]） |
| WSL 里 hbreak 报不支持 | 内核没把调试寄存器接口提供给 ptrace（[[R06-动态调试GDB与x64dbg#3.4 硬件断点：hbreak\|R06 3.4 节]]）；Windows 目标在 x64dbg 里没有这个限制 |
