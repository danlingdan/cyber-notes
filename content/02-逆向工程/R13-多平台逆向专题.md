# R13 多平台逆向专题
## Multi-Platform Reverse Engineering

> [!info]- 章节信息
> **所属方向**：逆向工程 ｜ **难度阶段**：L3 进阶专题期 ｜ **前置要求**：[[R04-可执行文件格式ELF与PE|R04]] · [[R05-静态分析工具链IDA与Ghidra|R05]] · [[R09-加壳与脱壳|R09]]
> **本章目标**：拿到陌生文件先识别"它是谁、用什么造的"，再按平台切换工具链——==先识别，后分析==。
> **示例平台**：x86-64 Linux（WSL）；ARM 小节为 AArch64 Linux。每个平台的示例程序都自建，命令配输出。

R1 到 R12 处理的附件绝大多数是 x86-64 的 ELF 与 PE。多平台题只是把附件换掉：Python 打包的 exe、jar/APK、Go、Rust、C++、.NET、wasm、固件、ARM 程序。[[R01-逆向工程与CTF竞赛生态导论#3. 常见附件类型与识别|R01 的附件类型表]]给过第一层印象，本章逐平台展开两件事：**怎么认出这个平台**（魔数、字符串、符号特征），**用什么工具链分析**（提取、反编译、反汇编）。每节的套路相同：自建一个带校验逻辑的小程序 → 编译/打包 → 把识别与分析完整走一遍。

## 1. 识别先行：陌生文件三步定性

[[R05-静态分析工具链IDA与Ghidra|R05]] 的分析流程、[[R09-加壳与脱壳|R09]] 的查壳，第一步都是 `file` 与 `strings`。多平台题把这两步的价值放大：==平台认错，后面全错==——拿 IDA 硬啃一个 PyInstaller 产物，读到的只是 Python 解释器的机器码；拿 objdump 反汇编 .NET 程序，看到的只是入口处一小段转发代码。

三步定性，按成本从低到高：

1. **魔数**：`file` 加 `xxd` 看文件头。后缀不可靠，[[12-隐写与流量取证|通用基础 12 章]]讲过；常见魔数[[03-计算机组成与数据表示|通用基础 03 章]]列过表。ELF 的 `\x7fELF`、PE 的 `MZ`、wasm 的 `\0asm`、Java class 的 `CA FE BA BE` 都在这一步确认。
2. **字符串特征**：`strings` 扫全文件。各平台的运行时会在产物里留下自己的名字：`pyi-`（PyInstaller）、`go1.23.4`（Go 工具链版本）、`_ZN`（C++/Rust 名字粉碎）、`mscoree.dll`（.NET）。一条 grep 常常直接定案。
3. **结构形状**：魔数与字符串都模糊时看结构——ELF 的 `readelf -h` 看 Machine 字段（非 x86 就是交叉平台），PE 的数据目录第 14 项非 0 就是 .NET（[[R04-可执行文件格式ELF与PE#3.5 Optional Header|R04 3.5]]），节区表里出现 `.data.rel.ro` 多半有 C++ 虚表。

三步之前先做一个分类判断，它决定工具链的大方向：

- **机器码**：ELF、PE、Mach-O、固件里的可执行段。CPU 直接执行，用反汇编器（objdump、IDA、Ghidra）。
- **字节码**：pyc、Java class、dex、.NET 的 CIL、wasm。由各自的虚拟机执行，优先找"还原成源码"的工具（pycdc、jadx、ILSpy、wasm2wat），字节码通常比机器码好读得多。
- **容器**：固件镜像、APK、jar 本质是"文件套文件"，先提取内层再按内层类型处理。

> [!note] 识别与查壳的先后
> 多平台识别和 [[R09-加壳与脱壳|R09]] 的查壳是同一件事的两个层次：`file`、strings、结构三步走完，既回答"什么平台"也常常回答"有没有壳"。UPX 的 `UPX!` 标记、PyInstaller 的 `pyi-` 字符串，在第 2 步就能看到。顺序永远是：先定性，再谈分析。

各平台的特征与首选工具汇总（本章各节展开）：

| 平台/语言 | 文件特征（魔数 / 字符串 / 结构） | 首选工具 |
| ---- | ---- | ---- |
| Python（PyInstaller 打包） | ELF/exe 外壳 + `pyi-`、`PYZ` 字符串；本体是压在包里的 pyc | pyi-archive_viewer 提取 → dis/pycdc |
| Python（pyc） | 头 4 字节是版本魔数（如 `2B 0E 0D 0A`）；`file` 常报 `data` | python3 dis、pycdc |
| Java | `CA FE BA BE`；jar 内有 `META-INF/MANIFEST.MF` 与 .class | javap、jadx |
| Android | zip 内含 `classes.dex`（魔数 `64 65 78 0A` 即 `dex\n`） | jadx、apktool；native 层加交叉 objdump |
| Go | `file` 直接报 `Go BuildID=`；`go1.x` 版本串；`runtime.*` 符号群 | nm、GoReSym |
| Rust | panic 字符串带源码路径；`_ZN…17h…E` 符号 | nm、c++filt / rustfilt |
| C++ | `_Z` 开头的粉碎符号；vtable 与 RTTI 符号 | c++filt、IDA/Ghidra |
| .NET | PE 但数据目录第 14 项非 0；导入表常见 `mscoree.dll` | dnSpy、ILSpy |
| WebAssembly | `00 61 73 6D`（`\0asm`） | wasm2wat / wat2wasm |
| Mach-O | `CE FA ED FE` / `CF FA ED FE`；fat 文件 `CA FE BA BE` | otool、IDA/Ghidra |
| 固件/IoT | `file` 报 `data`，内部嵌多种魔数 | binwalk |
| ARM/MIPS | ELF 但 `readelf -h` 的 Machine 不是 x86 | 交叉 objdump、qemu-user |

## 2. Python：PyInstaller 与 pyc

Python 是解释执行的，纯脚本没有"逆向"对象——附件里的 Python 题永远是两种形态之一：**裸 pyc**（源码编译后的字节码文件），或**打包产物**（PyInstaller 等工具把解释器和 pyc 捆成一个可执行文件）。两条路殊途同归：最后都拿到 pyc，都对它反汇编或反编译。

### 2.1 裸 pyc：头部与魔数

本章的示例脚本（也是 2.3 节的打包对象）：

```python
KEY = "mult1platf0rm"

def check(s: str) -> bool:
    v = 0
    for ch in s:
        v = (v * 31 + ord(ch)) & 0xFFFFFF
    return v == 0x3D2C1A

if __name__ == "__main__":
    s = input("key: ")
    if check(s):
        print("flag{py_p4ck3d_0k}")
    else:
        print("wrong")
```

`py_compile` 模块把源码编译成 pyc：

```bash
python3 -m py_compile pyapp.py
ls -l __pycache__/
xxd -l 16 __pycache__/pyapp.cpython-314.pyc
```

输出：

```
-rw-r--r-- 1 hua hua 811 Oct 22 12:27 pyapp.cpython-314.pyc
00000000: 2b0e 0d0a 0000 0000 b390 d96a 1901 0000  +..........j....
```

头 16 字节是 pyc 的元信息：前 4 字节是 **Python 版本魔数**，后 12 字节是位标志、源文件修改时间与大小。版本魔数是识别 pyc 的关键，也是 2.4 节补头的依据：

| Python 版本 | 魔数字节 |
| ---- | ---- |
| 3.8 | `55 0D 0D 0A` |
| 3.11 | `A7 0D 0D 0A` |
| 3.14 | `2B 0E 0D 0A` |

> [!warning] file 认不出新版本 pyc
> `file __pycache__/pyapp.cpython-314.pyc` 的输出是 `data`——file 的识别库没跟上 3.14 的新魔数。[[R01-逆向工程与CTF竞赛生态导论#3. 常见附件类型与识别|R01 第 3 节]]说过 file 报 `data` 不代表文件坏。==看到 `.pyc` 后缀加 `55 0D`、`A7 0D`、`2B 0E` 一类开头，按 pyc 处理==。

> [!info]- 头 16 字节的完整布局
> 4 字节魔数 + 4 字节位标志 + 4 字节源文件 mtime + 4 字节源文件大小。位标志为 0 时后 8 字节是时间戳与大小；基于哈希校验的 pyc（PEP 552）位标志非 0，后 8 字节换成哈希的上半段。题目附件里两种都可能出现，不影响反汇编。

### 2.2 dis：反汇编字节码

标准库的 `dis` 模块是字节码的 objdump，自带命令行入口，直接吃源文件：

```bash
python3 -m dis pyapp.py | head -12
```

输出：

```
  0           RESUME                   0

  1           LOAD_CONST               0 ('mult1platf0rm')
              STORE_NAME               0 (KEY)

  3           LOAD_CONST               1 (<code object __annotate__ at 0x798f6b932730, file "pyapp.py", line 3>)
              MAKE_FUNCTION
              LOAD_CONST               2 (<code object check at 0x798f6b82e0b0, file "pyapp.py", line 3>)
              MAKE_FUNCTION
              SET_FUNCTION_ATTRIBUTE  16 (annotate)
              STORE_NAME               1 (check)
```

对 pyc 文件，`python3 -m dis` 不认（它只接受源码），要用 `marshal` 模块跳过 16 字节头、加载代码对象、再交给 dis：

```bash
python3 -c "
import dis, marshal
data = open('__pycache__/pyapp.cpython-314.pyc','rb').read()
code = marshal.loads(data[16:])
dis.dis(code)
" | head -39
```

输出：

```

  3           LOAD_CONST               1 (<code object __annotate__ at 0x721b6042e830, file "pyapp.py", line 3>)

              PUSH_NULL
              LOAD_CONST               4 ('key: ')
```

两点值得注意：==flag 就在常量表里==（`LOAD_CONST 5 ('flag{py_p4ck3d_0k}')`）——pyc 不做字符串混淆时，反汇编一屏就能看到；3.14 会多出一个 `__annotate__` 代码对象（存放参数注解），与题目逻辑无关，跳过即可。输出截断在模块级代码，往下翻是 `check` 的字节码与 14 行起 `wrong` 分支，`dis.dis` 会递归反汇编嵌套的函数代码对象（2.4 节有 `check` 的单独展示）。

> [!info]- 反编译工具：pycdc 与 decompyle3 的版本局限
> 反汇编之上还有反编译：**pycdc**（Decompyle++，C++ 实现，GitHub 见延伸阅读）对新版本 pyc 支持到什么程度随版本浮动，输出可能有缺口，但覆盖面最广，装法是源码 cmake 构建：`git clone https://github.com/zrax/pycdc && cd pycdc && cmake . && make`。**uncompyle6 / decompyle3**（`pip install decompyle3`）只支持到 Python 3.8，之后的字节码格式改动（3.11 起的异常表、3.12/3.13 的指令调整）让它们直接放弃。==3.9 以上的 pyc，dis 反汇编是兜底手段，读字节码推逻辑==。

> [!note] Pyarmor 一句话
> Pyarmor 是商业 Python 混淆方案：把代码对象加密，运行时用自己的 runtime 包解密执行，产物不再是标准 pyc。见到它按壳处理（[[R09-加壳与脱壳|R09]] 的思路），CTF 里出场率远低于裸 pyc。

### 2.3 PyInstaller 打包：外壳的识别特征

安装 PyInstaller 后一条命令打包成单文件可执行程序：

```bash
pip install pyinstaller          # 已安装则跳过
pyinstaller --onefile --distpath dist --workpath build pyapp.py
```

输出（打包过程的日志行略，只保留收尾一行）：

```
5933 INFO: Build complete! The results are available in: /tmp/r13/py/dist
```

```bash
ls -l dist/pyapp
file dist/pyapp
echo wrongkey | ./dist/pyapp
```

输出：

```
-rwxr-xr-x 1 hua hua 9288416 Oct 22 12:27 dist/pyapp
dist/pyapp: ELF 64-bit LSB executable, x86-64, version 1 (SYSV), dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2, for GNU/Linux 3.2.0, BuildID[sha1]=e150a976096419cc5c8f6263525324b69993c408, stripped
key: wrong
```

`file` 的判定是普通 ELF 且 stripped——它确实是一个 ELF：里面装着自带的 Python 解释器（`libpython3.14.so`）和压缩后的脚本包。**只看 file 会误判成常规逆向题**，识别 PyInstaller 靠字符串：

```bash
strings dist/pyapp | grep -E "pyi-|PYZ" | head -6
```

输出：

```
pyi-enable-onefile-parent-verification
pyi-python-flag
pyi-runtime-tmpdir
pyi-contents-directory
pyi-bootloader-ignore-signals
pyi-
```

`pyi-` 前缀的引导字符串与 `PYZ` 归档名是 PyInstaller 的签名。PE 平台的 PyInstaller 产物同理（外壳换成 PE，字符串特征不变）。

### 2.4 提取：从 exe 到 pyc

PyInstaller 把所有资源放进文件末尾的一个归档段（CArchive）。官方自带的查看器 `pyi-archive_viewer`（随 PyInstaller 安装）先列出归档内容：

```bash
pyi-archive_viewer -l dist/pyapp
```

输出：

```
Contents of 'pyapp' (PKG/CArchive):
 position, length, uncompressed_length, is_compressed, typecode, name
 0, 232, 291, 1, 'm', 'struct'
 232, 2896, 5038, 1, 'm', 'pyimod01_archive'
 3128, 13829, 32319, 1, 'm', 'pyimod02_importers'
 16957, 2874, 6619, 1, 'm', 'pyimod03_ctypes'
 19831, 1158, 2048, 1, 's', 'pyiboot01_bootstrap'

 23042, 34585, 83120, 1, 'b', 'libbz2.so.1.0'
 …（其后是 libpython、libssl 等 20 多个 .so 与 base_library.zip、PYZ.pyz）
```

条目类型码 `'s'` 是脚本（marshalled 代码对象）、`'m'` 是模块、`'b'` 是二进制、`'z'` 是 PYZ 归档。名字与主脚本同名的 `'s'` 条目（`pyapp`，795 字节）就是入口代码。交互模式里用 `X` 命令提取，它接着会追问输出文件名；三次输入可以用管道喂进去，非交互完成：

```bash
printf 'X pyapp\npyapp_main\nQ\n' | pyi-archive_viewer dist/pyapp | tail -2
```

输出：

```
 7526908, 1686876, 1686876, 0, 'z', 'PYZ.pyz'
? Output filename? ?
```

`X pyapp` 提取、`pyapp_main` 回答输出文件名、`Q` 退出（末尾那个单独的 `?` 是下一次交互的提示符）。提取物不是合法 pyc——它只有 marshal 数据，没有 16 字节头：

```bash
ls -l pyapp_main
python3 -c "
raw = open('pyapp_main','rb').read()
print(len(raw), raw[:8].hex(' '))
"
```

输出：

```
-rw-r--r-- 1 hua hua 795 Oct 22 12:28 pyapp_main
795 63 00 00 00 00 00 00 00
```

开头字节 `0x63` 是 marshal 对 code 对象的类型标记（字符 `c`）。补上本机 Python 的魔数加 12 字节零，就是合法 pyc，反汇编：

```bash
python3 -c "
import dis, marshal, importlib.util
raw = open('pyapp_main','rb').read()
pyc = importlib.util.MAGIC_NUMBER + b'\x00' * 12 + raw
code = marshal.loads(pyc[16:])
fn = next(c for c in code.co_consts if hasattr(c, 'co_name') and c.co_name == 'check')
dis.dis(fn)
"
```

输出：

```
  3           RESUME                   0

  4           LOAD_SMALL_INT           0
              STORE_FAST               1 (v)

  5           LOAD_FAST_BORROW         0 (s)
              GET_ITER
      L1:     FOR_ITER                35 (to L2)
              STORE_FAST               2 (ch)

  6           LOAD_FAST_BORROW         1 (v)
              LOAD_SMALL_INT          31
              BINARY_OP                5 (*)
              LOAD_GLOBAL              1 (ord + NULL)
              LOAD_FAST_BORROW         2 (ch)
              CALL                     1
              BINARY_OP                0 (+)
              LOAD_CONST               1 (16777215)
              BINARY_OP                1 (&)
              STORE_FAST               1 (v)
              JUMP_BACKWARD           37 (to L1)

  5   L2:     END_FOR
              POP_ITER

  7           LOAD_FAST_BORROW         1 (v)
              LOAD_CONST               2 (4008986)
              COMPARE_OP              72 (==)
              RETURN_VALUE
```

`check` 的算法一步不落：逐字节 `v = (v*31 + ord(ch)) & 0xFFFFFF`，与 `4008986`（即 0x3D2C1A）比较。按 [[R05-静态分析工具链IDA与Ghidra|R05]] 逆推变换的方法算出 key，或直接注意到==校验是自乘累加哈希、存在碰撞==——写个同式循环找一串满足 `v == 0x3D2C1A` 的输入即可。

> [!info]- pyinstxtractor：另一种提取工具
> 社区脚本 pyinstxtractor（GitHub 见延伸阅读）一条命令解完整个归档，并自动给所有脚本条目补 pyc 头，支持新老 PyInstaller 版本。原理与上文手工流程一致：定位 CArchive 目录 → 逐条解压 → 补魔数。手工流程的价值在于看清归档结构；批量处理时用工具。

## 3. Java 与 Android：class、jar 与 APK

Java 编译产物是 class 文件（JVM 字节码），Android 把 class 再转成 dex（ART/Dalvik 字节码）。两边字节码都带完整元数据（类名、方法名、字段类型），反编译能还原出非常接近源码的结果，是所有平台里最"友好"的一类。

### 3.1 javac、jar 与 class 文件

分析对象：

```java
import java.util.Scanner;

public class License {
    static int mix(String s) {
        int v = 7;
        for (int i = 0; i < s.length(); i++) {
            v = v * 31 + s.charAt(i);
        }
        return v;
    }

    public static void main(String[] args) {
        Scanner sc = new Scanner(System.in);
        String s = sc.nextLine();
        if (mix(s) == 0x2A2B2C) {
            System.out.println("flag{j4va_byt3c0d3}");
        } else {
            System.out.println("wrong");
        }
    }
}
```

编译、打包、运行（JDK 的安装：`sudo apt install openjdk-21-jdk-headless`，含 javac；只运行 jar 的话 JRE 即可，jadx 调用的也是 java 命令）：

```bash
javac License.java
jar cfe license.jar License License.class
echo wrongkey | java -jar license.jar
```

输出：

```
wrong
```

class 文件的魔数是 8 个十六进制位里最著名的一个：

```bash
xxd -l 16 License.class
file License.class
```

输出：

```
00000000: cafe babe 0000 0041 003c 0a00 0200 0307  .......A.<......
License.class: compiled Java class data, version 65.0 (Java SE 21)
```

`CA FE BA BE` 之后紧跟次/主版本号（这里 `00 00 00 41`，主版本 65 = Java SE 21）。jar 是 zip 容器，`unzip -l license.jar` 可见 `META-INF/MANIFEST.MF` 与 class 列表。

想看 JVM 字节码本身，JDK 自带的 `javap` 相当于字节码版的 objdump：

```bash
javap -c -p License | sed -n '1,28p'
```

输出：

```
      27: goto          5
```

栈式字节码，方法名与常量都是明文，可读性远高于机器码。

### 3.2 jadx：反编译回 Java

jadx（开源，GitHub 见延伸阅读）把 class/dex/jar/APK 直接反编译回 Java。安装：GitHub Releases 下载对应平台的压缩包，或 `sudo apt install jadx`（发行版仓库版本可能偏旧，建议前者）：

```bash
jadx -d out license.jar
cat out/sources/defpackage/License.java
```

输出：

```java
package defpackage;

import java.util.Scanner;

/* JADX INFO: loaded from: license.jar:License.class */
public class License {
    static int mix(String str) {
        int iCharAt = 7;
        for (int i = 0; i < str.length(); i++) {
            iCharAt = (iCharAt * 31) + str.charAt(i);
        }
        return iCharAt;
    }

    public static void main(String[] strArr) {
        if (mix(new Scanner(System.in).nextLine()) == 2763564) {
            System.out.println("flag{j4va_byt3c0d3}");
        } else {
            System.out.println("wrong");
        }
    }
}
```

与源码几乎一致。==识别细节会变样但逻辑不变==：默认包被 jadx 命名为 `defpackage`，十六进制字面量 `0x2A2B2C` 被换算成十进制 `2763564`（两数相等），Scanner 被内联进条件。APK 的用法相同：`jadx -d out app.apk`，产物按 `sources/包名/类名.java` 组织，GUI 版（jadx-gui）带搜索与交叉引用，操作逻辑与 [[R05-静态分析工具链IDA与Ghidra|R05]] 的字符串窗口一致。

### 3.3 class 与 dex 的差异

Android 构建链把 javac 产出的 class 再编译成 dex。CTF 视角的差异：

| | Java class | dex |
| ---- | ---- | ---- |
| 运行环境 | JVM | Android 的 ART/Dalvik |
| 字节码模型 | 栈式：操作数压栈出栈 | 寄存器式：指令直接操作虚拟寄存器 |
| 文件组织 | 一个类一个 .class 文件 | 多个类合并进一个 classes.dex |
| 魔数 | `CA FE BA BE` | `64 65 78 0A`（`dex\n`）+ 版本 |

分析路径不变：APK 用 jadx 打开，看到的是反编译回的 Java；想看字节码本身才需要分清 class 与 dex 两套指令。

### 3.4 smali 最小速览

反编译回 Java 有失真的时候（混淆、jadx 还原失败的方法），这时退一步看字节码。dex 字节码的汇编形式叫 **smali**，jadx-gui 里每个类都有对应的 Smali 视图，apktool 解包 APK 也输出 smali。`mix` 方法在 smali 里的形状（示意，去掉了行号与调试信息）：

```smali
.method static mix(Ljava/lang/String;)I
    const/4 v0, 0x7            # v0 = 7（累加器，v 开头是虚拟寄存器）
    const/4 v1, 0x0            # v1 = 0（循环变量 i）
    :goto_0
    invoke-virtual {p0}, Ljava/lang/String;->length()I   # 调用 s.length()
    move-result v2
    if-ge v1, v2, :cond_0      # i >= length 则跳出
    mul-int/lit8 v0, v0, 0x1f  # v0 = v0 * 31
    invoke-virtual {p0, v1}, Ljava/lang/String;->charAt(I)C
    move-result v2             # 取返回值
    add-int/2addr v0, v2       # v0 += char
    add-int/lit8 v1, v1, 0x1   # i++
    goto :goto_0
    :cond_0
    return v0
.end method
```

读 smali 抓三类指令就够：`const*`（装常量）、`invoke-*`（调方法，`{参数}` 里放寄存器）、`move-result`（取上一条 invoke 的返回值）。寄存器 `vN` 是方法内的虚拟寄存器，`pN` 是方法参数（静态方法 `p0` 是第一个参数）。==smali 读法与 [[R03-x86与x64汇编精要复习|R03]] 读机器码的思路相同：盯常量、盯调用、盯分支==。

> [!info]- apktool 与 Frida
> **apktool**：把 APK 解包成 smali + 资源文件，改完可回打包成 APK——需要"改了再装回手机"的题（patch smali 跳过校验）用它。命令：`apktool d app.apk` 解包、`apktool b 目录` 回打包。
> **Frida**：动态插桩框架，把 JavaScript 脚本注入运行中的进程，直接 hook 任意方法。装法：电脑侧 `pip install frida-tools`，Android 设备侧运行对应架构的 frida-server。Java 层 hook 示例场景：校验函数过于复杂时，hook 住它直接打印入参返回值，或强制改返回值为 true。它是 [[R06-动态调试GDB与x64dbg|R06]] 动态调试思想在托管平台上的对应物。native 层的 hook（`Interceptor.attach`）在 3.6 展开。

### 3.5 APK 里的 native 层：从 native 声明到 .so

jadx 的输出里有一类方法没有方法体：声明带 `native` 关键字，实现在 APK 自带的 C/C++ 动态库里，不在 dex 里。这类库本身就是 ELF（[[R04-可执行文件格式ELF与PE|R04]]），反汇编工具与第 11 节的 ARM 题相同；本节补两块 JNI 专属的知识：**怎么从 Java 侧定位到 .so 里的函数**，以及**函数名的两种来源**——这决定了静态分析时去符号表里找，还是去数据段里找。

**.so 的位置**。APK 是 zip 容器，native 库按 ABI 分目录放在 `lib/` 下。自建一个最小布局验证（真实 APK 里另有 classes.dex、resources.arsc 等条目）：

```bash
mkdir -p apk_skel/lib/arm64-v8a
cp libnativedemo.so apk_skel/lib/arm64-v8a/
cd apk_skel && zip -q -r ../sample.apk . && cd ..
unzip -l sample.apk
```

**Java 侧的线索**。jadx 里看到两类东西就该往 native 想：带 `native` 关键字的声明（没有方法体），和加载库的调用 `System.loadLibrary("nativedemo")`——库名 `nativedemo` 对应文件 `libnativedemo.so`（`lib` 前缀与 `.so` 后缀由系统补全）。smali 视图里 native 声明同样直接可见：`.method public static native check(I)Z`。

**静态绑定：按名字导出**。native 方法要与 .so 里的 C 函数对上号，第一种方式是命名约定：C 函数按 `Java_包名_类名_方法名` 命名（包名的点换成下划线）并导出，ART 装载后按名解析。规则不必背——JDK 能直接生成。给声明加上加载调用：

```java
package com.ctf;

public class NativeDemo {
    static {
        System.loadLibrary("nativedemo");   // 装载 libnativedemo.so
    }

    public static native boolean check(int v);
    public static native boolean check2(int v);
}
```

编译时让 javac 生成 JNI 头文件：

```bash
javac -h jni_out -d classes com/ctf/NativeDemo.java
cat jni_out/com_ctf_NativeDemo.h
```

输出（节选）：

```c
/*
 * Class:     com_ctf_NativeDemo
```

签名 `(I)Z` 是参数与返回类型的 JNI 描述符（`I` = int，`Z` = boolean）。注意头文件给 check2 也生成了 `Java_com_ctf_NativeDemo_check2` 原型——下面的示例 .so 并不定义它，因为 check2 走另一条路。

**动态注册：RegisterNatives**。第二种方式在装载时把"方法名 + 签名 → 函数指针"的注册表交给虚拟机：实现函数不必按约定命名，声明成 `static` 就不会出现在任何导出符号里。注册发生在 `JNI_OnLoad` 里，把装载时机连起来看：

> `System.loadLibrary` 触发 dlopen 装库（`.init_array` 里的 ELF 初始化函数此时执行，[[R04-可执行文件格式ELF与PE|R04]]）→ ART 按名查找 `JNI_OnLoad` 并调用它，读返回的 JNI 版本号 → 之后 Java 代码调用 native 方法时，按注册表或按名绑定到实现函数。

示例 .so 把三种形态放在一起（AArch64 Linux；真实 APK 里的 .so 由 Android 的 bionic 工具链编译，符号可见性的结论一致）：

```c
#include <jni.h>

#define MIX_TARGET  401767     /* check  的目标常数：secret_mix(12345) */
#define MIX_TARGET2 31591      /* check2 的目标常数：secret_mix(777)  */

static jint secret_mix(jint v) {          /* static：不导出 */
    jint acc = 7;
    for (int i = 0; i < 2; i++) acc = acc * 31 + v;
    return acc;
}

/* 形态一：静态绑定，名字按 javac -h 生成的原型 */
JNIEXPORT jboolean JNICALL
Java_com_ctf_NativeDemo_check(JNIEnv *env, jclass cls, jint v) {
    (void)env; (void)cls;
    return secret_mix(v) == MIX_TARGET ? JNI_TRUE : JNI_FALSE;
}

/* 形态二的实现函数：static，动态符号表里查不到 */
static jboolean native_check2(JNIEnv *env, jclass cls, jint v) {
    (void)env; (void)cls;
    return secret_mix(v) == MIX_TARGET2 ? JNI_TRUE : JNI_FALSE;
}

/* 形态二：动态注册。ART 在 loadLibrary 装库后按名调它 */
JNIEXPORT jint JNICALL
JNI_OnLoad(JavaVM *vm, void *reserved) {
    (void)reserved;
    JNIEnv *env = NULL;
    if ((*vm)->GetEnv(vm, (void **)&env, JNI_VERSION_1_6) != JNI_OK)
        return JNI_ERR;
    jclass cls = (*env)->FindClass(env, "com/ctf/NativeDemo");
    if (cls == NULL)
        return JNI_ERR;
    static const JNINativeMethod methods[] = {
        { "check2", "(I)Z", (void *)native_check2 },
    };
    if ((*env)->RegisterNatives(env, cls, methods, 1) != JNI_OK)
        return JNI_ERR;
    return JNI_VERSION_1_6;
}

/* 对照组：真正的 ELF 初始化函数，编译器挂进 .init_array */
static volatile int g_ready = 0;

__attribute__((constructor))
static void demo_init(void) {
    g_ready = 1;
}
```

**.init_array 与 JNI_OnLoad 的区分**：

`.init_array` 的两个 8 字节槽位：0x700 是编译器自带的运行时初始化函数，0x8e0 正是 `demo_init`（与 nm 的地址一致）——`__attribute__((constructor))` 修饰的函数由编译器挂进这里，dlopen 时由动态链接器执行。`JNI_OnLoad`（0x7d4）不在其中：==它是 ART 按名调用的导出函数，不是 ELF 初始化函数==。读真实样本时两者的用途也要分开：.init_array 里的代码在装载时无条件执行，常放反调试；JNI_OnLoad 里的代码在装载后执行，常放注册与初始化。

**运行观察**。写一个同架构宿主程序模拟"装载 + 按名找符号"的过程（qemu-user 用法见 [[#11.1 交叉编译、qemu 运行、反汇编：三件套|11.1]]）：

```c
#include <stdio.h>
#include <dlfcn.h>

typedef unsigned char jboolean_stub;
typedef int jint_stub;

int main(void) {
    void *h = dlopen("./libnativedemo.so", RTLD_NOW);
    if (!h) {
        printf("dlopen 失败: %s\n", dlerror());
        return 1;
    }
    printf("dlopen 成功\n");

    void *sym = dlsym(h, "Java_com_ctf_NativeDemo_check");
    if (sym) {                       /* 静态绑定：按名能找到 */
        jboolean_stub (*fn)(void *, void *, jint_stub) = sym;
        printf("check(12345) = %d\n", fn(NULL, NULL, 12345));
    }
    printf("dlsym native_check2 -> %p\n", dlsym(h, "native_check2"));
    return 0;
}
```

harness 直接调用静态导出的函数——它不 deref 传进来的 JNIEnv\*，测试里传 NULL 即可；`dlsym` 对 `native_check2` 返回 NULL：dlsym 只查动态符号表，动态注册的函数不在那里。IDA/Ghidra 里的对应流程：载入 .so（自动识别 AArch64，[[R05-静态分析工具链IDA与Ghidra|R05]]）→ `Java_` 开头的函数即 Java 方法入口 → 搜字符串 `com/ctf/NativeDemo` 或从 JNI_OnLoad 的交叉引用找到注册表数组 → 读出隐藏实现函数的地址，继续按 3.6 挂 hook 或按 11.1 的路线静态分析。

> [!warning] Android 的 .so 链接 bionic，不是 glibc
> 本节样本用交叉编译器加 glibc 造出，符号与初始化机制的结论一致；真实 APK 里的 .so 链接 Android 的 bionic libc，`readelf -d` 的 NEEDED 是 `/system/lib64/libc.so` 这类路径。导入表里出现 `dlopen`/`dlsym`/`ptrace`，或字符串里出现 `/proc/` 路径，通常对应运行时自解密与反调试——先查 .init_array 与 JNI_OnLoad 两处。

### 3.6 Frida：native 层 Hook（Interceptor.attach）

3.4 的折叠框里 Frida 在 Java 层做的事——注入脚本、hook 任意方法——对 native 层同样成立，入口换成 `Interceptor.attach`：按地址挂回调，`onEnter` 读参数、`onLeave` 改返回值。==Frida 运行在设备侧：frida-server 跑在 Android 设备或模拟器上，电脑侧工具通过 USB 与它通信，WSL 实验环境没有设备——本节只给命令语法与脚本写法，不配输出==。

流程四步（push 与 shell 命令操作设备，其余在电脑侧执行）：

```bash
adb push frida-server-arm64 /data/local/tmp/fs
adb shell "chmod 755 /data/local/tmp/fs && /data/local/tmp/fs &"   # 设备侧起 frida-server（需 root）
pip install frida-tools                                            # 电脑侧工具
frida-ps -U                                                        # 确认设备上的进程可见
frida -U -f com.ctf.app -l hook.js                                 # 注入脚本并启动应用
```

静态导出的函数按导出名挂：

```javascript
// hook.js —— 拦截 check：打印入参，强制返回 true
Interceptor.attach(
    Module.findExportByName("libnativedemo.so", "Java_com_ctf_NativeDemo_check"), {
    onEnter(args) {
        // 静态方法的 JNI 参数布局：args[0]=JNIEnv*，args[1]=jclass，args[2]=int v
        console.log("check(v=" + args[2].toInt32() + ")");
    },
    onLeave(retval) {
        retval.replace(1);      // jboolean 的 true，校验当场通过
    }
});
```

动态注册的函数没有导出名，用"基址 + 偏移"挂——偏移就是 3.5 静态分析里读到的地址（`native_check2` 在 0x79c）：

```javascript
const base = Module.findBaseAddress("libnativedemo.so");   // 运行时基址，每次启动不同
Interceptor.attach(base.add(0x79c), {
    onEnter(args) {                                        // JNI 参数布局与静态绑定相同
        console.log("check2(v=" + args[2].toInt32() + ")");
    }
});
```

> [!info]- 连偏移都不知道时：截获注册表
> 函数指针会在 RegisterNatives 的 JNINativeMethod 数组里流过一次。Frida 侧的通行做法是趁 JNI_OnLoad 执行时截获这次调用：RegisterNatives 在 JNIEnv 函数表的第 215 项（64 位下偏移 215×8 = 1720，即 3.5 反汇编里的 `ldr x4, [x0, #1720]`），挂到该调用后从参数读出数组地址与元素个数，按 `{char* name, char* sig, void* fnPtr}` 逐项解析，拿到函数地址再 attach。字符串参数（jstring）的读取要走 JNIEnv 提供的 GetStringUtfChars 一类函数，属于 Java 与 native 的边界操作，用到时查 JNI 文档。

与 [[R06-动态调试GDB与x64dbg|R06]] 的断点对照：`Interceptor.attach` 是"断点 + 命令脚本"的自动化形态——onEnter 对应断在函数入口读寄存器，onLeave 对应断在返回处改返回值；区别是脚本常驻、免手工交互，适合批量打印或改写。Java 层 hook 要包在 `Java.perform` 里（3.4 折叠框），native 层直接 `Interceptor.attach`，两层可写在同一份脚本里：jadx 里看到 native 声明（3.5），Frida 里同时挂 Java 包装层与 .so 实现，输入输出对照读。

## 4. Go：runtime 符号群与 pclntab

Go 编译成原生机器码，分析工具与 C 相同（objdump、IDA、Ghidra），但产物带浓厚的自有特征，函数名还有一条独立于符号表的恢复通道。

示例程序：

```go
package main

import "fmt"

//go:noinline
func mix(s string) uint32 {
	var v uint32 = 0x811C9DC5
	for i := 0; i < len(s); i++ {
		v = (v ^ uint32(s[i])) * 0x01000193
	}
	return v
}

func main() {
	var s string
	fmt.Print("key: ")
	fmt.Scan(&s)
	if mix(s) == 0x9E3779B9 {
		fmt.Println("flag{go_r0ut1n3s}")
	} else {
		fmt.Println("wrong")
	}
}
```

`mix` 是 32 位 FNV-1a 哈希：

$$v' = (v \oplus b_i) \times \mathtt{0x01000193} \bmod 2^{32}, \quad v_0 = \mathtt{0x811C9DC5} \tag{13.1}$$

初值 0x811C9DC5（FNV offset basis）与乘数 0x01000193（FNV prime）是固定常数，[[R07-编码与算法识别还原|R07]]的常数识别表里能对上号。

### 4.1 编译与第一眼特征

```bash
go build -o gocrack main.go
file gocrack
echo wrongkey | ./gocrack
```

输出：

```
gocrack: ELF 64-bit LSB executable, x86-64, version 1 (SYSV), statically linked, Go BuildID=BHPv3mfdqZeH0Sy01dZ9/wxpdNQy3L_81LeHKVlAk/osbUlXocJeulzZeUxyEz/9vxnTD-FQpe9qi510EUd, with debug_info, not stripped
key: wrong
```

`file` 一眼定案：==输出里直接写着 `Go BuildID=`==。Go 默认静态链接（gocrack 约 2.3 MB，不依赖 libc），BuildID 存在 `.note.go.buildid` 这个 ELF note 里。两条命令再确认：

```bash
go tool buildid gocrack
strings -t x gocrack | grep -m2 "go1\.23"
```

输出：

```
BHPv3mfdqZeH0Sy01dZ9/wxpdNQy3L_81LeHKVlAk/osbUlXocJeulzZeUxyEz/9vxnTD-FQpe9qi510EUd
  e3440 go1.23.4
 160021 go1.23.4
```

`go tool buildid` 读出同一个 ID；strings 里能扫到工具链版本 `go1.23.4`（pclntab 元数据的一部分，4.2 讲）。==file 报 BuildID、strings 见 `go1.x`，两条特征合起来，Go 的识别不需要猜==。

### 4.2 符号形状：runtime.* 与包名.函数名

未 strip 的 Go 产物符号表完整，函数名是 `包名.函数名` 形式，库函数全部在 `runtime` 包下：

```bash
echo "runtime.* 符号数: $(nm gocrack | grep -c ' runtime\.')"
nm gocrack | grep -E "T main\.(main|mix)"
```

输出：

```
runtime.* 符号数: 1598
000000000049be20 T main.mix
000000000049be60 T main.main
```

1598 个 `runtime.*` 符号——Go 运行时（调度器、GC、内存管理）的函数群，见到这个规模的 `runtime.` 符号群即可断定是 Go。用户函数 `main.mix`、`main.main` 与 C 的 `main` 命名不同：带包名前缀，IDA 里看函数列表就能对上源码结构。示例里 `//go:noinline` 是防止编译器把 `mix` 内联进 `main`（小函数默认会内联，内联后独立符号消失）。

### 4.3 strip 之后：pclntab 还在

Go 的 strip 惯用 `go build -ldflags "-s -w"`（-s 去符号表，-w 去 DWARF 调试信息）：

```bash
go build -ldflags "-s -w" -o gocrack_s main.go
ls -l gocrack gocrack_s
nm gocrack_s
file gocrack_s
```

输出：

```
-rwxr-xr-x 1 hua hua 2280999 Oct 22 12:32 gocrack
-rwxr-xr-x 1 hua hua 1487000 Oct 22 12:32 gocrack_s
nm: gocrack_s: no symbols
gocrack_s: ELF 64-bit LSB executable, x86-64, version 1 (SYSV), statically linked, Go BuildID=es6fuJ0Tk-trAkV22hV5/J5El7QhCMcDywSvowd-y/osbUlXocJeulzZeUxyEz/Ou6CZ1KU-npQBlZKG76i, stripped
```

符号表没了，但 Go 程序的函数名另有出处：==pclntab==（procedure linkage table，Go 运行时自带的函数元数据表）记录每个函数的入口地址、源文件与函数名，供 panic 打印调用栈、profiling 等功能使用。它不属于 ELF 符号表，strip 删不掉，strings 都能直接扫到：

```bash
strings gocrack_s | grep -c "main\.mix"
strings gocrack_s | grep -c "go1\.23\.4"
```

输出：

```
1
2
```

`main.mix` 与版本串仍保留在 stripped 文件里。工具化这一步的是 GoReSym（Mandiant 开源，GitHub 见延伸阅读）：解析 pclntab，输出完整的函数列表、类型甚至源文件路径，对 stripped 的 Go 逆向是常规起手式。IDA/Ghidra 装 GoReSym 或同类插件（如 IDA 的 golang_loader_assist 思路的现代版本）后，函数名自动恢复。

## 5. Rust：panic 串与 _ZN 名字

Rust 也编译成原生机器码，识别特征集中在两处：panic 系统留下的源码路径字符串，和默认开启的名字粉碎。

安装工具链（Ubuntu 软件源版本足够本题使用）：`sudo apt install rustc`。示例程序：

```rust
fn mix(data: &[u8]) -> u32 {
    let mut v: u32 = 0x811C_9DC5;
    for &b in data {
        v = (v ^ b as u32).wrapping_mul(0x0100_0193);
    }
    v
}

fn check(s: &str) -> bool {
    mix(s.as_bytes()) == 0x9E37_79B9
}

fn main() {
    let mut buf = String::new();
    std::io::stdin().read_line(&mut buf).unwrap();
    if check(buf.trim()) {
        println!("flag{{rust_pan1c}}");
    } else {
        panic!("wrong key: {}", buf.trim());
    }
}
```

```bash
rustc demo.rs -o demo
file demo
echo wrongkey | ./demo
```

输出：

```
demo: ELF 64-bit LSB pie executable, x86-64, version 1 (SYSV), dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2, BuildID[sha1]=1192df1648b9213999ef4bd3b38b47e5a6d9cde8, for GNU/Linux 3.2.0, with debug_info, not stripped

thread 'main' (1966) panicked at demo.rs:19:9:
wrong key: wrongkey
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
```

三个识别特征已经出现：

1. **panic 消息自带源码位置**（`demo.rs:19:9`）。运行时 panic 是 Rust 程序的常态（数组越界、unwrap 失败、显式 panic!），位置字符串必然写进产物。strings 里还能扫到 `demo.rs` 这个文件名本身：

```bash
strings demo | grep -c "demo\.rs"
strings demo | grep -m1 "RUST_BACKTRACE"
```

输出：

```
1
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
```

==strings 见源码路径与 RUST_BACKTRACE 提示，基本可断定 Rust==。cargo 构建的程序路径是 `src/main.rs` 形式。

2. **`_ZN` 开头的符号**。Rust 默认用旧式（legacy）名字粉碎，形如 Itanium C++ 方案加一段哈希：

```bash
nm demo | grep _ZN4demo
```

输出：

```
000000000000b4d0 t _ZN4demo3mix17h39e8d29f77cc923eE
000000000000b540 T _ZN4demo4main17h9c6a30f2ed21e6bfE
000000000000b800 t _ZN4demo5check17hfe192772e8457aefE
```

`_ZN4demo3mix` 按 C++ 规则就是 `demo::mix`，尾巴的 `17h39e8d29f77cc923eE` 是 16 位十六进制的符号哈希（防止不同版本的同名函数冲突）。c++filt 能还原出主体：

```bash
nm demo | grep _ZN4demo | awk '{print $3}' | c++filt
```

输出：

```
demo::mix::h39e8d29f77cc923e
demo::main::h9c6a30f2ed21e6bf
```

哈希尾巴留在原地——c++filt 只按 C++ 规则翻译，Rust 的部分它不管，但==函数名与模块路径已经可读，定位用户函数足够了==。

> [!info]- v0 粉碎与 rustfilt
> 新版 rustc 可选用 v0 方案（编译参数 `-C symbol-mangling-version=v0`），符号以 `_R` 开头，结构与 C++ 完全不同，c++filt 无能为力。专用工具 rustfilt（`cargo install rustfilt`）能完整还原 v0 与 legacy 两种格式。看到 `_R` 开头的符号就换 rustfilt。

3. **体积大、库函数多**。11.8 MB 的文件里绝大多数是标准库（libstd）静态编入的代码，与用户逻辑无关。定位题目逻辑与 [[R05-静态分析工具链IDA与Ghidra#3.9 FLIRT：库函数签名识别|R05 的 FLIRT 思路]]相同：先认库函数跳过，剩下的小函数才是 check。Rust 无运行时 GC，panic 路径之外的代码与 C 产物密度接近。

## 6. C++：名字粉碎、vtable 与 RTTI

C++ 逆向的三个标志性对象：`_Z` 开头的粉碎符号、虚函数表、RTTI。示例程序把三者都放进去：

```cpp
#include <cstdio>
#include <string>
#include <vector>

class Animal {
public:
    virtual ~Animal() = default;
    virtual int speak(int n) { return n; }
};

class Dog : public Animal {
public:
    int speak(int n) override { return n * 3; }
};

int check(const std::string& s) {
    std::vector<int> v;
    for (char c : s) v.push_back(c * 2);
    int acc = 0;
    for (int x : v) acc = acc * 31 + x;
    return acc;
}

int main() {
    Dog d;
    Animal* a = &d;
    printf("%d\n", a->speak(7));
    printf("%d\n", check("ctf"));
    return 0;
}
```

### 6.1 _Z 名字粉碎与 c++filt

C++ 允许函数重载，符号必须把参数类型也编进去，这就是名字粉碎（name mangling），GNU 系编译器用 Itanium 方案，符号以 `_Z` 开头：

```bash
g++ -O0 -fno-pie -no-pie cppdemo.cpp -o cppdemo
nm cppdemo | grep -E "speak|check" | head -5
./cppdemo
```

输出：

```

0000000000402666 W _ZN3Dog5speakEi
0000000000402652 W _ZN6Animal5speakEi
0000000000402704 W _ZN6AnimalD0Ev
00000000004026e8 W _ZN6AnimalD1Ev
21

```

`_ZN3Dog5speakEi`：`N…E` 包住嵌套名（`3Dog`、`5speak` 前缀数字是长度），结尾 `i` 是参数 `int`。析构函数有 D0/D1 两个变体（删除型/完整型）。还原用 c++filt（binutils 自带）：

```bash
nm cppdemo | grep -E "speak|check" | awk '{print $3}' | c++filt
```

输出：

```

Animal::speak(int)

```

==c++filt 是 C++ 逆向的第一件工具==：反汇编里所有 `_Z…` 符号过一遍它，函数边界与角色立刻清晰。IDA/Ghidra 自动做这件事；命令行场景（objdump、grep）手动接管道。`std::vector`、`std::string` 的成员函数全带 `_ZNSt…` 前缀（`St` 是 std 的缩写），见前缀可整批归为库函数跳过。

### 6.2 vtable：多态在内存里的形状

`Dog` 重写了 `speak`，`a->speak(7)` 走到哪个函数要看对象的类型——运行时决定，靠的就是虚函数表。先看符号与节区位置（编译用了 `-fno-pie -no-pie`，地址固定）：

```bash
nm -C cppdemo | grep -E "vtable|typeinfo"
readelf -SW cppdemo | grep -E " \.(rodata|data\.rel\.ro) "
```

输出：

```
0000000000404188 V typeinfo for Dog
00000000004041a8 V typeinfo for Animal
00000000004041a0 V typeinfo name for Dog
00000000004041b8 V typeinfo name for Animal
0000000000404138 V vtable for Dog
0000000000404160 V vtable for Animal
  [15] .rodata           PROGBITS        0000000000404000 004000 0001c0 00   A  0  0  8
  [23] .data.rel.ro      PROGBITS        0000000000406d30 005d30 0000b8 00  WA  0  0 16
```

`nm -C` 已把符号翻译成 `vtable for Dog`、`typeinfo for Dog`。非 PIE 下每个类的 vtable 落在 `.rodata`（内含的函数地址链接期定死）。`objdump -s` 把 Dog 的 vtable 区域按字节读出来：

```bash
objdump -s -j .rodata cppdemo | sed -n '/404130/,/404180/p'
```

输出：

```

 404140 88414000 00000000 34274000 00000000  .A@.....4'@.....
```

全部小端，逐槽解读 Dog 的 vtable（`_ZTV3Dog` = 0x404138 起）：

| 地址 | 槽值 | 含义 |
| ---- | ---- | ---- |
| 0x404138 | 0 | offset-to-top（多继承时用，单继承为 0） |
| 0x404140 | 0x404188 | typeinfo 指针 → `_ZTI3Dog` |
| 0x404148 | 0x402734 | Dog 析构函数（D1） |
| 0x404150 | 0x402760 | Dog 析构函数（D0） |
| 0x404158 | 0x402666 | Dog::speak(int) |

==每个对象里存的 vptr 是"第一个函数槽"的地址，不是 vtable 符号地址==——中间隔着 offset-to-top 与 typeinfo 两个槽。Animal 的 vtable 同理从 0x404160 起：0x404170 起三个槽是 Animal 的 D1、D0 与 Animal::speak（0x402652）。虚函数按声明顺序排槽，析构函数占最前两个槽。

反汇编 main 里的虚调用，把这套结构用起来：

```asm
  40246e:	b8 48 41 40 00       	mov    eax,0x404148        ; vptr 初值 = _ZTV3Dog+0x10
  402473:	48 89 45 a8          	mov    QWORD PTR [rbp-0x58],rax  ; 存进对象（对象开头即 vptr）
  40247f:	48 8b 45 b0          	mov    rax,QWORD PTR [rbp-0x50]  ; a（Animal*）
  402483:	48 8b 00             	mov    rax,QWORD PTR [rax]       ; 取 vptr
  402486:	48 83 c0 10          	add    rax,0x10                  ; +0x10 → speak 的槽
  40248a:	48 8b 10             	mov    rdx,QWORD PTR [rax]       ; 取函数地址
  402491:	be 07 00 00 00       	mov    esi,0x7                   ; 参数 7
  402496:	48 89 c7             	mov    rdi,rax                   ; this
  402499:	ff d2                	call   rdx                       ; 间接调用
```

（x86-64 Linux，System V AMD64 ABI；this 指针走第一参数 rdi。）==反汇编里 `mov rax,[对象]; call [rax+偏移]` 的形状就是虚调用==：偏移 0x10 说明调的是虚表第 3 个槽。读懂 vtable 布局后，"这行虚调用调的是谁的函数"不再靠猜——查槽、对符号。

> [!warning] PIE 产物里 vtable 区域是零
> 不加 `-fno-pie` 时（主流发行版 gcc 默认 PIE），vtable 放进 `.data.rel.ro`（read-only after relocation，装载后转只读的可写节），文件里的地址槽位全是零，由装载时的 `R_X86_64_RELATIVE` 重定位填上（[[R04-可执行文件格式ELF与PE#1.5 重定位：哪个地址在什么时候填|R04 1.5]] 的机制）。文件里看到 vtable 区域全零不是坏了：`readelf -r` 的重定位表记着每个槽该填谁，IDA/Ghidra 载入时按重定位显示最终值。

### 6.3 RTTI：typeinfo 与类名

`typeid`、`dynamic_cast` 依赖的运行时类型信息也在产物里：`_ZTI6Animal`（typeinfo for Animal）与 `_ZTS6Animal`（typeinfo name，即字符串 `"6Animal"`）。`nm -C` 输出里的 `typeinfo for / typeinfo name for` 两类符号就是它们。作用有二：dynamic_cast 沿 typeinfo 里的继承链向上走（Animal 的 typeinfo 里存着父类指针）；逆向时 ==typeinfo 让反编译器把对象类型标出来==，IDA 伪代码里出现 `Dog` 类名多数来自这组符号。编译参数 `-fno-rtti` 可整体去掉（符号消失、dynamic_cast 不可用），题目用了它，伪代码里的类就只剩 vtable 形状可推。

## 7. .NET：PE 里的托管字节码

.NET 程序（C#、VB.NET 编译产物）是 PE 文件，但里面装的既不是机器码也不是本章前几节的字节码，而是 **CIL**（Common Intermediate Language，曾名 MSIL）加一套完整元数据表。识别与分析路径：

**识别**。`file` 只报 `PE32 executable`（R1 的附件类型表提过"需进工具确认"）。三条独立证据：

1. [[R04-可执行文件格式ELF与PE#3.5 Optional Header|R04 3.5]]的数据目录第 14 项（CLR Runtime Header，也叫 COM descriptor）非 0——这是格式层的判据，最可靠；
2. strings 扫到 `mscoree.dll` 与 `_CorExeMain`：.NET 程序的原生代码只有一小段启动桩，导入表通常只有这一个关键函数，由它把控制权交给 CLR 运行时；
3. 文件里有大段对齐的元数据表与字符串堆，`#~`、`#Strings`、`#US` 等节名特征。

**分析**。CIL 的元数据保真度比 Java class 还高（类名、方法名、字段、甚至参数名都在），反编译能还原出接近原始 C# 的代码：

- **dnSpy**（原版停更，社区维护版 dnSpyEx，Windows GUI，GitHub 见延伸阅读）：把 exe 拖进窗口 → 左侧程序集树逐层展开到类 → 双击方法，右侧直接显示反编译的 C#；选中行按 F5 下断点可当场调试（它自己就是调试器）。改代码重编译、patch CIL 也在这一个界面里完成，是 .NET crackme 的主力工具。
- **ILSpy**（开源）：GUI 版从 GitHub Releases 下载，同样的树形浏览 + C# 反编译；命令行版 `dotnet tool install -g ilspycmd`，`ilspycmd app.exe > app.cs` 一条命令导出全量源码，适合批量或脚本化。

> [!note] 与壳的交集
> .NET 也有壳（ConfuserEx 等混淆保护器），套壳后 dnSpy 打开看到的是运行时解密的骨架。判别与处理思路仍是 [[R09-加壳与脱壳|R09]] 的"等解密完成再取内容"：在 dnSpy 里断到解密后的程序集再导出。比赛里裸 .NET 题居多，先按裸的处理，打不开再怀疑壳。

## 8. WebAssembly：wat 与 wasm

WebAssembly（wasm）是给浏览器用的可移植字节码，CTF 里常以独立 `.wasm` 文件出题（配一个 JS 壳或直接让你分析模块）。wabt 工具集（WebAssembly Binary Toolkit，GitHub 见延伸阅读）是它的 binutils：`wat2wasm` 把文本格式编成二进制，`wasm2wat` 反着来。

### 8.1 手写 .wat 并编译

wat 是 wasm 的文本表示，本身就是最好的反汇编输出格式。一个最小的校验模块：

```wat
(module
  (func $mix (param $p i32) (result i32)
    local.get $p
    i32.const 31
    i32.mul
    i32.const 11290
    i32.add)
  (func $check (export "check") (param $in i32) (result i32)
    local.get $in
    call $mix
    i32.const 4008986
    i32.eq)
  (func (export "greet") (result i32)
    i32.const 2026)
)
```

```bash
wat2wasm mini.wat -o mini.wasm
ls -l mini.wasm
xxd -l 16 mini.wasm
file mini.wasm
```

输出：

```
-rw-r--r-- 1 hua hua 80 Oct 22 12:33 mini.wasm
00000000: 0061 736d 0100 0000 010a 0260 017f 017f  .asm.......`....
mini.wasm: WebAssembly (wasm) binary module version 0x1 (MVP)
```

魔数 `00 61 73 6d`（`\0asm`）后跟 4 字节版本号 `01 00 00 00`，80 字节的小模块。栈式字节码：`local.get` 压栈、`i32.mul` 弹两个压一个，读法与 3.1 节的 JVM 字节码同款。

### 8.2 wasm2wat 反汇编：名字去哪了

```bash
wasm2wat mini.wasm
```

输出：

```wat
(module
  (type (;0;) (func (param i32) (result i32)))
  (type (;1;) (func (result i32)))
  (func (;0;) (type 0) (param i32) (result i32)
    local.get 0
    i32.const 31
    i32.mul
    i32.const 11290
    i32.add)
  (func (;1;) (type 0) (param i32) (result i32)
    local.get 0
    call 0
    i32.const 4008986
    i32.eq)
  (func (;2;) (type 1) (result i32)
    i32.const 2026)
  (export "check" (func 1))
  (export "greet" (func 2)))
```

逻辑完整可读：`check(in) = (in*31 + 11290) == 4008986`。但 `$mix`、`$check` 这些名字没了，只剩编号——==wat 里的名字默认不存在于二进制里==，它们只活在 `--debug-names` 写入的 name section（一个可选的自定义段）里。编译时加上它再反一遍：

```bash
wat2wasm --debug-names mini.wat -o mini_name.wasm
wasm2wat mini_name.wasm | head -16
```

输出：

```wat
(module
  (type (;0;) (func (param i32) (result i32)))
  (type (;1;) (func (result i32)))
  (func $mix (type 0) (param $p i32) (result i32)
    local.get $p
    i32.const 31
    i32.mul
    i32.const 11290
    i32.add)
  (func $check (type 0) (param $in i32) (result i32)
    local.get $in
    call $mix
    i32.const 4008986
    i32.eq)
  (func (;2;) (type 1) (result i32)
    i32.const 2026)
  (export "check" (func $check))
```

带名字的产物反汇编回 `$mix`、`$check`。实战中拿到 wasm 先 `wasm2wat` 试；名字全变编号时接受现状，用导出名（`export "check"` 这类，必然保留）锚定关键函数。wabt 家族的 `wasm-decompile` 能再进一步输出类 C 伪码，`wasm-objdump -x -d` 则是 wabt 版的 objdump，用法与本章其他平台一致。

> [!note] wasm 与 VM 题的关系
> wasm 由宿主的解释器/编译器执行，逆向读的是字节码而非机器码——阅读姿态与 [[R12-虚拟机保护VM逆向|R12]] 的 VM 题相近（先摸清字节码语义再读逻辑），但 wasm 的指令集是公开标准、wabt 全套工具现成，难度远低于自造 VM。浏览器运行的 wasm 题常见变形是把关键逻辑藏在 JS 侧，wasm 只是算一轮哈希，JS 与 wasm 要一起读。

## 9. macOS 与 iOS：Mach-O

Mach-O 是 macOS/iOS 的可执行格式，CTF 里出镜率低于 ELF/PE，识别特征值得记住——`file` 不在（或识别库旧）时靠魔数。macOS 与 iOS 样本不在 Linux 实验环境里，本节只讲特征与工具链，不配输出。

文件头 4 字节的魔数（xxd 显示的是文件字节序）：

| 文件头字节 | 对应值 | 含义 |
| ---- | ---- | ---- |
| `CE FA ED FE` | 0xFEEDFACE | 32 位 Mach-O |
| `CF FA ED FE` | 0xFEEDFACF | 64 位 Mach-O（现代 macOS/iOS 主流） |
| `CA FE BA BE` | 0xCAFEBABE | fat/universal 二进制（多架构打包） |

`FEEDFACE`/`FEEDFACF` 是格式定义值，小端机器写进文件就成了"倒序"的 `CE FA ED FE`/`CF FA ED FE`；`file` 认识全部变体。

> [!warning] 0xCAFEBABE 撞魔数
> Mach-O 的 fat 二进制与 Java class 文件的魔数同为 `CA FE BA BE`——[[03-计算机组成与数据表示|通用基础 03 章]]的魔数表里它登记在 Java class 名下。区分看后续字节：Java class 紧跟次/主版本号（`00 00 00 34` 一类小数值），Mach-O fat 头紧跟架构数与每架构的 CPU 类型字段。只凭前 4 字节下结论会认错平台。

工具链：

- **otool**（macOS 自带，装 Xcode Command Line Tools 即有）：Mach-O 版的 readelf/objdump。常用三条：`otool -hv 文件` 看头部（架构、文件类型、标志）、`otool -L 文件` 列动态依赖（ldd 的对应物）、`otool -tV 文件` 反汇编文本段。
- **IDA/Ghidra**：都内置 Mach-O loader，Linux/Windows 上直接分析 Mach-O 文件，不需要 macOS；是多平台分析的主力工具（[[R05-静态分析工具链IDA与Ghidra|R05]]）。
- **iOS 额外一步**：App Store 分发的 IPA 经过 FairPlay 加密，二进制主段是密文，要先在越狱设备上砸壳（dump 解密后的内存镜像）再分析。[[R01-逆向工程与CTF竞赛生态导论#3. 常见附件类型与识别|R01 第 3 节]]的附件表里"iOS 题还需先砸壳"指的就是这一步；练习平台给的 iOS 样本通常已砸好。

## 10. 嵌入式与 IoT：固件镜像

路由器、摄像头、开发板的固件是"文件套文件"的容器：一个 `.bin` 里可能同时塞着内核、只读文件系统、配置数据。[[R01-逆向工程与CTF竞赛生态导论#3. 常见附件类型与识别|R01 第 3 节]]说过它 `file` 只报 `data`——专用工具是 binwalk（安装：`sudo apt install binwalk`），按签名库在文件里扫内嵌数据的魔数与位置。

### 10.1 自造固件：ELF + gzip + zip 拼接

先以出题人的方式造一个固件镜像——以 6.1 节的 cppdemo ELF 当"固件里的主程序"，后面拼一段 gzip 压的 flag 和一个 zip 配置包：

```bash
cp cppdemo base.elf
cp base.elf firmware.bin
gzip -9 -c flag.txt >> firmware.bin
zip -q fwcfg.zip config.txt
cat fwcfg.zip >> firmware.bin
ls -l base.elf firmware.bin
```

输出：

```
-rwxr-xr-x 1 hua hua 36752 Oct 22 12:43 base.elf
-rw-r--r-- 1 hua hua 36996 Oct 22 12:43 firmware.bin
```

ELF 尾上直接拼数据，完全合法——load 只看程序头，尾部多余字节它不管（[[R04-可执行文件格式ELF与PE|R04]]的装载视图不含文件尾）。看看拼缝处（36752 = 0x8F90 起是 gzip）：

```bash
xxd -s 36752 -l 32 firmware.bin
```

输出：

```
00008f90: 1f8b 0808 8f94 d96a 0203 666c 6167 2e74  .......j..flag.t
00008fa0: 7874 004b cb49 4caf 4e33 2cca 2d37 2932  xt.K.IL.N3,.-7)2
```

`1f 8b` 是 gzip 魔数，后面跟着原始文件名 `flag.txt`。

### 10.2 binwalk 扫描与提取

```bash
binwalk firmware.bin
```

输出：

```

DECIMAL       HEXADECIMAL     DESCRIPTION
--------------------------------------------------------------------------------
0             0x0             ELF, 64-bit LSB executable, AMD x86-64, version 1 (SYSV)
16656         0x4110          Unix path: /usr/include/c++/15/bits/stl_vector.h
36752         0x8F90          gzip compressed data, maximum compression, has original file name: "flag.txt", from Unix, last modified: 2026-10-22 04:43:59
36806         0x8FC6          Zip archive data, at least v1.0 to extract, compressed size: 20, uncompressed size: 20, name: config.txt
36974         0x906E          End of Zip archive, footer length: 22
```

三段内容的位置都在输出里，连 C++ 模板头文件路径这种"杂音签名"都扫了出来。自动提取一步完成：

```bash
binwalk -e firmware.bin
```

输出：

```

DECIMAL       HEXADECIMAL     DESCRIPTION
--------------------------------------------------------------------------------
36752         0x8F90          gzip compressed data, maximum compression, has original file name: "flag.txt", from Unix, last modified: 2026-10-22 04:43:59
36806         0x8FC6          Zip archive data, at least v1.0 to extract, compressed size: 20, uncompressed size: 20, name: config.txt


WARNING: One or more files failed to extract: either no utility was found or it's unimplemented
```

```bash
find _firmware.bin.extracted -type f
cat _firmware.bin.extracted/flag.txt
find _firmware.bin.extracted -name "*.zip" -exec unzip -o -q {} -d _firmware.bin.extracted \;
cat _firmware.bin.extracted/config.txt
```

输出：

```
_firmware.bin.extracted/config.txt
_firmware.bin.extracted/8FC6.zip
_firmware.bin.extracted/flag.txt
flag{f1rmw4r3_3xtr4ct3d}
cfg_version=2026.10
```

`-e` 把识别出的数据块逐个 dd 出来再交给对应解压工具，产物在 `_firmware.bin.extracted/`。那条 WARNING 不是失败：==ELF、"Unix path" 这类签名只报位置、没有（也不需要）提取工具，gzip 与 zip 都完整提出了==。

手工流程与 `-e` 等价，签名特殊或工具没配时用它：扫描拿到偏移 36752，`dd` 跳到偏移处截取，再管道给 gunzip：

```bash
dd if=firmware.bin bs=1 skip=36752 2>/dev/null | gunzip
```

输出：

```
gzip: stdin: decompression OK, trailing garbage ignored
flag{f1rmw4r3_3xtr4ct3d}
```

第一行是 gunzip 的提示：`dd` 从偏移处截到了文件尾，把后面的 zip 段也一并喂了进去，gunzip 解完自己的数据后忽略尾部（trailing garbage ignored），flag 完整解出。真实固件题的后续：提取出的多是 squashfs 文件系统镜像，先解出文件系统，再在里面找目标二进制按本章对应平台分析——容器剥完，剩下的仍是前面各节处理过的程序类型。

> [!info]- squashfs、jffs2 与硬件接口
> **squashfs**：只读压缩文件系统，固件根分区最常见的形式，魔数是小端 `hsqs`（68 73 71 73），用 unsquashfs 提取；厂商常用非标准压缩选项，binwalk 内置的 sasquatch 工具专治这类变体。**jffs2**：闪存日志文件系统，常见于可写分区，镜像里是一串节点（节点魔数 0x1985），提取工具支持不如 squashfs 成熟，必要时按节点手工拼。**UART/JTAG**：两个硬件调试接口——UART 串口接上设备能看控制台输出、常能拿到 shell；JTAG 接上能在线调试甚至直读 flash。固件题一般直接给 .bin 镜像，不涉及这两者；真到了设备旁边，那是硬件方向的另一套知识。

## 11. ARM 与 MIPS：换一套指令集

嵌入式设备与手机几乎不用 x86：路由器是 MIPS 或 ARM，手机是 AArch64。这类题的 ELF 格式没变（[[R04-可执行文件格式ELF与PE|R04]]的知识原样适用），变的是指令集——反汇编要交叉工具，运行要模拟器。

### 11.1 交叉编译、qemu 运行、反汇编：三件套

工具：交叉编译器 `sudo apt install gcc-aarch64-linux-gnu`（装在主机上，产物跑在别处，故称"交叉"），模拟器 qemu-user（用户态模拟，跑单个外来架构的 ELF，与跑整个操作系统的 qemu-system 不同）。

示例程序：

```c
#include <stdio.h>

int main(void) {
    int v = 0;
    for (int i = 0; i < 5; i++) {
        v = v * 31 + i;
    }
    printf("v=%d\n", v);
    return 0;
}
```

```bash
aarch64-linux-gnu-gcc armhello.c -o hello_arm
file hello_arm
```

输出：

```
hello_arm: ELF 64-bit LSB pie executable, ARM aarch64, version 1 (SYSV), dynamically linked, interpreter /lib/ld-linux-aarch64.so.1, for GNU/Linux 3.7.0, not stripped
```

还是 ELF，Machine 字段换成 `ARM aarch64`，动态链接器的路径也是 aarch64 专属的（`ld-linux-aarch64.so.1`）。x86 主机直接运行会报 exec format error，交给 qemu：

```bash
qemu-aarch64 -L /usr/aarch64-linux-gnu ./hello_arm
```

输出：

```
v=31810
```

`-L` 告诉 qemu 去哪找目标架构的动态库（交叉编译器包把 aarch64 的 libc 装在了 `/usr/aarch64-linux-gnu` 下）。静态编译则免掉这一步：`aarch64-linux-gnu-gcc -static armhello.c -o hello_static`，`qemu-aarch64 ./hello_static` 直接跑。反汇编用交叉版 objdump：

```bash
aarch64-linux-gnu-objdump -d hello_arm | sed -n '/<main>:/,/^$/p'
```

输出：

```
00000000000007a8 <main>:
 7a8:	a9be7bfd 	stp	x29, x30, [sp, #-32]!
 7ac:	910003fd 	mov	x29, sp
 7b0:	b9001bff 	str	wzr, [sp, #24]
 7b4:	b9001fff 	str	wzr, [sp, #28]
 7b8:	1400000b 	b	7e4 <main+0x3c>
 7bc:	b9401be1 	ldr	w1, [sp, #24]
 7c0:	2a0103e0 	mov	w0, w1
 7c4:	531b6800 	lsl	w0, w0, #5
 7c8:	4b010000 	sub	w0, w0, w1
 7cc:	b9401fe1 	ldr	w1, [sp, #28]

```

（AArch64 Linux，参数与返回值约定同 x86-64 思路：参数 x0–x7，返回值 x0；小写 `w` 开头是同一寄存器的低 32 位。）

对照 [[R03-x86与x64汇编精要复习|R03]] 的 x86 代码形状，五处不同一眼可见：

| AArch64 形状 | 对应的 x86-64 概念 |
| ---- | ---- |
| `stp`/`ldp` 成对存取两个寄存器，没有 push/pop | x86 的 `push rbp` + `mov rsp,rbp` 序言 |
| `x29`（帧指针）、`x30`（返回地址 LR）有专用寄存器 | x86 返回地址压栈，LR 无对应物 |
| `str wzr, [sp,#24]`——wzr 是恒零寄存器 | x86 用 `xor eax,eax` 或立即数 0 |
| `lsl w0,w0,#5` + `sub w0,w0,w1`——乘 31 被编译成移位减法 | x86 同样优化，但用 `imul` 的场合更多 |
| `adrp x0,…` + `add x0,x0,#0x830` 两步构造地址 | x86-64 一条 `lea rax,[rip+…]` |
| `ret` 跳的是 x30（LR） | x86 `ret` 弹栈 |

IDA/Ghidra 都原生支持 AArch64 与 ARM32，识别为交叉架构后载入即可，分析流程与 [[R05-静态分析工具链IDA与Ghidra|R05]] 完全一致。

> [!info]- ARM32 与 MIPS 的风格差异
> **ARM32**（`file` 报 `ARM, EABI5`）：寄存器 r0–r15，r13 即 sp、r14 即 LR、r15 即 PC；有真 push/pop 指令；同一程序可混排 ARM（4 字节定长）与 Thumb（2 字节定长）两种模式，反汇编错位时先查当前模式。**MIPS**（`file` 报 `MIPS`）：4 字节定长；临时寄存器 `$t0`–`$t9`、参数 `$a0`–`$a3`、返回值 `$v0`–`$v1`；没有标志寄存器，比较与跳结合在一条指令里（`beq $t0,$t1,label`）；有分支延迟槽——分支指令的下一条总会执行，读控制流时不要跳过它；取全局数据常经 `$gp` 寄存器相对寻址。两种架构 IDA/Ghidra 与交叉 objdump（gcc-mips* 交叉包或 binutils 多目标版）都支持。

## 12. 平台任务对照

每平台一行，给出典型题面与入手路线。前三步（file/strings/结构）是所有行的公共起点，表里只写其后的分岔：

| 平台 | 附件形态 | 入手路线 |
| ---- | ---- | ---- |
| Python（打包） | exe/elf，strings 见 `pyi-` | pyi-archive_viewer 或 pyinstxtractor 提取 → 补 pyc 头 → dis/pycdc 还原 check（[[#2. Python：PyInstaller 与 pyc\|第 2 节]]） |
| Python（裸 pyc） | `.pyc`，`file` 报 data | 看魔数定版本 → dis 反汇编，3.8 及以下可直接反编译（[[#2.2 dis：反汇编字节码\|2.2]]） |
| Java | jar 或 .class，`CA FE BA BE` | jadx 出 Java 源码 → 读校验 → 逆算法；失真退 smali（[[#3. Java 与 Android：class、jar 与 APK\|第 3 节]]） |
| Android | APK，zip 内 classes.dex | jadx-gui 搜字符串定位类；`native` 方法进 `lib/<abi>/` 分析 .so（[[#3.5 APK 里的 native 层：从 native 声明到 .so\|3.5]]）；动态取值用 Frida hook（[[#3.4 smali 最小速览\|3.4]]、[[#3.6 Frida：native 层 Hook（Interceptor.attach）\|3.6]]） |
| Go | `file` 报 Go BuildID | 定位 `main.main`（符号或 GoReSym）→ 读哈希 → 逆推；strip 亦然（[[#4. Go：runtime 符号群与 pclntab\|第 4 节]]） |
| Rust | panic 串带 `src/*.rs`，`_ZN` 符号 | panic 位置定入口 → c++filt/rustfilt 认函数 → 读算法（[[#5. Rust：panic 串与 _ZN 名字\|第 5 节]]） |
| C++ | `_Z` 符号、`.data.rel.ro` | c++filt 认函数；虚调用查 vtable 槽位与 RTTI（[[#6. C++：名字粉碎、vtable 与 RTTI\|第 6 节]]） |
| .NET | PE + 数据目录 14 非 0 | dnSpy/ILSpy 直接读 C#，复杂度等同读源码（[[#7. .NET：PE 里的托管字节码\|第 7 节]]） |
| WebAssembly | `00 61 73 6D` 魔数 | wasm2wat 读逻辑，export 名锚定函数（[[#8. WebAssembly：wat 与 wasm\|第 8 节]]） |
| Mach-O | `CF FA ED FE` / fat 头 | IDA/Ghidra 载入；iOS 先砸壳（[[#9. macOS 与 iOS：Mach-O\|第 9 节]]） |
| 固件 | `file` 报 data | binwalk -e 剥容器 → 解文件系统 → 按内层平台分析（[[#10. 嵌入式与 IoT：固件镜像\|第 10 节]]） |
| ARM/MIPS | ELF，Machine 非 x86 | 交叉 objdump 反汇编 → qemu-user 运行验证；IDA/Ghidra 同样通吃（[[#11. ARM 与 MIPS：换一套指令集\|第 11 节]]） |
| 综合 | 多平台嵌套（如固件里的 Go 程序） | 由外向内逐层剥：binwalk → 文件系统 → 目标文件 → 对应平台路线 |
| 算法卡住 | 已定位 check 但变换复杂 | 常数识别归算法（[[R07-编码与算法识别还原\|R07]]）；约束式校验交给自动化求解（[[R14-自动化分析angr与z3\|R14]]） |

选题时两条经验：第一，多平台题的难度常在"认出平台"这一步，识别练熟后题目本身往往是 [[R08-CrackMe经典题型|R08]] 级别的校验逻辑；第二，字节码平台（Python/Java/.NET/wasm）的反编译产物接近源码，分析成本低于机器码平台，比赛里适合当快速拿分点。

## 13. 常见问题

| 现象 | 原因与解决 |
| ---- | ---- |
| PyInstaller 产物拿 IDA 打开，全是解释器代码 | 平台认错了：逻辑在归档里的 pyc。strings 搜 `pyi-` 确认，按 [[#2.4 提取：从 exe 到 pyc\|2.4]] 提取后再分析 |
| pycdc 反编译报错或输出残缺 | 工具不支持该字节码版本（3.9+ 普遍如此）。退回 dis 反汇编（[[#2.2 dis：反汇编字节码\|2.2]]） |
| 提取出的 pyc 直接运行报 `bad magic number` | 头缺失或版本不匹配。补本机 Python 的 16 字节头；版本不同时找对应版本的解释器 |
| `python3 -m dis xxx.pyc` 报 null bytes 错误 | dis 的命令行入口只接受源码文件；pyc 走 `marshal.loads` + `dis.dis`（[[#2.2 dis：反汇编字节码\|2.2]]） |
| jadx 反编译某方法失败，只有注释 | 混淆或 jadx 支持不足。看该方法的 smali 视图（jadx-gui）或换 apktool 解包后读 smali |
| jadx 里方法没有方法体，声明带 `native` | 实现在 `lib/<abi>/*.so`：找 `System.loadLibrary` 的库名，解包取出 .so 按 [[#3.5 APK 里的 native 层：从 native 声明到 .so\|3.5]] 分析 |
| .so 里搜不到 `Java_` 开头的函数 | 方法是 RegisterNatives 动态注册的：从 JNI_OnLoad 顺 RegisterNatives 参数找注册表；strip 过的样本用 strings 搜类名/方法名/签名（[[#3.5 APK 里的 native 层：从 native 声明到 .so\|3.5]]） |
| Go 二进制 `nm` 报 no symbols | `-ldflags "-s -w"` 或 strip 过。函数名在 pclntab 里，GoReSym 恢复（[[#4.3 strip 之后：pclntab 还在\|4.3]]） |
| Go 符号表里找不到自己写的函数 | 被编译器内联了。分析自建程序时加 `//go:noinline`，分析题目时去调用点附近找内联后的代码 |
| Rust 符号 c++filt 还原后带 hash 尾巴 | legacy 粉碎的正常形态，主体可读即可用；`_R` 开头的 v0 符号换 rustfilt |
| 反汇编里 `call rdx`，看不出调了谁 | 虚调用。从对象取 vptr，按偏移查 vtable 槽位（[[#6.2 vtable：多态在内存里的形状\|6.2]]） |
| vtable 区域 `objdump -s` 读出来全是零 | PIE 产物的重定位延迟到装载时。看 `readelf -r` 或直接在 IDA/Ghidra 里读（6.2 的 warning） |
| .NET 程序 IDA 打开只有一小段代码 | 那是原生启动桩，主体是 CIL。换 dnSpy/ILSpy（第 7 节） |
| wasm2wat 输出的函数全是编号 | 名字不在二进制里，除非编译带 name section。用 export 名锚定函数（[[#8.2 wasm2wat 反汇编：名字去哪了\|8.2]]） |
| binwalk -e 报 WARNING，但产物完整 | 个别签名（ELF、"Unix path" 类）只报位置、无提取工具，属正常；核对关键数据是否提出（[[#10.2 binwalk 扫描与提取\|10.2]]） |
| `qemu-aarch64 ./程序` 报找不到文件 | 动态链接程序缺目标架构的解释器与库。加 `-L /usr/aarch64-linux-gnu`，或静态编译后运行（[[#11.1 交叉编译、qemu 运行、反汇编：三件套\|11.1]]） |
| Mach-O 魔数看着像反的 | 文件字节序显示 `CE FA ED FE`，对应定义值 0xFEEDFACE，正常（第 9 节） |
