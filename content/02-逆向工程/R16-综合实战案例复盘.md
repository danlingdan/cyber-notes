> **本章目标**：把散在前面各章的解题模式收拢成一张"特征 → 模式 → 第一动作"的对照表，并为四个不依赖现成工具的特殊模式（LD_PRELOAD oracle、fork 与管道校验、时间侧信道、INT3 自毁加 coredump 取证）各建立一个从靶子到解法的完整例子；形成读别人题解、沉淀复盘产出、使用 AI 辅助的固定流程。

## 1. 为什么要建模式库

前面的章节按"知识"组织：一章讲一类工具、一类对抗或一类算法。赛题不会报告自己属于哪一章——题目只给你一个二进制和一组现象。把现象和动作连起来的那层东西，本章称为**题型模式**：

- **知识点**回答"LD_PRELOAD 是什么"——定义、原理、语法；
- **模式**回答"看到这些现象，下一步做什么"——特征、原理、解法、出处、例题。

两个概念是包含关系：模式由若干知识点拼成。新人刷题到一定数量后，提升的关键不再是"又学了一个知识点"，而是==把重复出现的现象归纳成模式，再让模式可以被特征检索到==；训练目标是把"看到特征 → 想到模式 → 套解法"变成不假思索的第一反应。判一道题"做透了"的标准随之变化：不只看 flag 拿没拿到，还看能不能回答三个问题——这题的特征是什么、属于哪个模式、解法第一步是什么。回答得出，这道题就变成了模式库里的一个例题编号；回答不出，做十道同型题也只是十次互相独立的重复。

模式库的最小单元是**条目**，五个字段固定不变：

| 字段 | 填什么 | 反例 |
| ---- | ---- | ---- |
| 特征 | 反汇编、伪代码、程序行为里你实际看到的信号 | 写成"这道题是 XX 比赛"（比赛不是特征） |
| 原理 | 模式为什么成立，两三句说清 | 只写操作步骤不讲原因（换个变体就不会了） |
| 解法 | 从确认特征到拿答案的第一动作与主线步骤 | 把所有工具全列一遍（那不是解法是目录） |
| 出处 | 本库的章节双链，方便回读 | 只写外链（与自己的知识体系断开） |
| 例题 | 踩过这个模式的题，越多条目越可靠 | 空着（条目停在"听说过"的层面） |

本章第 2–5 节是四个模式的完整条目生产过程：每个模式先造一个靶子，再从零走一遍解法——==条目里的每一句话都要能落回到一个跑得通的例子上==。四个模式共同的选择标准：它们不依赖某个现成工具的一键功能，核心是"换一个角度看程序在做什么"，这也正是它们在赛题里频繁出现、又最容易被新手漏掉的原因。

## 2. 模式一：LD_PRELOAD 构造 oracle

### 2.1 原理与两种用法

动态链接的程序调用 libc 函数要经过 PLT；符号解析时，`LD_PRELOAD` 环境变量指定的共享库优先级最高，==同名符号会把 libc 里的真函数盖掉==。[[R10-反调试与反分析对抗#8.1 ptrace 自占：一个人只能被跟踪一次|R10 8.1]] 用这个机制写过"恒返回 0 的 ptrace"，让 ptrace 自占检测失效——那是第一类用法：**让检测失效**。本章把同一机制升级出两种更强的用法：

1. **改数据流**：覆盖 `open`、`read` 一类 I/O 函数，把校验程序本来读不到的内容喂给它——比如把"授权文件"重定向到你自己的文件；
2. **泄露比较**：覆盖 `strcmp`、`memcmp` 一类比较函数，把每次调用的两个操作数原样打印出来。校验无论多复杂，最后总要和你的输入比一次——==比较函数是正确答案的必经之地==，盖住它，就能把比较双方都打印出来。社区把这类"问一次、打印一次"的钩子叫 **oracle**（应答器）。

### 2.2 靶子

一个读授权文件做校验的程序。密钥由 seed 数组异或 0x5A 组装，运行时才成形：

```c
/* oracle.c —— LD_PRELOAD 靶子：open 读授权文件，strcmp 与运行时组装的密钥比较 */
#include <stdio.h>
#include <string.h>
#include <fcntl.h>
#include <unistd.h>

int main(void)
{
    char buf[32] = {0}, key[17];
    unsigned char seed[16] = {
        0x3C, 0x36, 0x3B, 0x3D, 0x21, 0x6A, 0x28, 0x6E,
        0x39, 0x36, 0x69, 0x05, 0x2A, 0x2D, 0x34, 0x27
    };
    for (int i = 0; i < 16; i++)          /* 密钥运行时组装，磁盘上没有明文 */
        key[i] = (char)(seed[i] ^ 0x5A);
    key[16] = '\0';

    int fd = open("license.dat", O_RDONLY);
    if (fd < 0) {
        puts("no license file");
        return 1;
    }
    read(fd, buf, 31);
    close(fd);
    buf[strcspn(buf, "\n")] = '\0';

    if (strcmp(buf, key) == 0)
        puts("Correct! license accepted");
    else
        puts("wrong license");
    return 0;
}
```

按基线编译，strings 扫一遍——只有提示语，没有答案：

```bash
gcc -O0 -fno-pie -no-pie oracle.c -o oracle
strings -t x oracle | grep -E '^ +2[0-9a-f]+ '
```

输出：

```
   2004 license.dat
   2010 no license file
   2022 Correct! license accepted
   203c wrong license
```

不放授权文件直接运行，程序在 `open` 处就退出：

```bash
./oracle
```

输出：

```
no license file
```

逆向这条常规路也能走：读 seed、异或 0x5A、拼出答案（[[R06-动态调试GDB与x64dbg#10. 实战：动态 dump 出密钥|R6 第 10 节]]的静态路）。本节的目标是展示另一条路——==不读校验逻辑，直接在库函数层动手==，它在你暂时读不懂伪代码、或校验藏在几十层调用深处时更快。

### 2.3 钩子库与三步走

一个共享库同时覆盖 `open` 和 `strcmp`：

```c
/* hook.c —— LD_PRELOAD 库：覆盖 open（重定向授权文件）与 strcmp（打印两个操作数） */
#define _GNU_SOURCE
#include <stdio.h>
#include <fcntl.h>
#include <stdarg.h>

/* 钩子内部不再调用被自己覆盖的 strcmp，逐字节比较自己实现 */
static int same(const char *a, const char *b)
{
    int i = 0;
    while (a[i] && a[i] == b[i]) i++;
    return a[i] == b[i];
}

int open(const char *path, int flags, ...)
{
    if (same(path, "license.dat"))
        path = "/tmp/mylic";
    return openat(AT_FDCWD, path, flags);
}

int strcmp(const char *a, const char *b)
{
    fprintf(stderr, "[oracle] strcmp(\"%s\", \"%s\")\n", a, b);
    int i = 0;
    while (a[i] && a[i] == b[i]) i++;
    return (unsigned char)a[i] - (unsigned char)b[i];
}
```

`open` 的钩子把文件名 `license.dat` 换成 `/tmp/mylic`，其余路径原样放行，转发用 `openat`——它是另一个符号，不会再落回钩子自己。`strcmp` 的钩子先把两个参数打到 stderr，再做一次自实现的逐字节比较，返回值语义与真 strcmp 一致。编译成共享库：

```bash
gcc -shared -fPIC hook.c -o hook.so
```

**第一步：喂假内容，看比较发生**。往 `/tmp/mylic` 放一个明显错误的串，挂上钩子运行：

```bash
echo AAAA > /tmp/mylic
LD_PRELOAD=./hook.so ./oracle
```

输出：

```
[oracle] strcmp("AAAA", "flag{0r4cl3_pwn}")
wrong license
```

程序顺利越过"文件不存在"这一关（`open` 钩子生效），停在比较上，而==stderr 上并排出现了输入和正确答案==——密钥 `flag{0r4cl3_pwn}` 从未出现在磁盘上的任何文件里，它只存在于这次调用的第二个参数中。

**第二步：喂真密钥，走通校验**：

```bash
echo 'flag{0r4cl3_pwn}' > /tmp/mylic
LD_PRELOAD=./hook.so ./oracle
```

输出：

```
[oracle] strcmp("flag{0r4cl3_pwn}", "flag{0r4cl3_pwn}")
Correct! license accepted
```

> [!warning] 钩子内部别再调被覆盖的函数
> 如果 `open` 的钩子里写了 `strcmp(path, "license.dat")`，这一次 `strcmp` 解析到的仍是钩子自己——先是多打一行噪声，若钩子内部逻辑依赖被覆盖函数的返回值，就可能递归到栈耗尽。两条通用写法：钩子内部需要比较、拼接这类基础操作时自己实现（本例的 `same`）；需要调用真函数时用 `dlsym(RTLD_NEXT, "函数名")` 拿到下一个定义再转发（`open` 钩子改用 `openat` 是同一思想的偷懒版——换一个没被覆盖的符号）。

> [!info]- dlsym(RTLD_NEXT) 的标准写法
> `RTLD_NEXT` 告诉动态链接器"从当前库之后开始找这个符号"，拿到的就是被盖住的真函数：
>
> ```c
> #define _GNU_SOURCE
> #include <dlfcn.h>
>
> static int (*real_strcmp)(const char *, const char *);
>
> int strcmp(const char *a, const char *b)
> {
>     if (!real_strcmp)
>         real_strcmp = dlsym(RTLD_NEXT, "strcmp");
>     fprintf(stderr, "[oracle] strcmp(\"%s\", \"%s\")\n", a, b);
>     return real_strcmp(a, b);
> }
> ```
>
> 编译命令不变。写转发型钩子（改参数后调真函数、按真返回值决定行为）时用它；纯替换型钩子（本节的 strcmp）自己实现更简单。

### 2.4 识别特征

两个信号说明一次成功或一次疑似的 LD_PRELOAD 介入：

**一，加载列表多一行**。`ldd` 内部靠 `LD_TRACE_LOADED_OBJECTS=1` 让动态链接器打印加载映射，普通运行与挂钩运行各看一次：

```bash
LD_TRACE_LOADED_OBJECTS=1 ./oracle
LD_PRELOAD=./hook.so LD_TRACE_LOADED_OBJECTS=1 ./oracle 2>/dev/null
```

输出：

```
	linux-vdso.so.1 (0x000077d90960a000)
	libc.so.6 => /usr/lib/x86_64-linux-gnu/libc.so.6 (0x000077d909200000)
	/lib64/ld-linux-x86-64.so.2 (0x000077d90960c000)
```

```
	linux-vdso.so.1 (0x000077d90960a000)
	./hook.so (0x00007de3d1769000)
	libc.so.6 => /usr/lib/x86_64-linux-gnu/libc.so.6 (0x000077d909200000)
	/lib64/ld-linux-x86-64.so.2 (0x000077d90960c000)
```

第二份列表多出的 `./hook.so` 一行，就是钩子库被映射进进程的直接证据。

**二，行为对环境变量敏感**。同一个二进制，设与不设 `LD_PRELOAD` 输出完全不同——`no license file` 变成一行 oracle 输出加 `wrong license`。赛题里读到一篇题解写"设上某个环境变量再运行"，识别的就是这个模式。

> [!warning] strcmp 钩子是全进程生效的
> 覆盖 `strcmp` 影响的是进程里**所有** strcmp 调用，不止校验那一次。直接 `LD_PRELOAD=./hook.so ldd ./oracle` 会看到输出被 `[oracle]` 行淹没：`ldd` 本身是个 shell 脚本，脚本自己的 strcmp 也被钩住了，而且 ldd 会把被跟踪进程的 stderr 合并进自己的 stdout，钩子的输出跟着进了管道。想看干净的加载列表，用上面 `LD_TRACE_LOADED_OBJECTS=1` 直接跑目标的形式。这个"淹没"现象反过来也是鉴定手段——输出里出现你的钩子标记，说明钩子确实在每一个新进程里生效。

> [!info]- 适用边界与 LD_PRELOAD 的另一面
> 静态链接的程序、绕过 libc 直接发系统调用的程序都不经过 PLT，`LD_PRELOAD` 无效，只能走 patch（[[R10-反调试与反分析对抗#8.1 ptrace 自占：一个人只能被跟踪一次|R10 8.1]] 的边界提示同样适用）；另有一类程序会读 `getenv("LD_PRELOAD")` 反过来检测钩子，那属于反调试，按 [[R10-反调试与反分析对抗|R10]] 的三板斧处理。防御视角也是同一个开关：安全加固会忽略特权程序的 `LD_PRELOAD`（setuid 程序上它不生效），运维用它给任意程序注入统计库——同一个机制，攻防两侧各用一半。

> [!info]- 模式库条目：LD_PRELOAD oracle
>
> | 字段 | 内容 |
> | ---- | ---- |
> | 特征 | 导入表里有 open/read/strcmp 一类库函数参与校验；答案运行时才比较；strings 扫不到 |
> | 原理 | `LD_PRELOAD` 指定的库在符号解析时优先级最高，同名符号盖住 libc |
> | 解法 | 覆盖 open/read 喂假数据；覆盖 strcmp/memcmp 打印比较双方；转发用 openat 或 `dlsym(RTLD_NEXT)` |
> | 出处 | 本节；机制与边界见 [[R10-反调试与反分析对抗#8.1 ptrace 自占：一个人只能被跟踪一次\|R10 8.1]] |
> | 例题 | 本节 oracle；远端服务类题目无法控制被测进程的环境时，等价思路见第 4 节 |

## 3. 模式二：fork 与管道校验：跟进子进程

### 3.1 靶子与难点

先补两个系统调用的最小背景：`pipe(pfd)` 造出一对文件描述符，向 `pfd[1]` 写入的字节按顺序从 `pfd[0]` 读出；`fork()` 把当前进程复制一份，在子进程里返回 0、在父进程里返回子进程的 PID。fork 之后父子各持同一对管道描述符的副本，管道就成了进程间传数据的最简通道。

靶子把校验整体搬进子进程：父进程读完输入后只负责经管道把输入送过去；子进程收下输入，在**自己**的栈上组装密钥、完成比较、打印结果：

```c
/* forkcheck.c —— 校验在子进程完成：输入经管道交给子进程，密钥也只在子进程内存里成形 */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void)
{
    char input[32];
    int pfd[2];

    if (pipe(pfd) != 0)
        return 1;
    printf("key: ");
    fflush(stdout);
    if (scanf("%31s", input) != 1)
        return 1;

    pid_t pid = fork();
    if (pid == 0) {                        /* 子进程：收输入、组装密钥、比较、报结果 */
        close(pfd[1]);
        char buf[32] = {0}, key[11];
        unsigned char seed[10] = {
            0x21, 0x2A, 0x73, 0x2E, 0x26, 0x1D, 0x32, 0x30, 0x72, 0x21
        };
        read(pfd[0], buf, sizeof buf - 1);
        close(pfd[0]);
        for (int i = 0; i < 10; i++)       /* 密钥只在子进程的栈上组装 */
            key[i] = (char)(seed[i] ^ 0x42);
        key[10] = '\0';
        if (strcmp(buf, key) == 0)
            printf("Correct! flag{%s}\n", key);
        else
            puts("wrong key");
        exit(0);
    }

    close(pfd[0]);                         /* 父进程：只搬运输入，随后等待子进程 */
    write(pfd[1], input, strlen(input) + 1);
    close(pfd[1]);
    waitpid(pid, NULL, 0);
    return 0;
}
```

先正常跑一遍（in.txt 内容是一行故意错误的输入 AAAA）：

```bash
gcc -O0 -fno-pie -no-pie forkcheck.c -o forkcheck
./forkcheck < in.txt
```

输出：

```
key: wrong key
```

难点在调试侧。[[R06-动态调试GDB与x64dbg|R6]] 的全部断点操作都建立在一个默认设置上：==GDB 默认只跟父进程，fork 出的子进程被放手不管==。而密钥组装和 strcmp 都在子进程的地址空间里——父进程从头到尾没碰过密钥。按 R6 10.3 的老经验"断在 `strcmp@plt` 上，一次拿到两个操作数"来试：

```bash
# run_parent.gdb
break strcmp@plt
run < in.txt
info breakpoints
```

```bash
gdb -q -batch -x run_parent.gdb ./forkcheck
```

输出（GDB 会话开头的线程库提示行与进程号每次运行都不同，本章此后一律省略）：

```
Breakpoint 1 at 0x4011a0
key: [Detaching after fork from child process 14224]
wrong key
[Inferior 1 (process 14221) exited normally]
Num     Type           Disp Enb Address            What
1       breakpoint     keep y   0x00000000004011a0 <strcmp@plt>
```

`[Detaching after fork from child process …]` 说明子进程出生即被放手；程序正常跑完、打出 wrong key，而 `info breakpoints` 的列表里**没有** `breakpoint already hit` 行——命中计数为零，断点一次都没停。校验在另一个进程里发生，==断点没有跟着走过去==。

### 3.2 follow-fork-mode child：跟到子进程里拿答案

GDB 用两个设置管理 fork 的跟踪归属：`follow-fork-mode` 决定跟谁（`parent` 默认 / `child`），`detach-on-fork` 决定不跟的那一方是放手（`on` 默认）还是挂起待命（`off`）。把模式改成"跟子进程、放手父进程"，在 `run` **之前**设好，断点照常下：

```bash
# run_child.gdb
set follow-fork-mode child
break strcmp@plt
run < in.txt
info inferiors
x/s $rdi
x/s $rsi
continue
```

```bash
gdb -q -batch -x run_child.gdb ./forkcheck
```

输出：

```

key: [Attaching after Thread 0x7ffff7fa9740 (LWP 14249) fork to child process 14252]
[New inferior 2 (process 14252)]
[Detaching after fork from parent process 14249]
[Inferior 1 (process 14249) detached]
[Switching to Thread 0x7ffff7fa9740 (LWP 14252)]

Thread 2.1 "forkcheck" hit Breakpoint 1, 0x00000000004011a0 in strcmp@plt ()
```

逐段读：

- `[Attaching after fork … to child process 14252]` 与 `[Detaching after fork from parent process …]`：这次 GDB 反了过来——挂到子进程，放手父进程。父进程脱离调试器后自由运行，把输入写进管道后退出；
- `Thread 2.1 "forkcheck" hit Breakpoint 1`：断点在子进程里命中（编号 2 是子进程这个 inferior 的编号，`info inferiors` 的 `*` 标出当前所在）；
- `x/s $rdi` 与 `x/s $rsi`：x86-64 Linux / System V AMD64 ABI 下 strcmp 的两个参数依次在 rdi、rsi（[[R06-动态调试GDB与x64dbg#6.1 print 与寄存器|R6 6.1]]）——rdi 是经管道送进来的输入 `AAAA`，rsi 是子进程刚组装好的密钥 `ch1ld_pr0c`；
- 最后一行 `wrong key`：输入本来就是错的，不影响密钥已经读到手。

密钥喂回靶子：

```bash

```

输出：

```

```

成功输出里的 flag 直接嵌着密钥——静态的 strings 里同样搜不到完整 flag，它的成形位置就是子进程的栈。

### 3.3 变体与识别

赛题里这一模式常见的加强形态：校验数据在父子之间**往返**——父进程发一个字节，子进程回一张"对/错"回执，逐字符推进；或者兄弟多个进程各持答案的一段，管道串成校验链。结构再复杂，识别与解法不变：

1. 反汇编里看到 `call fork@plt`（或 `pthread_create`，线程版见下方折叠框），先问==比较发生在哪个进程==；
2. 从比较函数（strcmp/memcmp/自实现循环）的位置反推它属于谁；
3. 用 `set follow-fork-mode child` 把调试器带到那个进程，[[R06-动态调试GDB与x64dbg#10.2 四步流程：断点、回溯、finish、dump|R6 10.2 的四步流程]]原样适用。

Windows 侧同类结构是 `CreateProcess` 加匿名管道，x64dbg 同样一次只细跟一个进程——先确认比较发生在哪个进程，再 Attach 那个进程，判断方法相同。

> [!info]- detach-on-fork off：两个进程都留在调试器里
> `set detach-on-fork off` 之后，fork 产生的新进程不再被放手，而是作为新的 inferior 挂起待命，GDB 只细跟其中一个：
>
> ```
> (gdb) set detach-on-fork off
> (gdb) run
> (gdb) info inferiors
>   Num  Description       Connection           Executable
> * 1    process 14221    1 (native)           .../forkcheck
>   2    process 14224    1 (native)           .../forkcheck
> (gdb) inferior 2
> ```
>
> `inferior 2` 把调试焦点切到子进程，此后断点、单步都作用于它。需要"在父子之间来回观察数据传递"时用这个模式；只想拿子进程里的答案时，`follow-fork-mode child` 更直接。

> [!info]- 线程版：同样的"答案在别处"，调度器换成调度单位
> 靶子把校验放进子进程；换成 `pthread_create` 起一个校验线程，密钥就只在那个线程的栈上组装。GDB 不需要 follow 类设置——线程默认全在同一个进程里，`info threads` 列出全部线程，`thread N` 切换，断点照常命中。识别特征从 fork@plt 换成 pthread_create@plt，其余流程一致。

> [!info]- 模式库条目：fork 与管道校验
>
> | 字段 | 内容 |
> | ---- | ---- |
> | 特征 | 反汇编见 fork@plt/pipe@plt（或 CreateProcess）；比较函数或密钥组装代码位于 fork 返回 0 的分支 |
> | 原理 | 子进程是独立地址空间，密钥只在子进程内存成形；调试器默认只跟父进程 |
> | 解法 | `set follow-fork-mode child` 后照常下断；或 `set detach-on-fork off` + `inferior N` 来回切 |
> | 出处 | 本节；断点与读寄存器基本功见 [[R06-动态调试GDB与x64dbg\|R6]] 第 3、6 节 |
> | 例题 | 本节 forkcheck；线程变体用 info threads + thread N |

## 4. 模式三：时间侧信道还原

### 4.1 原理

[[R08-CrackMe经典题型#8.1 逐字符校验|R8 8.1]] 的逐字符校验在反汇编里是一条 `cmp al,立即数` 链，第一处不匹配就直接跳失败。这个"早退"结构平时被当作可读性良好的校验，换个角度它在向外泄漏进度：==比较进行到第几轮，是输入前缀正确长度的函数==。只要存在任何一个能被外部观测、又随校验进度变化的物理量，这个进度就能被逐字符读出来。耗时是最常用的一个：

$$T(\text{候选}) \approx \text{已匹配字符数} \times \text{单字符延时} \tag{16.1}$$

固定前缀，只让第 $p$ 位取遍候选字符集，对每个候选测一次响应耗时，取最慢者——它让比较多走一轮，耗时多出一份单字符延时：

$$\hat{c}_p = \arg\max_{c}\; T(\text{已知前缀} \,\|\, c) \tag{16.2}$$

耗时之外，响应长度、报错顺序、返回码、甚至服务是否抛出特定异常，都随校验进度变化——==凡"校验进度影响可观测输出"的结构，都是侧信道==。本节以时间为例走完整流程。

### 4.2 靶子

一个循环应答的校验服务：从标准输入逐行读候选串，逐字符与密钥比较，==每匹配一个字符就多花 10 毫秒==，然后答 wrong 或 Correct!，继续读下一行：

```c
/* side.c —— 时间侧信道靶子：逐字符比较，每匹配一个字符多花 10 毫秒；循环应答，可反复询问 */
#include <stdio.h>
#include <string.h>
#include <time.h>

#define KEYLEN 13

static void delay_ms(long ms)
{
    struct timespec t = { .tv_sec = ms / 1000, .tv_nsec = (ms % 1000) * 1000000L };
    nanosleep(&t, NULL);
}

int main(void)
{
    char key[KEYLEN + 1];
    unsigned char seed[KEYLEN] = {
        0x43, 0x06, 0x5A, 0x06, 0x59, 0x50, 0x68,
        0x07, 0x45, 0x03, 0x54, 0x5B, 0x04
    };
    for (int i = 0; i < KEYLEN; i++)       /* 密钥运行时组装 */
        key[i] = (char)(seed[i] ^ 0x37);
    key[KEYLEN] = '\0';

    char buf[64];
    while (fgets(buf, sizeof buf, stdin)) {
        buf[strcspn(buf, "\n")] = '\0';
        for (int i = 0; i < KEYLEN && buf[i]; i++) {   /* 匹配一个字符，多等 10ms */
            if (buf[i] != key[i])
                break;
            delay_ms(10);
        }
        if (strlen(buf) == KEYLEN && strncmp(buf, key, KEYLEN) == 0)
            puts("Correct!");
        else
            puts("wrong");
        fflush(stdout);
    }
    return 0;
}
```

`delay_ms` 用 `nanosleep` 睡满指定毫秒，模拟"每核对一个字符的一次真实开销"。靶子的运行时形态对应真实场景：远端服务只告诉你对错，你能控制的只有"问什么"和"什么时候问到答案"。

```bash
gcc -O0 -fno-pie -no-pie side.c -o side
strings -t x side | grep -E '^ +2[0-9a-f]+ '
```

输出：

```
   2006 Correct!
   200f wrong
```

strings 里只有两条应答语，密钥不在磁盘上。

### 4.3 计时还原

攻击脚本按式 (16.2) 工作：保持一个到靶子的常驻连接（进程常驻，免去反复启动的开销），每个位置把候选字母表问一遍，取最慢的候选；补齐一位后接着找下一位。填塞用大写 `A`——密钥字符集是小写字母、数字、下划线，`A` 永远不会误匹配：

```python
# solve_side.py —— 时间侧信道还原：每个位置问一遍字母表，取最慢的候选
from pwn import *
import time, string

context.log_level = 'error'

ALPHA = string.ascii_lowercase + string.digits + '_'
KEYLEN = 13

p = process('./side')
known = ''
for pos in range(KEYLEN):
    best, best_t = '', -1.0
    for c in ALPHA:
        t0 = time.perf_counter()
        p.sendline((known + c).ljust(20, 'A').encode())
        p.recvline()
        dt = time.perf_counter() - t0
        if dt > best_t:
            best, best_t = c, dt
    known += best
    print("pos %2d: %s  %6.1f ms" % (pos, best, best_t * 1000))

p.sendline(known.encode())               # 还原出的完整串，喂回靶子确认
print("final :", p.recvline().decode().strip())
p.close()
print("restored:", known)
```

```bash
gcc -O0 -fno-pie -no-pie side.c -o side
time python3 solve_side.py
```

输出：

```

pos  1: 1    20.6 ms
pos  2: m    31.5 ms
pos  3: 1    41.4 ms
pos  4: n    51.8 ms
pos  5: g    61.8 ms
pos  6: _    72.3 ms
pos  7: 0    82.4 ms
pos  8: r    92.7 ms
pos  9: 4   103.4 ms
pos 10: c   112.5 ms
pos 11: l   123.1 ms
pos 12: 3   134.1 ms

user	0m0.349s

```

计时表逐级抬高：第 $p$ 位答对时，正确候选的耗时是 $(p+1) \times 10\,\text{ms}$，恰好比同位置的错误候选多 10ms——脚本没有读过一行校验逻辑，==答案完全由"问"与"计时"还原==。末尾把完整串喂回靶子，程序自己给出 Correct!，还原结果闭环。37 个候选 × 13 个位置共 481 次询问，30 秒完成。

> [!warning] 噪声决定单字符延时的下限
> 还原的可靠性取决于"相邻两位约 10ms 的差值"是否显著高于环境噪声。本地管道往返的抖动在亚毫秒级，10ms 的差值有十倍以上余量；换到远程服务，网络抖动几十毫秒起步，就要做三件事：把单字符延时估计出来（先用全对前缀与全错前缀各测一批，量出两级之间的差值）；每个候选测多次取最大值或中位数压噪声；用全错串测出基线往返耗时，所有读数先减基线再比较。==侧信道攻击的第一步永远是量噪声，不是写脚本==。

> [!info]- 两个工程细节与一个防御面
> **为什么常驻连接**：每次询问重启一次进程的话，进程启动的开销（数毫秒）会淹没小的耗时差；靶子的循环应答结构让 481 次询问共享一次启动。远端题天然满足这个条件。**为什么填塞**：候选串必须够长，否则比较循环因 `buf[i]` 提前为 0 而中止，进度信息被截断；填一个不会误匹配的字符把串垫长，让循环始终"走到该停的地方"。**防御面**：把比较写成"恒定时间"（比较耗时与是否匹配无关，例如对全部位累加差异后再判零）可以抹平时间信号——你遇到"怎么测耗时都一样"的校验时，先怀疑它，再换一个量测对象：响应长度、报错顺序、返回码，问的还是同一个进度。

> [!info]- 模式库条目：时间侧信道
>
> | 字段 | 内容 |
> | ---- | ---- |
> | 特征 | 校验逐字符进行且早退；服务可反复询问；存在随校验进度变化的可测物理量（耗时/响应长度/报错顺序） |
> | 原理 | 已匹配字符数是输入正确前缀长度的函数，早退让进度泄漏进计时（式 16.1） |
> | 解法 | 固定前缀逐位爆破，每候选计时，取最慢（式 16.2）；先测噪声基线 |
> | 出处 | 本节；逐字符校验的反汇编形状见 [[R08-CrackMe经典题型#8.1 逐字符校验\|R8 8.1]] |
> | 例题 | 本节 side；远端场景与防御面见上方折叠框 |

## 5. 模式四：INT3 自毁与 coredump 取证

### 5.1 原理

`int3` 是单字节指令，操作码 `0xCC`，触发 3 号陷阱。[[R06-动态调试GDB与x64dbg#3.1 软件断点：break 与 0xCC|R6 3.1]] 讲过它的调试器用途：软件断点就是把目标指令首字节改写成 0xCC。本节用它做相反的事——**出题人把 int3 写进程序自己的执行路径**：程序运行到某处主动触发陷阱，==没有调试器接住时，进程直接死于 SIGTRAP，同时把整份已写内存落成 core 文件==；而密钥在陷阱之前已经组装进了栈。

两个要点：

- **崩溃现场即证据现场**：core 是进程死亡那一刻的完整内存快照（已写过的页），[[R06-动态调试GDB与x64dbg#2.1 三种启动方式|R6 2.1]] 列过第三种启动方式 `gdb ./prog core`——读的就是这份快照。密钥只要在被组装之后、崩溃之前存在于内存，core 里就有它；
- **与反调试的方向相反**：[[R10-反调试与反分析对抗|R10]] 的程序用各种手段**阻止**你调试；这一模式反过来，出题人把"运行时事实"留在一份你自己就能打开的崩溃记录里。行为的取证读取与恶意代码分析里"关键事实只存在于运行中"的思路同源（[[R15-恶意代码分析基础|R15]] 的行为监控是同一哲学的工程化）。

### 5.2 打开 core 落盘

core 落盘要过三道开关，缺一不可：

1. **shell 侧资源限制**：`ulimit -c` 查看当前上限，默认常为 0（禁止落盘）；`ulimit -c unlimited` 对当前 shell 会话放开；
2. **内核侧命名规则**：`/proc/sys/kernel/core_pattern` 决定 core 文件名与落点，纯文件名（如 `core`）落在进程当前目录；很多发行版默认把它配成 apport / systemd-coredump 的管道处理，先改回 `core`。这一步写 `/proc/sys`，需要 root；
3. **文件系统**：core 要落在可靠文件系统上。WSL 里 `/mnt/c` 是挂载盘，core 落盘不可靠——把工作目录放 WSL 原生路径（`~` 下）再运行。

```bash
ulimit -c unlimited
echo core > /proc/sys/kernel/core_pattern
cat /proc/sys/kernel/core_pattern
```

输出：

```
core
```

> [!info]- WSL 无免密 sudo 时怎么写 core_pattern
> 从 Windows 侧以 root 进入 WSL 执行这一句，免密：
>
> ```bash
> wsl -d Ubuntu-26.04 -u root -- bash -c 'echo core > /proc/sys/kernel/core_pattern'
> ```
>
> 普通 Linux 环境用 `sudo`。core_pattern 是全局设置，WSL 重启后恢复默认，每次做实验前先 `cat` 一眼确认。

### 5.3 崩溃、读 core

靶子在 main 里先组装密钥，再执行一条内联汇编的 `int3`：

```c
/* coredemo.c —— 自嵌 int3 的自毁程序：陷阱之前密钥已组装进栈帧，崩溃现场即证据现场 */
#include <stdio.h>
#include <string.h>

int main(void)
{
    char key[14];
    unsigned char seed[13] = {
        0x3F, 0x6C, 0x2E, 0x6F, 0x03, 0x3A, 0x6C,
        0x2E, 0x6F, 0x32, 0x2F, 0x6D, 0x3F
    };
    for (int i = 0; i < 13; i++)           /* 密钥先组装，再触发陷阱 */
        key[i] = (char)(seed[i] ^ 0x5C);
    key[13] = '\0';

    puts("collecting evidence ...");
    fflush(stdout);
    __asm__ volatile("int3");              /* 自嵌 0xCC：无调试器时进程死于 SIGTRAP */
    puts("never reached");
    return 0;
}
```

反汇编确认自嵌的陷阱就是那一个字节的 `cc`（x86-64 Linux / System V AMD64 ABI）：

```
Program terminated with signal SIGTRAP, Trace/breakpoint trap.
#0  main () at coredemo.c:19
19	    puts("never reached");
#0  main () at coredemo.c:19
key = "c0r3_f0r3ns1c"
seed = "?l.o\003:l.o2/m?"
$1 = "c0r3_f0r3ns1c"
```

三行关键信息：

- `Program terminated with signal SIGTRAP`：死因是 3 号陷阱，与自嵌的 int3 对上；
- `#0 main () at coredemo.c:19`：崩溃帧在 main，指向的行是 int3 的**下一条**——==int3 属于陷阱类异常，保存的 rip 指向它的下一条指令==（反汇编里 `cc` 在 0x4011f5，崩溃位置 0x4011f6）；gdb 按 rip 落在的行号显示，读现场时脑内回退一条指令才是陷阱本身；
- `key = "c0r3_f0r3ns1c"`：带调试信息时 `info locals` 直接给出答案；`p key` 同样可行。这份密钥从未写进任何文件，它只在那次运行里存在过——而 core 里保存的正是那次运行结束时的内存。

> [!info]- 二进制被 strip 之后怎么读
> 没有符号与调试信息时，bt 只剩地址（`#0 0x00000000004011f6 in ?? ()`，`#1` 一层能看到 libc 的 `__libc_start_call_main`，`main` 的真实入口是它参数里的 `main=0x401176`）。密钥在栈上，两个不依赖符号的读法：
>
> ```bash
> gdb -q -batch ./coredemo_s core -ex 'x/8gx $rsp'
> strings core | grep -E '^..o2/m\?c0r3'
> ```
>
> 输出：
>
> ```
> 0x7fff85200a80:	0x0000000000000000	0x2e6c3f000000000d
> 0x7fff85200a90:	0x2f326f2e6c3a036f	0x665f337230633f6d
> 0x7fff85200aa0:	0x006331736e337230	0xb9a2069b49db7f00
> ```
>
> ```
> :l.o2/m?c0r3_f0r3ns1c
> ```
>
> 第一条：`x` 按地址读栈，小端序按字节顺序重排即见 ASCII（[[R06-动态调试GDB与x64dbg#6.2 x 命令完整语法|R6 6.2]] 的小端提醒）；crash 点的 rsp 就压在 main 的局部区旁，密钥就在 rsp 之上几十字节内。第二条更省事：core 本身是个大文件，密钥以原始字节躺在里面，`strings` 直接扫得出来。gdb 的 `find` 命令在 core 上搜字符串时容易因范围跨出已落盘区域而失败（core 只保存被写过的页，见下方 warning），扫答案优先用 `strings`。

> [!warning] core 只包含被写过的内存页
> core 不是整份进程地址空间的拷贝：代码段、已写的栈页、堆页在，未写过的页不在。栈只落了实际使用过的低端几页，所以搜索范围要贴着 `$rsp` 附近；把范围开到 `±0x2000` 就可能撞上未映射区，gdb 报 `Unable to access … target memory` 并中断搜索。另外 core 文件轻易几百 KB 到上百 MB，写题解时贴关键几行即可，不必附带整个文件。

> [!info]- 模式库条目：INT3 自毁与 coredump 取证
>
> | 字段 | 内容 |
> | ---- | ---- |
> | 特征 | 正常运行直接崩溃退出（Trace/breakpoint trap）；反汇编里出现自嵌的 `cc`；答案在崩溃前已进内存 |
> | 原理 | int3 无调试器接住时进程死于 SIGTRAP，内核把已写内存落成 core；core 是死亡瞬间的完整快照 |
> | 解法 | ulimit -c unlimited + core_pattern 改 core + 原生文件系统；gdb 程序 core 读现场；strip 时 x 栈或 strings 扫 |
> | 出处 | 本节；int3 与断点机制见 [[R06-动态调试GDB与x64dbg#3.1 软件断点：break 与 0xCC\|R6 3.1]]，core 启动方式见 [[R06-动态调试GDB与x64dbg#2.1 三种启动方式\|R6 2.1]] |
> | 例题 | 本节 coredemo；崩溃不限于 int3——raise(SIGSEGV) 同样落 core |

## 6. 精读别人的 WriteUp

### 6.1 怎么读：先做、再读、复现

一篇 WriteUp 是别人解法的成品记录，直接从头读到尾，得到的是"看过的解法"；按固定次序加工，才得到"用得出的模式"。次序三步：

1. **先自己 30 分钟**。拿到题先不看任何题解，按 [[R08-CrackMe经典题型#1.2 通用分流决策|R8 1.2]] 的分流走一遍。30 分钟不是解题时限，是形成"自己的问题"的时间：把卡在哪一步、当时在想什么、试过什么记下来。带着空白去读题解，读到的每一步都是作者的；带着问题去读，读到的才分得清哪些是你缺的。
2. **对照着读，只盯三处**。他的第一步分流是什么；他在哪一步换了路（你逆哈希他 patch、你静态他动态）；他用了哪个你没启动的模式。这三处就是 [[R08-CrackMe经典题型#9. 三遍学习法与错题本|R8 第 9 节]]说的"视角盲区"，逐条记进错题本，模板四列照用，外加一列"模式归属"指向模式库条目。
3. **脱稿复现**。合上题解，从 `file` 到拿 flag 重做一遍，产出一个能运行的 solve 脚本。复现卡壳的位置，就是第一步"以为看懂了"的位置——回题解对应段落重读，再复现到不卡为止。

> [!warning] 跳过第一步和第三步，读一百篇也建不起模式库
> 题解读起来顺，是因为作者替你踩完了坑并抹平了弯路；"看懂"发生在作者的语境里，不发生在你的手上。只有第一步让你知道"我缺什么"，第三步强迫"我用出来"，中间的阅读才会转化为自己的模式。同样的纪律也就是 [[R08-CrackMe经典题型#9. 三遍学习法与错题本|R8 第 9 节]]三遍学习法在"读别人的题解"上的应用。

### 6.2 哪里找、怎么挑

| 来源 | 特点 | 入口 |
| ---- | ---- | ---- |
| 平台官方 | 与赛题附件严格对应，格式统一，权威 | picoCTF 题解区、CTFtime 赛事页的官方存档 |
| 战队博客 | 成体系，常写思路取舍与换路原因 | 各战队官网与公开博客，赛后集中发布 |
| GitHub 合集 | 检索方便，覆盖面广，质量参差 | 搜索"赛事名 年份 writeups" |
| 题库社区 | 入门友好，按题目聚合 | BUUCTF、攻防世界的题解区（[[R11-代码混淆花指令与OLLVM#11. 配套练习与延伸阅读\|R11 第 11 节]]找样本用过） |

质量甄别看四条，命中越多越值得精读：

| 维度 | 可信的写法 | 存疑的写法 |
| ---- | ---- | ---- |
| 思路 | 写明分流依据与换路原因 | 只有最终 exploit 脚本 |
| 过程 | 保留失败尝试与排除记录 | 一步到位，全程无弯路 |
| 复现 | 给附件版本、命令可复制 | 无版本信息，命令缺上下文 |
| 结论 | flag 形态与题面一致、脚本可运行 | 只贴 flag 截图 |

同一道题读两三篇不同作者的解法，收益高于一道题读一篇加另一道题读一篇——==多篇对照才能把"这道题的解法"和"这类题的模式"区分开==。

## 7. 复盘产出物：错题本、模式库与一页纸

复盘的产出不是"一篇感想"，而是三件各司其职的沉淀物：

| 产出物 | 粒度 | 装什么 | 更新时机 |
| ---- | ---- | ---- | ---- |
| 错题本 | 每题一条 | 卡点、关键一步、对应章节（[[R08-CrackMe经典题型#9. 三遍学习法与错题本\|R8 第 9 节]]四列模板） | 当天 |
| 模式库 | 每模式一条 | 本章五字段：特征/原理/解法/出处/例题 | 出现新模式，或同类卡点第三次出现 |
| 一页纸总结 | 每场比赛一张 | 题目清单与完成状态、每题用时、卡点归类、新模式候选、可复用脚本清单 | 赛后 24 小时内 |

三者的分工由"复用时怎么查"决定：重做某道题时查错题本；开新题时按特征查模式库；准备下一场比赛时翻一页纸。错题本是模式库的例题来源——==同类卡点第三次出现，就把它的共性提炼成一条新条目，例题栏填上这三道题==；模式库又是一页纸的赛前素材——赛前按条目过一遍"特征 → 第一动作"，比赛中的分流就是在库内检索。

模式库的目录组织，在 Obsidian 里保持最简：

- 每个模式一条独立笔记，文件名即模式名（本章四节若抽出，就是四条笔记的雏形）；
- 条目正文按五字段模板填写，特征字段写"反汇编/伪代码/行为里你会看到什么"——因为将来检索时，你手里只有特征；
- 出处字段一律用双链指回章节，例题字段攒题目名与来源链接；
- 一页纸与错题本按日期或赛事归档，与模式库目录分开。

维护节奏固定四步：赛后 24 小时内补齐错题本与一页纸；每周从错题本里挑同类卡点合并成条目候选；候选攒够三道例题升为正式条目；每季度合并重复条目、删除从未被检索命中的条目。条目数量不是目标，==能被特征检索到才算数==——赛前自查的法子：随机挑一条目，只看特征字段，能不能在 30 秒内说出第一动作。

> [!note] 与比赛流程的衔接
> 一页纸总结是赛后动作，赛中怎么记、赛后怎么把它转进错题本，都由完整的比赛流程给出，[[R17-赛事策略与团队协作|R17]] 展开赛事侧的安排。

## 8. AI 辅助分析：假设与验证的分工

### 8.1 谁做什么

AI 助手读汇编、读伪代码、写脚本的速度远快于人，但它给出的是**语言上自洽的答案**，不是**事实上经过检验的答案**。分工按这个差异划线：

| AI 适合做 | 必须人工做 |
| ---- | ---- |
| 读大段反汇编并摘要：函数切分、循环与分支形状、可疑常数清单 | 断点与补丁的落点：地址、字节、==属于哪个进程==，逐一核实 |
| 提漏洞与校验假设清单（按可能性排序的那种） | 调用约定与寄存器归属：平台、位数、参数在哪个寄存器 |
| 写脚本骨架：pwntools 模板、z3 建模框架、文件解析 | 约束完整性：z3 建模是否漏了校验项（[[R14-自动化分析angr与z3#2.4 实战：异或 + 加法方程组的纯 z3 求解\|R14 2.4]] 的锚点教训） |
| 解释不认识的指令、结构、协议字段 | 环境事实：checksec 输出、libc 版本、程序实际行为 |
| 把你的思路复述成步骤清单，暴露逻辑缺口 | 一切"程序会怎样"的断言——跑一遍便知 |

判据一句话：==AI 产出的每一条，都要落成一条可以执行的检验命令==。假设被证实，它变成你模式库里的例题注脚；被证伪，它变成一次分流教训——两种结果都比"照单全收"值钱。

### 8.2 工作流示例：AI 给假设，人工验证，修正

以第 3 节的靶子为例走一遍完整闭环。设定：手里只有 `forkcheck` 这个二进制，没有源码。先做基础侦察，把 `file` 输出与 main 的反汇编片段喂给 AI，问"这个程序的校验逻辑在哪、怎么解"：

```bash
objdump -d -M intel forkcheck | sed -n '/<main>:/,/^$/p'
```

输出（节选，注释为后文讲解添加）：

```asm
; x86-64 Linux · System V AMD64 ABI · Intel 语法
  4012f8:	e8 73 fe ff ff       	call   401170 <pipe@plt>
  ……（printf、scanf 与参数装载省略）……
  40134e:	e8 8d fe ff ff       	call   4011e0 <fork@plt>
  401353:	89 45 8c             	mov    DWORD PTR [rbp-0x74],eax
  401356:	83 7d 8c 00          	cmp    DWORD PTR [rbp-0x74],0x0
  40135a:	0f 85 d0 00 00 00    	jne    401430 <main+0x15a>      ; 非 0 → 转去 401430：父进程分支
  401360:	8b 45 94             	mov    eax,DWORD PTR [rbp-0x6c]
  401363:	89 c7                	mov    edi,eax
  401365:	e8 f6 fd ff ff       	call   401160 <close@plt>
  ……（buf 清零省略）……
  40138a:	48 b8 21 2a 73 2e 26 	movabs rax,0x30321d262e732a21  ; 8 字节常量进栈：种子
  401394:	48 89 45 9b          	mov    QWORD PTR [rbp-0x65],rax
  401398:	66 c7 45 a3 72 21    	mov    WORD PTR [rbp-0x5d],0x2172     ; 常量剩余 2 字节
  ……（read 管道省略）……
  4013c7:	8b 45 88             	mov    eax,DWORD PTR [rbp-0x78]
  4013cc:	movzx  eax,BYTE PTR [rbp+rax*1-0x65]
  4013d1:	83 f0 42             	xor    eax,0x42                       ; 逐字节异或 0x42
  4013db:	mov    BYTE PTR [rbp+rax*1-0x5b],dl
  ……（循环判断省略）……
  4013fb:	e8 a0 fd ff ff       	call   4011a0 <strcmp@plt>
  401400:	85 c0                	test   eax,eax
  401402:	75 18                	jne    40141c <main+0x146>
  ……（成功输出与 exit 省略）……
  401430:	（父进程分支：close、write、waitpid 后收尾）
```

AI 的典型回答如下（要点摘录）：

> main 调用了 pipe 和 fork。fork 返回 0 的分支（401360 起）里有 read、一个 10 字节常量 `0x30321d262e732a21` 及其后续 2 字节、一段逐字节 `xor 0x42` 的循环和 strcmp——校验大概率在这个分支，即子进程里完成，密钥由常量异或 0x42 运行时组装。建议断在 strcmp@plt 上，第二个参数 rsi 即期望密钥。

按它的建议直接验证。第一步人工执行：照 [[R06-动态调试GDB与x64dbg#10.3 换条路：断在 strcmp@plt 上|R6 10.3]] 的做法断 `strcmp@plt`，默认模式运行——结果在 3.1 节已看到：==断点命中计数为 0==，子进程被 GDB 放手，校验发生在调试器看不见的地址空间里。

第二步修正：AI 对程序事实的判断（校验在子进程、常量是种子、xor 0x42 组装）逐条成立——3.2 节的现场就是证据；错的只是解法的最后一步，它没有考虑"断点跟进程走"。补上 `set follow-fork-mode child`，断点命中，rsi 给出 `ch1ld_pr0c`，答案到手。

第三步复盘，三行记录：

| AI 的假设 | 人工检验 | 结论 |
| ---- | ---- | ---- |
| 校验在 fork 返回 0 的分支，即子进程 | 反汇编确认 strcmp 在 jne 跳过的分支里 | 成立，采纳 |
| 断 strcmp@plt，rsi 即密钥 | 默认模式下命中计数为 0 | 不成立：断点没跟到子进程 |
| （隐含）常规断点流程适用 | 补 set follow-fork-mode child 后命中 | 修正后可用 |

这个闭环就是 AI 辅助的常态：==它把"读"的环节提速，把"想到可能"的环节扩面；证实与证伪都发生在你执行的命令里==。检验成本通常一两分钟，收益是把语言上自洽的答案升级为事实上成立的结论。

> [!info]- 喂材料的三个习惯
> 一、给"函数段"不给全文件：`objdump -d -M intel 目标 | sed -n '/<main>:/,/^$/p'` 截出目标函数，AI 的注意力不会被几十个无关函数稀释；strip 过的二进制先在 IDA/objdump 里定位函数边界。二、给环境事实：`file` 输出、运行一次的实际输出一起给，减少它对平台与调用约定的猜测。三、问"假设清单"不问"最终答案"：要求它按可能性列出两三个假设并说明依据，你逐条检验——单答案模式会诱导它把猜测包装成结论。

> [!info]- 与 PWN 侧的分工
> 本章的 AI 用法围绕"读懂程序"：读汇编、建约束、写还原脚本。PWN 方向的 AI 用法围绕"构造输入"：搜 gadget、生成 payload 骨架、核对偏移与保护，检验点换成 checksec、ROP 链地址计算与实际打靶，细节在那边更丰富，展开在 [[P22-综合实战赛事策略与AI辅助|P22]]。两个方向共用同一条红线：==AI 的产出必须落成可执行的检验==。

## 9. 常见问题

| 现象 | 原因与解决 |
| ---- | ---- |
| LD_PRELOAD 挂了钩子但程序行为没变 | 目标静态链接或直接 syscall，不经过 PLT，钩子无效（[[R10-反调试与反分析对抗#8.1 ptrace 自占：一个人只能被跟踪一次\|R10 8.1]]）；改走 patch |
| 钩子之后程序崩溃或行为怪异 | 钩子内部调用了被自己覆盖的函数，递归或语义错乱；内部自实现，或 `dlsym(RTLD_NEXT, …)` 转发（[[#2.3 钩子库与三步走\|2.3]]） |
| 钩了 strcmp 后输出出现大量 `[oracle]` 噪声行 | 覆盖是全进程生效的，其他代码的 strcmp 也被钩住；属正常现象，只关注校验那一次的输出 |
| `break strcmp` 直接报错或断点不命中 | 库函数有 IFUNC 多实现，要断 `函数名@plt`（[[R06-动态调试GDB与x64dbg#10.3 换条路：断在 strcmp@plt 上\|R6 10.3]]） |
| follow-fork-mode child 设了，断点还是不停 | 设置在 `run` 之后才生效不了；两个设置都要在 run 之前给。仍不停就确认断点是否真在校验路径上（`info breakpoints` 看命中计数） |
| 子进程的输出时有时无 | 子进程用 `_exit` 收尾会丢弃 stdio 缓冲；改用 `exit` 或打印后 `fflush`（[[#3.1 靶子与难点\|3.1]] 靶子的写法） |
| 侧信道还原到中间某位就错 | 相邻两位的耗时差被噪声淹没：加大单字符延时、每候选多次取样取最大/中位、先减基线往返耗时（[[#4.3 计时还原\|4.3]]） |
| 远端侧信道题本地脚本完全复现不了 | 填塞字符误匹配了密钥字符（大小写、符号集）；换一个必然不匹配的填塞字符再跑 |
| 程序崩了但当前目录没有 core | 三道开关逐一查：`ulimit -c` 是否为 0；core_pattern 是否被配成管道；工作目录是否在不可靠文件系统（WSL 的 /mnt/c）（[[#5.2 打开 core 落盘\|5.2]]） |
| gdb 读 core 时 `find` 报 Unable to access 后中断 | core 只存被写过的页，搜索范围跨出了已落盘区域；缩小到 `$rsp` 附近，或直接 `strings core` 扫（[[#5.3 崩溃、读 core\|5.3]]） |
| AI 给的断点位置/补丁字节照做后没效果 | 假设未经检验：核对地址、字节、进程归属三件事，再决定采信与否（[[#8.2 工作流示例：AI 给假设，人工验证，修正\|8.2]]） |
| 题解读了很多，开新题还是没思路 | 读题解跳过了"先做"与"复现"，模式停在"看过"层；按 [[#6.1 怎么读：先做、再读、复现\|6.1]] 的次序重读两篇试试 |

配套练习：

1. 给 `hook.c` 补一个 `memcmp` 钩子，把 `oracle.c` 的校验改成 `memcmp(buf, key, 16) == 0` 的版本，比较 oracle 照样泄露答案；体会"校验函数换了，模式不变"。
2. 把 `side.c` 的比较改成恒定时间版本（对全部 13 位累加差异位、最后统一判零），重跑 `solve_side.py`，观察还原失效；再把量测对象换成响应长度或报错顺序，设计一个新的还原脚本。
3. 给 `forkcheck.c` 的父进程分支加一道假校验：先比对一个 strings 里可见的假 flag，命中就输出假 flag，否则照旧走子进程——体验"父进程假路径 + 子进程真校验"的双层分流，再用第 2 节与第 3 节的两个模式各解一次。
4. 把 `coredemo.c` 的 `__asm__ volatile("int3")` 换成 `raise(SIGSEGV)`（SIGSEGV 同样产生 core），对比两份 core 的 gdb 输出：死因信号、崩溃帧、`p key` 是否都一致。
