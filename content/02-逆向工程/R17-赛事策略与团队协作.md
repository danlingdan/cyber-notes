# R17 赛事策略与团队协作
## Competition Strategy & Team Collaboration

> [!info]- 章节信息
> **所属方向**：逆向工程 ｜ **难度阶段**：L4 高级与实战期 ｜ **前置要求**：[[R16-综合实战案例复盘|R16]] · [[R01-逆向工程与CTF竞赛生态导论|R01]]
> **本章目标**：能作为 RE 主力参加一场线上赛并产出 2 篇以上 WriteUp。

## 1. 本章范围：从会做题到能完赛

前面 R1 到 R16 解决的是"一道题怎么做"：题型、工具、对抗手法各有专章。本章解决另一件事：**一场比赛从头到尾怎么打**。单人练习与组队正式赛的差别不在题目难度，而在约束条件——限时、限人、多方向并行、成绩按队伍计。约束变了，做法就要跟着变：赛前有报名与准备，赛中有时间分配与止损规则，赛后有复盘与产出物归档。本章按**赛前—赛中—赛后**三段组织，每一节都给出可以直接执行的动作，不写空话。

两个说明：

- 本章是逆向方向的方法论收束，但清单与惯例对其他方向同样适用。PWN 侧的赛事策略与 AI 辅助工具在 [[P21-综合实战赛事策略与AI辅助|P21]] 另讲，两章的协作惯例互为补充。
- 赛制、平台生态、flag 机制、合法边界在 [[R01-逆向工程与CTF竞赛生态导论|R01]] 已经讲过，本章只在用到的地方一句带过加双链，不重讲。

## 2. 赛前：选一场合适的比赛并完成报名

### 2.1 练习期与正式赛的目标差异

| | 练习期（平台刷题） | 正式赛 |
| ---- | ---- | ---- |
| 时间 | 不限，一道题可以做一周 | 固定 24–48 小时，过期关闭 |
| 目标 | 补题型、补工具，把 [[R08-CrackMe经典题型\|R08]] 的分流决策练熟 | 限时内多解出、并留下可复用的 WriteUp |
| 计分 | 个人进度，无对手 | 队伍总分排名，可能动态积分（[[R01-逆向工程与CTF竞赛生态导论#7. 平台使用与赛事生态\|R01 第 7 节]]） |
| 题目 | 按分类自由挑 | 一次放出全套，必须自己分级排序 |
| 干扰 | 没有 | 队友沟通、其他方向求助、平台卡顿同时发生 |
| 产出 | 错题本条目 | 解出数 + WriteUp + 复盘记录 |

==练习期的成败标准是"会不会做"，正式赛的成败标准是"时间花在哪了"==。一道值 500 分的难题做到一半，与一道值 100 分的签到题没人认领，正式赛里后者更伤——这是后文 5.2 题目分级要解决的问题。

### 2.2 第一场正式赛怎么选

选赛在 [[R01-逆向工程与CTF竞赛生态导论#7. 平台使用与赛事生态|R01 第 7 节]] 说的 CTFtime.org 上做。CTFtime 是全球赛事日历：Events 页按时间列出 upcoming 与过去的比赛，每场比赛有介绍页、报名入口链接与队伍列表。第一场比赛按五条标准筛：

1. **时长 48 小时以上**。长赛可以睡觉、可以错峰，容错高；8–24 小时的冲刺赛对首战不友好。
2. **办过往届、赛后公开题解**。有 archive 可查往届题目与难度分布，报名前能估出 RE 题量与难度是否匹配。
3. **页面上注明新手友好**（beginner-friendly / for beginners）。这类比赛签到题多、题目描述详细。
4. **报名开放、无预选门槛**。避开邀请制与需要预选赛出线的比赛。
5. **队名与人数限制宽松**。有些比赛限制最少人数或要求学校/组织邮箱，报名前看清楚。

> [!info]- 首战要不要打国际赛
> 打。国际赛的 RE 题与国内比赛题型一致，语言障碍主要在题面描述，翻译工具足够。倒是有两点提前确认：比赛平台是否需要科学上网（报名前先登一次平台确认能打开）、开赛时间是否落在深夜（第 2.4 节的时区换算）。国内比赛（CISCN、强网杯、XCTF 系）以学校或联赛渠道报名，流程各不相同，以官方通知为准。

### 2.3 CTFtime 报名流程

报名分两段：CTFtime 上找比赛，比赛平台上完成注册与组队。操作路径如下，按钮名称以页面实际显示为准：

1. **注册 CTFtime 账号**：ctftime.org 右上角 Sign up，邮箱验证。登录后在账号设置里把时区设为东八区，之后所有比赛时间按本地时间显示。
2. **筛比赛**：Events 页往后翻，按 2.2 的五条标准锁定一场，点进比赛页。
3. **读规则**：比赛页的描述与主办方官网的 rules 至少读一遍，重点四项——计分方式（错提交是否扣分）、flag 格式、hint 政策（是否免费、有无次数限制）、WriteUp 公开政策（赛内是否禁止公开讨论）。
4. **进入报名**：点比赛页的官方链接，跳转到比赛平台（多数是 CTFd 系统）。注册平台账号，邮箱验证。
5. **建队或入队**：平台里找到 Team 页面。你是发起人，就 Create Team，生成**邀请码（team invite code / token）**发给队友；你被拉入，就用队长给的邀请码 Join Team。确认成员列表里人都到齐。
6. **赛前确认**：开赛前 24 小时重新登录一次，能看见"比赛将于 XX 开始"的页面即报名生效。有些比赛需要额外提交队伍信息或签免责声明，平台会发邮件提示。

> [!warning] CTFtime 与比赛平台是两个账号
> CTFtime 只负责日历与赛事信息，解题在比赛平台进行。两处都要注册，邮箱保持一致方便接收通知。报名后收不到邮件先查垃圾箱，开赛前 24 小时仍未收到平台邮件，去主办方公告的群或 Discord 找人。

### 2.4 时区换算

国际赛页面常写 UTC 或美式时区。登录 CTFtime 并设好时区后，页面自动换算成本地时间；没登录看到的是 UTC。北京时间 = UTC + 8 小时：比赛写 `2026-11-07 00:00 UTC`，北京时间是 11 月 7 日 08:00 开赛。

> [!info]- 常见时区缩写对照
> | 缩写 | 含义 | 与 UTC 关系 | 与北京时间的差 |
> | ---- | ---- | ---- | ---- |
> | UTC / GMT | 协调世界时 / 格林尼治平时 | 基准 | −8 小时 |
> | EDT | 美东夏令时（3–11 月） | UTC−4 | −12 小时 |
> | EST | 美东标准时（11–3 月） | UTC−5 | −13 小时 |
> | PDT / PST | 美西夏令时 / 标准时 | UTC−7 / UTC−8 | −15 / −16 小时 |
> | CET / CEST | 欧洲中部（标准 / 夏令时） | UTC+1 / UTC+2 | −7 / −6 小时 |
>
> 换算不确定时别心算：手机时钟加一个对应城市的世界时钟，一眼对照。==开赛时刻以比赛平台页面显示的倒计时为准==，闹钟设在倒计时归零前 30 分钟。

## 3. 赛前：组队与分工

### 3.1 五向分工与交叉

解题赛常设五个方向。分工的准确含义是**第一响应人**：哪个方向来题先归谁看，不是"只能做这类题"。

| 方向 | 职责 | 主要工具 | 与 RE 的交叉 |
| ---- | ---- | ---- | ---- |
| RE | 二进制分析：读逻辑、脱壳、对抗反调试，算出 flag 或关键输入 | IDA/Ghidra、GDB/x64dbg、python3 | 本体 |
| PWN | 二进制漏洞利用：从"读懂"到"控制执行"，拿 shell 或读 flag | pwntools、GDB、gadget 工具 | ==每道 PWN 题的第一步是逆向==（[[P01-PWN导论与缓解机制全景\|P01]] 第 1 节） |
| Web | 网站漏洞：注入、逻辑缺陷、框架漏洞 | 浏览器、burp 类代理、python3 | 题目前端混淆的 JS 分析接近 [[R13-多平台逆向专题\|R13]] 的读法 |
| Crypto | 密码学题：RSA、分组密码、随机数 | python3、sage 类工具 | 与 [[R07-编码与算法识别还原\|R07]] 的编码算法近亲，识别方法共用 |
| Misc | 杂项：隐写、取证、编码连环、OSINT | 通用工具箱（[[12-隐写与流量取证\|通用基础 12 章]]） | 从容器里提出 ELF 后归 RE（[[R01-逆向工程与CTF竞赛生态导论#1. 逆向工程是什么\|R01 第 1 节]]划过这条边界） |

RE 主力在队内的职责清单：

- 开赛后快扫全部 RE 题附件，给出分级（第 5.2 节）；
- 维护 RE 题在状态板上的条目与进度；
- 给 PWN 队友做逆向前置支援（第 9 节）；
- 顺手接下 Misc 里"提出一个 exe/ELF"的题。

### 3.2 队内协作惯例

首战队伍建议 2–4 人，共用一套语音加一个共享文档。惯例五条，赛前约定好，赛中不商量：

1. **语音在线**：Discord 或会议软件常驻，RE 卡壳时口头描述伪代码比打字快。不方便开麦就固定一个文字频道，重要结论必须在文字里留底。
2. **状态板**：共享在线表格，列固定为**题名 / 方向 / 分值 / 状态 / 当前人 / 备注**。状态只有四个值：未动工、进行中、已解出、卡住。每完成一个阶段就更新，全队的分工调度都看这张表。
3. **脚本进共享库**：solve 脚本、逆出来的常量表、有用的输出，贴进共享文档或私有仓库，按题名归目录。赛后写 WriteUp 直接取材。
4. **flag 双人确认再提交**：提交前把 flag 贴进队内频道，第二个人核对前缀与内容后再点提交。有的比赛错提交扣分、重复提交无效，一次误操作的代价比十秒钟的核对高。
5. **换手规则**：一题被两人先后各卡 30 分钟，第三个人接手复盘或换题；人不够就换题。谁也不许在一道题上无限投入。

> [!note] 为什么提交前要双人确认
> 三类事故都发生在真实队伍里：flag 少粘了后半截、把别的方向的 flag 提到这题、把队友贴在频道里的"另一个队的 flag"（题解里抄来的）当成本队答案。动态 flag 按队伍生成，别人的 flag 提交必然无效（[[R01-逆向工程与CTF竞赛生态导论#6. flag 格式与提交机制|R01 第 6 节]]），确认这一步同时防误操作和防抄袭误会。

### 3.3 新人组队渠道

- **校队与社团**：学校信息安全协会通常组队打 CISCN 与各类联赛，新生赛是最低门槛的入口。首战队友从同校找，沟通成本最低。
- **练习平台社群**：攻防世界、BUUCTF、CTFshow 都有官方或社区群，群里常有人发组队信息。报上自己的方向与练习量（如"RE，刷完攻防世界新手区"），比"求带"有效。
- **CTFtime 的 open team**：部分比赛页面的队伍列表里，有队伍标 open to join，申请即可加入陌生队伍。首战更建议和认识的人打，陌生队伍的协作惯例需要磨合，正式赛不是磨合场。

## 4. 赛前：开赛清单

比赛里最贵的是"现装工具"：题目摆在那，环境却要临时装。开赛清单赛前一天过一遍，逐项打勾。分四组：

**信息与协作**

- [ ] 报名生效：比赛平台能登录、队伍成员到齐（2.3）
- [ ] 规则读过一遍：计分、flag 格式、hint 政策、WriteUp 政策
- [ ] 时区换算完成，闹钟设好（2.4）
- [ ] 状态板模板建好，队友都有编辑权（3.2）
- [ ] 附件目录建好：`ctf/<比赛名>/<题名>/`，附件、脚本、WriteUp 分开存

**Linux 侧（WSL）**

- [ ] `file`、`strings`、`objdump`、`readelf`、`xxd` 可用（[[01-Linux环境与CTF实验环境搭建|通用基础 01 章]] 环境）
- [ ] python3 可用，`import pwn` 不报错（[[P05-pwntools与GDB插件工具链|P05]]）
- [ ] IDA 或 Ghidra 能正常新建数据库，把 [[R05-静态分析工具链IDA与Ghidra#3.10 IDA 完整流程|R05 3.10]] 的流程预先走通一遍
- [ ] gdb 可用，`gdb -x` 批量命令文件的方式通过（[[R06-动态调试GDB与x64dbg|R06]]）
- [ ] `import z3`、`import angr` 不报错（[[R14-自动化分析angr与z3|R14]] 的安装命令）
- [ ] `upx -d` 在 PATH 里（[[R09-加壳与脱壳#4. UPX 专项：加壳、识别与自动脱壳|R09 第 4 节]]）
- [ ] CyberChef（本地版或网页收藏）可打开，[[R07-编码与算法识别还原#9. 实战落地：维护一套算法武器库|R07 第 9 节]]的识别脚本在顺手的位置

**Windows 侧**

- [ ] x64dbg 能启动，字符串引用搜索用过（[[R06-动态调试GDB与x64dbg#12. x64dbg：Windows 下的动态调试|R06 第 12 节]]）
- [ ] 查壳工具就位（[[R09-加壳与脱壳#3. 查壳：工具与手工特征|R09 第 3 节]]）
- [ ] jadx、pycdc 类多平台工具可用（[[R13-多平台逆向专题#1. 识别先行：陌生文件三步定性|R13 第 1 节]]的识别先行三步）
- [ ] 附件目录已加入杀毒软件排除项，或备好虚拟机（[[R01-逆向工程与CTF竞赛生态导论#8. 第一道 Reverse 题的完整流程：自建 crackme|R01 第 8 节]]的隔离操作）

**模板**

- [ ] solve 脚本模板、WriteUp 模板（7.1）放进模板目录
- [ ] 虚拟机快照干净，可回滚（[[R01-逆向工程与CTF竞赛生态导论#8. 第一道 Reverse 题的完整流程：自建 crackme|R01 第 8 节]]）

> [!info]- 清单的维护方式
> 每场比赛复盘时补一栏"这次缺了什么"：缺的工具当场装好再收工，缺的模板当场补进模板目录。三场比赛之后，这份清单就收敛成队伍自己的版本，之后每次备赛只剩打勾。

## 5. 赛中：时间管理与题目分级

### 5.1 开赛第一个小时

前 60 分钟的决定影响全场效率，固定动作如下：

| 时段 | 动作 | 产出 |
| ---- | ---- | ---- |
| 0–15 分钟 | 全队读一遍题面列表；RE 主力把全部 RE 题附件下载下来，每题执行 `file` + `strings` 快扫，**单题上限 3 分钟** | 每道题在状态板上有初始分级（5.2） |
| 15–45 分钟 | 按分级认领题目；签到题优先清掉——签到题的分是全场性价比最高的分 | 前两三道低分题入账，队伍进入正循环 |
| 45–60 分钟 | 第一次全员同步：每人 1 分钟报进展与卡点 | 分工调整，无人空转 |

3 分钟快扫不是解题，只是采集分级信号：位数与平台、是否 stripped、strings 里有没有疑似答案、要不要先脱壳。快扫的判断依据就是 [[R08-CrackMe经典题型#1.2 通用分流决策|R08 1.2]] 的分流表，赛前把它打印或贴在状态板里。

### 5.2 题目分级：三个信号

开赛时所有题同时放出，做题顺序用三个信号排：

1. **已解出队数**：平台实时显示每题被多少队解出。==跟着已解出队数走，不跟自己的难度感觉走==——这是 [[R01-逆向工程与CTF竞赛生态导论#7. 平台使用与赛事生态|R01 第 7 节]]"跟着通过率走"的赛时版。解出队数多的题先做，0 解出的题最后碰。
2. **分值走向**：动态积分制下，分值掉得快的题解的人多；初始分特别高（如 500 分起）的题预期难度大，排到最后。
3. **题目名与题面用词**：`easy`、`baby`、`signin`、`warmup` 开头的按签到题对待；题面直接点名技术（VM、control flow flattening、custom architecture）的按长题预期，对应 [[R12-虚拟机保护VM逆向|R12]]、[[R11-代码混淆花指令与OLLVM|R11]] 的工时。

> [!warning] 分级是动态的，每两小时刷新一遍
> 一道 0 解出的题，开赛 6 小时后被 40 支队解出，说明它其实不难——之前的判断错了就更新，别守着第一印象。反方向的例子同样成立：开局人人在做的题突然没人提交了，它多半卡住了全场的某个点，此时读一个 hint 或换条路，还能赶上这题的剩余分值。

### 5.3 卡题止损与 hint 决策

==30 分钟止损规则==：同一道题 30 分钟内没有产生任何新进展——没有新观察、没有新假设、脚本没有向前走一步——就把卡点按 [[R08-CrackMe经典题型#9. 三遍学习法与错题本|R08 第 9 节]]错题本的格式记进状态板，然后换题。规则要提前给自己定好，赛中执行时不讨论"再试五分钟行不行"：换题不是放弃，卡点已记录，晚些回来时往往有新思路；而连续盯一道题的第六到第八个小时，产出通常趋近于零。

> [!note] 止损记录本身是产出
> "卡在哪一步、当时在想什么、试了什么"三条写下来，换题。这三条赛后直接进错题本，也是复盘会（第 8 节）的原始材料。止损规则执行得好的队伍，赛后攒下的卡点清单比解题数更值钱。

hint 决策，读之前先比两组数：

- **hint 的代价**：扣多少分（如本题分值的 10–25%）、有无次数上限。写死在规则里，开赛前读规则时记下。
- **时间的价值**：剩余时间还够做几道别的题。比赛前半段，时间便宜、分值贵，hint 少读；比赛后半段，时间贵、分值相对便宜——一道已投入两小时的题，hint 代价若低于"这段时间本可再做半道中档题"的期望得分，就应读。

简化成两条执行规则：开局 4 小时内不读 hint；比赛剩余不足一半时，对投入已超 1 小时的卡题，评估后该读就读。==hint 是用分数买信息，是正常交易，不是认输==。

另两条全局时间规则：

- **每 2 小时全员同步一次**，超时的卡题当场调度（换人、读 hint、换题）；
- **最后一小时不开新题**，只收尾：提交、核对、写 WriteUp 草稿的收尾。开赛 47 小时才解出的题不值得冒险，提交失败一题的损失比解出一题大。

### 5.4 长赛的排班

48 小时的比赛不需要 48 小时清醒。RE 题量少的时段（通常是深夜）安排轮流休息，每人保证一段完整睡眠；状态板保证交接不断档——睡醒的人先读状态板与队内频道的记录，再接题。8–24 小时的短赛不打瞌睡战术，全程在线，中间定时起来活动。

## 6. 赛中：RE 方向的赛时工作流

RE 题的标准管线七步，每步有固定动作、固定产出与库内模板。赛时按这张表走，不临场发明流程：

| 2 扫字符串 | `strings -t x` 配 `grep` | 提示语、疑似明文答案 | [[R05-静态分析工具链IDA与Ghidra#2.2 strings：提取字符串线索\|R5 2.2]] |

## 7. WriteUp：标准结构与示范

WriteUp 是比赛的可交付产出：对内是复盘素材，对外是队伍记录。一篇合格的 WriteUp 的唯一标准：**陌生人只看这一篇，能从零复现这道题**。

### 7.1 标准结构模板

```markdown
# [比赛名] Reverse - 题名

## 题目信息
比赛名称与年份、方向、分值、解出队伍数、附件清单
（文件名、大小、SHA-256 前几位，方便后来者对上同一个文件）

## 思路
三到五行：这是什么题型、突破口在哪、为什么选这条路。
写"为什么"，不写"做了什么"——做了什么在下一节。

## 完整过程
按第 6 节的管线逐步记录：每条命令配真实输出，
输出用代码块原样贴，中间结论写成一句正文。
脚本给全文，不给片段。

## 复用要点
这道题沉淀了什么可迁移的东西：一个识别特征、一个脚本、一个坑。

## 关联章节
双链到知识库对应章节，方便按题型回溯。
```

### 7.2 合格 WriteUp 的自检清单

- [ ] 只看这一篇能从零复现，不需要问作者任何问题
- [ ] 每条命令可复制执行，每段输出真实来自这条命令
- [ ] 脚本是完整文件（含开头依赖），附运行方式
- [ ] 题目信息完整：比赛、方向、分值，别人检索得到
- [ ] 思路部分回答了"为什么这么想"，而不只是"做了什么"
- [ ] 没有粘贴其他队伍的 flag 或队名（动态 flag 各队不同，贴了也没意义还容易误会）
- [ ] 遵守该比赛的公开政策：多数比赛禁止赛内公开题解，赛后按规则发布

### 7.3 示范 WriteUp：mini_crackme

下面是一篇按模板填好的完整样本。题目是自建练习题（8 字节变换比较型 crackme），作为模板的实填参照——结构、粒度、输出贴法都按 7.2 的清单执行。

---

**# 练习 Reverse - mini_crackme**

**## 题目信息**

自建练习题，方向 Reverse，变换比较型。附件一个：`mini_crackme`（ELF）。目标：找出能让程序认可的 license，license 正确时程序输出 flag，flag 内容包含 license 本身，猜不出来，必须逆推。

**## 思路**

先 strings：只有提示语，没有形似答案的串，排除明文比较型。反汇编 main 读校验循环：一个逐字节"异或后减下标"的变换，与 `.rodata` 里的 8 字节常量表比较。每一步都可逆，走逆变换直接算出 license——题型与 [[R08-CrackMe经典题型#3. 类型二：变换比较型|R8 第 3 节]]的例题同型，差别有两处：下标正序取、变换里是减法不是加法。

**## 完整过程**

第一步，认文件：

```bash
gcc -O0 -fno-pie -no-pie mini_crackme.c -o mini_crackme   # 复现环境：x86-64 Linux
file mini_crackme
```

输出：

```
mini_crackme: ELF 64-bit LSB executable, x86-64, version 1 (SYSV), dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2, BuildID[sha1]=c27e99f3..., not stripped
```

x86-64 ELF，动态链接，未 strip，工具链与调用约定按 [[R03-x86与x64汇编精要复习|R03]] 的基线。

第二步，扫字符串：

```bash
strings -t x mini_crackme | grep -E 'license|wrong|Correct'
```

输出：

```
   2008 .hl4)e"*license: 
   201f wrong length
   202c wrong license
   203a Correct! flag{%s_1s_c0rr3ct}
```

四条串里没有答案，只有提示语与格式串。注意第一行：`license: ` 前面粘着一段可打印字节 `.hl4)e"*`——这是常量表的内容，它不是 C 字符串（没有结尾的 `\0`），strings 扫描时与前后的串连成了一条。

第三步，读校验循环：

```bash
objdump -d -M intel mini_crackme | sed -n '/<main>:/,/^$/p'
```

输出（省略序言、canary 与收尾，只留校验主干）：

```asm
; x86-64 Linux · System V AMD64 ABI · Intel 语法
  401231:  cmp    rax,0x8                      ; strlen(buf) == 8 ?
  401235:  je     401248 <main+0x72>           ; 相等 → 进校验循环
  401237:  mov    edi,0x40201f                 ; "wrong length"
  ……（puts 与 return 1，省略）……
  401251:  mov    eax,DWORD PTR [rbp-0x24]     ; ┐ i
  401254:  cdqe                                ; │
  401256:  movzx  eax,BYTE PTR [rbp+rax*1-0x20] ; │ buf[i]
  40125b:  xor    eax,0x5a                     ; │ ^ 0x5A
  40125e:  mov    edx,eax                      ; │
  401260:  mov    eax,DWORD PTR [rbp-0x24]     ; │ 再取 i
  401263:  sub    edx,eax                      ; │ − i
  401265:  mov    eax,DWORD PTR [rbp-0x24]     ; │
  401268:  cdqe                                ; │
  40126a:  movzx  eax,BYTE PTR [rax+0x402008]  ; │ enc[i]，表在 0x402008
  401271:  cmp    dl,al                        ; │ 只比低 8 位
  401273:  je     401286 <main+0xb0>           ; ┘ 相等 → 下一轮
  401275:  mov    edi,0x40202c                 ; "wrong license"
  ……（puts 与 return 1，省略）……
  401286:  add    DWORD PTR [rbp-0x24],0x1     ; i++
  40128a:  cmp    DWORD PTR [rbp-0x24],0x7     ; i <= 7 ?
  40128e:  jle    401251 <main+0x7b>
```

校验式一句话：`enc[i] == (unsigned char)((buf[i] ^ 0x5A) - i)`，i 取 0 到 7。常数表地址 0x402008，用 [[R05-静态分析工具链IDA与Ghidra#2.4 objdump -s：读取常量表|R05 2.4]] 的方法读出 8 个字节：

```bash
objdump -s -j .rodata mini_crackme
```

输出：

```

mini_crackme:     file format elf64-x86-64

Contents of section .rodata:
 402000 01000200 00000000 2e686c34 2965222a  .........hl4)e"*
 402010 6c696365 6e73653a 20002532 33730077  license: .%23s.w
 402020 726f6e67 206c656e 67746800 77726f6e  rong length.wron
 402030 67206c69 63656e73 6500436f 72726563  g license.Correc
 402040 74212066 6c61677b 25735f31 735f6330  t! flag{%s_1s_c0
 402050 72723363 747d0a00                    rr3ct}..        
```

0x402008 起的 8 字节即常量表：`2E 68 6C 34 29 65 22 2A`（第一行右侧的 `.hl4)e"*`，与 strings 首行对上了）。

第四步，逆变换求解。正变换是先异或 0x5A、再减 i；逆变换按相反顺序撤：先加回 i，再异或 0x5A，每步 `& 0xFF` 对齐比较时的字节截断：

```python
# solve_wu.py —— 由常量表逆推 license：变换是 (input[i] ^ 0x5A) - i
enc = [0x2E, 0x68, 0x6C, 0x34, 0x29, 0x65, 0x22, 0x2A]
key = [0] * 8
for i, e in enumerate(enc):
    key[i] = ((e + i) & 0xFF) ^ 0x5A   # 先加回 i，再异或 0x5A，与正变换顺序相反
print(bytes(key).decode())
```

```bash
python3 solve_wu.py
```

输出：

```
t34mw0rk
```

第五步，喂回程序验证：

```bash
echo aaaaaaaaa | ./mini_crackme
echo aaaaaaaa   | ./mini_crackme
echo t34mw0rk   | ./mini_crackme
```

输出：

```
license: wrong length
license: wrong license
license: Correct! flag{t34mw0rk_1s_c0rr3ct}
```

9 个字节报长度错误，8 个错误字符报校验错误，`t34mw0rk` 通过并输出 flag：`flag{t34mw0rk_1s_c0rr3ct}`。

**## 复用要点**

- 逆变换的顺序口诀（[[R08-CrackMe经典题型#3. 类型二：变换比较型|R08 第 3 节]]立过）：**后做的先撤**。本例正变换是"异或、减 i"，逆过来是"加 i、异或"。
- strings 的扫描单位是"连续可打印字节段"，不认 C 字符串边界：没有 `\0` 结尾的常量表会和相邻字符串连成一条。看到 strings 输出里粘着莫名前缀，那可能就是常量表露头——`-t x` 的偏移配合 `objdump -s` 能直接定位。
- 长度校验（`strlen != 8`）在逆变换之前，先用它确认答案长度，省去对表长度的猜测。

**## 关联章节**

题型与逆变换：[[R08-CrackMe经典题型#3. 类型二：变换比较型|R08 第 3 节]]；命令行分析流程：[[R05-静态分析工具链IDA与Ghidra#2. 命令行最小分析流程|R05 第 2 节]]；汇编读法：[[R03-x86与x64汇编精要复习|R03]]。

## 9. RE 与 PWN 的协同

[[R01-逆向工程与CTF竞赛生态导论#5. CTF 赛制与 Reverse 题型|R1 第 5 节]]说过社区的入门顺序：先逆向、后 PWN，因为 PWN 的每一步以读懂二进制为前提。落到组队协作上，这个关系变成三件具体的事：

**第一，PWN 题的逆向前置。** 一道 PWN 题发下来，附件先过一遍 RE 快扫：什么格式、静态还是动态链接、有没有反调试、输入被程序怎么处理。这五分钟扫描经常替 PWN 队友省半小时——反调试的存在直接改变调试策略（[[R10-反调试与反分析对抗|R10]]），静态链接意味着 libc gadgets 就在程序里（[[P01-PWN导论与缓解机制全景|P1]] 第 6 节的分类表）。

**第二，版本识别是两方向的交界地带。** [[P07-ret2libc-ret2syscall-ret2shellcode|P7]] 的 ret2libc 需要确定 libc 版本，完整操作流程在 [[P03-ELF链接与延迟绑定#6. libc 识别与版本匹配|P3 第 6 节]]；其中用到的功夫正是 RE 侧的基本功——读 ELF 符号与动态段（[[R04-可执行文件格式ELF与PE|R4]]）、用 strings 提取版本指纹并认出特征常数（[[R07-编码与算法识别还原|R7]] 的识别方法论）。PWN 队友卡在"泄露值对不上任何一版 libc"时，RE 主力接手指纹比对往往更快。

**第三，工具互补。** RE 用 GDB 看数据（变量、内存、解密结果），PWN 用 GDB 看布局（栈、偏移、溢出落点），同一个调试器两套问法；P5 的 pwntools 模板反过来供 RE 写本地交互测试脚本用（[[P05-pwntools与GDB插件工具链|P05]]）。两个方向共用一份 gdb 命令文件目录，是性价比最高的共享。

> [!note] 一句话的交接格式
> RE 给 PWN 的逆向交接写三行：输入从哪进（`scanf`/`read`/argv）、进了以后被怎么处理（哪个函数、哪个缓冲区、多大）、期望的触发条件是什么。PWN 给 RE 的反馈写两行：崩溃在哪个地址、当时寄存器被什么覆盖。三行换两行，比"你来看看这道题"高效得多。

## 10. 心态与行为红线

**压力管理**，三条平实的做法：一是把决策交给规则——30 分钟止损、两小时同步、最后一小时不开新题，"现在要不要换题"这类问题在赛中最耗心神，有规则就不用反复权衡；二是卡超过 90 分钟强制换人看一眼，第二双眼睛十分钟常有与自己一小时相当的产出，这不是能力问题，是视角问题；三是首战不设名次目标，目标定在产出——解出几题、写出几篇 WriteUp、复盘会开出几条行动项，这三个数字都只取决于自己的执行，名次还取决于别人。

**行为红线**，比赛期间全部适用：

- **不干扰其他队伍**：不扫描或攻击其他队的平台实例，不利用平台漏洞改分、窥题。
- **不赛外交流答案**：赛内解题讨论限队内；多数比赛明文禁止在公共渠道讨论题目，规则写了就照办，规则没写的按"不损害其他参赛者与平台"执行。
- **不提交他人 flag**：动态 flag 机制（[[R01-逆向工程与CTF竞赛生态导论#6. flag 格式与提交机制|R1 第 6 节]]）使抄袭必然无效且有记录，没有任何收益。
- **WriteUp 按政策公开**：赛内不公开题解是多数比赛的默认要求，赛后发布也以比赛规则为准。
- **合法边界**沿用 [[R01-逆向工程与CTF竞赛生态导论#4. 先划红线：合法边界在哪|R1 第 4 节]]：分析对象限于比赛附件与授权目标，赛后复现也只碰官方公开的题目。

## 11. 常见问题

| 现象 | 原因与解决 |
| ---- | ---- |
| CTFtime 上有比赛，点进去找不到报名入口 | 有的比赛只在 CTFtime 挂日程，报名在其自有平台；以比赛页描述里的官方链接为准（2.3） |
| 比赛时间对不上，差了 8 小时 | 页面显示的是 UTC，未换算本地时间；登录 CTFtime 设时区，或按 2.4 手动 +8 |
| 报名后收不到平台邮件 | 先查垃圾箱；开赛前 24 小时仍无邮件，联系主办方公告里的群或 Discord |
| 队伍凑不齐五个方向 | 按"第一响应人"合并：两人队一人管 RE+Misc、一人管 PWN+Web，Crypto 先用 [[R07-编码与算法识别还原\|R7]] 与 [[R14-自动化分析angr与z3\|R14]] 的工具顶住（3.1） |
| 30 分钟止损执行不了，总想"再试一会" | 把规则贴在状态板顶部；止损要求先记录卡点再换题，记录本身就是产出，执行阻力会小很多（5.3） |
| flag 提错了，怕被扣分 | 先查规则确认扣分政策；之后执行双人确认（3.2 惯例四），一次核对十秒钟，一次错提交可能扣几十分 |
| 想把卡住的题发出去问别人 | 多数比赛禁止赛内公开讨论题解；等赛后按政策发（7.2 清单末条） |
| 本地解出的 flag 和别人题解里的不一样 | 动态 flag 按队伍 token 生成，本队附件里解出的就是本队答案；提别人的必然无效（[[R01-逆向工程与CTF竞赛生态导论#6. flag 格式与提交机制\|R1 第 6 节]]） |
| 赛后没时间开复盘会 | 最小版本：状态板导出，每人写一条卡点，30 分钟结束；产出物照 8.3 归档，会可以短，归档不能省 |
| 首战解出 0 题，要不要继续 | 首战目标本就不是名次：完赛、流程走通、WriteUp 写满两篇，这一场就是成功的；卡点清单进错题本，下一场的分级与止损会顺很多 |

## 12. 配套练习与延伸阅读

> [!note] 实战任务
> **组队报名一场线上赛并完赛，产出 2 篇以上 WriteUp。** 全程按本章执行：CTFtime 按 2.2 的五条标准筛一场 48 小时以上、对新手友好的比赛 → 按 2.3 完成报名与组队 → 赛前一天过完第 4 节的开赛清单 → 赛中执行 5.1 的一小时开局、5.3 的止损规则与第 6 节的管线 → 解出的题按 7.1 的模板当场起草原稿 → 赛后一周内补完至少 2 篇 WriteUp（对照 7.2 自检清单逐项过），并开一次 8.2 议程的复盘会。完赛标准：比赛期间至少解出 1 题、WriteUp 归档、复盘行动项写入开赛清单。以队为单位做完这一轮，本章就完成了它的任务；此后的提高靠场次积累，单场的方法不变。

延伸阅读：

- CTFtime.org 的 Events 与 Teams 功能：选赛、排期与 open team 的第一手来源。
- CTF Wiki（ctf-wiki.org）：按题型组织的赛题知识库，与本章的赛前准备配合使用。
- 各大比赛赛后公开的题目仓库与官方题解：读别人的 WriteUp 学结构与详略取舍，读法照 [[R08-CrackMe经典题型#9. 三遍学习法与错题本|R8 第 9 节]]的第二遍学习法执行。
- [[R16-综合实战案例复盘|R16]]：完整的赛后复盘案例，本章复盘产出物的归档处与参照样本。
