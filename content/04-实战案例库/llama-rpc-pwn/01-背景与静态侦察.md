## 简要介绍

| 名字            |                                                                            |
| ------------- | -------------------------------------------------------------------------- |
| **llama.cpp** | 用 C/C++ 跑 LLM 推理的项目，CPU/GPU 都能跑                                            |
| **ggml**      | llama.cpp 底层的张量库（`ggml_tensor`、后端 `backend`、缓冲区 `buffer`），编译成 `libggml.so` |
| **ggml-rpc**  | 一个后端实现：把算力"外包"给远端机器。客户端在本机，服务端是 `rpc-server`                               |

用法：本机 llama.cpp 用 `--rpc host:port` 指向别的机器，权重和计算被切到远端执行。**服务端只认协议。**

> [!info]- 大模型推理在算什么（30 秒版）
> 大语言模型（LLM）回答问题前要做海量矩阵乘法——把你的输入变成一大片数字，乘上模型文件里存好的几百 GB 权重矩阵。这个"算"的过程叫**推理**。llama.cpp 的卖点是纯 C/C++ 就能跑推理，不依赖大显卡框架。

> [!info]- 张量（tensor）是什么
> 张量就是多维数组：一维是向量，二维是矩阵。神经网络里的权重、输入、中间结果全是各种维度的张量。ggml 管的东西只有三样：张量（`ggml_tensor`）、计算后端（`backend`，CPU 或 GPU）、装张量数据的缓冲区（`buffer`）。

> [!tip]- 为什么必须认识这三个名词
> 分层记：llama.cpp 是**产品**，ggml 是它依赖的**数学库**，ggml-rpc 是 ggml 的一个"可插拔算力来源"。漏洞不在产品层也不在数学层，而在"把算力外包出去"这个功能里——外包就要通信，通信就有协议，协议传了不该传的东西。分析开源项目，先搞清"洞在哪一层"。

> [!info]- 客户端/服务端（C/S）模型
> 发起请求的一边叫**客户端**，等着被连、处理请求的一边叫**服务端**，中间用 **socket**（网络套接字）收发字节流。本题里你写的 Python 攻击脚本是客户端，`rpc-server` 是服务端。安全常识：**永远别信任网络对端发来的数据**——这题的服务端偏偏全信了。

## 协议里传的是"裸指针"

题的根源漏洞在这里。上游序列化结构 `rpc_tensor`（题目 DWARF 里留了源码路径 `/share/llama.cpp/llama-pwn/ggml/src/ggml-rpc.cpp`）：

```c
struct rpc_tensor {
    uint64_t id;
    uint32_t type;
    uint64_t buffer;      // ← 远端 buffer 的"指针"
    uint32_t ne[4];
    uint32_t nb[4];
    ...
    uint64_t data;        // ← 张量数据的"指针"
    char     name[GGML_MAX_NAME];
};
```

客户端把"地址"当数据发给服务端，服务端直接拿它当指针用。上游敢这么写，是因为它的定位是"本地可信环境"：官方文档明确写着 RPC 后端**没有认证/加密**，建议只在内网或 SSH 隧道里跑。

> [!info]- 指针是什么，"裸指针上链路"危险在哪
> 指针就是一个存"内存地址"的变量。`data = 0x555555568030` 的意思是"数据在内存的这个位置"。正常设计里，客户端只该说"我要第 3 号缓冲区从 100 到 200 那段"，服务端查表算出真实地址；而这里客户端直接说"地址就是 0x555555568030"，服务端拿去就解引用。把"地址"当"数据"传，等于把内存钥匙交给了对端。

> [!important]- 这道题的根源
> `EDIT_BUFFER` 是明面上的洞，但真正让利用成立的是"服务端信任客户端"的协议设计——裸指针上链路。只补 `EDIT_BUFFER` 不补协议，洞还在别的地方（完整修复分析见 [[05-复盘与修复#修复建议]]）。

## ggml_backend_buffer：堆上的信息源

运行时 dump 出来的样子（怎么 dump 见 [[04-利用链与EXP#第②步：任意读，dump buffer 结构体|第②步]]）：

```
+0x00  ggml_backend_cpu_buffer_name          ┐
+0x08  ggml_backend_cpu_buffer_free_buffer   │
+0x10  ggml_backend_cpu_buffer_get_base      │  iface 函数指针表
+0x18  0 (init_tensor)                       │  ← 指向 libggml.so 的 .text
+0x20  ggml_backend_cpu_buffer_set_tensor    │
+0x28  ggml_backend_cpu_buffer_get_tensor    │
+0x30  ggml_backend_cpu_buffer_cpy_tensor    │
+0x38  ggml_backend_cpu_buffer_clear         ┘
+0x48  buft   → libggml.so 的 .data
+0x50  context → malloc 出来的数据块  ← free() 的目标，也是我们放命令字符串的地方
+0x58  size   (= 申请大小 + 0x20)
```

> [!info]- 结构体和"+0x50"怎么读
> 结构体是几个变量打包放在一块连续内存里。`+0x50` 表示"从结构体起始地址往后数 0x50（十进制 80）字节"。所以只要知道结构体的**起始地址**，再读它后面 0x50 处的 8 个字节，就拿到了 `context` 成员的值。本题反复做的就是这个动作："dump 结构体，按偏移取成员"。
> 前缀 `+0x00~+0x38` 那 8 个格子都是 8 字节的函数地址，所以每格差 0x08——这能帮你校验偏移表没抄错。

> [!info]- iface：C 语言里的"虚表"
> `iface` 是 interface（接口）的缩写，一张**函数指针表**：8 个格子，每格放一个函数的地址。C++ 类的虚表就是这个玩法。对攻击者它有个妙处：**改掉表里某一格，下次程序"调用接口"时就会调用你填的地址**——不用改代码，改数据就行。本题这 8 格全指向 libggml 的 CPU 后端实现（备用路线里真劫持过它，见 [[05-复盘与修复#其它可行路线]]）。

释放链上两个关键函数（x86-64 Linux，AT&T 语法，System V ABI）：

```asm
; libggml.so 0x95e10  ggml_backend_buffer_free
95e1a: mov 0x8(%rdi),%rax    ; rax = buf->iface.free_buffer
95e26: call *%rax            ; 以 buf 为参数调用它
95e2c: jmp free@plt          ; 再 free(buf) 本身

; libggml.so 0x955f0  ggml_backend_cpu_buffer_free_buffer
955f4: mov 0x50(%rdi),%rdi   ; rdi = buf->context
955f8: jmp free@plt          ; free(context)   ← 就是这里
```

> [!info]- 读这几行汇编
> Linux x86-64 传参按固定顺序进寄存器：第 1 个参数 `rdi`、第 2 个 `rsi`、第 3 个 `rdx`（这套约定叫 System V ABI）。AT&T 语法的 `mov 0x50(%rdi),%rdi` 读作：拿 rdi 里的地址加 0x50，从那取 8 字节放进 rdi——正是"取结构体的 context 成员"。`call *%rax` 是"调用 rax 指的那个地址"，星号表示"间接调用"。本文所有汇编都是这套语法。

`free(context)` 是整条利用链的落点：把命令字符串塞进 context，`free()` 就变成一次"以我们的字符串为参数"的调用。

> [!info]- free() 为什么能"变成别的调用"
> `free(p)` 的原型是 `void free(void *p)`——参数就是那个指针。glibc 的 `free` 开头有几行：先看全局变量 `__free_hook` 有没有被设置，有就调用它、把 `p` 原样当参数传过去（这是给内存调试工具留的口子）。2.31 还留着这个口子，所以 `__free_hook = system` 之后，每次 `free(p)` 实际执行 `system(p)`。详细利用见 [[04-利用链与EXP#第④步：劫持 __free_hook]]。

## file / checksec：版本与保护

```bash
$ file rpc-server
rpc-server: ELF 64-bit LSB pie executable, x86-64, dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2,
            for GNU/Linux 3.2.0, BuildID[sha1]=e563cc16..., with debug_info, not stripped          ← 注意这里

$ file libggml.so
libggml.so: ELF 64-bit LSB shared object, x86-64, dynamically linked, with debug_info, not stripped

$ strings -a libc.so.6 | grep 'GNU C Library'
GNU C Library (Ubuntu GLIBC 2.31-0ubuntu9.18) stable release version 2.31.     ← 版本 2.31

$ checksec --file=rpc-server
RELRO      STACK CANARY  NX        PIE      RPATH  RUNPATH  Symbols  FORTIFY
Full RELRO Canary found  NX enabled PIE enabled No RPATH RUNPATH 164    No

$ checksec --file=libggml.so
Partial RELRO  Canary found  NX enabled  DSO  ...   ← libggml 是 Partial RELRO，GOT 可写
```

> [!tip]- checksec 每一项都在防什么
> - **NX**（数据不可执行）：栈和堆的内存页标成"不许执行"，塞进去的机器码跑不起来 → 攻击者转向复用程序已有代码（ROP）
> - **Canary**（栈金丝雀）：函数返回前检查栈上一个暗号值有没有被改，改了立刻中止 → 拦"写多一点点盖掉返回地址"的溢出
> - **PIE**（位置无关可执行）：程序自身每次加载到随机地址，函数地址不再写死 → 想跳某个函数得先泄漏地址
> - **RELRO**（GOT 只读化）：Full = GOT 加载后设只读，改不了；Partial = 可写。注意它只防"写 GOT"，不防"读 GOT"——Partial RELRO 的 GOT 反而是攻击者的泄漏源
> - **FORTIFY**：编译期把 `memcpy` 等危险函数换成带长度检查的版本
>
> 看到输出就该列"这条路通不通"：本题 NX 开（所以走数据流劫持而不是塞 shellcode）、主程序 PIE（所以从带符号的 libggml 下手）、libggml Partial RELRO（泄漏 libc 就靠它）。

> [!info]- 动态链接与"为什么附件里有一整套 .so"
> 程序里调用的 `malloc`、`memcpy` 不在自己身体里，而在系统的共享库（`.so` 文件）里，运行时由**动态链接器**接上，这叫动态链接。附件把 `libc.so.6`、`libstdc++.so.6`、`ld-linux-x86-64.so.2`（链接器本身）全给你，是因为出题环境是 Ubuntu 20.04 而你的机器库更新。给你全套 = 让你本地 1:1 复刻远程内存布局。

> [!tip]- glibc 版本决定路线
> 2.34 之后 `__free_hook` 被删了。2.31，"`__free_hook = system`" 还在。版本号同时决定整条偏移表能不能用——同一函数在不同版本 libc 里偏移不同，拿 2.35 的偏移打 2.31 必崩。这是侦察阶段最先确认的东西，30 秒都不该省。

> [!info]- 两个 RELRO 读出来的信息
> 主程序 Full RELRO → 别想打 main 的 GOT；`libggml.so` 是 Partial RELRO，`.got.plt` 里存着**已解析好的 libc 地址**——这是泄漏源（不是写目标，写目标用后门直接写内存）。一句话：主程序的防护看一眼就行，攻击面在 libggml。

## nm 与 DWARF

没 strip 的二进制，`nm -C` 直接把 C++ 符号全给你：

```bash
$ nm -C --defined-only libggml.so | grep -E 'rpc_serve_client|rpc_server::|start_rpc_server'
00000000000d1dd4 t rpc_serve_client(ggml_backend*, int, unsigned long, unsigned long)
00000000000d224a T start_rpc_server
00000000000d1c62 T rpc_server::edit_buffer(std::vector<unsigned char, ...> const&)     ← 后门
00000000000d1342 T rpc_server::get_tensor(std::vector<...> const&, std::vector<...>&)  ← 任意读
00000000000d129c T rpc_server::set_tensor(...)                                         ← 被作者打桩
00000000000d0b16 T rpc_server::alloc_buffer(...)
00000000000d0f04 T rpc_server::free_buffer(...)
00000000000d10e0 T rpc_server::deserialize_tensor(ggml_context*, rpc_tensor const*)
```

debug_info 还白送源码路径：

```bash
$ readelf --debug-dump=info libggml.so | grep -m1 ggml-rpc
    <12>   DW_AT_name : (indirect string, offset: 0x1e2f4): /share/llama.cpp/llama-pwn/ggml/src/ggml-rpc.cpp
```

> [!info]- 符号、strip 与 C++ 修饰名
> 符号表是"名字 ↔ 地址"的对照表。发布软件常把它剥掉（strip），剩上万行无名汇编；本题没剥，`0xd1c62` 直接告诉你叫 `rpc_server::edit_buffer`——漏洞函数自己报了名字。
> C++ 允许同名函数（重载），编译器把类名、参数类型编进符号名（**名字修饰** mangling），原始形式像 `_ZN10rpc_server11edit_bufferERKSt6vectorIhSaIhEE`。`nm -C` 的 `-C` 就是翻译回人类可读形式。输出里小写 `t` = 本文件私有，大写 `T` = 全局导出。

> [!info]- DWARF 调试信息是什么
> 编译时加 `-g`，"这行机器码对应源码哪一行、变量什么类型、结构体成员偏移多少"都会记进 ELF 调试段，格式叫 DWARF。对逆向者是宝藏：`readelf --debug-dump=info` 能看到源码路径（上面那条还暴露了出题目录名 `llama-pwn`），`--debug-dump=decodedline` 能把任意地址映射回 `文件:行号`。

> [!tip]- 源码对照读法
> 知道文件名后去 GitHub 找 `llama.cpp` 的 `ggml/src/ggml-rpc.cpp` 对着读，注意挑和 `sizeof(rpc_tensor)==0x128`、enum 顺序一致的版本——开源项目迭代快，选错版本函数差别很大，会浪费很久。源码 + 自己的反汇编互相对照，比纯逆快得多。
> 另外 `readelf --debug-dump=decodedline` 能把地址映射到 `ggml-rpc.cpp:行号`，不确定某个基本块属于哪个 `if` 时很好用。

> [!tip]- 本篇命令速查
> - `file x`：文件类型、架构、是否 strip
> - `strings -a x | grep 词`：翻可打印字符串（`-a` 扫全文件）
> - `checksec --file=x`：保护机制一览
> - `nm -C --defined-only x | grep 词`：列符号（只看本文件定义的）
> - `readelf -r -W x`：重定位表（找 GOT 条目）
> - `readelf --debug-dump=info|decodedline x`：DWARF 信息、地址↔行号
> - `objdump -d -M intel x`：反汇编
