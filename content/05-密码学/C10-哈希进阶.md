## 1. 迭代哈希的内部结构：从压缩函数到海绵

### 1.1 Merkle-Damgård 结构的三个关键词

[[09-密码学基础#4.3 长度扩展攻击（实测）|09 章 4.3]]说过 MD5 与 SHA 系列都是 Merkle-Damgård（MD）结构：切块、逐块滚雪球。把它写成公式只有一行：

$$cv_0 = \text{IV}, \qquad cv_{i+1} = f(cv_i, M_i), \qquad \text{digest} = g(cv_L) \tag{10.1}$$

三个关键词各管一件事：

| 关键词 | 是什么 | 细节 |
| ---- | ---- | ---- |
| IV | 初始链值 $cv_0$ | 固定常数，写死在标准里（MD5 四个字、SHA-1 五个字、SHA-256 八个字） |
| 压缩函数 $f$ | 吃"当前链值 + 一个 512 位分组"，吐出下一个链值 | 真正干搅乱的部分，[[09-密码学基础#4.3 长度扩展攻击（实测）|09 章 4.3]]手写过 SHA-256 版 |
| 填充 | 消息补齐到 512 位的整数倍 | `0x80` + 补零 + 8 字节位长（MD 强化：摘要由内容与长度共同决定），`pad()` 函数见 [[09-密码学基础#4.3 长度扩展攻击（实测）|09 章 4.3]] |

最后一步 $g$ 通常是恒等或简单截断：MD5/SHA-1/SHA-256 直接把全部链值当摘要输出。==摘要就是处理完最后一个分组之后的内部状态，一字不差==——这句话是长度扩展攻击的全部根源：[[09-密码学基础#4.3 长度扩展攻击（实测）|09 章 4.3]]用这个事实伪造过 `SHA256(secret‖msg‖glue‖suffix)` 的签名，[[W17-语言特性与Tricky绕过|W17]] 第 3 节在签名 API 靶上把同一攻击完整打过一遍，本章不再重复，1.3 节会说明 SHA-3 为什么堵住了这条路。

> [!info]- IV 和轮常数从哪来
> MD5 与 SHA 家族的 IV 与轮常数都来自"无magic数字"的惯例：取素数平方根/立方根的小数部分前 32 位。SHA-256 的 8 个 IV 字是前 8 个素数平方根的小数部分，64 个轮常数 K 是前 64 个素数立方根的小数部分；SHA-1 的 IV（`67452301 EFCDAB89 98BADCFE 10325476 C3D2E1F0`）与 MD5 的四个 IV 字同源。设计者用这种办法表明常数不是藏了后门的暗数。

### 1.2 MD5、SHA-1、SHA-256 轮函数对照

三个算法的压缩函数都是同一类形态：32 位字上的"移位 + 异或 + 模加"循环（密码学里叫 ARX 结构），与 [[C05-分组密码内部#1. 两大家族：Feistel 与 SPN|C05 第 1 节]]的分组密码轮函数是亲戚。差别在步数、非线性函数与消息字的处理方式：

| | MD5 | SHA-1 | SHA-256 |
| ---- | ---- | ---- | ---- |
| 分组 | 512 位 | 512 位 | 512 位 |
| 状态字 | 4 个 32 位 | 5 个 32 位 | 8 个 32 位 |
| 步数 | 64 步（4 轮 × 16 步） | 80 步（4 组 × 20 步） | 64 步 |
| 非线性函数 | F/G/H/I 四个，按轮换 | Ch/Parity/Maj 三种，按组换 | Σ0/Σ1、σ0/σ1、Ch、Maj |
| 消息字扩展 | 不扩展：块内 16 个字按固定乱序直接上场 | 16 → 80：`w[i]=rotl1(w[i-3]^w[i-8]^w[i-14]^w[i-16])` | 16 → 64：`w[i]=σ1(w[i-2])+w[i-7]+σ0(w[i-15])+w[i-16]` |
| 字节序 | 消息字按**小端**装载，输出小端 | 大端 | 大端 |
| 摘要 | 128 位（4 字） | 160 位（5 字） | 256 位（8 字） |

三点值得停下来：

- **SHA-1 的消息扩展把低位的差"抖"进高位**：`rotl1` 循环左移让每个原始消息字的影响扩散到后面 64 个扩展字。MD5 没有扩展，每个消息字只用 4 次——这也是 MD5 的差分攻击更容易构造路径的原因之一（3.1 节）；
- **字节序是手写实现的头号坑**：MD5 小端、SHA 大端。09 章与 [[W17-语言特性与Tricky绕过|W17]]的手写 SHA-1 都是按大端解包 `>16I`，换成 MD5 就得用 `<16I`；
- **消息扩展是长度扩展攻击的"帮凶"**：续算时后缀字节进了扩展器，与直接进压缩函数的效果不同——所以续算必须从"块对齐"处开始（[[W17-语言特性与Tricky绕过|W17]] 第 3 节的"对齐长度 64"）。

哈希是纯算术，速度就是攻击者的资源。四个算法的单核速率基准（Python `hashlib`，各 30 万次取平均）：

### 1.3 SHA-3：海绵结构为什么免疫长度扩展

SHA-3（FIPS 202，2015，算法 Keccak）换掉了整个骨架。它不是"压缩函数迭代"，而是**海绵结构**（sponge）：1600 位的大状态分两部分——前 $r$ 位叫 rate（对外），后 $c$ 位叫 capacity（隐藏）。处理流程两步：

1. **吸收**（absorb）：消息切块（SHA3-256 的 $r = 1088$ 位，$c = 512$ 位），每块异或进状态前 $r$ 位，整个 1600 位状态过一个置换 Keccak-f[1600]（24 轮），重复直到消息吸收完；
2. **挤出**（squeeze）：把状态前 $r$ 位输出作为摘要，不够再"过置换 → 再吐 $r$ 位"。

填充是 `pad10*1`（`10…0 1`），再叠加**域分离后缀**：SHA-3 家族附加 `01`，SHAKE 附加 `1111`——同一个置换靠不同的后缀字节分出互不干扰的两个家族（实现里 SHA-3 的首填充字节常写作 `0x06`，SHAKE 写作 `0x1F`）。

长度扩展对它失效的原因就一句话：==MD 家族的摘要等于全部内部状态，海绵的摘要只是挤出相吐出的前若干位，真正携带"处理进度"的 capacity 那一半从未离开过黑盒==。攻击者拿到 256 位摘要，既没有可续滚的状态，也不知道隐藏半区的内容，续算无从谈起。这是"换结构"而不是"加参数"换来的免疫——标准的轮数、位数一个没加。

hashlib 的 API 名有两处容易写错：SHA-3 是 `sha3_256`（下划线），SHAKE 是可变长输出，`digest(长度)` 按需取：

```python
# sha3_api.py —— hashlib 里的 SHA-3 家族：固定长 sha3_* 与可变长 shake_*
import hashlib

m = b"abc"

print("== 固定长输出 ==")
print("sha3_224 :", hashlib.sha3_224(m).hexdigest())
print("sha3_256 :", hashlib.sha3_256(m).hexdigest())
print("sha3_384 :", hashlib.sha3_384(m).hexdigest())
print("sha3_512 :", hashlib.sha3_512(m).hexdigest())
print("摘要字数 :", [hashlib.new("sha3_" + n, m).digest_size for n in ["224", "256", "384", "512"]])

print("\n== 可变长输出 shake ==")
d16 = hashlib.shake_128(m).digest(16)
d32 = hashlib.shake_128(m).digest(32)
d64 = hashlib.shake_128(m).digest(64)
print("digest(16) =", d16.hex())
print("digest(32) =", d32.hex())
print("digest(64) =", d64.hex())
print("长输出以短输出为前缀:", d32.startswith(d16) and d64.startswith(d32))
print("shake_128 与 shake_256 同长输出不同:",
      hashlib.shake_128(m).digest(32) != hashlib.shake_256(m).digest(32))
```

## 2. 生日攻击：从直觉到 48 位碰撞

### 2.1 生日悖论与 √N 界

$n$ 个人里有两人生日相同的概率远超直觉：从 $N = 365$ 个取值里抽 $n$ 次，至少一对相等的概率是

$$P(\text{至少一对}) \approx 1 - e^{-n(n-1)/(2N)} \tag{10.2}$$

令概率过半，解出 $n \approx 1.18\sqrt{N}$。哈希同理：$b$ 位摘要共 $N = 2^b$ 个取值，==任意找一对碰撞（不管是谁撞谁）期望只需要约 $1.18 \cdot 2^{b/2}$ 次哈希==：

$$n_{50\%} \approx 1.18 \cdot \sqrt{2^b} = 1.18 \cdot 2^{b/2} \tag{10.3}$$

"任意一对"三个字是关键——碰撞有三个难度完全不同的版本：

| 目标 | 期望工作量 | 说明 |
| ---- | ---- | ---- |
| 原像：给摘要找输入 | $2^b$ | 单向性防线 |
| 第二原像：给 $m$ 找 $m' \neq m$ 同摘要 | $2^b$ | 签名场景真正的防线 |
| 任意碰撞：找 $m \neq m'$，摘要相同 | $2^{b/2}$ | 本节主题，多目标问题天生便宜 |

生日界是"多选多"的价：候选池越大、可配对的目标越多，价格越低。[[C02-数论进阶与原根|C02]]在离散对数一节里出现过的 BSGS 与 Pollard rho 同样吃这个 $\sqrt{N}$ 界——同一笔账在群结构里叫求对数，在哈希里叫找碰撞。

### 2.2 全量表法：多进程撞 48 位 SHA-1

按式 (10.3)，48 位截断 SHA-1 过半概率需要约 $1.18 \cdot 2^{24} \approx 1980$ 万条摘要。1.2 节测得单核每秒 260 万次，16 个进程并行（`multiprocessing`，每个进程负责一段互不重叠的消息区间）理论上不到一秒。实现选"全量表法"：==把生成的每条摘要全部存下来，排序后找相邻相等项==——排序数组就是那张全量表，内存换时间：

```python
# birthday.py —— 朴素并行生日攻击：截断 SHA-1 到 48 位，多进程全量表法找碰撞
# 方法：每个进程生成一段消息（8 字节计数器），算 SHA-1 取前 6 字节当 48 位摘要；
#       主进程把全部 (摘要, 消息号) 拼进紧凑数组，排序后找相邻相等项——排序数组就是那张"全量表"。
import hashlib
import resource
import time
from multiprocessing import Pool

import numpy as np

BITS = 48

def work(args):
    wid, n, offset = args
    d = np.empty(n, dtype=np.uint64)          # 48 位摘要
    m = np.empty(n, dtype=np.uint32)          # 消息号
    sha1 = hashlib.sha1
    base = offset + wid * n
    for i in range(n):
        nb = (base + i).to_bytes(8, "big")
        d[i] = int.from_bytes(sha1(nb).digest()[:6], "big")
        m[i] = base + i
    return d, m

def main():
    workers, per_worker = 16, 1 << 21         # 16 进程 × 2^21 条 = 2^25 条/轮
    offset = 0
    round_no = 0
    while True:
        round_no += 1
        t0 = time.perf_counter()
        with Pool(workers) as p:
            parts = p.map(work, [(w, per_worker, offset) for w in range(workers)])
        d = np.concatenate([x[0] for x in parts])
        m = np.concatenate([x[1] for x in parts])
        n = len(d)
        exp = n * (n - 1) / 2 / (1 << BITS)   # 理论期望碰撞对数
        order = np.argsort(d, kind="stable")
        ds = d[order]
        eq = np.nonzero(ds[1:] == ds[:-1])[0]
        dt = time.perf_counter() - t0
        print("第 %d 轮: %d 条摘要, 期望碰撞对数 %.2f, 找到 %d 对, 用时 %.1f 秒"
              % (round_no, n, exp, len(eq), dt))
        if len(eq):
            ia, ib = order[eq[0]], order[eq[0] + 1]
            ma = int(m[ia]).to_bytes(8, "big")
            mb = int(m[ib]).to_bytes(8, "big")
            print("消息 A =", ma.hex(), " 完整 SHA-1 =", hashlib.sha1(ma).hexdigest())
            print("消息 B =", mb.hex(), " 完整 SHA-1 =", hashlib.sha1(mb).hexdigest())
            print("48 位截断相等:", hashlib.sha1(ma).digest()[:6] == hashlib.sha1(mb).digest()[:6],
                  " 消息不同:", ma != mb)
            print("共同的截断摘要 =", hashlib.sha1(ma).digest()[:6].hex())
            print("全量表峰值内存 = %.0f MB"
                  % (resource.getrusage(resource.RUSAGE_SELF).ru_maxrss / 1024))
            break
        offset += workers * per_worker

if __name__ == "__main__":
    main()
```


逐项读：

- 第一轮就生成了 $2^{25} = 3355$ 万条，按式 (10.2) 期望有 $\binom{n}{2}/2^{48} \approx 2.00$ 对碰撞，至少找到一对的概率 $1 - e^{-2} \approx 86.5\%$——实际找到 2 对，取第一对；
- 两个 8 字节消息的完整 SHA-1 前六个字节完全相同（`1e76db148f7a`），后半段完全不同：截断后的"碰撞"在完整摘要上不成立，==截断哈希的碰撞攻击只对"按截断位比较"的系统有效==；
- 10.6 秒里大头不是哈希（$2^{25}$ 次 ÷ 每秒约 4000 万次 ≈ 0.8 秒），是排序 3355 万条与进程间传输——全量表法的瓶颈在内存与搬运；
- 峰值 1376 MB：摘要用 `uint64`、消息号用 `uint32` 的紧凑数组（每条 12 字节），已经是"表"的最省形态。

> [!warning] 别用 Python dict 当这张表
> 3355 万条摘要存进 dict（键值各一个 Python int），每条目开销上百字节，要吃掉 4 GB 以上——同样的信息压进 numpy 数组只要约 0.4 GB。==全量表法的工程版本是"紧凑数组 + 排序"，不是字典==。位数再往上（56 位起），内存换时间的路就走不动了，下一小节是另一条路。

### 2.3 Floyd 判圈：常数内存的另一种撞法

把 48 位截断摘要看成映射 $H: [0,2^{48}) \to [0,2^{48})$，从种子 $x_0$ 反复迭代 $x_{k+1} = H(x_k)$。值域有限，序列迟早重复，形状是希腊字母 ρ：一条尾巴（$\mu$ 步）接一个圈（周期 $\lambda$）。**Floyd 判圈**用一快一慢两个指针找相遇点，不需要记住任何历史值；相遇后回退到循环起点 $\mu$ 的两侧，就拿到一对碰撞：

$$H(x_{\mu-1}) = x_\mu = x_{\mu+\lambda} = H(x_{\mu+\lambda-1}), \qquad x_{\mu-1} \neq x_{\mu+\lambda-1} \tag{10.4}$$

种子取 8 字节（值在 $2^{48}$ 之外），保证 $x_0$ 不在映射的像里，即 $\mu \geq 1$、前驱必有两个不同的值：

```python
# floyd.py —— Floyd 判圈：常数内存找 48 位截断 SHA-1 的碰撞
# 把 48 位截断摘要看成映射 H: [0,2^48) -> [0,2^48)，从 x0 反复迭代 x_{k+1} = H(x_k)。
# 迭代序列像一条 rho：先走 mu 步进循环，再以 lam 为周期打转。
# 碰撞对取循环起点两侧的前驱：H(x_{mu-1}) = x_mu = x_{mu+lam} = H(x_{mu+lam-1})，
# 前者在循环外、后者在循环内，必不相同。
# 注意不能直接取相遇点 (i, 2i) 的前驱——Floyd 第一次相遇的 i 必是 lam 的倍数，
# x_{i-1} 与 x_{2i-1} 相差整周期，本来就是同一个值（自撞）。
# 种子 x0 取 8 字节（值在 2^48 之外），保证 x0 不在映射的像空间里，mu >= 1。
import hashlib
import resource
import time

BITS = 48
calls = 0

def H(x: int) -> int:
    global calls
    calls += 1
    return int.from_bytes(hashlib.sha1(x.to_bytes(8, "big")).digest()[:6], "big")

def main():
    x0 = int.from_bytes(b"seed1234", "big")   # > 2^48，在像空间之外
    t0 = time.perf_counter()

    tortoise, hare = H(x0), H(H(x0))
    i = 1
    while tortoise != hare:                    # 相遇点：tortoise 在 i，hare 在 2i
        tortoise = H(tortoise)
        hare = H(H(hare))
        i += 1

    v = tortoise                              # 循环长度 lam：从相遇值走回自身
    lam, h = 1, H(v)
    while h != v:
        h = H(h)
        lam += 1

    t, h2 = x0, v                             # 循环起点 mu：从 x0 与相遇值同步前进
    mu = 0
    while t != h2:
        t = H(t)
        h2 = H(h2)
        mu += 1

    a = b = None                              # 回放：取 x_{mu-1} 与 x_{mu+lam-1}
    x = x0
    for k in range(mu + lam):
        if k == mu - 1:
            a = x
        if k == mu + lam - 1:
            b = x
        x = H(x)
    dt = time.perf_counter() - t0

    print("mu = %d, lam = %d，判圈共 %d 次 SHA-1，用时 %.1f 秒" % (mu, lam, calls, dt))
    print("消息 A =", a.to_bytes(8, "big").hex(), " 完整 SHA-1 =", hashlib.sha1(a.to_bytes(8, "big")).hexdigest())
    print("消息 B =", b.to_bytes(8, "big").hex(), " 完整 SHA-1 =", hashlib.sha1(b.to_bytes(8, "big")).hexdigest())
    print("48 位截断相等:", H(a) == H(b), " 消息不同:", a != b)
    print("共同的截断摘要 =", H(a).to_bytes(6, "big").hex())
    print("峰值内存 = %.1f MB" % (resource.getrusage(resource.RUSAGE_SELF).ru_maxrss / 1024))

if __name__ == "__main__":
    main()
```

> [!warning] 相遇点的前驱是一对"假碰撞"
> 从相遇点 $(i, 2i)$ 直接回退一步取 $x_{i-1}$ 与 $x_{2i-1}$ 当碰撞对，会得到 $a = b$ 的自撞。原因：Floyd 第一次相遇的位置 $i$ 必然是周期 $\lambda$ 的倍数，$x_{i-1}$ 与 $x_{2i-1}$ 恰好相差整圈，本来就是同一个值。==碰撞对必须取在循环起点 $\mu$ 的两侧==——一侧在尾巴上、一侧在圈里，两个前驱才会不同。

### 2.4 两种方法的账与工程意义

把两次 48 位攻击并排放：

| | 全量表法（16 进程） | Floyd 判圈（单进程） |
| ---- | ---- | ---- |
| SHA-1 调用 | 3355 万次 | 1.395 亿次（判圈 3 步 + 回放） |
| 用时 | 10.6 秒 | 63.8 秒 |
| 内存 | 1376 MB | 14.4 MB |
| 输入可控 | ==可控==：消息格式、前缀、区间都能指定 | 不可控：碰撞对是迭代吐出来的，只能收下 |
| 并行 | 天然可分（各进程算各的区间） | 难并行（需要 distinguished points 变体） |

两条路工作量同阶（$2^{b/2}$），取舍在三处：==内存紧张选 Floyd，要求消息形态选全量表，要并行也是全量表顺手==。至于第二原像——给定 $m$ 找同摘要的 $m'$——两条路都帮不上忙，期望仍是 $2^b$：生日界只便宜"多对多"，不便宜"一对一"。

按 1.2 节的单核速率（260 万次/秒）与 16 进程折算，各截断位数过半概率的工作量：

| 截断位数 | 需要的摘要数 $1.18 \cdot 2^{b/2}$ | 单核 | 16 进程 |
| ---- | ---- | ---- | ---- |
| 40 位 | 约 124 万 | 0.5 秒 | 瞬间 |
| 48 位 | 约 1980 万 | 7.6 秒 | 1 秒级（本章 10.6 秒含排序搬运） |
| 56 位 | 约 3.2 亿 | 约 2 分钟 | 约 4 秒 |
| 64 位 | 约 50 亿 | 约 32 分钟 | 约 1 分钟 |

==把摘要截到 64 位以下当"唯一标识"或签名，在今天的算力下等于没有防线==。注意这还是 Python 的成绩——hashcat 一类 GPU 工具每秒数十亿次哈希，64 位以秒计。唯一常见的例外是"猜 token"类攻击：随机 token 被猜中的难度是原像难度 $2^b$，不是碰撞难度，64 位随机串当不记名凭证仍是可接受的（前提是真随机，见 [[C04-随机数攻防|C04]]）；==怕"伪造第二份"的系统（签名、指纹、去重）才怕碰撞==。

## 3. MD5 的碰撞构造：从王氏攻击到 chosen-prefix

### 3.1 王氏攻击与差分路径的直觉

2004 年 8 月，王小云团队在 CRYPTO 2004 的 rump session 上公布 MD5 及另外三个哈希函数的碰撞；2005 年 EUROCRYPT 的论文给出完整方法。此后的开源实现把构造成本从小型机集群压到普通 PC 秒级——[[W17-语言特性与Tricky绕过#2. md5 真碰撞：与 0e 的本质区别|W17 第 2 节]]贴的那对公开字节就是这条线的产物。生日攻击给 MD5 的碰撞下界是 $2^{64}$ 次哈希，结构性攻击把它打穿到秒级——==MD5 的抗碰撞性不是"被算力超过"，是被数学绕过==。

构造的骨架是**差分路径**，步骤三段：

1. **选输入差分** $\Delta M$：规定两个消息在哪些 32 位字上差、差多少。差分选得省"概率"——高位单比特差分最常被选，因为加法进位对高位的扰动小；
2. **排路径脚本**：MD5 的 64 步里，状态差在每一步如何穿过 F/G/H/I 与模加，逐步写死。非线性函数与进位让同样的输入差可以走出多种输出差，每一步都有概率——路径要挑"每步都高概率"的那条；
3. **消息修正**：按路径脚本搜索具体的消息对，发现状态差在哪一步"走岔"，就微调后面的消息字把它拉回脚本。

[[W17-语言特性与Tricky绕过#2. md5 真碰撞：与 0e 的本质区别|W17 第 2 节]]那对公开样本是这条流程的成品：128 字节共 32 个消息字，只有 6 个字不同（字 4、11、14、20、27、30），而且==每处差分都只有一个比特==——四个字差最高位 `0x80000000`，两个字差第 15 位 `0x8000`（MD5 消息字按小端装载，1.2 节对照表的字节序一行在这里兑现）。入口差分极少、极高位，正是"选差分"一步的痕迹；其余 26 个字保持原样，是"消息修正"把整条路径钉死的结果。

### 3.2 chosen-prefix 碰撞：前缀任选的加强版

3.1 的成品有一个使用限制，下一节的实验里会看见：那对字节只在**标准 IV** 下碰撞。真实文件的前面往往有应用规定的头（图片头、证书字段、脚本 shebang），头不归攻击者管——于是需要加强版：**选择前缀碰撞**（chosen-prefix collision）。给任意两个不同的前缀 $P_1 \neq P_2$，现造两个后缀 $S_1, S_2$，使

$$\text{md5}(P_1 \| S_1) = \text{md5}(P_2 \| S_2)$$

它比"随机对"强在哪一目了然：==随机对只能整块塞进文件开头，chosen-prefix 才能把碰撞嵌进"格式合法"的文件里==——两个证书的签发者字段、两个程序的注释头各不相同，照样碰撞。2008 年 CCC 上研究者用它伪造出合法 CA 签发的证书、2012 年 Flame 木马用它伪造微软代码签名证书，这两个案例 [[W17-语言特性与Tricky绕过#2. md5 真碰撞：与 0e 的本质区别|W17 第 2 节]]的折叠框讲过，此处不展开。工具是 Marc Stevens 的 hashclash 项目；最常用的入口 `fastcoll` 的命令形态一行：

```bash
md5collgen -p prefix.bin -o out1.bin out2.bin   # 为给定前缀现造一对碰撞后缀
```

秒级出结果。SHA-1 的进度落后 MD5 一个台阶但方向相同：2017 年 SHAttered 给出前 $2^{63.1}$ 次的（相同前缀）碰撞，2020 年 chosen-prefix 也被做到 $2^{63.4}$——用 SHA-1 做签名的系统（git 对象、旧证书）由此进入"成本可负担"区间。

### 3.3 组装对照：碰撞块在前，不放中间

拿 [[W17-语言特性与Tricky绕过#2. md5 真碰撞：与 0e 的本质区别|W17 第 2 节]] `coll.py` 生成的 `coll_a.bin` / `coll_b.bin`，测两个组装方式。碰撞块放**最前面**，后面接任意相同的自由内容；对照组把正常文本前缀放在碰撞块前面：

```python
# suffixcoll.py —— 公开碰撞对的正确组装方式与失效边界
#   文件 = 碰撞块在前 + 任意相同后缀  → md5 相同（状态已收敛，后续同内容同状态）
#   文件 = 正常前缀在前 + 碰撞块      → md5 不同（公开对只在标准 IV 下碰撞）
import hashlib

block_a = open("coll_a.bin", "rb").read()
block_b = open("coll_b.bin", "rb").read()
tail = ("# Release notes\n"
        "build 2026-10-24, signed artifact\n"
        "approved by: Alice\n").encode()

fa = block_a + tail
fb = block_b + tail
print("== 组装一：碰撞块在前 ==")
print("文件长度 %d 字节，仅开头 128 字节不同，其余相同:" % len(fa), fa[128:] == fb[128:])
print("md5(fa) =", hashlib.md5(fa).hexdigest())
print("md5(fb) =", hashlib.md5(fb).hexdigest())
print("md5 相同:", hashlib.md5(fa).digest() == hashlib.md5(fb).digest())

prefix = b"approved document, rev A\n\n"
pa = prefix + block_a
pb = prefix + block_b
print("\n== 组装二：正常前缀在前 ==")
print("md5(pa) =", hashlib.md5(pa).hexdigest())
print("md5(pb) =", hashlib.md5(pb).hexdigest())
print("md5 相同:", hashlib.md5(pa).digest() == hashlib.md5(pb).digest())
```

组装一成立的原因是式 (10.1) 的直接推论：两块处理完的链值相同，之后的任何相同内容只会走得一样远——==碰撞块之后的自由内容不受限制==，这就是"两个文件内容不同、md5 相同"的标准组装姿势（[[W17-语言特性与Tricky绕过#2. md5 真碰撞：与 0e 的本质区别|W17 第 2 节]]上传靶的通关写法）。组装二失败的原因同样来自 (10.1)：前缀把链值带去了别处，公开碰撞对的路径是从标准 IV 出发排的，起点一换就不收敛。==想让"正常前缀在前"也能碰撞，就必须用 3.2 的 chosen-prefix 工具为该前缀现造一对==——这正是真实攻击（证书伪造）必须用 chosen-prefix 的原因。

## 4. HMAC：把密钥包在两层哈希里

签名与摘要的关系先摆一句话：RSA 签的从来不是消息本身而是它的摘要（C07 RSA 攻击 I 从签名侧展开），==摘要层被攻破，签名层跟着失守==。所以"怎么把密钥和哈希组合成消息认证码（MAC）"是哈希应用里最要紧的一道设计题。

### 4.1 两种朴素构造各自的攻击面

直觉给出的两种拼法，各有一个结构性死穴：

**拼法一 `hash(key ‖ msg)`：长度扩展。** [[09-密码学基础#4.3 长度扩展攻击（实测）|09 章 4.3]]的结论直接适用：摘要就是内部状态，知道 `hash(key‖msg)` 与密钥长度就能续出 `hash(key‖msg‖glue‖suffix)` 的合法签名，密钥全程不用知道。

**拼法二 `hash(msg ‖ key)`：续不动了，但换了两条死法。** 把秘密放尾部，追加后缀会破坏已吸收的输入，长度扩展失效——这一步是对的。剩下两条：

1. **离线爆破密钥**：`(msg, mac)` 对是公开的（报文和签名都在线路上），密钥候选可以离线逐个测试。密钥若来自低熵口令，字典打穿只是时间问题；
2. **碰撞穿透**：若攻击者手上有等长的碰撞对 $H(m_1) = H(m_2)$，那么对**任何**密钥都有 $H(m_1 \| K) = H(m_2 \| K)$——MD 结构下，相同起点、相同长度、相同内容的追加把碰撞原样继承下去。MD5 的碰撞对是现成的（第 3 节），==攻击者根本不需要知道密钥==。

两条都用 3.3 节的碰撞文件验一遍：

```python
# suffixmac.py —— 秘密后缀构造的两条死法与 HMAC 的对照
import hashlib
import hmac

m1 = open("coll_a.bin", "rb").read()
m2 = open("coll_b.bin", "rb").read()
KEY = b"s3cr3t-K3y-16byt"             # 16 字节密钥，攻击者不知道

print("== 碰撞穿透 msg||key 构造 ==")
def suffix_mac(m: bytes) -> str:
    return hashlib.md5(m + KEY).hexdigest()

print("md5(m1||K) =", suffix_mac(m1))
print("md5(m2||K) =", suffix_mac(m2))
print("MAC 相同（伪造成功）:", suffix_mac(m1) == suffix_mac(m2))
print("HMAC 不同（挡住）:",
      hmac.new(KEY, m1, hashlib.md5).digest() != hmac.new(KEY, m2, hashlib.md5).digest())

print("\n== 离线爆破密钥 ==")
msg = b"auth=user1;ts=1792330000"
true_key = b"hunter2"
mac = hashlib.md5(msg + true_key).hexdigest()
print("已知 (msg, mac) 对，mac =", mac)
for cand in [b"123456", b"password", b"dragon", b"hunter2", b"qwerty"]:
    if hashlib.md5(msg + cand).hexdigest() == mac:
        print("字典命中密钥:", cand)
        break
```

密钥从头到尾没有被泄露，`md5(m1‖K)` 与 `md5(m2‖K)` 却逐字节相同——拿到 $m_1$ 的签名，交 $m_2$ 就完成了伪造。同一对消息在 HMAC 下指纹不同，穿透失败。

### 4.2 HMAC 的结构：两层各堵一个洞

HMAC（RFC 2104，1996）的公式一行：

$$\text{HMAC}_K(m) = H\big((K' \oplus \text{opad}) \,\|\, H((K' \oplus \text{ipad}) \| m)\big) \tag{10.5}$$

$K'$ 是把密钥补零（超长先哈希）填到压缩函数块长（64 字节），`ipad = 0x36` 重复 64 字节、`opad = 0x5c` 重复 64 字节。流程画开：

```text
                ┌──────────────── 内层 ───────────────┐   ┌──── 外层 ────┐
m ─────────────►│ (K' xor ipad) → H → 中间摘要（不出门）│──►│ (K' xor opad) │
                └──────────────────────────────────────┘   │ → H → HMAC   │
                                                            └───────────────┘
```

对照 4.1 的攻击清单看它怎么同时堵死两个洞：

- **对长度扩展**：攻击者拿到的只有外层输出。就算把外层摘要当状态续算（外层也是 MD 结构），续出来的仍是外层的"下一个值"，不是任何人认可的 MAC；而真正有续算价值的内层摘要从未离开过黑盒。两个哈希包在一起，==想续哪一层都缺那层的"起点"==；
- **对碰撞穿透**：内层在 $m$ 前面垫了 $K' \oplus \text{ipad}$——公开碰撞对从标准 IV 出发才碰撞（3.3 组装二），垫上未知前缀后路径不收敛，穿透失败（4.1 的输出里 `HMAC 不同`一行）；
- **更深一层**：HMAC 的安全证明（Bellare-Canina-Krawczyk，1996）只要求**压缩函数**像伪随机函数，==不要求哈希函数抗碰撞==。所以 MD5 撞穿之后 HMAC-MD5 也没有被构造出实用伪造——这不是侥幸，是结构带来的降级安全。新设计仍应选 SHA-256 当底座，成本为零。

### 4.3 标准库用法与自造 MAC 的错误形态

```python
# hmac_use.py —— hmac 标准库的正确用法
import hashlib
import hmac

key = b"k3y-2026-10-24"
msg = b"amount=100&to=alice"

mac = hmac.new(key, msg, hashlib.sha256)
print("hmac.new       :", mac.hexdigest())
print("hmac.digest    :", hmac.digest(key, msg, "sha256").hex())   # 一次性函数
print("两种等价       :", mac.digest() == hmac.digest(key, msg, "sha256"))
print("摘要长度       :", mac.digest_size, "块长:", mac.block_size)

recv = mac.hexdigest()
print("compare_digest :", hmac.compare_digest(recv, mac.hexdigest()))
print("篡改检测       :", hmac.compare_digest(recv[:-1] + "0", mac.hexdigest()))

print("\nmd5 底座也合法，但新设计一律选 sha256:",
      hmac.digest(key, msg, "md5").hex())
```

```
md5 底座也合法，但新设计一律选 sha256: b8cbabd1e6965e97b19a37591d4d5e7b
```

校验端用 `hmac.compare_digest`（恒时比较）而不是 `==`：后者逐字节短路返回，签名校验点的耗时泄漏进度，攻击面与 [[R16-综合实战案例复盘#4. 模式三：时间侧信道还原|R16 第 4 节]]的逐字符校验同型。

CTF 与真实代码里自造 MAC 的高频错误形态，对照修正：

| 错误形态 | 死法 | 正确写法 |
| ---- | ---- | ---- |
| `md5(secret + data)` | 长度扩展（[[09-密码学基础#4.3 长度扩展攻击（实测）\|09 章 4.3]]） | `hmac.new` |
| `md5(data + secret)` | 碰撞穿透 + 离线爆破密钥（4.1） | `hmac.new` |
| `==` 比较签名 | 时序侧信道 | `hmac.compare_digest` |
| HMAC 截到 8 字节用 | 64 位摘要，生日 $2^{32}$ 可撞（2.4 节） | 全长输出 |
| 同一密钥多处复用无域分离 | 跨协议重放 | 每个用途派生独立密钥 |
| HMAC 底座选 md5 | 无实用伪造，但升级零成本 | `digestmod=hashlib.sha256` |

"截断 HMAC"一条值得展开半句：截断损失的是碰撞抗性（生日按截断位算），原像抗性还在——当消息去重键用要按 2.4 节的账评估，当认证标签用别低于 128 位。

## 5. CRC32：不是哈希的"哈希"

CRC32 在 CTF 里常被误当哈希用——它也是任意长度输入压成 32 位十六进制串。但它的设计目标是**检测传输误码**，不是对抗对手，数学上与真哈希差着整整一层。

### 5.1 线性性质

CRC 的定义：把消息当 GF(2) 多项式，除以固定的 32 次生成多项式（标准 CRC-32 是 `0x104C11DB7`），取余数。==除法是线性运算==，所以 CRC 继承了 [[C03-序列密码与LFSR|C03]]里 LFSR 的全部线性弱点：无密钥、可逆、差分可叠加。`zlib.crc32` 在标准之上加了初值与终值的异或（这是它与"查表法裸余数"对不上的原因），线性变成仿射——同长消息 $x, y$ 满足：

$$\text{crc32}(x \oplus y) = \text{crc32}(x) \oplus \text{crc32}(y) \oplus \text{crc32}(0^{|x|}) \tag{10.6}$$

多出来的第三项是全零消息的 CRC（仿射常数）。验证一遍：

```python
# crc_lin.py —— CRC32 的仿射线性：同长消息上差值可叠加
import zlib

a, b = b"attack", b"atdawn"
L = len(a)
ab = bytes(x ^ y for x, y in zip(a, b))
z = b"\x00" * L

print("crc32(a)          =", format(zlib.crc32(a), "08x"))
print("crc32(b)          =", format(zlib.crc32(b), "08x"))
print("crc32(a^b)        =", format(zlib.crc32(ab), "08x"))
print("校正项 crc32(0^L) =", format(zlib.crc32(z), "08x"))
print("恒等式成立:",
      zlib.crc32(ab) == zlib.crc32(a) ^ zlib.crc32(b) ^ zlib.crc32(z))

# 同一消息上，翻动内容引起的 crc 变化与翻动的差分线性相关（5.2 伪造攻击的地基）
m = b"user: guest;note: AAAA;tail"
def patched(pos, delta):
    x = bytearray(m)
    for i, d in enumerate(delta):
        x[pos + i] ^= d
    return zlib.crc32(bytes(x))

d1 = bytes([0xFF, 0x00, 0x00, 0x00])
d2 = bytes([0x00, 0xFF, 0x00, 0x00])
both = bytes(x ^ y for x, y in zip(d1, d2))
print("两次翻动叠加 == 一次叠加翻动:",
      patched(6, both) ^ zlib.crc32(m) ==
      (patched(6, d1) ^ zlib.crc32(m)) ^ (patched(6, d2) ^ zlib.crc32(m)))
```


```
crc32(b)          = 491d597e
crc32(a^b)        = bf1fd5e6
校正项 crc32(0^L) = b1c2a1a3
恒等式成立: True
两次翻动叠加 == 一次叠加翻动: True
```

第二段验证的是伪造攻击的地基：==对消息的异或差分与对 CRC 的变化量之间是线性映射==。32 位输出、线性映射，意味着"指定任意变化量、反解所需差分"是一节线性代数作业——5.2 节把它做成攻击。

### 5.2 伪造：修补 CRC 打穿校验靶

**靶子**（7101 端口）：接收一个许可证文件，格式是头部字节加一行 `crc32: xxxxxxxx`（CRC 覆盖头部）。校验逻辑：CRC 对得上才继续，`user: admin` 给 flag：

```python
# crc_server.py —— CRC32 校验靶（7101）：
#   POST /check 上传许可证文件；文件 = 头部字节 + "crc32: xxxxxxxx\n"
#   头部 CRC32 与存储值一致才通过；user: admin 给 flag
import zlib
from http.server import BaseHTTPRequestHandler, HTTPServer

FLAG = "flag{crc_n0t_h4sh}"

class H(BaseHTTPRequestHandler):
    def _send(self, text: str):
        body = text.encode()
        self.send_response(200)
        self.send_header("Content-Type", "text/plain; charset=utf-8")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)

    def do_POST(self):
        n = int(self.headers.get("Content-Length", 0))
        raw = self.rfile.read(n)
        idx = raw.rfind(b"crc32: ")
        if idx < 0:
            self._send("no crc line")
            return
        data, crcline = raw[:idx], raw[idx + 7:idx + 15]
        stored = int(crcline, 16)
        if zlib.crc32(data) != stored:
            self._send("crc mismatch: stored %08x, computed %08x"
                       % (stored, zlib.crc32(data)))
            return
        if b"user: admin" in data:
            self._send(FLAG)
        else:
            self._send("crc ok, but user=guest")

    def log_message(self, *a):
        pass

HTTPServer(("127.0.0.1", 7101), H).serve_forever()
```

**攻击**：把 `guest` 改成 `admin`（5 字节差），CRC 变化量是固定的；note 字段留了 4 个可改字节——CRC 是 32 位，4 个字节的异或差恰好张满 32 维。5.1 已证"内容异或差 → CRC 变化量"是线性映射，令 $\text{col}_k$ 为对 note 字段异或单比特 $2^k$ 引起的 CRC 变化量，则求补丁 $x \in \{0,1\}^{32}$ 就是一节方程：

$$\bigoplus_{k:\,x_k=1} \text{col}_k = \text{crc32}(\text{改后}) \oplus \text{crc32}(\text{原}) \tag{10.7}$$

32 个未知数、32 个 GF(2) 方程，高斯消元求解：

```python
# crc_forge.py —— CRC32 伪造：内容 guest→admin（5 字节变化），
# 在 note 字段解 32x32 GF(2) 方程求一个 4 字节异或补丁，把 CRC 修补回原值。
# 关键语义：补丁是"异或差"——把 note 的 4 字节 ^= patch。CRC 变化量对这个异或差是线性的。
import zlib

raw = open("license.txt", "rb").read()
idx = raw.rfind(b"crc32: ")
body = raw[:idx]
stored = int(raw[idx + 7:idx + 15], 16)
assert zlib.crc32(body) == stored
print("原头部 %d 字节, crc32 = %08x" % (len(body), stored))

tampered = body.replace(b"user: guest", b"user: admin")
target = zlib.crc32(tampered) ^ zlib.crc32(body)     # 需要补丁抵消的变化量
q = body.index(b"note: ") + 6                        # 补丁落点：note 字段的 4 字节
print("改动引起的 crc 变化 = %08x，补丁位置 = %d" % (target, q))

def xor_patch_delta(delta_int: int) -> int:         # 对 note 字段异或 delta 后的 crc 变化量
    probe = bytearray(body)
    for i, b in enumerate(delta_int.to_bytes(4, "big")):
        probe[q + i] ^= b
    return zlib.crc32(bytes(probe)) ^ zlib.crc32(body)

cols = [xor_patch_delta(1 << k) for k in range(32)]  # 32 列：单个异或位引起的变化

rows = []                                            # GF(2) 高斯消元：32 行 x 33 列
for j in range(32):
    rows.append([(cols[k] >> j) & 1 for k in range(32)] + [(target >> j) & 1])
where, r = [-1] * 32, 0
for c in range(32):
    sel = next((i for i in range(r, 32) if rows[i][c]), None)
    if sel is None:
        continue
    rows[r], rows[sel] = rows[sel], rows[r]
    for i in range(32):
        if i != r and rows[i][c]:
            rows[i] = [x ^ y for x, y in zip(rows[i], rows[r])]
    where[c], r = r, r + 1
assert r == 32, "矩阵不满秩，换补丁位置"
patch = 0
for c in range(32):
    if rows[where[c]][32]:
        patch |= 1 << c

forged = bytearray(tampered)
for i, b in enumerate(patch.to_bytes(4, "big")):
    forged[q + i] ^= b
assert zlib.crc32(bytes(forged)) == stored, "修补失败"
print("解得 4 字节异或补丁 =", patch.to_bytes(4, "big").hex(),
      " 修补后 crc32 = %08x（等于原值）" % zlib.crc32(bytes(forged)))

open("tampered_nopatch.bin", "wb").write(tampered + raw[idx:])
open("forged.bin", "wb").write(bytes(forged) + raw[idx:])
print("已写 tampered_nopatch.bin / forged.bin")
```


```
改动引起的 crc 变化 = 1a2ff28b，补丁位置 = 42
解得 4 字节异或补丁 = 131b0747  修补后 crc32 = ecef8511（等于原值）
已写 tampered_nopatch.bin / forged.bin
```

> [!warning] 补丁的语义是"异或差"，不是"覆写"
> 构造线性方程的探针必须用 `^=` 把单比特异或进 note 字段。若探针直接把 note 字节**覆写**成探针值，得到的映射是仿射的而非线性的——差一个"原字节串"的常数项，按线性解出的补丁必然修不回去（解出的方程与真实变化量恰好差一个常向量）。检验方法：拿随机差分抽查"两次翻动叠加是否等于一次叠加翻动"（5.1 脚本第二段就是这么做的）。

另一个边界：改动位置与补丁位置的组合若让 32 列矩阵不满秩（比如两个位置相距恰好使线性映射退化），解不唯一或无解——换一个补丁落点再解即可。CRC64 同理，方程规模换 64。

### 5.3 与真哈希的对照

| | CRC32 | 真哈希（MD5/SHA 家族） |
| ---- | ---- | ---- |
| 输出 | 32 位 | 128–256 位 |
| 结构 | 多项式除法，线性（仿射） | 压缩函数迭代，雪崩 |
| 抗伪造 | ==无==：差分方程直接解出篡改 | 单向性 + 雪崩 |
| 抗碰撞 | 无（任意指定内容对都能修补） | 生日 $2^{n/2}$（MD5 已被结构性攻破） |
| 密钥 | 无，谁都能算 | 可组成 HMAC |
| 设计目标 | 检测随机误码 | 抵抗人为篡改 |

一句话分工：==CRC 管"坏了没有"，哈希管"改没改过"，HMAC 管"改没改过 + 是不是熟人改的"==。看到文件格式用 CRC32 做"完整性校验"，它防的只是传输误码。

## 6. 哈希的应用形态：PoW、爆破与口令存储

### 6.1 工作量证明：挖一个 20 位难度的块

工作量证明（Proof of Work）把哈希的"单向 + 雪崩"反过来用：找一个 nonce，使 $\text{sha256}(\text{header} \| \text{nonce})$ 的前导零达到难度要求。前导零没法构造，只能逐个试，每次成功概率 $2^{-d}$（$d$ 为零位数），期望 $2^d$ 次——==难度每加 1 位，工作量翻倍==。比特币的难度目标（摘要小于某个阈值）就是"前导零"的推广。

```python
# pow.py —— 工作量证明：多进程挖一个 20 位难度的块
# 难度：sha256("C10-block" || 8 字节 nonce) 的前 20 位全零；各进程 nonce 区间不重叠
import hashlib
import time
from multiprocessing import Pool

BITS = 20

def mine(wid):
    base = wid << 36                       # 每个 worker 占 2^36 个 nonce 的互斥区间
    n = 0
    while True:
        nb = (base + n).to_bytes(8, "big")
        h = hashlib.sha256(b"C10-block" + nb).digest()
        if h[0] == 0 and h[1] == 0 and h[2] < 16:
            return nb, h, base + n, n + 1
        n += 1

def main():
    t0 = time.perf_counter()
    with Pool(16) as p:
        results = p.map(mine, range(16))
    nb, h, nonce, tries = min(results, key=lambda r: r[1])
    print("命中 nonce =", nonce.to_bytes(8, "big").hex(), "(%d)" % nonce)
    print("区块摘要   =", h.hex())
    print("前 20 位为 0:", h[0] == 0 and h[1] == 0 and h[2] < 16)
    print("16 个进程合计尝试 %d 次（每个进程独立找块，合计期望 16×2^20 = %d）"
          % (sum(r[3] for r in results), 16 << BITS))
    print("用时 %.1f 秒" % (time.perf_counter() - t0))

if __name__ == "__main__":
    main()
```

```bash
python3 pow.py
```

输出：

```
命中 nonce = 000000c0001ae8dc (824635484380)
区块摘要   = 0000012f298b051edfc5c185d171c1e3733ab25c81db81f8682e3707b7acc133
前 20 位为 0: True
16 个进程合计尝试 24974718 次（每个进程独立找块，合计期望 16×2^20 = 16777216）
用时 2.3 秒
```

合计 2497 万次落在期望 1678 万次的波动范围内（几何分布叠加）。20 位只要 2.3 秒；按本次的合计速率折算，32 位要 16 × $2^{32}$ ≈ 688 亿次，同一台机器约 1.7 小时——PoW 的安全账与生日攻击的账是同一套乘法，只是目标从"相等"换成了"小于"。

### 6.2 字典爆破：john 的定位与小字典攻击

### 6.3 加盐与慢哈希

字典与彩虹表的共同前提是"哈希一次就能验证一个候选"。防御就是把"一次"变贵，两步：

- **加盐**：存储 `hash(salt ‖ password)`，盐是每用户随机的公开值。==盐不保密，它废掉的是预计算==——彩虹表必须为每个盐重算，成本回到逐用户爆破。5 个哈希 5 个盐（或如 6.2 的 `$1$` 自带盐），批量预计算就失去意义；
- **换慢哈希**：MD5/SHA-256 的设计目标是快（1.2 节每秒数百万次），这正是爆破者的资源。口令存储要用**故意慢**的算法：bcrypt（代价因子）、scrypt（额外吃内存，GPU 并行优势被压）、argon2（2015 年口令哈希竞赛冠军）。标准库自带 scrypt：

```python
# slowhash.py —— 快哈希与慢哈希：sha256 vs scrypt
import hashlib
import time

pw = b"correct horse battery staple"
salt = b"deadbeef-20261024"

t0 = time.perf_counter()
N = 200000
for _ in range(N):
    hashlib.sha256(salt + pw).digest()
t1 = time.perf_counter()
h = hashlib.scrypt(pw, salt=salt, n=2 ** 14, r=8, p=1, dklen=32)
t2 = time.perf_counter()

print("sha256  : %d 次共 %.3f 秒，单次 %.1f 微秒" % (N, t1 - t0, (t1 - t0) / N * 1e6))
print("scrypt  : n=2^14 单次 %.0f 毫秒" % ((t2 - t1) * 1e3))
print("慢了约 %.0f 倍" % ((t2 - t1) / ((t1 - t0) / N)))
print("scrypt 摘要 =", h.hex())
```

```
scrypt  : n=2^14 单次 33 毫秒

scrypt 摘要 = ac2abc29a19d29a3eaa751eceb671d4c6c16324cf876af3ae7ec161e82c9ae83
```

10 万倍的单次成本差：sha256 字典一秒试 300 万个，scrypt 一秒 30 个。bcrypt 与 argon2 标准库里没有（pycryptodome 也不含），`pip install bcrypt` 或 `pip install argon2-cffi` 一行装齐。验证端慢是特性不是缺陷——登录每分钟没几次，爆破每秒几十万次，代价只落在攻击者头上。

## 7. 常见问题

| 现象 | 原因与解决 |
| ---- | ---- |
| 生日攻击用 dict 当表，几十位就爆内存 | Python 字典每条目开销上百字节；换 numpy 紧凑数组（uint64 摘要 + uint32 编号）加排序，48 位约 0.4 GB（[[#2.2 全量表法：多进程撞 48 位 SHA-1\|2.2]]） |
| 截断位数选太高，脚本跑到天荒地老 | 先按 `1.18·2^(b/2)` 与测得速率算期望时间再定难度；Python 多进程的舒适上限是 48 位左右，56 位以上换 GPU 工具或换 Floyd 变体（[[#2.4 两种方法的账与工程意义\|2.4]]） |
| 生日攻击多轮重跑总找到同一对 | 每轮生成区间要换偏移，别在同一个消息空间里重复抽（[[#2.2 全量表法：多进程撞 48 位 SHA-1\|2.2]] 的 `offset`） |
| Floyd 判圈回退取到的"碰撞对" a == b | 相遇位置必是周期 λ 的倍数，相遇点前驱相差整圈本来就是同值；碰撞对取循环起点 μ 两侧（[[#2.3 Floyd 判圈：常数内存的另一种撞法\|2.3]] 的 warning） |
| 公开 md5 碰撞对拼上前缀后不碰撞 | 公开对只在标准 IV 下成立：碰撞块放文件最前、自由内容放后面；要前缀任选用 chosen-prefix 工具现造（[[#3.3 组装对照：碰撞块在前，不放中间\|3.3]]） |
| CRC 修补解出的补丁修不回原值 | 探针用了覆写而不是异或，映射成了仿射、差一个常数项；补丁语义必须是异或差，先用随机差分抽查线性（[[#5.2 伪造：修补 CRC 打穿校验靶\|5.2]] 的 warning） |
| CRC 补丁方程无解或不满秩 | 改动位置与补丁位置的组合让 32 列矩阵退化；换一个补丁落点再解（[[#5.2 伪造：修补 CRC 打穿校验靶\|5.2]]） |
| `zlib.crc32` 与查表法/在线工具对不上 | zlib 版含初值与终值异或；线性恒等式要带校正项 `crc32(0…0)`（[[#5.1 线性性质\|5.1]] 的式 10.6） |
| 手拼 `md5(key+msg)` 与服务端 HMAC 对不上 | 一个是裸拼、一个是标准双层结构，本来就不相等；全链路统一 `hmac.new`（[[#4.3 标准库用法与自造 MAC 的错误形态\|4.3]]） |
| 找不到 `hashlib.sha_256` / `sha3-256` | 名字是 `sha3_256`（下划线）；可变长用 `shake_128/256` 的 `.digest(长度)`（[[#1.3 SHA-3：海绵结构为什么免疫长度扩展\|1.3]]） |
| shake 取不同长度怀疑实现错了 | 同种子长输出以短输出为前缀，属正常；要互不相关换 seed 或换 shake_256（[[#1.3 SHA-3：海绵结构为什么免疫长度扩展\|1.3]]） |
| 裸 hex 哈希被 john 识别成 LM，0 命中 | 自动识别猜错加 core 版没有 Raw-MD5 动态格式；显式 `--format`，或用 `$1$` 带盐格式（[[#6.2 字典爆破：john 的定位与小字典攻击\|6.2]]） |
| scrypt 报 memory limit / `OSERROR` | `n·r` 超过 OpenSSL 默认上限；调小 n 或传 `maxmem`（[[#6.3 加盐与慢哈希\|6.3]]） |

## 8. 配套练习与延伸阅读

配套练习：

1. 把 `birthday.py` 的 `BITS` 改成 40、44、52，记录时间与内存；核对"每加 4 位，时间 ×4、内存 ×4"的预测，再用 2.4 节的表外推 56 位需要多少内存。
2. 给 Floyd 写 distinguished points 多进程版：每进程从不同种子出发，遇到"低 $k$ 位全零"的 distinguished point 就上报；对比全量表法的碰撞对质量与总耗时。
3. 把 [[W17-语言特性与Tricky绕过|W17]] 第 3 节签名靶的 `sign()` 改成 `md5(data + secret)`（秘密后缀），先打碰撞穿透（本章 4.1），再用 hashpumpy 试长度扩展并解释它为什么失效。
4. 给 5.2 的许可证文件加一个 `len: N` 字段并入 CRC 覆盖范围，重写伪造脚本；再把靶子换成 CRC64，评估方程规模与求解成本的变化。
5. PoW 难度从 20 位逐级升到 26 位，画"难度-用时"曲线；按曲线外推 30 位在 16 进程下的耗时，再跑一遍校准。
6. 用 `hashlib.scrypt`（每用户独立盐）搭一个小型口令存储，把同一份字典分别对"裸 sha256"与"scrypt 版"跑一遍，记录两条时间线的差距。

延伸阅读：

- FIPS 180-4（SHA-1/SHA-2 标准文本）与 FIPS 202（SHA-3/SHAKE）：1.1–1.3 节全部结构细节与填充定义的出处；
- RFC 2104（HMAC）：ipad/opad 取值与两轮结构的原始定义，配 Bellare-Canina-Krawczyk 的安全证明论文（检索 "HMAC: Keyed-Hashing for Message Authentication"）；
- Wang 与 Yu，*How to Break MD5 and Other Hash Functions*（EUROCRYPT 2005）：差分路径与消息修正的原始论文，3.1 节的直觉版对照读；
- Marc Stevens 的 hashclash 项目页与 fastcoll 源码：chosen-prefix 碰撞生成器；shattered.io 是 SHA-1 首个公开碰撞的官方页（两文件可直接下载对比）；
- Ross Williams，*A Painless Guide to CRC Error Detection Algorithms*：CRC 的多项式视角与全部变体参数表，5.1 节仿射常数的完整推导可在此补齐；
- 下一站：RSA 签的摘要在这一章被拆到了轮函数层，签名侧的对应攻击（伪造签名、PKCS#1 v1.5 编码）由 C07（RSA 攻击 I）展开；带密钥完整性的工程形态（AEAD、Encrypt-then-MAC）已在 [[C06-分组模式攻击全集#6.2 AES-GCM 的正确用法|C06 6.2]] 见过 HMAC 的表亲。书单与课程见 [[02-书单与Wiki|书单与 Wiki]]，hashcat/john/fastcoll 的工具条目见 [[03-工具清单|工具清单]]。
