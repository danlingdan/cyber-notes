## 1. 侧信道模型：黑盒之外的多说一句

前面的章节都在"数学面"上做攻击：拿到算法的输入与输出（密文、签名、摘要、参数），利用体制弱点或参数事故反推密钥——[[09-密码学基础|09 章]]第 5 节的 RSA 套路、[[C06-分组模式攻击全集|C06]] 的模式滥用、[[C07-RSA攻击I|C07]] 到 [[C09-RSA攻击III|C09]] 的参数与 oracle，全是这个模型。模型有一个共同前提：==算法是一个黑盒，攻击者能观测的只有输入和输出==。

真实实现不满足这个前提。密码学在程序里运行，程序跑在硬件上，中间每一层都带着超出输入输出的可观测量：一次请求的处理耗时、一次解密失败的报错内容、一块芯片的功耗曲线、一条缓存行的访问时间。这些"多出来的信号"叫**侧信道**（side channel）——算法之外的第二条信息通道。Kocher 在 CRYPTO '98 的论文第一次系统展示了它：只观测私钥运算的耗时，就能恢复 RSA 的指数。从那以后，==实现泄漏成为与数学弱点并列的一整类攻击面==。

CTF 里可操作的泄漏面按获取成本排一张表：

| 泄漏面 | 观测内容 | CTF 可操作性 | 出处 |
| ---- | ---- | ---- | ---- |
| 报错内容 | 响应体、状态码区分失败类型 | 高：一个 HTTP 客户端就够 | [[C06-分组模式攻击全集\|C06]]、[[C09-RSA攻击III\|C09]] |
| 响应时间 | 耗时随内部执行路径变化 | 高：一个带计时的客户端就够 | 本章第 2、3、5 节 |
| 响应长度与字段 | 错误页字节数、字段有无的差异 | 中：与报错内容同源 | [[C06-分组模式攻击全集\|C06]] 第 5 节 |
| 缓存 | 共享内存的访问时序 | 低：需要同机与共享库 | 本章第 6 节 |
| 功耗 / 电磁 | 示波器量测物理量 | 低：需要硬件 | 本章第 6 节 |

分工一句话：**报错类**侧信道的方法论已经两次打样——[[C06-分组模式攻击全集|C06]] 第 2 节的 padding oracle 与 [[C09-RSA攻击III|C09]] 第 5、6 节的 Bleichenbacher/Manger；**故障类**的 RSA-CRT 单故障分解也在 [[C09-RSA攻击III|C09]] 第 4 节完整做过。本章负责剩下的一大类：**时间**，以及跨算法通用的实现问题（比较逻辑、组合顺序、盲化、防御清单）。

时间为什么会泄漏？==只要代码的执行路径、循环次数或访问的内存位置取决于秘密数据，耗时就成了秘密的函数==。把一次校验的耗时写成最简模型：

$$T(\text{请求}) \approx T_{\text{固定}} + n_{\text{match}} \cdot t_b \tag{15.1}$$

$n_{\text{match}}$ 是请求里"碰对了"的字节数，$t_b$ 是每碰对一个字节的边际开销，$T_{\text{固定}}$ 是与内容无关的固定成本。模型看着平凡，攻击力全在 "$n_{\text{match}}$ 可以被逐位逼近" 上——第 2 节打穿的就是它。

> [!warning] 威胁边界：本章的靶全部自建
> 侧信道方法本身中立，但对**别人的**服务做计时测量、报错探测属于未授权访问。本章所有靶都监听在本机回环地址上，练习与比赛也只在题目环境里做。把方法用在自建靶与赛题上，是这套技术的全部合法范围。

## 2. 逐字节比较的时序泄漏

### 2.1 漏洞形态：提前返回

逐字节比较加提前返回，是时序泄漏里最常见、也最容易写出来的形态：

```python
def verify(token: bytes) -> bool:
    for i in range(len(secret)):
        if token[i] != secret[i]:
            return False          # 第一处不等立即返回
    return True
```

提前返回把"比较进行到第几轮"变成了==正确前缀长度的函数==：候选的第 0 字节错，循环跑 1 轮；前 7 字节对，循环跑 8 轮。结合式 (15.1)，每个位置的最优候选就是让耗时最长的那个：

$$\hat{b}_p \;=\; \arg\max_{b \,\in\, \{0,\dots,255\}} \; \hat{T}\big(\text{已知前缀} \,\|\, b \,\|\, \text{填充}\big) \tag{15.2}$$

$\hat{T}$ 是对耗时 $T$ 的统计估计（怎么估计是第 3 节的主角），填充字节补齐长度、不参与匹配。从位置 0 恢复到位置 11，12 字节就逐位拼出来了。这个套路与 [[C06-分组模式攻击全集|C06]] 第 2 节的 padding oracle 是同一个思想的两个载体：==oracle 的成立条件是"失败类型可区分"，至于是写在响应体里还是写在响应时间里，不改变攻击结构==——第 2.2 节的靶连报错都是统一的，可区分性全在时间轴上。

### 2.2 自建 HTTP 靶

靶由两个文件组成。第一个是共用模块：一个服务端持有的会话 MAC，和那份"逐字节提前返回"的校验实现。纯粹的逐字节比较每个字节只有十几纳秒（2.4 节的输出会量出来），放到网络尺度上不可见；所以靶给每个匹配字节加了 0.5 毫秒的**模拟开销**，代表"每个字节有真实工作"的实现——解析、查表、密码运算。这也是多数时序题靶的出题形态：出题人把信号做到可测，考的是攻击者的统计与脚本功力。

```python
# maccheck.py —— 会话 MAC 与逐字节提前返回的校验
import hmac
import time
from hashlib import sha256

# 会话 MAC：服务端持有，攻击者不可见。确定性生成，便于输出对账。
TOKEN = hmac.new(b"c15-demo-key/7600", b"session=sid-20261024", sha256).digest()[:12]
TLEN = len(TOKEN)                          # 12 字节
BYTE_COST_NS = 500_000                     # 每匹配一个字节的模拟开销：0.5 ms

def verify(token: bytes) -> bool:
    """漏洞形态：逐字节比较，第一处不等立即返回"""
    if len(token) != TLEN:
        return False
    for i in range(TLEN):
        if token[i] != TOKEN[i]:
            return False
        t_end = time.perf_counter_ns() + BYTE_COST_NS   # 模拟每字节的校验开销
        while time.perf_counter_ns() < t_end:
            pass
    return True

def verify_ct(token: bytes) -> bool:
    """修复形态：hmac.compare_digest + 固定总耗时（统一失败路径）"""
    ok = hmac.compare_digest(token, TOKEN)
    t_end = time.perf_counter_ns() + TLEN * BYTE_COST_NS
    while time.perf_counter_ns() < t_end:
        pass
    return ok
```

第二个是 HTTP 服务：`POST /verify` 收一个 hex token，返回 `{"ok": true/false}`：

```python
# t2_timing_server.py —— 时序 oracle 靶：POST /verify {"token": "<hex>"}
import json
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

import maccheck

class Handler(BaseHTTPRequestHandler):
    protocol_version = "HTTP/1.1"
    disable_nagle_algorithm = True         # 连接上直接开 TCP_NODELAY

    def log_message(self, *args):          # 关掉逐请求访问日志
        pass

    def _json(self, obj):
        body = json.dumps(obj).encode()
        # 头与体拼成一个缓冲一次写出：分两次写会撞上 Nagle × delayed ACK，
        # 每个请求多出约 40 ms 的固定底噪，把毫秒级时序信号整个淹没
        payload = (b"HTTP/1.1 200 OK\r\nContent-Type: application/json\r\n"
                   b"Content-Length: " + str(len(body)).encode() + b"\r\n\r\n" + body)
        self.wfile.write(payload)

    def do_GET(self):
        self._json({"hint": "POST /verify {\"token\": \"<hex>\"}"})

    def do_POST(self):
        n = int(self.headers.get("Content-Length", 0))
        req = json.loads(self.rfile.read(n))
        try:
            raw = bytes.fromhex(req["token"])
        except ValueError:
            raw = b""
        self._json({"ok": maccheck.verify(raw)})

class Server(ThreadingHTTPServer):
    request_queue_size = 128
    daemon_threads = True

if __name__ == "__main__":
    print("timing oracle listening on 127.0.0.1:7610", flush=True)
    print("服务端 MAC(hex) =", maccheck.TOKEN.hex(), "(攻击者不可见，打印出来供对账)", flush=True)
    Server(("127.0.0.1", 7610), Handler).serve_forever()
```

> [!warning] 计时靶的三层延迟都要管住
> 时序靶把毫秒级信号埋在请求往返里，三层传输延迟任何一层失控都会淹没信号：Nagle 算法与 delayed ACK 叠加出约 40 ms 的固定底噪（两侧 TCP_NODELAY，响应头体一次写出）；响应分片导致的多次小包；每请求新建连接的握手开销（keep-alive 长连接）。[[C09-RSA攻击III|C09]] 第 5 节的 Bleichenbacher 靶按同一张清单处理过，那边的原因分析更细。

起靶：

```bash

sleep 1
cat t2_server.log
```

输出：

```

服务端 MAC(hex) = 63b5db653380e55e60fc036e (攻击者不可见，打印出来供对账)
```

第一行是服务地址，第二行是攻击结束时要对账的真值——攻击者视角看不到它。先用 curl 各发一个 12 字节的错误 token，确认服务可用、报错形态统一：

```bash

```

```

{"ok": false}
```

两个不同的错误 token，响应一字不差——按 [[C06-分组模式攻击全集|C06]] 与 [[C09-RSA攻击III|C09]] 的标准，这个靶的**报错面是防御合格的**：内容上没有任何可区分信号。但 curl 不给时间。时间维度上，两种请求走过了不同数量的循环轮次，式 (15.1) 的差值就在那里。

### 2.3 攻击：按位置统计，取最慢候选

攻击脚本按式 (15.2) 工作。两个实现要点：一是统计量——每个候选采样 5 次取**最小值**再比较（为什么是最小值，第 3.3 节展开）；二是**信号方向**——匹配越多耗时越长，信号在慢侧，每个位置要取的是"最小耗时最大"的候选：

```python
# t3_timing_attack.py —— 逐字节恢复 MAC：按位置统计响应时间，取最慢候选
# 已知条件只有：token 是 12 字节（协议规定的长度）、校验逐字节进行。
import json
import socket
import time
import http.client

HOST, PORT = "127.0.0.1", 7610
SAMPLES = 5
TLEN = 12

conn = http.client.HTTPConnection(HOST, PORT)
conn.connect()
conn.sock.setsockopt(socket.IPPROTO_TCP, socket.TCP_NODELAY, 1)

queries = 0

def ask(token: bytes) -> float:
    """发一次请求，返回往返耗时（秒）"""
    global queries
    body = json.dumps({"token": token.hex()})
    t0 = time.perf_counter()
    conn.request("POST", "/verify", body, {"Content-Type": "application/json"})
    json.loads(conn.getresponse().read())
    queries += 1
    return time.perf_counter() - t0

def probe(token: bytes):
    """每个候选采样 SAMPLES 次，返回（最小值, 全部原始样本）"""
    ts = [ask(token) for _ in range(SAMPLES)]
    return min(ts), ts

known = b""
t0 = time.perf_counter()
for pos in range(TLEN):
    results = []
    for g in range(256):
        cand = known + bytes([g]) + bytes(TLEN - pos - 1)
        results.append((*probe(cand), g))
    results.sort()
    # 信号在慢侧：匹配的字节越多耗时越长，要的是"最小耗时最大"的候选
    best_t, best_raw, best_g = results[-1]
    runner_t = results[-2][0]
    known += bytes([best_g])
    if pos == 0:
        print("位置 0 耗时最长的 4 个候选（最小值 ms | 5 次原始样本 ms）:")
        for t, raw, g in reversed(results[-4:]):
            raws = ", ".join(f"{x*1000:.2f}" for x in raw)
            print(f"  0x{g:02x}: min {t*1000:6.3f} | [{raws}]")
    print(f"位置 {pos:2d}: 0x{best_g:02x}   min {best_t*1000:6.3f} ms   次名 {runner_t*1000:6.3f} ms")

elapsed = time.perf_counter() - t0
print(f"还原 MAC = {known.hex()}")
print(f"共 {queries} 次请求，耗时 {elapsed:.1f} s")
conn.request("POST", "/verify", json.dumps({"token": known.hex()}),
             {"Content-Type": "application/json"})
print("靶机校验:", json.loads(conn.getresponse().read()))
conn.close()
```

- **位置 0 的候选表**是整个攻击的原理样本：正确候选 `0x63` 的最小耗时 0.793 ms，次名 0.396 ms——差值约 0.4 ms，对应一个匹配字节的边际开销（模拟值 0.5 ms，最小值统计读出略低）；错误候选们挤在 0.37~0.40 ms 的平台上，那正是固定传输底座（3.2 节 k=0 的均值 0.371 ms），不含任何匹配信息；
- **逐位的台阶**：位置 $p$ 的胜者最小耗时约底座加 $(p+1) \times 0.5\,\text{ms}$——0 号位 0.793 ms、11 号位 6.575 ms，台阶斜率就是 $t_b$。攻击没有读过一行校验逻辑，==答案完全由"问"与"计时"构成==；
- **账目**：12 个位置 × 256 个候选 × 5 次采样 = 15360 次请求，49.9 秒。次名与胜者的差距在每个位置都超过 0.1 ms，5 次采样的最小值统计在这个信噪比下足够稳。

> [!warning] 先确认信号方向，再写排序
> 式 (15.2) 找的是**最慢**的候选。把排序方向写反（取"最快"）的脚本照样"稳定输出"——每一位都选出确定性最强的错误答案，最终校验不过，且过程中没有任何报错。动手前先固定已知前缀测一对候选（一个必对、一个必错），确认信号落在耗时分布的哪一侧，再决定取 max 还是 min。

### 2.4 修复：compare_digest 与恒时比较

修复的第一步是换比较函数。`hmac.compare_digest` 的实现不做"第一处不等就返回"：把全部字节比对完、差异**累积**到一个变量里（例如逐字节 `diff |= a[i] ^ b[i]`），最后统一判断累积值是否为零——==无论第几个字节失配、失配多少个，执行的指令序列都相同，耗时不含任何内容信息==。下面的脚本在进程内把三种比较批量计时，量化"漏洞的信号"与"修复的平坦"：

```python
# t1_local_timing.py —— 进程内高精度计时：逐字节循环 / compare_digest / == 
import gc
import hmac
import operator
import time

from maccheck import TOKEN, TLEN

def naive(a: bytes, b: bytes) -> bool:
    """与 maccheck.verify 相同的漏洞形态，去掉模拟开销，只测比较本身的耗时"""
    if len(a) != len(b):
        return False
    for i in range(len(a)):
        if a[i] != b[i]:
            return False
    return True

def batch_time(fn, a, b, reps) -> float:
    """批量调用 reps 次取平均，返回单次耗时（ns）"""
    gc.disable()
    t0 = time.perf_counter_ns()
    for _ in range(reps):
        fn(a, b)
    dt = (time.perf_counter_ns() - t0) / reps
    gc.enable()
    return dt

print("== 逐字节比较循环（进程内，5000 次取均值）==")
for k in (0, 3, 6, 9, 12):
    cand = TOKEN[:k] + bytes(TLEN - k)
    t = batch_time(naive, cand, TOKEN, 5000)
    print(f"匹配 {k:2d}/12 字节: {t:8.1f} ns/次")

print("== hmac.compare_digest（进程内，50000 次取均值）==")
for k in (0, 3, 6, 9, 12):
    cand = TOKEN[:k] + bytes(TLEN - k)
    t = batch_time(hmac.compare_digest, cand, TOKEN, 50000)
    print(f"匹配 {k:2d}/12 字节: {t:8.1f} ns/次")

print("== == 运算符（bytes 走 memcmp，进程内，200000 次取均值）==")
for k in (0, 6, 12):
    cand = TOKEN[:k] + bytes(TLEN - k)
    t = batch_time(operator.eq, cand, TOKEN, 200000)
    print(f"匹配 {k:2d}/12 字节: {t:8.1f} ns/次")

print("== compare_digest 的类型限制 ==")
cases = [(b"abc", "abc"), ("ábc", "abc"), (b"abc", b"abd"), ("abc", "abd")]
for a, b in cases:
    try:
        print(f"compare_digest({a!r:>10}, {b!r:>6}) ->", hmac.compare_digest(a, b))
    except TypeError as ex:
```

## 3. 放大器：采样统计与测量面

### 3.1 采样：噪声按 √N 收缩

时序攻击的两个放大器里，第一个是**采样**。单次耗时 = 信号 + 噪声；对同一候选重复测 $N$ 次取均值，噪声按

$$\sigma_{\bar T} = \frac{\sigma}{\sqrt{N}} \tag{15.3}$$

收缩，信号不动。要把两个候选的均值差 $\Delta$ 判别出来（工程上取 $3\sigma_{\bar T}$ 的裕度），需要的样本量是

$$N \;\approx\; \left(\frac{3\sigma}{\Delta}\right)^2 \tag{15.4}$$

==噪声与信号同量纲，放大器的开销却随它们的比值平方增长==：$\sigma$ 比 $\Delta$ 小时几次采样就够，$\sigma$ 比 $\Delta$ 大一个数量级就要上百倍样本。2.4 节第一段输出是式 (15.4) 的用法示范：逐字节循环的单字节差异约 15 ns，与单次调用的读数抖动同量级，单次测量毫无意义；批量 5000 次取均值后，$\sigma$ 按式 (15.3) 缩到 0.1 ns 级，斜率清晰可读。

3.2 节的进程内直测给出另一组数：0.5 ms 的字节信号、7 µs 的标准差，单次采样就足够判别。这两组数合起来的结论：==进程内测量面前，纳秒到毫秒级的信号都活得下来；离开进程，判据就只剩"信号是否大于一层传输噪声"==。

### 3.2 测量面：进程内、loopback 与远程

第二个放大器是**换测量面**——把观测点往靶的内部挪。同一个校验函数，进程内直接调用、经 loopback 网络访问，是两个噪声完全不同的世界。脚本对同一个靶做两组 100 次采样：

```python
# t4_amp_compare.py —— 放大器对比：同一校验，进程内直测 vs loopback HTTP
import gc
import json
import socket
import statistics
import time
import http.client

from maccheck import TOKEN, TLEN, verify

KS = (0, 6, 12)
N = 100

def cand(k: int) -> bytes:
    return TOKEN[:k] + bytes(TLEN - k)

# ---- 进程内直测 ----
print(f"== 进程内直测 verify()，每候选 {N} 次 ==")
local = {}
for k in KS:
    gc.disable()
    ts = []
    for _ in range(N):
        t0 = time.perf_counter_ns()
        verify(cand(k))
        ts.append(time.perf_counter_ns() - t0)
    gc.enable()
    local[k] = ts
    print(f"匹配 {k:2d} 字节: mean {statistics.mean(ts)/1e6:7.3f} ms  "
          f"std {statistics.pstdev(ts)/1e3:7.1f} us  min {min(ts)/1e6:7.3f} ms")

# ---- loopback HTTP ----
conn = http.client.HTTPConnection("127.0.0.1", 7610)
conn.connect()
conn.sock.setsockopt(socket.IPPROTO_TCP, socket.TCP_NODELAY, 1)

def ask_http(token: bytes) -> float:
    t0 = time.perf_counter()
    conn.request("POST", "/verify", json.dumps({"token": token.hex()}),
                 {"Content-Type": "application/json"})
    json.loads(conn.getresponse().read())
    return time.perf_counter() - t0

print(f"== loopback HTTP，每候选 {N} 次 ==")
http_t = {}
for k in KS:
    ts = [ask_http(cand(k)) for _ in range(N)]
    http_t[k] = [t * 1000 for t in ts]
    print(f"匹配 {k:2d} 字节: mean {statistics.mean(http_t[k]):7.3f} ms  "
          f"std {statistics.pstdev(http_t[k])*1000:7.1f} us  "
          f"min {min(http_t[k]):7.3f} ms  max {max(http_t[k]):7.3f} ms")

# ---- 直方图：k=6 的 100 个 HTTP 样本 ----
print("== k=6 的 100 个 HTTP 样本直方图（0.25 ms 桶宽）==")
lo, width = 3.0, 0.25
buckets = {}
for t in http_t[6]:
    b = int((t - lo) / width)
    buckets[b] = buckets.get(b, 0) + 1
for b in sorted(buckets):
    a_, b_ = lo + b * width, lo + (b + 1) * width
    print(f"{a_:5.2f}-{b_:5.2f} ms | {'#' * buckets[b]} {buckets[b]}")

# ---- 需要多少采样才能区分相邻字节（信号 0.5 ms）----
delta = 0.5
print("== 区分相邻字节（信号 0.5 ms）需要的均值采样数 N ≈ (3σ/Δ)² ==")
for name, k in (("进程内", 6), ("loopback", 6)):
    if name == "进程内":
        sigma = statistics.pstdev(local[k]) / 1e6          # ns -> ms
    else:
        sigma = statistics.pstdev(http_t[k])               # ms
    print(f"  {name:9s} σ = {sigma:6.3f} ms  ->  N ≈ {max(1, round((3*sigma/delta)**2))}")
conn.close()
```

### 3.3 统计判别的三种写法

把 2.3 与 3.2 用到的统计手法收拢成一张表，写任何时序脚本前先从里面选：

| 统计量 | 写法 | 适用 |
| ---- | ---- | ---- |
| 均值差 | 每候选测 $N$ 次取均值，比较相邻候选均值差是否达到 $3\sigma/\sqrt{N}$ | 噪声近似对称、无长尾时最省样本 |
| 最小值法 | 每候选测 $N$ 次取最小值再比较 | 噪声带**单向尖峰**（调度、GC、重传都只增不减耗时）——尖峰抬高均值却抬不高最小值，2.3 的靶用的就是它 |
| 直方图 | 把样本分桶看分布形状 | 判定"信号是否存在"、估 $\sigma$ 与 $\Delta$——写攻击脚本之前先看一眼 |

> [!note] 自适应加样
> 胜者与次名的统计量差距不足 $2\sigma_{\bar T}$ 时不要硬猜：对头两名候选追加采样直到分出胜负。固定预算打不准的位置，追加 5 次往往就拉开了——比整轮重跑便宜得多。

## 4. MAC-then-encrypt 的结构病

### 4.1 两种组合顺序

加密保机密、MAC 保完整，两者怎么拼是协议层的事，常见两种顺序：

| 顺序 | 构造 | 解密端动作 |
| ---- | ---- | ---- |
| MAC-then-encrypt（MtE） | $C = E_K(M \,\|\, \text{MAC}(M))$ | 先解密 → 查填充 → 算 MAC 比对 |
| Encrypt-then-MAC（EtM） | $C = E_K(M)$，$\text{tag} = \text{MAC}_{K_2}(C)$ | 先验 tag → 通过才解密 |

差别全在解密端==第一个动作处理的是什么==：EtM 先验证 tag，攻击者篡改的密文进不了解密函数；MtE 先解密，**填充检查跑在认证验证之前**——攻击者篡改的密文被解密端实打实地处理了，填充校验的结果（合法 / 非法）沿某个旁路漏出去，就是一台 oracle。[[C06-分组模式攻击全集|C06]] 第 2 节的 padding oracle 是"报错内容可区分"的版本；本章关心的是它的时序变体。

### 4.2 Lucky13：填充检查的计时残渣

TLS 1.2 的 CBC 记录用的正是 MtE。padding oracle 现世后，实现方把失败统一成同一个 alert（[[C09-RSA攻击III|C09]] 第 7 节的"统一报错"纪律），并补了一道看起来稳妥的措施：填充非法时也把 HMAC **假装算完**再失败，让两条失败路径的总耗时对齐。但耗时模型里藏着残余项：

$$T \;\approx\; T_{\text{base}} + T_{\text{unpad}} + \big[\text{填充合法}\big] \cdot T_{\text{HMAC}} + \dots \tag{15.5}$$

2013 年的 Lucky13 攻击（AlFardan–Paterson）证明：HMAC 依赖消息长度，合法与非法路径上的长度处理、缓存行为仍有纳秒到微秒级的系统差，用 $2^{18}$ 量级的会话样本统计放大，足以逐字节恢复 cookie——CBC 加 TLS 1.2 的这条组合就此判了死刑。修复的落点不在"把假算得更像"（补时长永远补不干净，见下方折叠），在换顺序：TLS 1.3（RFC 8446）删除全部 CBC 套件，记录层只保留 AEAD。

> [!info]- 补时长为什么补不干净
> 假 HMAC 要"像"，就得对一段等长数据真的算一遍 HMAC——但这段数据是**伪造的填充内容**，长度随篡改字节变化；HMAC 对不同长度输入的压缩轮数不同，耗时随长度阶梯变化，长度信息从"填充是否合法"换成了"伪造长度是多少"。后续研究（Lucky13 的微秒级精化与对 DTLS 的改造）反复证明：==靠对齐耗时去救一个先解密后验证的结构，是在给结构病打补丁==。结构病的正解是下面这节。

### 4.3 Encrypt-then-MAC 与 AEAD

EtM 把 tag 覆盖在密文上，解密端第一动作就是验证——失败路径唯一（统一报错、恒时），第 2 节的逐字节比较攻击和 4.2 的计时 oracle 同时失去落点。[[C06-分组模式攻击全集|C06]] 第 6 节的 AES-GCM 是这件事的现代形态：加密与认证一体，`decrypt_and_verify` 先验 tag 后解密，篡改必被拒。==拿到"自己拼加密 + 自己拼 MAC"的实现，先看顺序；看到 MtE，把它当作一个独立于具体算法的结构漏洞上报==。

## 5. RSA 的时序信号与盲化

### 5.1 裸实现的密钥依赖

RSA 私钥运算是模幂 $m = c^d \bmod n$。教科书的平方-乘实现按 $d$ 的二进制位逐位走：每个位做一次平方，位是 1 再多做一次乘法。==乘法次数由密钥的位模式直接决定==——耗时是密钥的函数，式 (15.1) 的 $t_b$ 换成了"每个 1 位的一次模乘"。下面把这条信号量出来：512 位模数、同一底数、三个位模式不同的 256 位指数，裸实现各跑 30 次取均值；随后用 gmpy2 的 `powmod`（GMP 库）在 1024 位模数上重复同样的三类测量，并加一组盲化对照。脚本一次跑完：

```python
# t5_rsa_timing.py —— 模幂的时序：裸实现的密钥依赖 / 库实现 / 盲化
import gc
import random
import statistics
import time

import gmpy2
from gmpy2 import mpz, powmod, invert
from sympy import nextprime

random.seed(20261024)

def report(name, ts_ms):
    s = sorted(ts_ms)
    p10 = s[len(s) // 10]
    p90 = s[len(s) * 9 // 10]
    print(f"{name:26s} mean {statistics.mean(ts_ms):7.3f} ms  "
          f"std {statistics.pstdev(ts_ms):6.3f} ms  min {s[0]:7.3f}  p90 {p90:7.3f}")

# ---------- 裸实现：教科书平方-乘（左到右），512 位模数 ----------
p = nextprime(2**511 + 123456)
q = nextprime(2**512 - 987654321)
n512 = mpz(p * q)

def modexp_bare(base, exp, mod):
    r = mpz(1)
    a = mpz(base) % mod
    for i in range(exp.bit_length() - 1, -1, -1):
        r = (r * r) % mod
        if (exp >> i) & 1:
            r = (r * a) % mod
    return r

base = mpz(random.getrandbits(511))
exps = [
    ("2^255",   1 << 255),
    ("随机 256 位", random.getrandbits(255) | (1 << 254)),
    ("2^255-1", (1 << 255) - 1),
]
print("== 裸平方-乘（512 位模数，同一底数，30 次取均值）==")
for name, ex in exps:
    gc.disable()
    ts = []
    for _ in range(30):
        t0 = time.perf_counter_ns()
        modexp_bare(base, ex, n512)
        ts.append((time.perf_counter_ns() - t0) / 1e6)
    gc.enable()
    print(f"指数 {name:12s} 位模式 1 的个数 {bin(ex).count('1'):3d}  "
          f"mean {statistics.mean(ts):7.3f} ms")

# ---------- 库实现：gmpy2.powmod，1024 位模数 ----------
P = nextprime(2**511 + 654321)
Q = nextprime(2**512 - 123456789)
n1024 = mpz(P * Q)
phi = (P - 1) * (Q - 1)
e = 65537
d = pow(e, -1, phi)
e_mpz = mpz(e)

def timed_pow(base_, exp_, reps):
    ts = []
    gc.disable()
    for _ in range(reps):
        t0 = time.perf_counter_ns()
        powmod(mpz(base_), mpz(exp_), n1024)
        ts.append((time.perf_counter_ns() - t0) / 1e6)
    gc.enable()
    return ts

print("== gmpy2.powmod：耗时随指数规模（40 次取均值）==")
for bits in (256, 512, 1024):
    ex = random.getrandbits(bits) | (1 << (bits - 1))
    ts = timed_pow(base, ex, 40)
    print(f"指数 {bits:4d} 位: mean {statistics.mean(ts):7.3f} ms")

print("== gmpy2.powmod：同一输入重复 200 次 vs 随机输入 200 次（1024 位密钥）==")
c = mpz(random.getrandbits(1023))
ts_same = timed_pow(c, d, 200)
report("同一输入重复", ts_same)
cs = [mpz(random.getrandbits(1023)) for _ in range(200)]
ts_rand = []
gc.disable()
for c_ in cs:
    t0 = time.perf_counter_ns()
    powmod(c_, d, n1024)
    ts_rand.append((time.perf_counter_ns() - t0) / 1e6)
gc.enable()
report("随机输入", ts_rand)

# ---------- 盲化：同一密文重复 200 次，每次乘上随机因子 ----------
print("== 盲化包装：同一密文重复 200 次（计时含 r^e 与求逆）==")

def blind_dec(c_):
    r = mpz(random.getrandbits(1023))
    r_inv = invert(r, n1024)
    c2 = (c_ * powmod(r, e_mpz, n1024)) % n1024
    m2 = powmod(c2, d, n1024)
    return (m2 * r_inv) % n1024

assert blind_dec(c) == powmod(c, d, n1024), "盲化结果应与直接解密一致"
ts_blind = []
gc.disable()
for _ in range(200):
    t0 = time.perf_counter_ns()
    blind_dec(c)
    ts_blind.append((time.perf_counter_ns() - t0) / 1e6)
gc.enable()
report("同一密文 + 盲化", ts_blind)
```

```
== 盲化包装：同一密文重复 200 次（计时含 r^e 与求逆）==
同一密文 + 盲化                  mean   0.262 ms  std  0.018 ms  min   0.238  p90   0.280
```

第一段输出就是 Kocher 观测的信号本体：指数从 2^255（1 个 1 位）到 2^255-1（255 个 1 位），耗时 0.106 → 0.165 ms，斜率约 0.23 µs/乘法——==裸实现的耗时把私钥的位模式直接写在表上==。反复观测私钥运算的耗时并统计，就能逐段推断指数位（Kocher 的原始攻击）；2003 年 Brumley–Boneh 进一步证明**隔着网络也可行**：对局域网里的 OpenSSL 做小时级的握手计时测量，恢复了 RSA 私钥——信号来自模乘的 Montgomery 约化对数据敏感，尽管比裸实现小得多。

### 5.2 库实现：信号去了哪里

第二段输出给出两条库层面的账。**规模信号**：指数 256 → 512 → 1024 位，耗时 0.062 → 0.124 → 0.240 ms，与位长成线性——观测耗时能暴露密钥规模与运算类型（这也是 CRT 签名快路径在时间上可识别的原因）。**数据信号**：同一输入重复 200 次的分布（std 0.011 ms）只比随机输入（std 0.015 ms）略窄——GMP 的滑动窗口按窗口统计决定乘法次数，密钥位模式与耗时的关系被摊平；Montgomery 约化的残余数据依赖只剩微秒级，与调度噪声同量级。==库的恒时化不是把耗时变成常数，是把数据依赖压到观测噪声之下==：2003 年之后主流实现默认开启 RSA 盲化，2013 年 Lucky13 之后 CBC 填充检查改写为恒时实现——历史脉络与本章防御清单（第 7 节）一一对应。

### 5.3 盲化

盲化在解密前把输入随机化：

$$\tilde{c} = c \cdot r^e \bmod n, \qquad m = \tilde{c}^{\,d} \cdot r^{-1} \bmod n \tag{15.6}$$

$r$ 是每次新取的随机数，$r^e$ 只用公开指数。模幂的输入从攻击者已知的 $c$ 变成随机的 $\tilde c$，==重复测量取均值这个放大器就此失效==：同一密文的一千次观测，对应的是一千个互不相同的内部计算路径。第三段输出是这个论断的量化形态：同一密文加盲化后 std 从 0.011 ms 涨到 0.018 ms，与随机输入的 0.015 ms 同宽——重复观测的分布回到了"随机输入"的水平。

> [!warning] "盲化前后测不出差异"是预期内的
> 现代库里数据依赖本就被压在噪声附近（5.2 的数字），盲化加在库上，能测出的变化自然只有零点几毫秒的标准差挪动。==盲化防的是"上万次重复取均值"的统计放大，不是让单次耗时变得看不出==。攻击裸实现（教科书平方-乘、自写的模幂循环）时这层防护不存在，5.1 的位模式信号才是完整的。判断一个靶能不能打时序，先看它用的是不是成熟库。

> [!info]- 滑动窗口与 Montgomery 为什么压小位模式信号
> 教科书平方-乘对每个 1 位做一次模乘，乘法次数 = popcount − 1。$m$-ary 滑动窗口把指数按窗口切分，预先算好 $2, 3, \dots, 2^m-1$ 的幂，每个窗口只做一次乘法——乘法次数由窗口**个数**决定，只依赖位长与"1 游程"的统计，与逐位模式的细节解耦。Montgomery 乘法则把"除模"换成移位加约化，约化步骤的分支由操作数的低位决定，带来残余的数据依赖——这是 5.2 里 std 0.011 ms 信号的来源，也是 Kocher 之后的时序分析真正在追踪的量。两层改造叠加后，位模式信号从毫秒级（裸实现）降到微秒级（库），再由盲化把"可控输入"变成"随机输入"。

## 6. 故障与缓存：概念谱系

故障注入与缓存侧信道是侧信道的另外两大分支。本节把谱系摆正，细节留在折叠框——它们在 CTF 里出场率低，但在真实世界的攻击报告里是常客。

**故障攻击**：电压毛刺、时钟毛刺、激光注入让运算的中间值出错，出错的位置和方式本身就是信息。RSA 侧的完整链条在 [[C09-RSA攻击III|C09]] 第 4 节已经打穿：RSA-CRT 签名错一位，一次 gcd 分解模数（Bellcore）。对称密码侧的对应玩法是差分故障分析（DFA），折叠框给出 AES 上的概念。

> [!info]- AES 的差分故障分析（DFA）概念
> AES 的轮结构见 [[C05-分组密码内部|C05]]。对**倒数第二轮**状态注入单字节故障，比较正确密文与故障密文的最后一轮输入差，最后一轮密钥的每个字节候选从 $2^{128}$ 全空间缩到约 $2^8$；用两到四个不同位置（或不同轮次）的故障即可唯一确定 AES-128 的最后一轮密钥，再由密钥扩展反推主密钥（Piret–Quisquater 的 DFA）。CTF 里通常以"程序返回了一条算错的密文"的形式给出故障，把物理注入换成题目设定——识别特征是附件里同时出现同一明文的正确与错误密文对。

**缓存侧信道**：现代 CPU 的缓存是按"最近是否访问过"分速的——命中约几纳秒，落内存约两百个时钟周期。Flush+Reload（Yarom–Falkner）把这个速度差做成探针：攻击者把共享库代码页的一行缓存**刷出**（`clflush`），等受害者执行，再**重读**同一行并计时——读得快说明受害者刚执行过它。按密码运算的代码行逐个探测，就能重建"执行了哪些运算"，进而恢复密钥相关数据。CTF 少见的原因是前提苛刻：需要与受害者同机、共享同一份只读库映射、还要高频高精度计时；真实世界多见的原因是这些前提在云环境（共享宿主的租户、共享的系统库）里恰恰成立。

> [!info]- 从缓存侧信道到 ECDSA 的 nonce 泄漏
> 缓存与时序探针打到椭圆曲线签名上，产物是 **nonce 的部分信息**：标量乘的执行轨迹随 nonce 的位模式变化（[[C11-椭圆曲线与ECDLP|C11]] 的 ECDSA 运算核心），缓存探测或计时统计能恢复每个签名的 nonce 的最高几位。拿到"带误差的部分 nonce"，每个签名给出一个关于私钥的不等式——这就是隐藏数问题（HNP），一组合规上式的签名交给格归约即可解出私钥。HNP 的建模与利用在 [[C12-数字签名|C12]] 展开，LLL 格基约简的工具本体在 [[C13-格密码与LLL|C13]]；本章补的是链条的第一环——==泄漏从哪来==。这条链的代表作：对 OpenSSL 的 Flush+Reload 攻击（CHES 2014）与 2019 年的 Minerva 系列（时序泄漏 + 格攻击打穿多个智能卡与库）。

## 7. 防御清单

把前面各节的防御收拢成一张表，每条对应一类泄漏：

| 防御 | 堵哪类泄漏 | 要点与出处 |
| ---- | ---- | ---- |
| 恒时比较 | 逐字节早退的时序 | `hmac.compare_digest` / 常数时间大数比较：全比完再汇总；密钥、MAC、tag 的比较一律走它（[[#2.4 修复：compare_digest 与恒时比较\|2.4]]） |
| 失败路径恒时且统一 | 报错 + 时间 oracle | padding、MAC、长度失败给同一响应、同一耗时；[[C06-分组模式攻击全集\|C06]] 与 [[C09-RSA攻击III\|C09]] 的结论在时间轴上同样成立（[[#4.2 Lucky13：填充检查的计时残渣\|4.2]]） |
| Encrypt-then-MAC / AEAD | 组合顺序病 | 先验证后解密；GCM 的 `decrypt_and_verify` 用法见 [[C06-分组模式攻击全集\|C06]] 第 6 节（[[#4.3 Encrypt-then-MAC 与 AEAD\|4.3]]） |
| 密钥不进分支与地址 | 时序（位模式） | 密钥位决定的循环、分支、查表都要恒时化；用成熟库，不手写模幂（[[#5.1 裸实现的密钥依赖\|5.1]]） |
| 盲化 | RSA 时序与故障 | 解密 / 签名前乘随机因子，重复取均值的放大器失效（[[#5.3 盲化\|5.3]]） |
| 签名后验签 | 故障攻击 | 输出前用公钥验一次，错签不出门；[[C09-RSA攻击III\|C09]] 第 4 节的防御 |
| nonce 纪律 + 恒时标量乘 | ECDSA nonce 泄漏 | nonce 生成的事故清单见 [[C04-随机数攻防\|C04]]；标量乘用带恒时保证的库（[[#6. 故障与缓存：概念谱系\|6]]） |

> [!note] 审计顺序：拿到一份实现先查什么
> ① 所有"比较秘密"的地方是不是恒时比较；② 解密 / 验证的每条失败路径，报错内容与耗时是否统一；③ 私钥运算用的是成熟库还是手写循环，有没有盲化；④ 加密与 MAC 的组合顺序，是不是先验证后解密；⑤ 随机数与 nonce 的来源；⑥ 失败路径的深处有没有密钥控制的分支或查表。六项里任何一项不过，对照上表找对应攻击面。

## 8. 常见问题

| 现象 | 原因与解决 |
| ---- | ---- |
| 每个请求都拖着约 40 ms 的底噪，毫秒级信号被淹没 | 响应分两次写、服务端没开 TCP_NODELAY，撞上 Nagle × delayed ACK；两侧都开 NODELAY、响应头体一次写出（[[#2.2 自建 HTTP 靶\|2.2]]） |
| 每个位置的"最快候选"非常稳定，拼出来的 token 却不对 | 信号方向搞反：匹配越多越**慢**，应当取耗时最大的候选；先固定前缀测一对必对/必错候选，确认信号在慢侧还是快侧（[[#2.3 攻击：按位置统计，取最慢候选\|2.3]]） |
| 按位置统计后仍偶尔选错字节 | 采样不足或统计量不合适：单向尖峰用最小值法、对称抖动用中位数；相邻候选差距不足 $2\sigma$ 时对头两名自适应加样（[[#3.3 统计判别的三种写法\|3.3]]） |
| `compare_digest` 报 TypeError | 只接受同类型操作数，str 必须双方都是 ASCII；统一 `encode()` 成 bytes 再比（[[#2.4 修复：compare_digest 与恒时比较\|2.4]]） |
| 比较换成 compare_digest 了，总耗时仍随输入变 | 只修了比较一处：长度检查、报错组装、补齐逻辑还有分支；修复要覆盖整条失败路径并固定总耗时（[[#2.4 修复：compare_digest 与恒时比较\|2.4]]） |
| 盲化前后重复测量的分布几乎不变，盲化是不是没用 | 现代库的数据依赖本就压在调度噪声下，能测出的只有零点几毫秒的标准差挪动；盲化防的是统计放大，不是单次可见（[[#5.3 盲化\|5.3]]） |
| 本地靶打得穿，换远程靶统计全乱 | 信噪比差两三个数量级，$N$ 按 $(3\sigma/\Delta)^2$ 增长；先量远程的 $\sigma$ 与 $\Delta$ 再估预算，预算不够就缩小测量距离（同机进程内）或放弃该攻击面（[[#3.2 测量面：进程内、loopback 与远程\|3.2]]） |
| 计时数据前几十个样本特别慢 | 解释器预热、缓存冷启动、CPU 频率切换：先空跑预热若干次，计时循环里 `gc.disable()`，用 `perf_counter_ns` 而非 `time.time`（[[#3.1 采样：噪声按 √N 收缩\|3.1]]） |
| 并发发请求想提速，计时反而没法看 | 并发请求在服务端排队，耗时互相污染；时序测量必须单连接串行，并发只用于不计时的 oracle（[[#2.3 攻击：按位置统计，取最慢候选\|2.3]]） |
| gmpy2 计时结果比预期大很多 | `int` → `mpz` 的转换被计进了热区：预先转好 `mpz`，只对运算段计时，转换开销与一次模乘同量级（[[#5.1 裸实现的密钥依赖\|5.1]]） |
| curl 打时序靶看不出任何差异，怀疑没有漏洞 | curl 只给内容不给时间；用带计时的小脚本对两个候选各采几十次，肉眼看不出的差异统计能看出（[[#2.2 自建 HTTP 靶\|2.2]]） |

## 9. 配套练习与延伸阅读

配套练习：

1. 把靶的 `verify` 换成 `verify_ct` 重跑 `t3_timing_attack.py`，确认全部候选的时间分布重合、攻击失效；再把 `maccheck.BYTE_COST_NS` 改成 0、token 加长到 64 字节，体验"信号变小后，进程内采样与网络采样的可行边界怎么移动"。
2. 写一个"显著差判定器"：输入两个候选的样本集，输出均值差、$3\sigma/\sqrt{N}$ 判定与所需样本估计；在进程内与 loopback 上分别对相邻字节跑一遍，对照式 (15.4) 验证预算公式。
3. 给 5.1 的裸模幂加盲化重跑统计；再把指数拆成 CRT 两半（模 p、模 q 的短指数），测单次运算的耗时差——时间信号还能区分"是否走了 CRT 快路径"。
4. 把 MAC 加长到 16 字节（`TLEN` 与候选构造同步改）重打完整攻击，核对总请求数是否符合"每位置 256 × SAMPLES"的公式；再把 `SAMPLES` 提到 9，比较每个位置胜者与次名的统计量差距怎么变。
5. cryptopals 的 Set 4 Challenge 31 / 32（带人工时延的 HMAC 计时攻击，平台入口见 [[01-练习平台索引|练习平台索引]]）：Challenge 31 就是本章靶的 SHA1 版本，Challenge 32 要求把采样与统计做得更省。
