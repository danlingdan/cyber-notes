## 1. 定位：从 12 章到压缩包全解

[[12-隐写与流量取证|12 章]]第 4 节给过压缩包的三条套路：zipfile 口令循环（[[12-隐写与流量取证#4.1 爆破：zipfile 口令循环|12 章 4.1]]）、伪加密标志位翻转（[[12-隐写与流量取证#4.2 伪加密|12 章 4.2]]）、bkcrack 一行命令（[[12-隐写与流量取证#4.3 明文攻击|12 章 4.3]]）。那三件事本章不再重讲，用到时直接引用。

12 章解决的是"知道有这条路"，本章解决"这条路从头走到尾"：ZIP 的字段表为什么长这样、AES 加密的包该怎么认、bkcrack 的明文从哪里凑、john 的哈希从哪里来、RAR 与 ZIP 差在哪、十层套娃怎么一口气拆完。拿到压缩包附件，按下面的顺序走，每一节对应一步：

1. `file` 问真身，`7z l` 列条目——压缩方法、加密标志、注释在这一步就能看到（第 2、3 节）；
2. 能直接打开，把内容全部拆出来，对每个文件回到第 1 步（第 8 节的脚本自动做这件事）；
3. 要口令但 `7z l` 一切正常——先怀疑伪加密（第 4 节）；
4. `unzip` 报 unsupported compression method 一类的话——是 AES 或新算法（第 3 节）；
5. 真加密：先找已知明文（第 5 节），找不到再爆破（第 6 节）；
6. RAR 附件走第 7 节的对应流程。

==压缩包是 MISC 最常见的"下一层容器"，它本身的结构与攻防值得单独一章==。[[M03-文件格式深拆II-JPEG与GIF|M03]] 5.1 尾巴上粘出来的 zip，本章把它拆透。

## 2. ZIP 三段结构：LFH、CDH 与 EOCD

### 2.1 骨架与解析器

一个 ZIP 由三段组成：每个文件一份**本地文件头**（Local File Header，签名 `PK\x03\x04`）加数据；每个文件一张**中央目录条目**（Central Directory Header，签名 `PK\x01\x02`）；文件末尾一个**EOCD**（End Of Central Directory，签名 `PK\x05\x06`）。先用 zipfile 造一个示范包，拍下开头的字节：

```python
# build_demo.py —— 造示范包，并拍下前 64 字节
import subprocess
import zipfile

with zipfile.ZipFile("demo.zip", "w", zipfile.ZIP_DEFLATED) as z:
    z.writestr("readme.txt", "hello zip structure\n" * 3)
    z.writestr("flag.txt", "flag{z1p_thr33_parts}")
data = open("demo.zip", "rb").read()
print(f"demo.zip 共 {len(data)} 字节")
print(subprocess.run(["xxd", "-l", "64", "demo.zip"],
                     capture_output=True, text=True).stdout)
```

输出：

```

== xxd 前 64 字节 ==

00000010: 36dc 1900 0000 3c00 0000 0a00 0000 7265  6.....<.......re
00000020: 6164 6d65 2e74 7874 cb48 cdc9 c957 a8ca  adme.txt.H...W..
00000030: 2c50 282e 292a 4d2e 292d 4ae5 ca20 520c  ,P(.)*M.)-J.. R.
```

开头 4 字节 `50 4b 03 04` 就是 `PK\x03\x04`（[[12-隐写与流量取证#2. 文件格式与魔数|12 章 2 节]]魔数表里的 ZIP 本地头）。多字节整数一律小端（[[03-计算机组成与数据表示|03 章]]），和 PNG 长度字段的大端相反。

解析器从文件末尾倒着开始读：EOCD 的注释长度不定，所以 EOCD 的位置不在固定偏移上，只能按签名向前找；EOCD 给出中央目录的位置；中央目录里每张条目又给出对应本地文件头的偏移。按这个顺序写完整个解析器：

```python
# zip_parse.py —— ZIP 三段结构解析器
import struct

def u16(b, o):
    return struct.unpack("<H", b[o:o + 2])[0]

def u32(b, o):
    return struct.unpack("<I", b[o:o + 4])[0]

data = open("demo.zip", "rb").read()

# EOCD：从文件尾往前找签名——注释长度不定，EOCD 不在固定偏移上
eocd = data.rfind(b"PK\x05\x06")
cd_size, cd_off = u32(data, eocd + 12), u32(data, eocd + 16)
print(f"[EOCD] 偏移 {eocd}")
print(f"  总条目数       = {u16(data, eocd + 10)}")
print(f"  中央目录大小   = {cd_size}")
print(f"  中央目录偏移   = {cd_off}")
print(f"  注释长度       = {u16(data, eocd + 20)}")

# 中央目录：逐张读条目
p = cd_off
entries = []
while p < eocd and data[p:p + 4] == b"PK\x01\x02":
    nlen, elen, clen = u16(data, p + 28), u16(data, p + 30), u16(data, p + 32)
    entries.append(dict(
        name=data[p + 46:p + 46 + nlen].decode(),
        made=u16(data, p + 4), need=u16(data, p + 6), flag=u16(data, p + 8),
        method=u16(data, p + 10), crc=u32(data, p + 16), csize=u32(data, p + 20),
        usize=u32(data, p + 24), iattr=u16(data, p + 36), eattr=u32(data, p + 38),
        lho=u32(data, p + 42)))
    p += 46 + nlen + elen + clen

METHODS = {0: "stored", 8: "deflate"}
for e in entries:
    print(f"[CDH] {e['name']}")
    print(f"  制作版本 0x{e['made']:04x}（高字节 {e['made'] >> 8} = Unix）"
          f"  解压所需版本 {e['need']}  标志位 0x{e['flag']:04x}")
    print(f"  压缩方法 {e['method']} ({METHODS.get(e['method'], '?')})"
          f"  CRC-32 0x{e['crc']:08x}")
    print(f"  压缩后 {e['csize']}  压缩前 {e['usize']}"
          f"  内部属性 0x{e['iattr']:04x}  外部属性 0x{e['eattr']:08x}")
    print(f"  本地头偏移 {e['lho']}")
print()

# 本地文件头：按中央目录给的偏移跳过去
e = entries[0]
lfh = e["lho"]
nlen, elen = u16(data, lfh + 26), u16(data, lfh + 28)
print(f"[LFH] {e['name']} 偏移 {lfh}")
print(f"  签名 {data[lfh:lfh + 4]}  版本(解压) {u16(data, lfh + 4)}"
      f"  标志位 0x{u16(data, lfh + 6):04x}")
print(f"  压缩方法 {u16(data, lfh + 8)} ({METHODS.get(u16(data, lfh + 8), '?')})"
      f"  CRC-32 0x{u32(data, lfh + 14):08x}")
print(f"  压缩后 {u32(data, lfh + 18)}  压缩前 {u32(data, lfh + 22)}")
print(f"  文件名长度 {nlen}  extra 长度 {elen}"
      f"  文件名 {data[lfh + 30:lfh + 30 + nlen].decode()}")
```

输出：

```

  总条目数       = 2

  中央目录偏移   = 126
```

几个数字先对上账：EOCD 在 236，自身 22 字节，文件总长 236 + 22 = 258；中央目录从 126 开始、长 110 字节，正好到 236；flag.txt 的本地头偏移 65 = 第一条目的 LFH（30 头 + 10 名）+ 25 压缩数据。==三段结构的账是闭合的==，哪一段对不上，文件就被动过手脚。

### 2.2 本地文件头 LFH

本地文件头贴在每份文件数据的前面。逐字段表（偏移相对签名，`readme.txt` 的值取自上面的输出与 xxd）：

| 偏移 | 大小 | 字段 | readme.txt 的值 | 说明 |
| ---- | ---- | ---- | ---- | ---- |
| 0 | 4 | 签名 | `50 4B 03 04` | `PK\x03\x04` |
| 4 | 2 | 解压所需版本 | 20（2.0） | 存储与 deflate 只需 2.0 |
| 6 | 2 | 通用标志位 | 0x0000 | bit0 = 加密，第 4 节的主角 |
| 8 | 2 | 压缩方法 | 8（deflate） | 第 3 节的主角 |
| 10 | 2 | 修改时间 | 0x99e8 → 19:15:16 | DOS 格式，见下方折叠 |
| 12 | 2 | 修改日期 | 0x5d58 → 2026-10-24 | DOS 格式 |
| 14 | 4 | CRC-32 | 0xdc360c62 | 对**压缩前**数据计算 |
| 18 | 4 | 压缩后大小 | 25 | |
| 22 | 4 | 压缩前大小 | 60 | |
| 26 | 2 | 文件名长度 | 10 | |
| 28 | 2 | extra 长度 | 0 | |
| 30 | n | 文件名 | `readme.txt` | |
| 30+n | m | extra 字段 | 空 | 键值对扩展区，AES 用它，见 3.2 |

对照 xxd 读一遍头 30 字节：`504b 0304`（签名）`1400`（版本 20，小端）`0000`（标志）`0800`（方法 8）`e899`（时间）`585d`（日期）`620c 36dc`（CRC）`1900 0000`（压缩后 25）`3c00 0000`（压缩前 60）`0a00`（名长 10）`0000`（extra 长 0），随后是文件名。==CRC 校验的是解压后的原始数据==，解压方据此确认还原正确。

> [!info]- DOS 时间与日期字段
> 时间、日期各占 16 位，按位拆：日期 = 年份-1980（7 位）｜月（4 位）｜日（5 位）；时间 = 时（5 位）｜分（6 位）｜秒÷2（5 位）——秒只有 2 秒分辨率。`0x99e8` = `10011 001111 01000`，即时 19、分 15、秒字段 01000 = 8 → 8×2 = 16 秒，合 19:15:16；`0x5d58` = `0101110 1010 11000`，即 2026-10-24。与 3 节 `7z l` 列表显示的修改时间一致。

### 2.3 中央目录 CDH

中央目录是每个条目的"登记卡"。前 46 字节里与 LFH 重复的字段（解压所需版本、标志位、方法、时间日期、CRC、两个大小、名长、extra 长、文件名）不再重复列表，差异字段如下：

| 偏移 | 大小 | 字段 | readme.txt 的值 | 说明 |
| ---- | ---- | ---- | ---- | ---- |
| 0 | 4 | 签名 | `50 4B 01 02` | `PK\x01\x02` |
| 4 | 2 | 制作版本 | 0x0314 | 高字节 3 = Unix，低字节 0x14 = 按 2.0 规范写入 |
| 32 | 2 | 条目注释长度 | 0 | 条目级注释，与 EOCD 的包级注释是两回事 |
| 34 | 2 | 起始盘号 | 0 | 跨盘（分卷）zip 才非零 |
| 36 | 2 | 内部属性 | 0x0000 | bit0 = 1 表示文本文件，现代工具基本不写 |
| 38 | 4 | 外部属性 | 0x01800000 | Unix 下高 16 位是权限：0o600（zipfile 的 writestr 默认值） |
| 42 | 4 | 本地头偏移 | 0（flag.txt 为 65） | 从文件头到该条目 LFH 的距离 |
| 46 | n | 文件名 | `readme.txt` | |

==解析器真正依赖的是中央目录：文件名列表、大小、CRC、加密标志、数据位置都从 CDH 读==。unzip 与 zipfile 决定"要不要口令"看的是 **CDH** 里的标志位，这是第 4 节几个反常行为的根源。CDH 与 LFH 的重复字段被改得不一致时，行为由工具自己选——第 4 节的对照表会给出具体行为。

### 2.4 EOCD 与 ZIP 注释

EOCD 收尾整个文件，字段只有 9 个：

| 偏移 | 大小 | 字段 | demo.zip 的值 | 说明 |
| ---- | ---- | ---- | ---- | ---- |
| 0 | 4 | 签名 | `50 4B 05 06` | `PK\x05\x06` |
| 4 | 2 | 当前盘号 | 0 | 分卷用 |
| 6 | 2 | 中央目录起始盘号 | 0 | 分卷用 |
| 8 | 2 | 本盘条目数 | 2 | |
| 10 | 2 | 总条目数 | 2 | |
| 12 | 4 | 中央目录大小 | 110 | |
| 16 | 4 | 中央目录偏移 | 126 | |
| 20 | 2 | 注释长度 | n | |
| 22 | n | ZIP 注释 | | ==包级注释住在这里== |

ZIP 的注释是 EOCD 的最后一个字段，随包整体存在，不属于任何条目。造一个带注释的包，用几个工具对照着读：

```python
# eocd_comment.py —— 往 EOCD 塞注释，再用几个工具对照
import struct
import subprocess
import zipfile

def u16(b, o):
    return struct.unpack("<H", b[o:o + 2])[0]

with zipfile.ZipFile("demo_comment.zip", "w", zipfile.ZIP_DEFLATED) as z:
    z.writestr("flag.txt", "flag{z1p_thr33_parts}")
    z.comment = b"flag{n0te_in_eocd}"

for cmd in (["file", "demo_comment.zip"],
            ["strings", "demo_comment.zip"],
            ["unzip", "-z", "demo_comment.zip"]):
    r = subprocess.run(cmd, capture_output=True, text=True)
    print("$", " ".join(cmd))
    print(r.stdout.rstrip())
    print()

d = open("demo_comment.zip", "rb").read()
e = d.rfind(b"PK\x05\x06")
cl = u16(d, e + 20)
print(f"解析器读 EOCD：注释长度 {cl}，注释内容 {d[e + 22:e + 22 + cl]}")
```

输出：

```
$ file demo_comment.zip
demo_comment.zip: Zip archive data, at least v2.0 to extract, compression method=deflate

$ strings demo_comment.zip
X]10
flag.txtK
/H,*)
X]10
flag.txtPK
flag{n0te_in_eocd}

$ unzip -z demo_comment.zip
Archive:  demo_comment.zip
flag{n0te_in_eocd}

解析器读 EOCD：注释长度 18，注释内容 b'flag{n0te_in_eocd}'
```

三个事实：`file` 的输出里根本没有注释；`strings` 只在注释恰好是长可见串时扫得到它；`unzip -z` 专门打印包注释。新版 7z 的列表也会显示：`7z l demo_comment.zip` 的信息区里有一行 `Comment = flag{n0te_in_eocd}`。注释是检查点之一——做题拿到 zip，先 `unzip -z` 一遍，成本一秒。

> [!note] strings 不认的注释也存在
> 注释可以存任意字节。把上面的靶子改成 `z.comment = "flag{utf16_c0mment}".encode("utf-16-le")`，单字节模式的 `strings` 就扫不到了，要加 `-e l` 扫 UTF-16LE：
>
> ```
> $ strings demo_comment16.zip  ->  命中 flag 相关行: ['flag.txtK', 'flag.txtPK']
> $ strings -e l demo_comment16.zip  ->  命中 flag 相关行: ['&flag{utf16_c0mment}']
> 解析器读 EOCD：注释 38 字节，raw = b'f\x00l\x00a\x00g\x00{\x00u\x00t\x00f\x001\x006\x00_\x00c\x000\x00m\x00m\x00e\x00n\x00t\x00}\x00'
> 按 UTF-16-LE 解码 = 'flag{utf16_c0mment}'
> ```
>
> 编码后的字节对 `strings` 不可见，对按结构读的解析器不存在障碍——==宁可写十行解析，不赌一把 strings==。

### 2.5 ZIP64

字段都是定长的：4 字节的大小装不下超过 4 GB 的文件，2 字节的条目数装不下超过 65535 个条目。超出这些限制时格式切换到 ZIP64：extra 字段（类型 0x0001）里补 8 字节宽字段，EOCD 换成 ZIP64 EOCD（签名 `50 4B 06 06`）加定位器（`50 4B 06 07`）。CTF 里很少直接考 ZIP64 结构，常见的是"大附件打不开"——老版本工具不支持 ZIP64，升级 7z、unzip 即可。

## 3. 压缩方法与加密

### 3.1 method 编号表

LFH 与 CDH 各有一个 2 字节的压缩方法字段，常用编号：

| 编号 | 名称 | 出现场景 |
| ---- | ---- | ---- |
| **0** | stored（存储，不压缩） | 已压缩数据（图片、压缩流）与小文件 |
| **8** | deflate | 缺省方法，绝大多数条目 |
| 9 | deflate64 | 大文件的 deflate 加强版，少见 |
| 12 | bzip2 | 老压缩工具的高压缩率选项 |
| 14 | LZMA | 少见，7z 系工具可造 |
| 93 | zstd | 新方法，老工具不认 |
| **99** | AES 加密标记 | ==不是压缩算法==，见 3.2 |

zipfile 的常量 `ZIP_STORED` = 0、`ZIP_DEFLATED` = 8 与表对应。看到 0 和 8 走正常解压流程；看到 99 先读 3.2；看到 12、14、93 且 unzip 打不开，换 7z 试试。

### 3.2 加密位与两代加密：ZipCrypto 与 WinZip AES

标志位 bit0 = 1 表示条目加密。bit0 = 1 时，绝大多数是 **ZipCrypto**——[[12-隐写与流量取证#4.1 爆破：zipfile 口令循环|12 章 4.1]]手搓过的那套 PKWARE 传统流密码，数据前面带 12 字节加密头，[[12-隐写与流量取证#4.3 明文攻击|12 章 4.3]]的 bkcrack 攻的就是它。

另一代是 **WinZip AES**：条目的 method 字段写 **99**，真实的压缩方法与 AES 参数写进 extra 字段。造三种包对照（stored 与 deflate 用 zipfile，AES 用 7z）：

```python
# build_methods.py —— 造 stored / deflate / AES256 三种 zip
import subprocess
import zipfile

open("data.txt", "w").write("A" * 200)

with zipfile.ZipFile("m_stored.zip", "w", zipfile.ZIP_STORED) as z:
    z.write("data.txt")
with zipfile.ZipFile("m_deflate.zip", "w", zipfile.ZIP_DEFLATED) as z:
    z.write("data.txt")
subprocess.run(["7z", "a", "-tzip", "-mem=AES256", "-pcrypt123",
                "m_aes.zip", "data.txt"])
```

输出（7z 造 AES 包的尾部）：

```
Add new data to archive: 1 file, 200 bytes (1 KiB)

Files read from disk: 1
Archive size: 216 bytes (1 KiB)
Everything is Ok
```

再读三个包第一个条目的 method 与 extra 字段：

```python
# read_methods.py —— 读 LFH 的 method 与 extra 字段
import zipfile

def u16(b, o):
    return int.from_bytes(b[o:o + 2], "little")

for fn in ("m_stored.zip", "m_deflate.zip", "m_aes.zip"):
    d = open(fn, "rb").read()
    p = d.find(b"PK\x03\x04")
    method = u16(d, p + 8)
    nlen, elen = u16(d, p + 26), u16(d, p + 28)
    extra = d[p + 30 + nlen:p + 30 + nlen + elen]
    print(f"{fn:14s} method={method:<3d} extra={extra.hex(' ') if extra else '(空)'}")
```

### 3.4 "unsupported compression method" 的展开

[[12-隐写与流量取证#9. 常见问题|12 章 9 节]]的常见问题表里有一句："unsupported compression method 不是伪加密，是压缩算法问题"。这里把最常见的 AES 场景展开说清：这条报错在 AES 包上有三种形态——unzip（6.00）报 `need PK compat. v5.1 (can do v4.6)`，部分构建报 `unsupported compression method 99`；zipfile 不给口令报 `RuntimeError`，给了**正确**口令也只报 `NotImplementedError`——Python 标准库压根没实现 WinZip AES。==口令对不对与支不支持是两件事==。

能开 AES zip 的工具：**7z 带 `-p` 口令**（上面已通过）、WinZip 本家、个别编译了 AES 支持的 unzip。做题直接用 7z；同理，method 12/14/93 一类新算法也优先交给 7z。

## 4. 伪加密：标志位的四种组合

标志位偏移（LFH 签名 +6、CDH 签名 +8）与"两处都要改"的翻转函数是 [[12-隐写与流量取证#4.2 伪加密|12 章 4.2]]的内容，这里只引用。本节补上 12 章没有的问题：**只改其中一处会怎样？不同工具看的是哪一处？**造四个包：全 0（正常）、全 1、只 LFH 置 1、只 CDH 置 1，然后让三方工具逐个表态。

```python
# build_pseudo.py —— 造四种标志组合，逐个测三方工具
import subprocess
import zipfile

DEVNULL = subprocess.DEVNULL

def u16(b, o):
    return int.from_bytes(b[o:o + 2], "little")

def build(path):
    with zipfile.ZipFile(path, "w", zipfile.ZIP_DEFLATED) as z:
        z.writestr("flag.txt", "flag{n0t_really_encrypted}")

def set_flag_bits(zbytes, lfh_on, cdh_on):
    """偏移见 12 章 4.2：LFH 在签名 +6，CDH 在签名 +8；on 传 False 即清零"""
    b = bytearray(zbytes)
    i = 0
    while (i := b.find(b"PK\x03\x04", i)) >= 0:
        b[i + 6] = (b[i + 6] | 1) if lfh_on else (b[i + 6] & 0xFE)
        i += 4
    i = 0
    while (i := b.find(b"PK\x01\x02", i)) >= 0:
        b[i + 8] = (b[i + 8] | 1) if cdh_on else (b[i + 8] & 0xFE)
        i += 4
    return bytes(b)

build("p_ok.zip")
base = open("p_ok.zip", "rb").read()
for name, (l, c) in {"p_both.zip": (1, 1), "p_lfh.zip": (1, 0),
                     "p_cdh.zip": (0, 1)}.items():
    open(name, "wb").write(set_flag_bits(base, l, c))

print("标志字节（LFH / CDH）：")
for fn in ("p_ok.zip", "p_both.zip", "p_lfh.zip", "p_cdh.zip"):
    d = open(fn, "rb").read()
    i = d.find(b"PK\x03\x04")
    j = d.find(b"PK\x01\x02")
    print(f"  {fn:<11} LFH=0x{u16(d, i + 6):02x}  CDH=0x{u16(d, j + 8):02x}")
print()

print("== unzip -t -P ''（喂空口令，不进交互）==")
for fn in ("p_ok.zip", "p_both.zip", "p_lfh.zip", "p_cdh.zip"):
    r = subprocess.run(["unzip", "-t", "-P", "", fn], capture_output=True,
                       text=True, stdin=DEVNULL)
    txt = " / ".join(ln.strip() for ln in (r.stdout + r.stderr).splitlines()
                     if ln.strip())
    print(f"{fn:<11} {txt}")

print()
print("== 7z t（无口令）==")
for fn in ("p_ok.zip", "p_both.zip", "p_lfh.zip", "p_cdh.zip"):
    r = subprocess.run(["7z", "t", fn], capture_output=True, text=True,
                       stdin=DEVNULL)
    txt = (r.stdout + r.stderr).strip().splitlines()
    print(f"{fn:<11} {txt[-1] if txt else '(无输出)'}")

print()
print("== 7z l（无口令）==")
for fn in ("p_ok.zip", "p_both.zip", "p_lfh.zip", "p_cdh.zip"):
    r = subprocess.run(["7z", "l", fn], capture_output=True, text=True,
                       stdin=DEVNULL)
    names = [ln.split()[-1] for ln in r.stdout.splitlines()
             if ln.strip().endswith(".txt")]
    print(f"{fn:<11} 列出: {names}")

print()
print("== zipfile.read ==")
for fn in ("p_ok.zip", "p_both.zip", "p_lfh.zip", "p_cdh.zip"):
    try:
        out = zipfile.ZipFile(fn).read("flag.txt")
        print(f"{fn:<11} 正常读出: {out.decode()}")
    except Exception as e:
        print(f"{fn:<11} {type(e).__name__}: {e}")
```

- ==unzip 与 zipfile 看 CDH 的标志位，7z 解数据时看 LFH 的标志位==。只改一处，工具之间就会出现"它能开、我不能开"的分歧。
- `7z l` 只读中央目录、不解数据，所以==四个包它都列得出文件名==——"要口令但 7z 能列表"正是伪加密的第一信号。
- `7z t` 对 p_cdh 报 `Headers Error`：它按 LFH 的标志 0 去按明文解析，与 CDH 的置位冲突。

### 4.1 修复与验证

修复就是把两处 bit0 清零（`set_flag_bits` 的 `on` 传 `False` 即清零，与 [[12-隐写与流量取证#4.2 伪加密|12 章 4.2]]的翻转函数是同一个函数的两个方向）：

```python
# fix_pseudo.py —— 清零两处标志位并逐工具读回
import subprocess
import zipfile

def u16(b, o):
    return int.from_bytes(b[o:o + 2], "little")

def clear_flag_bits(zbytes):
    b = bytearray(zbytes)
    i = 0
    while (i := b.find(b"PK\x03\x04", i)) >= 0:
        b[i + 6] &= 0xFE
        i += 4
    i = 0
    while (i := b.find(b"PK\x01\x02", i)) >= 0:
        b[i + 8] &= 0xFE
        i += 4
    return bytes(b)

fixed = clear_flag_bits(open("p_both.zip", "rb").read())
open("p_fixed.zip", "wb").write(fixed)
d = open("p_fixed.zip", "rb").read()
i = d.find(b"PK\x03\x04")
j = d.find(b"PK\x01\x02")
print(f"修复后标志字节：LFH = 0x{u16(d, i + 6):02x}，CDH = 0x{u16(d, j + 8):02x}")
r = subprocess.run(["unzip", "-t", "-P", "", "p_fixed.zip"],
                   capture_output=True, text=True)
print("$ unzip -t -P '' p_fixed.zip")
print((r.stdout + r.stderr).rstrip())
print(f"zipfile 读出: {zipfile.ZipFile('p_fixed.zip').read('flag.txt').decode()}")
```

输出：

```
修复后标志字节：LFH = 0x00，CDH = 0x00
$ unzip -t -P '' p_fixed.zip
Archive:  p_fixed.zip
    testing: flag.txt                 OK
No errors detected in compressed data of p_fixed.zip.
zipfile 读出: flag{n0t_really_encrypted}
```

`unzip -t` 的判据就在这两行输出里：==末尾 `No errors detected in compressed data` 意味着解压出的数据 CRC 全部对上==，伪加密修复到此完成。修复后若仍要口令，检查是不是只清了一处；修复后 CRC 报错，看下一条。

> [!warning] 反方向：真加密被抹了标志
> 把真加密包（如 5.2 的 flag.zip）的两处 bit0 清零，unzip 不会要口令，而是直接报 CRC 错：`bad CRC 836c5a2d  (should be 8fca7b03)`，并提示 `ucsize 13 <> csize 25 for STORED entry`（解压后大小与压缩后大小对不上）。==CRC 对不上且报错发生在"解压之后"，说明数据本身是密的==——把标志位改回去，按真加密处理（第 5、6 节），不要在伪加密的路上浪费时间。

## 5. bkcrack 已知明文攻击：完整流程

### 5.1 原理与明文从哪里来

ZipCrypto 的内部状态是三个 32 位数，由口令初始化。Biham 与 Kocher 在 1994 年给出已知明文攻击：拿到足够多的"明文字节 ↔ 密文字节"对应关系，就能恢复这三个内部数，之后整个包可以解，不需要口令。[[12-隐写与流量取证#4.3 明文攻击|12 章 4.3]]记了标准命令，这里展开全部细节。

三条前提：

1. **只对 ZipCrypto 有效**。AES 包（3.2 的 method 99）不存在这条攻击——AES-256 没有可用的已知明文攻击。
2. **至少 12 字节已知明文**（bkcrack 的报错原文就是 minimum is 12），bkcrack 还会自动把加密头里的校验字节算进去；连续明文越多，筛选越狠、攻击越快（5.3 有量级对照）。
3. **明文必须是"压缩后的数据"**。`-c` 指定的条目如果用了 deflate，密文是 deflate 流，`-p`/`-x` 给的也必须是 deflate 流里的对应字节。图片、音视频这类本就压缩过的数据通常以 stored 收进 zip，流里就是原字节，签名直接可用；文本条目则需要"孪生包"（见 5.2）。

适用场景（[[12-隐写与流量取证#4.3 明文攻击|12 章 4.3]]）：题面直接给了某个原文件；或包里塞了公开可下载的东西。==先找明文，再想爆破==。

### 5.2 完整流程：造包 → 恢复密钥 → 解出全包

造靶：readme.txt 是"公开文件"（原文在手，600 字节），secret.txt 藏 flag，两个条目一起用 `zip -P` 加密（`zip -e` 是交互式问两遍口令，脚本里用 `-P` 直接收口令，效果相同）：

```bash
$ zip -P temp flag.zip readme.txt secret.txt
  adding: readme.txt (deflated 66%)
  adding: secret.txt (stored 0%)
```

deflate 条目需要孪生包：同一个文件、同样的压缩工具与设置、不加密。两个包里 readme.txt 的压缩率一致（66%），压缩流才对得上：

```bash
$ zip plain.zip readme.txt
  adding: readme.txt (deflated 66%)
```

已知明文攻击。`-C` 加密包、`-c` 密文条目，`-P` 孪生包、`-p` 明文条目（bkcrack 自己从孪生包里取压缩字节）；`-j 32` 开 32 线程（bkcrack 按 [[M01-MISC导论与工具箱|M01]] 2.2 源码编译的产物调用，下文简写为 bkcrack）：

```bash
$ bkcrack -C flag.zip -c readme.txt -P plain.zip -p readme.txt -j 32
```

输出（中间的进度行略去）：

```
bkcrack 1.8.1 - 2025-10-25
[19:41:20] Z reduction using 199 bytes of known plaintext
[19:41:21] Attack on 40375 Z values at index 6
（中间的进度行略去，12.6% 处命中）
Keys: a43e0218 403b0056 1c7700c7
Found a solution. Stopping.
You may resume the attack with the option: --continue-attack 5092
[19:41:22] Keys
a43e0218 403b0056 1c7700c7
```

readme.txt 压缩后 206 字节（600 字节原文 deflated 66%），其中 199 字节参与了筛选（`Z reduction using 199 bytes`），候选 Z 值只剩 40375 个，整体 1.6 秒结束，输出三段 32 位密钥。拿到密钥后解出整个包：

```bash
$ bkcrack -C flag.zip -D flag_plain.zip -k a43e0218 403b0056 1c7700c7
```

输出：

```
bkcrack 1.8.1 - 2025-10-25
[19:41:22] Writing decrypted archive flag_plain.zip

100.0 % (2 / 2)
```

`-D` 把每个条目解密后另存为一个新 zip，条目一个不少。新包不再要口令，直接解压：

```bash
$ unzip -o flag_plain.zip -d out_plain
Archive:  flag_plain.zip
  inflating: out_plain/readme.txt
  extracting: out_plain/secret.txt
$ cat out_plain/secret.txt
flag{kn0wn_pl4intext_att4ck}
```

> [!note] 密钥由口令唯一决定
> 5.3 的另一个包（口令同样是 temp）攻击得到的是同一组密钥 `a43e0218 403b0056 1c7700c7`——==同一口令在任意 ZipCrypto 包里对应同一组内部密钥==。这也解释了为什么 `-k` 三段数可以直接跨包使用，以及 5.4 的口令反推为什么可行。

### 5.3 只有文件头：-x 部分明文

包里只有一个 PNG、没有原文？PNG 的头 16 字节是固定的：8 字节签名 `89 50 4E 47 0D 0A 1A 0A`，加 4 字节 IHDR 长度 `00 00 00 0D`（IHDR 数据恒为 13 字节），加 4 字节 `IHDR`。把 PNG 以 **stored** 收进包（`zip -0`，压缩数据本就不该再压），流里第 0 字节起就是这 16 个字节：

```bash
$ zip -P temp -0 img.zip sample.png
  adding: sample.png (stored 0%)
```

先看明文不够 12 字节的报错——`-x` 是"偏移 + 十六进制数据"，只给 8 字节签名时（bkcrack 自动补上加密头的校验字节后共 9 字节）：

```bash
$ bkcrack -C img.zip -c sample.png -x 0 89504e470d0a1a0a
```

输出：

```
bkcrack 1.8.1 - 2025-10-25
Data error: not enough plaintext (9 bytes available, minimum is 12).
```

补到 16 字节连续明文（签名 + 长度 + IHDR），发起攻击：

```bash
$ bkcrack -C img.zip -c sample.png -x 0 89504e470d0a1a0a0000000d49484452 -j 32
```

输出（中间的进度行略去）：

```
bkcrack 1.8.1 - 2025-10-25
[19:14:48] Z reduction using 9 bytes of known plaintext
[19:14:49] Attack on 682977 Z values at index 6
（中间的进度行略去，31.8% 处命中）
Keys: a43e0218 403b0056 1c7700c7
Found a solution. Stopping.
You may resume the attack with the option: --continue-attack 216900
[19:15:45] Keys
```

三段密钥与 5.2 完全一致（同一口令）。量级对照：连续明文从 199 字节缩到 16 字节，候选 Z 值从 40375 涨到 682977，耗时从 1.6 秒涨到约 56 秒（同为 32 线程）。==明文越少，枚举空间越大==；如果还能补上 IHDR 里的宽高、位深、颜色类型等字节（出题人图片规格常见、可猜），每次补一个字段都是一次提速。

> [!warning] -x 的偏移在压缩流里
> `-x` 的偏移是相对该条目**压缩后数据**的。deflate 条目的流里没有 PNG 签名——那些字节被压缩过了。所以本节的靶子必须 `-0` 收进包。遇到 deflate 条目只有文本可猜的情况，把猜的内容按同样方式压缩后按偏移喂给 `-x`，或直接回到 5.2 的孪生包路线。

### 5.4 -r：从密钥反推短口令

拿到密钥后，bkcrack 能反推"能产生这组密钥的口令"，`-r` 指定长度上限与字符集（`?l` 小写字母、`?d` 数字、`?a` 字母数字等）：

```bash
$ bkcrack -C flag.zip -k a43e0218 403b0056 1c7700c7 -r 4 ?l
```

输出：

```
bkcrack 1.8.1 - 2025-10-25
[19:41:22] Recovering password
length 0-6...
Password: temp
Found a solution. Stopping.
[19:41:22] Password
as bytes: 74 65 6d 70

```

造包用的口令 temp 被原样找回来了。==密钥反推只对短口令现实==（bkcrack 的反推上限在 6 位左右），长口令对应的密钥组太大；反过来，这也意味着短口令的包拿密钥反推比字典爆破更直接。

### 5.5 什么时候想起明文攻击

按成本排序的决策路径：

1. 题面或附件目录里出现了包内某文件的**原件**——直接 5.2；
2. 包里是**公开可下载**的内容（某软件 readme、系统文件）——搜到原件即 5.2；
3. 包里是**标准格式文件**（PNG 等）——16 字节保底明文走 5.3；
4. 什么明文都没有——第 6 节爆破，或回到题目描述找口令线索。

反推口令（5.4）放在攻击成功之后顺手做；口令本身常常是下一层套娃的钥匙。

## 6. 口令爆破工程化：zip2john 与 john

[[12-隐写与流量取证#4.1 爆破：zipfile 口令循环|12 章 4.1]]的 zipfile 口令循环负责纯数字短口令——千级候选 Python 秒杀。真实赛题的口令是字典词或带规则的串，交给 john（或 hashcat）：zip2john 把加密包转成 john 能吃的哈希行，john 挂字典跑。

### 6.1 完整一遍

造一个用字典词加密的包，走 zip2john → john → --show：

```bash

$ zip2john lock.zip
```

输出：

把输出整行存进 ziphash.txt（john 接受 zip2john 的完整输出行），然后挂字典：


输出：

`banana` 命中。`2184Kp/s` 是每秒尝试的候选数——PKZIP 的验证只需要两个校验字节，速度在百万级。已破解的口令随时可查：



> [!info]- zip2john 的哈希行怎么读
> `:...:` 之间是哈希本体：`$pkzip$` 开头、`$/pkzip$` 结尾，字段按 `*` 分隔。开头的 `1` 是条目数，随后每个条目一组参数——压缩方法、压缩后长度（0x22 = 34）、解压后长度（0x16 = 22）、CRC、时间戳校验字节（`9af6`，对应 stderr 行里的 `TS_chk`）和一小段密文。ZipCrypto 的验证只需加密头 12 字节里的两个校验字节，所以哈希行里密文片段很短。行尾的 `flag.txt:lock.zip` 是条目名与来源包名，`--show` 时用来定位。需要完整读法时查 john 源码 `pkzip_fmt_plug.c` 的注释。

> [!note] 字典与规则
> `/usr/share/john/password.lst` 是 john 自带的小字典，做演示够用；实战换 rockyou.txt。john 还支持 `--rules` 派生规则（首字母大写、尾部加数字等）；GPU 环境用 hashcat 的 PKZIP 模式（`-m 17200` 系列）。注意 PKZIP 的速度是百万级每秒（见上方 `2184Kp/s`），RAR 则慢三个数量级（7.4 节对照）——==能走明文攻击的包，不要花时间爆破==。

## 7. RAR：两种魔数与两代加密

### 7.1 RAR4 与 RAR5

RAR 有两代格式，魔数差别在第七字节（[[12-隐写与流量取证#2. 文件格式与魔数|12 章 2 节]]魔数表的展开）：

| 格式 | 文件头 | file 输出 |
| ---- | ---- | ---- |
| RAR4 | `52 61 72 21 1A 07 00`（7 字节） | `RAR archive data, v4` |
| RAR5 | `52 61 72 21 1A 07 01 00`（8 字节） | `RAR archive data, v5` |

==第七字节 `00`/`01` 是分水岭==，`file` 据此报 v4/v5。结构上，RAR4 的块头是 7 字节定长（CRC16 + 类型 + 标志 + 大小）；RAR5 改用可变长整数（vint），块头长度字段含自身，加密信息放进专门的加密头块。做题时认魔数、报版本就够，块结构细节仅在手写 RAR 解析器时才需要：

> [!info]- 两代块结构的差异（细节）
> RAR4 块头 7 字节：HEAD_CRC(2, 对头部的 CRC32 低 16 位)、HEAD_TYPE(1)、HEAD_FLAGS(2)、HEAD_SIZE(2，定长字段区域)。文件块的头部之后固定接压缩前后大小、CRC32、时间、压缩版本等字段。
> RAR5 的块头以 vint（每字节 7 位有效、最高位续传）依次存类型、标志、大小，大小字段把自身算进去；额外的字段（哈希类型、加密参数、文件名）按标志位有选择地出现。加密的 RAR5 用 PBKDF2-HMAC-SHA256 派生密钥（7.4 的爆破速度因此掉三个数量级）。
> 加密强度：RAR4 用 AES-128，RAR5 用 AES-256。

## 8. 套娃自动化

### 8.1 四层靶

压缩包的常见形态是套娃：zip 里一个 gz，gz 里一个 tar，tar 里一个 7z。造一个四层靶（由内向外：flag.txt → 7z → tar → gz → zip）：

```bash
$ 7z a -t7z inner.7z flag.txt          # 第 1 层：7z 包住 flag.txt
$ tar cf mid.tar inner.7z              # 第 2 层：tar 包住 7z
$ gzip -c mid.tar > mid.tar.gz         # 第 3 层：gzip 压 tar
$ zip outer.zip mid.tar.gz             # 第 4 层：zip 包住 gz
$ file -b outer.zip mid.tar.gz mid.tar inner.7z
```

输出（zip 那步打印 `adding: mid.tar.gz (stored 0%)`——gzip 的产物压不动了，zip 自动改用 stored，3.1 的 method 0 正是这种场合）：

```
Zip archive data, made by v3.0 UNIX, extract using at least v1.0, last modified Oct 24 2026 19:32:40, uncompressed size 270, method=store
gzip compressed data, was "mid.tar", last modified: Sat Oct 24 11:32:39 2026, from Unix, original size modulo 2^32 10240
POSIX tar archive (GNU)
7-zip archive data, version 0.4
```

### 8.2 通用自动解包脚本

四层靶逐层手拆是四条命令，套娃题的实际深度不可预期。按第 1 节的动作顺序写成一个循环脚本：`file` 识别真身 → 按类型解压到下一层目录 → 对解出的每个文件回到识别 → 直到队列里没有压缩包、或扫到 flag：

```python
# auto_unpack.py —— 通用自动解包：识别 → 按类型解压 → 循环
import os
import re
import subprocess

FLAG_RE = re.compile(rb"flag\{[^}]{1,64}\}")
KINDS = [("zip", "Zip archive"), ("rar", "RAR archive"), ("7z", "7-zip archive"),
         ("gzip", "gzip compressed"), ("bzip2", "bzip2 compressed"),
         ("xz", "XZ compressed"), ("tar", "tar archive")]


def kind_of(path):
    """问 file 要真身，映射成解压动作类型"""
    t = subprocess.run(["file", "-b", path], capture_output=True,
                       text=True).stdout.strip()
    for k, pat in KINDS:
        if pat in t:
            return k, t
    return None, t


def extract(path, k, dest):
    """把压缩包解到 dest，返回解出的全部文件"""
    os.makedirs(dest, exist_ok=True)
    if k in ("zip", "7z", "rar"):
        subprocess.run(["7z", "x", "-y", "-o" + dest, path], capture_output=True)
    elif k == "tar":
        subprocess.run(["tar", "xf", path, "-C", dest], capture_output=True)
    elif k in ("gzip", "bzip2", "xz"):
        # 单文件流压缩：-dc 读到标准输出，不依赖文件名后缀
        prog = {"gzip": "gzip", "bzip2": "bzip2", "xz": "xz"}[k]
        stem = re.sub(r"\.(gz|bz2|xz)$", "", os.path.basename(path)) or "out"
        out = os.path.join(dest, stem)
        with open(out, "wb") as f:
            subprocess.run([prog, "-dc", path], stdout=f,
                           stderr=subprocess.DEVNULL)
    return sorted(os.path.join(root, fn)
                  for root, _, fns in os.walk(dest) for fn in fns)


def auto_unpack(path, max_depth=10):
    queue = [path]
    for depth in range(1, max_depth + 1):
        if not queue:
            print("候选队列已空，结束")
            return
        nxt = []
        for f in queue:
            k, t = kind_of(f)
            print(f"[{depth}] {f}: {t}")
            if k is None:
                m = FLAG_RE.search(open(f, "rb").read())
                if m:
                    print(f"[flag] {m.group().decode()}  <-  {f}")
                    return
                print("    不是压缩包，跳过")
                continue
            nxt += extract(f, k, os.path.join(os.path.dirname(f), f"L{depth}"))
        queue = nxt
    print(f"超过深度上限 {max_depth}，停止")
```

跑一遍：

```bash
$ python3 -c "from auto_unpack import auto_unpack; auto_unpack('outer.zip')"
```

输出：

```
[1] outer.zip: Zip archive data, made by v3.0 UNIX, extract using at least v1.0, last modified Oct 24 2026 19:32:40, uncompressed size 270, method=store
[2] L1/mid.tar.gz: gzip compressed data, was "mid.tar", last modified: Sat Oct 24 11:32:39 2026, from Unix, original size modulo 2^32 10240
[3] L1/L2/mid.tar: POSIX tar archive (GNU)
[4] L1/L2/L3/inner.7z: 7-zip archive data, version 0.4
[5] L1/L2/L3/L4/flag.txt: ASCII text
[flag] flag{unp4ck_all_th3_w4y}  <-  L1/L2/L3/L4/flag.txt
```

四层、七行日志，flag 已定位。脚本有几个刻意的决定：`max_depth` 限制循环（防自造的无限套娃或恶意构造的 zip 炸弹）；每层解压到独立目录（防同名文件互相覆盖）；对非压缩包文件做一次 flag 正则扫描（[[M01-MISC导论与工具箱|M01]] 4.2 的二进制正则），flag 可能藏在任何一层；KINDS 表按子串匹配，模式串互不为彼此的子串，新增格式加一行即可。

### 8.3 识别顺序与重命名坑

两个容易踩的细节：

1. **gunzip 要求后缀**。把 mid.tar.gz 复制成无后缀的 blob，`gunzip` 直接拒绝：
   `gzip: blob: unknown suffix -- ignored`。`file` 照样认得它（gzip 头里还存着原始文件名 `was "mid.tar"`）。两条路：改名补后缀，或用 `gzip -dc blob > blob.out` 读到标准输出——auto_unpack 的 gzip 分支用的就是后者，所以脚本对改名问题免疫。
2. **识别顺序按"从特殊到一般"写**。`file` 对 `.tar.gz` 这类组合只会报最外层（gzip compressed data），解开后才会暴露里面的 tar——auto_unpack 的队列天然按层推进，不需要预判；要是想用 7z 一把梭（`7z x` 能吃 zip/gz/tar/rar 大多数格式），也成立，代价是日志里看不出每层的类型变化。

> [!warning] zip 炸弹
> 递归解包脚本一定要有深度与总量上限。42.zip 一类的经典炸弹，六层 zip 套娃解压出 4.3 PB 数据。`max_depth` 是第一道闸；更严格的做法在 extract 里累计解压字节数，超限即停。

## 9. 常见问题

| 现象 | 原因与解决 |
| ---- | ---- |
| `unzip` 报 `unsupported compression method 99` 或 `need PK compat. v5.1` | WinZip AES 加密的 zip（3.4 节）。`7z x -p口令` 解；给对口令也没用的 zipfile 同理是支持问题不是口令问题 |
| zipfile 给对口令仍报 NotImplementedError | Python 标准库未实现 AES zip（3.4 节），换 7z |
| 伪加密改了标志还报错 | 两处标志位都要清（LFH +6、CDH +8）；unzip/zipfile 看 CDH、7z 看 LFH，只清一处会出现部分工具能开的假象（4 节对照表） |
| 清了标志反而报 bad CRC | 真加密被伪装成未加密（4.1 节警告）。把标志改回去，走明文攻击或爆破 |
| bkcrack 报 `not enough plaintext (minimum is 12)` | 已知明文不足 12 字节。用 `-x` 偏移补标准文件头字节，或找同文件的完整明文（5.3 节） |
| bkcrack 报 `ciphertext is smaller than plaintext` | `-p` 给的是未压缩原文，而条目是 deflate。打一个不加密的孪生包用 `-P` 喂（5.2 节） |
| bkcrack 出了密钥，`-d` 解出来是乱码 | 明文与密文偏移没对齐：`-x` 偏移错、孪生包压缩设置与原包不同、或把未压缩数据喂给了 deflate 条目。先用已命中的条目确认密钥，再扩展 |
| john 报 no hash loaded | 哈希行不完整或被 zip2john 注释掉了；或格式名不对：zip 用 PKZIP、RAR5 用 rar5、RAR4 用 rar（6、7 节） |
| `7z` 解 RAR 报 `Unsupported Method` | 该构建不带 RAR 解压 codec，或包是新版 rar 造的新压缩算法（7.3 节）。用 unrar 解；老 unrar 开不了新包就升级 unrar |
| `7z` 解加密 zip 时停在交互问口令 | 脚本与批处理里用 `-p口令` 直接给（3.3、4 节的输出都这么喂）；伪加密时 `7z l` 列表正常、解压才要口令 |
| `7z l` 一个条目都列不出、只等口令 | -hp 或整包加密（7.3 节）：文件名表也密了，必须先有口令 |
| unzip 解出中文文件名乱码 | Windows 下打包常用 GBK 文件名：`unzip -O GBK x.zip` 指定编码，或改用 7z |
| `gunzip` 报 `unknown suffix -- ignored` | 文件名不带 .gz 后缀。`gzip -dc 文件 > 输出` 重定向，或先改名（8.3 节） |
| 大 zip（>4 GB / >65535 条目）老工具打不开 | ZIP64 格式（2.5 节），升级 7z / unzip |
| 题目给的是自解压 exe | SFX = 压缩包粘了个引导头，`7z x` 直接解；或 binwalk 分离出包再处理（[[12-隐写与流量取证#8. 磁盘与内存取证一瞥\|12 章 8.1]]） |
