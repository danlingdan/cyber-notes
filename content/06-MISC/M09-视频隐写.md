# M09 视频隐写
## Video Steganography

> [!info]- 章节信息
> **所属方向**：MISC ｜ **难度阶段**：L2 核心期 ｜ **前置要求**：[[12-隐写与流量取证|12 章]] · [[M03-文件格式深拆II-JPEG与GIF|M03]] · [[M05-图片隐写I-LSB与位平面|M05]]
> **本章目标**：把视频当"容器 + 编码"两层来拆——会读 MP4 的 box 树，会跑 ffmpeg/ffprobe 的流清单、拆帧、分离与合成工作流；算清逐帧隐写在有损压缩下的死路与两条活路；掌握帧间信息、字幕轨、容器尾部三类夹带的造靶与拆解。

## 1. 定位：从图片到视频

视频的文件结构分两层：外层是容器（本章用 MP4），内层是编码（本章用 H.264）。[[12-隐写与流量取证|12 章]]的解题总流程照常起步：file 认真身、xxd 看头尾、binwalk 扫签名，这套动作在 [[M01-MISC导论与工具箱|M01]] 5 节已经工程化。图片系列把像素层拆透了：LSB 与位平面在 [[M05-图片隐写I-LSB与位平面|M05]]，动图的帧结构、拆帧与帧延迟在 [[M03-文件格式深拆II-JPEG与GIF|M03]]。

视频的增量只有一句话：==帧在进容器之前先被编码器压过一遍==。这一层改变了隐写的选址逻辑——藏在像素细节里的信息，要先问自己能不能活着穿过压缩；藏在帧的组织方式里的信息（帧的数量、类别、节奏、轨道清单），压缩管线碰不到它。本章就按这个逻辑展开：先拆容器（第 2 节）与工具流（第 3 节），再算逐帧隐写的有损账（第 4 节），然后把选址挪到帧间（第 5 节）、字幕轨（第 6 节）与容器尾部（第 7 节）。

本章所有靶子现场自造，素材是 8 张 64×48 的程序噪声图，ffmpeg 与 ffprobe 随 [[M01-MISC导论与工具箱|M01]] 的装机清单一起就位。

## 2. MP4 容器：box 树

MP4 属于 ISO Base Media File Format 家族，组织方式和 [[M02-文件格式深拆I-PNG全解|M02]] 的 PNG 同族：整棵文件是一棵带类型的树。PNG 里叫 chunk，MP4 里叫 box。每个 box 的开头是三件东西：

==box = 4 字节大端大小 + 4 字节类型 + 数据==

大小字段把这 8 字节头也算在内；类型是四个 ASCII 字符（ftyp、moov、mdat……）。box 分两种：**容器 box** 的数据区里装着子 box，一层层往下套；**叶 box** 的数据区是纯数据。解析 = 从偏移 0 读头，按大小跳到下一个 box，遇到容器就递归进去——套路与 [[M02-文件格式深拆I-PNG全解|M02]] 数 chunk 同源，区别是 box 没有 CRC，改坏了不会立刻报错。struct 的大端打包见 [[M01-MISC导论与工具箱#4.1 struct 的完整用法|M01 4.1]]。

解题要认识的 box 就这几个：

| box | 一句话 |
| ---- | ---- |
| ftyp | 文件类型声明（isom 等 brand），永远是第一个 box |
| free | 占位 box，内容被解析方忽略——缝隙夹带的候选位置（第 7 节） |
| mdat | 媒体数据本体，压缩后的视频帧、音频帧都堆在这里 |
| moov | 元数据容器，播放需要的全部索引在这棵子树里 |
| mvhd | moov 的头：总时长、时间刻度 |
| trak | 一条轨道，视频、音频、字幕各一条 |
| stbl | 采样表：每帧的大小、时间戳、在 mdat 里的偏移，播放器靠它取帧 |

moov 与 mdat 的分工一句话：mdat 是货，moov 是提货单。没有 moov，播放器面对一坨压缩字节无从下手。

### 2.1 造靶

```python
# build_targets.py —— 造本章基础素材：8 帧噪声 PNG → vonly.mp4 / base.mp4 / base_fast.mp4
import os
import shutil
import subprocess
from PIL import Image

os.chdir(os.path.dirname(os.path.abspath(__file__)))

shutil.rmtree("src", ignore_errors=True)
os.makedirs("src")
W, H, N = 64, 48, 8
for i in range(N):
    im = Image.new("RGB", (W, H))
    px = im.load()
    for y in range(H):
        for x in range(W):
            px[x, y] = ((x * 4 + i * 30) % 256, (y * 5 + i * 20) % 256, (x + y + i * 40) % 256)
    im.save(f"src/{i:04d}.png")


def run(*cmd):
    subprocess.run(cmd, check=True)


# [1] 纯视频：8 帧 @ 5 fps，libx264 有损合成
run("ffmpeg", "-y", "-loglevel", "error", "-framerate", "5", "-i", "src/%04d.png",
    "-c:v", "libx264", "-pix_fmt", "yuv420p", "vonly.mp4")

# [2] 视频加音频：同一条视频流，配 1.6 秒 440 Hz 正弦
run("ffmpeg", "-y", "-loglevel", "error", "-framerate", "5", "-i", "src/%04d.png",
    "-f", "lavfi", "-i", "sine=frequency=440:duration=1.6",
    "-c:v", "libx264", "-pix_fmt", "yuv420p", "-c:a", "aac", "-shortest", "base.mp4")

# [3] moov 挪到文件头：-c copy 不重编码，只重排容器布局
run("ffmpeg", "-y", "-loglevel", "error", "-i", "base.mp4",
    "-c", "copy", "-movflags", "+faststart", "base_fast.mp4")

for f in ("vonly.mp4", "base.mp4", "base_fast.mp4"):
    print(f, os.path.getsize(f), "字节")
```

输出：

```
vonly.mp4 2902 字节
base.mp4 18000 字节
base_fast.mp4 18000 字节
```

三份靶分工：vonly.mp4 只有视频轨，树短，用来完整看一遍结构；base.mp4 加了音轨，是第 3–7 节的主靶；base_fast.mp4 是 base.mp4 加 `-movflags +faststart` 重排的产物，moov 位置相反。

### 2.2 纯 Python box 树解析器

```python
# box_parse.py —— MP4 box 树解析器（第 7 节会 import 复用）
import struct

CONTAINERS = {"moov", "trak", "edts", "mdia", "minf", "dinf", "stbl", "mvex", "udta"}


def walk(data, start, end, depth, boxes, max_depth):
    """扫描 [start, end) 区间内的 box；返回 (走到的位置, 是否撞上不合法的 box 头)"""
    pos = start
    while pos + 8 <= end:
        size = struct.unpack(">I", data[pos:pos + 4])[0]
        typ = data[pos + 4:pos + 8].decode("latin-1")
        header = 8
        if size == 1:                       # 64 位扩展：真实大小在类型之后的 8 字节
            size = struct.unpack(">Q", data[pos + 8:pos + 16])[0]
            header = 16
        elif size == 0:                     # size=0：box 一直延伸到区间末尾
            size = end - pos
        if size < header or pos + size > end:
            return pos, True                # 大小字段不合法：box 树到此为止
        boxes.append((depth, typ, pos, size))
        if typ in CONTAINERS and depth < max_depth:
            walk(data, pos + header, pos + size, depth + 1, boxes, max_depth)
        pos += size
    return pos, False


def parse(path, top_only=False):
    """打印 box 树（top_only=True 只看顶级），返回 (文件字节, box 列表, 顶级覆盖终点)"""
    data = open(path, "rb").read()
    boxes = []
    top_end, bad = walk(data, 0, len(data), 0, boxes, 99)
    for depth, typ, off, size in boxes:
        if top_only and depth:
            continue
        print(f"{'  ' * depth}{typ:<6} off={off:<6} size={size}")
    if bad:
        print(f"box 树覆盖 0 ~ {top_end}，其后 {len(data) - top_end} 字节不属于任何 box")
    else:
        print(f"box 树覆盖 0 ~ {top_end}，与文件长度 {len(data)} 一致")
    return data, boxes, top_end


if __name__ == "__main__":
    print("== vonly.mp4 完整 box 树 ==")
    parse("vonly.mp4")
    print()
    print("== base.mp4 / base_fast.mp4 顶级对比 ==")
    parse("base.mp4", top_only=True)
    print()
    parse("base_fast.mp4", top_only=True)
```

逐行读这棵树：顶级是 ftyp、free、mdat、moov 四个 box；moov 里一条视频轨 trak 从 tkhd（轨道头）套到 mdia（轨道媒体）再到 minf（媒体信息），最底层的 stbl 挂着七个叶子——stsd 登记编码格式（H.264 的 avc1 住这里），stts/stss/ctts 登记时间与关键帧位置，stsc/stsz/stco 登记每帧在 mdat 里的排布；moov 末尾的 udta 是用户数据 box，编码器署名这类杂项住在它的 meta 子 box 里。base.mp4 有视频、音频两条 trak，树形相同、只是更长。第 5 节的帧级靶改的就是 stbl 里这些表。

moov 的位置对比一眼可见：base.mp4 的顶级顺序是 ftyp → free → mdat → moov，提货单垫在文件尾；base_fast.mp4 则是 ftyp → moov → free → mdat。moov 在头叫 faststart：网页播放器边下载边播，先拿到提货单才能播第一帧，moov 在尾就得等整个文件下载完。moov 在尾是 ffmpeg 的默认行为——写完全部媒体数据才能统计出每帧的索引；`+faststart` 不重编码，只把 moov 搬到前面、mdat 整体后移。=="视频本地能播、在线预览一直转圈"先想到 moov 位置==，一条 `ffmpeg -i in.mp4 -c copy -movflags +faststart out.mp4` 解决；对解题更重要的收获是最后那行汇总：==解析器顺手报告了"box 树覆盖不到的字节"，这就是第 7 节尾部夹带的探测器==。

> [!info]- 大文件的 64 位大小分支
> 大小字段 4 字节，最大表示 4 GB − 1。更大的 box 把 size 写成 1，真实的 8 字节大端大小跟在类型字段之后（box 头从 8 字节变 16 字节）；size 写 0 表示 box 一直延伸到文件尾。解析器里的两个分支处理的就是这两种特例：size == 1 时再读 8 字节，size == 0 时按剩余长度算。CTF 靶很少超 4 GB，但读别人的解析代码时要认得这两个约定。

## 3. ffmpeg 与 ffprobe 工作流

ffmpeg 负责转码与拆装，ffprobe 负责"只看不动手"的体检，两个是一套。本节的动作合在一个脚本 `workflow.py` 里，按四个部分依次展开。

### 3.1 ffprobe：流清单

```python
# workflow.py 第 1 部分 —— ffprobe 流清单
import os
import shutil
import subprocess

os.chdir(os.path.dirname(os.path.abspath(__file__)))


def run(*cmd):
    r = subprocess.run(cmd, capture_output=True, text=True)
    r.check_returncode()
    return (r.stdout + r.stderr).rstrip()


def extract(src, dst, extra=()):
    shutil.rmtree(dst, ignore_errors=True)
    os.makedirs(dst)
    subprocess.run(["ffmpeg", "-y", "-loglevel", "error", "-i", src, *extra, f"{dst}/%04d.png"],
                   check=True)
    return len(os.listdir(dst))


print("[1] ffprobe 流清单")
print(run("ffprobe", "-v", "error", "-show_entries",
          "stream=index,codec_type,codec_name,width,height,channels,sample_rate",
          "-of", "compact=p=0", "base.mp4"))
```

输出：

```
[1] ffprobe 流清单
index=0|codec_name=h264|codec_type=video|width=64|height=48
index=1|codec_name=aac|codec_type=audio|sample_rate=44100|channels=1
```

base.mp4 两条流：0 号视频 h264、1 号音频 aac。==流清单是发现"多出来的轨"的第一步==：第 6 节的字幕轨、真题里混进来的第二条音轨，都先在这份清单里现形。`-show_entries` 挑字段、`-v error` 关日志，输出就这几行；裸跑 `-show_streams` 会把每条流的上百个参数全部刷出来，翻起来很费劲。

### 3.2 拆帧与 -vsync 0

拆帧是视频题的第一动作：把每一帧落成 PNG，之后 [[M05-图片隐写I-LSB与位平面|M05]] 的全套图片手段直接接上。先合成一个变帧率（VFR）靶——每帧时长 0.2 秒和 1.0 秒交替，用 concat demuxer 的 `duration` 指令指定每张图的停留时长：

```python
# workflow.py 第 2 部分 —— VFR 靶与拆帧坑
lines = []
for i, d in enumerate([0.2, 1.0, 0.2, 1.0, 0.2, 1.0, 0.2, 1.0]):
    lines += [f"file 'src/{i:04d}.png'", f"duration {d}"]
open("list.txt", "w").write("\n".join(lines))
subprocess.run(["ffmpeg", "-y", "-loglevel", "error", "-f", "concat", "-safe", "0", "-i", "list.txt",
                "-vsync", "vfr", "-c:v", "libx264", "-pix_fmt", "yuv420p", "vfr.mp4"], check=True)
n = run("ffprobe", "-v", "error", "-select_streams", "v:0", "-count_frames",
        "-show_entries", "stream=nb_read_frames", "-of", "csv=p=0", "vfr.mp4")
print(f"vfr.mp4 帧数 {n}；默认拆帧 {extract('vfr.mp4', 'fr_def')} 张；"
      f"-vsync 0 {extract('vfr.mp4', 'fr_v', ('-vsync', '0'))} 张")
```

输出：

```
vfr.mp4 帧数 8；默认拆帧 23 张；-vsync 0 8 张
```

默认参数拆出 23 张，加 `-vsync 0` 才是 8 张。vfr.mp4 的帧间隔不均匀，ffmpeg 默认按恒定帧率重采样，长间隔的帧被复制成好几张、时序整个变形。[[M03-文件格式深拆II-JPEG与GIF#7.3 ffmpeg：拆帧与合成的延迟陷阱|M03 7.3]] 的 GIF 拆帧踩过同一个坑，MP4 的 VFR 源（屏录、慢动作、手机视频）同样会踩；base.mp4 这种恒定帧率（CFR）的源默认恰好一帧一张，但坑只在换源之后才引爆。

> [!warning] 拆帧先问帧数
> 提出来的帧数对不上预期，第一嫌疑就是重采样。先 `ffprobe -count_frames` 问源有几帧，再决定要不要 `-vsync 0`；凡是按帧数找规律的靶（第 5 节），一律带上 `-vsync 0`。新版 ffmpeg 会提示数字形式的 `-vsync 0` 已弃用，等价新写法是 `-fps_mode passthrough`，行为一致。

### 3.3 音视频分离与重合成

```python
# workflow.py 第 3 部分 —— 音视频分离
subprocess.run(["ffmpeg", "-y", "-loglevel", "error", "-i", "base.mp4", "-vn", "-c:a", "copy",
                "audio_only.m4a"], check=True)
subprocess.run(["ffmpeg", "-y", "-loglevel", "error", "-i", "base.mp4", "-an", "-c:v", "copy",
                "video_only.mp4"], check=True)
print(run("file", "audio_only.m4a", "video_only.mp4"))
print("audio_only.m4a:", run("ffprobe", "-v", "error", "-show_entries", "stream=codec_type",
                             "-of", "compact=p=0", "audio_only.m4a"))
print("video_only.mp4:", run("ffprobe", "-v", "error", "-show_entries", "stream=codec_type",
                             "-of", "compact=p=0", "video_only.mp4"))
```

输出：

```
audio_only.m4a: ISO Media, Apple iTunes ALAC/AAC-LC (.M4A) Audio
video_only.mp4: ISO Media, MP4 Base Media v1 [ISO 14496-12:2003]
audio_only.m4a: codec_type=audio
video_only.mp4: codec_type=video
```

`-vn` 丢弃视频只要音频，`-an` 反之；`-c copy` 让流原样搬运、不重编码，拆出的 m4a 直接进 [[M08-音频隐写|M08]] 的频谱与口令套路。反方向是把帧序列合回视频：

```python
# workflow.py 第 4 部分 —— 帧序列重合成：-framerate 决定按多快读图
subprocess.run(["ffmpeg", "-y", "-loglevel", "error", "-framerate", "5", "-i", "src/%04d.png",
                "-c:v", "libx264", "-pix_fmt", "yuv420p", "rebuilt.mp4"], check=True)
subprocess.run(["ffmpeg", "-y", "-loglevel", "error", "-i", "src/%04d.png",
                "-c:v", "libx264", "-pix_fmt", "yuv420p", "rebuilt25.mp4"], check=True)
subprocess.run(["ffmpeg", "-y", "-loglevel", "error", "-framerate", "5", "-i", "src/%04d.png",
                "-c:v", "libx264", "-pix_fmt", "yuv420p", "-r", "10", "rebuilt_r10.mp4"], check=True)
for f in ("rebuilt.mp4", "rebuilt25.mp4", "rebuilt_r10.mp4"):
    d = run("ffprobe", "-v", "error", "-show_entries", "format=duration", "-of", "csv=p=0", f)
    n = run("ffprobe", "-v", "error", "-select_streams", "v:0", "-count_frames",
            "-show_entries", "stream=nb_read_frames", "-of", "csv=p=0", f)
    print(f"{f} 时长 {d} 秒，帧数 {n}")
```

输出：

```
rebuilt.mp4 时长 1.600000 秒，帧数 8
rebuilt25.mp4 时长 0.320000 秒，帧数 8
rebuilt_r10.mp4 时长 1.600000 秒，帧数 16
```

同样 8 张 PNG，三种时长：`-framerate 5` 按 5 帧/秒读，1.6 秒；不写就是默认 25 帧/秒，8 帧被读成 0.32 秒；输出端的 `-r 10` 把读进来的每帧复制两份去凑 10 帧/秒，时长不变、帧数翻倍。==`-framerate` 管"按多快读这叠图"，`-r` 管"按多快播"==，合成帧序列时写错帧率，时间轴相关的一切都会跟着错。

## 4. 逐帧隐写与压缩的有损账

把 [[M05-图片隐写I-LSB与位平面|M05]] 的 LSB 搬进视频，想法很直接：视频本来就是一叠帧，每帧藏一点。但视频和 GIF 差一层——帧进容器前先过编码器，这一层决定逐帧 LSB 的死活。

### 4.1 有损合成：LSB 全灭

```python
# lsb_roundtrip.py 第 1 部分 —— 造帧藏 LSB（写入与提取共用的一对函数在第 2 部分登场）
import os
import shutil
import subprocess

import numpy as np
from PIL import Image

os.chdir(os.path.dirname(os.path.abspath(__file__)))
W, H, N = 64, 48, 8
MSG = b"flag{lsb_vs_h264}"                         # 17 字节
BITS = "".join(f"{b:08b}" for b in MSG) + "0" * 8  # 末尾 8 个 0 作结束哨兵


def make_stego():
    """8 帧噪声图，每帧的 R 通道最低位各藏一遍 MSG"""
    shutil.rmtree("stego", ignore_errors=True)
    os.makedirs("stego")
    for i in range(N):
        im = Image.new("RGB", (W, H))
        px = im.load()
        idx = 0
        for y in range(H):
            for x in range(W):
                r = (x * 7 + y * 13 + i * 29 + (x * y) % 251) % 256
                g = (x * 3 + y * 5 + i * 17) % 256
                b = (x * 11 + y * 2 + i * 23) % 256
                if idx < len(BITS):
                    r = (r & 0xFE) | int(BITS[idx])
                    idx += 1
                px[x, y] = (r, g, b)
        im.save(f"stego/{i:04d}.png")


def extract_frames(src, dst, extra=()):
    shutil.rmtree(dst, ignore_errors=True)
    os.makedirs(dst)
    subprocess.run(["ffmpeg", "-y", "-loglevel", "error", "-i", src, *extra, f"{dst}/%04d.png"],
                   check=True)
    names = sorted(os.listdir(dst))
    return [Image.open(os.path.join(dst, n)).convert("RGB") for n in names]


def extract_lsb(frames):
    """按帧序取每帧 R 通道最低位，8 位一组，遇到全 0 字节（哨兵）停"""
    out = bytearray()
    for im in frames:
        arr = np.array(im)[:, :, 0].flatten()
        by = np.packbits((arr & 1).astype(np.uint8)).tobytes()
        for byte in by:
            if byte == 0:
                return bytes(out)
            out.append(byte)
    return bytes(out)


make_stego()
print(f"[1] {len(MSG)} 字节消息藏进 8 帧各自的 R 通道最低位（每帧占 {len(BITS)} 位 / {W * H} 位容量）")
```

写入用的是 [[M05-图片隐写I-LSB与位平面#3. 提取组合全参数化|M05 3 节]]同一套参数：R 通道、最低位、按帧序行优先连写、8 位一组、全 0 字节哨兵，提取端原样读回。libx264 有损合成之后再提帧，读出来是乱码——帧 0 的 R 通道 3072 个像素里 3030 个被动过。原因在编码管线：==libx264 合成时像素要走 RGB → YUV 色彩空间转换、色度下采样（yuv420p 把色度分辨率砍半）和 DCT 量化，最低位的那点扰动在第一步就被抹掉==。

> [!info]- 连 -qp 0 都救不了走 YUV 的路

### 4.3 活路二：信息不进像素

像素细节靠不住，就把信息放到压缩管线动不了的地方——帧的组织方式。==压缩改得了"每帧内部长什么样"，改不了"总共几帧、每帧是什么、按什么节奏排"==。第 5 节的三类靶全部基于这个思路，它们在 yuv420p 有损合成下照样存活。

## 5. 帧间信息：把 flag 写进帧的组织方式

### 5.1 黑白帧靶：一帧一位

最经典的帧间靶：flag 逐位展开，1 → 白帧，0 → 黑帧，恒定帧率合成。黑白是纯色块，有损压缩压不坏它的亮度语义：

```python
# frame_bits.py 第 1、2 部分 —— 黑白帧靶：造靶、合成、提帧、还原
import os
import shutil
import subprocess

import numpy as np
from PIL import Image

os.chdir(os.path.dirname(os.path.abspath(__file__)))


def run(*cmd):
    r = subprocess.run(cmd, capture_output=True, text=True)
    r.check_returncode()
    return (r.stdout + r.stderr).rstrip()


print("[1] 造靶：flag 逐位展开，1 = 白帧，0 = 黑帧")
FLAG = b"flag{fr4m3_1s_data}"                    # 19 字节 = 152 位

for i, bit in enumerate(bits):
    Image.new("RGB", (64, 48), (255, 255, 255) if bit == "1" else (0, 0, 0)).save(f"bw/{i:04d}.png")
subprocess.run(["ffmpeg", "-y", "-loglevel", "error", "-framerate", "10", "-i", "bw/%04d.png",
                "-c:v", "libx264", "-pix_fmt", "yuv420p", "bw.mp4"], check=True)
```

输出：

```

[2] 提帧 → 逐帧平均亮度 → 比特流
```

解码链很短：提帧（照例 `-vsync 0`，帧数与源一致）→ 每帧转灰度算平均亮度 → 大于 128 记 1，否则记 0 → 8 位拼 1 字节。帧亮度落在 0 和 255 两端，阈值容错空间极大，有损合成后的黑帧亮度依然是 0、白帧依然是 255——这就是"信息不进像素细节"的直观形态。

> [!note] 常见变体
> 真题的变体是把黑白帧插在正常画面里（每 N 帧一个数据帧）、用红蓝两色代替黑白、或按帧数奇偶编码。识别特征是帧序列里出现规律的纯色帧或重复帧；提帧后先按帧序排好，再按题面规律取数据帧，判定逻辑不变。

### 5.2 关键帧选择

H.264 把帧分两类：I 帧（关键帧）携带完整画面，P/B 帧只存与前面帧的差异——单独渲染 P 帧是残缺的。出题人"只在关键帧里藏内容"时，要把 I 帧单独拎出来：

```python
# frame_bits.py 第 3 部分 —— 关键帧靶：ffprobe 读帧类型 + select 滤镜提取 I 帧
print("[3] 关键帧提取")
subprocess.run(["ffmpeg", "-y", "-loglevel", "error", "-framerate", "5", "-i", "src/%04d.png",
                "-c:v", "libx264", "-pix_fmt", "yuv420p", "-g", "2", "key.mp4"], check=True)
types = run("ffprobe", "-v", "error", "-select_streams", "v:0", "-show_entries", "frame=pict_type",
            "-of", "default=nw=1:nk=1", "key.mp4").split()
print("key.mp4 帧类型序列:", " ".join(types))
shutil.rmtree("kf", ignore_errors=True)
os.makedirs("kf")
subprocess.run(["ffmpeg", "-y", "-loglevel", "error", "-i", "key.mp4",
                "-vf", "select=eq(pict_type\\,I)", "-vsync", "0", "kf/%02d.png"], check=True)
print(f"select=eq(pict_type\\,I) 提出关键帧 {len(os.listdir('kf'))} 张 -> kf/")
```

输出：

```
[3] 关键帧提取
key.mp4 帧类型序列: I P I P I P I P
select=eq(pict_type\,I) 提出关键帧 4 张 -> kf/
```

`-g 2` 强制每 2 帧插一个关键帧（GOP 长度为 2），ffprobe 逐帧读出 pict_type 序列，select 滤镜按条件挑帧输出。filtergraph 里逗号是过滤器的分隔符，`eq(pict_type,I)` 的逗号必须写成 `\,`，否则 ffmpeg 会把 `I)` 当成下一个过滤器报错。日常视频的 GOP 长得多（几十到几百帧），关键帧占比更低，这一条对"只有少数帧画面完整"的题同样有用：把 I 帧和全量帧各提一份做对照，差异帧里可能另有内容。

### 5.3 帧时长

每帧的显示时长是帧间的另一个信息位。MP4 把它登记在 stbl 的 stts（采样时间增量表）里，ffprobe 用 `ffprobe -v error -select_streams v:0 -show_entries frame=pts_time,duration_time -of compact` 能逐帧读出时间戳与时长——拿它看 3.2 的 vfr.mp4，0.2 秒与 1.0 秒交替的节奏立刻现形。把 flag 编进帧间隔的靶与 [[M03-文件格式深拆II-JPEG与GIF#7.1 帧延迟靶|M03 7.1]] 的 GIF 帧延迟同类，只是 MP4 的时长藏在增量表里、读起来多一道换算，出题人用得少，识破即可。

## 6. 字幕轨夹带

MP4 可以挂字幕轨，mov_text 是 MP4 原生的字幕编码。字幕轨在播放器里默认不显示，ffprobe 的流清单里却一目了然——"看不见"正是它适合夹带的原因。

```python
# sub_track.py —— 字幕轨夹带全程
import os
import subprocess

os.chdir(os.path.dirname(os.path.abspath(__file__)))


def run(*cmd):
    r = subprocess.run(cmd, capture_output=True, text=True)
    r.check_returncode()
    return (r.stdout + r.stderr).rstrip()


SRT = """1
00:00:00,000 --> 00:00:00,600
第一条字幕：正文内容

2
00:00:00,600 --> 00:00:01,200
flag{m0v_text_track}

3
00:00:01,200 --> 00:00:01,600
第三条字幕：正文内容
"""
open("sub.srt", "w", encoding="utf-8").write(SRT)

print("[1] 合成带字幕轨的 MP4")
subprocess.run(["ffmpeg", "-y", "-loglevel", "error", "-i", "base.mp4", "-i", "sub.srt",
                "-c:v", "copy", "-c:a", "copy", "-c:s", "mov_text", "base_sub.mp4"], check=True)
print(run("ffprobe", "-v", "error", "-show_entries",
          "stream=index,codec_type,codec_name,width,height,channels,sample_rate",
          "-of", "compact=p=0", "base_sub.mp4"))
print()

print("[2] 提取字幕轨")
subprocess.run(["ffmpeg", "-y", "-loglevel", "error", "-i", "base_sub.mp4",

print(open("out.srt", encoding="utf-8").read())
```

输出：


三步：SRT 文件按"序号 + 时间轴 + 文本"写好，文本里夹 flag；合成时视频、音频 `-c copy` 原样搬运，字幕轨用 `-c:s mov_text` 编码进容器；提取时 `-map 0:s:0` 指定 0 号输入的第一条字幕流，落回 SRT 明文。3.1 的流清单在这里兑现价值：==末尾多出的 `codec_type=subtitle` 一行就是靶子露馅的时刻==。

## 7. 容器末尾夹带：box 树之外的字节

尾部粘文件在 [[12-隐写与流量取证#8.1 binwalk / foremost：分离嵌套文件|12 章 8.1]]讲过：播放器读完 moov 就收工，file 只看头部，尾部粘什么都不影响"能打开"。MP4 上的差别只在定位切割点的方法：PNG 数到 IEND，MP4 用 box 树——顶级 box 走完还剩字节，剩下的就是夹带。

```python
# tail_zip.py —— MP4 末尾粘 ZIP：box 树发现 → 切割 → 解包
import io
import os
import subprocess
import zipfile

from box_parse import parse

os.chdir(os.path.dirname(os.path.abspath(__file__)))


def run(*cmd):
    r = subprocess.run(cmd, capture_output=True, text=True)
    r.check_returncode()
    return (r.stdout + r.stderr).rstrip()


data = open("base.mp4", "rb").read()
buf = io.BytesIO()
with zipfile.ZipFile(buf, "w", zipfile.ZIP_DEFLATED) as z:
    z.writestr("secret.txt", "flag{tail_after_mdat}")
zipb = buf.getvalue()
open("tail.mp4", "wb").write(data + zipb)
print(f"[1] base.mp4 {len(data)} 字节 + ZIP {len(zipb)} 字节 = tail.mp4 {len(data) + len(zipb)} 字节")
print("file:", run("file", "tail.mp4"))
print()

print("[2] box 树解析：顶级 box 覆盖不到的地方")
data2, boxes, top_end = parse("tail.mp4", top_only=True)
print()

print("[3] 切割解包")
open("carved.zip", "wb").write(data2[top_end:])
print("carved.zip 里读出:", zipfile.ZipFile("carved.zip").read("secret.txt").decode())
```

输出：

```
[1] base.mp4 18000 字节 + ZIP 141 字节 = tail.mp4 18141 字节
file: tail.mp4: ISO Media, MP4 Base Media v1 [ISO 14496-12:2003]

[2] box 树解析：顶级 box 覆盖不到的地方
ftyp   off=0      size=32
free   off=32     size=8
mdat   off=40     size=16107
moov   off=16147  size=1853
```

file 的输出与没夹带时一字不差。解析器按大小字段走到 moov 末尾，再读尾部字节时，ZIP 的开头 `PK\x03\x04` 被当成一个 size 巨大得不合法的 box 头，walk 返回"撞上不合法 box"，于是汇总行直接给出边界：==box 树覆盖 0 ~ 18000，其后 141 字节不属于任何 box==——一个偏移就够切割出手。binwalk 也能扫出这 141 字节里的 ZIP 签名，box 树解析器的优势是给出精确边界、不受伪签名干扰。切出 ZIP 之后进 [[M04-压缩包全解#8. 套娃自动化|M04 8 节]]的套娃流程，逐层剥。

> [!note] 缝隙夹带
> 夹带不止尾部一种缝：free box 的内容被规范定义成"可忽略"，mdat 声明的大小若大于实际媒体数据、或 box 之间留了空洞，播放器同样毫无察觉。第 2 节的解析器把每个 box 的 off 与 size 打印出来，声明范围之外的字节无所遁形——遇到构造精巧的缝隙靶，手工核对 box 边界比扫签名可靠。

## 8. 常见问题

| 现象 | 原因与解决 |
| ---- | ---- |
| 提帧数量和预期不符 | 默认按恒定帧率重采样，VFR 源的帧被复制或丢弃。先 `ffprobe -count_frames` 问源帧数，拆帧一律加 `-vsync 0`（新写法 `-fps_mode passthrough`），见 3.2 |
| 无损视频里逐帧 LSB 提不出来 | 合成走了有损编码，或 `-qp 0` 但像素走了 YUV（4.1 的对照）。确认编码器是 libx264rgb / ffv1 这类 RGB 无损、pix_fmt 不带 yuv；真题里信息也可能根本不在像素里，转第 5 节 |
| ffprobe `-show_streams` 输出上百行难翻 | 用 `-show_entries stream=字段,字段` 挑列、`-v error` 关日志，只留关心的几项（3.1） |
| 视频本地能播、网页预览一直转圈 | moov 在文件尾，网页播放器要等整个文件下完。`ffmpeg -i in.mp4 -c copy -movflags +faststart out.mp4` 重排，不重编码（2.2） |
| 无损合成的视频文件巨大 | 无损编码放弃压缩率的正常代价；靶子只为提帧还原服务，大小无所谓（4.2） |
| 字幕轨"看不见" | 播放器默认不挂字幕轨，界面无提示。ffprobe 流清单看得到，`ffmpeg -i in.mp4 -map 0:s:0 out.srt` 直接提取（第 6 节） |
| select 滤镜报 No such filter: 'I)' | filtergraph 里逗号是分隔符，写成 `select=eq(pict_type\,I)`（5.2） |
| libx264rgb 报 Unknown encoder | 该编码器随 libx264 一起编译，个别发行版没带上。换 ffv1（容器换 .mkv），或换完整版 ffmpeg |

## 9. 配套练习与延伸阅读

配套练习：

1. 把 2.2 的解析器跑在手机拍摄的 MP4 上：找 moov 位置、数顶级 box、确认尾部没有多余字节；再用 `-movflags +faststart` 重排一次，对比解析器输出的顶级顺序。
2. 复现 4.2 的无损链路，把消息改成分摊式：帧 0 藏前半段、帧 1 藏后半段，提取端按帧序把所有帧的位流拼起来再解码——检查写入与读取的顺序约定是否一致。
3. 按 5.1 造一个黑白帧靶丢给同学，只给一句提示"一帧一位"；等他解出后，再按 5.1 的变体把黑白帧插进正常画面里，出一版加难的。
4. 给 base.mp4 挂两条字幕轨（第二个 SRT 用 `-i` 传入、`-map` 指明来源流），先 ffprobe 数流，再用 `-map 0:s:1` 提第二条，与 sub2.srt 逐字对照。
5. 用 `-g 2` 合成 key.mp4 后，把 5.2 的 select 条件换成只提 P 帧，对照两类帧的 PNG 尺寸差异，理解"差异帧为什么小"。
