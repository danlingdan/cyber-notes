写 EXP 前必须知道"发什么字节、收什么字节"。服务端和客户端两头对着读，互相印证。

> [!info]- 什么叫"逆协议"
> 服务端和客户端约定了一套字节格式（协议）：第 1 个字节是命令号，后面跟长度和数据。源码你看不全（有的只有二进制），就通过读汇编反推出格式——这叫协议逆向。逆清楚了才能用 Python 照着拼字节包，跟服务端对话。

## 服务端主循环：帧格式

```bash
$ objdump -d --demangle --no-show-raw-insn --start-address=0xd1dd4 --stop-address=0xd21db libggml.so
```

```asm
; rpc_serve_client，每轮循环（x86-64 Linux，AT&T 语法，System V ABI）
d1e3b: call recv_data(sockfd, &cmd, 1)        ; ① 读 1 字节命令号
d1e66: call recv_data(sockfd, &input_size, 8) ; ② 读 8 字节输入长度
d1ea7: call vector::resize(input_size)        ; ③ 按长度分配
d1ed3: call recv_data(sockfd, input.data(), input_size)   ; ④ 读输入
d1efa: cmp    $0xb,%eax
d1efd: ja     d20e5                           ; > 11 → "Unknown command" + ok=false
d1f19: lea    0x3bc10(%rip),%rdx              ; 跳转表基址 0x10db30
d1f23: notrack jmp *%rax                      ; ⑤ 12 路跳转分发
; 分发完成后（d2116 起）
d2155: call send_data(sockfd, &output_size, 8)      ; ⑥ 先发 8 字节输出长度
d218c: call send_data(sockfd, output.data(), output_size)  ; ⑦ 再发输出
d21d5: jmp  d1e24                             ; 回到循环开头
; ok == false 时（d2122）直接跳到收尾，关闭连接
```

```
请求:  [1B cmd][8B input_size][input ...]
响应:  [8B output_size][output ...]
        任何命令返回 false → 服务端直接关连接（不发响应）
```

> [!info]- TCP 字节流与"长度前缀"
> TCP 是字节流：你发 100 字节，对端可能分 3 次收到，也可能两次发送粘成一团到达。所以协议都带**长度前缀**——先说"接下来有 N 字节"，接收方收满 N 个才处理。这题的约定是：请求 = 1 字节命令号 + 8 字节（小端 u64）输入长度 + 数据本体；响应 = 8 字节输出长度 + 数据。你写 EXP 时必须凑够字节、读响应也必须先读 8 字节长度再读定长数据，多一个少一个字节全盘错位。
> 还有个要命的设计：**处理函数返回 false 时服务端不发任何响应、直接断开连接**。客户端表现为"读到了 EOF"——要能意识到这是"命令被拒"，不是网络抖了。

> [!tip]- 协议不明时先读客户端
> 客户端的构造/发送函数通常写得很直白，比读服务端的 `recv → 长度 → dispatch` 快。客户端实现 `send_rpc_cmd` 就在同一个 `libggml.so` 里（0xcdf19 起），汇编显示它发的正是"1 字节命令 + 8 字节长度 + 数据"，两端对上，帧格式确认无误。

## 跳转表：命令号与处理函数

```bash
$ objdump -s -j .rodata --start-address=0x10db30 --stop-address=0x10db60 libggml.so
 10db30 f643fcff 1b44fcff 3344fcff 4b44fcff
 10db40 7044fcff 9144fcff b244fcff d744fcff
 10db50 fc44fcff 2145fcff 4645fcff 9745fcff
```

> [!info]- 跳转表是什么
> C 的大号 `switch` 编译出来不是一串 if-else，而是一张表：表里第 i 格放着"命令号为 i 时该跳去哪"。程序拿命令号当索引查表、一次跳转到位。上面那 48 字节就是 12 个表项，每项一个 4 字节（int32）**相对偏移**——不是绝对地址，要拿表基址 0x10db30 加上去才是真函数地址。

> [!info]- 0xfffc43f6 为什么是负数（补码）
> 表项 `f6 43 fc ff` 按小端拼成整数是 0xfffc43f6。int32 的最高位是符号位，0xfffc43f6 首字节高位是 1，所以它是负数：负数用补码表示，`0xfffc43f6 - 0x100000000 = -0x3bc0a`。于是 `0x10db30 + (-0x3bc0a) = 0xd1f26`。手算时记住口诀：读出来比 0x80000000 大就是负的，减 0x100000000。

12 个偏移逐个算完（或用脚本算）：

| cmd | 处理函数 | 语义 |
|---|---|---|
| 0 | `alloc_buffer` | 申请 buffer，返回句柄 |
| 1 | `get_alignment` | 返回 32 |
| 2 | `get_max_size` | 返回 -1 |
| 3 | `buffer_get_base` | 由句柄查 base |
| 4 | `free_buffer` | 释放 buffer |
| 5 | `buffer_clear` | memset |
| 6 | `set_tensor` | **打桩**（"no set_tensor!"，见 [[02-读patch与漏洞原理#patch 里另外两处改动]]） |
| 7 | `get_tensor` | **读张量 → 任意读** |
| 8 | `copy_tensor` | 张量互拷 |
| 9 | `graph_compute` | 执行计算图 |
| 10 | `get_device_memory` | 返回 free/total |
| 11 | `edit_buffer` | **后门 → 任意写** |

## rpc_tensor 字段偏移

`deserialize_tensor` 是"把线上结构体拷进 `ggml_tensor`"的函数，读它等于直接读结构体定义——它从线上数据的哪个偏移取字段，那个偏移就是字段的在线位置：

```asm
d112c: mov 0x8(%rax),%esi     ; type   ← ggml_new_tensor_4d(ctx, type, ...)
d1127: mov 0x14(%rax),%eax    ; ne[0]
d1115: mov 0x1c(%rax),%eax    ; ne[2]
d110b: mov 0x20(%rax),%eax    ; ne[3]
d1180: mov 0xc(%rax),%rax     ; buffer  ← +0x0c 没对齐，packed 布局
d1204: mov 0x34(%rax),%edx    ; op
d1242: mov 0x78(%rax),%edx    ; flags
d1253: mov 0xdc(%rax),%rax    ; data    ← 任意读地址
d126c: lea 0xe4(%rax),%rdx    ; name
```

`get_tensor` 的入口校验反推出 `sizeof`：

```asm
d1378: cmp  $0x138,%rax       ; input 总长必须正好 0x138，否则 return false（断连）
d13ab: add  $0x128,%rax       ; offset 字段在 rpc_tensor 之后 8 字节
d13c4: add  $0x130,%rax       ; size   字段再往后 8 字节
```

写 EXP 直接照抄：

| off | 字段 | 说明 |
|---|---|---|
| `0x00` | `id` | 随便 |
| `0x08` | `type` | 用 `GGML_TYPE_F32 = 0` |
| `0x0c` | `buffer` | 必须是在案 buffer 句柄（`alloc_buffer` 的返回值） |
| `0x14` / `0x24` | `ne[4]` / `nb[4]` | 决定 `ggml_nbytes()` |
| `0x34` | `op` | 用不到 |
| `0x78` | `flags` | 0 |
| `0xcc` / `0xd4` | `view_src` / `view_offs` | 0 |
| `0xdc` | **`data`** | **读地址** |
| `0xe4` | `name[64]` | 随便，记得补 `\0` |

> [!info]- "packed"与非对齐访问
> 一般编译器会把结构体成员对齐到 4/8 字节边界（空隙填 padding），方便 CPU 读。但网络协议的字节格式是**一个字节都不能多**的（这题 GET_TENSOR 校验总长必须正好 0x138），所以 `rpc_tensor` 是 packed 布局——成员紧挨着排。证据：`buffer` 字段（8 字节宽）落在 0x0c，不是 8 的倍数。写 EXP 时用 `bytearray(0x128)` 按偏移硬填，别用 struct 直接打包一个对齐过的结构体，padding 会让总长对不上。

## 用附件 loader 起服务端

```bash
cd attachment
./ld-linux-x86-64.so.2 --library-path . ./rpc-server --host 127.0.0.1 --port 50052 --mem 100
# create_backend: using CPU backend
# Starting RPC server on 127.0.0.1:50052, backend memory: 100 MB
```

> [!warning]- 直接跑会 `version 'GLIBC_2.xx' not found`
> `rpc-server` 是在 Ubuntu 20.04（glibc 2.31）上编译的，编译时往二进制里写了"我需要 2.31 版的这些符号"。你的系统库更新，符号版本号更高，旧版本号找不到就拒绝运行。解法就是**用附件里的旧链接器 + 旧库**跑：`./ld-linux-x86-64.so.2 --library-path . ./rpc-server`，让程序完全活在题目自带的那套库里。

> [!info]- ld-linux 是什么，程序启动顺序
> 你敲 `./rpc-server` 回车后，内核先加载的不是 rpc-server 自己，而是 ELF 头里指定的**动态链接器** `/lib64/ld-linux-x86-64.so.2`，由它去找齐所有 `.so`、填好 GOT、把控制权交给 main。附件直接给你这个链接器本体，就能手动接管启动过程：`ld-linux --library-path 目录 程序` 的意思是"用我指定的链接器，库全部从这目录找"。这样运行时内存布局和远程完全一致。

> [!note]- 远程环境实测
> `docker-entrypoint.sh` 里 `echo $ICQ_FLAG > /flag; cd /src && ./rpc-server`，root 直接监听。远程 socket 的 fd = **4**（0/1/2 被 entrypoint 占用）。fd 在拿回显时是关键（[[04-利用链与EXP#第⑦步：回显与触发|第⑦步]]）。

## 最小客户端：先把协议跑通

```python
import socket, struct

def p64(x): return struct.pack("<Q", x & 0xFFFFFFFFFFFFFFFF)
def u64(b, o=0): return struct.unpack("<Q", b[o:o+8])[0]

def recvn(s, n):
    b = b""
    while len(b) < n:
        c = s.recv(n - len(b))
        if not c: raise EOFError(f"closed after {len(b)}/{n}")
        b += c
    return b

class Client:
    def __init__(self, host, port):
        self.s = socket.create_connection((host, port), timeout=15)
    def cmd(self, cmd, data=b""):
        self.s.sendall(bytes([cmd]) + p64(len(data)) + data)
        n = u64(recvn(self.s, 8))
        return recvn(self.s, n) if n else b""
```

> [!info]- 这 20 行 Python 逐段拆
> - `struct.pack("<Q", x)`：把整数按**小端** 64 位打包成 8 字节（`<` 小端，`Q` unsigned long long）；`unpack` 反向。协议里所有整数都是小端，这组函数贯穿全程
> - `bytes([cmd])`：把 0~255 的整数变成 1 字节
> - `sendall`：发到发完为止（裸 `send` 可能只发一半）
> - `recvn(s, n)`：**循环 recv 直到凑满 n 字节**。TCP 是字节流，单次 `recv(8)` 可能只回来 3 个字节，不凑满就会错位。`recv` 返回空字节串说明对端关了连接，抛 EOFError
> - `cmd()`：按帧格式拼"1 字节命令 + 8 字节长度 + 数据"，读响应时先读 8 字节长度再读定长数据
> - `socket.create_connection((host, port), timeout=15)`：建 TCP 连接，15 秒没连上抛异常

先发几条无害命令验证协议，再谈漏洞：

```python
c = Client("127.0.0.1", 50052)
print(c.cmd(10).hex())               # GET_DEVICE_MEMORY
print(u64(c.cmd(1)))                 # GET_ALIGNMENT  -> 32
print(c.cmd(0, p64(0x100)).hex())    # ALLOC_BUFFER   -> 16 字节
print(c.cmd(0, p64(0x200)))          # 超上限 -> 服务端直接关连接(false)
print(c.cmd(6, b"A"*0x140))          # SET_TENSOR     -> b'no set_tensor!'
```

实测输出：

```
devmem: 00004006000000000000400600000000     # free=0x6400000 total=0x6400000
align : 2000000000000000                     # 32
alloc : 6091f265555500002001000000000000     # 句柄=0x555565f29160, size=0x120 (=0x100+0x20)
alloc 0x200: EOFError（连接被关）
```

> [!tip]- 这一步能排除 80% 的"后面怎么都不对"
> 协议层没跑通就上利用，出错时分不清是协议错还是利用错。五条测试各验一件事：响应长度前缀读得对（devmem 16 字节）、8 字节小端解得对（align=32）、分配返回了句柄（alloc）、超限走的是"断连"而不是报错（0x200 那条）、打桩命令返回了固定字符串（set_tensor）。另外注意 `alloc` 返回的 size 是申请值 + 0x20——`malloc(size + 0x20)` 的结果，[[04-利用链与EXP#第⑥步：payload 容量上限|第⑥步]] 的 payload 容量由它决定。

## 调试三板斧

**(1) 看进程内存映射**，验证算的基址对不对：

```bash
$ pid=$(pgrep -f 'rpc-server --host'); grep -E 'libggml|rpc-server' /proc/$pid/maps
7ab4d4aef000-7ab4d4b31000 r--p 00000000 libggml.so
7ab4d4b31000-7ab4d4beb000 r-xp 00042000 libggml.so      ← 基址 = 7ab4d4aef000
```

**(2) 看它自己的 fd**，确认 socket 是几号（决定 shell 命令往哪个 fd 写）：

```bash
$ ls -l /proc/$pid/fd
0 -> /dev/null     1 -> log   2 -> log   3 -> socket:[...]   4 -> socket:[...]   ← 4 是和你的连接
```

想更严谨就对 `/proc/net/tcp` 的 inode 反查。本地 `socat`/`xinetd` 型部署通常是 0/1/2 = socket。

**(3) gdb 打点看调用链**：可直接用的脚本和实测日志在 [[04-利用链与EXP#gdb 打点：看着链子跑通|利用链一篇的 gdb 打点]]。

> [!info]- /proc 是什么，maps 怎么读
> `/proc/进程号/` 是内核把进程内部状态暴露成文件的特殊目录，`maps` 是它的内存地图，每行一段：`起始地址-结束地址 权限 文件内偏移 文件名`。权限四个字符 = 可读/可写/可执行/私有或共享，`r-xp` 就是"可读可执行不可写"，代码段都长这样。**一个 .so 占多行，权限最全段之前那个 r--p 行的起始地址就是加载基址**——ASLR 让它每次开机都不同，所以调好的地址不能背，要现查现用。
>
> [!info]- fd（文件描述符）是什么
> Linux 的设计是"一切皆文件"，socket、日志、终端在进程眼里都是编号的"文件"，这个编号就是 fd。0/1/2 固定留给标准输入/输出/错误，之后每打开一个东西递增。`system()` 出来的 shell **原样继承**这些编号——所以"往 fd 4 写"就能把数据送到和你相连的 socket 上。这是第 4 篇拿回显的全部原理。
>
> [!info]- pgrep 是什么
> `pgrep -f '关键词'` 按完整命令行模糊查进程号（`grep` 是搜文件内容，`pgrep` 是搜进程）。`pgrep -f 'rpc-server --host'` 返回那个服务端进程的 PID，拼进 `/proc/$pid/` 就能看它的 maps 和 fd。
