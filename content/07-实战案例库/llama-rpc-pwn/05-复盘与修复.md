> [!warning]- 输出别直接接管道
> `bash reproduce_local.sh > out.log` 这种写法有一个隐蔽坑：`system()` 出来的 shell **继承服务端打开的一切 fd**，包括你接的管道写端。之后 shell 的输出会和 EXP 的输出混在一起，还可能把管道堵死。重定向到文件再 `grep` 稳得多：`bash reproduce_local.sh > /tmp/out.log 2>&1 ; grep -a FLAG /tmp/out.log`（`-a` 把 log 当文本搜，防二进制字符混入导致 grep 说 Binary file matches）。

## 故障排查表

现象 → 原因 → 处理，细节展开在 [[04-利用链与EXP#第⑥步：payload 容量上限|第⑥⑦步]]：

| 现象 | 原因 | 处理 |
|---|---|---|
| 服务端 Segfault | payload 超过 `malloc(size+0x20)`，踩坏下一个 chunk header | `alloc(0x1ff)` + 长度断言 |
| 客户端 `MemoryError`，帧头像天文数字 | hook 装上后被释放的内存被当命令执行，输出冲掉协议帧头 | 触发后只发不读，裸读 socket |
| `for f in ...; do echo x >&$f; done` 收不到数据 | dash 内建 echo 的 stdio 缓冲 + 重定向恢复顺序 | 用 `( ... ) >&$f` 或 `/bin/echo` |
| 第二条连接一直超时 | 服务端单连接串行，第一条没关 | 先 `close()` 再连 |
| 新服务端报 `Failed to create server socket` | 上次 `system()` 的 shell 继承监听 socket 挂着，占住端口 | `fuser -k -n tcp PORT` |
| 同一服务端第二次打就乱 | 常驻进程的 `__free_hook` 还留着 | 先读 hook 判断，跳过回读校验 + 协议层 resync |

> [!info]- fuser 是什么
> `fuser -k -n tcp 50052` = 找到占着 50052 端口的进程并杀掉（`-k` kill，`-n tcp` 按协议+端口找）。排查"端口被占"的第一反应工具，同类还有 `ss -ltnp | grep 端口`（看是谁占的，但不杀）。

## 其它可行路线

**劫持 `iface.get_base`（实测可用，`aux/alt_iface_hijack.py`）**：知道结构体地址，可以不动全局 hook——`buffer+0x00` 放命令串（必须 NUL 结束在 +0x10 之前，≤15 字节），`buffer+0x10` 覆盖成 `system`，然后发 `BUFFER_GET_BASE(buf)`：

```asm
; ggml_backend_buffer_get_base @ 0x95ea0
95ea8: call *0x10(%rdi)          ; rdi = buffer → 变成 system(buffer)
95eab: test %rax,%rax
95eae: je 95eb5 → ggml_abort     ; 返回值必须非 0
```

实测命令确实执行了（`id` 输出从 socket 回来），但 `system` 成功返回 0 会踩中非空断言、服务端跟着 `ggml_abort`——想让它活着，命令末尾补 `; false`。优点是没有"每次 free 都炸一次"的噪音，缺点是命令只有 15 字节。

**栈上 ROP（思路，未逐条实测）**：任意读 `libc+0x1ef600`（`environ`）拿栈地址 → 定位 `rpc_serve_client` 的返回地址 → `EDIT_BUFFER` 写 ROP 链（`pop rdi; ret` + 命令串指针 + `system`）。

> [!info]- 这条栈 ROP 路线的原理
> `environ` 是 libc 里存环境变量指针的全局变量，它的值指向**栈上**一块固定相对位置——这是经典的"借 libc 找栈"手法，因为栈地址也随机化了，但栈和 libc 的相对位置在单次运行里是稳定的。拿到栈地址就能算出"函数返回地址存放的位置"，用任意写往那里摆一串"返回地址链"（ROP：每个 8 字节要么是 gadget 要么是数据，`ret` 指令像串珠子一样依次执行它们）。比 `__free_hook` 干净在"不污染全局状态"，代价是多两步泄漏、要精确找栈偏移。
> 想系统学 ROP：库里 `03-PWN` 方向 P6–P8 就是这条线。

**不值得走的路**：`free@got` 覆盖（本来就能写任意地址，绕 GOT 没有意义，还容易误伤 Full RELRO 的主程序）；tcache 投毒 / `__malloc_hook`（2.31 可做，但原语已经更强，绕远）；`graph_compute`（能控制 `op` 号，控制流复杂、ROI 低）。

> [!info]- "tcache 投毒"是什么（为什么这里不用）
> tcache 是 glibc 2.26+ 的线程本地释放缓存：free 掉的 chunk 先按尺寸放进 12 个桶里，下次 malloc 同尺寸直接从桶里拿。投毒 = 改桶里 chunk 的 next 指针，让下次 malloc 返回**你指定的地址**——本质是用"堆操作"间接实现任意分配，通常和 UAF/堆溢出搭配。本题已经有了直白的任意写，再绕道堆机制纯属降级，但做堆题时它是必须掌握的主干技术。

## 修复建议

按"根因 → 表面"排序。

**1. 根因：协议不该传裸指针。** `rpc_tensor` 的 `buffer`/`data` 是地址，服务端直接拿来用。正确做法是"句柄 + 偏移"，且服务端做完整区间校验：

```
1) buffer 必须是本进程分配并登记在案（现在做了 ✓）
2) data 必须落在 buffer->context .. buffer->context + buffer->size 之间（现在没做 ✗）
3) offset + size 必须 <= tensor 实际的 nbytes（现在用客户端给的 ne/nb 算，等于没校验 ✗）
```

第 2、3 条补上，`GET_TENSOR` 的任意读就没了，`COPY_TENSOR` / `GRAPH_COMPUTE` 同理。

**2. `EDIT_BUFFER` 这类命令不该存在。** 任何"让对端指定地址 + 长度 + 内容"的接口都是后门。调试用途也要：绑定句柄而非裸地址、校验区间、读写权限分离、只在 DEBUG 构建开启并有审计日志。

**3. 先校验、后使用。**

```c
// 现在的写法：input 为空时 input.data() == nullptr -> memcpy from NULL -> 段错误
uint64_t edit_buf;  memcpy(&edit_buf,  input.data(), 8);
uint64_t edit_size; memcpy(&edit_size, input.data() + 8, 8);
if (input.size() < 16 + edit_size) return false;

// 应该是：
if (input.size() < sizeof(uint64_t) * 2) return false;              // 先校验长度
uint64_t dst, len;
memcpy(&dst, input.data(), 8);
memcpy(&len, input.data() + 8, 8);
if (input.size() < sizeof(uint64_t) * 2 + len) return false;         // 再校验负载
```

**4. 架构层面：RPC 端口要有认证与加密。** 上游文档自己写着"没有认证/加密，建议走 SSH 隧道"——"文档即安全"。生产环境至少要 token/mTLS、默认只听 `127.0.0.1`、白名单 + 限速。

> [!info]- "文档即安全"（security by documentation）为什么靠不住
> 把安全寄托在"文档里写了别这么用"上，等于假设所有使用者都读文档并且都照做。现实是：RPC 端口一开，扫描器先到；内网里任何一个被攻破的相邻容器都能直连它。安全设计要按"最坏情况下的调用者"来——默认不信任网络对端，而不是指望对端自觉。

**5. 编译加固，缩小爆炸半径。**

| 措施 | 作用 |
|---|---|
| `-fPIE -pie` | 主程序已有 ✓ |
| `-Wl,-z,relro,-z,now`（Full RELRO） | 主程序已有 ✓；`libggml.so` 目前 Partial RELRO，GOT 可写，建议一起开 |
| `-fstack-protector-strong` | 已有 ✓ |
| `-D_FORTIFY_SOURCE=2` + `-O2` | 让 `memcpy` 类越界更容易在编译期/运行期被拦 |
| glibc ≥ 2.34 + 不开 hook | `__free_hook` 消失，"劫持 free"这条路自然没了 |

> [!info]- FORTIFY_SOURCE 实际干了什么
> 编译器拿到优化信息后，很多 `memcpy(dst, src, n)` 其实"编译时就知道 dst 的总大小"。开 `-D_FORTIFY_SOURCE=2`（需配合 `-O2`）后，这类调用被替换成 `__memcpy_chk`：运行时先比对 n 是否越界，越界直接中止。它拦不住"长度完全来自网络"的场景（编译期不知道大小），但能拦住一大类内部缓冲区误用——所以叫"缩小爆炸半径"，不叫修复。

> [!important]- 升级 glibc 不是修复
> 它只是让这类利用更难——本例就算没有 `__free_hook`，也还有栈 ROP（`environ` 泄漏）。真正要修的是第 1、2 条。

## 方法论 checklist

"改过的开源项目 + 服务端"这类题的推进顺序：

- **侦察（10 min）**：`file`/`checksec` 看架构、保护、符号；`strings libc` 确认 glibc 版本；`nm -C` 找可疑函数（`*_set`、`*_write`、`custom`、项目特有名字）；`readelf --debug-dump=info` 拿源码路径去 GitHub 对照。
- **读 patch（5 min，优先级最高）**：逐行找"从网络取地址/长度 + memcpy/strcpy/赋值"的形状，标 AAR/AAW 候选；作者"顺手关掉的功能"（本题的 `set_tensor` 打桩、`alloc` 上限）往往在暗示唯一留出来的通路。
- **协议逆向（30 min）**：先读客户端（构造/发送），再读服务端（recv → 长度 → dispatch）；跳转表算出"命令号 ↔ 处理函数"全表；从 `deserialize_*` 反推结构体偏移，从 `cmp $imm, size` 反推 `sizeof`。
- **原语化（30 min）**：每条命令写成"输入 → 输出"的原语表；**先写最小客户端把协议跑通，再谈利用**。
- **利用（1 h）**：泄漏 → 劫持 → 触发。泄漏要多符号交叉验证；劫持挑"必然以我们控制的参数调用某函数"的链；触发前想清楚输出怎么回来（fd、缓冲、协议是否已污染）。
- **反脆弱**：常驻服务要能重复打（状态残留）；脏数据要能 resync；每个故障记下"现象 → 原因 → 处理"，这类题的故障高度重演。

> [!important]- 这题最值得带走的一句话
> `EDIT_BUFFER` 是明面上的洞，但真正让利用成立的是上游"信任客户端"的协议设计（裸指针上链路）。只补 `EDIT_BUFFER` 不补协议，洞还在别的地方。审查时盯两处："部分校验"里没被校验的字段，和"文档说只在内网用"的默认信任。
