RAID 5 比 RAID 0 多两类未知量：校验块在盘间怎么轮换（布局），以及数据块在校验盘两侧怎么排。这一章会看到一个反直觉的事实——异或校验关系本身**无法**区分这些布局，能当裁判的只有文件系统和文件校验和。

## 锚点形势：首尾各锁定一对盘

对 RAID 5 包的 5 块盘做同样的签名扫描：

```bash
python3 scan.py dl/raid5
```

输出：

```
3D8qN9DH91Q.img  EFI PART at: [33553920]   XFSB at: []
3RlmViivyG8.img  EFI PART at: [512]         XFSB at: []
60kE0MQisyY.img  EFI PART at: [512]         XFSB at: [4757572]
IrYp6co7Gos.img  EFI PART at: []            XFSB at: []
QjTgmgmwXAM.img  EFI PART at: [33553920]    XFSB at: []
```

与 RAID 0 不同：GPT 头这次出现在**两对盘**上，首尾各一对；XFS 超级块一处对齐命中都没有。

> [!info]- 为什么 GPT 头会出现在两块盘上
> RAID 5 的 0 号条带里，一块盘存数据、一块盘存校验（其余四块数据按字节异或的结果）。GPT 头所在区域（LBA 0~33）只有第一块数据盘有内容，其余数据盘全是零，于是==校验盘上的异或结果就等于第一块数据盘的内容本身==——两个盘上出现一模一样的 GPT 头。哪块是真身、哪块是"影子"，扫描分不出来，只能各记一笔。
> 同理，阵列末尾的备份 GPT 头让最后一条带的数据盘与校验盘成对出现。`IrYp6co7Gos` 两头都不沾，只能占中间的纯数据位。
> 那个非对齐的 `XFSB`（偏移 4757572）与 RAID 0 包里的情况一样，是文件内容，不是文件系统结构。整个 RAID 5 阵列没有任何对齐的 XFS 签名——这本身就是提示：盘里的文件系统可能不是 XFS。

## mdadm 的边界：--build 不收 RAID 5

自然的想法是沿用 RAID 0 的路数，用 `mdadm --build` 拼阵列。这条路在这里走到头了：

```bash
mdadm --build /dev/md5 --level=5 --layout=left-symmetric --chunk=64 \
    --raid-devices=5 loop0 loop1 loop2 loop3 loop4
```

输出：

```
mdadm: Raid level 5 not permitted with --build.
```

`--build` 只支持 linear、RAID 0、RAID 1 这类无校验或镜像的级别。要拼 RAID 5 只能自己写组装器——好在映射规则一条公式就写完，128 MiB 的阵列在 Python 里逐条带复制，几秒拼完。

## 候选生成：锚点过滤后剩 32 组

RAID 5 的布局参数有三个维度：

| 维度 | 取值 | 含义 |
| ---- | ---- | ---- |
| 校验轮换方向 | left / right | 0 号条带的校验盘从最后一盘还是第一盘开始轮 |
| 数据排布 | symmetric / asymmetric | 数据块跟在校验盘后顺延，还是总是从盘 0 开始填 |
| 条带大小 | 64 / 128 / 256 / 512 / 1024 / 2048 扇区 | 常见值都在 2 的幂上 |

四个布局乘六个条带再乘 5! 种盘序，全空间 2880 组；把两组 GPT 锚点（首条带的"数据盘+校验盘"对、末条带的同款）作为约束过滤后，只剩 32 组候选。

> [!info]- 锚点怎么变成约束
> 对每组（布局，条带）都能算出"LBA 1 落在哪个盘序位置、0 号条带校验盘是哪个位置"这两个槽位号。锚点要求：这两个槽位上的盘恰好是 {3RlmViivyG8, 60kE0MQisyY} 这一对；末条带的两个槽位同理，恰为 {3D8qN9DH91Q, QjTgmgmwXAM}。满足两对约束的排列才入围。

## 异或校验当不了裁判

解 RAID 5 的标准思路是拿校验关系验布局：把每组候选按自己的规则拼几条条带，检查"数据异或 == 校验块"。这道题里这个裁判会全员放行——`solve_r5.py` 取数据稠密的阵列中段做了一次演示：

```
中部条带五盘内容异或 = 0x0（恒 0，布局判别只能交给文件系统与文件校验）
```

==任何一个条带的五块盘内容异或恒为零==，这是校验关系成立时的恒等式。把它变形就能看清对称性：任意一块盘的内容 = 其余四块的异或。于是"哪块是校验盘"从异或关系里根本读不出来——每个位置都有资格当校验盘。条带大小也一样：只要候选条带是真实条带的 2 的幂分块或整倍数，逐字节的异或零关系原样保持。32 组候选在这个裁判面前完全等价。

> [!info]- 这层对称性是 RAID 5 的性质，不是这道题的巧合
> 校验关系只约束"五块盘内容的异或为零"这一件事，而异或运算可交换、可分组，对"哪块盘扮演校验角色"完全 blind。实战中它依然有用：校验关系不成立的候选（条带边界错位到非对齐位置、盘组不对）会被立刻否决——它是必要条件的过滤器，不是充分条件的判别器。

## 终审：挂载 + 盘内评分器

剩下的判别只能用"语义层"的证据：拼出来的镜像要能挂载，挂载出来的文件要能通过出题人的校验和。`solve_r5.py` 把 32 组候选逐组组装成镜像、`losetup` 挂 loop、按偏移 1 MiB 试挂 ext4、跑盘内 `getflag.py`：

```bash
sudo ATTACH_R5=dl/raid5 python3 solve_r5.py
```

输出：

```
锚点过滤后候选（布局 x 条带 x 盘序）: 32 组
中部条带五盘内容异或 = 0x0（恒 0，布局判别只能交给文件系统与文件校验）
[01] left-symmetric   chunk=  64KiB 3Rlm|IrYp|3D8q|QjTg|60kE
     挂载 + 文件校验通过 -> Flag: flag{a18325a1ec0f58292908455c2df8ffcd}
唯一胜者: left-symmetric, chunk 64 KiB, 盘序 3RlmViivyG8|IrYp6co7Gos|3D8qN9DH91Q|QjTgmgmwXAM|60kE0MQisyY
```

第一组候选就通过了全部终审。挂载失败和校验失败的候选会被逐组淘汰（脚本按固定顺序尝试，错序的镜像在挂载阶段就因超级块对不上而失败），直到出现同时通过两关的组合。

> [!info]- 分区里为什么是 ext4
> 扫描没有任何对齐的 XFS 签名，这排除了 XFS。拼好的镜像分区起点 +1080 字节处恰好是 0x53EF——ext 超级块魔数的标准位置（前 1024 字节是引导区，全零）。两个小问各用一种文件系统，对应两种不同的锚点体系：XFS 靠 AG 副本给锚点，ext4 自身没有等价的多副本结构，锚点只能来自 GPT 层。

第二个 flag：

```
Flag: flag{a18325a1ec0f58292908455c2df8ffcd}
```
