## 1. 从"算法选对了"到"用法做对了"

前面各章按知识组织：一章讲一类算法或一类攻击。审计不这样看。拿到一个真实系统（或一道模拟真实系统的题），问题不是"AES 安全吗"，而是==这把 AES 的密钥从哪来、放在哪、用在哪、和什么组合==——算法正确性与工程正确性是两份独立的检查清单，前者 [[09-密码学基础|09 章]] 到 [[C18-后量子密码|C18]] 已经铺完，后者就是本章。

工程侧事故有两条判别线索：

- **同型复现**：换一个系统，同样的坑再踩一遍。密钥写死在源码里这个错误，与语言、框架、算法都无关，只与"密钥在交付物里"这个事实有关——所以它值得被收拢成清单条目，而不是散在各章的注脚里；
- **层间独立**：随机数没错、模式没错、比较恒时，协议层少一个序号字段，系统照样被重放打穿。==每层各自正确，加起来不一定正确==。

## 2. 密钥存储与硬编码

### 2.1 密钥写进交付物

**错误写法**：把密钥当常量写进源码，随编译进二进制。最小样本：

```c
/* hardkey.c —— 密钥写死在源码里的最小样本 */
#include <stdio.h>
#include <string.h>

static const unsigned char aes_key[16] = "C19H4rdC0d3Key!!";
static const char *license_salt = "s3rtsalt";

int check(const char *input)
{
    unsigned char buf[32];
    (void)aes_key; (void)license_salt;
    memset(buf, 0, sizeof buf);
    return input != NULL && strlen(input) == 16;
}

int main(void)
{
    printf("check=%d\n", check("0123456789abcdef"));
    return 0;
}
```

密钥是 `const` 数组，编译器把它放进 `.rodata` 段。`strings` 按可打印字节扫整个文件，扫得到它：

```bash
gcc -O0 -fno-pie -no-pie hardkey.c -o hardkey
strings -t x hardkey | grep -E 'C19H4rd|aes_key'
```

输出：

```
   2010 C19H4rdC0d3Key!!s3rtsalt
   34d0 aes_key
```

**后果**：两行输出各泄一层。第一行是==密钥本体与盐并排躺在文件偏移 0x2010 处==——攻击者不需要逆向任何代码，一条 strings 就拿到了加密密钥；第二行连符号名 `aes_key` 都在（未 strip 的符号表里保留了它），等于把"哪一段字节是密钥"也标注了。源码、配置文件、前端 JS、移动端 APK、固件镜像，全都是同一类交付物：[[W03-信息泄露与前端安全|W03]] 里前端调试信息泄密钥、CTF 里 `strings` 扫出 key，是同一个坑在不同载体上的形态。

> [!warning] strings 扫不到不等于没有
> 密钥做两层 XOR 混淆、或拆成字节表在运行时组装，strings 就扫不到完整密钥——但这只是把密钥从"字符串层"挪到"代码层"。识别特征是反汇编里"逐字节异或同一常数"或"逐字节查表"的短循环；对这种形态，动态调试断在密钥参与运算的函数入口、直接读内存即可拿到组装完成的密钥。判断一个二进制有没有硬编码密钥，strings 是初筛，不是结论。

**正确写法**：密钥不进任何交付物。三个层级，从轻到重：

1. **环境变量或密钥文件**：进程启动时注入。这只解决"不进代码仓库"，不解决"不落盘"——环境变量会进 `/proc/<pid>/environ`，进程崩溃时 core 文件把堆栈和内存里的密钥一起带走，密钥文件要管权限（`0600`、属主收敛）；
2. **密钥管理服务（KMS）**：密钥集中生成、集中托管，应用按需取用或只拿"用主密钥加密过的数据密钥"；轮换、审计、权限都收在服务侧，应用侧始终不持有长期主密钥的明文。云厂商的 KMS 产品与开源的 Vault 属于这一层；
3. **硬件边界**：安全元件（SE/TPM/HSM）里密钥写进硬件后读不出来，只能发起运算。这是密钥防护的终态，成本也最高。

> [!info]- CTF 里三类题对应三个存储层
> 题面给"加密脚本 + 密文"的，密钥在脚本的变量里，坑通常是密钥的来源（[[C04-随机数攻防|C04]]）；题面给"服务 + 密文"的，密钥在服务进程内存里，坑通常是打 oracle（[[C06-分组模式攻击全集|C06]]、[[C09-RSA攻击III|C09]]）；题面给"二进制/固件"的，密钥在交付物里，本节的 strings 与运行时读取就是主攻手段。三类题的分工恰好对应"密钥在哪"的三个位置。

### 2.2 密钥派生用未加盐哈希

**错误写法**：随机密钥"不好记"，于是拿口令的哈希当 AES 密钥：

```python
key = hashlib.md5(password.encode()).digest()
```

`kdf_demo.py` 完整呈现攻击两方。加密方只泄露密文，口令不出场；攻击方拿口令字典逐个派生密钥，用"明文以 `flag{` 开头"这条常识验签：

```python
# kdf_demo.py —— 未加盐哈希派生密钥：口令字典逐候选派生，已知明文验签
from Crypto.Cipher import AES
from Crypto.Util.Padding import pad
import hashlib

# 加密方：AES 密钥直接取口令的 MD5（无盐、无慢哈希）
password = "letmein123"
key = hashlib.md5(password.encode()).digest()
msg = b"flag{kdf_n0_s4lt}" + b" filler for one more block"
iv = b"0123456789abcdef"
body = AES.new(key, AES.MODE_CBC, iv=iv).encrypt(pad(msg, 16))
print("泄露物：iv=%s body=%s（口令不泄露）" % (iv.hex(), body.hex()[:24] + "..."))

# 攻击方：只有密文与"明文以 flag{ 开头"这个常识
wordlist = ["123456", "password", "qwerty", "admin", "letmein123",
            "root", "test1234", "iloveyou", "abc123", "welcome1"]
for cand in wordlist:
    k = hashlib.md5(cand.encode()).digest()
    pt = AES.new(k, AES.MODE_CBC, iv=iv).decrypt(body)
    if pt.startswith(b"flag{"):
        print("命中口令: %r -> 还原明文: %s" % (cand, pt.decode()[:len(msg)]))
        break
else:
    print("字典未命中")
```

```bash
python3 kdf_demo.py
```

输出：

```
泄露物：iv=30313233343536373839616263646566 body=a80017e4daabc86dcfdea2b4...（口令不泄露）
命中口令: 'letmein123' -> 还原明文: flag{kdf_n0_s4lt} filler for one more block
```

**后果**：密钥的全部熵来自口令——AES 密钥名义上 128 位，实际候选空间就是口令字典的大小。MD5 又快（[[09-密码学基础|09 章]] 4.2 节的"爆破一亿次也就几分钟"在这里同样成立），每秒能派生百万级候选。加盐哈希存口令（防彩虹表）与加盐慢哈希派生密钥（拉高逐候选成本）缺一不可。

**正确写法**：密钥有两条正路，按熵来源选：

- 熵来自生成器：`os.urandom(16)` / `secrets.token_bytes(16)` 直接生成，不经过任何口令（[[C04-随机数攻防|C04]] 第 8 节的防御清单）；
- 熵确实来自人的口令（磁盘加密、端到端同步这类场景）：用专门的口令基密钥派生函数 PBKDF2 / scrypt / argon2，盐随机存，代价参数按"单次派生几十毫秒"起步——慢是设计目标。[[C10-哈希进阶|C10]] 6.3 节给过加盐与慢哈希的完整账。

## 3. 密钥复用与用途混用

一把密钥一个用途。混用的机制性原因：==每个用途有自己的攻击面，混用时 A 用途被攻破直接变成 B 用途被攻破==——两个用途各自的安全性证明都以"密钥不另作他用"为前提，前提破了，证明全部失效。

### 3.1 一把 RSA 既加密又签名

**错误写法**：服务端持有 `(n, d)`，同时开两个接口：`encrypt` 收外部密文（$c = m^e \bmod n$），`sign` 对任意提交的数出签名（$s = x^d \bmod n$，无填充、不审数值）。[[C12-数字签名|C12]] 第 1 节讲过"加密方案安全推不出私钥当签名用也安全"，这里看反方向——签名接口反过来把加密接口打穿：

```python
# key_mix.py —— 一把 RSA 既加密又签名：签名 oracle 反哺解密（教科书 RSA，教学尺寸）
from Crypto.Util.number import getPrime, bytes_to_long, long_to_bytes, GCD
import os

e = 65537
while True:
    p, q = getPrime(128), getPrime(128)
    n = p * q
    if GCD(e, (p - 1) * (q - 1)) == 1:
        break
d = pow(e, -1, (p - 1) * (q - 1))

# 服务端暴露两个接口，背后是同一把 (n, d)：
#   encrypt: c = m^e mod n   —— 接收外部密文
#   sign(x): s = x^d mod n   —— 对任意数出签名（无填充、不审内容）
msg = bytes_to_long(b"RSA dual-use key demo")
c = pow(msg, e, n)
print("密文 c 已生成，d 与 msg 均不出服务端")

# 攻击方：想解 c，又不直接递 c。乘一个自选因子 r：
# c' = c * r^e = (m*r)^e，签名 c' 得 (m*r)^d = m*r mod n，除掉 r 即 m
r = bytes_to_long(os.urandom(8)) % n
s = pow(c * pow(r, e, n) % n, d, n)          # 走 sign 接口
m_hat = s * pow(r, -1, n) % n
print("盲化-签名-去盲化，恢复明文:", long_to_bytes(m_hat))
```

```bash
python3 key_mix.py
```

输出：

```
密文 c 已生成，d 与 msg 均不出服务端
盲化-签名-去盲化，恢复明文: b'RSA dual-use key demo'
```

**后果**：签名运算和私钥解密运算是同一个 $x^d \bmod n$——==sign 接口就是一个解密 oracle==，盲化因子 $r$ 只是把目标密文挪进"业务数值"的形状里。它与 [[C09-RSA攻击III|C09]] 第 5 节的 Bleichenbacher 攻击是同一件事的两个难度档：那边要在"填充对/错"的单比特反馈下一步步夹逼，需要上千次询问；这边接口直接返回完整运算结果，一次询问收工。

**正确写法**：加密与签名用两对独立的密钥。X.509 证书的 `keyUsage` 扩展就是这件事的机制化：`keyEncipherment` 与 `digitalSignature` 分开声明，验证方按用途拒收错位密钥。应用层也一样：签发侧与解密侧各持各自密钥，接口审计"收到的是不是为它签发的密钥"。

### 3.2 对称密钥跨用途：加密与 MAC 同钥

**错误写法一**：加密用 $\mathrm{AES}(k)$，"MAC" 也用 $\mathrm{AES}(k)$——图省事，直接拿分组密码当消息认证码：

```python
# sym_mix.py —— 加密与 MAC 共用一把密钥，MAC 退化成"密文自我校验"
from Crypto.Cipher import AES
from Crypto.Random import get_random_bytes

k = get_random_bytes(16)

def enc(m):                       # 加密用 ECB(k)
    return AES.new(k, AES.MODE_ECB).encrypt(m)

def mac(m):                       # "MAC" 也用 ECB(k)：tag = E(k, m)
    return AES.new(k, AES.MODE_ECB).encrypt(m)

def verify(c, tag):               # 服务端：解密取 m，重算 MAC 对 tag
    m = AES.new(k, AES.MODE_ECB).decrypt(c)
    return mac(m) == tag, m

m = b"SINGLEBLKMSG16BY"           # 单块消息，恰 16 字节
c = enc(m)
token = (c, mac(m))
print("合法令牌通过校验:", verify(*token)[0])

# 攻击者没有 k：任取一段密文，把 tag 抄成密文本身
c2 = get_random_bytes(16)
ok, m2 = verify(c2, c2)
print("伪造令牌 (%s, tag=密文自身) 通过校验: %s  解出明文: %s" % (c2.hex()[:12] + "...", ok, m2.hex()[:12] + "..."))
print("原因: tag = E(k, m) 而 m = D(k, c)，校验恒为 tag == c，对任意密文恒真")
```

```bash
python3 sym_mix.py
```

输出：

```
合法令牌通过校验: True
伪造令牌 (7c347606715e..., tag=密文自身) 通过校验: True  解出明文: f0f702aaf289...
原因: tag = E(k, m) 而 m = D(k, c)，校验恒为 tag == c，对任意密文恒真
```

单块消息下 $\text{tag} = E(k, m)$，而服务端重算时 $m = D(k, c)$，代回去 $\text{tag} = E(k, D(k, c)) = c$——==校验条件退化成"tag 等于密文自身"，任何人都恒能满足==。完整性保护整体失效，攻击者不需要密钥就能让服务端"认证"任意一段垃圾。

**错误写法二**：CBC 懒得起 IV，拿密钥凑数，且 IV 按惯例拼在密文前面明文传输：

```python
# iv_is_key.py —— CBC 把密钥当 IV：IV 栏随密文上线，密钥当场可读
from Crypto.Cipher import AES
from Crypto.Random import get_random_bytes
from Crypto.Util.Padding import pad, unpad

k = get_random_bytes(16)
msg = b"PAYLOAD:*" + b"rest of message here..."

ct = AES.new(k, AES.MODE_CBC, iv=k).encrypt(pad(msg, 16))
wire = k + ct                                    # 发上线的东西：iv || ciphertext
print("线上字节前 16 字节（iv 栏）:", wire[:16].hex()[:24] + "...")

key_guess = wire[:16]
body = wire[16:]
pt = AES.new(key_guess, AES.MODE_CBC, iv=key_guess).decrypt(body)
print("用 iv 栏当密钥解密:", unpad(pt, 16))
```

```bash
python3 iv_is_key.py
```

输出：

```
线上字节前 16 字节（iv 栏）: 22aac34571b42eaa93b805de...
用 iv 栏当密钥解密: b'PAYLOAD:*rest of message here...'
```

IV 本来就设计为公开，把它拼上线没有错；错在它**等于密钥**——线上前 16 字节就是 AES 密钥本钥。[[C06-分组模式攻击全集|C06]] 讲过"IV 固定"泄漏首块相等，那是泄漏统计特征；IV=密钥是泄漏密钥本体，量级完全不同。

**正确写法**：一条主密钥进系统后，先派生再使用——每个用途一把子密钥：

```python
from Crypto.Protocol.KDF import HKDF
from Crypto.Hash import SHA256
k_enc, k_mac = HKDF(master, 32, salt, SHA256, num_keys=2, context=b"session-7")
```

派生时给每个用途一个不同的标签（`context`/`info`，如 `"enc"`、`"mac"`、`"svc-a"`、`"svc-b"`），两个用途的子密钥在计算上独立，A 用途出事不再反哺 B 用途。这种"按用途分隔"叫**域分隔**，[[C12-数字签名|C12]] 的签名检查清单与 [[C15-实现漏洞与侧信道|C15]] 的防御清单都把它列为固定项。更省事的替代：直接用 AEAD（GCM 的 `encrypt_and_digest`），加密与认证在同一接口下完成，密钥安排由标准规定好（[[C06-分组模式攻击全集|C06]] 6.2 节）。

### 3.3 跨环境复用：测试密钥上生产

**错误写法**：开发、测试、生产共用一把密钥（常与"密钥写进配置文件"连体出现：配置随包发布，密钥就随包共享）。

**后果**：密钥的暴露面按环境数量倍增，而 weakest link 生效——测试环境人员杂、日志多、镜像外发，任何一个出口泄钥，生产等于泄钥。真实世界的对应事故发生在设备侧：2012 年的 "Mining your Ps and Qs" 研究扫描全网，发现数千台路由器与嵌入式设备因出厂烧录同一把密钥或首启熵不足，生成了共享素数的 RSA 密钥——==买一台设备，就能解密全部同类设备的流量==。

**正确写法**：每个环境独立生成密钥，测试密钥永不进生产；密钥不进版本库（`.gitignore` 覆盖 + 提交历史检查），已经进过历史的按已泄露处理，直接换钥。

## 4. 标签截断与生日界

### 4.1 截断标签的两本账

认证标签的完整值有 128 位（GCM/CMAC），工程上常被截短：省带宽（物联网每包省 12 字节）、省存储（数据库里的 token 字段）。截短后标签只剩 $t$ 位，安全性要按两本独立的账算：

$$P_{\text{在线伪造}}(v) = 1 - \left(1 - 2^{-t}\right)^{v} \approx v \cdot 2^{-t} \tag{19.1}$$

$$P_{\text{碰撞}}(q) \approx \frac{q^2}{2^{t+1}} \tag{19.2}$$

- 式 (19.1) 是**在线伪造**：攻击者对着验证接口逐个试标签，每次尝试是 $2^{-t}$ 的独立事件，试 $v$ 次的累计成功率如上；
- 式 (19.2) 是**生日碰撞**：同一密钥下合法签发 $q$ 条消息，标签值只有 $2^t$ 个可能，$q = 2^{t/2}$ 时两条消息共用同一标签的概率过半——这就是 [[C10-哈希进阶|C10]] 生日攻击的同一条公式，只是对象从摘要换成了标签。

==两本账都按 $t$ 的指数走：标签每砍 1 位，两本账的代价各掉一半；砍 8 位，掉 $2^8$ 倍==。对照表：

| 标签位数 $t$ | 在线伪造过半所需 $v$ | 碰撞过半所需 $q$ | 工程事实 |
| ---- | ---- | ---- | ---- |
| 16 | $2^{15}$ | $2^{8}$ | 仅供教学演示，无人实际使用 |
| 32 | $2^{31}$ | $2^{16}$ | NIST 允许的下限；只撑得起 $2^{16}$ 量级的消息量 |
| 64 | $2^{63}$ | $2^{32}$ | 内部系统偶见，需按消息量评估 |
| 96（GCM 默认） | $2^{95}$ | $2^{48}$ | 当前的常规选择 |
| 128 | $2^{127}$ | $2^{64}$ | 完整标签 |

### 4.2 32 位截断 GCM 标签的撞车

用消息量把式 (19.2) 顶到线上。靶子用正确的 GCM 用法（nonce 严格递增、不复用），只把标签截到 32 位（pycryptodome 允许的最短值），连续签发消息并记录已见标签：

```python
# tag_collide.py —— 32 位截断 GCM 标签的生日碰撞：撞点在 2^16 量级
from Crypto.Cipher import AES
from Crypto.Random import get_random_bytes

key = get_random_bytes(16)
TAG = 4                                    # 32 位截断（pycryptodome 允许的最短 GCM 标签）
CAP = 1 << 17                              # 搜索上限 2^17

seen = {}
coll = None
for i in range(CAP):
    nonce = i.to_bytes(12, "big")          # nonce 严格递增，不复用
    _, tag = AES.new(key, AES.MODE_GCM, nonce=nonce, mac_len=TAG).encrypt_and_digest(b"m%d" % i)
    if tag in seen:
        coll = (seen[tag], i, tag.hex())
        break
    seen[tag] = i

if coll:
    print("第 %d 条消息撞上第 %d 条：同标签 %s（标签值共 %d 个）" % (coll[0], coll[1], coll[2], 1 << 32))
    print("期望撞点 1.18·2^16 ≈ %d，本次落在 %d" % (int(1.18 * (1 << 16)), coll[1]))
else:
    print("2^17 内未撞出，属正常涨落，重跑一次")
print("近似公式 q^2/2^(t+1)：q=2^16 时 = %.2f（生日界 2^(t/2)）" % ((1 << 16) ** 2 / (2 * (1 << 32))))
print("对照：128 位完整标签下，2^16 条消息的碰撞概率约 2^16/2^127 ≈ 0")
```

```bash
python3 tag_collide.py
```

输出：

```
第 22728 条消息撞上第 42516 条：同标签 9387f33d（标签值共 4294967296 个）
期望撞点 1.18·2^16 ≈ 77332，本次落在 42516
近似公式 q^2/2^(t+1)：q=2^16 时 = 0.50（生日界 2^(t/2)）
对照：128 位完整标签下，2^16 条消息的碰撞概率约 2^16/2^127 ≈ 0
```

几万条消息后，两条不同的消息拿到了同一个 32 位标签。碰撞的具体后果按协议而定：标签被当唯一凭证用（去重表、防重放键）时，碰撞直接让两条消息混淆；更一般地，==碰撞出现意味着"每个标签 $2^{-32}$ 的伪造概率"这个承诺只在 $2^{16}$ 量级的消息量以内有效==——NIST SP 800-38D 允许 32 位标签，同时用伪造概率上界限制单密钥下的数据量，卡的就是这条生日线。

> [!note] 撞车演示必须建立在 GCM 用法正确之上
> 演示里 nonce 逐条递增，绝不复用：nonce 重用本身就是 [[C06-分组模式攻击全集|C06]] 6.2 节的另一种崩溃（认证钥 $H$ 直接现形，任意伪造），混进来就分不清"是标签太短的锅，还是 nonce 重用的锅"。截断标签的账，只对用法正确的 GCM 记。

### 4.3 截断标签的在线伪造

式 (19.1) 的在线伪造需要一个有反馈的验证接口（答 accept/reject 的 oracle）。用 16 位标签的教学靶把它跑通——HMAC-SHA256 截到 2 字节当标签，公式与 GCM 完全一致：

```python
# tag_forge16.py —— 截断标签在线伪造：v 次尝试成功率 1-(1-2^-t)^v
import hmac, hashlib
from Crypto.Random import get_random_bytes

key = get_random_bytes(16)

def mac16(msg):                            # 教学靶：HMAC-SHA256 截到 16 位
    return hmac.new(key, msg, hashlib.sha256).digest()[:2]

def server_verify(msg, tag):
    return hmac.compare_digest(mac16(msg), tag)

msg = b"transfer 100 to alice"
bad = b"transfer 999 to eve"               # 攻击者想伪造的指令
good_tag = mac16(bad)                      # 真标签未知于攻击者，这里仅供核对

found, tries = None, 0
for g in range(1 << 16):                   # 顺序扫全部 2^16 个候选标签
    tries += 1
    if server_verify(bad, g.to_bytes(2, "big")):
        found = g.to_bytes(2, "big")
        break

print("伪造在第 %d 次尝试被接受，标签 %s（真标签 %s）" % (tries, found.hex(), good_tag.hex()))
print("t=16 时该次数的累计成功率 1-(1-2^-t)^v: %.3f" % (1 - (1 - 1 / (1 << 16)) ** tries))
for t in (32, 96, 128):
    print("同栏 2^16 次尝试打 %d 位标签的累计成功率: %.2e" % (t, (1 << 16) / 2 ** t))
```

```bash
python3 tag_forge16.py
```

输出：

```
伪造在第 27911 次尝试被接受，标签 6d06（真标签 6d06）
t=16 时该次数的累计成功率 1-(1-2^-t)^v: 0.347
同栏 2^16 次尝试打 32 位标签的累计成功率: 1.53e-05
同栏 2^16 次尝试打 96 位标签的累计成功率: 8.27e-25
同栏 2^16 次尝试打 128 位标签的累计成功率: 1.93e-34
```

几万次尝试撞出一个能通过验证的假标签，累计成功率与式 (19.1) 对上。同样的尝试量打到 32 位标签，成功率掉到十万分之一量级——这不是"安全了"，是"本地脚本跑不动"：$2^{31}$ 次尝试的期望量对有稳定验证接口的攻击者仍是可观的预算。完整标签（96/128 位）下同量级尝试的成功率接近零，这就是默认标签长度的意义。

> [!info]- 在线伪造与离线伪造的差别
> 式 (19.1) 的前提是每次尝试都有 accept/reject 反馈（在线）。没有验证接口的离线伪造，攻击者只有一次命中机会，成功率就是 $2^{-t}$——[[C10-哈希进阶|C10]] 的 48 位截断 SHA-1 碰撞属于离线碰撞那一类，靠的是式 (19.2) 的生日结构加本地暴力。两类攻击对协议设计的要求不同：防在线要限速与告警（验证失败计数），防离线只能加长标签。

### 4.4 短摘要当签名是同一件事

把签名值截短（`md5(内容)[:8]` 一类的接口）、用 32 位哈希当校验码，走的是同两张账：短摘要的碰撞过半点按式 (19.2) 收缩。[[C10-哈希进阶|C10]] 2.4 节算过的"48 位 SHA-1 碰撞"就是 $t=48$ 时代价 $2^{24}$ 量级的直接换算；签名值截到 32 位，$2^{16}$ 量级的候选就能撞出两条同签名的消息，伪造与冒领随之而来。判断口诀与 4.1 相同：==摘要/标签被用了几位，就按几位算生日界，与底层算法多强无关==。

## 5. legacy 算法的现状陷阱

### 5.1 DES：没被"攻破"的弱密钥也在账上

DES 的 8 字节密钥里每字节最低位是奇偶校验位，实际密钥 56 位；56 位里有 4 个特殊值，密钥扩展的 16 轮子钥全部相同，加密运算退化为自反运算。用 pycryptodome 对四个弱密钥各跑一遍：

```python
# des_weak.py —— DES 四个弱密钥：E(k,E(k,m))=m 且 E(k)=D(k)
from Crypto.Cipher import DES

msg = b"DESWEAK!"   # 8 字节一块

for name, k in [
    ("0101010101010101", bytes.fromhex("0101010101010101")),
    ("fefefefefefefefe", bytes.fromhex("FEFEFEFEFEFEFEFE")),
    ("e0e0e0e0f1f1f1f1", bytes.fromhex("E0E0E0E0F1F1F1F1")),
    ("1f1f1f1f0e0e0e0e", bytes.fromhex("1F1F1F1F0E0E0E0E")),
]:
    E = DES.new(k, DES.MODE_ECB)
    c1 = E.encrypt(msg)
    c2 = DES.new(k, DES.MODE_ECB).encrypt(c1)      # 连续加密两次
    d1 = DES.new(k, DES.MODE_ECB).decrypt(msg)     # 解密
    print("%s  E(E(m))==m: %-5s  E(m)==D(m): %-5s  E(m)=%s"
          % (name, c2 == msg, c1 == d1, c1.hex()))

# 对照：普通密钥两次加密不回原点
k = bytes.fromhex("0E329232EA6D0D73")
E = DES.new(k, DES.MODE_ECB)
c1, c2 = E.encrypt(msg), DES.new(k, DES.MODE_ECB).encrypt(E.encrypt(msg))
print("普通密钥 0E329232EA6D0D73  E(E(m))==m: %s" % (c2 == msg))
```

```bash
python3 des_weak.py
```

输出：

```
0101010101010101  E(E(m))==m: True   E(m)==D(m): True   E(m)=94e4ea71c8dad14a
fefefefefefefefe  E(E(m))==m: True   E(m)==D(m): True   E(m)=f7935fb2c5992ddb
e0e0e0e0f1f1f1f1  E(E(m))==m: True   E(m)==D(m): True   E(m)=b55231d36c5938e7
1f1f1f1f0e0e0e0e  E(E(m))==m: True   E(m)==D(m): True   E(m)=f5acc571d9e22553
普通密钥 0E329232EA6D0D73  E(E(m))==m: False
```

弱密钥下 $E_k = D_k$ 且 $E_k$ 自反：连续加密两次回到明文，"双重加密"在弱密钥上等价于单层。它还连带一类设计错误——"为了安全把 DES 跑两遍"的双重加密方案，遇到弱密钥或半弱密钥对（6 对半弱密钥满足 $E_{k_1} = D_{k_2}$，两把连用等于没加密）整体失效。这套演示同时说明了审计的另一个动作：==弱性不一定来自"算法被攻破"，可以来自算法规范内部的结构点==，密钥黑名单（DES 的 4 弱 + 6 对半弱、AES 无此类点）是生成密钥时的固定检查项。

DES 的其余两笔账一句话各记：56 位密钥的暴力下界 1999 年被专用硬件压到 22.5 小时（EFF Deep Crack 与 distributed.net 联合）；3DES 把密钥加到 112/168 位，但 64 位块长的生日界没变——单密钥下 $2^{32}$ 块（约 32 GB 流量）后碰撞泄漏（Sweet32，2016），NIST 已在 2023 年后停止 3DES 的加密用途许可（SP 800-131A）。MD5 的证书签名链是"签在摘要上"的对应事故：2008 年研究者用 MD5 碰撞伪造出合法的 CA 证书，2012 年披露的 Flame 蠕虫已用同一技术伪造微软代码签名证书——[[C10-哈希进阶|C10]] 3 节的碰撞构造落到信任链上就是这个形态。RC4 的死因见 [[C03-序列密码与LFSR|C03]]。

### 5.2 "没被攻破"不是"还能用"

审计里最常出现的误判形态："MD5 确实能碰撞，但我们只是拿它当校验和" / "3DES 没被攻破，还能撑几年"。判断标准不是"算法是否被攻破"，而是三本账：

| 算法 | 亏的是哪本账 | 新项目 | 遗留数据 |
| ---- | ---- | ---- | ---- |
| DES | 56 位暴力下界；弱密钥结构点 | 禁用 | 解密后按 AES 重加密 |
| 3DES | 64 位块生日界（Sweet32）；密钥有效强度约 112 位 | 禁用（NIST 2023 起停止加密用途） | 限期迁移 |
| RC4 | 密钥流统计偏差（RFC 7465 禁用） | 禁用 | 同 DES |
| MD5 | 碰撞实用化（前缀碰撞、chosen-prefix） | 禁用于任何认证/签名场景 | 校验和用途限期换 SHA-256 |
| SHA-1 | 选择前缀碰撞实用化（shattered，2017） | 签名/证书禁用 | 内容寻址等非对抗场景可观察使用 |
| RSA-1024 | 密钥强度余量贴近公开算力上限 | 新项目 3072 位起 | 迁移 3072/4096 |

两句话概括：==亏块长的账（DES/3DES）与亏结构的账（弱密钥、RC4 偏差）不能靠"加长密钥"补==；==亏余量的账（RSA-1024）按算力增长动态复查，安全余量要按"十年后的算力"估，不是今天的==。量子计算对这个表的影响只在最后一行——[[C18-后量子密码|C18]] 的结论是 Shor 动公钥体系、Grover 对对称只折半，本表的对称侧判断不变。

## 6. 协议组合的边界遗漏

算法、密钥、模式都对，协议字段少一个，边界就漏。三个最小靶各堵一个漏。

### 6.1 无序号字段：重放

**错误写法**：一条"加密即令牌"的支付指令协议——令牌 = CTR 加密的指令，服务端解密成功就执行，不查任何序号与时效：

```python
# replay_server.py —— 自造最小"加密协议"靶：token = AES-CTR(k, 指令)，无序号无时效
from Crypto.Cipher import AES
from Crypto.Random import get_random_bytes
from http.server import HTTPServer, BaseHTTPRequestHandler
from urllib.parse import parse_qs

k = get_random_bytes(16)
balance = {"alice": 1000}

def issue_token(cmd: str) -> str:
    """合法客户端：加密即令牌（模拟被离线抓包拿到的东西）"""
    n = get_random_bytes(8)
    c = AES.new(k, AES.MODE_CTR, nonce=n).encrypt(cmd.encode())
    return (n + c).hex()

def apply_token(token_hex: str) -> str:
    """服务端：解密成功就执行，不查任何序号与时效"""
    raw = bytes.fromhex(token_hex)
    try:
        cmd = AES.new(k, AES.MODE_CTR, nonce=raw[:8]).decrypt(raw[8:]).decode()
    except Exception:
        return "bad token"
    if cmd.startswith("PAY "):
        _, who, amt = cmd.split()
        balance[who] = balance.get(who, 0) - int(amt)
        return "ok %s balance=%d" % (who, balance[who])
    return "unknown cmd"

class H(BaseHTTPRequestHandler):
    def log_message(self, *a):
        pass

    def do_GET(self):
        q = parse_qs(self.path.split("?", 1)[1]) if "?" in self.path else {}
        if "issue" in q:
            body = issue_token("PAY alice " + q["issue"][0]).encode()
            self.send_response(200)
        elif "token" in q:
            body = apply_token(q["token"][0]).encode()
            self.send_response(200)
        else:
            body, code = b"usage: ?issue=AMT | ?token=HEX", 400
            self.send_response(code)
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)

if __name__ == "__main__":
    HTTPServer(("127.0.0.1", 7901), H).serve_forever()
```

起靶，以合法客户端身份领一枚令牌：

```bash
python3 replay_server.py &
curl -s --noproxy '*' 'http://127.0.0.1:7901/?issue=100'
```

输出：

```
f0e3688a339ee859917c66f5ada0180e89e34ccf24
```

攻击者只需要原样重发——令牌一字节不改：

```bash
curl -s --noproxy '*' 'http://127.0.0.1:7901/?token=f0e3688a339ee859917c66f5ada0180e89e34ccf24'
curl -s --noproxy '*' 'http://127.0.0.1:7901/?token=f0e3688a339ee859917c66f5ada0180e89e34ccf24'
curl -s --noproxy '*' 'http://127.0.0.1:7901/?token=f0e3688a339ee859917c66f5ada0180e89e34ccf24'
```

输出：

```
ok alice balance=900
ok alice balance=800
ok alice balance=700
```

**后果**：同一枚令牌执行了三次，余额从 1000 扣到 700。加密保的是机密性（第三方读不出指令内容），认证保的是完整性（第三方改不了指令内容），==新鲜性是第三本独立的账==：令牌里没有任何"这条指令只许执行一次"的信息，三本账少一本，协议就在那一本上塌。重放不需要任何密码学攻击，只需要复制粘贴——这也是 [[W13-逻辑与认证漏洞|W13]] 里"凭据可重放"类逻辑洞的密码学侧同构。

**正确写法**：令牌里带一个一次性的 nonce（或单调计数器 + 时间窗），并把它纳入认证范围；服务端记账，同一 nonce 只受理一次：

```python
# replay_fix.py —— 正确写法：nonce 入账 + 服务端记住用过的 nonce，重放被拒
from Crypto.Cipher import AES
from Crypto.Random import get_random_bytes

k = get_random_bytes(16)
seen_nonces = set()
balance = {"alice": 1000}

def issue_token(cmd):
    n = get_random_bytes(8)
    return (n + AES.new(k, AES.MODE_CTR, nonce=n).encrypt(cmd.encode())).hex()

def apply_token(token_hex):
    raw = bytes.fromhex(token_hex)
    n, body = raw[:8], raw[8:]
    if n in seen_nonces:                       # 同一 nonce 只受理一次
        return "replayed, rejected"
    seen_nonces.add(n)
    cmd = AES.new(k, AES.MODE_CTR, nonce=n).decrypt(body).decode()
    _, who, amt = cmd.split()
    balance[who] = balance.get(who, 0) - int(amt)
    return "ok %s balance=%d" % (who, balance[who])

tok = issue_token("PAY alice 100")
for i in range(1, 4):
    print("第 %d 次提交同一令牌:" % i, apply_token(tok))
```

```bash
python3 replay_fix.py
```

输出：

```
第 1 次提交同一令牌: ok alice balance=900
第 2 次提交同一令牌: replayed, rejected
第 3 次提交同一令牌: replayed, rejected
```

> [!info]- 去重状态的工程账
> `seen_nonces` 集合会无限增长，工程上换成滑动窗口：只记住最近 $T$ 秒（或最近 $N$ 条）的 nonce，同时拒绝带"窗口外时间戳"的令牌——两道闸合起来覆盖全部时间轴。[[C17-协议密码学|C17]] 5 节 TLS 0-RTT 的重放窗口是同一个设计在标准协议里的形态。

### 6.2 无降级保护：协商被削

**错误写法**：版本/算法协商取"双方都支持的最左一个"，但收到的候选列表不在认证范围内。最小演示把协商抽成一行函数：

```python
# downgrade.py —— 协商结果没有被认证覆盖：中间人删条目，双方"自愿"落到弱算法
CLIENT_HELLO = ["TLS_AES_256_GCM", "TLS_AES_128_GCM", "DES_CBC3", "RC4_128"]

def handshake(client_list, peer_list=None, mitm_strip=None):
    """服务端选双方都支持的最左一个；常规实现不把收到的列表纳入认证"""
    offered = client_list
    if mitm_strip:                              # 中间人：把强算法从列表里删掉再转给服务端
        offered = [c for c in offered if c not in mitm_strip]
    peer = peer_list if peer_list else offered
    common = [c for c in offered if c in peer]
    return common[0] if common else None

print("无中间人，双方协商:", handshake(CLIENT_HELLO))
print("中间人删掉两个 AES 条目后:", handshake(CLIENT_HELLO, mitm_strip={"TLS_AES_256_GCM", "TLS_AES_128_GCM"}))
print("服务端视角: 客户端'只支持'弱算法, 协商全程没有一步能发现列表被动过")
```

```bash
python3 downgrade.py
```

输出：

```
无中间人，双方协商: TLS_AES_256_GCM
中间人删掉两个 AES 条目后: DES_CBC3
服务端视角: 客户端'只支持'弱算法, 协商全程没有一步能发现列表被动过
```

**后果**：协商落在双方"都支持"的弱算法上，而支持弱算法这一点（为了兼容旧客户端保留在列表里）是双方自己声明过的——==降级攻击不需要攻破任何算法，只需要删掉列表里的强项==。[[C17-协议密码学|C17]] 第 4 节大案表里的降级族（Logjam/FREAK/POODLE）根因全是这一条：协商参数没有被握手认证覆盖。

**正确写法**：协商结果必须纳入认证——TLS 1.3 把全部握手消息（含候选列表）纳入 `Finished` 的 MAC，中间人改一个字节握手就断；应用层自定义协议至少做到：候选列表进 MAC/签名，且服务端对"客户端声称只支持弱算法"的会话记录告警。

### 6.3 无长度检查

一句话记两层的账。解析层：长度字段缺失或未校验，缓冲区溢出归 [[W04-SQL注入|W04]]–[[W11-XXE|W11]] 的注入与解析家族管，不是密码学洞。密码层：==消息格式里的每个字段——包括长度字段本身——都必须落在认证范围内==。认证不覆盖长度时，攻击者可以截断尾部（CBC 密文砍掉尾块，明文静默变短）或拼接两条消息（长度字段仍声明旧值，解析器照常吞下）；[[C06-分组模式攻击全集|C06]] 的字节翻转与 [[C15-实现漏洞与侧信道|C15]] 的 MAC-then-encrypt 结构病是这类"认证范围不全"的两个已展开形态。

### 7.2 30 分钟审计动作序列

固定次序，每步有明确产物：

1. **分清原语与组合（3 分钟）**：读附件，列出用了哪些算法、什么模式、什么编码。产物：一张算法清单。入口按 [[C01-密码学导论与工具链|C01]] 的工作流模板；
2. **生成层（5 分钟）**：随机源与参数按 [[C04-随机数攻防|C04]]、[[C07-RSA攻击I|C07]] 的清单过。产物：命中/不命中记录；
3. **存储层（5 分钟）**：strings/grep 扫全部交付物（二进制、前端、配置、仓库历史），命中的密钥记录偏移与形态。产物：密钥来源表；
4. **使用层（5 分钟）**：画"密钥-用途"对照表，数每个密钥的用途数与 nonce/IV 来源。产物：对照表，混用行标红；
5. **协议层（5 分钟）**：按 [[C17-协议密码学|C17]] 第 6 节的六项清单（认证覆盖/身份绑定/公钥校验/nonce/降级/重放）过一遍字段。产物：字段覆盖表；
6. **实现层（5 分钟）**：按 [[C15-实现漏洞与侧信道|C15]] 防御清单的六项（比较/失败路径/库/组合顺序/随机数/密钥分支）过一遍。产物：实现弱点记录；
7. **定型（2 分钟）**：对命中项写最小 PoC——能复现的写成"错误写法 → 后果 → 正确写法"三段，不能复现的标注原因。产物：可交付的审计结论。

> [!note] "不命中"也是产物
> 每一步的产物都是"命中/不命中"的记录。审计的价值一半在找到洞，另一半在==排除==：五层全不命中的系统，结论是"该范围内的工程面未发现弱点"，这份记录本身可以进交付物。做题时同理——清单过完全不命中，说明弱点在数学层（[[C07-RSA攻击I|C07]]–[[C13-格密码与LLL|C13]] 的攻击面），换决策表重进。

## 8. 常见问题

| 现象 | 原因与解决 |
| ---- | ---- |
| strings 扫不到密钥，断定没有硬编码 | 密钥异或混淆或运行时组装，不进 `.rodata`：strings 只是初筛。看反汇编里"逐字节异或同一常数"的短循环，动态调试断在密钥参与运算处读内存（[[#2.1 密钥写进交付物\|2.1]]） |
| `openssl des-ecb` 报 unsupported，弱密钥演示做不了 | OpenSSL 3.x 默认 provider 不带 DES：加 `-provider legacy -provider default` 才能跑；且 EVP 路径不查弱密钥表，弱密钥照样出密文。演示直接用 pycryptodome 的 `Crypto.Cipher.DES` 最省事（[[#5.1 DES：没被"攻破"的弱密钥也在账上\|5.1]]） |
| 弱密钥表与自己构造的对不上 | 四个弱密钥里两个左右半不同（`e0e0e0e0f1f1f1f1`、`1f1f1f1f0e0e0e0e`），`e0`×8、`1f`×8 不是弱密钥；DES 每字节最低位是奇偶位，不参与密钥（[[#5.1 DES：没被"攻破"的弱密钥也在账上\|5.1]]） |
| 撞车演示想全程复用同一个 nonce 省事 | nonce 重用是 [[C06-分组模式攻击全集\|C06]] 6.2 节的另一种崩溃（认证钥现形、任意伪造），会把"标签太短"与"nonce 重用"两个锅混在一起：nonce 严格递增，账才分得清（[[#4.2 32 位截断 GCM 标签的撞车\|4.2]]） |
| GCM 想截 16 位标签，报 `Parameter 'mac_len' must be in the range 4..16` | pycryptodome 的硬下限是 4 字节；更短的截断教学靶用 HMAC-SHA256 自截（[[#4.3 截断标签的在线伪造\|4.3]]） |
| 截断标签伪造脚本扫完 $2^{16}$ 次还没中 | 单次尝试是 $2^{-t}$ 的独立事件：$t=16$ 时期望 $2^{15}$ 次、单轮未中是正常涨落；$t=32$ 期望 $2^{31}$ 次，本地脚本跑不动，量级看 4.1 的对照表（[[#4.3 截断标签的在线伪造\|4.3]]） |
| 重放靶打不出"执行两次" | 服务端自己带了状态（框架级去重/幂等键）或令牌里混入了时间戳：靶子的接收端要无状态化，验证只看密文本身，重放才成立（[[#6.1 无序号字段：重放\|6.1]]） |
| sign 接口声称"只签业务数据"，盲化桥照样打通 | 服务端审的是格式不是数值：$c \cdot r^e \bmod n$ 就是一个合法形状的"业务数"。数值层防护要么限定消息空间（域内拒绝非预期值），要么换带填充的签名方案（[[#3.1 一把 RSA 既加密又签名\|3.1]]） |
| 3DES 换了强密钥还是被撞生日 | 块长的账与密钥无关：64 位块的碰撞界按加密块数算（约 $2^{32}$ 块），换钥不掉这条线，只能换块长 128 位的算法（[[#5.2 "没被攻破"不是"还能用"\|5.2]]） |
| nonce 用 `random.randint` 生成，觉得统计上够随机 | MT19937 可预测（[[C04-随机数攻防\|C04]]）；nonce 要的是"不可预测"或"严格不重复"其中之一，用 `os.urandom` 或单调计数器，不从 `random` 取（[[#6.1 无序号字段：重放\|6.1]]） |
| 降级演示里服务端"自愿"选了弱算法，觉得是服务端的锅 | 服务端按声明列表选算法没有错：错在列表可被中间人改而不被发现。修复动作在认证覆盖，不在"服务端更强势"（[[#6.2 无降级保护：协商被削\|6.2]]） |
| 审计清单过完全不命中 | 工程面排除完毕，弱点转数学层：按 [[C07-RSA攻击I\|C07]] 的"特征 → 攻击"决策表重进，或回 [[C10-哈希进阶\|C10]]/[[C13-格密码与LLL\|C13]] 找对应攻击面（[[#7.2 30 分钟审计动作序列\|7.2]]） |
